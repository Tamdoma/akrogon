The one mental model: treat every issue like a package moving through a careful workshop. The package contains the intent. Different stations clarify it, plan it, build it, inspect it, and finally ship it. The state label tells everyone which station comes next.

1. Why this system exists

Before tools and files, start with the human problem: software work becomes unsafe when intent is vague, decisions are hidden, building and checking blur together, or unfinished work touches the main branch.

Without a lifecycle

Memory becomes the plan

The original request gets reinterpreted as work moves between people and agents.

Without independence

One opinion becomes “agreement”

A second reviewer can accidentally echo the first instead of finding a genuinely different risk.

Without gates

Done becomes a feeling

Code may be merged before the contract, tests, cleanup, and operator approval are complete.

The smallest thing moving through the system

It is not merely a code change. It is an issue contract: a written bundle of intent, boundaries, decisions, implementation steps, evidence, and current state.

IntentWhat outcome matters?
→
ContractWhat exactly will be done?
→
EvidenceHow do we know it worked?

Six first-principles rules

  • Write intent down before building.
  • Get independent views before agreement.
  • Keep one shared plan as the authority.
  • Build away from the main checkout.
  • Let a separate pass inspect the result.
  • Require a human gate before the final merge.

What the lifecycle is not

  • It is not a chat transcript archive.
  • It is not eight unrelated commands.
  • It is not a substitute for operator judgment.
  • It is not permission to expand an issue silently.
  • It is not “merge when the agent feels ready.”

2. The whole system at a glance

The skills are stations on one route. Some stations create durable artifacts. Some only help people understand. Three explicit operator approvals prevent the system from quietly deciding too much on its own.

3. The components

The system separates “what we know,” “what comes next,” and “where risky work happens.” That separation is what makes handoffs reliable.

Repository setup

issues/config.yaml

The repository’s issue-lifecycle address book. It tells skills where issue files, helper scripts, and worktrees live. It may also point to trusted grounding documents and Discord routing.

Active work

issues/open/

The active working set. It contains portable seed reports, real issue folders, or a series made from several related issue folders.

Shared authority

plan.md

The judge file for a phase. In planning/ it records the agreed decision. In implementation/ it records the agreed execution contract.

Independent views

claude.md and codex.md

Separate consultant positions. Each agent first thinks independently, then joins the required rebuttal rounds: two during planning and one during implementation planning. These files are evidence for synthesis—not competing final plans.

Next durable step

state.yaml

The lifecycle ledger. Its phase does not describe mood or percent complete. It states the next durable action that is allowed.

Safety lane

issues/worktrees/

Isolated checkouts for implementation. Code changes happen here so unfinished work does not disturb the primary checkout or another issue.

Mechanical rails

issues/.scripts/

Repository-local helpers that create worktrees, read and transition state, commit owned changes, merge safely, audit references, and clean up. Operators usually invoke the skills; the skills use these rails.

Reality checks

Grounding anchors

Configured docs provide vocabulary; live code provides behavior truth. Plans record which surfaces were checked and any doc/code tension so later agents do not build on an unverified assumption.

Two places, two responsibilities

Primary checkout = control room

Consult plans, consultant records, approvals, and authoritative lifecycle state are controlled here.

⇄

Issue worktree = workshop

Implementation code, inspection, fixes, and active review addenda are handled here while work is prepared for merge.

Do not use the worktree’s copied state.yaml as authority. It is a snapshot. The primary checkout’s state ledger decides which lifecycle action is allowed.

4. Every skill, one by one

Each skill has one job. The cleanest operator habit is to name the issue and the skill, then let the skill enforce its own entry and exit gates.

1

init-issues

Plain meaning
Install the issue workshop into a repository.
Use it when
The repo does not yet have issues/config.yaml, lifecycle scripts, or the managed worktree area.
What it does
Proposes one config, waits for confirmation, adds missing folders and scripts, adds the worktree ignore rule, then self-tests the setup.
What it protects
It will not overwrite a divergent config or silently replace modified lifecycle scripts.
Exit
Initialized, already initialized with no changes, or drift detected.
2

seed-issue

Plain meaning
Turn a messy report into a portable problem statement.
Use it when
You know what happened and what should have happened, but you are not ready for full planning.
What it does
Separates the shared system failure from incidental local evidence, sharpens unclear points, and writes one small Markdown seed. If the problem is only a one-off local mistake, it explains why no systemic seed should be created.
What it does not do
It does not create the full issue folder, pick an implementation, or change lifecycle state.
Exit
One portable report ready for consult-issue.
3

explain-issue

Plain meaning
Translate issue machinery into a beginner-safe mental model.
Use it when
An operator needs the “why,” the current flow, the proposed change, or a disagreement explained plainly.
What it does
Reads the canonical brief, grounds the explanation in the real repo, and uses one clear analogy plus a compact flow sketch.
What it never does
No planning, code edits, review verdict, merge, or lifecycle transition.
Exit
Understanding—not approval.
4

consult-issue

Plain meaning
Use two independent consultants, structured rebuttal rounds, and one shared synthesis to create a trustworthy contract.
Use it when
Creating/importing an issue, planning the decision, planning execution, rebutting, synthesizing, or recording phase approval.
What it owns
Both the planning phase and the implementation-planning phase.
What it can produce
One simple issue, or a complex issue series made from several real leaf issues when the work can be separated safely.
Key rule
The first consultant must not read the peer’s position before writing its own.
Exit
A shared plan awaiting approval, or an approved issue ready for the next phase.
5

implement-issue

Plain meaning
Execute the approved implementation contract.
Use it when
The authoritative state is I-ready.
What it does
Creates or confirms an isolated worktree, edits the real target surfaces, runs planned verification, performs a quality self-check, and requires an extra QA pass.
What it follows
The implementation plan, including any active review-fix checklist from an earlier check.
Exit
Committed work in the issue branch and state advanced to C-ready.
6

check-issue

Plain meaning
Independently compare the delivered work with the promised contract.
Use it when
The state is C-ready or the issue has returned to C-fix.
What it looks for
Missing requirements, regressions, overreach, weak verification, needless complexity, grounding drift, and quality evidence. Measured quality advisories remain non-blocking unless the operator explicitly promotes one.
What it writes
Its own named review subsection and concrete fix checklist inside the implementation plan.
Exit
C-fix if repairs are required, otherwise merge-ready while still awaiting explicit operator approval.
7

merge-issue

Plain meaning
Safely land an approved issue and remove its temporary machinery.
Use it when
A separate operator approval has advanced the state to D-merge.
What it does
Normalizes the branch against main, audits references, merges with file-aware conflict rules, pushes, updates needed docs, cleans the worktree and branch, and retires issue artifacts at the right time.
Important boundary
It must run from the primary checkout—not from inside the feature worktree.
Exit
Merged, pushed if available, cleaned, and handed to broadcast by default.
8

broadcast-issue

Plain meaning
Tell the audience what changed without dumping implementation detail.
Use it when
Posting issue completion, merge summaries, release notes, framework updates, or session updates to Discord.
What it sends
One short summary plus a small list of plain-language changes.
Safety rule
Preview first. Routing names live in repository config; secret webhook values stay outside git.
Relationship to merge
merge-issue discovers and calls it by default unless the operator requests a quiet merge.

The consult cycle: how two views become one plan

consult-issue is intentionally repeated. It is a conversation recorded in files, not a one-shot vote. Planning uses two rebuttal rounds; implementation planning uses one.

Planning: two rebuttal rounds

ClaudeIndependent view
＋
CodexIndependent view
→
Round 1Challenge the first positions
→
Round 2Answer remaining disagreements
→
SynthesisRewrite plan.md
◆
OperatorApprove phase

Implementation planning: one rebuttal round

ClaudeIndependent execution view
＋
CodexIndependent execution view
→
Round 1Challenge the execution details
→
SynthesisRewrite plan.md
◆
OperatorApprove execution

Why independent first?

If the second consultant reads the first answer too early, it may anchor on that answer. Separation creates two real attempts at the problem.

Why two rounds in planning?

The first round challenges the original positions. The second lets both sides address what survived that challenge before the direction is settled.

Why synthesis?

Operators should not have to merge two essays mentally. Synthesis judges both views and rewrites plan.md as one current contract.

Why one round in implementation?

The direction is already settled. One round is enough to challenge execution details without reopening the planning debate.

Optional planning grill: when a new planning brief is materially fuzzy, ask the creating consultant to “grill the brief first.” It asks focused questions in batches, sharpens the shared brief, and stops before writing a position. Claude and Codex then begin their independent passes from the same improved starting point.

5. Operator runbook: start to finish

This is the normal happy path for one issue. You may enter later if the repository is already initialized or the issue already exists.

  1. Initialize once per repository

    Run init-issues. Review the proposed config as one block. Confirm it only when the locations, grounding sources, and broadcast routing names are right.

    “Run init-issues for this repository.”

  2. Capture the problem

    Use seed-issue when the report is still rough or needs to travel. Describe what happened, what should have happened, and which promise was broken. For a clear new issue, you can create it directly with consult-issue.

    “Seed this issue: [symptom, expected result, violated intent].”

  3. Create or import the issue

    Run consult-issue against the request or seed. It decides whether the work should remain one simple issue or become a complex series of independent leaf issues. It then creates the planning files and starts the first independent planning position.

    “Use consult-issue to import issues/open/example.md.”

  4. Complete planning consultation

    Have both Claude and Codex write independent planning positions. Complete two rebuttal rounds so each side can challenge the initial positions and then address the disagreements that remain. Finally ask one agent to synthesize planning/plan.md.

    “Synthesize the planning phase after both rebuttal rounds are complete.”

  5. Approve the planning decision

    Read the synthesis walkthrough. If the scope, outcome, trade-offs, and acceptance criteria are right, explicitly approve moving into implementation planning. This opens I-draft.

    “I approve the planning synthesis. Begin implementation planning.”

  6. Complete implementation consultation

    Have both agents write independent execution positions, complete one rebuttal round, then synthesize. This phase focuses on execution order, target surfaces, regression checks, risks, and verification.

    “Run the implementation consult pass for this issue.”

  7. Approve execution readiness

    Approve the synthesized implementation plan only when another agent could execute it without inventing missing decisions. The issue then becomes I-ready.

    “I approve the implementation synthesis. Mark the issue execution-ready.”

  8. Build in the isolated worktree

    Run implement-issue. The skill follows the plan, performs verification and quality self-checks, gets an additional QA pass, commits the worktree changes, and advances to C-ready.

    “Run implement-issue for [issue path].”

  9. Review independently

    Run check-issue, ideally in the other agent. If required fixes exist, the issue enters C-fix. Run implement-issue to repair the shared checklist, then run check-issue again.

    “Run check-issue against the completed implementation.”

  10. Approve merge readiness separately

    A clean check reports “merge-ready, awaiting operator approval” but stays in checking. Explicitly approve the move to D-merge. This approval prepares durable deliverables; it does not perform the merge.

    “I approve D-merge for this reviewed issue.”

  11. Merge, clean up, and notify

    Run merge-issue from the primary checkout. It merges safely, pushes if available, updates needed documentation, removes temporary worktree/branch state, retires the completed issue artifacts, and calls the broadcast skill by default.

    “Run merge-issue for [issue or worktree].”

6. How to read lifecycle state

State is a traffic signal, not a progress score. Read it as: “What durable step is next?” The issue folder name stays stable; state.yaml is the authority.

StatePlain meaningNormal next action
P-draftPlanning consultation is incomplete.Finish independent planning positions and both rebuttal rounds.
P-synthPlanning views are complete; a shared decision and approval are next.Synthesize, then operator approves implementation planning.
I-draftImplementation consultation is incomplete.Finish independent execution positions and one rebuttal round.
I-synthImplementation views are complete; a shared execution plan and approval are next.Synthesize, then operator approves execution.
I-readyThe execution contract is approved.Run implement-issue.
C-readyImplementation is ready for checking, or a re-check is clean.Run check-issue; if clean, await merge approval.
C-fixReview found required repairs.Run implement-issue on the review checklist, then re-check.
D-mergeThe operator has approved the reviewed work for merge.Run merge-issue.
The review loop is intentional: C-ready → C-fix → C-ready. A failed check does not send the issue back to planning or pretend implementation never happened. The review addendum becomes the repair contract.

7. How Pi, Claude, and Codex fit

The folders are three installations of the same operator playbook—not three separate lifecycles. The duplication lets the same named skill behave consistently wherever the operator invokes it.

Shared behavior

Most skills are role-neutral

init, seed, explain, merge, and the lifecycle concepts are effectively the same across homes. Sender commands point to the local home that owns the skill.

Role ownership

Consult and check name the actor

Claude writes claude.md and its own review subsection. Codex writes codex.md and its own review subsection. The Pi copies currently mirror the Codex-role wording for those role-sensitive skills.

Independence rule

Same brief, separate first pass

Both agents receive the same canonical brief. Neither should read the peer’s first position until both independent positions exist.

Shared result

One plan, not two winners

The consultant files remain attributed. The synthesized plan.md becomes the shared authority regardless of which agent performed synthesis.

Recommended division of labor

Planning

Use both Claude and Codex. Either may go first; keep the first passes independent.

Implementation

One agent implements. Its workflow includes an extra QA pass before sign-off.

Checking

Prefer the other main agent for fresh eyes. Each checker owns only its named subsection.

Operator remains the governor. Agents can draft, challenge, synthesize, build, and inspect. Only the operator approves the major phase transitions and the final move to D-merge.

8. Simple and complex issues

consult-issue can produce two shapes. A simple issue follows one lifecycle from planning to merge. A complex issue becomes a series containing several real leaf issues that can be planned, accepted, and often executed separately.

Simple issue

One connected unit of work

Use this when the parts depend on each other, touch the same behavior, or only make sense when accepted together. It has one issue root, one lifecycle state, and one implementation worktree.

Complex issue

A coordinated series of leaf issues

Use this when the request naturally separates into independently plannable and testable pieces. Each leaf follows the normal lifecycle while the series map records order and dependencies.

Why split a complex issue? Independent leaves can be assigned to different agents or operators at the same time. Safe parallel work shortens the overall execution time—but forcing coupled work to run in parallel creates conflicts and unreliable results.
Use a series when
  • Leaves touch separate files or owned surfaces.
  • One leaf can run without another leaf’s runtime result.
  • Each leaf can pass acceptance on its own.
  • Any dependency barrier can be stated plainly.
Keep one issue when
  • The work is merely long.
  • Every part must ship together to be useful.
  • The parts edit the same behavior in coupled ways.
  • Acceptance only makes sense for the complete bundle.

How operators read a series

SERIES.md is the map. The series master state.yaml holds each leaf’s lifecycle phase. Every leaf begins with a global order number followed by an execution marker:

01p-...

The number gives global order; p means parallelizable. Once its dependency barrier is satisfied, it may run at the same time as sibling p leaves. This is where a complex issue can execute faster.

03s-...

The number gives global order; s means sequential. It must run after the prior numbered leaf or named dependency because its result is coupled to earlier work.

Not everything can be marked p. Parallel leaves must have separate file ownership, independent runtime behavior, and independent acceptance. If any of those conditions fail, use s or keep the work as one simple issue.
Every leaf follows the normal lifecycle. It gets its own planning, implementation plan, state, worktree, check, and merge. The series container is retired only after all leaves are terminal.

9. Worked example: one package end to end

Suppose users report: “Search crashes when a quoted phrase is entered. It should return matching results or no results, never an error.”

SeedThe report is reframed around the broken input-handling contract, not just the one screen that exposed it.
Planning consultClaude examines user behavior and regression boundaries. Codex examines parser ownership and system effects. They complete two rebuttal rounds before synthesis chooses one bounded outcome.
Operator approvalThe operator confirms that the issue covers quoted search input but not a general search redesign.
Implementation consultThe agents propose execution details independently, challenge them through one rebuttal round, and agree which parser surface changes, which tests prove the behavior, and what must stay untouched.
ImplementThe chosen agent edits the parser in an isolated worktree, adds the agreed regression tests, runs checks, and completes the QA pass.
CheckThe other agent compares the actual diff to the plan. If an escaped-quote case is missing, it writes that exact repair into the review checklist and moves the issue to C-fix.
Repair and re-checkimplement-issue adds the missing case and checks it off only after verification. check-issue confirms the fix and reports merge-ready.
Approve and mergeThe operator approves D-merge. merge-issue lands the branch, cleans the worktree, and broadcasts the user-visible outcome.
Notice the boundary: no agent silently broadened “quoted search crashes” into “rebuild search.” The written contract carried that constraint through every station.

What an operator should always know

Before a pass

  • Which issue or series leaf?
  • Which skill?
  • Which phase does control-root state report?
  • Is this an approval or only a request for work?

After a pass

  • What durable artifact changed?
  • What state changed, if any?
  • What verification ran?
  • What exact next step did the skill report?

11. Guardrails and common mistakes

Do not skip lifecycle states

P-draft cannot jump to I-ready, and I-ready cannot jump to D-merge. Each gate exists because a different kind of evidence must be produced first.

Do not let the second consultant anchor early

Independent positions must be written before either consultant reads the peer’s position. Otherwise the dual-consult benefit is mostly lost.

Do not treat consultant files as competing final plans

claude.md and codex.md hold attributed reasoning. The synthesized plan.md is the shared contract operators approve.

Do not build in the primary checkout

The issue worktree isolates implementation. The primary checkout remains the control point for canonical state and consult artifacts.

Do not confuse a clean check with merge approval

A checker reports merge readiness but does not normally advance to D-merge. The operator must approve that transition in a separate invocation.

Do not erase another reviewer’s work

Claude and Codex each own their review subsection. Open required items across all present subsections remain mandatory until verified.

Do not silently broaden the issue

Incidental evidence is not automatic scope. When live evidence demands a major change to the contract, return to consultation instead of inventing scope during implementation.

Do not put Discord secrets in repository files

The repository stores only environment-variable names. The actual webhook values stay in the selected skill home’s environment store and are never printed or committed.

The shortest safe operating rule: trust the canonical plan, trust the freshly read control-root state, keep implementation isolated, and never turn readiness into approval without the operator.
