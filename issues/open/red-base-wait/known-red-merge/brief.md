# Brief: known-red-merge

## What
The merge turn uses the same known-red rule as `known-red-leaf`, against the exact target the whole stack stands on (`batch.built_on`), and the repo hold is retired.

When merge checks fail with no cause in the whole-stack diff, B reruns the same command once on the tested top. If it is still red, B runs it once on `batch.built_on` through `akrogon base-run --base <built_on> --attempt <id> -- <command> <args>` and writes one comparison record per red check, bound to the merge attempt. When every failing unit is known-red, B runs `akrogon phase <slug> merged --slot B --check --attempt <id> --compare <file>...` and the normal push follows. Any failure the stack causes, any new or unverified unit, and any unit named by a batch leaf's own done-criteria keep today's culprit, split and repair path, where only that leaf's A corrects a wrong expectation (A,B).

Before stamping `--check`, the command validates each record by its state, as `known-red-leaf` does (A,B). It also checks that the record's attempt is the batch attempt, its leaf revision is the recorded top, its counterpart is `batch.built_on`, and its base log comes from a `base-run` record line whose parent attempt is this attempt and which started after slot B's `prompted_at` (A,B). The tested-top, attempt-id and fast-forward guards stay. Accepted records stay on the batch until a restack has made its `reuse` decision or the landing is settled (A,B,C).

The repo red record updates at merge:
- known-red units add entries and notices by the `known-red-leaf` rule;
- an active entry whose unit passed on the `built_on` side resolves at `--check`, under the `known-red-leaf` ancestry rule (A,C);
- on green or known-red checks, B passes a `green` record for each command it ran that has active entries. The record holds that run's log and each active unit's outcome on the tested top, with no retry and no counterpart (A,B). A unit that passed there resolves only when the landed revision equals the record's leaf revision. This holds in every path that records a landed push (A,B).

A restack whose accepted records hold any known-red unit reruns the checks instead of taking `reuse`. A green-only pair keeps today's `reuse`.

The hold is retired. Nothing reads or writes `held.yaml`, and an existing file is left in place untouched. `mergeHolder` loses its fix routing. `--red-on-base`, `--command`, `hold-fix` and `unhold` are removed, and a stale call fails with an error that points to the known-red rule in `skills/merge-issue/SKILL.md`. The hold line in `akrogon status` and the hold print in `akrogon unpause` go. Pause and normal queue order stay. A `held` outcome already in `issues/merge-attempts.jsonl` still parses.

This leaf owns the refresh of active merge seats when it lands. The retired-call errors stop a seat that is still on the old hold path, and every later merge prompt loads the new skill. No restart machinery is added (design, held disagreement B F9).

Owned files: `src/phase.ts` (merge paths: `batchCheck`, `batchPush`, `finishPush`, restack, the `check.fix` endings and flag parsing for the retired flags) (A,B), `src/next.ts` (the hold gate, `fixHeld`, and resolve in the reconcile), `src/hold.ts`, `src/state.ts` (batch fields), `src/compare.ts` (merge binding and the `green` state), `src/red-record.ts` (merge-time resolve), `src/status.ts` (hold line), `src/akrogon.ts` (retired commands and flags, unpause print), `src/AREA.md` (today `:30`), their tests, every test asserting the hold (today `tests/hold.test.ts`, `culprit`, `command-reference`, `pause-status`, `pause-next`, `next`, `status`, `batch-merge`, `merge-attempts`), `skills/merge-issue/SKILL.md` (today `:43`, the fix-forward clause of `:55`, `:73`), `docs/guide/next.md` (today `:119`), `docs/guide/merge.md` (today `:29`), `docs/guide/cheat.md` (today `:110-116`) and `README.md` (today `:134`, `:144-145`).

## Why
It consumes from `known-red-leaf` the comparison record schema and validation (`src/compare.ts`), the red record with its notice and ancestry rule (`src/red-record.ts`) and the `--compare` flag, and from `base-run` the `akrogon base-run --attempt` command with its record line. `merge-issue/SKILL.md:55` is edited after `test-proof-rules` has landed, which `known-red-leaf`'s own `blocked-by` guarantees (A,C).

Tamdoma/akrogon#76 and #77: a red main ends every merge run in a repo hold (`src/phase.ts:844-889`, `src/next.ts:1044-1076`), so the pile-up moves from implement to merge. The operator chose to retire the hold and apply the per-test rule at merge, against the stack's own target (chart red-base-wait, fork merge-gate). The 2026-10-10 red-main-hold stale-clear lesson stays active for the red record.

## Done-criteria
1. A merge run whose red checks have validated records with every failing unit known-red against `batch.built_on` stamps `--check` and pushes through the normal flow. No hold is written and the leaf does not go to `check.fix` for that red.
2. `merged --check --compare` refuses, naming the field or file, a record that fails the `known-red-leaf` checks for its state, or whose attempt is not the batch attempt, whose leaf revision is not the recorded top, or whose counterpart is not `batch.built_on`. It also refuses a base log with no `base-run` record line naming this attempt as parent, started after slot B's `prompted_at`, with the record's base, command and args and a recorded end and exit status (A,B). It refuses any new or unverified unit and any unit named by a batch leaf's own done-criteria (A,B). The tested-top, attempt-id and fast-forward refusals behave as today.
3. A failure the evidence attributes to the stack, including one inside a unit also red on `built_on`, keeps today's culprit, split and repair behavior.
4. Known-red units at merge add entries and notices as in `known-red-leaf`. A unit passing on the `built_on` side resolves at `--check` under the ancestry rule (A,C). A unit passing in a `green` record resolves only after the push lands with the landed revision equal to that record's leaf revision. This holds in `merged`, in the landed path after a refused or failed push, and in the next pass's reconcile (A,B). A `reuse` push resolves nothing. Every add and resolve reads the red record inside the lock the caller already holds and compares before writing.
5. A restack whose accepted records hold a known-red unit prints `rerun`, never `reuse`. The restack decides with the records and then drops them on both decisions (A,C). A green-only pair keeps today's `reuse` decision.
6. No code reads or writes `held.yaml`. With a nonempty legacy `held.yaml` present, dispatch, the merge turn, `akrogon status` and `akrogon unpause` behave as with none, and the file is unchanged. `mergeHolder` has no fix routing.
7. `--red-on-base`, `--command`, `akrogon hold-fix` and `akrogon unhold` each fail without changing any state and name the known-red rule in `skills/merge-issue/SKILL.md`. A `held` outcome in `issues/merge-attempts.jsonl` still parses.
8. `skills/merge-issue/SKILL.md` states the merge retry, comparison, `green` record, `--compare` and tested-top resolution rules, and drops the hold ending (A,B). It replaces the unconditional fix-forward clause of `:55` with the known-red rule and sends a batch leaf's own-criteria unit to the culprit path. B corrects no expectation at merge (A,B). Other clauses of `:55` keep the text `test-proof-rules` landed. The doc and README lines above match.
9. A sweep of `skills/`, `docs/`, `README.md` and `src/AREA.md` by meaning finds no hold, `hold-fix`, `unhold` or merge red-on-base stop. Hits outside scope are listed in the report.
