# Mismatch reporting: independent operator round B

## Q1

When a registered repo holds leaves whose `state.repo` names another registered key, does `akrogon next` print one aggregated line per repo per invocation, or keep one line per leaf?

Context: `discover()` reports every mismatched leaf separately and counts it unreadable (`src/next.ts:98-107`), while `report()` deduplicates by repository/path within the invocation (`src/next.ts:77-83`). The same repository is discovered repeatedly during sweeps, dispatch, capacity counting and cleanup (`src/next.ts:451,260,515-524,574-576`). The exit status depends on recorded skips (`src/next.ts:660`), so aggregation must preserve failure signaling as well as reduce output.

Research: Operator > practitioner > primary code/docs > model knowledge. The intake requests one actionable message and carries “once per invocation,” with cleanup and import prevention off route. The practitioner seed reports 96 errors per pass, while intake records that the incident's leaves were later removed. Inspected report/discovery, invocation construction, selection, sweep and mismatch tests at `tests/next.test.ts:1098-1140`; searched `unreadable`, `unknown`, `skipped`, `lookup` and `process.exitCode` in `src/next.ts`. Inspected plugin event subscriptions. No new practitioner interview or web research was conducted, and the consumer's current state was not rechecked in this round.

A (recommended): Emit one structured mismatch summary per affected repository per invocation. Include the registered key/root, unique affected-leaf count and offending paths paired with their stored keys, plus an instruction to repair ownership in the registered checkout. Deduplicate paths across repeated discoveries, retain a nonzero exit status, and preserve separate diagnostics for malformed state, duplicate local slugs, I/O failures and dependency failures. This removes the repeated per-leaf lines without discarding the evidence needed to repair the tree.

B: Keep one diagnostic per leaf with current within-invocation deduplication. This preserves the existing diagnostic shape and direct path lookup, but reproduces the reported flood. It requires reopening the intake's stated aggregation scope rather than simply choosing another implementation of it.

Pitfalls: One line can still contain substantial data, so distinguish fewer records from less evidence. Do not count the same path again on each discovery, suppress subsequent explicit invocations, merge unrelated errors into the mismatch summary, or clear failure status just because valid work also ran. Accumulate enough information to produce a complete summary across discoveries rather than printing an incomplete first-path record and suppressing the rest. A mismatch is any stored key unequal to the registered key, including a key not present in the registry: `src/next.ts:102` and existing tests using `wrong`/`other` already enforce this. Do not require the foreign key itself to remain registered. Test many leaves, several stored keys, closed-only contamination, repeated scans and a second invocation, while proving foreign state remains unchanged.

## Q2

Does a foreign leaf stop dispatch of that repo's own valid leaves, or do valid leaves keep dispatching while the foreign ones are reported?

Context: `discover()` excludes foreign leaves but retains valid ones, and sweeps dispatch the retained inventory (`src/next.ts:102-107,527-531`). However, `activeCount()` treats every mismatch as unreadable and counts all retained leaves plus unreadable leaves toward the global limit (`src/next.ts:255-265`), so 96 foreign records can prevent new allocation even in another repository. The existing healthy-leaf test raises `max_active` to four for a single bad leaf (`tests/next.test.ts:1102-1110`), which does not cover a flood exceeding capacity.

Research: Operator > practitioner > primary code/docs > model knowledge. The seed reports other repositories continuing, but that observation does not prove new work can allocate under every capacity setting. Followed discovery's `unreadable` result through selection and capacity counting, and inspected allocation's limit check at `src/next.ts:289-293`, dependency lookup at `:151-154`, and mixed-leaf tests. No operator decision on whole-repository blocking has been recorded. The capacity consequence above is a direct inference from those code paths, not an additional observed incident.

A (recommended): Keep valid local leaves eligible for dispatch while reporting and excluding foreign leaves. Distinguish a successfully parsed ownership mismatch from genuinely unreadable or unknown inventory so foreign records alone cannot consume allocation capacity or switch all valid leaves into the conservative unreadable count. Preserve normal active-leaf accounting, dependency checks and existing conservative treatment of malformed/unreadable state. This contains the fault to the foreign records and makes “valid work continues” true for new allocation as well as already allocated leaves.

B: Block dispatch for the contaminated repository until its foreign leaves are repaired. This gives a stricter repository-level ownership boundary, but stops otherwise valid local work and changes current sweep behavior. Define that block explicitly and keep it local to the affected repository rather than letting foreign-record counts exhaust global capacity. It still requires deliberate inventory handling, not merely retaining today's unreadable counter.

Pitfalls: Aggregating log output alone does not implement A. Keep foreign leaves out of dispatch, merged-leaf cleanup and dependency satisfaction, and never rewrite their repo key to make them eligible. Selection currently uses `inventory.unreadable` to avoid a second misleading no-match error (`src/next.ts:566-569`), so separating mismatches from unreadable state must preserve useful behavior when explicitly selecting a foreign leaf. Valid work may still wait for legitimate capacity, missing dependencies or genuinely unknown inventory. Test more foreign leaves than `max_active`, an otherwise idle valid leaf in the same repo, a valid leaf in another repo, explicit foreign selection, foreign-only inventory and a local dependency naming a foreign-only slug. Test malformed state alongside foreign records so this change does not weaken existing unknown-inventory protection.

## Q3

Is detection walk-time only, or also refused at registration (`akrogon init`) when foreign leaves already exist?

Context: Initialization derives the registered key from the repository folder and writes config, local scaffolding and the registry without checking existing leaf ownership (`src/init.ts:16-49`). Walk-time detection sees both open and closed leaves on each discovery (`src/next.ts:113-116`) and catches contamination introduced after registration. Status is a separate contract: overview walks open only and returns one unreadable-repository record on a mismatch (`src/status.ts:44-79,288-289`), so it is not a replacement for next's broader walk.

Research: Operator > practitioner > primary code/docs > model knowledge. The intake scopes the current chart to next's actionable reporting and leaves importing/cleanup elsewhere. The seed offers registration or first-walk detection without selecting registration as mandatory. Inspected initialization's write order and status traversal, searched registration/mismatch coverage in `tests/init.test.ts`, and read `tests/status.test.ts:269-320`. No inspected evidence shows that registration refusal would have prevented this particular later merge, and no external sources were needed for these local implementation facts.

A (recommended): Keep ownership detection at walk time for this chart and leave registration unchanged. This covers existing registrations and later contamination with one reporting contract. It avoids adding a second boundary when the requested next behavior already needs walk-time handling regardless of registration checks.

B: Also refuse registration when existing open or closed leaves have a foreign repo key. This gives earlier feedback for a contaminated checkout presented to init, but adds validation, failure semantics and tests in another command. Perform that validation before any writes at `src/init.ts:31-49`, and retain walk-time detection because later merges remain possible. This is a separate scope choice, not a substitute for A's ongoing detection.

Pitfalls: Registration validation cannot prevent future imports and must not silently adopt, delete or relabel foreign history. If B is selected, test that rejection leaves both local configuration and the global registry unchanged, including reinitialization and closed-only contamination. Do not expand this chart into validating legacy logs, chart prose or every historical record. Do not change status semantics merely to make all readers identical. Walk-time summaries describe the leaf inventory inspected, not proof that all other issue artifacts belong to the repository.

Challenge check: Recommend Q1-A, Q2-A and Q3-A. Q1 is largely settled by the intake's requested outcome, while Q2 contains a real scheduling choice that cannot be answered by output formatting alone. The newly inspected `activeCount()` dependency means the implementation must explicitly own mismatch classification, selection behavior and capacity handling if it promises valid work continues. That is necessary for the selected outcome, not permission for a general scheduler rewrite. Keep malformed-state protection, nonzero diagnostic status and foreign-state immutability. “18 first, then 17” establishes order only, and chart 18's handoff introduces no code dependency here. No polling, remembered suppression, automatic cleanup or import-workflow changes are part of these recommendations.
