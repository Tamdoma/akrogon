# Brief: known-red-leaf

## What
A leaf before merge never stops, waits or fails because main is red. When a check run in plan.synthesis, implement, check.review, check.repair or check.fix fails with no cause in the leaf's diff (A,B), the seat reruns the same command once with the change (same args, scope and configuration) and writes one comparison record per red check under the `leaf=` folder. The seat writes the record file holding the first run before the retry, so a replaced session that finds it does not retry again, and a record holds one retry at most (A,C). With-change run logs go into the leaf's implementation folder, where `base-run` writes its pre-merge log (A,C). If the retry is green, the record marks the check inconsistent and no base run happens. If it is still red, the seat runs the command once without the change through `akrogon base-run --base "$AKROGON_BASE" -- <command> <args>`, reads the complete logs, and completes the record, including whether each run completed (A,B). Each failing unit (runner or stage, file or suite, full name) is one of:
- known-red: fails in both with-change runs, fails without the change, and the seat judges no cause in the diff;
- new: passes without the change;
- unverified: missing, crashed, timed out, skipped or unreadable on either side, or prevented by a setup or build stage that failed on either side (A,B).

Only known-red units let the leaf continue. New and unverified units block as today, through repair or the existing incomplete-verification stop. A unit belonging to the leaf's own done-criteria is never known-red: it takes the repair path, where only A corrects a wrong expectation under the rule `test-proof-rules` lands (A,B). At `plan.synthesis`, a planned test's intended red is not compared, and any other failure takes this rule (A,B).

The seat passes each record on its phase move with a repeatable `--compare <file>` flag. The command checks the record for function only, then updates one repo red record inside the akrogon lock:
- a known-red unit with no active entry for the same unit and provenance (command, args, scope, material conditions) becomes one entry plus one herdr notification to the operator;
- a unit already active joins silently;
- an active entry resolves when a validated record shows its unit passing on the without-change side, and the entry's first-seen revision is that counterpart revision or an ancestor of it (A,C).

`akrogon status` lists active entries and any failed notice. A leaf never repairs a recorded red outside its own criteria.

Owned files: `src/akrogon.ts` (the `--compare` flag, with its place in the `phase` synopsis of `README.md:134` and `tests/command-reference.test.ts`), `src/phase.ts` (flag parsing and the validation call on seat moves; merge paths belong to `known-red-merge`), new `src/compare.ts` (record schema and validation), new `src/red-record.ts` (repo record, notice, add and resolve), `src/status.ts` (the active-entry line only), `src/base-run.ts` (only to add the log path to the record line if the landed line lacks it) (A,B), their tests, `skills/implement-issue/SKILL.md` (today `:38`, `:61`, `:74`), `skills/check-issue/SKILL.md` (today `:59`, `:63`, `:85`), `skills/plan-issue/SKILL.md` (one sentence in the `plan.synthesis` section as `test-proof-rules` lands it) (A,B), the base-red sentences of `docs/guide/phases.md` (today in `:94`), and any other `docs/` or `README.md` line stating the pre-merge base-red stop.

## Why
It consumes from `base-run` the `akrogon base-run` command, its record line (leaf, slot, base, command, args, start, end, exit status) and its log path printed as `log: <path>` (A,B). It consumes from `test-proof-rules` the `plan.synthesis` test gate, the rule that only A corrects one wrong expectation, and its lines of `docs/guide/phases.md` (A,B,C).

Tamdoma/akrogon#76: `implement-issue/SKILL.md:38` and `check-issue/SKILL.md:63` end a proven base red with a per-leaf `failed`, and no record is shared outside merge. On framework main 5cb74c3c6 every leaf reran a full verify (about 7-15 minutes each) and failed one by one, and two leaves fixed the same test separately. Tamdoma/akrogon#77: a leaf moved back to check.review was failed again within minutes from base-red logs recorded before main was repaired outside git. The operator chose that a change is judged only by what it breaks, per failing test, with one same-command retry and a fresh without-change run every time (chart red-base-wait, forks waiting-leaf, comparison, base-evidence-reuse, red-record). Chromium's commit queue works the same way (https://chromium.googlesource.com/chromium/src/+/master/docs/infra/cq.md, read 2026-10-10).

## Done-criteria
1. A seat move carrying valid comparison records, each either inconsistent or with every failing unit known-red, goes where it would go with green checks, and no leaf reaches `failed` because a check is red on its base.
2. A record is refused, naming the field or file, when it does not parse, a state is outside its allowed set, a required field is blank, a log file is missing, its leaf revision differs from HEAD, its retry run is missing or more than one retry is recorded (A,C), or a red retry has no without-change run whose revision equals the leaf's `AKROGON_BASE` and whose log comes from a `base-run` record line of this leaf and slot started after that slot's `prompted_at`, with the same base, command and args as the record and a recorded end and exit status (A,B).
3. A record listing a new or unverified unit, or a unit of the leaf's own done-criteria, is refused on a move toward `implement`, `check.review` or `merge` (A,B).
4. A known-red unit with no active entry for the same unit and provenance adds one entry and sends one herdr notification naming the repo, unit and command; a second record of the same unit adds no entry and no notification; the notification result is stored apart from the entry.
5. An active entry resolves only when a validated record shows that exact unit passing on its without-change side under the same provenance, at the entry's first-seen revision or a descendant of it (A,C). A pass at an older revision, absence from output, a merged fix, an issue close or a newer main never resolves it (A,C). One unit can resolve while another of the same command stays active, and a recurrence after resolution is a new entry with a new notification.
6. Every add and resolve reads the red record inside the lock the command already holds and compares before writing, so a resolve never closes an entry that is newer than its evidence (the mechanism in `learnings/history/2026-10-10-red-main-hold-stale-clear.md`) (A,B,C).
7. `akrogon status` prints each active entry with its unit, command, first-seen revision and notification result.
8. `skills/implement-issue/SKILL.md`, `skills/check-issue/SKILL.md` and the `plan.synthesis` section of `skills/plan-issue/SKILL.md` (A,B) state the retry, retry budget, log location, comparison, record and `--compare` rules above (A,C). They drop the `failed --reason "<command> red on base <sha>"` stop for a completed comparison, keep the incomplete base-run stop, route a wrong expectation in the leaf's own criteria to A's correction under `test-proof-rules` and drop B's fix of a test red on base (A,B), and let a failed `checks` command block unless every failing unit is known-red in a validated record (today `check-issue/SKILL.md:59`).
9. A sweep of `skills/` and `docs/` by meaning finds no line telling a pre-merge seat to stop, wait or fail on a check red on its base, or to reuse an earlier base result; out-of-scope hits, including the merge lines `known-red-merge` owns, are listed in the report.
