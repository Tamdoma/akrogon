## Decisions

- D1 Resolver reach (design Open question 2): the reset helper imports `src/transcript.ts` and `src/hc.ts` from the release (`../../../src/...`), as `scripts/direct-guards.ts` already does. One resolver: the code lookup lives in `src/transcript.ts`.
- D2 Code lookup: `transcriptByCode(seat: { session: string; address: string }, code: string, sinceMs: number): Promise<string | null>` in `src/transcript.ts`. It reads the seat's process like `transcriptFor` (`pid`, then `foreground.pid`) and searches only that kind's folder: claude `<CLAUDE_CONFIG_DIR or HOME/.claude>/projects/<cwd-mangled from the open tasks handle>/*.jsonl`, pi the folder of the argv `--session-id` file, both only files with mtime after `sinceMs`; codex the rollouts open in `/proc/<pid>/fd`, newest first. Returns the one file whose text contains `code`, `null` when none, and throws naming the files when more than one does. It writes no label (the helper's label stage does). Plus `transcriptKind(path): 'claude' | 'codex' | 'pi' | null` from the same path shapes the resolver produces, used by the helper to pick the reset key and the input-record parser.
- D3 Door transcript reads: new CLI verb `akrogon transcript <address>` prints the resolver's path for a terminal of the door's repo session (`repoSpace`, as `seat --slot`), or `-` when unknown (session-id Q3 3a); hc errors exit non-zero. The door uses it for its own and each consultant's seats.yaml `session`. Reason: the door has no other way to call the resolver, and `Bash(akrogon:*)` already covers it in auto mode.
- D4 Exchange wait (Q1 answered O1): after A finishes its own notes for an exchange, A runs `hc wait --children any --timeout <s> --json` from its own terminal and stays in its turn. Each wake is one of: a message (reason `message`, `from` = a terminal; a consultant report is `<hc from="<address> <name>">done <X>: <path></hc>`), or `children` naming the child that stopped (turn ended, blocked, error, exited). A handles that wake (collect, nudge or drop per D6), then re-arms the same wait while any prompted consultant of the exchange has neither reported (with its return file) nor been dropped. News already seen does not end the next wait (hc's "unseen news"). A timeout is a check-in, never a drop.
- D5 Consultant lifecycle in skill text: start `akrogon seat --slot <x> --harness <h> --model <m> --effort <e> --task "You are slot <X>. Read and follow <brief path>"` at the consultant's first exchange (the start verb's 60 s proof is the first ask's delivery proof); later asks `hc send --json <address> "You are slot <X>. Read and follow <brief path>"` only to a consultant whose `hc get` status is `idle` or `done`; report `hc send <door> "done <X>: <return path>"`; restart `herdr-consultant-column --save <door> <door-created consultants>`, `hc kill <address>`, `hc rm <address>`, the same start under the same name, then `herdr-consultant-column --restart <door> <consultants>`; after a start or removal `herdr-consultant-column <door> <consultants>`. Consultants in seat-letter order; supplied consultants are never passed, killed or restarted. A "door not in a tab" exit is logged once per round and the round goes on; any other non-zero exit is a check-in for A.
- D6 Collection (delivery Q4): a consultant is done for an exchange only when its return file exists and its `<hc from="<address> ...">` report came from its current address. A consultant that stopped without both gets one `hc send` nudge naming what is missing; a second silent stop drops it for the session, recorded under `consultant:` with harness kind and model.
- D7 Reset helper CLI (design literal): A's last action is `hc run --bg --no-notify --rm --no-parent -- bun <skill-folder>/scripts/door-reset.ts <A address> <log> "<start prompt>"`. The helper resolves the session by `repoSpace` of its cwd (the door's repo), resolves A's pre-reset path with `transcriptFor`, and records that file's byte length as the queue boundary. It logs one JSON line per stage to `<log>`: `{ t, step, result, ...}`, with `pre` and `boundary` on `started`, `code` and `turn` on `warm-up`, `path` on `code-lookup`. A stage that fails logs its result and the helper exits non-zero. The step names below are the log's machine interface, read by criterion 3's test.
- D8 Helper stages, in order, each stopping with a logged result on failure:
  0. `started`: the pre-reset path and boundary are recorded.
  1. `wait-turn-end`: `waitFor` A on hc events until status `idle` or `done`, bounded by `DOOR_RESET_TURN_BOUND_MS` (default 600000); bound → `turn open`; A finished or gone → `identity changed`.
  2. `input-check`: an operator input record past the boundary in the pre-reset transcript (claude `user` or `queued_command` attachment with `origin.kind` `human`, codex `task_started` or role-`user` `response_item`, pi role-`user` `message`, today's parsers kept) → `superseded`, nothing more sent.
  3. `reset-keys`: `hc keys <A> / c l e a r enter` (claude) or `/ n e w enter` (codex, pi), one key name per character (`/` is accepted as a key name by hc 0.1.18, seen at planning); the reset start time is taken just before.
  4. `warm-up`: `hc send --json <A> "reply OK <code>"` with a fresh random code; `started: false` → `warm-up not started`.
  5. `warm-up-turn-end`: `waitFor` A until its turn is past the send's turn and status `idle` or `done`, same bound.
  6. `code-lookup`: `transcriptByCode(A, code, resetStart)`; `null` → `reset unconfirmed`. Success logs `found` with `path`.
  7. `differing-path`: the found path equal to the pre-reset path → `same transcript`.
  8. `label`: `hc label <A> akrogon.transcript=<path>`.
  9. `start-prompt`: `hc send --json <A> "<start prompt>"`; `started: false` → one `hc keys <A> enter`, logged.
  The input check runs once, after the turn end: an operator's submitted input during A's turn is a transcript record that stays, so one read after the turn sees it. The old polling during the wait goes.
- D9 Handover entry and start prompt (design Open question 1): the entry keeps today's shape with the pane replaced by A's hc address and the session id by A's transcript path: `- mode <time> <A address> <A transcript path>: handover <time> <log>: attended next <chart>; consultants <surviving>; signposts <path>; instructions <...>`. The start prompt (corrected in Implementation notes): `Run the chart-issues skill (<absolute skill folder>/SKILL.md): continue handover <time> door <A address> next <absolute chart folder>`. Fresh A continues only when the address and chart match the latest unconsumed handover entry and its own `akrogon transcript <address>` path differs from the entry's path; an unknown (`-`) path never counts as the same conversation, nor as a continuation.
- D10 seats.yaml entry: `{ seat, address, name, recipe: { harness, model?, effort? }, session }`, `session` an absolute transcript path, `name` the hc name or null. A and supplied consultants carry `recipe: { harness }`; door-created consultants carry the start verb's harness, model and effort. An entry is appended when address or path changes, and only with a known path. `chart-usage.ts` parses this shape (strict) and reads `recipe.harness` and `session` as a path for every kind. Stated limit: a seats.yaml written before this leaf fails to parse with a field error naming the entry; a failed measurement never holds a handoff (SKILL.md Handoff).
- D11 Gate: inside hc means `HC_TERMINAL_ID` set and `hc get $HC_TERMINAL_ID` answering; otherwise the door says it is outside hc and continues single slot or with supplied consultants. The temp-path rule goes: the chart folder and seats.yaml are written at Open.
- D12 Old code removed in this leaf: `scripts/peer-create.ts`, `peer-ask.ts`, `peer-wait.ts`, `peer-restart.ts`, `peer-anchor.ts`, `tests/peer-create.test.ts`, `peer-ask.test.ts`, `peer-wait.test.ts`, `peer-restart.test.ts`; `scripts/door-reset.ts` is rewritten and `tests/door-reset.test.ts` replaced. Deletion lands only after criteria 1, 3 and 5 are green (signpost 2a).
