# Design: slow-merge-notice

## Binding decisions, verbatim

From `issues/chart/merge-slow-alarm/forks/slowdown-alarm.md` `## Taken`, 2026-10-28, A's pick under autopilot (not operator words): `1a 2a 3a 4a`.

- Q1 1a: the normal is the median wall time (`end - start`) of the last 20 eligible merge-scope runs before the one checked, eligible meaning completed (`end` set), setup 0, no `compares`, no `reused` or `blocked` entry; at least 5 eligible runs are needed or no check runs. Every completed merge-scope head run (no `compares`) is checked, partial ones included. A run is flagged when its wall time is more than 1.5x the normal and at least 2 minutes more. Command text is not part of eligibility, so a config change that adds cost still alarms. Reason: partial runs spend real time (B F1), reused runs would make the normal cheap. Rejected 1b: hides partial slow runs.
- Q2 2a: a flagged run opens an episode that keeps its pre-jump normal; later checked runs compare with that normal; the episode closes when a fresh eligible run is back under the threshold (recovered) or when every one of the last 20 eligible runs lies inside the episode (accepted as the new normal); derived from the ledger with a `slow` field per checked run, no new file. Reason: rolling-only clears falsely (B F2). Rejected 2b.
- Q3 3a: name the episode's first flagged run (red attempts included) with its leaf, run id, measured and normal minutes, worded "first seen at", never "caused by". Reason: framework history shows the first slow run was a red attempt.
- Q4 4a: one herdr notification `<repo> merge slow` per episode, reserved under the receipt lock and sent outside it like `main red`, an undelivered or failed send retried by the next completed merge run of the same episode; an `akrogon status` line while an episode is open, and a `verify slow:` stdout line naming an accepted close; a `verify slow:` stdout line on each flagged run. Merge exit status and receipt eligibility never change. Rejected 4b (broadcast): delayed to owner completion, misses attempts that never land.
- Standing dissent (B rebuttal F4): no step makes a merge seat read the status line; accepted, a green land has no seat and the operator and watcher read status. (B F5) false alarms from host load cost attention; accepted, the message shows minutes and says "first seen at".

Carried locks: framework D3 (never fail merges on a wall-clock cap); operator lock 2026-09-18 (no clocks, polls or watchdogs): the comparison runs once inside the verify pass at its end, never on a timer.

Excluded: per-command timing and a Discord broadcast of slowdowns (chart Off route).

Standing design: `/home/ivan/.claude/skills/chart-issues/assets/standing-design.md`. Interpretation: no vanity tests; each criterion is proven by the repo's existing bun tests at the `verify` and `status` command boundary using seeded `verify-runs.jsonl` histories and the existing fake herdr (`FAKE_HERDR`, `tests/fake-herdr.ts` `notification show` handler) unchanged; no live framework run, since the arithmetic and wiring need none; the one deliberate break per new behavior turns its test red. (A,B) The herdr stage replays recorded output: the fake's success reply `{shown: true, reason: 'shown'}` equals the `result` of the real call recorded in `readiness.yaml` `proofs` (2026-10-28, herdr 0.9.1, command named there), compared at charting; its existing `failNotification` and `failNotificationOnce` seams cover the failed and retried sends, so no proof machinery is built or extended. A fresh herdr call is needed only if the notification argv or reply contract changes from that recording.

## Leaf architecture

- Owned: `src/verify.ts` (the comparison, the `slow` receipt field in `verifyRunSchema`, the notice reservation and send for slow episodes inside `runOnce`'s locked final rewrite, the `verify slow:` line), `src/status.ts` (the `Slow merge:` line, computed from each registered repo's ledger next to `unpackedLines`), their tests, and the verify paragraph in `src/AREA.md`.
- `verifyRunSchema` is a strict object: the new `slow` field is optional so every existing record still parses; its shape (normal ms, ratio, episode first run id, close reason, notice delivery) is open for the plan, with the notice delivery kept separate from the main-red `notice` field.
- Consumers relying on the receipt and unaffected by the change: `requireGreenReceipt`, `reuseSource`, `greenRun`, `redRun`, `knownRedReceipt`, `newRedUnits`, `reportRun` (exit code). The plan checks each reads no new field and that `reportRun`'s exit is computed before and independent of the slow check.
- The slow decision and reservation happen inside the existing `withLock(lock, ...)` final rewrite in `runOnce`, the herdr send after it, reusing `repoSession` and `herdr` as `sendMainRedNotice` does. Open for the plan: whether to generalize `sendMainRedNotice` or add a sibling.
- `end` is set only on a completed pass; a thrown pass has no `end` and is neither checked nor counted.
- (A,B) Order: "earlier", "first", "last 20" and "inside the episode" all use ledger row order in `issues/verify-runs.jsonl`, which is receipt append order (start order) and is total, so no tie rule is needed. A run's check is decided once, inside its own final locked rewrite, over the earlier rows that are completed at that moment, and its stored `slow` result is never recomputed later; the next run continues the episode from the latest earlier row holding a `slow` field. `akrogon status` reads the last ledger row holding a `slow` field and prints the line when that row's episode is open. Overlapping merge passes are rare because the merge lane is serial; a row completed after a later run's decision does not change that decision.
- Exclusions: land, broadcast and merge-issue skill text are unchanged.
