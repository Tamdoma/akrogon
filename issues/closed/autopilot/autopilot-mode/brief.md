# Brief: autopilot-mode

## What
The chart-issues door gains a non-default autopilot mode that the operator switches on in words for one door session in herdr. While it is on, the door runs every step it runs today. At each point where the operator would answer (fork rounds, the split proposal, the handoff review including debate and seats), A writes the round as today, then answers it itself using the evidence and the operator's standing values. It records each pick as its own, keeps an Autopilot record in each handed chart and hands off through the lifecycle route. The operator's watcher takes over after handoff. Attended mode stays the default, and other door tabs are unaffected. The change is skill and guide text only: `skills/chart-issues/SKILL.md`, `skills/chart-issues/assets/questions.md`, `skills/chart-issues/assets/shapes.md`, `docs/guide/chart.md`.

## Why
The operator wants to hand incoming, non-original work such as bug fixes to a door, without sitting at the computer answering technical questions where the recommendation is usually right (operator record 2026-09-16 to 2026-10-16: 89% of answers took the recommendation). Today `questions.md` states "Recommendations and silence cannot supply an operator answer", and the fork shape and preflight in `shapes.md` need an operator answer, so a door cannot finish a chart without the operator. Earlier attempts at full autopilot failed on unattended operation: operator-only inputs not listed in advance, unasked changes, autonomy past what the operator started, and records the agent wrote as if they were the operator's (INTAKE.md history). This mode keeps every step and gives A only the operator's answers inside the work handed at switch-on.

## Done-criteria
1. Switch-on: `SKILL.md` states that autopilot starts only from the operator's words in the door's own pane, at door start or later naming a chart. The words carry the mode, the handed work and the consultants or none. Outside herdr the door says autopilot cannot start. The first reply echoes the mode, handed work and consultants. It says that handed-off work waits for the operator's watcher, which the door cannot check. After the door reads the handed work, the first reply shows a best-guess list of things to supply (logins, API keys, files), each with purpose and destination, with no approvals on the list. The operator's words go verbatim into each handed chart's INTAKE.md, and a mode line goes into its CHART.md with the time, the door pane and A's session id. Answers the operator gave before a mid-chart switch-on stay the operator's.
2. Answering: under autopilot every step of today's process still runs. At each point where the operator would answer, A writes the full round in its pane, picks by the evidence and the operator's values, and records the pick in the fork's Taken as A's with its reason, rejected options and any standing consultant dissent, never as operator words. The skill names the values itself: simplicity, function over form, removing over adding, systems thinking, speed and price. `questions.md` states the one exception to "Recommendations and silence cannot supply an operator answer", and the exception applies only under autopilot. The fork shape and the handoff preflight in `shapes.md` accept an A answer recorded under autopilot as taken, while approvals stay operator-only.
3. Waits and limits: these make that chart wait while the door moves on within its handed list: grant approval, fixture retention and secret-save approval; a mutating proof call, which waits for the operator's grant approval while read-only proofs proceed; a missing need; and a human-only prerequisite. Existing checks still stop a handoff, and A repairs what they refuse. A step on main or a lesson write that would change autopilot's own switch or limits also waits for the operator (C). The door never turns autopilot on, extends the handed list, changes the consultants or raises an existing bound in the skill.
4. Route: under autopilot every handed chart takes the lifecycle route. The direct route is not offered.
5. Scope: under autopilot Drain takes only the handed list, with no oldest-chart or seed steps, and imports nothing new. A full match between a destination seed and handed work is A's to confirm. Other seed matches, open-time close offers for skipped identities, and flaky tests or failed leaves outside the handed list are recorded only. Handed work is held when another door's open chart has the same chart folder, GitHub identity or legacy path, or when A sees the same outcome open there. Two doors started on the same work at the same moment is a stated limit. A failed leaf the operator hands to the door is charted like other handed work.
6. Consultants: a consultant is dropped for the rest of the session, never re-prompted, with its completed returns kept, when its exchange ends in `failure` or `blocked`, when herdr refuses its prompt, or when a `budget` outcome with status idle or done and `signal: unproven` repeats after one more full wait. A return file that arrives after the drop is ignored and recorded as ignored. Working-status budgets are still rerun at once, and a mistake in A's own call is repaired without dropping anyone. A consultant whose pane is a peer seat in another door's open chart (no end marker, latest A seat on a different pane) is skipped the same way. The door's own charts never cause a skip.
7. Off and resume: the mode ends when every handed chart's last marker is `Handed off` or `Closed`. A chart waiting on a need, approval or prerequisite keeps the mode on, also across the end of a pass, and the operator's next message in that door, such as a supplied key, resumes it. Only the operator's words in the door pane turn it off early. Supplying a key or changing the handed list keeps it on. Every mode change (on, off, changed list, "continue autopilot") is added to the mode record with its time, and a door reads the latest entry before continuing. Once off, an open peer turn is collected first and the next question goes to the operator. After compaction the same session continues while the latest entry says on. A door whose session id differs from the latest entry starts attended until the operator says "continue autopilot", which resumes the same handed list with lost consultants still lost.
8. Record: the CHART.md shape in `shapes.md` gains the mode record and an Autopilot section, written as the pass goes, whose every line is a list item. The section holds, in order: boundary breaches first; the switch-on reference; the consultants, each loss with its reason and the charts run without it, and ignored late returns; the route with its debate choice (C); handed-off leaves; completed steps on main and lesson writes for handed work (C); waits, each with the exact missing need, approval or prerequisite and the next step; pending steps on main as "after <leaf> lands, open a chart door to finish <step>"; picks against the round's recommendation; recorded-only seeds and candidates; friction; and the linked usage lines. It records observed states only and never says "started" or "merged" without evidence. The pass ends with one line per chart in the door pane. The handoff footer says "handed off", not "started", and names a pause when `akrogon status` shows one. Nothing computes a score.
9. `docs/guide/chart.md` explains autopilot to the operator: how to switch it on and off, what still waits for the operator, where to read the record, the stated cost that a wrong pick can merge to main (and for akrogon, deploy) before the record is read, not to hand the same work to two doors, and that the first run happens once with the operator around, answering nothing and able to say stop.
10. `git --no-pager diff --name-only "$AKROGON_BASE"...HEAD` lists only the four files above.
