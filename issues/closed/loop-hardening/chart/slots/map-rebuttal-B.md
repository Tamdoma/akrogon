# B disagreement-only rebuttal

- **RB1 · F9 is not “confirmed on all points.”** The merged finding contradicts its own missing-pane qualification and omits the capacity correction. `src/next.ts:138-140` counts a leaf only when a live pane matches its tab or worktree. Stale fields alone do not inflate capacity. Allocation writes both seat IDs before dispatch (`src/next.ts:183-187,321-324`). **Alternative:** mark the seed partly confirmed, explicitly reject unconditional stale-field inflation, and retain missing-seat failure as unproven under normal command invariants. Do not create fixes for either unproven claim.

- **RB2 · Worktree mismatch is not limited to a mid-leaf config change.** `src/next.ts:102-104` compares a stored absolute worktree path with a path derived from both `repo.root` and `worktree_root`. Moving a repository with a relative worktree root can change the expected path even when issues/config.yaml is untouched. The successful stable-key rename probe had no active worktree. **Alternative:** say “after a repository-root or worktree-root change with a recorded worktree,” and explicitly distinguish registration identity from active-worktree relocation in `repo-identity` scope.

- **RB3 · The repo field does guard something.** A leaf copied from another registered repository is rejected by `src/state.ts:58` and `src/status.ts:48`. Removing enforcement silently accepts that foreign record. That may be an elected simplification, but “guards nothing” is false. **Alternative:** retain the key as persistent identity and permit path updates independently. If enforcement is removed, ask the operator to accept location as sole authority and define treatment of the now-unenforced stored field. Do not describe removing this check as behavior-preserving cleanup.

- **RB4 · `closure-before-move` is not yet a complete recovery contract.** Reordering future completions does not repair already-closed records whose closure failed. Those return at `src/phase.ts:65`, and closure currently requires a surviving worktree at `src/pull.ts:185-189`. The original B probe reproduced exactly that closed-but-unresolved state. **Alternative:** name the leaf by its outcome, such as `resumable-source-closure`, and include both future failure prevention and an explicit disposition for existing failed completions. Closing before rename and retaining worktrees is a reasonable candidate for future operations, but recovery after prior cleanup still needs trustworthy commit evidence or a clearly surfaced unresolved state. Do not invent a commit or claim that ordering alone resolves the intake.

- **RB5 · The split silently loses the source-owner completion decision.** It assigns narrow sources to issues inside an epic, but current completion waits for the entire epic (`src/phase.ts:67-76`) and unions all descendant sources (`src/pull.ts:183`). Shapes explicitly permits issue-level completion ownership (`skills/chart-issues/assets/shapes.md:163`). Merely moving closeSources before rename retains the same delayed issue-source closure. “Issue complete semantics” does not resolve whether broadcasts mean shipped child work or externally closed outer-owner intake. **Alternative:** retain Q6 as an operator fork and give the completion leaf explicit ownership of its answer. Either preserve the delay as an accepted contract or specify how issue-owned sources become distinguishable from epic-owned sources. The latter remains unspecified until runtime ownership can be represented or derived reliably.

- **RB6 · A time window alone does not justify automatically failing a busy agent.** Busy includes blocked (`src/next.ts:72-74,221`), and `tests/next.test.ts:94-114` intentionally verifies waiting without consuming attempts. The state schema contains no progress timestamp (`src/state.ts:10-31`). A timer therefore measures elapsed duration, not a demonstrated stall. **Alternative:** separate the immediately specifiable session/merge-busy corrections from stall policy, and initially signal suspected stalls without interrupting ownership. Automatic failure requires an elected progress signal, deadline and interruption contract, especially during merge. Keep that work unspecified rather than treating a configurable number as the missing evidence.

- **RB7 · Transition-only notification loses recoverability.** State is saved before later effects (`src/phase.ts:50-56`). A crash or notification failure after entry into failed would leave a failed record that never re-enters commitMove. Existing tests require notification failures to remain visible (`tests/next.test.ts:165-173`). **Alternative:** persist successful notification delivery per failure episode and let later sweeps retry unsuccessful delivery, resetting on an explicit restart. This provides recoverable deduplication. It does not promise exactly-once delivery across a crash after send but before recording.

- **RB8 · Herdr notification cannot be the sole dispatch-isolation error report.** Notification itself can fail, as exercised by `tests/next.test.ts:165-173`. Some isolated errors concern a missing registered path before any slug can be read (`src/next.ts:340`, `src/config.ts:69-74`), so a list of skipped slugs is also insufficient. **Alternative:** emit contextual per-scope errors and an aggregate nonzero result as the required outcome. If the operator wants a notification too, make it a secondary summary with repository/path identifiers where slugs are unavailable, and ensure its failure cannot interrupt remaining dispatch or replace the original errors.
