## Material forks

### D1. F13: preserve ownership freshness or reuse owners observed before waiting?

**Evidence:** `src/next.ts:645` through `:695`. The reads surround the global lock. `ownsPane` accepts persisted pane IDs or a live pane cwd inside a leaf worktree (`src/next.ts:163`). `dispatchLeaf` rediscovers a selected slug under the repo lock (`:483`) but does not re-evaluate ownership. Rediscovery therefore cannot fully compensate for a stale owner choice.

A concrete sequence: a bare hook identifies leaf X, then waits for the global lock. The current holder parks X or changes its pane assignment. Today's second lookup can find no owner or a different owner. Reusing the first result instead dispatches the old slug, which can produce a skipped-leaf error or act on a leaf that no longer owns the pane. Herdr can also change its live cwd independently of akrogon's global lock.

**Recommended answer:** preserve the post-lock ownership lookup. Under the note's explicit rule that a speed fix is skipped if it needs more machinery, omit F13 unless the operator authorizes a revised approach. That is a recommendation to change the requested batch, not an already-settled exclusion.

The alternative is to authorize a routing change that performs the needed ownership lookup once under the lock, preserving event short-circuits, explicit-target precedence, and cwd dispatch for unowned operator panes. That requires more than storing the existing first result. Moving all selection under the lock would break explicit-invalid-target tests that require rejection before any flock (`tests/next.test.ts:1565`). Reusing pre-lock owners would instead require explicitly accepting the stale-ownership behavior and an exception to the note's no-snapshot rule. Neither tradeoff should be hidden inside a supposedly behavior-preserving deletion.

### D2. F7: where does the one source pattern live, and may `src/pull.ts` change?

**Evidence:** the pattern is a private literal inside `closeSource` at `src/pull.ts:110`; the note's production edit list includes only state/config/next/phase. There is no existing shared source validator. `pull.ts` already imports from `state.ts` at `:6`.

This keeps the exact existing grammar and avoids two separately maintained literals or a new module. Keep close-source extraction and remote retry behavior unchanged.

A separate source module adds a file for one shared constant. The chart should explicitly settle the small scope allowance rather than leave the implementer to pick silently.

### D3. F6: is the contract the narrow `requireClean` fix or every missing-worktree failure?

Keep the check only at `requireClean`, as the note specifies. Leave already-merged repair, deleted command cwd, non-directory paths, and shell-wide error handling outside this leaf. A universal diagnostic would require additional checks and edit scope.

**Recommended answer:** record deletion as an explicit merge-time action, performed only after successful merge, without introducing a general cleanup mechanism. If the intended meaning is instead “the file should disappear as part of the merged diff,” authorize deleting it in the implementation commit. The final contract must name which interpretation applies. Neither interpretation authorizes deleting the original issue note.
