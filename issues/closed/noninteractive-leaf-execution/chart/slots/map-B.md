## C1 — Execution admits requirements it has not proven

Coverage: #20 events 1 and 5, and #19's preflight observation. Both enter execution with an unproven external prerequisite, but Git readiness and API authorization need different evidence.

**Root mechanism and resolution:** Fresh branch creation uses `target(repo)` without an earlier readiness check (`src/next.ts:241-250`, `src/config.ts:111-116`). A missing local remote-tracking ref therefore surfaces as a worktree command failure, potentially for each eligible leaf. The consumer's initial commit/push fixed its instance, not this admission rule. Charting checks credential presence and records human prerequisites (`skills/chart-issues/SKILL.md:47`), but neither token presence nor successful reads establishes write capability. Planning still postpones missing credentials into operator actions (`skills/plan-issue/SKILL.md:55`). The reported manual scope repair fixed one consumer permission, not the general handoff gap.

**Elegant option:** Make chart handoff the attended admission boundary. Before emitting dispatchable leaf state, establish the actual prerequisites for that work: a usable configured Git base and an operation-level capability proof using the intended account, environment and resource. Record commands, results, cleanup and limits in the chart. Keep Git readiness checked at its runtime use boundary too because handoff evidence can become stale, but do not fabricate a branch or silently use another base. Let the consumer own service-specific probes rather than teaching generic akrogon every API.

**Material forks:**

- **K1:** Explicitly refuse an unborn/missing-base repository versus bootstrap an initial commit/push during attended setup. Recommend refusal with the configured ref and concrete remediation unless bootstrap is explicitly chosen at chart time. A missing local tracking ref is not proof the remote has no branch. Separate absent fetch state from an actually empty remote when defining remediation.
- **K2:** Admission location: chart handoff plus a narrow runtime readiness check versus init-only enforcement. Init-only misses later changes and may forbid useful charting in an uninitialized project. Do not require a base for chart drafting itself.
- **K3:** Evidence for writes: reversible probes where safe versus documented capability introspection or another approved proof where a probe has irreversible effects. Recommend operation-level proof, not a universal “POST then DELETE” recipe. If no adequate safe proof exists, hold the affected handoff for an attended decision. No fallback to GET-only evidence.

**Practitioner questions:** **Q1:** What does the setup owner want for a genuinely empty remote: an explicitly approved bootstrap or a held handoff? **Q2:** Which exact external operations, identities and environments are required, and which can be tested without emails, workflows, payments or other side effects that deletion cannot reverse? These questions belong in charting, never in an execution seat.

**Pitfalls:** “Every write” should mean each required capability/resource context, not repeating identical probes per leaf. Separate permission denial, invalid request, network failure and missing environment values. Do not log tokens or count operator assurances as executed proof. Cleanup failure is failed preflight with recorded residue. Proof can expire, so C2 still needs a legitimate stop path. Credential access itself is not a human-only prerequisite under standing design, but granting a permission unavailable to the agent may be. Name the actual unavailable action.

**Destination:** Proposed akrogon chart `execution-readiness`, covering chart/plan skill handoff rules and the Git admission contract, with separate leaves for independent runtime and skill work. Consumer-specific GHL probe repair/permissions belong to boulevard-automation and its account owner. The generic skill must specify evidence, not hardcode GHL scope names. No auto-bootstrap or live probe is performed by this map.

## C2 — An execution seat can open a human conversation instead of ending its attempt

Coverage: #19's seven-hour stall and #20 events 3, 4 and 7. Event 4 is a recovery-interface consequence, not an independent reason to preserve interactive execution.

**Root mechanism and resolution:** Pi globally registers the question tool and guidelines instructing it to ask for decisions (`~/.pi/agent/extensions/tamdoma-request-user-input/index.ts:989-1011`, README:25-31). The extension emits `herdr:blocked` when a batch is pending (`index.ts:827-828`), and the Herdr bridge prioritizes that over active/idle state (`~/.pi/agent/extensions/herdr-agent-state.ts:187-222`). Akrogon's implementation skill explicitly says to tell the operator and wait on missing credentials (`skills/implement-issue/SKILL.md:39`), contradicting the new operator rule. None of this is resolved by the shipped artifact-placement change.

The lifecycle also lacks the obvious proposed escape: `implement -> failed` is not legal in `src/routing.ts:26-38`, and `src/phase.ts:106-108` rejects it. Failure currently arises through dispatcher retry exhaustion (`src/next.ts:383-385`). “Have the skill call phase failed” is therefore not an implementable skill-only answer today.

**Elegant option:** Give charting an interactive capability and execution a noninteractive capability. Remove the question tool and its asking guidelines from execution seats, preserve it for attended charting, and make lifecycle skills independently state that execution never asks in prose either. At an unforeseen genuinely human-only blocker, preserve partial work and a precise blocker record, end the attempt through a supported command-owned outcome, and notify through C3. Routine engineering choices remain agent-owned within the locked design. This removes the pending-question state from normal execution instead of automating answers.

**Material forks:**

- **K4:** Enforce the capability in Pi execution launch/session policy versus rely on skill prose alone. Recommend capability enforcement plus matching skills. Exact Pi activation API and session-reuse behavior need source verification in pi-extensions before a contract names an API. Do not globally disable questions for charting.
- **K5:** Reuse a reason-bearing `failed` outcome versus add `needs-operator`/waiting state. Prefer reusing failure if it can retain reason, interrupted phase and safe resumption without new counters or parallel state. A new state is justified only by materially different recovery semantics. Either choice needs routing/state/command ownership, not direct skill edits to YAML.
- **K6:** Which authority detects an escaped question: seat-declared blocker, observed blocked event, or both? Recommend an explicit seat stop contract plus immediate event handling for an unexpected required-seat block. A blocked inactive peer must not fail the current pass. Existing coverage deliberately permits blocked B while merge A runs (`tests/next.test.ts:1565-1596`).
- **K7:** Partial-work preservation and recovery: define how the stop works with dirty code, outstanding peer work and current phase guards, and who authorizes a fresh attempt after prerequisites change. Do not weaken normal clean/code-only handoff checks to make exceptional stopping possible. The existing command checks cleanliness before normal moves (`src/phase.ts:117-118`).

**Practitioner questions:** **Q3:** What exact evidence and required operator action must a stopped attempt preserve, and should recovery resume its interrupted phase? **Q4:** Can the Pi owner enforce tool availability for both newly launched and reused execution sessions? **Q5:** Does any required-seat `blocked` state represent something besides a human question that should remain recoverable without ending the attempt? Ask these at chart time.

**Pitfalls:** Disabling a tool does not itself prevent prose questions or create a failure transition. Do not retry-prompt a pending question, type invented approvals through `pane run`, or classify `unknown` as human-blocked. The retry cap cannot rescue the present stall: `dispatchSlot()` returns for blocked/working/unknown before reaching it (`src/next.ts:369-385`). Keep already-running peers and preserved files safe. The seed's `agent prompt` refusal is not proof of a Herdr defect: pending-question replies are a different operation from a new task prompt.

**Destination:** One proposed cross-repository chart `noninteractive-leaf-execution`. Akrogon owns the lifecycle stop/resume contract and its lifecycle skills. Pi-extensions owns contextual tool/guideline availability, with an explicit interface from akrogon's launch context. These changes need coordinated contracts, not an implied shared environment flag. Herdr owns any separately desired typed answer/cancel/read API for general interactive clients. That API is off route for making unattended leaves noninteractive. Consumer repair of the existing pending session is operator-owned.

## C3 — Observed blocked/final states do not become accurate, actionable operator state

Coverage: #19 visibility/notification, #20 event 3's silent duration and event 6's stale busy markers. This class covers state recording and delivery, not preventing questions.

**Root mechanism and resolution:** `busy()` conflates working, blocked and unknown (`src/next.ts:169-173`), and status renders only persisted `busy_since` (`src/status.ts:87-100`). A blocked status event is not discarded: only `working` events return early (`src/next.ts:604-607`), and owner routing dispatches the corresponding leaf (`:655-660`). The event reaches code that treats blocked as busy and waits. The 60-minute notification is checked only on observation (`:179-207`), not by a scheduled wakeup. An isolated block event need never receive a later observation at the threshold. Failed notifications are also only desktop/list notifications on subsequent dispatch (`:479-484`).

Merged state preserves busy fields by spreading prior state in `commitMove()` (`src/phase.ts:26-41`), while next deliberately skips observation for merged leaves (`src/next.ts:468-477`). Merged children can remain visible under an unfinished owner, so this is not only a closed-history presentation issue. The watchdog proves the symptom, and no inspected fix clears it.

**Elegant option:** Record the relevant execution condition on its observed event or explicit transition. A blocked/ended attempt must have a distinct visible outcome and immediate actionable notification, not an aging busy label. Clear live activity metadata when a leaf reaches a terminal outcome, while preserving identifiers still needed for cleanup. Use a single owner for the transition and notification contract. Keep status a read-only view of authoritative state rather than making it poll live panes.

**Material forks:**

- **K8:** A typed persisted seat condition versus representing a human blocker through C2's failure reason only. If C2 turns blocked into failed immediately, do not also invent a second waiting state. If blocked remains observable, distinguish it from working and unknown in state/status. Resolve this once across C2 and C3.
- **K9:** Notification destination and delivery contract. Existing `broadcast.discord.webhook_env` (`src/config.ts:46`) and the skill-local sender provide a transport precedent, but their contract is completed-issue team broadcasts (`skills/broadcast-issue/SKILL.md`, Context/Send), not private actionable failures. Decide whether those exact targets are appropriate before reusing them. Missing configuration and failed delivery must surface explicitly. A remote HTTP success still does not prove the operator saw the message.
- **K10:** Immediate event-triggered delivery with bounded retry versus a durable outbox requiring later execution. Prefer the former for this scope unless crash-surviving delivery is explicitly required. Do not promise exactly-once delivery across a crash between send and persisted acknowledgment, and do not introduce polling to service an outbox. Failure must remain visible even if notification delivery fails.
- **K11:** Clear busy fields at merge plus ignore legacy merged busy data on rendering versus migrate old records. Prefer terminal-state invariants and terminal-aware presentation. Old records need not be rewritten just to stop displaying an impossible live state. Do not delete `pane`, `tab` or `worktree` before cleanup, which still uses them (`src/next.ts:509-515`).

**Practitioner questions:** **Q6:** Which recipient/channel is expected to wake or reach the operator, and what controlled delivery test is acceptable at chart time? **Q7:** Does a recorded and immediately sent actionable failure meet the requirement, or is crash-surviving delivery required? **Q8:** Should long-running work retain its existing observation-based busy notice? That separate policy must not be mistaken for a guaranteed timer.

**Pitfalls:** Do not create a watchdog to discover a state already delivered by an event. Distinguish an observed blocked seat from `blocked-by` dependencies. Ensure duplicate events do not spam or overwrite a newer phase, and no stale peer state fails a current pass. Notify on the stop rather than waiting for another invocation to notice failed state. A CLI-owned notification path must not rely on an already blocked model calling a broadcast skill. Do not reset live busy tracking indiscriminately on every normal phase move without checking cross-seat behavior.

**Destination:** Proposed akrogon chart `execution-outcome-visibility`, coordinated with C2's chosen stop representation. Akrogon owns state, transitions, status, event-triggered notification invocation and tests. Transport extraction/reuse needs a named owner if selected. Herdr notification/read behavior belongs to Herdr only if an independently demonstrated platform defect or missing general interface is selected. Consumer/ operator owns destination provisioning. The terminal busy fix is an independent leaf here and need not wait for Pi capability work.
