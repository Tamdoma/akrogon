# Brief: known-red-filing

## What

A seat that judges a red also red on base, with no cause in the leaf's diff, files it as a bug through the `seed-issue` skill inside its pass, on every route: implement end and check.fix, check.review and check.repair, merge, and the chart door's direct landing. `seed-issue` gains the lifecycle filing contract (what one filing holds, how it returns to the calling pass) and stops letting a closed report hide a red that came back. Filing changes no pass or fail status.

## Why

Tamdoma/akrogon#121: a framework leaf spent over an hour proving 38 reds in an ad-hoc suite were also red on base, concluded "no leaf-caused regression" and moved on. Nothing turned that into a lasting record, so the broken test stayed red for the next leaf. The only existing signal is `akrogon verify`'s herdr main-red notice, which is transient and covers configured checks only. The operator expects a red that is also red on main to be filed as a bug automatically.

## Done-criteria

1. `skills/implement-issue/SKILL.md` Shared context known-red rule states that when the known-red judgment agrees for a configured command, or, for a command outside `checks` (a done-criterion proof or ad-hoc suite), the seat's own completed base run of the same command fails the same tests, the seat files that red through `seed-issue`'s lifecycle filing section inside the pass and records the created or found URL, or the failing command and its error, in `implementation/report.md`; that a green retry (`inconsistent`), a disagreeing judgment, or a killed or incomplete base run is not filed as a base red; that filing changes no verification status, so a red done-criterion stays blocking; and that a `gh` failure while filing is not an operator blocker.
2. `skills/check-issue/SKILL.md` check.review known-red rule states the same filing for either reviewing slot, recorded in that slot's `review-<slot>.md`, and the check.repair pass reaches it through its existing reference to that paragraph.
3. `skills/merge-issue/SKILL.md` red verify paragraph states the same filing on both triggers of criterion 1 (a known-red pass the judgment agrees with, or a completed base run of a command outside `checks` failing the same tests when the pass holds that evidence), recorded in `review-B.md`, adding no proof run and relaxing no proof requirement. (A,B)
4. `skills/chart-issues/SKILL.md` `## Direct route` landing step 3 states the same filing by the door on both triggers of criterion 1 (a known-red pass its judgment agrees with, or a completed base run of a command outside `checks` failing the same tests when the attempt holds that evidence), recorded in `<chart>/direct/report.md`, adding no proof run and relaxing no proof requirement. (A,B)
5. `skills/seed-issue/SKILL.md` holds one lifecycle filing section that the four seat skills point to, stating: one report per observed defect, grouping commands and failing tests only when evidence supports a common cause, otherwise separate reports; the report names the exact command and scope, the head and compared base SHAs, the retry result, a short failing excerpt, the kept log paths and the leaf, and claims nothing about main beyond the compared SHA; the filing reuses the evidence the calling pass already holds and starts no extra verification; and its final two lines go into the caller's pass record while the calling pass continues to its own phase action and footer.
6. `skills/seed-issue/SKILL.md` lookup rule states that a closed report covers a failure only through an open report it names that covers it (closed as a duplicate); a supported recurrence of a defect whose closed report's fix was delivered, or a current defect with no open covering report, posts with the closed report on its Related line, never reopening or commenting on it. Open-report coverage by mechanism is unchanged.
7. `git --no-pager diff --name-only "$AKROGON_BASE"...HEAD` lists only the five skill files above.
