## Q3 stored names (leaf stored-failure-names, blocked by failure-names)

- [corr] `verifyRunSchema` command entry gains optional `failures`: a non-empty deduplicated string array holding exactly what the name reader returns for that entry's live log at write time. It is written only where the command itself ran and exited non-zero: never on `blocked`, `reused`, exit 0, or an entry pushed because setup failed, and never holding `(log gone)`.
- `flips` and `newRedUnits` use `failures` when present and the log otherwise. `knownRedReceipt` never reads `failures` and always reads both logs with the current reader.
- Rows without the field parse as today.
- Stated cost: an akrogon older than this change cannot parse a ledger holding the field.

Pitfalls avoided, binding: names come from tool structure only, so planted free text never becomes a name; per-stream collection keeps a failed script beside a named failure; a wrapper never doubles a name; padding never changes a name; a coarse name always gets the whole two-log read; stored names never let a missing log through `verify --known-red`; a blocked, reused or setup-failed entry stores no names; the symlinked `skills/lifecycle-rules.md` is edited in place.

Excluded here, owned by `failure-names`: Q1 (the names), Q2 (the seat texts) and Q4 (the read on a lookup miss). This leaf calls that reader and changes none of it.

## Leaf architecture

- Owned surfaces: src/verify.ts (`verifyRunSchema`'s command entry, the sites in `runOnce` where a command result is recorded, `newRedUnits`); src/flaky.ts (`flips`, and the call that turns a live log into names at write time); the tests that show criteria 1 to 5 (tests/verify.test.ts, tests/flaky.test.ts, tests/receipt-gates.test.ts only if needed); docs/reference/files.md; src/AREA.md.
- Literal interface: `failures?: string[]` on an entry of `commands` in a `verify-runs.jsonl` row, non-empty and deduplicated when present. Unchanged: every other field, `z.strictObject`, the `akrogon flaky` line, the notice text, the `verify known-red` line.
- Where it is written: `runOnce` (src/verify.ts) records a command result in several places. Only an entry whose own `checkedRun` returned a non-zero code gets `failures`: the sequential check site and the `merge_checks` member site. The entries pushed when setup failed (they copy `setup.code` and `setup.log`) and the entries pushed with `blocked` (they copy the blocker's exit and log) get none. `runOnce` writes no `reused` entry today (C); `reused` exists in the schema so old rows parse, and readers that skip a `reused` entry keep skipping it before any name is read. The schema states only the field's shape (optional, non-empty, deduplicated); which entries carry it is the writer's rule, shown through what `akrogon verify` writes. The names come from the log file `checkedRun` just wrote, read directly at its path, so a holder outside the `issues/` grammar stores its names too. Open for the plan: the exact sites and whether the pass that writes a base run for `--known-red` shares them.
- Changed state and its consumers: a command entry may now hold names. `flips` (src/flaky.ts): decision, stored first, log otherwise. `newRedUnits` (src/verify.ts), both the unit list for the current run and the match against earlier runs: decision, stored first, log otherwise. `knownRedReceipt` (src/verify.ts): decision, never reads the field, always reads both logs through the reader, so a gone log still refuses. The boundary for an already-recorded pair is the receipt gate (`requireGreenReceipt`, as the existing linked-pair refusal case in tests/verify.test.ts exercises it); `verify --known-red` reuses a completed red head row but always starts a fresh base run when the base tree has no whole-green row, so only the gone-head half shows at that CLI. (B,C) `readVerifyRuns` and every caller that parses the ledger through `verifyRunSchema` (src/status.ts `scanRepo`, src/flaky.ts `flakyCommand`, src/verify.ts): decision, the optional field parses, rows without it parse as today. Any code that rewrites the whole ledger must carry the field through: Open for the plan, name each rewrite site (the locked final rewrite in `runOnce`, the notice and slow updates) and confirm it writes parsed rows back whole.
- Stated cost, observed at charting (P3): today's `verifyRunSchema` rejects a row holding `failures` with `unrecognized_keys`, so an akrogon older than this change cannot read a ledger written after it. akrogon is installed once per machine, so one release moves every reader; a rollback past this change needs the field removed from the rows first. No migration or backup machinery is built.
- Existing cases that stay: tests/verify.test.ts `the receipt schema accepts both old entries and entries carrying a reused source run`; the deleted-log, packed, corrupt-archive and missing-member cases in tests/flaky.test.ts, which use rows without the field.
- Exclusions with owners: the name grammar, the seat texts and the read on a lookup miss (leaf `failure-names`); recovery of rows whose log is already gone, in akrogon or framework (off route in the chart, signpost 4a); a separate index file (foreclosed); `issues/` (none touched by the branch; the ledger is written by the command at run time, not by the leaf).
- Dependencies: `failure-names` (blocked-by), for the names the writer stores.
