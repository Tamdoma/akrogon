# Brief: failure-names

## What

The name reader `failedTests` (src/flaky.ts) names a red log from the lines Bun itself prints, per stream: a real `(fail) <title>` stays as it is; a failed script whose stream printed no `(fail)` line becomes `(script) <script>`, read from Bun's `<chain> | Exited with code <n>` line with the innermost script kept and wrappers dropped; a bare `(fail) (unnamed)` becomes `(unnamed) <script>`. A log with none of these keeps `(no test name)`, and no name ever comes from free text or from a `Signaled:` line. On a lookup miss the reader opens the recorded file when it still exists.

Every user of the name follows with no compare change of its own: `akrogon flaky` lists the script, `akrogon verify --known-red` no longer covers a head red in one script by a base red in another, and a red-main notice no longer folds a new failed script into an earlier different one. The seat judgment in skills/lifecycle-rules.md (`## Red check with no cause in the leaf's diff`) and in landing step 3 of skills/chart-issues/assets/direct-route.md requires the whole two-log read whenever any red name on the head is not a real test title. docs/reference/checks.md, docs/reference/files.md and src/AREA.md state the changed names.

No new configuration, no record field (that is `stored-failure-names`), no change in src/evidence.ts or `akrogon log`, no compare by output or exit code.

## Why

Tamdoma/akrogon#134: in framework, whose verify command fans out to 168 scripts, 13 flips showed as `(no test name)` and 2 as `(unnamed)` although each red log names the failed script in Bun's own exit line; `test:remote-image` flipped 8 times in two weeks with no name and no fix was opened. The same placeholders are the comparison keys of `verify --known-red` and of red-main notices, so two different nameless reds under one configured command compare equal and only the reviewing seat stands between them. In 23 framework logs a failed script beside a named test failure is dropped silently.

## Done-criteria

1. For a red-then-green flip whose red log comes from a Bun fan-out in which one script exited non-zero without printing a `(fail)` line, `akrogon flaky` lists the flip under `(script) <innermost script>`: the same name whether the script ran under one wrapper or another, no entry for a wrapper script, and no `(no test name)` entry. When the same log also holds a real `(fail) <title>` on another stream, both the title and the script are listed. It fails on the base and passes after.
2. A bare `(fail) (unnamed)` line is listed as `(unnamed) <innermost script>` when its stream carries a script and as `(unnamed)` when it carries none. A real `(fail) <title>` behind a script prefix is still listed by its title alone. Both hold when the log also holds that script's own `Exited with code` line and its wrapper's: no `(script)` entry appears for that script or for its wrapper. (C)
3. A log whose only failure-looking lines are free text such as `[FAIL] ...` or Bun `Signaled:` lines, with no `Exited with code` line and no `(fail)` line, is still listed as `(no test name)`; such lines beside a real name add no name.
4. `akrogon verify --known-red` judges `fail`, so the head does not satisfy the receipt gate while its runs stay recorded (B), for a head whose configured check is red only in script X when the completed base run at the merge-base holds the same command red only in script Y, neither log holding a `(fail)` line; it fails on the base, where this pair passes. The same failed script on both sides still prints `verify known-red <sha>: pass`, and a single-command check naming nothing on both sides is still covered as before.
5. A red on main in script Y of a configured check is reported as a new red while an unresolved, already-noticed red of the same check in script X exists; a repeat of script X is still not reported twice.
6. A red check whose recorded log is an existing regular file outside the `issues/(open|closed|parked|chart)/` path grammar is read: its flip is listed by its real name and a known-red pair written with such a holder is judged from both logs. A recorded path with no file is still `(log gone)`, and a path inside the grammar still resolves through its owner and archive first.
7. skills/lifecycle-rules.md `## Red check with no cause in the leaf's diff` and landing step 3 of skills/chart-issues/assets/direct-route.md each state that the whole two-log read applies when any red name on the head is not a real test title (`(script) ...`, `(unnamed)`, `(unnamed) ...`, `(no test name)`), that only a head whose red names are all real test titles also failing on the base takes the named branch, and that tests or hooks that timed out inside a run that ended with the runner's own summary are the command's own verdict. Neither still limits the two-log read to a log that names no test. The four skills' `lifecycle-rules.md` entries (plan-issue, implement-issue, check-issue, merge-issue) are still symlinks to the one file. (C)
8. docs/reference/checks.md (`## Known red`, the `akrogon flaky` paragraph and the `verify known-red <sha>: fail` row), docs/reference/files.md (the `akrogon flaky` paragraph) and src/AREA.md's verify paragraph state the names the reader returns and where they come from, and none still says a name comes only from a `(fail)` line.
