## Fixes

**F1. An unchanged returning leaf skips its required base verdict when main has stayed put.** `src/land.ts:139–153` matches the previous red run by holder SHA and excludes every run on the current SHA. When the current holder already descends from main, `buildStack` can produce the same SHA again. In the local CLI reproduction, a real Bun test on main failed with the same name twice. The first top, previous red SHA, second holder and second top were identical. The second `land` moved the leaf back to `check.repair` with zero base passes and no `base_verdict`. This leaves a reproducible main red undiscovered and blocks criterion 9. The tests at `tests/merge-red-exit.test.ts:524–660` seed a previous receipt at a different SHA, which lets the test miss the normal unedited return. Add the actual red exit and `phase … merge --slot B` round trip to the proof.

**F2. A previously covered title can trigger an extra base suite.** `src/land.ts:212` uses the whole-run cover verdict. `taken8Trigger` at lines 157–168 then treats any repeated failing title as eligible. For example, a previous red run can contain only alpha. Before the leaf returns, another base comparison can establish coverage for alpha and a new change on main can make beta red. On the rebased return, the run has alpha and beta, only alpha repeats, and only beta is uncovered. The code runs the base suite even though no uncovered failure repeated. This consumes the merge line outside the exception in criterion 9 and Taken 8. The deleted same-tree test in `tests/green-merge.test.ts` also protected the distinction between an older covered run and a newer run with an uncovered failure. Its `Test-Change` citation justifies replacing the seat assertions. Keep that behavior covered at the land boundary.

**F3. A green leaf receipt reused at the base can be lost from the exit record.** `src/verify.ts:199–206,1013–1018` accepts a whole-green row by tree and command list across scopes. In this repo, leaf and merge have the same command list. A normally landed leaf can therefore leave only its green leaf-scope receipt on the new main tree because merge reused that receipt. When the base pass for a returning red leaf skips on that row, `src/land.ts:173–195` looks only for a merge-scope green row and omits `base_verdict`. B loses the evidence for deciding the second red. Criterion 9 requires the actual row that stood in for the base pass. The existing green-base test seeds only a merge-scope row.

**F4. A wake can take over a failed restack and record the old base.** After a non-fast-forward refusal, `restack` in `src/phase.ts:807–843` writes `applied: true, top: undefined` when the build conflicts or applying it hits a dirty worktree. On that path it keeps the old `built_on`. A concurrent listener wake or `akrogon next` can enter the legacy branch in `src/next.ts:965–985` before the live land process writes its exit. That branch does not check `landAlive`, moves the leaf to repair as a conflict against the old base, and clears the batch. The intended land exit then becomes stale. An operator editing a holder during a refused push can reach the same state and get a conflict record for a dirty worktree. Both violate the exit record in criterion 2 and send B to rebase against the wrong commit.

**F5. The repair instructions can rerun a full configured suite and route a main red to A.** A B seat following `skills/check-issue/SKILL.md:101` is told to run leaf-scope `akrogon verify --known-red` after an untouched-diff merge red. That command can run the full `checks` set when the merge receipt differs from the leaf command list, and this repo includes a full test suite in `checks`. The paragraph also allows a repeated failure to go to `check.fix` without reading the named base result for that unit, and omits the `failed` ending for an uncovered main-caused red. A base run can be red overall while the repeated unit itself was green. Taken 3 and criterion 10 require narrow reproduction, an unchanged return when B clears the red, the main-red stop, and a unit-specific base judgment when Taken 8 triggered. `skills/lifecycle-rules.md` currently repeats the full leaf-verify instruction for merge exits.

**F6. The report omits required proof and some named scenarios lack an assertion.** The committed green receipt covers the suite as it stands. The report gives a blanket claim that all 18 cases ran red before implementation. It provides no deliberate break evidence by criterion or base/head runs for criterion 4, and the history contains tests and product changes together. It also lists standalone commands without their kept results or an equivalence record for changed proof commands. The dirty and restack-conflict cases in `tests/merge-red-exit.test.ts:210–295` have no second queued leaf and therefore cannot catch a missing next turn in either case. The dead-B case does not constrain capacity, so it cannot establish the cap condition in criterion 4. Existing file runners and fixtures can prove these cases. Keep the current green receipt and add the missing evidence under the plan's proof rule.

**F7. The linked operator docs send readers to the retired merge-seat workflow.** `docs/use/a-working-day.md:14` tells the operator B takes over with merge-issue after a red or rebase. `docs/use/when-work-fails.md:50` tells an operator with a push error to wait for B, although `src/land.ts:99–125` moves that leaf to `failed` for operator recovery.
