# Brief: command-owner

## What

The lifecycle skills state one rule, written once in `skills/plan-issue/SKILL.md`: a done-criterion locks only its observable result, and `plan.md` owns the command that proves it. When a proof command is wrong (it departs from the repo's configured runner semantics, or it is red for a cause outside the leaf while the criterion's result holds), A replaces it with a command that observes the same result, preferring the repo's configured runner, and records the old command, the new command, the reason and the evidence. B judges the correction in review. B in `check.repair` and in merge hands a proof-command correction to A instead of making it. A runner command already written inside a criterion counts as proof under this rule; an invocation that is itself the product behavior the criterion names stays locked. A correction never widens a live or paid action. The citations of the undefined `test-proof-rules` in `implement-issue`, `check-issue` and `merge-issue` point to this rule instead.

## Why

In framework leaf `registered-rule-loading` (#105) a criterion named a plain `bun test` over three files; the repo's runner uses `--isolate`, and the plain command had the same 9 failures at base and head. Seat A treated the command as locked brief text and stopped for the operator, who changed only the flag: about 25 minutes and an operator round trip, a recurrence of #47. The rule already exists in pieces that do not meet: `shapes.md` says a criterion is an observable result, `plan-issue` maps each criterion to its command, and three skills route a wrong criterion unit to A "under `test-proof-rules`", a closed leaf's slug that no seat can read.

## Done-criteria

1. `skills/plan-issue/SKILL.md` states the rule above once: the result is locked, the proof command is the plan's, who corrects it (A), the preference for the configured runner, the equivalence guard (the same tests and cases still run and a deliberate break still fails), what A records (old command, new command, reason, and evidence of that guard), that a runner command inside a criterion is proof, that a product invocation named as the result stays locked, and that a correction never widens a live or paid action (C).
2. `skills/implement-issue/SKILL.md` lets A correct a wrong proof command during implement and `check.fix` under that rule before any failure ending; every place that stops on a wrong criterion (the Shared context failure ending and the `implement` test-writing paragraph) applies only when the criterion's result itself cannot be shown within the leaf (C); and in `check.fix` a merge-returned failure whose cause is the proof command keeps its original failure evidence, reruns the corrected command with unchanged coverage, and may return to review without the old command turning green, while configured `checks` keep their receipt and known-red requirements (B).
3. `skills/check-issue/SKILL.md` has B, in `check.review`, judge a recorded correction against the rule's equivalence guard by naming that `plan-issue` section, not restating it (C), and has B, in `check.repair`, list a needed proof-command correction under `Handed to A` instead of making it; `skills/merge-issue/SKILL.md` routes the same correction to A.
4. No text under `skills`, `docs` or `README.md` cites `test-proof-rules`.
5. On the direct route the door corrects a proof command under the same rule and records it in `<chart>/direct/plan.md` (`implement-issue` `Direct form`), and B in `check-issue` `Standalone review` judges the proof mapping and any correction from `<chart>/direct/plan.md` (B,C).
