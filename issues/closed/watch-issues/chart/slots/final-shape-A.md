# Proposed final shape · watch-issues (after operator round 1, 2026-09-19)

Operator answers verbatim: "1 - It should be watching everything that I start. For example, I might start a whole epic and then when the new epics start being created in tabs, it should take care of all of them. But only the things that I start. However, when I do start them they should all be watched | 2a | 3 - There should be only one skill, /watch-issues. We need to create this skill. When this skill activates, the skill also contains the scripts folder according to the naming conventions and patterns across the board that we have inside of Acrogon. Push back on this if you don't think this is a good idea. | 4 - It can restart the failed leaf as many times as necessary in order to make the work move forward. Remember the intent is to have the same thing as me. This is replacement for me at times when I'm away. [...] | 5a - Basically when everything that I started is done or when I tell it to stop and that I will take over | 6a - A small notes file. Maybe that is not necessary at all because of the context compaction. I'm trying to create the least amount of movable parts and the least amount of complexity as possible. Only introduce new files and mechanisms is absolutely necessary."

Shape:
1. Scope: every leaf under issues/open of the registered repo, re-read at each fire. Every leaf there was handed off by the operator (handoff is an operator door), so "everything I start" = the open tree; later-dispatched leaves of an epic are included automatically. Repo-scoped `akrogon next --all` (cwd = registered root) is therefore allowed; targeted `next <slug>` when one leaf is the anomaly.
2. Interval: 20 minutes.
3. One skill `skills/watch-issues/` with `SKILL.md`, `package.json`, `scripts/observe.ts` + `observe.test.ts` (convention: skills/broadcast-issue). `/watch-issues` invoked directly: runs one check and, when CronList shows no job whose prompt is `/watch-issues`, creates one (`*/20 * * * *`, prompt `/watch-issues`, recurring) and reports the id and the 7-day expiry. Each scheduled fire runs the same skill: the check. `/watch-issues stop`: CronDelete that job, no check. No `/loop` needed by the operator, though `/loop 20m /watch-issues` would also work. Claude Code only: when CronCreate is absent, the skill says so and ends.
   observe.ts (read-only, bun): reads every state.yaml under issues/open, calls `herdr agent list` once, prints one line per leaf: slug, phase, attempts, per-seat pane + live status + busy age, failure cause/reason when failed, blocked-by. Tests with fixture states and a fake herdr response.
4. Authority per fire: (a) leaf waiting for a pass (idle seats, phase needs dispatch): `akrogon next`. (b) failed leaf: read `failure.reason`, the seat pane, and the leaf artifacts; if the cause is something a pass can move (delivery, transient error, exhausted attempts whose last error is gone), `akrogon phase <slug> <failure.phase>` then `next`, as many times as the work keeps moving forward; if the reason names a human prerequisite (credential, permission, operator decision) notify once with the required action and leave it; if the same failure repeats with no new evidence, notify and leave it (repeating an identical failure is not moving forward). (c) busy seat: read the pane once; notify only on concrete evidence of a stop (error loop, fatal message, dead process); never kill, never send keys. (d) command errors: report. Never: edit state.yaml, worktrees or issues/; open .env; answer a seat; `phase failed`.
5. Stop: the fire deletes its own job when no leaf remains under issues/open with a phase other than merged (closed inventory moves them), or when every remaining leaf is failed on a human prerequisite already notified; or the operator runs `/watch-issues stop`. 7-day expiry stays the cap.
6. No ledger file. Cross-fire memory is the session context (and its compaction summary). Repeat-notification suppression uses existing records only: failed leaves already got their failure-attention notice at the transition; the fire notifies about a failed-on-human-prerequisite leaf once per fire only when it took a recovery decision, otherwise it stays silent about an already-announced failure. Busy notices: `busy_notified` in state.yaml already dedups the core one-hour notice; the fire adds a notice only with new evidence.
7. Bash timeouts only on read-only commands (observe.ts, herdr reads); `akrogon next` and `akrogon phase` run without a timeout; an interrupted or failed mutation is re-read from state before any further action.
