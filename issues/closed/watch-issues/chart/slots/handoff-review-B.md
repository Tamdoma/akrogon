1. **F1 — Recovery eligibility contradicts the Taken two-cycle rule.** Draft `watch-issues-skill/brief.md:4` requires that the last recovery moved forward, but criterion 5 explicitly permits a second recovery after the first immediately fails again. The Taken Q4 and `design.md:24` stop only after two consecutive unproductive recoveries. **Fix:** replace the brief's condition with the two-cycle rule. Define its computation as ordered records for the exact repo/slug: pair `failed -> P` with that slug's immediately following move; `P -> failed` is an unproductive cycle, another transition is progress. `src/log.ts:19-27` provides the necessary fields. Read/filter enough history to establish both cycles, not an arbitrary global `tail` (`design.md:20`), which can omit this leaf's records in a busy repo. Missing or malformed history must produce unknown eligibility, not zero prior failures. Add synthetic log cases for interleaved slugs, progress between recoveries, and insufficient history.

2. **F2 — Re-notification cannot update the state used by the stop rule.** `design.md:23,27` re-notifies when `failure.delivery != shown`, then stops only when it equals shown. A direct `herdr notification show` does not update that field; only failure announcement inside the lifecycle command does (`src/phase.ts:48-71`). With state edits forbidden, a successful lead re-notification leaves the field unchanged, so the skill cannot meet the stop condition and will notify again next fire. **Fix:** for the current fire, treat either persisted `delivery: shown` or that fire's successful `shown` response as evidence of notification. Use that evidence in the stop decision. If other leaves keep the watch alive, retain the re-notification outcome in the allowed context carry and explicitly specify behavior when that carry is lost. Do not promise durable dedup from a field the skill cannot change. This is a defect in the recorded rule itself, not something the implementer can repair by adding unauthorized state.

3. **F3 — Job identity and zero-match behavior are inconsistent.** `brief.md:4` and Taken Q3 create on zero matches, but criterion 3 and `design.md:20` require exactly one match or end. Matching any prompt that ends with the root also permits deleting another scheduled task. **Fix:** use the complete canonical `/watch-issues tick <absolute-root>` prompt as identity. Specify zero/one/multiple behavior separately for start, tick and stop: start may create on zero only after a nonterminal initial check; tick never creates; stop on zero reports already stopped; ambiguous matches are reported without deleting a guessed job. A start whose check already satisfies completion must not create a job afterward. Include spaces in root paths in the invocation contract.

4. **F4 — The waiting rule misses an idle required peer while the other peer is working.** `design.md:21` requires all required seats idle or absent. In check.review, A may be working while B missed its prompt; this rule never dispatches B. The existing command intentionally handles required slots individually (`src/next.ts:475-478`) and skips the busy/done slot (`:350-354`). **Fix:** permit targeted next when at least one required unfinished seat needs dispatch, leaving the command to guard the other seats. Add the mixed A-working/B-idle case to the walkthrough. This does not weaken failed-recovery quiescence.

5. **F5 — Busy diagnosis depends on an observation the helper omits, and adds an unowned one-hour gate.** `design.md:25` requires the core notice to be absent, but the helper fields at `design.md:18` omit `busy_notified`. More materially, Taken Q4 and the brief allow judgment on a concrete stop; they do not require waiting an hour or ignoring a new fatal error after an earlier generic busy notice. **Fix:** allow a bounded pane read when current evidence warrants investigation, with age only a triage hint. If core-notice status is needed for dedup, include `busy_notified` in the observation. Test that a prior generic core notice does not hide new actionable evidence.

6. **F6 — Legacy failed records and malformed inventory need defined non-mutating behavior.** `src/state.ts:44` makes failure optional, so a valid legacy failed leaf may have no failure.phase/reason/delivery. The draft helper and recovery rule assume all three, while criterion 1 tests only unreadable files. A malformed or foreign-repo state must also never be treated as an empty tree that causes cron deletion. **Fix:** specify schema validation, root/repo identity checks, and an unknown-failure display; legacy failures lacking a recovery phase are notify-only. Add malformed YAML, invalid phase, legacy failed-without-failure and wrong-repo negative fixtures. The injected fake Herdr path is workable in Bun; also require nonzero/invalid-JSON Herdr responses to fail observation rather than become missing panes.

7. **F7 — A copied AKROGON_HOME alone does not isolate the end-to-end walkthrough.** Criterion 5 and `design.md:13` call a scratch AKROGON_HOME copy safe, but registered repo paths in that config can still point at the live store, and Herdr still receives the inherited session environment (`src/shell.ts:17-23`). Cron tools are also not part of a Bun process. **Fix:** construct temporary registered repositories/worktrees and rewrite the fixture config to those paths; route every Herdr call through the fake command, including notification and tab rename. Distinguish a simulated cron walkthrough from an actual Claude Code activation/deletion test. If real cron evidence is required, name the Claude Code test harness as a prerequisite rather than declaring that an arbitrary implementer can produce it from scratch AKROGON_HOME alone.
