### Q1 · Should intervention require a repeated action/result pattern, or also allow demonstrated drift from the leaf contract?

A loop is repeated completed work without new information or a changed approach. It is different from one silent command still running. For example, repeating the same failed probe after identical errors is evidence; rerunning a test after each distinct patch is productive iteration. A seat modifying unrelated files may be off-task without repeating itself.

Research: **operator** — the current request explicitly includes doing something they should not be doing, not only exact repetition. **practitioner** — [OpenHands detector](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py), lines 18,59-75,141-166,251-280: a bounded active-branch event window, matching action/observation pairs and alternating patterns. **better-than-training** — installed `/home/ivan/.pi/agent/extensions/tamdoma-pi-tweaks/index.ts:12-20,34-60` already hashes tool name/input/content and steers after 30 repeated results in a 40-result window. This favors contextual lead judgment on the remaining cases, not another numerical detector copied into akrogon.

- **A (recommended):** Require concrete evidence of either repeated completed action/result cycles without progress, or a specific action contradicting the locked brief/design. Read a bounded recent pane history, then the relevant artifact/contract. Three matching completed cycles are a useful investigation cue, not an automatic verdict. State the repeated action or violated requirement and what must change before intervening.
- **B:** Intervene only on repeated action/result cycles; notify on suspected off-task work. Narrower and easier to explain, but misses the operator's broader drift concern.

Pitfalls: Screens can truncate earlier steps or show the same output twice without another execution. A spinner, busy age, blocked status or unchanged screen is not a loop. If Herdr's visible/recent output cannot establish the sequence, report insufficient evidence rather than inventing it. Do not ingest unbounded session history or env contents. Child activity shown in a parent pane is not proof the child has a directly addressable Herdr pane: children are SDK sessions (`S/child-session.ts:666-683`). The existing parent/child guard is already loaded by path (`S/worker-tools.ts:30-33`, `S/child-session.ts:612-619`), so check whether it already intervened before duplicating it.

### Q2 · May the lead send one concrete corrective instruction to the seat without interrupting it?

Recommend a small, evidence-based intervention that tells the seat which approach failed and which allowed next step resolves it. “Continue” alone is not a resolution. Example: identify the repeated wrong path, point to the authoritative path in the brief, ask the seat to use it and verify the criterion. The lead must not supply credentials, relax acceptance criteria or invent a new design decision.

Research: **practitioner** — OpenHands' `get_action_error_nudge` targets the failed action and asks for corrected arguments or a different approach, with duplicate-error suppression (source above, lines 198-225). **better-than-training** — `H/src/app/api/agents.rs:62-110` submits text then Enter to the foreground agent; it is not a pi RPC steer call. Installed pi's interactive submit path uses steering while streaming (`P/dist/modes/interactive/interactive-mode.js:2530-2541`); its SDK documents delivery after the current assistant turn's tool calls finish (`P/docs/sdk.md:224-234`). This supports non-interrupting input but does not guarantee immediate receipt by the model.

- **A (recommended):** Authorize `herdr agent prompt <verified-seat-pane> <correction>` once for an evidenced problem, after checking the pane still hosts the expected seat/session and its editor is not holding operator input. Use ordinary text, not slash commands. Ask the seat to explain the changed approach briefly and execute the next contract-consistent step. On later observation, verify actual receipt and changed behavior before calling the intervention successful. For a nested child, address its parent with the evidence and requested correction; do not assume a child pane exists.
- **B:** Queue no mid-turn instruction. Deliver the correction only once the seat is idle, otherwise notify. This avoids competing steering but cannot redirect an actively repeating turn while the operator is away.

Pitfalls: A Herdr success response or `--until working` is not proof the corrective message was consumed, especially when the seat was already working. A timeout is not permission to resend. Pi extension input handlers can intercept text, so do not mimic child-answer syntax or interactive answers. A queued instruction cannot free an indefinitely running tool or a parent waiting on a child that never returns. Explicitly accept that unresolved case as notify-only under current locks. Before handoff, use a small synthetic same-version test: busy pi receives one ordinary correction, consumes it at a safe boundary, and no concurrent command is cancelled. Source inspection supports the mechanism; this pass has not performed that live test.

### Q3 · Should failed steering lead to notification, or a cooperative seat stop followed by existing recovery?

Esc is not a harmless way to wake pi. Its interactive handler aborts a streaming run or user bash (`P/dist/modes/interactive/interactive-mode.js:2253-2258`); bash's abort path kills its process tree (`P/dist/core/tools/bash.js:64-86`). Calling `akrogon phase failed` changes bookkeeping, not the running process, so it cannot substitute for safely stopping a tool.

Research: **practitioner** — [SWE-agent reference](https://swe-agent.com/latest/reference/agent/), `handle_action` and `forward`, uses consecutive timeout and total runtime limits; this gives bounded recovery but its interruption behavior cannot be imported under this lock. **better-than-training** — `src/phase.ts:198-209` records a failed stop without process cancellation; `src/phase.ts:95-111` resets phase completion state during recovery. Taken Q4 already requires quiescence and stops recovery after two consecutive unproductive log cycles. A steering-only loop has no phase transitions, so that existing log bound alone cannot limit repeated messages.

- **A (recommended):** One correction for the same evidenced problem; no repeat without confirmed receipt plus materially new evidence or a changed proposed resolution. If the correction cannot be delivered or the same loop continues, notify with the unresolved cause and leave running work intact. After compaction, unknown intervention history is not proof no correction was sent. Check existing pane/session evidence; if it cannot establish receipt/history, do not send another. Existing failed-leaf recovery remains separately authorized by its Taken rules.
- **B:** In addition, allow the corrective instruction to ask the seat to finish its current safe boundary, record the blocker in its pass artifact and declare `akrogon phase <slug> failed --reason ... --slot <S>` itself when it cannot find a permitted resolution. Only after all relevant seats are quiescent may the lead use the existing judged recovery policy. More autonomy, but no guarantee the looping seat will cooperate, and no permission for the lead to fabricate its stop.

Pitfalls: Do not rename a productive process “stuck” to exempt it from the no-kill rule. Neither option allows Esc, Ctrl+C, closing a pane, resetting a working phase, editing the worktree directly, or repeated vague nudges. A completed command followed by the next identical mistake is measurable recurrence; a queued message that has not been consumed is not a failed correction yet. Two recovery cycles can be computed from lifecycle logs, but correction dedup relies on actual message evidence/context and must fail conservatively if unavailable. Continuing to monitor other leaves remains allowed.
