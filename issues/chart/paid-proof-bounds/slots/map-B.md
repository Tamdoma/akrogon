## F1 — #102: one invalid state blocks unrelated work

**Verdict: confirmed mechanism, overstated universality.** `src/state.ts:readState` rejects `reported` and `notes`; `allLeaves` parses both open and closed trees before returning any leaf, and `findLeaf` uses that global scan. `src/config.ts:effectiveConfig` also scans every leaf merely to resolve the caller's seat configuration. `src/run-check.ts` uses `allLeaves` to identify its caller. A scratch reproduction with one valid and one invalid leaf produced the reported `unrecognized_keys` error from `allLeaves`, while reading the valid leaf directly succeeded.

It is not literally every command: `src/next.ts:discover` already catches individual unreadable states and reports them, while later merge operations still call the throwing `allLeaves`. `src/status.ts:scanRepo` has another traversal whose outer error handling loses the repository's normal inventory. This is inconsistent fault isolation, not just a strict-schema defect.

**Deeper cause and smallest coherent simplification.** Three inventories attach different failure meanings to the same filesystem. Consolidate discovery around a parsed result that retains both valid leaves and invalid paths, replacing the duplicate walks in state/next/status. Keep invalid state visibly invalid, and let operations needing that leaf refuse with its path and cause. Remove unrelated all-repository validity requirements from targeted operations. Some new result typing and caller handling are needed; deleting strictness alone does not solve missing required fields or broken YAML. Evidence: the functions above, plus `tests/state.test.ts`, test “migration retains strict validation of unknown keys, required fields, known values and YAML shapes”.

**D1 — material fork.** Tolerate arbitrary extra keys, or retain strict lifecycle state and isolate errors. Recommend strict state plus isolation. Changing `strictObject` to stripping unknown fields is the smallest patch for these two keys, but silently loses annotations on a later save and hides misspelled optional control fields. Adding `reported` and `notes` to an allowlist repeats the current migration exception pattern in `readState`.

**Q1 — practitioner question.** Which operations truly require complete inventory, and which need only the requested leaf? Missing prerequisite information must remain blocking for dependents, not become “dependency absent means satisfied”. Inspect callers of `allLeaves`, `src/turn.ts:eligibility`, and source-ownership operations before setting the boundary.

**R1 — lifetime pitfall.** An unreadable leaf must retain its filesystem identity for cleanup purposes. `src/reconcile.ts:reconcile` currently has a separate `collectSlugs` walk that catches parse errors with the comment “unreadable state.yaml protects nothing”. Reusing a valid-leaves-only list for cleanup could treat live work as unowned. The consolidated boundary must preserve unknown ownership, duplicate-slug and foreign-repo diagnostics. No evidence establishes why the original seat wrote those keys. The current affected state has been repaired. A promise that a seat *cannot* write invalid YAML requires an actual write boundary, not another prose reminder; do not claim isolation supplies that guarantee.

## F2 — #103: completion depends on a disposable worktree

**Verdict: confirmed defect, conditional rather than “never completes”.** `src/pull.ts:closeSources` resolves the comment's commit from worktree HEAD before checking any source. `src/reconcile.ts:removeMergedWorktree` clears the worktree and deletes its branch. `src/phase.ts:completeOwner` may defer closure until all issue leaves merge, and retries use whichever merged leaf triggered completion. Thus an earlier leaf can lose the only commit source this function accepts before a later completion call.

The initial merge does attempt completion immediately: `src/phase.ts:commitMove` saves the merged phase, then calls `completeOwner`. Also, `src/reconcile.ts:mergedWorktree` retains an open leaf's worktree when `ownerCompletes` is true. These guards explain why the defect is not universal. They do not protect an earlier merged sibling while its owner is incomplete. `src/next.ts:dispatchLeaf` later retries completion for merged leaves. The example `framework/issues/closed/check-accuracy/component-loader/component-loader/state.yaml` is now closed with no worktree, so the reported 20 stuck leaves are historical evidence, not a verified current backlog.

**Deeper cause and smallest coherent simplification.** A durable business transition uses a temporary execution directory as its evidence. Remove the worktree argument/dependency from source closure. Pass a durable landed commit recorded with the merged transition, before follow-up operations can fail. That requires a small persisted commit field and plumbing through successful push/recovery paths, then repository-root source closure. `src/phase.ts:batchPush` already knows the pushed head and member tips. `src/state.ts:stateSchema` has no durable landed commit; `merge_stamp` is a timestamp. Batch data is temporary.

**D2 — material fork.** Record durable completion evidence, or retain all merged worktrees until all source closures finish. Recommend durable evidence. Retention keeps disk, branch and cleanup policy coupled to GitHub availability and sibling progress. Using the operator checkout's current HEAD would be simpler but can cite an unrelated or stale commit (`src/self-update.ts:moveCheckout`).

**Q2 — practitioner question.** Does a source shared across several leaves cite the final owner's completing commit or each leaf's landed commit? Preserve current owner-level closure semantics, but name the witness explicitly. `completeOwner` closes private sources at issue completion and remaining shared sources at epic completion. For old merged states without worktrees, use verified landing evidence or an explicit repair step. Do not fabricate historical commit identity.

**R2 — lifetime pitfall.** Reusing only `issues/log.jsonl` is insufficient for new transitions: `commitMove` saves state first and appends through `logMove` afterward, which can fail. `src/log.ts:logMove` also substitutes repo-root HEAD when no worktree exists. Preserve closure retry before archive movement and the existing idempotent `closeSource` behavior. This chart does not require changing cleanup policy.

## F3 — #104: red stack information expires after each successful merge

**Verdict: confirmed recurrence, with two important corrections.** `src/batch.ts:pickMembers` selects all eligible followers. `src/attempts.ts:redMemberHeads` excludes red heads only on the same `built_on`. `src/phase.ts:phaseCommand` records a red membered attempt, restores the holder, and starts that holder alone. The next successful holder changes main, allowing the unchanged failed followers into the next stack.

A member rebase conflict does **not** fail the whole stack: `src/batch.ts:buildStack` skips that member and continues. Its `ok: false` path is the holder's rebase failure. A `red` attempt recorded through `phaseCommand` is therefore not a counter of rejected member rebases. Also, `members` excludes the holder. The report's 32 rows with `members.length > 1` omit two-leaf stacks. Recounting `framework/issues/merge-attempts.jsonl` through 2026-10-18 07:54:59Z gives 242 rows, 32 with more than one follower (31 red, one merged), and 41 with any follower (36 red, four merged, one ejected). Its stated outcome totals themselves sum to 242, not 241. The poor outcome remains real.

**Deeper cause and smallest coherent simplification.** The system deliberately forgets adverse evidence when an unrelated change lands. Remove the base equality from automatic follower exclusion, so an unchanged head that appeared in a red stack stays eligible as holder but is not repeatedly carried as a follower. This needs no new culprit command, scheduler, bisection or size parameter. It prevents this specific repeated-head waste while keeping unlimited green batching. It does not repair bad leaves or promise a particular throughput gain. Evidence: `redMemberHeads`, `pickMembers`, `src/turn.ts:mergeQueue`.

**D3 — material fork and existing lock.** Keep per-(head,base) retry, or exclude the same red head across base changes until its head changes. Recommend the latter, but explicitly reopen the recorded red-skip choice. `issues/closed/merge-batch/stacked-turn/design.md`, Binding decisions, records the operator's “No caps at all”, all-or-holder batching, and foreclosure of bisection, `--culprit`, caps and speculative trains. It also records A's per-(head,base) refinement. Do not silently resurrect the older batch-limit/culprit choices in `issues/chart/merge-throughput/forks/batch-size.md`. The new recurrence evidence challenges the refinement's stated “one extra verify wall” cost: the same members can impose that cost after every main move.

**Q3 — practitioner question.** How much wasted verification comes from unchanged member heads versus new heads, and what green batching opportunity is lost by excluding innocent co-members? Red aggregation is not proof that every member is faulty. Exclusion should affect batching eligibility only, never correctness verdicts or the normal holder repair route. A conservative exclusion costs innocent members a solo turn; retaining retries risks unbounded repeated aggregate runs.

**R3 — lifetime pitfall.** A main change can repair a previously red combination, so persistent head exclusion intentionally trades that acceleration opportunity for finite repeat waste. Conversely, using only a whole-stack fingerprint lets the same offender reappear with different companions. Adding automatic blame would need evidence not supplied by aggregate exit status. Current `attemptRecordSchema` has no culprit field, so absence is not a failure to populate a supported current feature.

There is concrete current evidence of product/contract reds, not just host load: `framework/issues/open/redirect-inventory/run-binding/run-binding/review-B.md:129-153` records attempt `ed08c3f0-ab4a-4449-9b0c-89ea18b8e85a`, setup success, four hooks failures attributed to formspark-settings-update, url-serving and purchase-facts, and a memberless restart. This is practitioner evidence from that review, not an independently rerun full suite. Do not infer that every historical red shares its causes.

## F5 — #106: identical ignored files are treated as destructive collisions

**Verdict: confirmed.** `src/sync.ts:integrate` builds a set from incoming tree paths plus paths touched by local replay history, then rejects every ignored path intersecting a file or directory shape. It never compares content. Both `syncCommand` and `src/self-update.ts:gitStage` call it.

**Deeper cause and smallest coherent simplification.** The guard equates path overlap with data loss. Retain overlap discovery and type/ancestor collision protection, but reject a same-path ordinary file only when the relevant replacement representation differs. Remove unconditional same-path rejection. A small content/type comparison is necessary; deleting the entire guard is unsafe.

Scratch probes on Git 2.56.0 used an ignored `collision` file, then an incoming commit force-tracking it. Both `git rebase --autostash <incoming>` (sync's operation) and `git read-tree -m -u <base> <incoming>` (self-update's move) succeeded for equal bytes **and differing local bytes**. In the latter cases Git replaced `operator bytes` with `incoming`. Temp repositories were removed. This confirms the missing comparison and disproves “Git will protect differing ignored content for us”. Existing tests in `tests/sync.test.ts`, “sync preserves ignored … against …”, intentionally preserve differing content across incoming and replayed paths.

**D5 — material fork.** Define equality as regular-file content with explicit type/mode rules, or rely on Git's default overwrite behavior. Recommend explicit comparison. Do not bypass checks merely because a blob hash happens to match while filesystem types differ.

**Q5 — practitioner question.** Which target is being compared when local commits are replayed? The guard includes incoming paths and local history; matching origin's blob alone does not establish safety for every replayed replacement. `integrate` must preserve its existing local-commit protection as well as allow the reported equal incoming file. Follow the actual move paths in `syncCommand` and `self-update.ts:gitStage/moveCheckout`.

**R5 — lifetime pitfall.** Test symlink versus regular file, executable mode, directory/file conflicts, filters/line-ending conversion, and local changes between comparison and move before broadening equality. Reuse the equality concept already present for tracked/untracked colliders in `self-update.ts:moveCheckout`, but its `hash-object` comparison is not by itself a proof for ignored symlinks or replay history. Keep differing files intact on refusal. No fixture relocation or ignore-rule cleanup is needed to fix this chart.

## Shared mechanisms and chart split

**F6.** #102 and #104 both enlarge failure impact from one unit to unrelated work, but their mechanisms and outcomes differ: schema inventory versus speculative merge eligibility. #103 and #106 both depend on Git lifecycle details, but one needs durable evidence and the other needs a preservation check. #105 shares verification vocabulary with #104 but changes contract ownership rather than queue scheduling. None is a prerequisite for another. Evidence: the functions and contract rules cited in F1–F5.

**D6.** Keep these five destinations separate:

1. **C1 — Leaf-state isolation (#102):** invalid leaf state remains visible and blocks only work whose correctness depends on it, while unrelated commands continue.
2. **C2 — Durable sourced completion (#103):** landed owners close their sources and archive successfully after worktree cleanup and through completion retries.
3. **C3 — Finite repeated stack waste (#104):** unchanged heads from failed stacks stop consuming repeated aggregate verification as main advances, while batching and solo correctness gates remain.
4. **C4 — Behavioral acceptance contracts (#105):** correcting an incidental proof invocation does not require changing the requested outcome or an operator rescue.
5. **C5 — Lossless identical-file sync (#106):** equal ignored files can become tracked while genuinely differing content and filesystem-shape collisions remain protected.

Do not introduce implementation dependencies simply because charts touch shared files. C1 and C2 may both edit state typing, which calls for merge coordination, not a product dependency. Within C2 only, recovery of historical merged states may depend on the chosen durable-evidence implementation and must be an explicit repair step, not a reason to retain worktrees forever.
