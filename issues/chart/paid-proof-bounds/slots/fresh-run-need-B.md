# Slot B: fresh-run-need

## 1. Pick, reason and cost

**O1 — Reuse genuine model output while running the changed product and its consumers for real. Pay for a fresh affected model stage when its model-facing inputs/contract changed, the capture is no longer applicable, or the property requires a new live interaction. Require a full fresh pipeline only when the whole run is the property or no smaller existing proof establishes it.**

This is substantially the existing rule in `skills/chart-issues/assets/standing-design.md:10,15-16`, not a new testing architecture. It already requires cheapest sufficient proof, real recorded model/outside stages, a fresh call after prompt/model/settings/output-contract changes, changed-stage/consumer reruns, and full fresh runs only where justified. The defect is its translation into concrete plans and later reruns. Current implementation/check rules already preserve unaffected green proof, but identify changed “proof inputs” broadly without distinguishing a changed consumer from an invalidated model capture (`implement-issue`, implement:67; `check-issue`, check.repair:93).

The inspected plans make that ambiguity expensive. Hub-child-links' W3 says any failure restarts the same full command in a fresh evidence directory. Replay-cases' verification table triggers a full paid replay on “leaf head or plumbing fixture change”, with restart from scratch. A new commit is provenance, not evidence that every model stage changed. Those plans convert deterministic repairs into another end-to-end model sample.

**Cost and limits:** maintain trustworthy captures, identify what the diff actually invalidated, and run affected deterministic consumers against those captures. This needs reviewer judgment, not a guessed cache key or a new state field. A saved final result is not enough: current product code must execute where its behavior is being proved. A failed run can provide real inputs for a repair test without proving the entire pipeline passed. I cannot assign an exact number of avoidable paid runs from the summaries alone.

Limit-mechanism Taken is settled: every fresh paid launch still consumes the one lifetime grant. A missing capture, a replay miss or a failed test does not authorize automatic live execution. No counter, native cap or provider stop is proposed. Framework stage resume remains off route under operator 4a.

## 2. Rejected options

- **O2 — One new full paid run after every failed attempt, change or review.** Reject. It repeatedly samples unchanged model stages to discover deterministic defects and ignores recorded-output reuse. The two plans show this policy concretely. It also cannot guarantee a green result when nondeterministic workers still misbehave.
- **O3 — Always reuse the most recent output.** Reject. A previous response does not show a new prompt, model contract or live dispatch path works. Capture provenance and actual inputs matter more than recency. A historical completed stage cannot certify an unexecuted later stage.
- **O4 — Exactly one live run, once at the end, for every leaf.** Reject. Entirely deterministic leaves need none, while a genuine later model-facing change may need another authorized capture. One successful sample also does not prove reliability. That blanket count belongs neither in this fork nor as a replacement for bound-unit.
- **O5 — Build stage resume or a general record/replay service now.** Reject under operator 4a and existing machinery rules. Reuse can start with existing consumer tests, saved outputs and renderer checks. If a necessary proof truly lacks sufficient machinery, expose the limitation and stop/amend its contract through the authorized route; do not claim the smaller proof exists.

## 4. Pitfalls and what removes each

- **R17 — Calling unchanged saved model output a fresh-model proof.** Label the captured stage and the actual current consumers executed. State which live/model behavior remains untested. Do not alter capture bytes or provenance to match a new head.
- **R18 — “Input changed” expands to the whole repository.** The plan identifies the real dependency of the acceptance property. Shared-file/env/lockfile changes require analysis and rerunning affected consumers; they are not automatic permission to resample every model stage. If the dependency cannot be established, keep the proof unresolved and apply the bound/stop rule.
- **R19 — A cassette miss secretly spends money.** No live fallback. A missing relevant capture requires an explicit, grant-covered fresh call or an operator blocker. Preserve raw failed input before cleaning a run folder.
- **R20 — Replacing a statistical failure with one lucky green sample.** Record worker-conformance failures and avoid claiming reliability from a single run. The chart must ask for the actual behavioral property; expanding this into a repeated sampling campaign requires its own explicit scope and authorization.
- **R21 — Prose promises stage reuse that existing commands cannot perform.** Name actual existing consumer checks and what they prove. When the only available full-proof runner starts from scratch, never invent stage-resume support or count an isolated consumer check as its full receipt. The old locked criterion stays unverified until legitimately proven or amended.
- **R22 — Different seats each buy the same evidence again.** Review the retained record and dependency changes, and run the deterministic current consumer proof needed for the verdict. Fresh paid execution is triggered by invalidated evidence/live behavior, not seat identity or phase change. All uses still share the settled lifetime authorization.

- **Q15 — Does “fresh paid run only where model behavior is under test” include actual live session admission, hook permissions, routing and recovery?** Those can require a real interaction without testing prose quality. F17/F21 show why a text-only definition is too narrow.
- **Q16 — What is the required property when the existing runner enforces an exact-head full receipt?** Retain that requirement and pay for an authorized whole run, or amend the contract to the actual sufficient product proof. Skills alone must not weaken its checker.
- **Q17 — Must existing live leaves' contracts be corrected now, or only future handoffs?** This is a main-record/operator action, not a leaf's unilateral edit. The reports' prior waivers do not authorize changing other leaves.
- **Q18 — Are the raw captures and consumer inputs actually retained and runnable with existing tools?** Summary logs can diagnose a defect without supplying a replayable state. If the required artifacts are absent, do not claim a particular past paid run was avoidable with certainty.
