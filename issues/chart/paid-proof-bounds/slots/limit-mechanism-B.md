# Slot B: limit-mechanism

## 1. Pick, reason and cost

**O1 — Pick the written grant rule for this chart.** Extend the existing authorization boundary to paid or quota-consuming model launches, including launches hidden inside proof runners. Make each launch consume the same operator-approved total across probes, retries, repair seats and replacement sessions. Put the authorization and evidence in the existing grant and pass artifacts. Add no akrogon counter, launcher, gateway, watchdog or pricing calculator.

The confirmed defect is that local Claude launches were classified as having no external effect and therefore received `grants: []`, while reuse instructions checked authorization only “before mutating”. The current grant already has billing effects and repeat/recovery bounds. Correct that boundary instead of maintaining a separate paid-session permission system. Sources: `skills/chart-issues/SKILL.md:63`, Take; `skills/implement-issue/SKILL.md:53`, Shared context; `skills/check-issue/SKILL.md:35`, Shared context; `src/readiness.ts:grantSchema`.

**Cost and accepted limitation:** this is a seat-followed rule. It cannot guarantee that a noncompliant process stops spending. A lost or ambiguous usage record must stop further paid launches rather than reset the allowance. A numerical allowance also does not by itself cap money spent inside one long run. The next bound-unit fork must settle what is counted and how a multi-session runner fits the allowance. Do not claim that this pick creates a hard financial ceiling.

An akrogon counter would not remove the fragile interpretation by itself. `src/run-check.ts:checkedRun` executes arbitrary argv; one shell command can launch many model sessions. The framework's `lib/session-trace.ts:launchSkillSessionAsync` launches Claude through `runSession`/`Bun.spawn`, and seats can invoke Claude directly. There is no exclusive model-call boundary in akrogon. A counter at `run-check` would count wrappers unless runners also cooperated, and direct commands could bypass it. Genuine enforcement requires a different execution/credential boundary, not merely an integer in state.

This pick preserves proof-cost's prohibition on automated budgets/timers. The operator must still approve the concrete grant-bound policy through this chart. I do not interpret the older lock as forbidding an operator from giving a bounded authorization. If the operator instead requires prevention independent of seat compliance, reject O1 and reopen the lock explicitly for actual call-boundary enforcement.

## 2. Rejected options

- **O2 — Add an akrogon-enforced counter now.** Rejected because counting arbitrary `run-check` commands does not count the paid operations inside them. Reliable enforcement would require all launch paths to reserve from a common durable allowance before spending, with concurrency, crash recovery and bypass prevention. It would also reopen the existing operator lock. A schema counter without that boundary creates an inaccurate enforcement claim. Evidence: `src/run-check.ts:runCheck/checkedRun`, `src/readiness.ts:grantSchema/gaps`, framework `session-trace.ts:buildArgv/runSession/launchSkillSessionAsync`.
- **O3 — Require Claude `--max-budget-usd` as the whole solution.** Rejected as a substitute for the leaf total. The documented cap is per print-mode run, uses estimated cost, can overshoot, and excludes restored earlier totals on resume. Another fresh process gets another allowance. It counts subagent spend in that run, but does not provide an aggregate allowance over every separately launched parent and rerun. It could bound one invocation after a separately approved future decision and real proof, but is not a complete answer here. [Claude CLI reference](https://code.claude.com/docs/en/cli-reference), read 2026-10-19.
- **O4 — Keep current prose and show a larger estimate.** Rejected because the existing estimate is deliberately information only and the actual example has no paid grant. More cost disclosure does not change what authorizes the next launch. Sources: proof-cost/proof-run Taken; chart-issues Handoff; hub-child-links readiness in the #107 evidence.
- **O5 — Adopt an organization gateway or provider-budget service in this chart.** Rejected for current scope. This is the strongest external pattern for hard fleet limits, but it changes how model traffic and credentials are controlled and introduces service dependencies. It does not follow from choosing a small correction to this repository's grant workflow. If the operator wants a hard ceiling, this class of approach deserves its own concrete design rather than a nominal shell counter.

## 4. Pitfalls and what removes each

- **R11 — Another session treats the total as fresh.** Remove the reset by keeping launch intent and result evidence in the existing authoritative leaf artifacts, carrying the same grant through every handoff. Neither disposable evidence folders nor the agent's memory is the record. If prior consumption cannot be established, stop further paid launches and ask the operator to settle it.
- **R12 — Two seats each see the same remaining allowance.** A written rule needs an explicitly accountable launch owner or preallocated authorizations between simultaneous seats. Settle that before handoff in bound-unit; otherwise O1 has a concurrency hole. Do not silently add a reservation service under the label “written rule”.
- **R13 — A single runner or model process spends much more than expected.** Require its transitive fan-out to fit the chosen grant unit and expose known limits. A run count is not a dollar ceiling. If the required guarantee is monetary, choose actual model/provider enforcement instead of O1.
- **R14 — Red-check retry and final-proof rules are read as overriding the grant.** T5–T7 explicitly make authorization a prerequisite. At exhaustion, the proof stays unverified and the existing operator-action route applies. Never mark it green because the allowance ran out.
- **R15 — A paid “reply OK” probe or a delayed reset retry is called free setup.** T1/T2/T4 include paid probes before the first proof, and provider resets do not renew the operator's authorization. Cleanup that launches models also needs coverage; ordinary deterministic cleanup remains required.
- **R16 — A nominal counter makes the operator expect a hard ceiling.** State the pick's behavioral limit in the final contract. If enforcement is chosen instead, prove rejection at the actual call boundary, including direct and nested launches, before claiming the destination delivered. No test asserting particular prose is adequate proof.
