# Blind notes: fresh-run-need (slot C)

## 1. Pick, reason, and cost

**Pick: freshness is decided by whether the model stage's named inputs changed, not by the pass, the head, or a repair round. No new freshness rule is needed; propagate the standing-design rule that already exists into plan, implement, and check rerun decisions.**

A saved real run answers a proof when all of these hold:

1. The inputs that determine the model or outside stage's output are unchanged since it was recorded: prompt, instructions or templates, model pin and settings, input data and fixtures, context, tool or provider contract, and output shape. Shared files, lockfiles, and env count when they feed that stage.
2. The recording is complete, unpatched, and carries provenance: source run, revision or date, capture command, model/settings, and the artifacts reviewers need.
3. Every deterministic consumer, checker, renderer, and later stage runs for real on the final head against the saved output.

Pay for a fresh run only when a named input above changed, the outside system makes the recording unreliable, no sufficient recording exists, or the criterion itself is fresh-start, ordering, concurrency, live-orchestration, or whole-run behavior that a saved stage output cannot exercise. An unknown input dependency counts as changed.

That is already the standing design, almost verbatim:

- Cheapest sufficient proof; a real model call is justified when that behavior is under test; a slow/live run names what no smaller test proves (`standing-design.md:10`).
- Model and outside stages replay one real run's recorded output with provenance, never hand-patched; a prompt, model, settings, output-shape, or outside-call change runs one real call through the consumer and re-records (`standing-design.md:15`).
- Rerun changed stages and their consumers; a clean full run is required only when reuse cannot be shown or fresh start, order, or whole-run behavior is under test (`standing-design.md:16`).

The rules fail to reach three later decisions:

- **Planning.** `plan.md` maps a criterion to a command, size, and "rerun trigger" (`plan-issue/SKILL.md`, plan synthesis), but never asks for the model stage's input set, the saved recording it may reuse, or which deterministic consumers run real. Both framework plans therefore translated "one full replay" into a fresh-run loop: hub-child-links' plan says "on failure rerun the same command against a fresh evidence dir" with a rerun trigger of "templates, brief or verify changes" (`.../hub-child-links/plan.md:52,61`), and replay-cases uses "leaf head or plumbing fixture change" and "failed full replay restarts from scratch" (`.../replay-cases/plan.md:51,53`). A verify change is deterministic downstream, and a head change alone says nothing about model inputs.
- **Implement/check reruns.** Implement reruns each proof whose "inputs (files, helpers, fixtures, config, lockfiles) changed" (`implement-issue/SKILL.md`, implement end), and check does the same after repair and can reject proof run before the latest helper change (`check-issue/SKILL.md`, check.review/check.repair). Neither partitions inputs by stage, so any touched helper in a large replay buys a whole fresh paid pipeline. Check B "replaying the exact command" (check.repair) also reads as fresh execution, not replay of saved stage output through real consumers.
- **Saved-output durability.** The standing chain rule assumes recordings in the consumer's own suite. A failed run's `.temp` consumer tree is a debugging artifact, not yet reviewable proof, until its provenance and path are recorded in the report or it is promoted to a durable fixture. The intake's `rm -rf` pattern destroyed exactly the evidence that would have answered the next question.

Concrete sentence changes under this pick:

- `standing-design.md:15` (chain bullet): widen the opening scope from only "one leaf's output consumed by code another leaf owns" to any multi-stage proof, within one leaf as across leaves. No other words in the bullet change; its re-record triggers are already the freshness test.
- `standing-design.md:16` (slow/live bullet): replace "the final proof must be valid at the final commit" with "deterministic consumers and checks in the final proof run at the final commit; a reused model or outside stage must have named inputs still valid at that commit." Delete "when unsure it restarts from a trustworthy point" as a paid-run instruction, or qualify it to deterministic stages: uncertainty about a model stage makes reuse unshown (fresh or blocker under the settled grant rule), it does not silently buy a full restart.
- `shapes.md`, `## Preflight and validation` audit: add one refusal to the existing live-run clauses — refuse a live-run done-criterion whose brief/design does not name the property a saved stage output with real consumers cannot prove. A criterion worded as a fresh/full replay is accepted only when fresh or whole-run behavior is that property.
- `plan-issue/SKILL.md`, plan synthesis criterion mapping: for a model/outside stage, the plan names its input set (the re-record trigger), the recording it reuses or the one fresh call that creates it, and the deterministic consumers/checks that run real. A rerun trigger of "head changed" alone is invalid for a paid stage. The sentence "a whole run the brief names stays" gains: a named whole run may replay saved model stages through the real spine unless the brief names fresh whole-run behavior as the property.
- `implement-issue/SKILL.md`, Shared context proof order and implement-end rerun rule: partition "inputs changed" by stage. Deterministic stages and consumers rerun real; a model/outside stage reuses its recording while its named input set is unchanged and reliable. The report section for slow runs (already: "reused stages with their source commit") also names the recording's provenance and the input set judged unchanged.
- `check-issue/SKILL.md`, check.review planned-test check and check.repair rerun rule: "current" proof for a model stage is a final-head real consumer/check run over an eligible recording, not a new generation date. In check.repair, "B runs planned live proofs itself, replaying the exact command" becomes: B first replays the recording through the real consumers; B pays fresh only when eligibility fails, within the settled grant bound.

Deleted text: "final proof must be valid at the final commit" as a blanket freshness claim, and the unqualified restart-from-trustworthy-point clause. Nothing else needs new prose; in particular no freshness text goes into briefs case by case, and no code, hash, or expiry machinery is added.

Cost: the eligibility judgment ("did anything that feeds the model stage change?") is a seat judgment and can be wrong in both directions. The named input set written at planning is what makes that judgment reviewable instead of vibes.

## 2. Rejected options, each with reason

- **Always fresh at the final head** (the current practical reading of implement/check rerun rules). This is what burned the spend: it pays full price to rediscover deterministic defects one per run and samples model variance until a lucky pass. A fresh date is not evidence quality.
- **Never fresh after the first recording (cassette forever).** A recording silently goes stale when prompts, model pins, provider behavior, input data, or output contracts change, and it can never prove new writer instructions are actually followed. Standing design already rejects this through its re-record triggers (`standing-design.md:15`).
- **Time-based expiry (re-record every N days).** Arbitrary, and the leaf-run-stalls lock forbids clock triggers. Input-change is the meaningful event, not age.
- **Automatic hash/cassette invalidation machinery in akrogon.** Adds a tool to maintain, and a content hash cannot see provider-side model drift, env, or whether a changed file actually feeds the model stage. The plan naming the input set is the reviewable version of the same idea with no code.
- **Build stage-resume into the framework replay runner now.** Would make fresh cheaper, but the operator split answer 4a (2026-10-18) already declined charting it, and it does not answer this question — a resumable runner still reruns paid stages whose saved output was sufficient.
- **Treat a partial or failed saved run as proof of the whole criterion.** Both leaves closed criterion 4 by operator acceptance over incomplete runs. Acceptance is an operator waiver recorded as such; generalizing it would make "deepest failed run" a proof form and destroy the meaning of the criterion.

## 4. Pitfalls, with what removes each

- **P1. Silent provider drift.** A pinned model name can change behavior provider-side, so identical named inputs still produce different output and the recording quietly stops representing the live system. Removed partially by provenance (model pin + date on the recording) and by the unreliable-recording trigger; a criterion that asserts *current* provider behavior must say so, and then it is a whole-run/live criterion that pays fresh. Residual: drift between recordings is invisible until someone re-records.
- **P2. One lucky output treated as conformance proof.** A single saved good run shows the pipeline *can* produce compliant output once; hub attempts 12–15 show the same pipeline also produces non-compliant output. Removed by criterion honesty at charting: if the property is reliability across runs, the brief must name that (and pay for sampling under a grant), instead of a "one full replay" criterion silently collecting samples until one passes.
- **P3. Losing the artifact.** `.temp` consumer trees are deleted by cleanup, worktree removal, or the seat's own `rm -rf`. Removed by: a recording counts as proof only when durable — a committed fixture in the consumer's suite (standing pattern) or a preserved evidence path with provenance in the implementation report. If it is gone, reuse "cannot be shown" and the standing rule already requires the fresh run or the blocker stop.
- **P4. Hand-patched or cherry-picked recordings.** Editing saved output to green is fake proof; selecting the one flattering run from many is the quieter version. Removed by the existing "re-recorded never hand-patched" plus provenance (capture command, head, run id), and by check seats reading the recording's source run in the report, including failed attempts already counted under the settled grant.
- **P5. Input-set omission.** Lockfiles, env, shared templates, and a changed upstream deterministic producer all feed model inputs; miss one and reuse proves the old pipeline. Removed by the standing "shared files, lockfile and env count as inputs" and "unknown counts as changed," made concrete by the plan naming the set. If a deterministic producer *before* the model stage changes its output, the model stage's input changed — fresh for that stage, not reuse.
- **P6. Whole-run side effects a cassette cannot exercise.** Lease binding, dispatch/concurrency, session recovery, and fresh-start state live in the launching, not in stage outputs. Removed by criterion wording: when orchestration behavior is the product (replay-cases), the criterion names whole-run behavior and pays its one fresh run; saved transcripts still prove the recovery *logic* offline, so the fresh run is final confirmation, not discovery.

## 5. Questions this fork does not ask

- Q-C1. When no durable recording exists yet, may an implementing leaf create and commit one as a test fixture in the consumer's suite, or is that "proof machinery" requiring a prerequisite leaf under standing-design line 10? My read: a recording is test input, not a runner or dispatcher, so the leaf that makes the one authorized fresh call should be able to keep it — but the line should be stated, or every leaf will re-litigate it.
- Q-C2. May a later leaf reuse a recording captured by a *different* leaf at a different head, if model pin, settings, prompts, and input data match but surrounding deterministic code has moved? Standing design's chain rule implies yes (consumers run real at the current head), but nobody has said whose provenance and upkeep a shared recording carries when it goes stale.
