## C2 — Agent tools can access the protected file directly

**Mechanism:** The confirmed leak used a shell tool, so blocking only Pi's read/edit/write tools misses the observed path (E2). Pi's call hook can deny a known operation before tool execution (`PI/docs/extensions.md:790-817`), but a shell command is a program, not a reliable file-access declaration. Akrogon's inspected launcher constructs harness arguments and starts agents; it is not the interception point for their subsequent shell/read calls (`src/next.ts:215-222,389-404`).

**K3 — Skill-only prohibition versus runtime interception:** Recommend a pi-extensions-owned guard plus consistent skill prose. Reject direct protected-file reads and writes through supported structured file tools and recognized shell operations before execution. Return a clear policy error naming the file class and allowed loading route, without question dialogs or values. Do not silently rewrite a forbidden command into another command or append redaction pipelines on its behalf.

**K4 — How strong must “never opens” be:** A call hook with command recognition prevents the accidental patterns reported here, but does not establish a security boundary against arbitrary shell code, interpreters, aliases, symlinks or scripts that open the same file. Likewise, an allowed arbitrary `bun --env-file ...` script can read and print `process.env`. Recommend explicitly scoping the first runtime contract to supported tool operations and tested accidental disclosure paths. If “never” means an absolute isolation guarantee, the alternate design is a restricted credential-operation interface whose untrusted tools cannot access the file or credentialed environment. That is a materially larger architecture decision, not something a few command regexes can honestly promise. No sandbox, broker or external service is proposed without that scope decision.

**K5 — Protected paths and trustworthy access:** Define protection by the authoritative credential file and its resolved aliases across the registered checkout/worktrees, not just the substring `.env`. Decide whether `.env.example` and ordinary documentation references are outside protection. Runtime loading remains allowed, and the extension's internal access needed for filtering must be distinguished from model-visible read tools. Do not ban all commands mentioning `.env`, since that would reject the explicitly sanctioned loader.

**Practitioner questions:** **Q3:** Is the intended guarantee prevention of accidental operations in this installed Pi toolset, or isolation from any program the model can execute? **Q4:** Which credential-file paths and aliases exist across registered roots/worktrees, and should nonsecret templates stay editable?

**Pitfalls:** Check redirection, shell expansion, relative paths, symlinks, patches, editor tools and subprocess interpreters. Avoid equating a file name match with actual access. A blocked call must not become a silent success or an automatic retry loop; `terminate` alone is not a lifecycle stop and only terminates a parallel batch under the documented condition (`PI/docs/extensions.md:792-793`). Keep the known allowed credentialed-call route working.

**Destination D2:** A new pi-extensions chart for protected credential-file tool access and safe tool-result handling, with a clear, bounded promise. Akrogon owns the cross-harness skill contract, not Pi tool middleware. The installed Pi hook implementation lives in the registered `/home/ivan/.pi/agent/extensions` repository. Do not add an akrogon command that merely moves the same unsafe arbitrary shell access behind another name.

## C3 — Tool output enters the transcript before a guaranteed secret filter

**Mechanism:** A successful allowed credentialed call can still echo values in stdout, stderr, structured details or an error, so source-file blocking alone is insufficient. Pi's `afterToolCall` runs extension result hooks and uses their returned content/details (`PI/dist/core/agent-session.js:244-270`); tool-result messages are then persisted at `:388-398`. That supports filtering final result messages before persistence, not a blanket claim that all streams or artifacts have been sanitized. Partial tool updates have their own event path (`:537-545`).

**K6 — Replacement strategy:** Recommend local exact-value filtering using values acquired privately by trusted code from the protected credential source, applied to all supported tool results, not only calls whose command mentions `.env`. This covers an API error containing a token and the numbered grep result observed here. Key-name patterns alone miss unlabeled credentials. Preserve the tool's error status and useful nonsecret diagnostics. Do not send output or credentials to an external redaction service.

An alternative is dropping entire results from credential-related operations, which hides useful verification and still misses unrelated commands that print inherited values. Arbitrary encoding, fragments, images and unknown secrets are not guaranteed covered by exact-value replacement. Define these limits explicitly. Empty/common nonsecret values must not make the filter destroy every result; classification of secret versus ordinary configuration belongs to the contract.

**K7 — Final results versus every persisted/visible channel:** Before claiming “before transcript,” prove the exact storage boundary with a synthetic secret. Cover result content and details, error messages, tool arguments already containing a value, partial updates, truncation spill files and parent/child sessions. `tool_result` does not retroactively erase a secret emitted in an assistant tool-call argument or previously persisted message (`PI/dist/core/agent-session.js:394-398`). If the needed guarantee includes those paths, assign an earlier wrapper/persistence boundary or explicitly hold that claim until verified. Do not implement a final-result filter and describe it as universal log sanitization.

**K8 — Root versus child sessions:** Recommend one enforcement contract active in every Pi execution runtime that can access the file, including delegated workers. The fact that the API package is installed under tamdoma-subagents does not prove child hook inheritance. Verify this with a child runtime fixture and do not rely only on redacting the parent's returned child summary after the child has written its own log.

**Practitioner questions:** **Q5:** Which channels count as transcript for this deployment: model context, JSONL, visible streaming output, spill files and worker logs? **Q6:** Can the installed child runtime inherit the same guard, and where does it persist results relative to hooks? **Q7:** How should trusted filtering obtain and refresh secret values without exposing them or adding a watcher?

**Pitfalls:** Use synthetic values for tests and never copy the production incident into fixtures. Test exact values both labeled and unlabeled, numbered/prefixed lines, multiline results, stderr, details and errors. A newly operator-written value must become protected without a poller; define refresh at an existing command/session boundary rather than assuming a launch snapshot remains correct. Filtering should fail explicitly if required trusted loading fails, not silently emit unchecked output. No result hook repairs an already written log.

**Destination D3:** Same pi-extensions chart as D2 because both intercept the same execution surface and share protected-source configuration. Access prevention and output filtering may be separate leaves only once their common source/coverage contract has an owner. Consumer scripts must still avoid printing credentials. The broader cross-harness guarantee is not achieved merely by this Pi-specific implementation.
