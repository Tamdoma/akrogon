Blind notes B: turn-count
Evidence dates below are read 2026-11-16. Recommendations are design judgments, not observed new behavior.

Q1. Count location
Pick: count in next.ts dispatchSlot when a delivered prompt's turn is observed completed without a phase report, before deciding to redeliver or replace. Remove increments from seat.ts startSeat and dispatchSlot deliver. Keep the limit at 3. Persist counted_prompt.{A,B}, each the existing Prompted shape {address,turn}, identifying the delivered prompt already charged. Compare it with prompted[slot], and charge at most once when the same address has seat.turn > prompted.turn and is idle, done or finished. Then save attempts and counted_prompt together. A missing terminal provides no completed-turn evidence. Cost: one small persisted cursor and changed existing tests.
Reject: count on delivery, because it charges starts that die mid-turn. Count every hc turn delta, because unsolicited turns and a changed address are not additional deliveries of the phase task.
Evidence: operator tier, INTAKE #137 and signpost 4a, 2026-11-16. Better-than-training tier, inspected startSeat, firstTask and dispatchSlot: working proves delivery, increments happen on delivery, and replacement currently precedes the limit check.
Pitfalls/removal: failed redelivery must not charge the same old prompt again, removed by counted_prompt. Repeated wakes must not change the count, removed by persisted prompt identity. A confirmed working start does not reset silent-turn history. commitMove clears counted_prompt with prompted and attempts on every phase move. Preserve dispatchSlot's initial phase/done checks.
Missing question: when a finished terminal has a newer turn, do we count its completed prompt before replacement? Yes, using the same rule. Missing metadata never becomes inferred completion.

Q2. Live checked runs
Pick: defer counting AND redelivery/replacement while admission.ts liveRuns has a record matching repo.name and leaf.slug. Include waiting records, as liveRuns already does. Once the run finishes, evaluate the pending completed prompt normally. This prevents prompt storms during actual work without excusing a later silent turn. Cost: run-completion must wake dispatch.
Reject: count/re-prompt immediately, because the framework capture demonstrably continued while the controller failed its seat. Infer execution from check_start without check_end, because killed writers leave unmatched historical events. A new polling watcher duplicates existing liveness tracking.
Evidence: operator tier, INTAKE #136. Better-than-training tier, framework timing/log records inspected 2026-11-16: capture-buffalo 21:36:32–21:39:09Z, redeliveries 21:36:35Z/21:36:46Z, failure 21:36:56Z on 2026-11-15. liveRuns validates PID/boot identity; listenCommand currently wakes on hc events, not admission-record removal.
Pitfalls/removal: no completion wake means a permanent idle leaf. Add a completion wake through existing next --wake after the outer withAdmission record is removed and its admission locks are released, on success and error. Nested admissions let their outer holder wake. Prove a sleeping listener resumes the idle leaf after a fake background command exits. Wake failure stays visible without rewriting the command's exit result. Existing stopped/failed-run recovery remains available. Do not hold a global state lock while waiting for the command.
Missing question: verification has gaps between checkedRun stages. Do not claim this rule proves that an entire verify pass is active. If pass-level deferral is wanted, first use verify's existing pass records, not a new timer. The reported single run is the required case here.

Q3. Loss bound
Pick: persist seat_losses.{A,B} with zero defaults. Allow 2 automatic replacements after consecutive losses without a completed task turn. Increment when a recorded seat is missing/finished without completed-turn evidence, before replacement. When increment would reach 3, save the loss evidence and move only that leaf to failed with cause=blocked, phase=current.phase, slot, reason="seat A lost 3 consecutive starts before a completed task turn; see implementation/seat-events.jsonl". Reset that slot's loss counter only on observed completion of a delivered task turn, or all counters on commitMove. Working status alone never resets it. Cost: a separate bounded failure class, with operator recovery rather than misleading no-report failure.
Reject: unlimited restarts, because paid startup can loop forever. Reuse attempts, because loss and ended-turn evidence are different. Stop on the first loss, because normal reboot recovery should get a replacement chance.
Evidence: operator tier, signposts 4a/5a and INTAKE #137. Better-than-training tier, dispatchSlot absent/finished branch has no attempts bound; firstTask can confirm merely working. The number 2 is B's proposed tradeoff, not a measured optimum.
Pitfalls/removal: listener restart must not reset the bound, removed by state persistence. An already-recorded missing seat must not spend the counter repeatedly after a failed replacement call. Store the charged identity as lost_seat.{A,B}={session,address}; charge each old identity once. A confirmed new seat updates state.seat, enabling its own later loss charge. Failed initial launches also need a bounded count, identified by their launched address, before propagating their start error. No foreground success or start event clears loss history.
Missing question: should a loss-bound failure be automatically recovered by watch? No. Its reason must explicitly identify infrastructure loss requiring operator diagnosis, and watch Judge must classify it as notify-only. Otherwise existing generic failed recovery would reopen the same spending loop.

Q4. Durable loss evidence
Pick: before end or overwriting the recorded seat, append one structured event to <leaf>/implementation/seat-events.jsonl. Record ts, kind=seat_lost, repo, slug, phase, slot, session, address, observed state/status/turn, prompted, attempts, seat_losses, transcript path and current screen when the terminal still exists. Missing terminal is an explicit observation, not an invented exit cause. Cost: one append-only diagnostic artifact and an awaited read for surviving records.
Reject: terminal removal first, because the lost facts cannot be reconstructed. Timings only, because timing.ts appendTiming warns and continues after append failure and its schema lacks loss fields. Preserve every dead terminal indefinitely, because it accumulates operational clutter without a bound.
Evidence: operator tier, #137 and the no-evidence-erasure hard limit. Better-than-training tier, hc.ts end performs kill then rm; Seen/terminalSchema do not expose exit code or signal. Do not promise those fields without proving hc exposes them.
Pitfalls/removal: require the evidence append to succeed before destructive teardown. A missing terminal needs no screen read. Propagate other inspection failures and retain the terminal. Repeated observations must not duplicate loss charges, using lost_seat from Q3. Capture exit/signal only if an inspected hc surface actually supplies them.
Missing question: can an evidence-write failure stop only this leaf? Yes. Surface the path/error through the existing per-leaf error reporting, and leave unrelated leaves runnable.

Q5. Existing attempts
Pick: add optional attempts_rule: literal "ended-turns". Its absence marks old delivery semantics. On the first mutating dispatch under the existing global lock, append a migration event retaining the old attempts, set attempts={A:0,B:0}, counted_prompt=current structured prompted entries, seat_losses={A:0,B:0}, lost_seat={}, and attempts_rule="ended-turns" in one saved state. New states and commitMove write that marker. This applies lazily to every registered repo's visited open leaves, not by editing framework now. Cost: one marker and discarding ambiguous historical budget usage once.
Reject: retain old numbers as completed turns, because they are not that measurement. Guess subtraction from prompt timing, because old starts/turns/losses cannot be reconstructed reliably. Reset every invocation, because that removes the limit entirely.
Evidence: better-than-training tier, state.ts stateSchema accepts historical attempts without a semantic version; phase.ts commitMove resets both slots. Operator tier, #137 establishes old values include launches.
Pitfalls/removal: do not reset failed phase, failure reason, done, worktree, grants or old log history during migration. Old failed leaves remain failed until normal authorized recovery. Read-only status must not perform migration. Unknown rule values fail schema validation. No second migration after the marker is saved.
Missing question: should untouched parked/closed leaves be rewritten? No. If they later re-enter dispatch, migrate then. A repository-wide rewrite adds risk without improving the first action's correctness.
