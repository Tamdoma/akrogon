Blind notes B: failed-refusal
Evidence dates below are read 2026-11-16.

Q1. Refusal scope
Pick: refuse every new leaf- or worker-owned checkedRun while its authoritative phase is failed. Preserve standalone chart/direct holders. Do not add restrictions on other phases in this chart. Use the existing optional caller.phase to distinguish leaf-backed callers from holders, and readState(dirname(caller.target)) for the established leaf implementation target. Both worker callers and verify callers retain that owner target. Cost: failed-leaf diagnostics must resume the leaf through the existing operator recovery path before executing checks.
Reject: paid-only classification, because arbitrary argv can spend money indirectly and there is no reliable cost schema here. More phase restrictions, because legitimate check/merge flows need separate evidence and contracts. Warnings only, because they preserve the spending defect.
Evidence: operator tier, INTAKE #136 and named lesson background-wait-fails-leaf, 2026-11-15 case. Better-than-training tier, run-check.ts leafTarget/leafFields/checkedRun and admission.ts withAdmission inspected 2026-11-16: phase is captured and logged but not enforced. Framework records independently confirm new failed-phase starts.
Pitfalls/removal: scope="leaf" alone includes non-leaf holders, so do not use it alone. --holder from a recognized worktree already resolves to its leaf before the holder branch, so keep that ownership resolution. Invalid/missing owner state is a loud refusal/error, never an exemption. Do not trust the caller's phase snapshot to decide eligibility.
Missing question: how is refusal durable without starting a child? Reuse checkedRun's existing retained runRoot/out.log + refusal.json mechanism and PublishRefusedError.log. Allocate the diagnostic root before refusing, retain it, and include repo, slug, owner path, observed phase, name, argv, cwd and timestamp in refusal.json. Emit "Refusing checked run: leaf <repo>/<slug> is failed; recover the leaf phase before running checks. Evidence: <log>". A failed diagnostic write propagates; it must never launch the child.

Q2. Freshness and admission
Pick: check authoritative phase before admission, and again after admission waiting and publication-lock acquisition immediately before child spawn. The second read is essential. Keep existing ownership fencing as well. Do not hold the global lifecycle lock for the child lifetime. Cost: two small state reads and the preserved refusal artifact.
Reject: leafTarget snapshot only, because a queue can wait across a phase move. Fresh read only before admission, for the same reason. A check only after spawn cannot prevent cost. Claiming a fresh read creates atomic ordering with failure would be false.
Evidence: better-than-training tier, checkedRun calls withAdmission before its callback launches; withAdmission can wait in awaitLineTurn. phase.ts transition serializes operator moves with globalHome/.lock. Sources inspected 2026-11-16.
Pitfalls/removal: define the last fresh eligibility read as acceptance. A failure committed after that read does not retroactively cancel the accepted run under Q3. This leaves a small read/spawn interval, stated explicitly. If the contract instead demands that no OS spawn follow any committed failed transition, it needs a short shared lifecycle-lock admission/spawn transaction and a demonstrated lock order. Do not smuggle that stronger guarantee into a two-read implementation.
Missing question: is strict atomic ordering required? Recommend the explicit acceptance boundary for this chart, which stops the observed stale launches and avoids a new cross-lock protocol. The contract must state that choice.

Q3. Accepted runs
Pick: allow an accepted in-flight command to finish, publish its real output and preserve its real exit status. Refuse subsequent new checkedRun calls if the leaf is now failed. Cost: existing accepted spend can finish after failure.
Reject: cancel-on-phase-change, because it discards possibly paid results and needs an additional watcher/cancellation policy. Discard successful output, because that hides useful evidence without undoing cost. grandfather the entire parent verify pass, because later stages are new commands.
Evidence: operator tier, #136's original buffalo run started before failure and finished afterward. Better-than-training tier, checkedRun owns captures throughout a command, and ownerRefusal currently protects closure/publication rather than phase eligibility.
Pitfalls/removal: do not add a post-run failed-state check that converts a valid result into a refusal. Existing owner-gone/closed publication fences remain. Do not record later stage execution as if it belonged to the original command's acceptance.
Missing question: does waiting in admission mean accepted? No. Q2's final eligibility decision follows the wait. Queue registration alone grants no execution authority.

Q4. Verification callers
Pick: no failed-leaf carve-out. Ordinary verify can resolve a failed leaf today through verifyCaller -> leafTarget, but no inspected lifecycle contract requires it to execute while failed. verify --attempt already selects phase=merge exclusively. runOnce calls checkedRun for setup and each stage, so each new stage gets the same fresh refusal. Existing completed receipt reuse is read-only and need not be prohibited by this launch fix. Cost: a verify pass crossing failure can finish its current stage and then stop with an incomplete receipt.
Reject: exemption for all verify calls, because it reopens the same paid-execution path. Exempt --known-red, because its base comparison is still new execution under the leaf's caller authority. Rejecting all receipt reads would expand this task beyond launches.
Evidence: better-than-training tier, verify.ts verifyCaller, verify, runOnce and verify-pass.ts passCaller, inspected 2026-11-16. Normal callers preserve phase/target, merge-attempt lookup requires merge, known-red passes reuse the same caller. runOnce leaves end absent on thrown checkedRun errors and preserves the incomplete record in finally.
Pitfalls/removal: update serialized caller identity only if the chosen fresh-state lookup changes it. Existing records already carry phase and implementation target, so avoid adding another identity field unnecessarily. A refusal must not synthesize a green or completed verify receipt. Prove ordinary verify, setup, sequential stages, member stages and known-red all meet the same rule with free commands.
Missing question: can callers escape through a checkout holder? Legitimate non-leaf holders remain supported, but a mapped leaf worktree must continue to resolve to its owner first. This is execution-state enforcement within that existing contract, not a security boundary against arbitrary shell commands.
