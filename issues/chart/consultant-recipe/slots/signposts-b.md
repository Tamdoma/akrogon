# Signposts missed angles, slot B: consultant-recipe

## Missed questions

- M1 Where must the gap become visible, and when? The draft's options bundle detection with mechanism, but the failure surface is its own fork: (a) at config load — any akrogon command refuses a config without the key; (b) at watch start — `watch-issues` refuses or warns before the first case exists; (c) at consult trigger, but loudly and before the leaf is doomed (today's behavior, the defect); (d) at install/upgrade time only. This steers S1 and S2 harder than either does itself: schema-required (S2a-adjacent) means every command on every machine breaks at load, while watch-start validation confines blast radius to the feature that needs the key. Several later picks flip depending on this answer.
- M2 Who provisions the key permanently, not just on this machine? S4 only covers the live `~/.akrogon/config.yaml` (needs row). The permanent fork is untouched: (a) install seeds it; (b) `init` seeds it at registration; (c) the state-home migration or config load auto-heals a missing key; (d) nothing writes it — it becomes schema-required and the human owns it. Whichever M2 picks decides whether S4a is a one-time manual step or a stopgap the code soon makes unnecessary, and whether old machines upgrading into a required key self-heal or break.
- M3 Must configs already in the wild keep working after the change (the 6a analogue)? `docs/start/install.md` says landing auto-deploys to this machine within minutes. If the schema makes the key required before the live config is healed, every akrogon command on this machine — including the door's own lifecycle — starts throwing until someone edits YAML. So: (a) heal-then-enforce ordering is part of the change, or (b) enforcement may land first and the operator repairs. This is the highest-stakes missed question: the recommended direction in draft S2 (fail loudly) combined with auto-deploy creates a self-inflicted outage window on the very machine running the door.
- M4 Is one-time provisioning enough, given the key demonstrably disappeared once? The intake records a working config on 11-23 and a keyless one on 11-25 with no supported hypothesis. `init.ts` rewrites the global config as `{...global}` where `global` is the schema-parsed object — zod strict parsing strips unknown keys, so anything the schema does not know is silently dropped on every registration (true today for genuinely unknown keys; not the mechanism that removed `slots.consultant`, since it is schema-known). Worth one question: (a) treat the disappearance as out of scope (operator or editor error) and provision once, or (b) make the writer path key-preserving/auditable as part of the same change. If (b) is answered no and the unknown cause recurs, the stall returns.

## Missing option in a draft question

- S4 lacks option (c): the leaf's own mechanism seeds the key into the live config as part of the code change (e.g., the schema load or install seeds a documented default when absent), making N1 unnecessary. The draft frames the choice as operator-hand vs door-hand, but both are manual edits to a file the product could write — and M2's answer may make either edit redundant. Without this option the door can pick a manual step that the code change itself obsoletes days later.
