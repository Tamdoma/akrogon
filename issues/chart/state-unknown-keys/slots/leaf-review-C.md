# Leaf review C: shared-inventory

- Wrong fact in the design's standing-design interpretation: "Tests that pin rejection of legacy keys at `readState` (`tests/state.test.ts`) stay, now as the leaf's own error." At HEAD `tests/state.test.ts` pins rejection of legacy keys only at `stateSchema.parse` ("strict schema rejects legacy keys"), while its `readState` tests pin the opposite ("lazily migrates `priority`, `slot`, `failed_notified` regardless of legacy value type" across open, closed, and parked, expecting the migrated state back). Criterion 5 requires those files to be reported as errors, so the migration tests cannot stay; they must be rewritten to expect the leaf's own error, with the deleted-shim reason recorded.
- The stated interface drops two inventory states existing consumers depend on. Design Interface: one function returns `{ leaves, failures }`, each failure a leaf folder path and error, and the binding list makes a repo-key violation just a failure entry. At HEAD `src/next.ts` `discover` returns `Inventory { leaves, unreadable, unknown, foreign }`: `unknown` marks a directory read failure where the leaf set may be incomplete and capacity treats it as `max_active`, not as one owned leaf; `foreign` leaves are readable states stored under another repo key, summarized separately and not capacity-reserving, pinned by `tests/next.test.ts` "unreadable leaves reserve capacity while foreign leaves summarize separately." A folder-path failure cannot express an unreadable directory, and a generic failure entry would make a foreign leaf reserve capacity under criterion 4. The return type is listed as open for the plan, but retaining `unknown` and `foreign` as distinct results is settled behavior the design must state, not leave open.
- Missed walker area: parked leaves. The brief's What and criterion 6 scope the one inventory to `issues/open` and `issues/closed`, and the design deletes `leavesUnder`, but at HEAD `src/park.ts` reads parked leaves through `leavesUnder` in `stranded` (unpark dependency check) and after the move in `parkCommand` (timing records), and `src/timing-report.ts` `flowReport` reads them with `leavesUnder(parked, parked)`. The design's settled line for park and timing-report ("a failure inside the folders they act on blocks that action") even assumes parked failures are visible for unpark. As written there is no replacement for these reads: either the inventory must also serve a named subtree or area including parked, or a parked-only walk stays, contradicting the deletion. The contract must settle which.
- Criterion 6 cannot be proven by the proof route the design assigns to every criterion. The design's standing-design interpretation says "every criterion is proven through the repo's existing CLI test fixture with temporary repos," but criterion 6 ("No module other than `src/state.ts` walks `issues/open` or `issues/closed` for `state.yaml` files or parses a leaf state outside `readState`") is a source-structure claim: a duplicate walk in another module can produce identical CLI behavior in every fixture case, so no CLI run can show it. Its proof has to read the source tree and assert the property, which `standing-design.md` allows for source-derived properties, and the design must name that proof form for this criterion instead of the CLI fixture.
