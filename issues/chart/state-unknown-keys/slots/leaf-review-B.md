# Leaf review: shared-inventory (slot B)

Reviewed against HEAD `96a96979d15bc355115a70f409ec297a9fa81587`.

- **F1: Criterion 6 cannot pass within the listed ownership.** `skills/watch-issues/scripts/observe.ts` owns another recursive `leavesUnder` (line 114), another parser and retired-key filter (line 85), and duplicate depth, slug and repo checks (lines 78 and 264 onward). It imports `stateSchema` directly and aborts observation on a bad sibling. Neither this script nor its tests is in the owned surfaces. Add ownership of this consumer and its tests, migrate it to the shared inventory and give healthy-leaf observation beside a bad sibling an observable criterion. Leaving it intact contradicts both criterion 6 and Taken 1a's requirement that every walker use the shared inventory. The shapes audit requires every criterion to be achievable within ownership.

- **F2: The inventory contract omits distinctions needed to preserve dispatch policy.** The draft describes failures only as bad leaf folders and says capacity counts failures “as today.” Current `src/next.ts` distinguishes unreadable leaves, an unknown directory population and foreign repo records. `activeCount` reserves one slot per unreadable leaf, all available capacity for an unknown population, and no capacity for foreign records. Existing tests explicitly protect these differences: `unknown directory population reserves all new capacity but allows existing tabs` (`tests/next.test.ts:1656`) and `foreign leaves do not consume capacity while healthy leaves in both repos dispatch` (`:1445`). Settle these semantics in the design, retaining directory failures as well as leaf failures and enough classification to preserve those policies. Counting every failure as one leaf would change scheduling despite the explicit exclusion of capacity-policy changes. The exact encoding can remain for the plan.

- **F3: The test-retention description reverses existing legacy behavior.** The Standing design interpretation says tests already pin rejection of legacy keys at `readState`. In `tests/state.test.ts:34`, rejection is at `stateSchema.parse`; the lazy-migration cases starting at line 41 instead require `readState` to accept and strip retired keys, with `expect(state).toEqual(supported)` at line 83. State explicitly that these compatibility expectations are replaced because Taken 2a retires the shims, while direct schema-rejection coverage remains. Keeping the existing readState expectations would contradict criterion 5.
