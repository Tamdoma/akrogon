# Blind notes C: fork unknown-keys

Question: Ignore unknown top-level keys and delete the hand-made skip list, or keep strict parsing and fail only the bad leaf through one shared inventory?

## 1. Pick

Keep strict parsing. Fail only the bad leaf through one shared inventory.

Reason: the destination covers a leaf that is "unreadable or extended." Stripping unknown top-level keys fixes only the extended case. Bad YAML, a missing required field, a bad `phase`, a duplicate `done` slot, or an unknown key inside the still-strict `batch`, `failure`, or `delivery_error` objects would still throw out of `allLeaves` and stop every other leaf. Isolation fixes the whole class: one leaf fails to parse, that leaf is reported and skipped, and commands for other leaves proceed. Commands that name the bad leaf itself still fail with that leaf's parse error. This is also the removal move the carry asks for: `next.ts` already has a working tolerant inventory (`discover`, with `leaves`, `unreadable`, `unknown`, and `foreign`), so the fix promotes that one walk into `state.ts` and deletes the other walks (`allLeaves`/`leavesUnder` as the throwing inventory, the separate walk in `status.ts` `scanRepo`, and the `collectSlugs` walk in `reconcile.ts`) instead of adding a new tolerance layer beside them. Strict parsing keeps two protections stripping would lose: a misspelled optional key such as `worktre` fails loudly instead of silently dropping the value, and an older akrogon binary that meets a state file written by a newer one fails on that leaf instead of stripping the new key and deleting it on the next `saveState`.

Cost: this is the bigger change. Every caller of the old throwing inventory (`phase`, `status`, `config`, `run-check`, `reconcile`, `next`) has to take the shared inventory and decide whether an unreadable leaf inside its own decision scope blocks it. The 4-key skip list in `readState` stays. A seat that writes unknown keys still breaks its own leaf until someone removes them, though it can no longer be re-prompted into repeating the write while the leaf is unreadable, because dispatch only sees readable leaves.

## 2. Rejected options

- O1 Strip unknown top-level keys (`z.object` instead of `z.strictObject`) and delete the skip list. Rejected because it does not meet the destination: every other kind of unreadable `state.yaml` still stops the whole repo through `allLeaves`, including unknown keys nested in `batch`, `failure`, and `delivery_error`, which stay strict. It also makes damage silent: parsed state drops the unknown keys, and the next `saveState` for that leaf deletes them from disk, whether they were seat notes, a misspelled optional key, or a field written by a newer akrogon version. Its one real gain, deleting the skip list, does not need stripping (see question Q1 below).
- O2 Strip but preserve unknown keys through a save (loose object with passthrough). Rejected because it keeps O1's failure to cover unreadable files, and adds a new cost: `State` gains an open index shape, typo keys and retired keys then persist forever instead of being cleaned, and nothing ever reports them.
- O3 Keep strict parsing and wrap each command or caller in its own try/catch. Rejected because it stacks copies of the same tolerance logic in five or more places, with separate handling of duplicate slugs, foreign repo keys, and bad leaf depth bound to drift apart. That is the redundancy the carry says to remove first, and the tolerant walk in `next.ts` already exists to be shared.
- O4 Stop seats from writing `state.yaml` (hook, permission, or instruction only). Rejected as the sole fix because it does nothing for hand edits, merge damage, corrupt YAML, or keys written by another akrogon version, and the intake records that nobody has yet inspected why the seat wrote those keys or whether a guard was meant to stop it.
- O5 Automatically move or quarantine an unreadable leaf out of `issues/open`. Rejected because it hides the failure, changes the leaf's location and dispatch state without an operator decision, and risks cleanup treating its worktree as unowned.

## 3. Evidence

- E1 Tier: direct code read, akrogon HEAD `abfee125`, 2026-10-19. `src/state.ts`: `stateSchema` is a `z.strictObject`; `readState` filters only `priority`, `slot`, `failed_notified`, and `solo` before parsing (plus an empty `batch.members` shim); `leavesUnder` and `allLeaves` throw on the first bad leaf; `findLeaf` is built on `allLeaves`, so a command for one good leaf parses every leaf in `open` and `closed`. The top level is not the only strict layer: `batchSchema`, `failureSchema`, `deliveryErrorSchema`, and `toolSchema` are also `z.strictObject`, while `busy_since`, `verdict`, `pane`, and similar nested records are plain `z.object` and already strip.
- E2 Tier: direct code read, akrogon HEAD `abfee125`, 2026-10-19. `src/next.ts` `discover` already implements the pick's shape: it catches per-leaf errors, reports each once per invocation as a JSON line, and returns valid leaves plus `unreadable`, `unknown`, and `foreign`; its callers already treat an unreadable leaf as still occupying capacity and as an `unreadable` dependency label. The other walks do not: `src/status.ts` `scanRepo` has its own walk and fails the whole repo scan on one bad state, `src/config.ts` `effectiveConfig` and `src/run-check.ts` `leafTarget` call `allLeaves` just to find one leaf by worktree, and `src/reconcile.ts` `collectSlugs` swallows read errors with the comment "unreadable state.yaml protects nothing."
- E3 Tier: intake report, Tamdoma/akrogon#102 via `issues/chart/state-unknown-keys/INTAKE.md`, incidents 2026-10-17/18. One leaf's added `reported` and `notes` keys made `status`, `next`, `phase`, `config`, and `run-check` fail repo-wide twice, including another leaf's handoff; the second break came from re-prompting the same seat after the operator removed the keys by hand.
- E4 Tier: live count, all 11 repos listed by `akrogon config`, 2026-10-19. I parsed every `state.yaml` under `issues/open`, `issues/closed`, and `issues/parked`: 821 files, 0 unknown top-level keys, and the skip list matches only 2 files, both closed (`issues/closed/akrogon-loop/bootstrap/command` and `core-skills` in the akrogon repo, each carrying `priority: n`). No live file carries `slot`, `failed_notified`, or `solo`.
- E5 Tier: direct test read, akrogon HEAD `abfee125`, 2026-10-19. `tests/state.test.ts` pins strict top-level rejection on purpose ("migration retains strict validation of unknown keys"), and `tests/batch.test.ts` pins rejection of unknown keys in `batch` and at top level. Under the pick those `readState` and schema tests stand; only the inventory-level expectations (for example `allLeaves` depth failures throwing) move to the shared inventory's invalid list.
- E6 Tier: opening map, `issues/chart/paid-proof-bounds/slots/map-merged.md` section "#102 strict state parse", 2026-10-18. Slots A, B, and C confirmed the defect at HEAD and recorded the same two options this fork asks about, plus two pitfalls carried into section 4 below.

## 4. Pitfalls

- P1 Cleanup can delete an unreadable leaf's worktree. `reconcile` receives only readable leaves from `discover`, and `collectSlugs` records nothing for a leaf it cannot parse, so that leaf's worktree can look unowned. Removed by carrying the unreadable leaf paths (folder names, which name the slug) in the shared inventory and having reconcile keep any worktree, tab, or slice matching an unreadable leaf, or by skipping destructive cleanup for a repo while its inventory has unreadable leaves, the same caution `next` already applies to capacity when a repo is `unknown`.
- P2 Decisions that need a complete set go silently wrong if the inventory just drops the bad leaf. `completeOwner` in `phase.ts` and the equivalent check in `reconcile.ts` ask whether every leaf under an owner is `merged`; the merge queue and `blocked-by` dispatch also assume the set is complete. Removed by scoping the block: a caller fails or waits only when an unreadable leaf sits inside the set it is deciding over (that owner's subtree, that leaf's dependency closure, the merge queue), and ignores unreadable leaves outside it.
- P3 Single-leaf lookups report the wrong failure. If `findLeaf` only searches readable leaves, asking for the bad leaf by slug reports "Missing leaf" instead of its parse error, and the worktree matching in `config` and `run-check` silently falls back when the matching leaf is the unreadable one. Removed by locating the named leaf's folder without parsing other leaves (the folder walk already exists in `hasSlugFolder`) and then calling `readState` on that leaf alone, and by making worktree matching name the unreadable paths as possible matches when no readable leaf matches.
- P4 The shared inventory loses checks the throwing one had. `allLeaves` currently enforces leaf depth, duplicate slugs, and stored repo key matching the registered repo. Removed by keeping all three checks once inside the shared inventory, as `discover` already does, with each violation landing in the invalid list rather than throwing.
- P5 The bad leaf becomes invisible or becomes noise. If commands proceed silently, nobody fixes the leaf; if every command dumps a full `ZodError`, the signal drowns. Removed by the reporting `next` already does: one deduped JSON line per invocation on stderr naming repo, path, and error, and a visible invalid entry in `status` instead of a failed repo scan.
- P6 A bad leaf under `issues/closed` forces edits to history. Closed leaves are records, and most commands never need to act on them. Removed by the same scoping as P2 and P3: a closed unreadable leaf blocks only commands that actually need that leaf (looking it up, packing, completion), and appears in `status` as invalid without stopping work on open leaves.

## 5. Questions the fork does not ask

- Q1 Can the skip list be deleted anyway, without stripping? E4 shows it now serves only 2 closed files across all 11 live repos. Is the elegant move a one-time rewrite of those 2 files plus deleting the 4-key filter and the empty `batch.members` shim, accepting that any out-of-tree leaf still carrying a retired key becomes an isolated unreadable leaf under the pick? Or is the shim kept forever for trees this count cannot see?
- Q2 What, if anything, should stop a seat from writing `state.yaml` directly? The intake's expected behavior has a second half, "a seat cannot leave `state.yaml` in a state that akrogon refuses to read," which this fork's destination drops. Under the pick the seat still strands its own leaf. Is that accepted, or should the leaf contract also cover finding out why the seat wrote `reported` and `notes` there, which the intake records as not inspected?
- Q3 Is version skew a real case? If a newer akrogon adds a state key while panes still run an older installed release, strict parsing plus isolation makes those leaves unreadable only to the old binary, while stripping would let the old binary silently delete the new key on save. Does the operator's upgrade path guarantee one live version at a time, or must the contract state which behavior skew gets?
- Q4 Should tolerance, if any is ever wanted, stop at the top level? The fork asks only about top-level keys, but `batch`, `failure`, and `delivery_error` are strict while other nested records already strip unknown keys. Is that mix intentional, or should the leaf contract state one rule for the whole file so the next extension does not reopen this fork at a deeper level?
