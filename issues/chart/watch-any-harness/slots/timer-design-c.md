# Timer design notes (slot C)

## Q1 — Where do checks run?
- **Pick:** (a) invoking conversation. Preserves the operator's chosen harness, model, permissions, visible replies, and watch-scoped memory (one-steer-per-seat, notice de-dup in `skills/watch-issues/SKILL.md` § Judge) without new config (`src/seat.ts` requires slot/harness definitions). Cost: shares the terminal with operator chat, drafts, and `/clear`/`/new`.
- **Rejected:** (b) dedicated watcher terminal — needs harness/model/permission config and trust-dialog handling (`tests/e2e/kinds.e2e.ts`), hides replies in another terminal, and breaks starting the watch in whichever CLI the operator opened.
- **Evidence:** `operator` (`INTAKE.md` § Source, 2026-11-20); `better-than-training` (`skills/watch-issues/SKILL.md` § Judge, `docs/use/watch-while-away.md` § Start the watch, `src/seat.ts`, 2026-11-20).
- **Pitfalls:** Compaction drops in-memory steer/notice tracking -> accepted as today (`SKILL.md` § Judge); chat/draft collision -> handled by Q4 waiting on idle and `hc send` draft hold.

## Q2 — What hosts and binds the timer?
- **Pick:** (a) `skills/watch-issues/scripts/timer.ts` as an `hc run --bg --no-notify --rm` child of the watcher terminal, pinning harness `{pid, procStart}` at `start` and exiting if gone/replaced before every send, plus subscribing to `hc events --terminal <watcher>`. Combines `hc` parent-exit cleanup with shell-hosted agent-exit protection (lock 2a). Cost: must walk `/proc` ancestors during `start` instead of trusting `foreground.pid`, and leaves a tiny check-to-send window.
- **Rejected:** (b) parent rule alone — violates lock 2a because `hc` kills children only when the terminal's *root* process exits (`hc --skill` § Status, recovery, and cleanup), so exiting an agent started inside an interactive shell leaves the timer ticking into the shell or a replacement program; (c) detached OS process + PID file — survives terminal exit on Unix (`hc --skill`) and invites orphans and stale PID reuse.
- **Evidence:** `better-than-training` (`hc --skill` § Status, recovery, and cleanup, `hc run --help`, `src/transcript.ts` `procStart`/`seatPids`, commit `3fdf8cd2` 2026-11-08, inspected 2026-11-20).
- **Pitfalls:** `foreground.pid` during `start` is `bun`/subshell, not the harness -> walk `/proc/<pid>/stat` ancestors from `start` up to `t.pid` and pin harness `{pid, procStart}`; agent exits while `hc send` waits on a draft -> keep an `hc events --terminal <watcher>` listener that aborts in-flight `hc send` on `finished`/`lost`/`status:null`; unset `HC_TERMINAL_ID` (outside `hc` or Codex without `--no-daemon`) -> refuse `start` cleanly and prove env survival per harness under N1.

## Q3 — How is a reset (/clear, /new) caught?
- **Pick:** (b) skill-side first-prompt stop PLUS timer-side `transcriptFor` comparison (`src/transcript.ts`) before each send where known. Satisfies lock 2a by catching `/clear`/`/new` on `claude` (`claudeTranscript`), `agy` (`agyConversation`), and `codex` (`rollouts`) *before* sending even if the operator already typed another prompt, while the first-prompt rule still covers `pi` `/new` (unobservable via `/proc` per `piStart`/`transcriptFor` and `skills/chart-issues/scripts/transcript.ts`) and fresh sessions with no file yet. Cost: must handle initially-`null` transcripts lazily.
- **Rejected:** (a) skill-side only — fails lock 2a on `claude`/`codex`/`agy` whenever the operator types a normal prompt after `/clear` before the next tick (the flaw documented in `SKILL.md` § Invocations).
- **Evidence:** `operator` (`forks/signposts.md` `## Taken` 2a, 2026-11-20); `better-than-training` (`src/transcript.ts` `claudeTranscript`/`agyConversation`/`rollouts`/`piStart`/`transcriptFor`, `skills/chart-issues/scripts/transcript.ts`, `skills/watch-issues/SKILL.md` § Invocations, 2026-11-20).
- **Pitfalls:** Fresh session returns `null` transcript at `start` (e.g. Claude pre-JSONL or interactive `pi` without `--session-id`) -> lazily latch the first non-null path for the pinned `{pid, procStart}` (and read `PI_SESSION_FILE` during `start` if set), treating only non-null -> different non-null as reset; `pi` `/new` + intervening prompt -> document as the accepted lock-2a limit.

## Q4 — Due tick while watcher is busy, blocked, or holding a draft?
- **Pick:** (a) wait until watcher is `idle` or `done`, collapsing missed dues into one check. `observe.ts` inspects current state fresh, so back-to-back duplicate checks after a busy span add no value; waiting avoids mid-turn steering on `codex`/`pi`/`agy`, avoids `hc send` exit 9 on `blocked` (`hc send --help`), and prevents backlog storms. Cost: alters `tests/e2e/watch-check.e2e.ts`'s two-queued-ticks assertion (two missed deadlines yield one post-idle catch-up check, not two) — confirm against lock 6a's "no regressions" expectation.
- **Rejected:** (b) send on time while busy — `hc send` fails on `blocked`, waits 60s on drafts, and may steer/interrupt an active turn on `codex`/`pi`/`agy` rather than queue; (c) skip when busy — a check crossing the 20m mark leaves a 40m blind gap.
- **Evidence:** `better-than-training` (`hc send --help`, `hc --skill` § Talk, wait, and collect results, `skills/watch-issues/SKILL.md` § Observe/Invocations, `tests/e2e/watch-check.e2e.ts`, 2026-11-20).
- **Pitfalls:** Watcher resets/exits while waiting to become idle -> re-run PID/`procStart`/transcript guards immediately before sending and drop pending dues on stop/exit/reset; `hc send` returns `started: false` (`skills/chart-issues/scripts/door-reset.ts`) -> probe per harness under N1 and press `enter` once only if identity still holds.

## Q5 — How is one watch per repo enforced and found?
- **Pick:** (a) deterministic `hc --name` from repo prefix + label `akrogon.watch=<repo>` in the repo's resolved session (`repoSpace` in `src/hc.ts`), cross-terminal `stop`, and tick verification against live timer ownership. Atomic unique `--name` (`hc run --help`) blocks concurrent start races with no stale state files, and label lookup lets any terminal inspect or stop the repo's watch. Cost: timer name must fit `hc`'s 32-char limit, watcher must be in the repo's resolved session, and `SKILL.md` § Never needs a scoped carve-out (or `timer.ts stop` sending `SIGTERM` so `--rm` removes it).
- **Rejected:** (b) lock/PID file under `~/.akrogon` — outlives core stops/crashes, risks PID reuse, and duplicates `hc`'s live terminal registry without cross-terminal liveness visibility.
- **Evidence:** `better-than-training` (`hc run --help`, `hc ls --help`, `src/hc.ts` `seatName`/`repoSpace`/`terminals`/`end`, `skills/watch-issues/SKILL.md` § Never, 2026-11-20).
- **Pitfalls:** Name > 32 chars -> hash like `src/hc.ts` `seatName`; `hc kill` tension with `SKILL.md` § Never -> `timer.ts stop` matches strictly on `akrogon.watch=<repo>` and terminates only that timer (explicitly exempted in § Never); delayed tick after stop+restart passing parent check -> embed timer address/nonce in tick prompt (see Q8).

## Q6 — What text does the timer send?
- **Pick:** (a) one shared plain prompt `watch-issues tick <root>` (plus timer id/nonce per Q8), mirroring `src/next.ts` `promptFor` (`${skill} ${slug} ...`). Keeps lock 1a truly single-path and avoids unknown-slash-command failures (`pi` uses `/skill:watch-issues`, `codex` `$watch-issues`, `agy` progressive disclosure). Cost: depends on each harness activating `watch-issues` from plain text even after compaction or `/clear` (must prove live under N1; fall back to phrasing tweak or (b) only if a harness ignores plain text).
- **Rejected:** (b) per-harness native syntax from `argv` — fragile against wrapper binaries/aliases and CLI syntax drift, and splits delivery into four branches before evidence shows (a) fails.
- **Evidence:** `better-than-training` (`src/next.ts` `promptFor`, `agy-customizations/SKILL.md` § Discovery Locations, `tests/e2e/watch-check.e2e.ts`, 2026-11-20).
- **Pitfalls:** Child `hc send` gets wrapped in `<hc from="...">` (which `hc --skill` § Talk, wait, and collect results says to treat as child report, not user instruction) -> send via `src/hc.ts` `send` (`hcEnv` strips `HC_TERMINAL_ID`/`HC_TERMINAL_SOCKET`), so ticks arrive untagged; model ignores plain prompt -> verify exact wording across all 4 harnesses under N1.

## Q7 — How does agy find the skill?
- **Pick:** (a) add `.gemini/config/skills` to `src/install.ts` (`planSkillLinks`) alongside existing roots (`.claude/skills`, `.agents/skills`, `.codex/skills`, `.pi/agent/skills`), after confirming live under N1 that `agy` does not load `~/.agents/skills`. Needed so `agy` actually works in real operator repos (lock 1a/6a) with automatic stale-link pruning and conflict detection. Cost: small edit to `src/install.ts` + `tests/install.test.ts` (confirm alignment with lock 5a).
- **Rejected:** (b) manual link only — leaves `agy` broken out of the box and drifts across `akrogon` releases.
- **Evidence:** `better-than-training` (`src/install.ts` `planSkillLinks`, `agy-customizations/SKILL.md` § Discovery Locations, filesystem check of `~/.gemini/config/skills` vs `~/.agents/skills`, 2026-11-20).
- **Pitfalls:** Pre-existing non-symlink directory under `~/.gemini/config/skills` -> `planSkillLinks` already reports conflicts without overwriting.

## Q8 — Old Claude cron jobs armed before upgrade?
- **Pick:** (a) no Claude-specific cron deletion in the shared skill; gate ticks strictly on a live timer carrying the matching repo + parent + timer instance id/address. Keeps lock 1a clean (zero `CronList`/`CronDelete` text confusing non-Claude harnesses). Cost: a pre-upgrade Claude session's orphaned cron may emit harmless refusals until session end or 7-day expiry.
- **Rejected:** (b) delete old Claude cron jobs on start — reintroduces Claude-only cron logic into the shared skill (violating lock 1a) and fails to clean up sessions where `start` is not rerun.
- **Evidence:** `operator` (`forks/signposts.md` `## Taken` 1a, 2026-11-20); `better-than-training` (`skills/watch-issues/SKILL.md` § Invocations, commit `3fdf8cd2` 2026-11-08, 2026-11-20).
- **Pitfalls:** Old Claude cron firing in the *same* terminal after a new timer starts would pass a parent-only Q5a check and cause double checks -> require the tick prompt to carry the live timer's address (e.g., `watch-issues tick <root> timer=<address>`); old `/watch-issues tick <root>` lacks it and is refused (also blocks delayed ticks after stop+restart).

## Questions the fork does not ask
1. **Start ordering (claim before check):** Should `start` claim the repo timer *before* running the immediate check, so a second concurrent start reports the winner instead of running a duplicate check? (Rec: yes, claim before check.)
2. **Cross-session watcher:** What if the watcher's `$HC_SESSION` differs from `repoSpace(repo).session` (`src/hc.ts`)? (Rec: refuse at `start`, since `--parent` and `hc send` require one session.)
3. **Timer send tagging (`hcEnv`):** Should `timer.ts` send via `src/hc.ts` `send` (stripping `HC_TERMINAL_ID` so ticks arrive untagged) rather than raw `hc send` (which wraps child messages in `<hc from=...>`)? (Rec: yes, untagged via `src/hc.ts` `send`.)
4. **Test-interval override:** Will `timer.ts` expose a test-only interval env override (like `OBSERVE_AKROGON` in `skills/watch-issues/scripts/observe.ts` `main`) for fast E2E runs under lock 6a? (Rec: yes.)
