# Timer design: one watch script for every harness

## Question

Q1 Where do checks run? (a) in the conversation that started the watch, as today, (b) in a dedicated watcher terminal the skill starts with a chosen harness.

Q2 What hosts and binds the timer? (a) one bun script `skills/watch-issues/scripts/timer.ts` started by the skill from its own tool shell as an hc child of the watcher terminal (`hc run --bg`, default parent), which pins the harness process (pid and start time) at start and, before every send, exits instead of sending when that process is gone or the terminal's program changed; (b) the same child without the process pin, relying on hc's parent rule alone; (c) a detached OS process with a pid file.

Q3 How is a reset (/clear, /new) caught? (a) skill-side only: a tick that is the first prompt of its conversation stops the watch and runs no check, as today, on every harness; (b) also a timer-side check that the watcher's transcript path is unchanged before each send, where akrogon's resolver knows it.

Q4 What happens to a due tick while the watcher is busy, blocked or holds an operator draft? (a) the timer waits until the watcher is idle or done, then sends one tick; dues that pass while waiting collapse into that one; (b) send every due tick on time and let the harness queue it; (c) skip dues that find the watcher busy.

Q5 How is one watch per repo enforced and found? (a) the timer terminal gets a fixed hc name from the repo prefix plus a label `akrogon.watch=<repo>` in the repo's resolved session; start reports a live one and starts nothing, stop kills and removes the one found (from any terminal in the session), several are reported and none touched; a tick runs a check only when a live timer for this repo has this terminal as parent; (b) a lock or pid file under ~/.akrogon.

Q6 What text does the timer send? (a) one plain text for every harness, `watch-issues tick <root>`, like the plain `plan-issue <slug> ...` prompts akrogon already sends seats, (b) each harness's native skill syntax chosen from the watcher's argv.

Q7 How does agy find the skill? (a) add agy's global skill folder to akrogon's install links (`src/install.ts` planSkillLinks), (b) leave install alone and document a manual link.

Q8 What happens to a Claude cron job armed by the old skill when the new skill lands? (a) nothing special: its ticks reach the new skill, which runs a check only when a live timer for the repo is parented to this terminal (Q5a), so old cron ticks report "no watch" until the job dies with its session or 7-day expiry, (b) the new skill deletes old Claude cron jobs on start.

## Taken

A's picks under autopilot (door t126, 2026-11-20), not operator words; operator corrections S1, S2a and S3a (forks/signposts.md) are the operator's. Final shape after four final-shape checks (slots/timer-design-final-shape*.md and their -b/-c returns):

1. Q1a. Checks run in the conversation that started the watch. Signpost 4a (one watch per repo) and 1a (one path).
2. Q2a. Start runs a synchronous step in the watcher's own tool shell that identifies the harness process among the tool shell's ancestors, reads its start time and, when akrogon's transcript resolver knows one, its transcript path, and passes them as arguments to the timer, `skills/watch-issues/scripts/timer.ts`, started with `hc run --bg --no-notify --rm` (default parent: the watcher terminal). The timer never walks ancestry itself (it is not an OS descendant). Open for the plan: the exact identification rule (harness as terminal root, or the root's child on the ancestor chain when launched from a shell), against `src/transcript.ts` seat lookup and the codex shape (root codex, tool shell's parent the root).
3. Q2a/Q3b. On every poll, while waiting and right before each send, the timer exits without sending, discarding pending dues, when: the pinned process is gone or has another start time; the watcher terminal's current foreground process is neither the pinned process nor one of its descendants; the watcher terminal is finished; or the resolved transcript path differs from the pinned one (a path first seen after start is latched and is weaker). An agent exit during the wait so ends the timer and frees the name. The skill's first-prompt stop stays for every harness.
4. Stated limits: (operator S2a, S3a) a tick hc holds behind the operator's unfinished draft may land in the shell left behind, or in a program the operator starts there within that hold, when the operator exits a shell-hosted agent in that window; a replacement agent running the skill refuses it by the tick's `pid=`; pi `/new`; codex `/new` until its new rollout appears; a reset followed by an operator prompt on those two.
5. Q4d (B's option). The timer counts dues every interval. With at least one due pending and the watcher idle or done, it sends one tick for the oldest pending due n and waits for the watcher's hc turn to advance and the watcher to be idle or done again. Due n is delivered only when the timer's own label then reads `akrogon.watch-due=<n>`; otherwise it is resent once at the next readiness, then dropped while the schedule continues. The skill sets that label with `hc label <timer> akrogon.watch-due=<n>` right after its `akrogon status` call, before the paused short-circuit. Dues are numbered from 1 per timer; start's immediate check is not a due. This keeps today's behavior that ticks due during a busy check each run their own check (lock 6a).
6. Q5a. One watch per repo. The timer's hc name is `<prefix>-watch` (repo prefix from akrogon config), label `akrogon.watch-timer=<repo>` (a key distinct from the removed `akrogon.watch`), in the repo's resolved session. Start and stop first count live terminals in that session labelled `akrogon.watch-timer=<repo>`: zero means none (start claims the name before its immediate check; stop reports already stopped); more than one is reported with every match untouched; exactly one is a timer only when its hc name is `<prefix>-watch` and its own top-level argv from `hc get --json` runs `skills/watch-issues/scripts/timer.ts`; then start reports it and starts nothing, stop kills and removes it. A `<prefix>-watch` name held by an unlabelled or unverified terminal is a reported conflict and nothing is touched. Stop works from any terminal in the session. § Never gains this single carve-out. A watcher outside the repo's resolved session, or with no `HC_TERMINAL_ID`, is refused.
7. Q6a. Tick text, every harness: `watch-issues tick timer=<address> pid=<pinned pid> due=<n> <root>` (root is the rest of the line), sent with akrogon's `src/hc.ts` send from the timer's own terminal. Before any check or first-prompt stop the skill (a) requires the terminal at `<address>` to be the verified timer of item 6 with this terminal as its parent, else reports no watch and runs nothing (refuses old Claude cron ticks and ticks after stop or restart), and (b) identifies its own harness process by the start rule of item 2 and requires it to equal `pid`, else stops the watch (item 6 stop) and runs no check.
8. Q7 (operator S1): `src/install.ts` planSkillLinks links every akrogon skill into agy's global folder `~/.gemini/config/skills`, the same way and with the same stale-link and conflict handling as the other roots.
9. Q8a and signpost 3a: no expiry; Claude cron text (CronCreate, CronList, CronDelete, 7-day expiry) is removed from the skill and docs.
10. Test-only env `WATCH_TICK_SECONDS` overrides the 20-minute interval, like `OBSERVE_AKROGON`.

Rejected: Q1b dedicated watcher terminal (two agents per watch, against 4a's single steering); Q2 timers hosted by the listener or a new akrogon command (signpost 5a); Q3a no reset detection beyond first-prompt stop (weaker than 2a where harnesses show it); Q4a drop or merge busy dues (regresses today's two-queued-checks behavior, lock 6a); Q6 slash-command tick text (codex rejects unknown `/` commands); Q8b keep cron for Claude (signpost 1a).

Standing dissent: C held Q4a (redundant checks over the same state) until B F3; C no longer disputes after shape 3 ("no defects"). B's final-check-4 points F2 and F4 are answered by items 4 (operator S3a) and 5.
