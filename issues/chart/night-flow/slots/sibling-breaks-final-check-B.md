# Slot B: final-shape disagreements and missing pitfalls

- **F12: The refresh needs a clean, committed leaf before rebase.** pass-refresh requires the final refresh before proof, but the existing implement workflow commits remaining edits after proof. Inline A can therefore reach the new rebase with uncommitted implementation work. Git rejects a dirty rebase by default, and retrying the same phase does not remove that cause. Require A to commit its scoped outstanding work before the refresh, with workers removed, then prove the resulting integrated head. Do not discard or stash those edits. - **F13: Per-refresh range-diffs do not necessarily contain A's repair.** Suppose the start refresh changes reviewed H0 into H1, A commits the repair as H2, and the final refresh is a no-op. The only required recorded range-diff is H0 → H1. It contains the rebase adaptations but omits H1 → H2. Reading it alone cannot supply B's repair review, while the existing raw old-head-to-new-head diff includes newly landed main changes. Require a complete comparison from B's prior reviewed base/head to the final handed-off base/head, or explicitly tell B to derive that comparison from the review and final report. It must include both refresh conflict resolutions and the repair. - **F14: Separate resolvable conflicts from terminal refresh errors.** pass-refresh says to resolve conflicts or correct the plan, then says a failed rebase is aborted and the pass ends. An ordinary rebase conflict also returns nonzero. Without this distinction, the generic failure sentence can repeatedly abort the conflict before the plan-correction rule is used. Resolve ordinary conflicts under the stated rule. If they need an in-scope plan correction, abort the active rebase and perform that correction before retrying. For a failed fetch or other terminal refresh error, record the original error and end without a phase move. Abort only if a rebase is active, so a fetch failure is not replaced by a “no rebase in progress” error. - **F15: “Only slow work” must mean merge-only work, not removal of cheap checks from integration.** cheap-check-placement's What and criterion 1 say merge_checks holds only slow work. Its setup sentence correctly permits a merge command to rerun cheap checks. Clarify the former statements to match the latter: cheap checks must run before review and may also run on the integrated merge candidate. Otherwise an implementer can satisfy “leaving only slow work” by stripping the fast stage from an aggregate merge command, losing protection against a sibling landing after review.
