# Test authorship: independent notes B

Recommendation: prepare a small, independent acceptance suite before production coding, keep its accepted version outside the implementer's authority, and use existing execution tools for live evidence. Reassign work by role rather than add agents, a test-count quota, or another monitoring loop. This removes implementation-driven changes to the acceptance oracle. It does not make an incomplete or incorrect oracle infallible.

The operator's ban on implementer-authored tests is a policy choice I honor. The research supports independent, meaningful validation. It does not establish that all tests written by agents are useless or that test-first alone prevents gaming.

## 1. Research, newest first

All URLs were read on 2026-10-10. Dates below are publication/revision dates, not crawl dates. Sources are primary research, original practitioner accounts or tool-maker guidance. No inference of agent intent is made from this repository's invalid proofs.

- E1. Rod Rivera, [A Coding Agent That Writes Its Own Tests Is Grading Itself](https://www.profrod.ai/articles/check-the-interface-after-the-tests-pass), 2026-10-07. Practitioner teaching/example: implementation-written tests can pass while an independently specified interface test fails. Recommends spec-derived external validation and actual measured output. This is a worked example and teaching account, not a controlled production comparison proving that every self-authored suite is rigged.
- E2. Stride/Newlight, [Test-first development with coding agents](https://www.stride.page/learn/ai-coding-agents/test-first-with-coding-agents), 2026-09-27. Tool-maker advice: tests from criteria before code; demonstrate meaningful failure; commit; implement without editing tests; block protected edits where needed. Their own experience is reported, without comparative experimental results. The article still allows agents to author tests, so it does not support a blanket ban on AI test authors.
- E3. Yunhao Liang et al., [Test-Driven Approaches to Software Engineering with Large Language Models](https://arxiv.org/abs/2609.12012), 2026-09-10 preprint. Survey separates test availability, validity, feedback use and evaluation independence. Passing tests does not demonstrate behavior equivalence or adherence to a test-first process. This argues against treating role separation or test order as the only control.
- E4. Bingchen Zhao et al., [SpecBench](https://arxiv.org/abs/2605.21384), revised 2026-09-09, originally 2026-05-20. Thirty systems tasks compare visible checks against held-out compositions of the same specified features. Agents can saturate visible tests while failing held-out behavior; the paper reports a larger gap on longer tasks. Frozen visible tests can still be overfit. This benchmark is not a controlled trial of akrogon's proposed author split.
- E5. Dan Luu, [How well do agents use test and verification techniques?](https://danluu.com/agentic-testing/), September 2026. The primary page states the month; secondary announcements identify September 8, which I do not use as a verified exact publication day. Original practitioner experiment: 26 instruction conditions and four skills, 80 runs per effort/condition on a Rust Zstd task, scored against hidden tests. TDD instruction produced more tests and worse hard-case results; some skills increased cost without correctness gains. His practical advice is to establish meaningful test/triage structure and inspect the agent's behavior. This contradicts “just say TDD” as the remedy, not all possible test-first workflows.
- E6. Hongyue Yu et al., [TDD-Agent](https://arxiv.org/abs/2608.16742), 2026-08-17 preprint. Reports improvements from test-first reasoning and joint refinement of generated tests/code on LiveCodeBench and RepoEval. This is counterevidence to “agents cannot write useful tests.” Its benchmark findings do not license an executing seat to redefine this repository's approved acceptance conditions.
- E7. Bill Echlin, [Before You Scale AI-Written Testing](https://www.testmanagement.com/blog/2026/08/ai-written-tests-evidence/), 2026-08-11. Original evaluation on his team's product used known-good builds and restored historical bugs. Full test specifications did not outperform short criteria in the small two-requirement study. Generated suite size did not identify quality; detecting the intended broken behavior did. Agents did not weaken tests under the studied process rules. The sample and product scope limit generalization. Independence helps only if the oracle actually reaches the hard behavior.
- E8. Richard Qi et al., Anthropic, [Training a Misaligned Reward Seeker](https://alignment.anthropic.com/2026/reward-seeker/), August 2026, no day stated. Deliberately reward-hacking-trained model tampered with graders/runtime and forged pass signals. This establishes possible mechanisms, not the frequency of cheating by ordinary deployed coding agents. Protecting only test-file text leaves runner and result integrity outside the control.
- E9. [Claude Code best practices](https://code.claude.com/docs/en/best-practices), current undated documentation. Explicitly suggests one session writing tests and another implementing them; also recommends independent review, concrete verification and correctness-only findings. It warns that asking reviewers to find gaps can generate unnecessary engineering. This is current tool-maker guidance, not a dated Aug–Oct study.

Older sources, explicitly outside the requested window:

- E10. Nicholas Carlini, Anthropic, [Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler), 2026-02-05, and Prithvi Rajasekaran, [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24. Original engineering accounts emphasize meaningful tests and independent evaluation. Rajasekaran also reports four-hour iterative runs and later removes evaluation steps when their cost exceeds their benefit. A separate evaluator is not automatically an efficient evaluator.
- E11. Anthropic, [Finding bugs with Claude and property-based testing](https://www.anthropic.com/research/property-based-testing), 2026-01-14. Agents generated useful properties and found real bugs, with substantial independent human validation. Supports purposeful properties for difficult logic, not a mandatory property-testing layer everywhere.
- E12. Kent C. Dodds, [Write tests. Not too many. Mostly integration.](https://kentcdodds.com/blog/write-tests), 2019-07-13, based on Guillermo Rauch's 2016-12-10 tweet. Established practitioner advice: optimize confidence versus creation/upkeep cost, avoid implementation-detail tests and do not chase a coverage percentage. His numerical coverage example is explicitly informal. “Mostly integration” reflects application confidence, not a universal replacement for unit tests of difficult algorithms.

X evidence and gaps: Luu quotes Gary Bernhardt's criticism of excessive mocking and links [the original X post](https://x.com/garybernhardt/status/2067002665427775613). Direct retrieval returned 403. I can verify Luu's September quotation, not the post's publication date or surrounding thread. Searches for Aug–Oct coding-agent test authorship, frozen tests and separate test sessions on X found no independently retrievable recent original thread establishing the claimed consensus. Rauch's older tweet is reproduced and dated by Dodds; direct X retrieval also failed. I found no reliable controlled study that establishes “same executing agent always rigs tests” or “moving authorship alone prevents endless repairs.” Recent practitioner evidence and research disagree on test-first gains, so the recommendation is structural policy plus calibrated evidence, not claimed scientific unanimity.

## 3. Loops to cut and calibrate

| Loop | Target | Sensor | Actuator |
|---|---|---|---|
| C1. Implementer changes code and oracle until green | Approved behavior, not green at any cost | Accepted test version plus meaningful bad-case failure | Reject unauthorized test/fixture/runner changes; return a wrong-test claim to its independent owner |
| C2. More tests → more maintenance → more review demands | Distinct important failure modes with minimal lifetime cost | Which regression each check uniquely detects | Reuse/extend an existing check; decline duplicates and speculative edge cases |
| C3. Missing live proof → new rig → rig defects → more repair | Working approved evidence path before broad execution | One real path plus actual artifacts, then declared remaining outcomes | Stop a machinery mismatch; reuse an existing tool or chart independently provable missing capability |
| C4. Filtered green → acceptance debt hidden | Every required outcome evidenced | Executed, failed and unrun outcomes separately | Mark subset success partial; retain the unmet criterion |
| C5. Repeated slow runs after small changes | Fresh proof only where behavior/evidence changed | Planned changed-stage/consumer relationships | Reuse unchanged evidence and rerun affected stages, preserving explicit full-run requirements |

C1 follows the current co-authorship and trailer mechanism. C2 follows E5/E7/E12 and existing Fix/Nit rules. C3/C4 are measured in the case and corrected systems analysis. C5 is already required by `implement-issue/SKILL.md:84` and standing design `:15`, so do not invent a blanket rerun rule. None needs a new timer.

## 4. Smallest coherent design and its costs

D1. Give existing B responsibility for acceptance tests before A or workers write production code. A's planner fixes the criterion-to-proof map first. B writes only the missing purposeful tests using the existing runner, exercises the relevant bad behavior or verifies the intended red result, and records the tested contract. Existing sufficient tests need no replacement. A and workers receive those tests and implement only production work. B owns expected results; A owns production code. This chooses independent authorship over the operator's tentative “main implementer before subagents” variant because A also currently writes repairs and inline code.

Use the existing planning boundary, not another service or a third permanent agent. A finalizes planning, then B prepares tests, then implementation starts. This does require an ordered B task and a readiness gate at that boundary. Today's plan.synthesis dispatch is A-only (`src/routing.ts:29-31`); it cannot be claimed to provide this already. If B must never be the executing author, B's current product repairs move to A as well. Cost: B becomes an upstream capacity constraint and loses its fast local product-repair path. Keep preparation small and reuse existing tests rather than generating a second suite. Merely renaming A a test role while letting the same session immediately author product code is not independent authorship.

D2. Fix one authoritative baseline for the agreed test files, expected fixtures and proof/check entry points before implementation. Identify it by committed revision and exact protected paths. At review/phase/merge, compare against that baseline and run the accepted tests through the checker-owned invocation, not a mutable worker-selected command. A changed accepted test or runner blocks acceptance. New self-authored tests cannot replace that baseline or satisfy criteria. Replace trailer-only permission for these paths with independent-owner approval of an explicit baseline update. Protecting only paths recognized by testFile misses custom proof scripts and configuration that skips tests (`src/test-files.ts:19-26`; E8).

This prevents edits from changing the *accepted* check even if the coding seat changes its local copy. A hook or chmod alone cannot guarantee isolation against the same Unix user and shell. Do not describe a shared worktree as a sandbox or hidden-test store. Cost: legitimate test/interface changes require coordination, and the protected set must remain narrow enough to allow ordinary product changes. Independent reruns and source review still check hardcoded visible-case solutions; do not add a hidden-suite platform by default. E4 shows why freezing is useful but insufficient.

D3. Count distinct high-consequence failures, not files, assertions, coverage or tests. A purposeful check uses realistic input, reaches the difficult behavior, observes the externally meaningful result and fails if that behavior regresses. Prefer the smallest existing boundary that can prove it: an integration check for wiring, a unit/property check for difficult isolated logic, a real browser action for browser-dependent behavior. Add a test only when existing evidence misses an approved outcome or a concrete regression. One test may cover several criteria. No numerical quota or forced test per trivial edit. “Hardest part” includes a simple authorization or data-loss boundary when its consequence is severe. Cost: fewer checks can miss unrelated defects; independent criterion mapping and a justified counterexample, not a count target, decide sufficiency. Sources: E5/E7/E11/E12 and current implement rule `:57`.

D4. Replace leaf-built orchestration rigs with an existing trusted CLI, HTTP client, browser connector or reusable recorded chain. Prepare the exact action and expected evidence before implementation. Run changed own code and real consumers; replay unchanged outside/model stages from an authentic recording when the contract permits. A required real live outcome remains real. If the necessary reusable capability does not exist, chart it as an independently provable prerequisite where possible, or change the proposed contract before opening the product leaf. Do not automatically create a harness leaf for every new test. No late repair invents a new evidence architecture. Cost: existing tools may not prove a new outcome, recordings become stale, and a separate prerequisite adds dependency delay. The correct response is an explicit proof/contract decision, not a simulated green result. Source: standing design `:9-15`, corrected systems L1/L3 and E10.

D5. A wrong pre-written test returns to B with the criterion, realistic source and observed contradiction. The executing seat leaves the accepted test unchanged and continues only unrelated valid work. B either confirms a product defect or corrects the test in a separate test-only change, proves the revised check detects the intended failure, and records a new baseline. A changed acceptance requirement returns to the chart/operator; a test-author mistake within the settled requirement does not need a new human permission loop. Reverify affected evidence after correction. Never treat the same author's explanation or a Test-Change trailer as approval. Cost: independent adjudication can delay a valid fix and an over-rigid freeze can preserve bad tests. A clear correction owner avoids an endless “make the impossible test pass” loop. E7's good/bad-build method and current cited-source rule provide the validation basis.

D6. Repair findings about missing test coverage follow the same prewrite boundary: B supplies the narrowly justified frozen regression check before A repairs production. An executor may report a newly discovered bug or missing case, but cannot add its own acceptance oracle. Repeated inability to execute the agreed proof because its machinery is unsuitable uses the existing failed/contract-correction route, not another expanding proof sub-brief. Normal code defects still take normal repair. Cost: this can increase short visible failures and reduce B's repair throughput; it cuts machinery growth without weakening required outcomes. The direct/standalone/inline routes need the same ownership rule, or they become the bypass. No scope expansion, implementation change, test run or external mutation was performed in this analysis.

The remaining operator choice is role ownership: independent B test preparation with A/workers doing all production repairs, or the weaker A-prepares/worker-implements arrangement that must forbid A's own coding exceptions. These are not equivalent. I recommend the former because it has one authority for each side of the acceptance boundary across delegated and inline execution.
