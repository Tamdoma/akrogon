# Territory map, slot D: seat-shell-kill

Date: 2026-11-25. Host for all observations: kernel 7.2.15-5-omarchy, systemd 262, cgroup2fs unified hierarchy, `SHELL=/usr/bin/bash`, `/bin/sh` -> bash.

One line: put every tool shell into a `shells` sub-cgroup of its seat scope at spawn time, and end leftovers with one `cgroup.kill` write at phase advance. Membership is then set by fork inheritance, not read back from a moving tree, so the selection races that killed shell-sweep cannot exist. The hard parts move to two places: how each harness's shell gets in (FK1), and the fact that the `akrogon phase` caller and the run-check writer start inside the kill set (FK3, FK4).

## Ground facts

- G1 Seat layout. `src/seat.ts:startSeat` launches `systemd-run --user --scope --unit=<slice>-<seat>-<rand>.scope --slice=<leafSlice> -p TimeoutStopSec=5 -p CollectMode=inactive-or-failed -p SendSIGHUP=yes -- env <akrogon env> <harness argv>`. Harness, its tool shells, the seat's `akrogon phase` caller and each run-check writer all start in this one scope. The unit name is generated with a random suffix and not saved in state (only session and address are recorded).
- G2 Run-check layout. The writer is the Bun `akrogon run-check` process in the seat scope. A held run's payload goes through `src/scope.ts:runUnitArgv` into a sibling `akrogon-run-<uuid>.scope` in the same leaf slice, with a guard service from `startRunGuard` that stops the scope when the writer dies. A nested run's payload runs in the writer's own cgroup (`src/run-check.ts:checkedRun`, `admission.kind === 'nested'`). The payload env is constructed (`constructedEnv`): only a fixed copied list plus repo `env`/`pass_env` pass through, and the bus is cut. Payloads therefore never inherit a seat-level `BASH_ENV` unless a repo config passes it.
- G3 Phase path. `src/phase.ts:phaseCommand` holds the home-wide `.lock` across `commitMove`. Any kill work inside `commitMove` must be a bounded write, never a wait (this was F10 and F12).
- G4 Delivery path. `src/next.ts:dispatchSlot` returns unless hc status is `idle` or `done`, and takes the lost-seat path only for a missing or `finished` terminal. `src/listen.ts:listenCommand` wakes on `turn`, `blocked`, `finished`, `lost` events only. No timer exists.
- G5 Leaf close already kills by cgroup. `src/reconcile.ts` stops the leaf slice for finished leaves, which ends every scope under it. Escapes into sibling scopes under the slice are therefore already bounded by leaf close.
- G6 Kernel. From the kernel cgroup v2 documentation (read 2026-11-25, https://docs.kernel.org/admin-guide/cgroup-v2.html): a forked child is born into its parent's cgroup at fork time, and migrating a process does not move its existing descendants. `cgroup.kill`: writing `1` SIGKILLs every process in the cgroup tree, and it "will deal with concurrent forks appropriately and is protected against migrations". `cgroup.freeze`: freezing may take some time (`frozen` in `cgroup.events` marks completion), frozen processes can still be killed, and processes can enter or leave while a freeze races a fork. Creating child cgroups under a populated cgroup is fine as long as no domain controllers are enabled in `cgroup.subtree_control` (no-internal-process constraint does not bite for grouping-only subcgroups).
- G7 systemd delegation. From `systemd.resource-control` (systemd 262, local man page): with `Delegate=` the manager "will refrain from manipulating control groups or moving processes below the unit's control group", and the tree below the unit is owned by the unit. Without it, that promise does not exist. `DelegateSubgroup=` also exists but only chooses where the unit's own processes start.
- G8 Old proofs that still hold. P1 and P1b: claude reports `done` and advances `turn` after its background tool shell's group gets TERM or KILL. P3: codex keeps `node_repl` and `codex-code-mode-host` as direct harness children; claude and pi hold only tool shells. P2: hc keep-recovery shapes for the bare-shell seat.

## What F1 to F12 actually were

- Race, kill too little: F1 (child forked after the census, reparented before the second pass, survives).
- Race, spare set goes stale: F2 (run-check writer admitted after the spare scan gets killed), F3 and F8 (process migrates to its run scope between snapshot and signal, gets signalled outside the boundary).
- Rule, kill too much: F6 (any orphan counts as a root, an unrelated `ssh-agent` dies), F11 (process-group sharing pulls in a non-shell harness child).
- New stuck state: F9 (an interrupted sweep leaves a shell SIGSTOPped forever).
- Wait under a lock: F10 (exit polling under the home lock), F12 (admission lock taken under the home lock stalls unrelated repos).
- Process only: F4, F5, F7 (test coverage, trailers, fixture hygiene). No mechanism choice removes these; they follow any design.

Every mechanism below is judged against these classes. A mechanism "removes" a class only if the failing read or wait no longer exists anywhere in it.

## Forks

### FK1. How does a tool shell get into its own cgroup?

This is the fork the whole chart turns on. Entry must happen at spawn, because only fork inheritance is race-free (G6). Akrogon controls the seat env and the harness argv (`startSeat`, `harnessArgv`), nothing else in the spawn path.

- O1a `BASH_ENV` self-move. Akrogon sets `BASH_ENV=<akrogon-owned script>` in the seat env. Bash runs that file at every non-interactive start (`bash` manual, Invocation: "When bash is started non-interactively... it looks for the variable BASH_ENV"). The script reads `/proc/self/cgroup` and, if the shell sits in its seat scope root, writes its own pid into `<scope>/shells/cgroup.procs`. Children forked after that point inherit `shells`. Proven free in E6 below, including a nested bash and a `setsid` orphan.
  - pi: works today. Pi 1.6.0 runs `/bin/bash -c` for its bash tool (installed docs `/usr/lib/pi-coding-agent/docs/shell-aliases.md`). This session's own tool shell is a direct `bash` child of `pi` (observed, E0).
  - claude: works when claude's shell is bash. Claude picks its Bash-tool shell from `CLAUDE_CODE_SHELL`, else `$SHELL` if it is bash or zsh, else the first working zsh then bash (env-vars reference, read 2026-11-25, https://code.claude.com/docs/en/env-vars). On a zsh seat, O1a misses unless akrogon also forces `CLAUDE_CODE_SHELL=/usr/bin/bash`, which changes the seat's shell snapshot source from `.zshrc` to `.bashrc`. P1 observed bash on this host.
  - codex: env delivery is documented (`shell_environment_policy.inherit`, `.set`; config reference read 2026-11-25, https://developers.openai.com/codex/config-reference.md), and the 0.172.0 binary contains `/bin/bash` and "falling back to /bin/sh" strings. Which shell it actually spawns for the exec tool, and whether that shell reads `BASH_ENV`, is unverified. Model knowledge only; searches of the config reference found no shell-program key.
  - agy: nothing found. The 1.5.16 binary contains `/bin/bash` and `/bin/sh` strings, `--settings` takes a session JSON object, and no doc or help names a shell key. Unverified.
  - Breadth problem: `BASH_ENV` fires for every bash in the seat scope, including one spawned by a non-shell helper (a codex helper running a script). The old brief protected shells under helpers. The script can narrow at spawn time (its parent is alive and stable at that instant, unlike a later census), but any parent test reintroduces a small rule. See FK5.
  - Failure mode must be silent and total: a failing move must never break or dirty a tool call. The script needs all output discarded and a zero exit whatever happens.
- O1b Harness shell settings per harness.
  - claude `CLAUDE_CODE_SHELL_PREFIX` wraps every shell command claude spawns, but the same reference says it also wraps hook commands and stdio MCP server startup. MCP servers are long-lived harness children that must survive a phase advance, and the wrapper receives only the command string, so it cannot tell an MCP launch from a tool shell. This poisons O1b for claude unless the chart accepts MCP servers dying at each phase advance.
  - claude `CLAUDE_CODE_SHELL` accepts only a working bash or zsh path and is ignored otherwise. A wrapper script named or shaped to pass that check is unverified and version-coupled.
  - claude also has `CLAUDE_CODE_TOOL_MEMORY_LIMIT`, which already herds tool commands into a claude-owned cgroup for accounting (tools reference, read 2026-11-25). Reusing that cgroup as the kill target is claude-only, needs version 2.1.233+, and its path and lifetime are undocumented. Worth one probe, not a foundation.
  - pi `shellPath` and `shellCommandPrefix` exist (installed `docs/settings.md`) but live in `~/.pi/agent/settings.json` or a project `.pi/settings.json`. Akrogon has no per-seat way to set them: the user file would affect every pi session on the host, and the project file is repo-owned. No env or flag override was found in the installed docs.
  - codex and agy: no shell-path or shell-prefix setting found in config reference, help output, or binary strings (searched 2026-11-25).
- O1c PATH shadowing. Akrogon puts a directory of `bash`/`sh`/`zsh` wrappers first in the seat `PATH`. Misses every harness that execs an absolute path (pi execs `/bin/bash` first by its own docs), and it changes what every seat script that calls `bash` gets. Worse than O1a on both counts.
- O1d Move after spawn. A watcher (akrogon or a helper in the scope) polls `cgroup.procs` and moves new shells into `shells`. A child forked before its parent is moved stays behind in the scope root and escapes the kill (G6: migration does not move existing descendants). This keeps a smaller F1: the miss needs a fork inside one poll interval, and the consequence is a leftover, never a wrong kill. It also needs a permanent poller per seat. Strictly worse than O1a where O1a works; it is the only entry that needs no harness cooperation at all.
- O1e No entry. Skip per-shell cgroups and kill at scope granularity. That is FK2 O2b and O2c.

### FK2. What gets killed, with what primitive?

- O2a `cgroup.kill` on `<seat scope>/shells` (needs FK1 entry). One bounded write, no census, no signals, no wait, no locks. Removes F1 (fork inheritance plus kill-side fork handling, G6), F3 and F8 (nothing is signalled by pid, so migration between read and signal has no read to race), F9 (no stopped state exists), F10 and F12 (no wait and no admission lock). F2 changes shape rather than dying: the writer starts inside `shells`, see FK4. F6 and F11 change shape: the kill set is "everything that entered through a tool shell", see FK5. New invite: escape by self-migration (FK6).
- O2b Stop the whole seat scope and relaunch or resume the harness. `systemctl --user stop <seat>.scope` ends harness, helpers, shells and writers together; no selection of any kind, and no FK1 entry needed. Costs: seat continuity. Pi already gets a pinned `--session-id` in `startSeat`, so a resume is plausible; claude needs its session id for `-r`; codex `resume` needs a session pick that is ambiguous across parallel seats; agy resume by conversation id is undocumented here. Every phase advance would pay a harness restart and a transcript re-read, lose in-flight harness state (background subagents, MCP connections), and need care not to charge the deliberate restart as a lost seat in `dispatchSlot`. It also kills live run-check writers of the leaf unless gated on live run records, which brings back a read before the stop. And the caller is inside the scope it stops (FK3, harder here: the caller cannot move out and still be the seat's tool shell). Removes all race classes by removing the seat, at the highest running cost.
  - Variant O2b-min: keep the scope, `cgroup.kill` the scope root. Same as O2b without systemd stop semantics; the scope unit dies anyway once empty. No saving over O2b.
- O2c `cgroup.freeze` the seat scope, select from the now-stable tree, kill, thaw. Freezing does stop the tree from changing under the census once `frozen 1` lands, so F1 and F3 mostly close (a fork that races the freeze itself can still land outside, G6). The selection rule itself survives untouched, so F6 and F11 stay fully open, and the rule was half the failure. Two new problems are proven below: the caller inside the scope freezes itself and can never thaw or kill (E5b), so the whole operation must run from outside the scope; and a killer that dies mid-operation leaves the entire seat, harness included, frozen until something thaws it (F9 one level up, worse blast radius). Freeze is a guard on the old design, not a removal of it.
- O2d Move the keep set out, then kill the rest. Move harness, caller chain and known writer pids into a `keep` subcgroup, then `cgroup.kill` the scope root remainder. The keep set still has to be discovered: harness pid comes from hc, writers from run records, and codex's helpers (P3) appear in no record, so a census returns for exactly the processes that broke F6 and F11. Moving a writer also strands any children it already forked. No class fully closes.
- O2e The stopped design (census plus per-pid SIGKILL, any refinement). Five rounds of evidence say each refinement trades one class above for another. Not re-argued further.

### FK3. Who writes the kill? Where does the `akrogon phase` caller sit?

Under O2a the caller runs inside a tool shell, which is inside `shells`. E5a proves a process that writes `1` to its own cgroup's `cgroup.kill` is SIGKILLed by that write and runs nothing after it. The old design spared the caller's ancestor chain; a cgroup kill cannot spare anyone inside.

- O3a Caller moves itself and its tool shell out to the scope root, then writes the kill. The tool call completes and returns its result normally. A background child forked by that same shell in the gap between the move and the kill is born in the scope root and escapes this advance (it is still ended at the next advance only if a later shell starts it, and at leaf close by G5). Moving the shell also needs its pid, which the caller has as its parent chain.
- O3b Detached helper. `commitMove` spawns a small helper in a sibling scope of the leaf slice (the `startRunGuard` pattern already uses `tail --pid=<writer>` plus a `systemctl stop`), which waits for the caller's tool shell to exit and then writes `cgroup.kill`. The phase command returns, the seat ends its turn, then the leftovers die and claude flips to `done` (P1). Waiting on the tool-shell pid rather than the `akrogon phase` pid covers a tool call shaped `akrogon phase ... && more`. Cost: one transient unit per phase move and a kill that lands moments after the move instead of inside it. Nothing waits under the lock: spawning the helper is the only in-lock work, and even that can sit after the commit.
- O3c A later `next` pass writes it. The masked seat produces no event to wake a pass (G4), so the kill waits for unrelated activity or never lands. This reopens the original stall. Rejected as the primary path.
- O3d Caller writes the kill last and accepts its own SIGKILL. The move is committed by then, but the tool call reports a killed shell to the harness. A seat that retries its phase call after a "failed" tool result now calls phase twice for one move. Ugly and unnecessary given O3b.
- Caller position under the other FK2 options: O2b kills the caller's whole scope, so only O3b-style outside help or O3c works, and the restart must also come from outside. O2c needs an outside operator for freeze, census, kill and thaw (E5b). An operator-run `akrogon phase` from their own terminal sits outside every seat scope and can write any of these directly; only seat-originated calls need FK3 handling.

### FK4. Where do run-check writers and payloads sit?

- Payloads are already safe under O2a: held runs live in their sibling run scope (G2), outside the seat scope entirely. Nested payloads run in the writer's cgroup, so their fate follows the writer.
- The writer is the exposure. It is spawned from a tool shell, so under FK1 it starts inside `shells` and a phase advance during a long check (from the other seat, or the operator) would SIGKILL it mid-run or mid-publish. A killed writer can leave an abandoned capture pair that refuses later moves (the F2 consequence, via `src/run-check.ts:abandonedCaptures`).
  - O4a Akrogon relocates itself at startup. Any `akrogon` process that finds its own cgroup is a seat `shells` cgroup moves itself to the scope root before doing anything else. Akrogon owns the writer and the phase caller, so both leave the kill set by construction, before capture files or state writes exist. Remaining window: the milliseconds between the shell spawning `akrogon` and the relocate, during which a concurrent phase advance could still catch it. In that window the writer has published nothing and holds no captures, so the consequence is a lost in-flight command, not a poisoned leaf. That is a strictly smaller F2.
  - O4b Phase advance skips or delays the kill while leaf run records are live. This is one record read before the write (not a process selection), but it reintroduces a spare decision about writer liveness and leaves shells alive past the advance whenever a check is running, which is exactly when seats usually advance. Weaker than O4a.
  - O4c Accept writer kills. No; the abandoned-capture refusal is a leaf-blocking state, worse than the stall being fixed.
  - Note the seat's other akrogon commands (`status`, `stop`, `run-check`) also relocate under O4a. Nothing akrogon-owned should ever be in the kill set, and O4a makes that a property of the binary rather than of each call site.

### FK5. How wide is "leftover"?

The operator decision says leftover seat shells end at phase advance. The old brief additionally protected non-shell harness children and shells under them. Entry-at-spawn redraws that line:

- O5a Uniform: everything whose ancestry passes through a tool shell dies at phase advance, shells and non-shells alike. Direct harness children that never went through a shell (codex helpers, MCP servers) are automatically out, with no allowlist. Things that die which the old rule spared: a dev server or `ssh-agent` a seat started from a tool shell for later phases, a shell a helper spawned (if FK1 entry is every-bash). One sentence explains the whole rule, and it cannot be wrong about a process it never reads.
- O5b Narrow entry: the FK1 entry script moves a shell only when its parent is the harness or an already-moved shell. The parent read happens at spawn, when the parent is guaranteed present, so it is not the old census race. It preserves helper-spawned shells. It costs a parent identity test in the entry path forever, plus a way to know which pid is the harness (the entry script would need it in env, and `startSeat` does not know the harness pid until after launch).
- What breaks later under O5a: any future seat workflow that intentionally parks a long-lived process across phases (a watch loop is the incident; a language server started by a tool shell is the sympathetic case). Under O5b: a new harness that spawns tool shells through an intermediary (a code-mode host) silently falls out of the kill set and the stall returns for that harness.

### FK6. Delegation and escape

- O6a Add `-p Delegate=yes` to the seat scope in `startSeat`, and have `startSeat` create the `shells` subcgroup once scope entry is proven (`scopeEntry` already waits for the harness to land in the scope; the path is derivable via `cgroupOf`). Delegation is the supported contract that systemd will not rearrange the subtree (G7). Side effects to accept: controllers get enabled for siblings in the slice (man page note), and seat processes can manage their own subtree within parent limits. Scope stop still ends the whole tree.
- O6b No Delegate. E1 shows subcgroup creation and moves work on this host without it, because the user manager's tree is user-owned. But nothing promises systemd will not move processes back to the scope root on a reload or unit change, and a silent flatten would empty `shells` and bring back the stall with no error anywhere. The saving is one unit property. Not worth it.
- Escape, either way: E4 shows a process in `shells` can move itself up to the seat scope root (same user owns the delegated subtree), and any seat process with bus access can `systemd-run --scope` into a sibling scope, exactly as run-check payloads do by design. Moving above the seat scope by direct write failed in E1 and E2. So the kill set is "tool-shell descendants that did not deliberately leave", not a confinement boundary. Seats are trusted agents and the incident leftovers are accidents, not escapes. Anything that leaves into the leaf slice is still ended at leaf close (G5). Cutting the bus in the seat env would close the `systemd-run` exit but breaks legitimate seat use of user systemd in tool shells and goes past #157. Recommend recording escape as accepted, not engineering against it.

### FK7. The bare-shell seat (second half of #157)

Unchanged by any FK2 choice: dispatch treats a `live`, null-status terminal in either P2 recovery shape as lost and takes the existing lost-seat path. This drew no review finding in the old leaf. It shares nothing with the kill mechanism except the leaf. Keep it in the same leaf (signpost 4a, fewest leaves); there is no fork here unless the door wants to split it out to land it ahead of FK1 verification.

### FK8. Scope of the residual (seed-decision Findings F1)

A shell started after the seat's phase call, and a turn that ends silently with a shell running and no phase call, stay masked under every option above, because nothing wakes a pass (G4). That residual was recorded, not locked. O2a does make a future delivery-time kill cheap (one write, no census), but the wake and the threshold questions are untouched. Recommend the new leaf keep the recorded residual and the periodic wake stays a separate chart candidate, exactly as the seed finding left it.

## Risks and pitfalls over the work's lifetime

- R1 Entry coverage decays silently. A harness update that changes how tool shells spawn (pi extension replacing the bash tool, codex routing exec through its code-mode host, claude switching a seat to zsh) drops that harness out of `shells` with no error; the symptom is the original silent stall. Mitigation is a cheap standing signal: the kill path can record `shells` population at each advance, and a seat whose shells cgroup is always empty while it runs tool calls is visible in timings. Per-harness spawn proofs need re-running when a harness major version changes.
- R2 `cgroup.kill` is SIGKILL only. No grace period, no cleanup traps. The old design already chose SIGKILL, so this is not a regression, but FK5 O5a widens who receives it (any tool-shell descendant, including a seat-started database or dev server).
- R3 Reporting. The old design promised a `shell_sweep` timing row with ended pids and names. `cgroup.kill` reports nothing. Reading `shells/cgroup.procs` just before the write gives a for-report-only snapshot that may miss a just-forked pid. That is fine for evidence as long as nothing acts on it. Decide the row's contents in the leaf (Q5); do not let reporting reintroduce selection.
- R4 Seat scope resolution at kill time. The unit name is random-suffixed and not recorded (G1). Resolving through the harness pid from hc works while the harness lives; shells that outlive a dead harness sit in a scope nobody can name from state. Recording the unit name in the seat record at `startSeat` is a small state change that makes the kill path independent of hc and of harness liveness. The old design's per-sweep hc resolution is the alternative (Q7).
- R5 `BASH_ENV` breadth and hygiene. The file must be akrogon-owned (under the akrogon home or release dir, an absolute path), never in a worktree. It runs on every bash spawn in the seat, including build-system subshells by the hundred, so it must stay at one proc read and at most one write. It also fires for `bash script.sh`, not only `bash -c`, which is desired here. If a repo later passes `BASH_ENV` through its run-check `env` or `pass_env` config, payload bashes would run it inside run scopes; the script must act only when the current cgroup is exactly a seat scope root it recognizes (an akrogon-set env marker naming the `shells` path is the clean gate), and do nothing anywhere else.
- R6 Consultant and direct seats are out of scope, correctly. `src/seat.ts:launch` starts them with plain `env`, no systemd scope; this very session sits in an `hc-hold-*.service` cgroup. Seat env additions must go in `startSeat` only, or chart consultants would start self-relocating inside a cgroup akrogon does not own.
- R7 Tests must cross the real systemd boundary. The old fake `/proc` and cgroup roots (`AKROGON_PROC_ROOT`, `AKROGON_CGROUP_ROOT` in `src/scope.ts`) can prove path handling but cannot prove a kill. A real test needs a throwaway delegated user scope like E2 and E3, and must refuse or skip loudly where no user manager exists. That is cheaper than the old 738-line sweep test plus 492-line freshness test on the stopped branch, because there is no selection logic left to enumerate.
- R8 Freeze as a future temptation. If a later problem wants "pause the seat", E5b is the standing warning: never freeze a cgroup you are inside, and a frozen scope whose freezer dies stays frozen. Any freeze design needs an outside owner and a thaw watchdog. Nothing in this chart should build one.
- R9 Platform. Akrogon is already systemd-bound end to end (seat scopes, run scopes, guards, slice stops in reconcile). `cgroup.kill` and delegation add no new platform requirement beyond cgroup v2 unified, which the whole run-unit design already assumes. The kernel version floor for `cgroup.kill` is not stated in the doc page read; model knowledge says it is an old addition relative to this host's kernel 7.2. Treat "works on this host" as proven (E3) and portability past this host as unexamined.
- R10 Codex masking through helpers stays open (old residual). If codex holds `working` through `node_repl` or the code-mode host rather than a tool shell, no shell kill of any design unblocks it. O2a neither fixes nor worsens this. Only a paid codex probe like P1 settles it.

## Observations (free, own throwaway units, 2026-11-25)

All units were `probeD-*` user scopes created by this session, removed or verified gone after each run (`systemctl --user list-units 'probeD*'` empty at the end; probe files under `/tmp/akr-probeD` deleted). No foreign process was signalled or moved. No paid harness launch was run.

- E0 Pi tool shell shape. Command: inspect this session's own shell. Result: `bash`, parent `pi`, cgroup `.../app.slice/hc-hold-7db5510a.service` (a consultant launch, not a leaf seat). Confirms pi spawns bash directly and consultants sit outside seat scopes.
- E1 Subcgroup without Delegate. Command: `systemd-run --user --scope --unit=probeD-e1 -- inside.sh`, where the script makes a `shells` subcgroup in its own scope, moves itself in, forks a child, then tries two escapes. Result: mkdir, self-move and child inheritance all worked; move up to the scope root worked; move above the scope failed (`Device or resource busy`). Limits: proves this host today, not a systemd promise (G7).
- E2 Same with `-p Delegate=yes`. Identical results.
- E3 `cgroup.kill` on `shells`. A delegated scope ran a harness-side sleeper at the scope root and, inside `shells`, a looping bash that forked `sleep` children plus a `setsid` detached sleeper. One `echo 1 > shells/cgroup.kill` from outside: `shells` reported `populated 0`, the loop and both sleepers were gone, the root sleeper stayed alive. Cleanup by stopping the scope.
- E4 Escape (part of E1 and E2). From inside `shells`, writing the own pid to the scope root's `cgroup.procs` succeeded; writing it to the parent slice failed. Containment boundary on this host is the seat scope, not `shells`.
- E5a Kill from inside. A script moved itself into `shells` and wrote `1` to `shells/cgroup.kill`. It was SIGKILLed by the write (systemd-run exit 137); the line after the write never ran.
- E5b Freeze from inside. A script wrote `1` to its own scope's `cgroup.freeze`. `cgroup.events` showed `frozen 1` and the script made no progress until an outside `echo 0` thawed it, after which it exited normally.
- E6 `BASH_ENV` entry. In a delegated scope with a pre-made `shells`, `BASH_ENV` pointed at a script that moves the shell into `shells` when it starts at the scope root. A tool-style `bash -c`, a nested `bash -c` inside it, and a `setsid` orphan it started all landed in `shells`; after the tool bash exited, the orphan was the only member, and one `cgroup.kill` write cleared it (`populated 0`).

Doc searches that found nothing stronger (all 2026-11-25): no shell-path or shell-prefix key in the codex config reference or the agy help and settings surface; no per-seat override for pi `shellPath` in the installed pi docs; no kernel-version floor stated for `cgroup.kill` in the cgroup v2 documentation. Codex and agy shell selection above is binary-string evidence plus model knowledge, marked as such in FK1.

## Recommendation

- D1 Take O2a: `shells` subcgroup per seat scope, one `cgroup.kill` write per recorded seat in `commitMove` after the move is saved and logged (the old Q1 call site, including moves to `failed` and `merged`), never blocking or failing the committed move. This is the only option that removes the census entirely, which removes F1, F3, F8, F9, F10 and F12 as classes and converts F2 and F6/F11 into FK4 and FK5 placement properties.
- D2 Entry via O1a (`BASH_ENV` self-move gated on an akrogon env marker) with O6a (`Delegate=yes`, `startSeat` creates `shells`), plus O4a (akrogon relocates itself out of `shells` at startup) and O3b (detached helper waits for the caller's tool shell to exit, then writes the kill; a caller outside every seat scope writes directly). Record the seat scope unit in state at `startSeat` (R4).
- D3 Keep FK7 (bare-shell lost seat) in the same leaf, unchanged from the old Q3 shape.
