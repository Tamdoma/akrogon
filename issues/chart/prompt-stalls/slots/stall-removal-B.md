**Pick and cost.** Choose 1a: enforce `permissions.denyInsteadOfPrompting: true` in the existing Claude settings argument at `harnessArgv`. Deny the request and let the seat correct it. This removes an indefinite permission wait without approving an uncertain deletion. It reaches seats and code-launched consultants using this function. Do not describe it as removing every possible interactive dialog.

**Rejected options.** 1b gives the same policy a per-machine owner and an external readiness dependency when code already owns Claude-specific launch policy. 1c cannot guarantee prevention, misses other prompt causes and depends on agent compliance. 1d removes the dangerous-deletion safeguard and admits uncertain targets, contrary to signpost 4a. Watch approval of this particular rm request is likewise excluded by that lock.

**Evidence.** Better-than-training, inspected code: `src/seat.ts:harnessArgv` already appends AskUserQuestion exclusion and is shared with `startConsultant`; `akrogon config` carries existing subagent-model env in settings. Observed-by-A evidence, not independently repeated: `slots/map-A.md` O3–O5 reports indefinite subagent rm prompt, immediate denial with the setting, and replacement of an earlier settings argument. Better-than-training, official documentation, read today: [denyInsteadOfPrompting](https://code.claude.com/docs/en/settings-reference.md#permissions-denyinsteadofprompting) applies to interactive sessions and subagents, requires 2.1.319+, denies approval-dependent calls and also suppresses question/plan tools and MCP elicitation. Installed version independently read earlier: 2.1.325.

**Pitfalls and removal.** Preserve the existing settings through Q2 instead of appending a second flag. Prove a subagent receives the denial and that a later permitted tool completes; denial alone is weaker than resumed work. Retain the directories in the unsafe test case. Keep version and configuration in proof evidence. Existing watch loop judgment handles repeated same-result calls; it does not prove the seat always finds a valid rewrite. An actually necessary denied operation remains an operator prerequisite, not an instruction to disguise it.

**Missing question.** Does any supported lifecycle step require Claude's plan-mode transition tools? The setting removes them, and a session already in plan mode cannot independently exit. Inspect the actual lifecycle launch and tool use before calling this side effect harmless. Do not expand the leaf into removing the already-landed AskUserQuestion flag merely because it becomes redundant.

## Q2. Merge settings without losing configuration

**Pick and cost.** Support the used inline JSON forms and absence, and explicitly refuse file-path settings before launching. This follows the current machine surface and avoids inventing file resolution and serialization behavior for an unused form. Cost: the leaf narrows accepted Claude template forms, so state that incompatibility explicitly. If preserving file-path compatibility is required, that is a different picked contract, not a silent fallback.

1. A separated inline flag and an equals-form inline flag both produce one effective settings object. Preserve every unrelated top-level and permissions field, override only `permissions.denyInsteadOfPrompting`, and emit one flag/value pair.
2. With no flag, add that object. With multiple flags, use the last effective value, matching the observed CLI behavior, then emit a single merged flag. Do not combine shadowed earlier objects and accidentally restore settings the operator intentionally replaced.
3. Refuse a file operand, malformed JSON, non-object settings or an invalid permissions value with a diagnostic identifying the Claude template and failed operand. Do not drop the value, replace it with an empty object, mutate its source or write a temporary settings file.
4. Interpret settings flags only in the option portion before `--`. Insert the enforced setting before that delimiter. Text after it is task text, even if it contains `--settings`.

**Rejected options.** Appending a second settings flag loses model/env policy. Replacing the whole permissions object loses unrelated restrictions. Editing a supplied file changes shared configuration. Loading arbitrary settings files into JSON expands this leaf into path resolution relative to the eventual launch cwd, file-format compatibility and snapshot semantics. It is defensible only if compatibility is explicitly selected and tested.

**Evidence.** Better-than-training, inspected code: `src/seat.ts:harnessArgv` parses the substituted template into argv; it currently has no launch-cwd parameter, while seat and consultant launches use different cwd sources. `src/config.ts` validates harnesses as strings, not Claude settings objects, so the new external JSON needs boundary parsing. Observed-by-A: map-A O5 establishes last-flag replacement; it does not establish arbitrary settings-file parsing behavior. Date: today.

**Pitfalls and removal.** Test semantic settings preservation at the existing argv boundary: today’s subagent env, unrelated permission restrictions, both inline spellings, no flag, repeated flags and an explicit unsupported-file failure. A string substitution over the shell command cannot reliably preserve these semantics; transform the already-parsed argv. Keep non-Claude argv unchanged. The policy must override an explicit false while preserving all other fields.

**Missing question.** Is file-path compatibility actually a required supported contract? If yes, read the file relative to the cwd Claude will use and preserve its supported parser semantics. Do not resolve relative paths against the door's current cwd merely because `harnessArgv` runs there. I prefer the explicit narrow contract until evidence requires this added behavior.
