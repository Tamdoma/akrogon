## Forks
1. Who is the minimum reader? Intake says "all people who want to build", but the floor is a terminal, Herdr, Bun, git and at least one agent CLI. Options: (a) "someone who has used one coding agent in a terminal" and say so on page 1; (b) true non-developer, which needs install hand-holding the tool cannot remove (Herdr, systemd). Later risk of (b): promises the product can't keep.
2. Doc architecture. (a) Concept ladder + separate reference (Diátaxis-style split of learn vs look-up), each fact in one home; (b) one long linear book; (c) Diátaxis full four quadrants. Practitioner: Daniele Procida, diataxis.fr (Django, Canonical adopt it): mixing tutorial and reference is the main cause of "all over the place". (c) is heavy for ~20 pages. Later risk of (b): every feature edit touches the middle of a narrative.
3. Docs vs skill text ownership. (a) Guide explains what/when/why; skill files own exact rules, guide links to them and never restates; (b) guide restates rules in plain words. (b) drifts weekly (chart.md today). (a) costs: beginners must click into dense skill text for detail.
4. Where on GitHub. (a) Markdown in docs/ rendered by GitHub, no build; (b) GitHub Pages site (VitePress/MkDocs) — search, nav, but a build, a deploy, and agents read source anyway; (c) wiki — separate repo, drifts. 
5. SVGs. GitHub renders SVG via <img> through its proxy: CSS/SMIL animation works, no JS, no hover, no external fonts; dark mode via prefers-color-scheme inside the SVG or <picture>. Which set: factory overview, life of a leaf (animated), the chart door with consultants, unattended (watch + autopilot), maybe direct vs lifecycle. Authoring: (a) hand-written SVG files; (b) generated by a script from a source (e.g. phase list in src/routing.ts) so they can't go stale. Respect prefers-reduced-motion. Low confidence: exact GitHub sanitizer limits — needs a real render probe.
6. Running example. (a) Keep one simple fictional example through the ladder + a real case-studies page; (b) real cases only. Real cases carry other people's paths/origins (seeds cite another person's home path and project), Croatian slugs, private repos → must be scrubbed or chosen from akrogon itself.
7. Staying current. (a) Standing rule: every feature leaf that changes operator-visible behavior updates its one doc home (put in standing design / init guidance); (b) mechanical check: docs link check + command table vs src; (c) nothing. A link check is the only cheap thing that catches restructure breakage; no such machinery exists on main → prerequisite leaf if wanted.
8. Split. Candidate leaves: skeleton + concept ladder pages; reference pages (commands, config, files, phases); SVG set; README rewrite; case studies. Real dependency: README and ladder link into reference/SVG paths — fixed by naming paths in the design, so they can run in parallel; only a link-check leaf (if chosen) must come first.

## Pitfalls over lifetime
- Restating rules → drift (fork 3).
- Counts in prose ("ten workflows") go stale → never write counts.
- Animated SVG noise, motion sickness, unreadable in dark mode → reduced-motion, both themes, only where motion shows a sequence.
- Large restructure breaks inbound links (README anchors, grounding.index, skills linking docs/guide/*.md) → keep or redirect paths, link check.
- Agents use docs as grounding → plain beginner prose must still be exact.
