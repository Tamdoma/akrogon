# Leaf review: fresh-first-worktree, slot B

Two disagreements.

## F1. Done-criterion 6 cannot pass within the leaf's ownership unless need N1 is an input — and no input is declared

Criterion 6 requires `learnings/LESSONS.md` to no longer hold the line "leaf worktree kept at a stale base" and the history file to gain an `Applied` line, in this leaf's diff. The leaf works on a fresh worktree created from the tracking ref — that is the entire point of this leaf. As of today neither the line nor the history file exists on main: `git show origin/main:learnings/LESSONS.md` has no "stale base" line, `git log origin/main -- learnings/history/2026-11-24-leaf-worktree-stale-base.md` prints nothing, and both are uncommitted in the working checkout (` M learnings/LESSONS.md`, `?? learnings/history/2026-11-24-leaf-worktree-stale-base.md`). The chart's own needs sheet (signposts "## Needs", N1) states the operator must commit these writes and the fresh-leaf-base leaf needs the line on main to remove it. If the leaf dispatches before that commit lands, its base has nothing to remove: the criterion either degenerates to a no-op diff or the implementer writes the lesson files itself, contradicting N1's assignment to the operator. Either way the outcome depends on an event outside the leaf's control, and `readiness.yaml` declares `inputs: []`, so nothing holds the leaf back — dispatch would start it immediately against a base where the criterion is unsatisfiable as specified.

Evidence:
- `git log origin/main --oneline -- learnings/history/2026-11-24-leaf-worktree-stale-base.md` empty; `git show origin/main:learnings/LESSONS.md | grep "stale base"` empty; `git status --porcelain learnings/` shows the writes uncommitted (practitioner, akrogon checkout, 2026-11-25).
- issues/chart/fresh-leaf-base/forks/signposts.md section "## Needs", N1 (practitioner, read 2026-11-25): "the operator commits the uncommitted lesson writes … the fresh-leaf-base leaf must remove that lesson line in its own diff (lesson rule Retire), which needs the line on main. Consumer: fresh-leaf-base leaf handoff only."
- Draft readiness.yaml (under review): `inputs: []`.
- `src/turn.ts:blockDetail` and `src/readiness.ts:inputSchema` (practitioner, code read 2026-11-25): a `file` input with a `done` test blocks dispatch until satisfied, which is the existing mechanism for exactly this shape of dependency.

Smallest fix: declare one input in readiness.yaml of kind `file` for `learnings/history/2026-11-24-leaf-worktree-stale-base.md` (or the LESSONS.md line), holder the akrogon checkout, done naming the commit on main — mirroring N1's done text. Cost of not fixing: the leaf either stalls in review with a vacuous criterion or absorbs the operator's commit into its own diff, against N1.

## F2. The design orders the HEAD-refusal before the adoption rule, contradicting the binding "adopted as-is, as today" for branches with their own commits

The draft design section "## Leaf architecture" sequences the gate as: first, when the store path exists, `symbolic-ref` must be `refs/heads/<slug>` "Otherwise refuse (criterion 3)"; then, separately, the branch condition with "With commits of its own, adopt as today (criterion 4)". Read literally, a leftover whose branch carries its own commits but whose worktree HEAD is detached or on another branch is refused by the first rule before the adoption rule is ever consulted. The binding text carries the same contradiction: fork "## Taken" states the HEAD refusal unconditionally ("A store path whose HEAD is not refs/heads/<slug> … at first allocation: refuse loudly … Never remove it, never adopt it") and the adoption unconditionally ("A slug branch with its own commits: adopted as-is, as today"). Both cannot hold when both conditions are true.

This matters because it is exactly the direct route's growth-stop shape in its messier instances: a handoff whose worktree was left detached or switched, with the partial work committed on the slug branch. Today that handoff is adopted with no HEAD inspection whatsoever — `src/next.ts:ensureWorktree` validates only worktree-root and common-dir identity. If the leaf refuses it, valid work the decision says must keep working is refused; if it adopts it, criterion 3's unconditional phrasing fails. An implementer must guess which rule yields.

Evidence:
- `src/next.ts:ensureWorktree` (practitioner, code read 2026-11-25): the path-exists branch performs no HEAD check today, so "as today" includes detached or wrong-branch HEADs.
- skills/chart-issues/assets/direct-route.md section "Growth stop" (practitioner, read 2026-11-25): the handoff "relies on `ensureWorktree` adopting the worktree as-is"; nothing in the handoff constrains HEAD beyond the branch carrying the partial commit.
- Fork file sections "## Taken" plus its dated correction, and the draft design "## Leaf architecture" gate bullets (the texts under review, read 2026-11-25).
- My own probe record stands behind the premise that detached HEADs are real states, not hypotheticals (charting proofs G2, fork "## Charting proofs": ff-only on a detached HEAD moves HEAD and leaves the branch behind).

Smallest fix: scope the HEAD refusal inside the commit-free gate — i.e. the gate reads the branch condition first, and only when the branch is commit-free does the HEAD inspection decide between replace and refuse; a branch with its own commits takes today's adoption path untouched, whatever HEAD says. If the chart instead wants the refusal to win even then, the adoption bullet in the binding and criterion 4 must say so explicitly ("with its own commits, adopted unless the store path's HEAD is off the branch"), because that is a behavior change to the growth-stop contract, not a clarification. I recommend the first: the HEAD refusal exists to protect the recreation decision, which never runs for a branch with commits, and a commit-carrying branch means the content is protected regardless of HEAD (my rebuttal-B D2 argued the wider reachability framing; the narrower fix is enough to remove the contradiction).
