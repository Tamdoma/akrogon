# Rebuttal: leftover-worktree, slot B

Three disagreements with the merged notes.

## D1. The branch-reset difference should not stand as a tie: A's bound delete is better than `-B` under the gate

The merged notes list `-B` with a gated option (B,C,D) versus a bound branch delete then today's branch-missing path (A) as an open difference. I hold this against my own attributed position: A's variant is strictly better on two grounds, and the difference should close in its favor.

1. Crash convergence. If the process dies between the worktree removal and the creation, A's shape has already deleted the branch, so the next allocation finds no branch and takes today's plain branch-missing path — no gate re-evaluation needed, no options, the existing code path converges on its own. Under `-B`, the next allocation re-enters the gate, re-tests ancestry, and must pass the gated `-B` option again; the crash window is closed only by repeating the special path rather than by falling into the normal one.
2. Ref-move interlock. `git update-ref -d refs/heads/<slug> <sha>` fails if the branch moved after the ancestry test, so a branch that gained a commit in between is never silently overwritten; the error surfaces. A gated `-B` resets whatever the ref currently points at — the ancestry test and the reset are separate reads with no binding between them. The race is narrow (a direct-route door committing at the wrong moment) but A's shape makes it impossible rather than narrow.
3. Cost symmetry. The claimed cost of A's variant — one extra ref operation — matches what `-B` does internally anyway, and A's variant adds zero surface to `createSparseWorktree` (no new option, no caller discipline about when `-B` is permitted, which was C's own caveat). Fewest moving parts wins the tie even before the two grounds above.

Evidence: probes from my first notes (practitioner, /tmp/wt-probe, 2026-11-25, git 2.56.1): `git branch -d` succeeds on a commit-free branch because it is merged (P12), and `git worktree add -B` refuses while the branch is checked out elsewhere but succeeds after removal (P7b/P11) — both shapes are implementable, so the choice rests on the crash and interlock properties above, which are logical, not probed (low-to-medium confidence on the frequency of the race; high confidence on the crash-convergence asymmetry). `src/next.ts:createSparseWorktree` (practitioner, code read 2026-11-25): today `-b` is passed only when the branch is missing, so A's variant touches nothing outside the gate.

## D2. HEAD not on the slug branch: C's refuse is wrong; the A/D reachability rule is right, and for a reason the merged notes do not state

The merged notes list this as an open difference. It should close for A/D: a detached or wrong-branch HEAD whose commit is still reachable from the tracking ref holds zero protected content — every object in it is upstream history — so recreating is pure healing of a corrupt arrangement, and refusing (C) converts a self-healing case into an operator stall. The value test is the same one the whole gate already applies: recreation is safe exactly when nothing irreproducible is destroyed, and reachability of the HEAD commit is precisely the test for committed content. C's refusal protects nothing in the reachable case; it only punishes weirdness. In the unreachable case both positions agree the leftover adopts as-is, so the difference is exactly the nothing-to-lose states, where refusal is pure cost.

Evidence: logic from the gate's own premise plus `src/next.ts:ensureWorktree` (practitioner, code read 2026-11-25), whose path-exists branch today validates only worktree-root and common-dir identity — so "adopt as today" for the unreachable case preserves every committed object by construction, and the reachability exclusion needs no trust in the leftover's internal arrangement. Probe support from my first notes (practitioner, 2026-11-25): P8 showed the detached-HEAD case is real behavior, not hypothetical — git happily advances a detached HEAD independently of the branch, so these arrangements occur in practice. Confidence: high on the value argument; the reachability rule should also cover the equal-SHA case, which the merged notes already record through C's ancestry-test point.

## D3. C's `processesInside` addition to the live check protects nothing and should be dropped

The merged notes list the live check as an open difference: the `live` flag (A,D) or additionally `src/reconcile.ts:processesInside([path])` with a refusal naming the pids (C). The addition should be dropped. Inside the gate the tree is porcelain-clean, which means everything in it is either upstream content, `.env` (rewritten by `writeLeafEnv` on every allocation), or ignored rebuildable output. A foreign process squatting in such a tree — a forgotten operator shell — loses nothing when the tree is recreated; the worst case is a shell with an invalidated cwd, which is rudeness, not data loss. `reconcile`'s process veto, which C's addition mirrors, exists because reconcile removes trees whose contents it has not vetted; the gate is the opposite situation — the vetting (porcelain-clean) is exactly what has already happened. Adding the check imports a stall mode (a stale ssh session or a zombie shell pins the leaf for the operator) to protect value that the gate has already proven absent. The `live` flag covers the one case with real value at risk: a live seat of this leaf actively writing files that do not yet exist, and therefore cannot yet be porcelain-visible as committed-or-clean.

Evidence: probe (practitioner, /tmp/wt-probe2, 2026-11-25, git 2.56.1): `git worktree remove` on a clean tree with a foreign process cd'd inside exits 0 and deletes the tree — git itself does not treat occupancy as protection-worthy, so the check is not even aligning with git, only with reconcile. `src/reconcile.ts:removeWorktree` (practitioner, code read 2026-11-25): the veto there precedes removal of unvetted trees. `src/next.ts:ensureWorktree`/`allocate` (practitioner, code read 2026-11-25): the `live` flag already exists at the call site. Confidence: weakly held — the cost of C's addition is one cheap `/proc` scan and a rare stall, and the consistency argument for it is coherent; I disagree on the value calculus, not the facts.
