# Rebuttal: leftover-worktree (slot C)

1. **Branch reset via `git update-ref -d refs/heads/<slug> <sha>` (sections "Q1 clean leftover" and "Where slots differ", slot A) and `git branch -d` note (slot B)**
   - **Why I disagree:** `git update-ref -d` bypasses git's worktree-checkout check. When `refs/heads/<slug>` is checked out in another worktree (for example an operator checkout or a legacy path while `<store>/<slug>` is absent), `git update-ref -d refs/heads/<slug> <sha>` exits `0` and deletes the branch out from under that other worktree, leaving it broken on an unborn branch (`rev-parse HEAD` fails); the following `git worktree add -b <slug>` still fails with exit `128` (`already used by worktree`), so allocation fails while leaving the other worktree corrupted. Using `-B <slug>` on `git worktree add` checks every worktree first and refuses atomically without mutating any ref.
   - Separately, slot B's note that `git branch -d` succeeds on a commit-free branch is false whenever `trackingRef(repo)` is ahead of `repo.root`'s local `HEAD` — the routine state after `landPush` pushes directly to the remote without fast-forwarding `repo.root`. In that state `git branch -d` exits `1` (`not fully merged`) even though the branch is an ancestor of `trackingRef(repo)`.
   - **Evidence:**
     - `practitioner` — Temp-repo probes, git 2.56.1 (2026-11-25): with `slug` checked out in `other-wt`, `git update-ref -d refs/heads/slug <sha>` exited `0`, leaving `other-wt` with `symbolic-ref HEAD = refs/heads/slug` and `rev-parse HEAD` failing, and `git worktree add --no-checkout -b slug` then exited `128` (`'slug' is already used by worktree`); with `origin/main` ahead of `repo.root` `HEAD` and `slug` at `origin/main`, `git merge-base --is-ancestor refs/heads/slug refs/remotes/origin/main` exited `0` while `git branch -d slug` exited `1` (`the branch 'slug' is not fully merged`).
     - `practitioner` — `src/phase.ts:landPush` (inspected 2026-11-25): pushes `<head>:refs/heads/<default_branch>` directly to the remote without advancing `repo.root`'s checked-out branch.

2. **Handling a leftover worktree whose `HEAD` is not `refs/heads/<slug>` by reachability (sections "Q1 clean leftover" and "Where slots differ", slots A and D)**
   - **Why I disagree:** Judging a mismatched `HEAD` by reachability fails in both outcomes:
     - If `<path>` is checked out on another branch whose tip is reachable from `trackingRef(repo)`, removing `<path>` deletes a checkout of an unrelated branch instead of `<slug>`.
     - If `<path>` is on detached `HEAD` or another branch whose tip is not reachable from `trackingRef(repo)`, adopting `<path>` as today lets seats commit onto detached `HEAD` or the wrong branch while akrogon's merge and batch machinery reads `refs/heads/<slug>` and runs `reset --keep` on `<path>`.
   - Even direct-route growth-stop handoff requires `<path>` to be on `<slug>`, so there is no valid first-allocation case where `<store>/<slug>` has a different `HEAD`. Allocation should refuse loudly whenever `<path>`'s `HEAD` is not `refs/heads/<slug>`.
   - **Evidence:**
     - `practitioner` — `src/next.ts:mergeTurn`, `src/batch.ts:branchSha`, `src/batch.ts:move`, `src/phase.ts:restack` (inspected 2026-11-25): merge and restack look up `refs/heads/<slug>` and move `<worktree>` with `git -C <worktree> reset --keep <target>`, assuming `<worktree>` is checked out on `refs/heads/<slug>`.
     - `practitioner` — `skills/chart-issues/assets/direct-route.md` section "Growth stop" (inspected 2026-11-25): "the leaf slug equals the branch so the command's worktree setup adopts it".

3. **Guarding a live process inside the leftover using `allocate`'s `live` flag alone (sections "Pitfalls and what removes each" and "Where slots differ", slots A and D)**
   - **Why I disagree:** Under the first-allocation gate (`state.worktree === undefined`), a newly handed-off leaf has both `state.seat.A` and `state.seat.B` unset. `leafSeats` short-circuits and returns `{ A: undefined, B: undefined }`, so `allocate`'s `live` flag is always `false`. It cannot detect an old seat from a withdrawn attempt (whose `state.yaml` was deleted) or an operator shell parked in `<path>`. Checking `processesInside([path])` is required to actually stop removal under a live process.
   - **Evidence:**
     - `practitioner` — `src/next.ts:allocate` and `src/reconcile.ts:leafSeats` (inspected 2026-11-25): `live` is derived solely from `leafSeats`, which returns `{ A: undefined, B: undefined }` when neither seat is recorded in `state.seat`.
     - `practitioner` — `src/reconcile.ts:removeWorktree` and `src/reconcile.ts:processesInside` (inspected 2026-11-25): reconcile checks `/proc` cwd and open fds before `git worktree remove` specifically to catch processes unknown to leaf state.
