### Q1. Do we build recorded check evidence, change scheduling, or do both?

Scheduling chooses when a command runs. A record says which code and execution inputs its result covers. The seed requests both (`INTAKE.md:49-53`), but they solve different problems: the consumer’s 901-second success followed a rebase (`L/implementation/report.md:126-129`), while review already reused broad results (`L/review-B.md:18,117`). A record alone would not avoid required full-suite runs on new heads.

Research: operator-placed intake, read 2026-10-01, `issues/chart/check-reruns/INTAKE.md:47-55`, requests tool-produced results and changed scheduling. Live code, `src/config.ts:34-36` and `src/akrogon.ts:32-91`, has command maps but no runner. [GitHub Checks API](https://docs.github.com/en/rest/checks/runs), read 2026-10-01, attaches check runs to a commit with status and conclusion. [Nx caching](https://nx.dev/docs/concepts/how-caching-works), read 2026-10-01, accounts for source, configuration, dependency versions, runtime and arguments. These sources support recording execution identity, but do not make an arbitrary shell command safe to reuse by SHA alone.

- **1a (recommended): Deliver both scheduling changes and a tool-written runner.** Scheduling removes the blanket slow-suite runs. The runner records command, tested revision, outcome, duration and log so seats have a shared result to cite. The reason to do both is that each resolves a distinct part of the stated request. Scheduling can be independently verified and need not wait for the runner.
- **1b: Change scheduling only.** This is the smallest immediate reduction in slow runs, using existing `merge_checks`. Reports and logs remain the evidence interface. It leaves seed points 1-3 undelivered and must be described as that limited scope, not completion of #48.
- **1c: Build the runner only.** This standardizes evidence and may prevent identical-input reruns. It retains the initial/repair full-suite rules, so repairs and rebases can still pay the full cost.

Pitfalls: A tool-written file is execution provenance under the current trusted-agent model, not protection against an agent forging a writable file. Passing records must not cover dirty or changed inputs merely because HEAD matches. Record identity, invalidation, concurrent runs and cancellation need their own settled contract if 1a or 1c is chosen. Do not add remote caching, CI integration or a general dependency graph by implication. “Once per commit” and “always execute again at merge” conflict on a no-op rebase. This question chooses scope, not that later reuse rule. A post-push `phase merged` guard cannot enforce a pre-push guarantee (`skills/merge-issue/SKILL.md:43,47`; `src/phase.ts:215-250`).

### Q2. What must A run before review, after implementation and after repair?

A currently runs changed tests during implementation, then the full suite and every blocking check (`skills/implement-issue/SKILL.md:42,48`). The blanket repair sentence also calls for a full-suite rerun (`:52`), despite changed-stage reuse already being permitted (`skills/chart-issues/assets/standing-design.md:12`). We already have a place for expensive merge-only checks (`skills/init-akrogon/SKILL.md:20`; `docs/guide/setup.md:53-54`).

Research: operator-placed intake, read 2026-10-01, `INTAKE.md:52`, asks for affected tests plus fast blocking checks. The operator’s earlier smallest-proof decision remains relevant (`issues/chart/realistic-fix-bar/forks/test-bar.md:39-43`). Mike Wacker, a Google testing practitioner, recommends focused integration proof when it detects the same failure as a larger end-to-end test in [Just Say No to More End-to-End Tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html?hl=ja_JP), researched 2026-10-01 through the indexed primary article after the canonical page failed to fetch. [Nx affected tasks](https://nx.dev/docs/features/ci-features/affected), read 2026-10-01, grounds affected selection in changed files and the project graph. The recommendation keeps mandatory proof while removing the unconditional suite rule.

- **2a (recommended): Use the same proof obligation after implementation and repair.** A supplies passing proof for every leaf criterion, the affected tests including affected consumers, and every configured `checks` command. Reuse eligible unchanged evidence rather than re-executing it. Do not run `merge_checks` before review just because implementation or repair ended. Merge proves both configured maps on the final integrated code. This uses the existing configuration split and keeps sufficient proof before review without a blanket full-suite requirement.
- **2b: Run the full suite once before initial review, then affected tests and every `checks` command after repairs.** This reduces repair cost but retains one expensive run per leaf regardless of whether it proves anything beyond the criterion tests.
- **2c: Keep full-suite runs after implementation and every repair.** This keeps the current broad gate and its repeated cost. A runner can only reduce repeats when the tested inputs remain eligible for reuse.

Pitfalls: “Affected” includes consumers and shared inputs, not only tests next to an edited file (`standing-design.md:12`). A slow command left in `checks` still blocks before review under 2a. Agents cannot skip it by calling it slow. Placement in `merge_checks` is an explicit repo configuration choice, not automatic duration-based classification. A leaf’s whole-run criterion can still require expensive proof before review when no smaller test proves it. Failed checks and locked criteria remain blockers (`skills/check-issue/SKILL.md:49`), and existing contracts are not silently weakened. Post-merge health checks do not replace the selected pre-push gate. No numeric runtime threshold is proposed, consistent with `issues/chart/cross-leaf-proof/forks/proof-selection.md:28-29`.

### Q3. Which check criteria should the chart audit refuse?

“The whole framework is green” can make a bounded leaf responsible for unrelated failures. But a command spanning the repository can also catch a real integration defect caused by the leaf. Current charting already requires cheapest sufficient proof (`skills/chart-issues/assets/standing-design.md:10`) and permits a repo-wide command if it is first put in blocking `checks` (`skills/chart-issues/assets/shapes.md:132,170`). A blanket ban would discard necessary integration proof. Keeping the current rule unchanged can pull a slow merge-only suite back into every leaf pass.

Research: operator-placed intake, read 2026-10-01, `INTAKE.md:53`, proposes area criteria. The earlier operator decision requires each slow proof to name the property no smaller test proves (`issues/chart/cross-leaf-proof/forks/proof-selection.md:24-25`), already implemented in `standing-design.md:10` and `skills/plan-issue/SKILL.md:57`. Wacker’s [Google article](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html?hl=ja_JP) supports smaller sufficient integration tests. It supports a proof-adequacy judgment, not a ban based solely on command breadth.

- **3a (recommended): Refuse unbounded repo-health criteria and unnecessarily broad proof.** Each criterion names an outcome within the leaf’s ownership and a command/test that detects its failure. If repo-wide proof is necessary, the chart must name the specific integration or whole-run property that no smaller proof establishes, resolve any required prerequisite, and explicitly accept its before-review cost. Routine repo-health suites stay in `merge_checks`, outside leaf acceptance. Retain the existing command/test eligibility rules. This prevents accidental global ownership while preserving necessary integration checks.
- **3b: Refuse every repo-wide command in leaf criteria.** This is simpler, but can reject the only sufficient proof of a cross-component change. It also needs a precise definition of “repo-wide” to avoid judging coverage by command name.
- **3c: Keep the current eligibility audit only.** A repo-wide command in `checks` is acceptable without a stronger ownership/proof audit. This permits broad criteria to restore the same repeated cost despite the scheduling change.

Pitfalls: A justification must name an observable failure, not “safety” or “confidence.” Merely moving a command into `checks` does not make a global health claim leaf-owned. Conversely, the audit must not reject a fast, sufficient integration test just because it covers several areas. Judge scope and proof function, not exact wording or a required sentence template. Mirror changed rules in the guide (`docs/guide/phases.md:91`) and preserve required spine proof (`standing-design.md:11`; `shapes.md:172`).
