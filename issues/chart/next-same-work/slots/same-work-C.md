# Blind notes, slot C: same-work Q1

## 1. Pick

Pick (a): if every match for a bare name selects the identical leaf set, treat the matches as one target and start that set once. Otherwise refuse, list each match by kind and path, and start nothing.

Reason: `next` starts work, so a wrong silent choice is worse than a refusal. Under (a) no bare name that works today changes meaning, because today a name only works when it has exactly one match. Option (a) only converts some of today's refusals into starts, and only where every reading of the name starts the same leaves. Where the readings differ, the failure is loud and the user can pass a path. It also fixes the reported case exactly: in `framework`, issue `cache-proof` and leaf `cache-proof/cache-proof` both select the one leaf.

Cost: this reverses part of the 2026-10-08 lock in `next-named-targets/forks/names.md` Taken item 3. A name's meaning is no longer fixed as an issue grows. `next x` starts work while issue `x` holds only leaf `x`, then refuses after a second leaf is added to `x`. That break is accepted because it breaks into a refusal, never into different work. Other costs: the existing test "ambiguous name refuses an issue and its same-name leaf" flips to a dispatch test, and the path-workaround text in `docs/guide/parts.md` section "Folders, because this is where everyone trips" needs new wording.

## 2. Rejected options

Rejected (b), leaf slug always wins: it silently picks one reading when the readings start different work. If issue `x` holds leaves `x` and `y`, `next x` starts only leaf `x` and never tells an operator who meant the issue that `y` was skipped. If an owner `own` and an unrelated leaf `own` both exist, the owner becomes unreachable by name and the wrong work can start. Adding a leaf can also flip a name that works today from an owner set to a single leaf, silently. Leaf matches also include closed leaves, so a closed leaf could win over a live open owner. Its benefits are real: the slug is the unique leaf identifier used by `findLeaf` in `src/state.ts`, and the watch loop passes slugs meaning one leaf. But `next` also has an owner form that starts a set, and a silent partial start is the worst outcome on this surface.

Rejected (c), keep refusing and change the watch loop to pass paths: it keeps the 2026-10-08 stability benefit, but leaves #109 unfixed for operators. The same-name single-leaf layout is a normal documented pattern, and every such issue would need a full path forever. It also does not fit the intake scope, which puts the change in `src/next.ts` `resolveName` and `docs/guide/parts.md`. Fixing the watch loop under (c) is extra work on a second surface: the observe output in `skills/watch-issues/SKILL.md` carries `slug=` and no leaf path, so paths would have to be added there and in the Judge section. Path passing in the watch loop may still be worth doing separately (see U3), but it is not a substitute for fixing `next`.

## 4. Pitfalls

- P1. Comparing sets by size instead of by leaf identity would collapse two same-name single-leaf issues under different epics, each of size one but different leaves. Removed by comparing leaf path sets and requiring every match to be equal, with the existing two-epics refusal test kept.
- P2. Returning the union of equal matches would dispatch the same leaf twice. Removed by returning one match's set once, with a test that the dispatched slugs are exactly the single leaf.
- P3. A hidden leaf could fake equality: owner sets are built only from discoverable open leaves, so issue `x` with readable leaf `x` plus an unreadable second leaf looks equal to leaf `x` alone. Removed by refusing the collapse when the inventory reports an unreadable or unknown leaf under a matched owner, keeping the "unreadable leaf under a named issue reports its read error" behavior.
- P4. Growth changes a working name into a refusal, which can break operator habit and the watch loop for that name. Removed only in part: the refusal lists kind and path for each match and starts nothing (no Herdr call, per the still-binding lock), `docs/guide/parts.md` should say to pass the leaf or issue path once they differ, and a test should pin that adding a second leaf flips `next x` to a refusal with no dispatch.
- P5. The equal-set rule reaches further than #109: an epic whose only issue has the epic's name also collapses, which can start many leaves at once. Removed by the operator confirming the general rule (U1) and a test pinning whichever scope is chosen.
- P6. A closed leaf whose slug equals an open owner's name produces differing sets, so it still refuses under (a), even though a closed owner name does not block a new open owner. Removed only if the operator answers U2; until then (a) keeps today's refusal there.

## 5. Questions the fork does not ask

- U1. Should the collapse cover every equal-set case (epic and its only same-name issue, any ancestor and descendant selecting the same leaves), or only the issue and same-name leaf pair that #109 reports?
- U2. When an open owner matches a name, should a closed leaf with that slug count as a match at all, the way a closed owner already does not block an open owner?
- U3. Should the watch loop pass leaf paths instead of slugs anyway, so it keeps working for a same-name leaf inside a multi-leaf issue, where (a) still refuses?
- U4. Should `next` and `phase` share one name resolver, so the same bare name cannot mean a leaf in `phase` and refuse in `next`?
- U5. On a differing-set refusal, should the error show how many leaves each match selects, so the user sees why the name is ambiguous before choosing a path?
