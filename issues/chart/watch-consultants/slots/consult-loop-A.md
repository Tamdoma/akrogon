# consult-loop notes (A)

Evidence: `hc --skill` Talk, wait, and collect results (read 2026-11-21): "`reason: message`: the message arrives as your next input, possibly late; it is not output to fetch". `hc wait --help`: `--children any` ends on a child's news or a message to the caller. skills/chart-issues/assets/questions.md Blind peer exchange: return file + `done <X>: <path>` report, never `hc get` a child between waits. timer.ts `poll`: readiness needs idle/done, so dues queue while the watcher works. src/log.ts `readLog` parses every line with `logSchema`.

Q1 Pick: one consult per tick holding every leaf now in the notify class (S1 1a); the consultant decides which share a cause and returns a verdict per leaf; after its fix the watch re-observes, and leaves still failing on another cause get the next consult (one alive at a time, S5). Grouping is the consultant's model choice recorded in its return. Rejected: watch-side clustering by reason text (a text match standing in for a model choice; standing-design model-choice line). Cost: a big first consult when many leaves fail. Pitfall: a leaf whose cause the consultant misjudges — re-observe after the fix catches it.
Q2 Pick: a consult folder `<akrogon home>/watch/<repo>/consults/<UTC stamp>/` holding `brief.md` (watcher's literal address, each leaf's observe line, failure reason, paths to state/brief/design/review files and worktree, the S3 stop list, the locks) and `return.md` (per-leaf cause, action taken: commits and pushed SHA, recommended watch move, or the operator stop it hit); the consultant's first task points at the brief; every later question either way is a file in the folder plus an `hc send` naming it. Rejected: inline text in `hc send` (arrives possibly late as next input, not readable inside the wait); files under issues/ (Never). Pitfall: a late `done` arriving as the watcher's next prompt after the consult ended — the skill reports and ignores a consult message whose folder is closed.
Q3 Pick: the chart-door wait loop: `hc wait --children any --timeout 180 --json` repeated with no give-up; wake on `reason: message` from the consultant reads the folder; one nudge on a silent stop; a second silent stop, blocked, error or exit closes that consultant (`hc kill` + `hc rm`) and starts a fresh one on the same folder (no total cap). Timer is also a child: a wake from the timer is ignored and the wait repeats. Rejected: ending the turn (S4 reading; replies would race ticks). Pitfall: `hc get` on the consultant between waits swallows its news — forbidden as in questions.md.
Q4 Pick: consulting on a leaf ends when the consultant returns an operator stop (S3) or returns "no fix found" with its evidence; the watch then notifies once with the return path. A disagreement must name a concrete defect with evidence; the consultant answers it in the same consult; a defect neither resolves is a notify. A fix stands on evidence: checks green on the pushed tree and no S3 stop crossed. Rejected: numeric cap (operator said none). Cost: an unfixable failure could get re-consulted each tick — removed by: the watch does not re-consult a leaf whose failure record is unchanged since a consult that ended in a stop or no-fix (the record's failure reason and phase, the consult folder named).
Q5 Pick: drain as today, no timer change (removing over adding; each queued check is a cheap status+observe, and a fresh observe after a long consult is wanted anyway). Rejected: coalesce in timer.ts (touches merged, proven timer code). Cost: back-to-back checks after a long consult.
Q6 Pick: the consult folder is the record; the watch's reply names its path; no `issues/log.jsonl` rows. Rejected: notice per consult (noise).

Question the fork does not ask: whether the consultant may also answer the leaf's own seat when its failure names an operator decision that is not one of S3's stops (belongs to fix-and-resume).
