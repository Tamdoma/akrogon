## 1. Pick, reason and cost

D1 Pick (a), refined: separate installed runtime from the authoring checkout. Automatically prepare the exact successfully landed akrogon revision, then activate the coherent command/skills/plugin release at a safe boundary. Do not fast-forward a directory while anything is reading/executing it. Prefer an immutable prepared revision and one active-release pointer over mutating the live checkout in place. Root remains the registered authoring repo and issue store.

Reason: root cleanliness can no longer block delivery or let uncommitted development become production. Code, skill text, dependencies and plugin must be one revision. This closes the missing flow: landed fixes -> active runtime -> lower rework. Installing to another mutable checkout without activation coordination only relocates the race.

Cost: one deploy preparation/activation path, installed-link migration, explicit stable state home and authoring-root resolution, compatible-state checks, activation smoke proof, rollback boundary, and session/plugin adoption proof. This is not a one-line post-push hook. No per-leaf version scheduler unless the operator chooses concurrent incompatible versions.

D2 Timing recommendation: automatically stage after verified remote delivery and completed merge-state bookkeeping. Activate once no old invocation or active seat can read the old global skills or issue calls under its old contract. Prevent new dispatch during the switch. Finish current passes without killing them, then start fresh skill sessions under the new release. Idle sessions may retain old instructions, so idle alone is insufficient. Pausing dispatch is useful but is not a drain or a code-version guarantee.

For releases compatible with persisted leaf states, a completed-pass boundary can suffice after session refresh. For incompatible state/protocol changes, finish the affected leaves under the old release or explicitly migrate them before activation. That compatibility decision belongs in the release contract, not an implementer's guess. Avoid automatic hot switching in the middle of a proof or merge attempt.

D3 “Merged” cannot honestly guarantee immediate “in effect” while old work is deliberately allowed to finish. Keep successful source landing terminal. Distinguish landed SHA, pending deployment, and active SHA. Activation failure is a deployment failure, never a fake failed merge or a reason to replay an already successful push. Automatic preparation plus automatic safe activation removes the routine manual pull while preserving this distinction.

## 2. Rejected options

- O1 (b) Root fast-forward when clean, warn otherwise: reject as the permanent solution. Dirty authoring state is normal here, so this preserves exactly the blocked delivery path. It also makes installs depend on operator edits and changes global skills during active work. Never auto-stash, reset, merge or discard the root edits. A clean-root pull can be a separately authorized bootstrap action after reconciliation, not the architecture.
- O2 (c) Warn only: useful accompanying visibility, insufficient answer. The existing stale-checkout lesson already records a warning/check practice. A sensor without a delivery action leaves operator delay in the balancing loop. Report active and landed SHA rather than assuming a cached origin ref is fresh.
- O3 (d) Manual pull: reject. It explains today's 52-commit gap and means delivered throughput/learning fixes remain inactive until the operator notices. Reserve operator action for a genuinely unsafe release, recovery, and the one-time migration.
- O4 Literal (a), immediately fast-forward live deploy directory on every push: reject. Command startup and lazy imports, skill reads and plugin hooks can observe different files during update. Existing seats invoke the global command by name and receive skills by name. Separate directory ownership does not solve version coherence.
- O5 Pin every leaf to a separate release immediately: do not choose by default. It adds command-path, skill-path, plugin and state compatibility coordination per leaf, while shared state can still make old/new command writers incompatible. Consider only if measured drain delay is unacceptable and the operator explicitly wants that complexity.

## 4. Pitfalls and what removes each

- R1 Bad release becomes a host-wide regression. Remove: exact tested revision, dependencies prepared before exposure, smoke checks using the declared state/config without production mutations, previous release retained. Smoke success cannot guarantee defect-free behavior. A runtime defect stops affected dispatch and receives a bounded explicit rollback/recovery decision.
- R2 Rollback binary cannot read state the new release wrote. Remove: establish backward state compatibility or a concrete recovery plan before activation. A pointer switch alone is not rollback. Never roll back the remote source branch or erase lifecycle state to make old code run.
- R3 Mid-seat skill changes or old cached contract calling new command. Remove: coordinated no-new-dispatch window, completed passes, fresh sessions and verified state compatibility. If mixed old/new leaves must continue, that is the explicit O5 fork, not a silent assumption.
- R4 One component updates while another does not. Remove: one release includes command, dependencies, skills and plugin. Verify effective executable/skill paths and actual plugin subscriptions before resuming. A single pointer does not prove plugin caching behavior.
- R5 Root edits lost or implicitly shipped. Remove: human prerequisite owned by the operator: identify the owner and disposition of each dirty code/test/skill/doc change, decide commit/review versus retain/discard, and authorize exact link migration. Slot B must not reconcile or stash them. Mutable issue/lesson artifacts stay in the registered authoring store. Runtime separation can retain legitimate dev edits, but cannot assume they are unnecessary for current live sessions.
- R6 Deployment failure causes a second push or false merge failure. Remove: persist/derive pending landed SHA separately from active SHA, make activation repeat-safe, and resume deployment without repeating source delivery. Publish success only for the component that succeeded.
- R7 Empty deployment home breaks global config, locks, relative repos and authoring routing. Remove: one stable home and explicit authoring root, verified across manual command, leaf command and plugin invocation. Reuse existing home capability where sufficient. No copied drifting configs.
- R8 Deploy only on lifecycle push misses direct/manual updates, or activates untested later remote tip. Remove: common verified-revision recognition for every accepted delivery path, and define whether later external tips require fresh release checks. Never substitute latest origin for the tested SHA silently.
- R9 Automatic rollout waits forever behind continuous new work. Remove: activation-pending prevents new affected dispatch and drains to its defined boundary. Measure drain delay. Keep rollout waiting distinct from a stuck leaf. Do not kill long proofs merely to satisfy the wording “merged means in effect.”

## 5. Questions this fork does not yet ask

- Q2 Is a short host-wide dispatch drain acceptable, or must old/new leaf versions run concurrently? Recommend drain first. Exact boundary includes cached chart/peer sessions using changed skills, not only leaf busy flags.
- Q3 Where is the stable mutable home and which registered root owns akrogon authoring/lessons after migration? Existing defaults and skill root discovery make this a required contract decision.
- Q4 Who owns reconciliation of the dirty root edits, and which must be preserved for in-flight work? Operator prerequisite. Preparation can be reviewed before migration, but no safe live cutover can guess this.
- Q5 What is the rollback promise after state writes, and who stops/restarts work for an incompatible release? Requires a compatibility boundary, not an arbitrary timeout or silent automatic fallback.
- Q6 How does the running Herdr instance adopt plugin manifest changes, and can the effective subscriptions be verified without losing events? Primary local plugin/Herdr source or a permitted real probe is still needed before handoff. This read-only pass proves no reload API.
- Q7 Which revisions are eligible for automatic activation: every verified default-branch landing, only changes to runtime surfaces, and how are external operator pushes validated? Must include the direct route without reopening its settled merge rules.

Recommendation: separate authoring from runtime, automatically prepare landed revisions, and activate one coherent release at a verified safe boundary. The root fast-forward/warn path leaves the original failure intact.
