# deploy-path final-shape check, slot C

Scope: 1c as taken. Defects and missing binding decisions an implementer hits at the push sites. Root is at origin/main today (git status -sb: `main...origin/main`, HEAD f3199df), so citations are HEAD.

C1. Direct route has no command call at its push. skills/chart-issues/SKILL.md:110 step 5.5 is a raw `git push <remote> <sha>:refs/heads/<default_branch>` run by the door; the only command-owned push is batchPush (src/phase.ts:478-480), plus `akrogon sync` (src/sync.ts:136). The Taken says "lifecycle merge and direct route" but gives the direct route nothing to run. Binding needed: either (i) a new verb the door runs right after step 5.5, or (ii) the skill step itself runs the pull. `pull` is taken (src/akrogon.ts:93 pulls GitHub seeds), so (i) needs a name. SKILL.md:115 "a failed local update is reported" already exists and must be the line the new step hangs on. Recommend (i): one implementation, one error text, and `sync` can call it too.

C2. Root ahead of origin is routine and makes `--ff-only` refuse at every landing until the operator acts. `commitMove` writes state files only (src/phase.ts:159-161), so akrogon's own issue moves sit uncommitted in the root until the operator commits (HEAD "add issues", author Ivan) or `akrogon sync` commits and pushes them (src/sync.ts:117-136). Between that commit and its push the root is ahead; the next leaf landing makes it diverged, and `git pull --ff-only` prints "Not possible to fast-forward". Decision 3 reports it, but the same refusal then repeats on every landing and the runtime stays stale, which is the 52-commit lag again by another route. Binding needed: the refusal line names the remedy (`akrogon sync`, which already rebases with autostash at sync.ts:122) and whether the command may `--rebase` when the root is ahead by committed commits only. The foreclosure covers stash, reset and merge of root edits, not rebase of committed root commits, so it is undecided. Recommend report-plus-remedy, no auto-rebase: a rebase conflict inside an unattended merge seat is worse than a lag line.

C3. Root HEAD may not be on the default branch. `git pull --ff-only` with no refspec acts on the checked-out branch and fails with "no tracking information" when detached or on a branch without upstream; the solo path can even put the root on a leaf branch (`state.worktree ?? repo.root`, src/phase.ts:467). Binding: run `git pull --ff-only <remote> <default_branch>` explicitly, and when `git symbolic-ref --short HEAD` is not the default branch, skip and report instead of pulling.

C4. Position and error shape inside batchPush. The pull must run after the member moves and the holder transition (src/phase.ts:482-486), because `completeOwner` moves folders under root issues/ and anything thrown before it becomes a merge failure. It must return a printed result, never throw: a throw after the push lands as `MoveCommittedError` "move committed, follow-up failed" (src/phase.ts:160-170), which contradicts decision 3 and would alarm the seat. Binding: pull outcome is a printed line (`deployed <sha>` or the refusal with lag), never an exception.

C5. "Only when the landed repo is akrogon itself" needs a comparison the code does not have. `toolRoot` is used nowhere outside config.ts and install.ts. Binding: `realpathSync(repo.root) === realpathSync(toolRoot)` (toolRoot = `resolve(import.meta.dir, '..')`, config.ts:170), with a test that the symlinked `~/.local/bin/akrogon` entry resolves `import.meta.dir` to the real tree under bun; if it does not, resolve the bin link with realpath instead.

C6. Lockfile change detection. File is `bun.lock` (ls), not bun.lockb. Capture `git rev-parse HEAD` before and after the pull and run `git diff --name-only <before> <after> -- package.json bun.lock`; install only on a non-empty list. A pull that moved HEAD but whose install fails leaves the root on new source with old deps; the report must say so (`pulled <sha>, install failed`), and the next landing reruns the install when the diff since the last successful install includes the lockfile. Binding: what "last successful install" is keyed on. Simplest: always run `bun install --frozen-lockfile` when the lockfile differs between the pre-pull sha and HEAD, and otherwise skip, so a failed install is retried only when the operator fixes it or the lockfile changes again. Say that in the fork.

C7. The `next` warning fires only when the akrogon repo is in the pass. `next` fetches per repo (src/next.ts:882, 1028); with cwd=framework and no `--all` nothing fetches akrogon. The plugin runs `next --all` (plugins.json snapshot), so herdr events cover it. State in the fork that the line is printed from the akrogon repo's pass.

C8. Landings that bypass batchPush's success branch. By-ancestry completion (src/next.ts:901-905) finishes a holder whose push landed before the process died, so no pull ran. `akrogon sync` pushes root HEAD (sync.ts:136) and needs no pull. Binding: either the `next` warning is the only cover for the ancestry case, or `next` also runs the same ff-only pull on the akrogon root when it finds it behind after its fetch. Recommend the latter: same command, same report, no new model, and it also covers a landing pushed from another machine.

No defect found in: decision 2 ordering of install after pull, decision 3 "never fails the merge" (compatible with C4), mixed-version acceptance (Off route), plugin snapshot as operator relink step.
