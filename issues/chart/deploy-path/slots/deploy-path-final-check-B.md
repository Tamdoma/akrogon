# Slot B final-shape check

Checked the Taken section and CHART.md against HEAD f3199df. Only concrete gaps below. The operator's 1c decision is respected. No separate-runtime proposal or reopening of accepted mixed-version/plugin costs.

- F1 Direct landing has no command hook to perform the promised update. Taken:22 says “the command” updates after lifecycle and direct pushes. Lifecycle has batchPush (src/phase.ts:443-488), but direct landing is a raw `git push` issued by the chart door (skills/chart-issues/SKILL.md:110), followed by close/broadcast/cleanup (:111-115). Editing batchPush cannot cover this route. The contract must own the direct-route skill step and name the callable update operation, including its registered-root lookup and non-failing result, or explicitly move direct pushing through a command. This is required for the stated two-route outcome, not a new feature.

- F2 Dependency-install failure leaves the root current but dependencies old, with no recovery condition. Taken:23 installs only when a pull changes package.json/bun.lock, while :24 reports installation failure and keeps the merge successful. After a failed install, the next successful pull can be a no-op, so no changed-file trigger remains. The behind warning (:25) also goes quiet once the root SHA is current. Decide and record how an incomplete install remains visible and is retried or repaired without replaying the push. Also define update sequencing relative to lifecycle completion and mergeWake: src/phase.ts:483-487 commits merge state after push, and src/akrogon.ts:81-82 invokes mergeWake in finally. A deployment/install error must not abort that bookkeeping or surface as a failed merge through subsequent wake handling. Existing setup execution uses an install lock (src/config.ts:260), which the update path must respect rather than race.

- F3 The promised pull target is not defined independently of checkout/upstream state. Taken:22 gives plain `git pull --ff-only`; :25 hardcodes origin, but pushes use configured repo.remote/default_branch (src/phase.ts:478-480; src/config.ts:40-41). Current root is main tracking origin/main, so the current case works. A registered root on another branch, detached HEAD, or changed upstream can refuse or fast-forward the wrong live branch. Bind the operation to the registered root's configured default-branch target, define refusal for a mismatched root branch/upstream, and use the same configured tracking ref for lag. No automatic checkout/reset/stash. “Akrogon itself” also needs an identity rule based on the installed/registered authoring root, not a guessed repository key. These conditions preserve 1c without silently changing where it pulls.

- F4 The update contract omits installed links for newly added or removed skills. install.ts enumerates skill directories and creates each harness's symlink once (:12-22,46-49), and prunes dead links only during install (:24-32). Existing linked skills receive edits through a pull, but a new skill directory does not acquire an installed link, and removed directories leave dangling links. Taken:22-23 only pull and install dependencies. Bind whether the update also reconciles owned skill links, with existing conflict refusals preserved, or explicitly exclude skill additions/removals from “landed work takes effect for every seat” (CHART.md:4). This is distinct from the already excluded Herdr manifest snapshot drift (CHART.md:16), which I am not reopening.
