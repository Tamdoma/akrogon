# deploy-path rebuttal, slot C (disagreements only)

R1. D2, I withdraw in-place ff and concede to release dir + pointer, with one correction. `src/akrogon.ts` on origin/main lazy-imports every subcommand (`await import('./phase')` :61, `./next` :62,90, `./pull` :95, `./sync` :105, `./park` :111, `./hold` :115), so B F7's mixed-file read during an in-place ff is real, not hypothetical. Correction to A's refinement: use `git worktree add <releases>/<sha> <sha>` from one deploy clone, not a fresh clone per SHA, and keep exactly two releases (current, previous). A clone per SHA plus unbounded releases adds a pruning job that nobody asked for.

R2. Contract surface "stable home must stay at the authoring root via AKROGON_HOME" (B): disagree with the location, not the need. Evidence that the need is bigger than noted: `globalHome()` defaults to `toolRoot` (config.ts:171-172) and holds `config.yaml` (tracked in git, `git ls-files config.yaml`), `paused.yaml` (gitignored, pause.ts:19), `held.yaml` (origin/main hold.ts:30) and the global `.lock` (pause.ts:49, park.ts:51). With per-SHA release dirs and the default home, every release swap drops pause and hold state and changes the lock path, so two processes on different releases do not exclude each other. Pointing AKROGON_HOME at the authoring root re-couples runtime state to the dev checkout, which is what (a) separates, and the variable must then be set in three environments: operator shell, seat panes, and herdr hook commands whose cwd is the plugin dir (LESSONS.md:19, 2026-09-28). Pick instead: default `globalHome()` to a fixed path outside any checkout (`~/.config/akrogon` or `AKROGON_HOME`), and `install` moves `config.yaml` there once. One default, zero env vars, survives release swaps. `config.yaml` stops being a tracked file in the repo; it is operator config, not source.

R3. "Plugin adoption after relink unproven" understates it. `~/.config/herdr/plugins.json` is a snapshot of the manifest taken at link time: it records `plugin_root` and copies `startup`/`events`. It already disagrees with the checkout: plugins.json startup has `next.sh --all`, plugin/herdr-plugin.toml has `next.sh --resume`. So a pointer swap updates the scripts but never the manifest, and any landing that changes `herdr-plugin.toml` is silently not deployed. The deploy step must run `herdr plugin unlink akrogon` then `herdr plugin link <current>/plugin` whenever the manifest differs between previous and current release, and the relink probe (B Q6) must check that herdr tolerates `plugin_root` through a symlink without realpath-pinning it to a SHA dir. Evidence: primary, 2026-10-10, plugins.json lines 7-8 and 13-21 vs plugin/herdr-plugin.toml.

R4. D1 drain boundary (B): disagree. Each `akrogon` call is one short process (`#!/usr/bin/env bun`, akrogon.ts:1); no long-lived daemon reads state across a swap. origin/main's state.ts adds only optional fields (`started`, `recorded`, `excluded`) and drops `solo` from the saved record, so both releases parse the same files. Draining needs a "no new dispatch" flag plus a wait for every busy seat, which is new state plus a stall path, for a hazard the additive-optional rule already removes. Keep the rule, skip the drain.

R5. "Deploy the exact tested SHA, not latest origin silently" (B F6): disagree with "never latest origin". The runtime invariant should be `current == origin/<default_branch>` after every fetch. The tested SHA is that tip at push time, and an operator push is a landing by design (red-main-hold clears on operator push). Deploying a tested SHA while origin has moved on leaves the runtime one landing behind, which is the lag this fork exists to end. Catch-up on `next` (my Q-a) must therefore deploy the fetched tip, not a recorded SHA.
