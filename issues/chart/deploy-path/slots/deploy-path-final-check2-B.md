# Slot B focused check 2: concrete defects

- F1 The existing fetch is not a reliable deployment entry point (shape2:4,9). mergeWake calls mergePass, not nextCommand (src/next.ts:1287-1296). mergeTurn returns before fetching when no merge holder remains (:1003-1006), and also when an applied holder already exists (:1007-1017). Thus the final lifecycle landing, a direct landing with no lifecycle queue, or an external landing on an idle repo need not reach the proposed hook. Define a root-update pass independent of merge-holder existence and cover mergeWake as well as nextCommand. Changing only the code after the existing fetch does not deliver the claimed coverage.

- F2 The claimed plugin trigger is incorrect (shape2:10). Tracked plugin startup runs next --resume, events run next without arguments (plugin/herdr-plugin.toml:10-27; plugin/next.sh:3). Pane hooks select their owning repo and add only that repo to touched (src/next.ts:1556), then run mergePass only for touched repos (:1559-1561). A framework seat event does not guarantee an akrogon pass. Even --all is cwd-sensitive (:1466-1476). Bind the actual invocation path that guarantees checking the installed root. Leave the accepted plugin snapshot issue off route, but do not rely on a nonexistent next --all event contract.

- F3 Install/link failure recovery remains missing (shape2:5). If pull moves HEAD and bun install or link reconciliation fails, HEAD is already current. The next next pass performs no pull because the behind predicate is false, so step 2 never retries. “Retries naturally on the next pull” means waiting for another remote commit, possibly indefinitely. The same occurs after a process dies between pull and setup. Define a pending setup condition that survives HEAD advancement and a retry/remedy when there is no newer commit. Report deployment success only after dependency installation and skill-link reconciliation complete. This fixes the existing incomplete-deployment case without replaying any push.
