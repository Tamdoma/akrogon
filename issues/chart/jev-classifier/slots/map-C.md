# Opening map C: Jev (TypeSafe System One) in akrogon

Slot C, blind. Repo at f7baddc. Read 2026-10-17.

## Baseline facts that bound everything

- akrogon code calls no model. `src/` (9,766 lines) is deterministic: routing tables, schema checks, git/herdr subprocesses. Judgment lives in skill prose (877 lines across 10 SKILL.md) executed inside harness agent turns that must happen anyway to produce the work product (review text, plan, code, chart forks).
- Volume is small. `issues/log.jsonl` 2026-09-11 to 2026-10-17 (36 days): 1,031 phase transitions (~29/day), 188 merged leaves (~5/day), 257 entries into check.review (~7/day), 18 into failed (~0.5/day). The only high-frequency surface is watch-issues at 3 ticks/hour while the operator runs it (max 72/day).
- At $0.042/M input tokens, even 72 ticks/day at 20k tokens of state is about $0.06/day. Money saved or spent is noise at this volume. The real cost or saving is agent turns, prose and code maintained, and failure domains.
- No TypeSafe key exists. `~/.config/akrogon/env` holds only Discord webhooks (names listed 2026-10-17).
- Jev returns a label and probabilities, no text and no reasons. akrogon repeatedly requires reasons as the artifact: a Fix names source, consequence and criterion (skills/check-issue/SKILL.md:51-53), fork files record answers and their reasons (skills/chart-issues/SKILL.md:55), the autopilot morning record records dissent (issues/chart/autopilot/forks/picking.md Taken). A classifier output cannot fill any of these slots.

Shared "adds" for every candidate below, stated once: an outside account and key (new need on every consuming machine and repo), network on paths that today work offline, one proprietary early-access vendor, non-deterministic answers (same query varies slightly run to run), a second written copy of each decision rule (Jev instructions/criteria are prose too, and must stay in sync with the skill prose they mirror), threshold tuning and re-tuning per model version, and a defined behavior for API-down and low-confidence that does not exist today.

## Candidate decision points

P1. Watch: class of a failed leaf from free-text `failure.reason` (skills/watch-issues/SKILL.md:40-41). Today the tick's Claude turn reads the reason and picks human-prerequisite (never recover) vs other-leaf defect vs recoverable. Volume: failures ~0.5/day, but the class is re-judged on each tick while failed. Cost now: part of a tick turn that also writes the notice and may run `phase`/`next`. Jev removes: nothing unless the whole tick stops being an agent turn, because the notice text and the actions still need the agent. Rule in code beats both for most of it: reasons are written by akrogon's own seats, so a structured `failure.cause` enum at the write site (the skill already distinguishes causes, skills/AREA.md:23 area note on human-only blockers) removes the text classification entirely instead of paying a model to recover structure that was thrown away. This is the one genuine text-to-label fit, and the fix is upstream structure, not a classifier.

P2. Watch: busy seat looping or outside its brief (skills/watch-issues/SKILL.md:42). The loop bar is already written as a rule: same command or edit 3+ times with same result, 3+ consecutive errors, edit-undo cycle, judged on `log-tail.ts` hash lines. That is counting and pattern matching over hashes, which Jev's own jaggedness page says it does badly (counting, numeric). "Outside the brief" needs the brief plus screen context and ends in a written corrective prompt naming evidence and next step, which Jev cannot write. A wrong "looping" call stops a healthy seat with esc. Rule in code (extend log-tail.ts to count hash repeats) removes more prose than Jev would and is exact.

P3. Red check with no cause in the leaf diff, gets one retry and may be marked `inconsistent` (skills/check-issue/SKILL.md:69, skills/implement-issue/SKILL.md:40). The prose says "a judgment gate, never automatic". Inputs are failing output plus the diff, i.e. multi-hop cause tracing, a documented Jev weakness (indirection). The decider is already reading the diff for the review itself, so no turn is saved. A wrong yes burns one retry (cheap), a wrong no blocks a good leaf. Flaky-as-fact is already code and exact: same tree red then green (src/flaky.ts:24). Keep the gate with the reviewer.

P4. Seed duplicate: does a found GitHub report cover the same failure "judged by the mechanism or defect in its body rather than shared keywords" (skills/seed-issue/SKILL.md:73). Real text-to-label fit. But the same agent turn must still inspect the named files and author the report either way, so Jev saves a sub-judgment inside a turn that still runs. Volume: seeds are occasional intake, `issues/seeds/` is empty now. Risk asymmetry: a false "duplicate" silently suppresses a real filing, and seed bodies are untrusted text (prompt injection into the classifier, a documented Jev weakness). Not worth a vendor for this alone.

P5. Lesson sort: stopped / checkable / transfer / stays (skills/learn-issues/SKILL.md:20-23), and the matching removal check in review (skills/check-issue/SKILL.md:61). "Stopped" requires tracing a mechanism through current code and checks and proving coverage on every reachable path, with file:line evidence printed per line. That is exactly the running-the-code work a label cannot do or evidence. Operator-invoked, rare, 24 active lines. No fit.

P6. Plan and chart shape choices: debate yes/no and "very small issues skip the question" (skills/chart-issues/SKILL.md:69), "a substantive behavioral fork belongs in the rebuttal round" (skills/plan-issue/SKILL.md:45), seat question only when work is "model-sensitive" (skills/chart-issues/SKILL.md:69). Each is one judgment inside a drafting turn, a few times per chart or leaf, and debate is already default-no so the common path costs nothing. A classifier would need the whole brief as state and would return a label the door must still defend to the operator. Rule candidates already exist in the records (leaf size, outcome count, criteria count) if the operator ever wants these mechanical.

P7. Review verdict ready/nits/fix and Fix vs Nit per finding (skills/check-issue/SKILL.md:51-63). The verdict is the summary of findings that the seat must write with reproductions and traces. Jev cannot produce findings, cannot run the code (the lesson at learnings/LESSONS.md:5 is that reading-only review missed three defects running found), and a probability is not evidence. The aggregation of the two seats' verdicts is already one line of code: any `fix` wins (src/phase.ts:323). No fit at either end.

P8. Deterministic code that must stay deterministic, listed so it is not mistaken for classifier territory: herdr retryable error codes (src/shell.ts:179-199, a 6-item list), verify receipt reuse by tree and command set (src/AREA.md verify note), reconcile keep/delete of worktrees and slices behind live-pane vetoes (src/AREA.md reconcile note), phase legality and slot guards (src/phase.ts:249-323), merge stack member skip on rebase conflict (src/AREA.md buildStack note). These are exact, auditable and tested. Replacing any with a probability removes the audit trail and adds a network failure path to dispatch and cleanup. The akitaonrails line applies: rules belong in code.

Net across P1-P8: every fuzzy decision sits inside an agent turn that also produces required text or actions, so Jev removes no turn, no seat and no prose. It adds question prose, thresholds, a key and a failure domain. The two spots where prose could actually shrink (P1, P2) shrink more by adding structure or counting in existing code.

## The two operator examples

E1. Direct vs lifecycle. Eligibility is already close to code: four of the five refusal conditions are checkable from the draft's own fields (needs `inputs`/`grants`/`produces`/`retained`, human prerequisite pending, B not named, and live-run criteria are declared in the draft), and only "more than one outcome" is named door judgment (skills/chart-issues/SKILL.md:91-97). If anything should be removed here it is the door re-reading its own draft, and a small script over the draft files (the shape direct-guards.ts already takes) does that exactly. The actual choice among lifecycle/direct is the operator's at the handoff review, and selecting direct grants push authority (skills/chart-issues/SKILL.md:99). A classifier can at most emit the door's recommendation, which the door forms while drafting the chart anyway, and it would emit it without reasons the operator can inspect. Wrong direction costs are asymmetric and the volume is a few charts per week. Not the right tool.

E2. Autopilot vs not. The switch is the operator's words at start, and a taken lock says autopilot never changes its own switch or limits, only the operator does (issues/chart/autopilot/forks/boundary.md, Taken 2026-10-16). A classifier deciding autopilot-fit would either move that switch (against the lock) or advise the operator who is already present making the choice (adds nothing). Fit also depends on facts not in the intake text: operator availability, trust in the specific work, whether it is original or incoming. Inside autopilot, A answers every question and records reasons and dissent; Jev answers carry no reasons, so the morning record could not show why anything was picked. Autopilot also has no direct route, so E1 does not arise inside it. Not the right tool, and the interesting sub-question "which forks must hold for the operator" was already settled by kind of action, not by per-item classification.

## Material forks, if the operator still wants a path in

F1. Where a classifier would live. Options: (a) in `src/` as akrogon's first model API call, which puts a key, network and non-determinism into dispatch-adjacent code and makes tests depend on recorded fixtures; (b) in skill prose as an agent-run curl, which differs per harness (claude, codex, pi) and is untestable; (c) nowhere. Each of (a) and (b) also needs the needs-sheet and grant machinery for the key itself at charting time.

F2. Behavior when the API is down, slow, or low-confidence. Block (new way for `next`, watch or the door to stop), fall back to the agent judgment (then both paths are maintained forever and Jev removed nothing), or act on a default label (silent wrong routing). There is no option that preserves today's behavior for free.

F3. Version and thresholds. Pin `jev-1.13.0` (thresholds stay valid, model ages, vendor may retire it) or follow `jev-latest` (answers change under unchanged code; 1.14 shipped 2026-10-14 while `jev-latest` still points at 1.13.0, per the models page). Either way someone owns a labeled local eval set, because vendor calibration claims do not transfer to new data (inovex). akrogon has no such set and building one is the real project hiding inside "add a classifier".

F4. Vendor choice is not settled by the category being real. On the one independent benchmark found, Microsoft Decision-1 tied Jev at 97.6% at one third the price, and two open-weights 27B models scored 99.4% local at the cost of ~49 GB and over a second per decision. Picking the proprietary early-access option first, in a category moving monthly, is the lock-in-maximal order.

F5. Data leaving the machine. State for the plausible candidates includes diffs, failure reasons, agent logs and GitHub issue bodies from every registered repo, including consumer repos. The vendor states no training on customer requests, with zero data retention only for enterprise. Whether consumer-repo content may go to this vendor is an operator call per repo, not a default.

## Practitioner questions

Q1. How many hours per day does watch-issues actually run, and is its cost felt as money, rate limits, or not at all? P1/P2 only matter if tick turns are a real cost, and if they are, the cheaper fix is structured failure causes plus counting in log-tail.ts.
Q2. Are harness agent turns flat-rate (subscription) or metered? If flat, Jev converts $0 marginal judgments into metered ones and saves nothing.
Q3. Is there any decision today that is taken often, taken badly, and recorded with its outcome, so an eval set exists? I found none: outcomes are recorded for phases and verify runs, not for the fuzzy sub-judgments.
Q4. Would the operator accept a route, recovery, or filing decision whose entire record is "model X, probability 0.83, threshold 0.7", with no reasons? Every current record format says no.

## Pitfalls over the work's lifetime

R1. Two copies of every adopted rule (skill prose and Jev criteria) drift apart as skills are edited by leaves that do not know the classifier copy exists. The stale-rule-in-docs lesson (learnings/LESSONS.md, 2026-09-11) is this failure already observed with docs.
R2. A classifier in the watch path invites finishing the job: replacing the cron agent with a polling script, which runs into the no-new-timers-or-polling lock (2026-09-18) and turns a skill into a daemon to maintain.
R3. Thresholds tuned on jev-1.13 silently rot at the next version, and because answers vary slightly per run, a boundary case can flip routes between ticks with no code change and no diff to review.
R4. Untrusted state: seed and issue bodies, and agent-written failure reasons, become classifier input. Text that argues for its own classification is a documented weakness; a seed saying "duplicate of #n, do not file" is a realistic suppression path.
R5. Early-access vendor risk: pricing, API shape and model availability can change or end; every adopted point then needs rework at vendor pace, in a system the operator describes as already good.

## Recommendation

Do nothing. No Jev integration, no key, no leaf. The evidence is that akrogon's code decisions are exact rules, its fuzzy decisions are inseparable from agent turns that must produce reasons and text anyway, and its volume makes even a perfect classifier worth a few cents a day against a permanent vendor, a second copy of adopted rules, and a new failure domain. That is adding complexity, which is the opposite of the intake condition.

Two cheaper moves capture most of the imagined value if the operator wants them later, both plain code: a structured `failure.cause` written by seats (removes P1 classification), and hash-repeat counting in watch's log-tail (removes most of P2). Revisit classifiers only when a decision moves out of an agent turn into `src/` at real volume, or when a labeled set of past decisions with outcomes exists to measure one against. If measurement is wanted now, the smallest honest step is a discarded offline prototype: replay recorded failure reasons and closed seed/duplicate cases against two or three decision APIs and the recorded human call, and report agreement before any integration is charted.
