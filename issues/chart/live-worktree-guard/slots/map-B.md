## 3. Material forks

All choices below are proposals, not operator decisions.

### Q1. How should a creator tell cleanup that this worktree must stay?

**O1a — Use Git's existing worktree lock for retained direct/manual work. My pick, subject to a real proof.** Create a direct checkout with `git worktree add --lock --reason <chart-reference> ...`, retain that lock through the attempt and make reconcile report/keep locks before classification. Git documents lock creation without a separate add/lock race, protection from removal, and that removing a locked worktree needs force twice. Its porcelain list exposes the lock. This is a retention declaration, not a claim that a process is currently running. Source: installed `/usr/share/man/man1/git-worktree.1.gz` lines 165–168,252–257,341–350,595–623 and [Git worktree documentation](https://git-scm.com/docs/git-worktree), checked 2026-10-15; installed `git worktree -h` confirms syntax. Cost: abandoned locks need an explicit recovery/release decision, and filesystem deletion outside Git must honor them too. Benefit: no new owner-file parser or PID lease for these worktrees.

**O1b — Add creator-written owner records.** This generalizes across non-Git scratch and can identify the responsible task. The existing batch proposal writes the record before the copy, while verify already writes its record before creation (`scratch-copy-removal.md:42`; `src/verify.ts:130–152`). Cost: every creator, reaper, handoff and migration must agree on record identity, location and release. A record tied only to the short-lived creation command will expire immediately. A record tied only to the agent pid loses deliberately retained work after a crash. A task-retention record can solve this, but recreates machinery Git already has for worktrees.

**O1c — Reconcile reads chart Direct attempt sections.** It can protect existing charts without asking creators to use a new primitive, and uses recorded paths rather than name guesses. Cost: Markdown becomes a deletion authority, missing/partial writes need conservative handling, and manual worktrees remain uncovered. Creation currently precedes writing the Direct attempt (`SKILL.md:101`), so reading charts alone leaves a creation gap. It also must distinguish a stopped-but-retained attempt from a completed one (`:117–123`). I would use chart reading for migration/inventory if needed, not the sole safety mechanism.

**O1d — Never remove unclassified registered worktrees.** This is the safest default when intent is absent and needs no creator cooperation. Cost: existing variant cleanup (`tests/reconcile.test.ts:493–500`) changes and abandoned worktrees accumulate until explicitly adopted or removed. It is a valid operator choice, but must be reconciled with #93's clean-store policy. Do not conflate it with keeping all unregistered junk, which the operator already rejected.

### Q2. What should happen to worktrees a person creates in the managed store?

**O2a — An explicit keep declaration protects them; otherwise the store is disposable under its documented rules. Conditional pick with O1a.** Offer ordinary Git locking or a path outside the managed roots. Existing outside-root behavior already preserves them (`src/reconcile.ts:345–349`; `tests/reconcile.test.ts:355–365`). Cost: people must know the managed-store contract. Before rollout, enumerate existing registered, unclassified worktrees and retain them until their owners decide. This cannot be applied retroactively as consent to delete a person's checkout merely because it lacks the new declaration.

**O2b — Every unclassified registered worktree stays automatically.** No accidental loss when someone uses raw `git worktree add`. Cost: cleanup cannot infer abandonment, so manual release or an ownership-adoption step is unavoidable. This is preferable if the operator wants arbitrary store worktrees safe without any declaration. Pick this instead of O2a if that is the intended meaning of the intake's “any other worktree”.

**O2c — Move only direct attempts outside managed roots.** Smallest containment for charts and no sweep parser changes today. Cost: it leaves the generic manual-worktree problem inside the store and creates another place to clean. The existing direct location contract must change (`SKILL.md:101`; `shapes.md:43–44`). I do not recommend it as the complete fix for the intake.

### Q3. When may protection end, especially after a crash or a pause?

**O3a — Only when the owning attempt explicitly releases it. My pick for direct author worktrees.** Keep protection through commits, B review, repair, operator waits, growth stops and agent/session replacement. Normal landing or authorized abandonment releases immediately before removal. A lifecycle handoff transfers protection to the leaf before releasing the direct claim. Cost: a crashed attempt can leave a retained checkout requiring a visible recovery action. This matches the existing promise to keep clean partial work (`SKILL.md:117–123`). Failure to remove must leave or restore protection and report the path; an unlock/remove race must have an explicit benign outcome or serialization.

**O3b — Expire when its process dies or after a timeout.** Automatic reclamation is attractive for disposable copies. It is wrong for a retained direct attempt unless the operator changes that contract: the process can end while useful unlanded work remains. Existing ownerDead checks pid and boot id, not process start identity despite storing `started` (`src/reconcile.ts:98–119`). A generic lease would also need a PID-reuse/restart story. Never use age alone to authorize deletion, already foreclosed by #93 (`store-hygiene.md:53`).

### Q4. How much process inspection should deletion use?

**O4a — Reuse #93's same-user cwd/open-file check as a veto, alongside durable ownership. My pick.** It catches detached tools and processes outside a leaf slice, while durable protection covers idle gaps. Source: `store-sweep/brief.md:17` and `scratch-copy-removal/brief.md:17`. Cost: proc races and permission failures need an explicit conservative result. Scan once per pass, but revalidate a removal candidate before destructive action where identity can change.

**O4b — Extend pane inspection to foreground cwd/process-info only.** Better than today's cwd, fewer host process reads. It misses other process groups and commands launched in separate PTYs and still cannot distinguish an idle retained attempt from abandoned work (F7). Not sufficient as the primary fix.

**O4c — Trust ownership only and drop process checks.** Less scanning, but a tool may outlive a disposable owner, including a browser outside its parent's cgroup. The recorded Chrome case is `learnings/history/2026-10-13-chrome-escapes-cgroup.md`, and #93 explicitly requires the veto. Reject without reopening that safety lock.

## 4. Practitioner questions and lifetime pitfalls

These are engineering questions grounded in the inspected mechanisms, not attributed to an unconsulted practitioner.

**R1 — Can cleanup see the path before its claim exists?** Remove the gap using a creation operation that establishes protection before exposing a usable worktree. Git add-with-lock is the candidate for worktrees; owner-before-copy is already the batch decision. A later chart write or add-then-lock sequence is insufficient. Prove this at the creation boundary, including interruption before checkout finishes. Sources: Q1, `scratch-copy-removal.md:42`.

**R2 — Does the claim survive an idle or replaced agent?** Keep task intent separate from process liveness. Prove a clean checkout with no pane/process inside survives repeated passes while review is pending, then prove it survives creator exit and can be resumed. A matching task record/lock must survive until explicit release. Source: `SKILL.md:117–123` and F7.

**R3 — Can names or parent cleanup bypass the claim?** Exercise direct/manual slugs resembling `verify-*`, `batch-*`, `<leaf>-u1`, and a longer `<leaf>-suffix`. A declared lock must beat prefix classification and force-copy removal. An enclosing store/repo deletion must not erase protected descendants, including when a repo registration changes. Sources: `store-sweep/brief.md:13–18`, `scratch-copy-removal/brief.md:13–18`.

**R4 — Can a release or replacement race delete the wrong attempt?** Bind protection to the canonical repo/worktree identity, not just a reusable display slug. Before release, verify the expected worktree still occupies the path. A stale owner must not unlock a replacement. Test concurrent create/release/reconcile, including a caller that loses its cwd. The existing next global lock covers next's own work, not arbitrary Git calls by chart agents (`src/next.ts:1391`; direct `SKILL.md:101,113`). Native worktree locking is retention, not mutual exclusion among every shell command.

**R5 — What happens if the inventory is incomplete?** Preserve #93's pane-unavailable keep behavior and make failed process/owner/lock reads errors or conservative keeps with a reason. Do not equate unreadable evidence with no owner. Current readKept now propagates read/parse errors (`src/reconcile.ts:26–41`), but a display report must not become the ownership database. Last-cleanup reports can be stale.

**R6 — How does a retained checkout eventually leave?** Normal direct completion owns removal (`SKILL.md:113–114`); interrupted attempts need a clear resume/abandon route. No automatic expiry of source work. Report the reason and clearing action through the accepted leftovers surface, including stale locks that need a person. Preserve the distinction from active leaf/run entries that leftovers intentionally hides (`src/leftovers.ts:9–20`).

**R7 — How will the regression be proven without another real deletion?** Extend `tests/reconcile.test.ts` and existing Git/temp fixtures, not a new runner. They already create registered variants and simulate unavailable/live pane inventories (`:428–449,493–500`); `tests/helpers.ts:44–55,81–93` provides isolated roots and CLI overrides. Cover both next and tab-close paths, clean retained direct work, actual release/removal, manual declared work, unknown work policy, collision cases, and surviving child processes. Use the in-flight test-isolation guarantees so no fixture reaches the real store. No tests or destructive experiments were run in this read-only map.

**R8 — Which historical claims should drive the contract?** Guard the reachable failure without pretending to know the historical caller. The seed and the existing worker fix are sufficient sources for a fail-before/pass-after test. Broader removal auditing would help future attribution but is a separate scope choice, not a prerequisite for protecting live attempts. Sources: F6, F8.
