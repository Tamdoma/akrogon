# Per-repo leaf caps — Slot C

## 1. Per-repo cap

- **Key & schema:** Optional `max_active: z.number().int().positive().optional()` in `repoSchema` (`issues/config.yaml`, `src/config.ts:48-75`), matching `globalSchema.max_active` (`src/config.ts:25`). No default: omitted means bounded only by the machine cap.
- **Combination with global cap:** In `activeCount` (`src/next.ts:369-397`) and `allocate` (`src/next.ts:403-421`), count both host `total` and `repoTotal` using the same rule (unfinished non-`merge` leaves with a live seat in that repo's session, plus `unreadable`, fail-closed on `unknown`). An un-live leaf starts only when `total < global.max_active` **and** (`repo.config.max_active === undefined || repoTotal < repo.config.max_active`). Already-live leaves keep running; `merge` leaves still do not count. `seatCommand` (`src/next.ts:1190-1193`) should name which cap blocked.
- **What it breaks / invites:** (a) **`effectiveConfig` shadowing bug (`src/config.ts:472-474`):** spreading `...global` then `...withSetup(repoConfig)` overwrites `global.max_active` with `undefined` when the repo omits `max_active`, or hides the machine cap when set — `effectiveConfig` must preserve global `max_active` and show the repo cap explicitly (e.g. effective `Math.min` or `repo_max_active`). (b) `issues/config.yaml` is git-tracked, so tuning a cap per machine requires a commit — acceptable because repo `max_active` reflects suite heaviness while `~/.akrogon/config.yaml` reflects the PC.

## 2. Challenge to WordPress-style priority numbers

- **Feasible, yes (~15 lines); needed, no — and it adds cold, sticky mental load.** Assigning integers (`10`, `20`, `50`) across separate repos' `issues/config.yaml` files forces you to remember an invisible cross-repo scale and whether lower or higher wins. Worse, priority in git is **static**, whereas urgency is **transient** (today akrogon is urgent, tomorrow framework is): you end up committing config edits to bump a repo and forgetting to revert them, starving lower-priority repos whenever a higher-priority repo has a backlog.
- **Simpler, warmer option:** **Per-repo caps + oldest-waiting-first across repos.** Per-repo caps already solve the real problem (a heavy repo with 12 leaves can no longer swallow all 9 global slots — e.g. `framework: 4` leaves 5 slots permanently open for other repos). When two repos are both under their cap and compete for a global slot, starting the **oldest waiting leaf** (matching your own first instinct: *"The oldest one waiting"*) is fair, zero-config, starvation-free, and requires zero numbers to remember. For one-off urgency on a given afternoon, existing `akrogon next <slug>` (start one leaf now) and `akrogon pause` (hold a noisy repo without touching git) already work cleanly.

## 3. Today's dispatch order when a slot frees (`file:line`)

- **Slot release does NOT auto-start waiting leaves in other repos today:** `landedWake` (`src/next.ts:1237-1249`) only calls `dispatchDependents` inside the same repo; `listen.ts:12,34,87,93` only triggers `next --resume`/`--wake`, which filters strictly to `phase === 'merged' || tab !== undefined || worktree !== undefined` (`src/next.ts:1442-1458`), skipping unstarted leaves waiting on `capacity`.
- **Cross-repo dispatch happens only in `akrogon next --all` (outside a repo):** `registeredRepos` (`src/next.ts:127-140`) reads `Object.entries(global.repos)` (`src/next.ts:130`) in raw `~/.akrogon/config.yaml` key order. `sweepAll` (`src/next.ts:790-802`) runs `merged` first, then loops `for (const repo of repos)` (`src/next.ts:793`) calling `sweep` (`src/next.ts:804-841`) greedily to completion on repo #1 before inspecting repo #2. Inside `sweep`, leaves sort by `merged` then descending `dependentCounts` (`src/next.ts:830-836`) with no wait-time or `created` tie-breaker, hitting `allocate` (`src/next.ts:415`). So repo #1 in `config.yaml` greedily takes every free slot up to `global.max_active`.

## 4. Recommended shape

Add optional positive integer `max_active` to `repoSchema` (`issues/config.yaml`, `src/config.ts`), enforce `total < global.max_active && repoTotal < repo.config.max_active` in `activeCount`/`allocate` (`src/next.ts`) with `effectiveConfig` (`src/config.ts`) printing both caps cleanly, and drop repo priority numbers altogether. Replace `sweepAll`'s repo-by-repo greedy loop (`src/next.ts:790-802`) with one cross-repo pass that collects eligible leaves across non-paused repos and orders them by **oldest waiting first** (earliest `wait: capacity` timestamp from `issues/timings.jsonl` falling back to `state.created`, breaking ties by `dependentCounts` so prerequisites still unblock first), skipping any leaf whose repo is at its `max_active`. Keep `akrogon next <slug>` and `akrogon pause` for ad-hoc urgency, and decide explicitly whether a freed slot in `landedWake`/`--wake` should also wake leaves already marked `wait: capacity` (so freed slots actually refill automatically without starting freshly charted leaves the operator has not queued yet).
