## 1. Pick, with reason and cost

Migrate, one run per repo, closed owners and ended chart direct only. After the taken pack/`akrogon log`/flaky code is merged and installed on this host, the operator (or chart door) runs the owner pack at each repo's main checkout on its default branch, then `akrogon sync` to commit and push the `issues/` deletions plus archives. Akrogon first (18.3 MiB, dogfoods the run), framework second. Open and parked tracked logs stay tracked until their owner's close-time pack deletes them. Fixtures outside `issues/` and the slots scraps are untouched by this fork.

Reason: closed owners are 99.8% of framework's tracked log bytes (943.15 of 944.9 MiB), so any answer that skips them does not solve the reported problem. The taken form already defines exactly where these bytes belong (`<owner>/evidence.tar.zst`, members relative to the owner), and recorded paths do not change, so every existing reader keeps working through the taken resolver. Per-owner archives of today's files, measured by streaming each owner through tar and zstd -19: framework 944.9 MiB in 46 groups (45 closed owners + 1 chart direct) → 23.43 MiB packed (40x); akrogon 18.3 MiB in 31 groups → 1.18 MiB. Chart direct needs no new mechanism: taken log-coverage already gives `akrogon pack <chart>` plus a plain-status warning naming each ended chart still holding plain logs. The new work is only letting the same pack run on a closed owner folder (taken `akrogon pack <chart>` packs only `direct/`), or a migrate verb that loops closed owners.

Who runs it, when: never a leaf. A leaf worktree cannot carry the framework commit at all, and in both repos `issues/` changes land from the main checkout on the default branch through `akrogon sync`, which refuses any other branch (src/sync.ts:30) and stages all eligible `issues/` changes into one `sync issues` commit and push (src/sync.ts:159-165). So the sequence per repo is: taken code installed → clean `issues/` status → run pack per closed owner and per warned chart → verify (below) → `akrogon sync`. Framework is a separate, later, operator-run application of the shipped command; the akrogon leaf's done-criteria can only prove the command on akrogon's own backlog and on fixtures.

Cost, stated plainly: the git pack and clone download do not shrink. Framework's pack is 177,731 KiB today, and unique `.log` blobs across all history occupy 115.7 MiB of it (3,965 blobs, 896.1 MiB raw; akrogon 5.0 MiB of a 10.6 MiB pack). With history rewrite out, those blobs stay reachable forever, and the migration commit adds about 23 MiB of archive blobs, so a fresh clone downloads slightly more than today and checks out about 921 MiB less. What improves is every working tree (main checkout and non-sparse worker worktrees) and the end of growth. One framework pack run took 110 s with external tar and zstd -19 in my measurement. The sync commit is 4,460 deletions plus 46 archives in framework, reviewable only by the verification counts, not by eye. Migrated logs also stop being readable on GitHub's web view and stop matching `git grep` over the tree; host reads go through `akrogon log <path>`, one path at a time. That loss is the same one the taken shape already accepts for future closes.

What each surface sees after this pick:
- Tree: plain logs gone under migrated owners and chart direct folders; one `evidence.tar.zst` per migrated owner (none for an owner with no logs) and per ended chart's `direct/`.
- Pack: grows by the archive blobs (framework about 23 MiB); all old log blobs remain.
- Fresh clone: same or slightly larger download; checkout smaller by 921 MiB (framework) and 17 MiB (akrogon) for logs.
- Readers: reports citing paths (520 unique `/`-bearing `.log` strings in akrogon `issues/**/*.md` at HEAD, 1,996 in framework, by `git grep`) keep resolving through `akrogon log`, which maps the recorded `open/` path to the closed owner's archive member. `verify-runs.jsonl` is unchanged; its unique recorded logs (akrogon 54, framework 77 in the live files) resolve the same way, except ones already dead today (akrogon 12 and framework 1 point into a removed `/home/ivan/.claude/jobs/.../tmp` worktree and resolve by neither plain file nor any future archive). flaky, moved to the same resolver by the taken shape, reads red logs from archives and errors only on a broken archive or missing member. Timings `check_end` log fields (akrogon 274, framework 1,088 in the live files) are recorded strings no code opens (src/timing.ts:48 is schema only; the only code that opens a recorded log is flaky, src/flaky.ts:10-17 today, resolver after the taken change).

## 2. Rejected options, with reasons

- O1. Remove from the tree without archives. Tree win is the largest (no 23 MiB of archives) and the pack does not grow, but the bytes then live only in history blobs, and the taken resolver has no history source: it prints the plain file else the archive member. Every cited path in reports and receipts goes dead in the tree, flaky prints `(log gone)` for closed red runs instead of naming failed tests, and recovery needs `git show <old-commit>:<path>`, which no skill teaches. The reporter asked for lossless and readable; this is neither in practice.
- O2. Leave the backlog as is. Zero risk and every reader unchanged, but framework keeps 944.9 MiB of plain logs in every full checkout forever, and the taken close-time pack only stops new growth. Since closed owners never reopen in normal flow, "leave" is permanent, and it leaves two forms of closed evidence side by side with no rule for which a reader meets.
- O3. Migrate only large or old owners. The top 5 framework owners hold 424.6 MiB (45%), so a threshold captures much of the win, but it adds a permanent threshold rule, keeps two closed-evidence forms, and the status and ignore logic must then explain which plain closed logs are legitimate. The per-owner archive is already the right granularity; a uniform run is simpler than a cutoff.
- O4. History rewrite. Out per the fork's carries; not considered. It is also the only option that would shrink the pack (115.7 MiB of framework log blobs), which is worth naming so nobody expects that win from O1 or the pick.

## 4. Pitfalls, and what removes each

- P1. Migrating before the new readers are installed. Today's flaky reads plain files only (src/flaky.ts:10-17), so a framework migration run against a pre-taken akrogon install makes flaky report `(log gone)` and leaves seats with dead cited paths. Removed by order: taken leaf merged, `akrogon install` (or self-update) done, then migration; before the sync commit, sample `akrogon log` on recorded paths from receipts and confirm `akrogon flaky` output is unchanged from a pre-migration run.
- P2. Sync sweeping unrelated pending `issues/` work into the migration commit. Sync stages every modified, deleted and new eligible `issues/` path (src/sync.ts:141-165), and framework's checkout carries modified chart files today. Removed by requiring a clean `git status` for `issues/` (sync or commit pending work first) immediately before packing, and re-checking the staged list before the migration sync.
- P3. Packing from a dirty disk instead of the tracked tree. The taken pack reads files on disk, so an untracked stray or a locally modified log inside a closed owner would be archived as if it were the tracked evidence, and the tracked blob's bytes could differ from the member that replaces it. Removed by P2's clean-tree requirement scoped to the targeted owners, plus comparing the archive member list per owner against `git ls-tree` for that owner before any plain file is deleted; a mismatch stops that owner.
- P4. Trusting a 4,460-file deletion on the pack's word alone. Removed by a pre-sync verification the run prints and the operator checks: per owner, files packed equals files tracked equals files deleted; byte-compare a sample of members against `git show HEAD:<path>`; total counts equal the table above (framework 4,460 closed + 2 chart direct; akrogon 694 + 36). The taken pack already does byte-equal read-back before deleting each plain log; the sample guards the migration loop and member naming, which are the new parts.
- P5. Expecting the clone or pack to shrink. It does not (see pick cost). Removed only by stating it in the run's report and the sync commit context, so the operator does not judge the migration a failure when `du` on `.git` is unchanged.
- P6. Scope creep onto logs that are not evidence. A repo-wide `*.log` sweep would pack framework's 3 test fixtures under `.claude/hooks/tests/fixtures/` and break those tests' inputs. Removed by keying the migration strictly to `issues/closed/<owner>/` folders and ended charts' `direct/` folders, the same folders the taken pack and warning already name.
- P7. A seat reading a closed log while its owner is mid-pack sees the plain file vanish. Closed owners have no writer (and after the taken change run-check refuses closed targets), so the window is one owner's pack-and-delete. Removed by running the migration while no chart door or learn pass is open on that repo; the pack's verify-then-delete per owner keeps any single owner's window short, and `akrogon log` works the moment the archive lands.

## 5. Questions the fork does not ask

- Q-A. Do open and parked tracked logs get untracked now, or only deleted by their close-time pack? Counts make it near-moot today (framework 0; akrogon 4 files, 3,920 B, in one open owner), but the fork should record the rule for the next repo that has more, including an open owner that fails and never closes.
- Q-B. One sync commit per repo, or one per owner? And who checks the framework run: the operator at the main checkout has no checker seat, so is the printed verification in P4 the whole review, or does a peer read it before sync pushes?
- Q-C. What happens to tracked `*.log` files under `issues/` that are neither owner evidence nor chart direct (akrogon's 9 slots outcome scraps, 1,128 B total): deleted as junk under the operator's clean-folders rule, packed, or left? They are too small to matter for size, but the migration's folder rule should say.
- Q-D. After migration there is no content search across old evidence: `akrogon log` needs an exact recorded path, and tree-wide `git grep` no longer sees log text. Does the operator need a search or list surface over archive members for the backlog, or is exact-path reading enough, as the taken shape assumes for future closes?
- Q-E. Is GitHub-web readability of already-closed logs a requirement for the backlog specifically? The taken shape trades it away for future closes in exchange for `akrogon log`; the backlog makes that trade retroactive over 4,460 framework files that are readable on the web today.
