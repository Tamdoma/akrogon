### 1 · Should slow proof rerun only the stages affected by a repair, or stop after one repair?

The existing standing rule already says to rerun changed stages and consumers, reuse valid unchanged stages, and require a full clean run when fresh-start, order or whole-run behavior is under test. Make that rule concrete in the existing proof plan: each slow proof names its inputs, consumed stage outputs, shared resources and trustworthy restart boundary. After a repair, A records which stages changed and reuses only evidence valid for the final code and external state.

Research: **operator / primary code**, read 2026-10-01 · named standing-design.md:9–11, K/skills/plan-issue/SKILL.md:57–59, implement-issue/SKILL.md:54–56 and L/plan.md:111–124. The operator’s standing design supplies the reuse rule, but this plan’s criterion-level trigger cannot identify which unchanged stages can be kept. This favors a specific application of the existing rule over a new retry cap. **Practitioner:** Marc Brooker, AWS Builders’ Library, [Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf), read 2026-10-01, explains repeated side-effect risk and safe retries. It supports checking external state before rerunning. Its advice concerns API retries, not a justified one-repair limit for development defects.

- **1a (recommended)** Make stage reuse explicit in the existing verification plan and report, rerunning changed stages and consumers because this removes unnecessary repeat work without discarding valid repairs.
- **1b** Stop a criterion after one repair and one rerun, preserving artifacts in `failed`, which bounds attempts but can stop at the next distinct owned defect and require recovery.
- **1c** Keep current wording and plan detail, which adds no work but leaves broad C8 rerun decisions to A during the expensive run.

Pitfalls: Source commit alone does not establish unchanged inputs. Shared files, lockfiles, env inputs and external fixture state count. A stage that tests the full order cannot be replaced by separately passing components. A contract explicitly requiring a fresh final-code full run still requires it. No criterion change or live-leaf rewrite is authorized here.

### 2 · May A start independent implementation or repair work while a slow proof runs?

Yes, when the proof’s input code and fixture stay unchanged. Run independent units in their worker worktrees and land them after the proof returns. Overlap excludes a shared fixture, an output dependency, or an edit to anything the command reads. Once the commits land, use question 1’s rule to decide whether the result still proves final code. Final criterion/check handoff remains after all units land and worker worktrees are removed.

- **2a (recommended)** Allow independent worker work during a slow proof while keeping proof inputs and shared fixtures stable, because otherwise A waits even when a valid independent unit is ready.

The measured launch tail has no established large independent unit available throughout it, so promise conditional savings, not a 104m reduction.

### 3 · Should A observe a slow command through completion rather than long sleep-and-tail polls?

Recommend using the harness’s existing command-completion mechanism when it preserves the command’s exit status and result. A starts independent work if available, otherwise waits for completion rather than repeatedly issuing a long sleep followed by a partial tail. Logs remain diagnostic evidence. This is a workflow rule, not a new watchdog, timeout, background runner or command wrapper.

Research: **primary measured result**, read 2026-10-01 · L/implementation/evidence/c8/launch.json and S:665–666 show approximately 2m10s of observation lag after gate-close evidence. S:235–855 contains 43 numeric sleep calls during the main tail. This favors reducing result-observation lag, but does not establish a portable completion tool for every configured harness. Exact harness operations must be inspected and probed before a handoff names them.

- **3a (recommended)** Prefer an existing completion result over ad hoc long sleep polls, because it exposes command completion and failure sooner without another lifecycle mechanism.
- **3b** Keep current polling behavior, which needs no harness-specific change but retains observation lag and extra turns.

Pitfalls: A background job returning a PID is not a completed command. A quiet log is not success, and process exit needs its actual status. A supported completion wait must not add a new elapsed ceiling. If a harness offers no sufficient completion operation, hold that implementation portion for operation proof instead of inventing a fallback.
