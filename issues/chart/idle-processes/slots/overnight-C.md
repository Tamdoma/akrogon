# Overnight stall — C

## Q1. What held akrogon.slice anon+shmem over 48 GiB?

- The gate itself made the total decisive: `usage()` sums only `anon + shmem` for the whole akrogon.slice (`src/admission.ts:88-107`), and `denied()` blocks every new top-level start at ≥48 GiB before even checking spacing (`src/admission.ts:121-123`). It therefore counted seats, bare/direct work, browsers and files left by other leaves, not only admitted checks. Favicon B observed exactly that state at 55.5 GiB "with no admitted checks running" (`issues/log.jsonl:2631` in framework; review-B.md:391-403).
- Dead waiting records still in `runs/*.yaml` give sampled gate readings of 61.8 GiB at 00:38, 53-62 GiB at 04:07-04:31 and 49.6-49.7 GiB at 06:49-06:59 local (record `wait_reason` fields, files 98b95b…, 0eed9b…, f144f5…). By my 07:30 read it had fallen to anon 15.75 + shmem 13.41 = 29.2 GiB (`.../akrogon.slice/memory.stat`), so the block was a standing baseline, not one run's peak.
- **Tmpfs scratch was a large, durable part of shmem, but not a proven 30-42 GiB.** At 07:30, `du` found 12 GiB under `/tmp/akr-1000` (3.3 GiB more in `/tmp/page-measure-*`), and the largest leaf root, schema-capture's, was 7.0 GiB while its slice reported shmem 7.03 GiB — for that leaf the file/shmem match is almost exact (live `du` and per-slice `memory.stat` commands). Surviving file blocks with mtime ≤00:38 are only a 3.1 GiB lower bound, rising to 10.9 GiB by 04:30 (my `find`/`st_blocks` walk); deleted files are invisible, so the peak tmpfs share cannot be reconstructed exactly. [low confidence on the peak split]
- Why those files persist: seat `TMPDIR` is the per-leaf scratch (`src/next.ts:463-478`) on fixed `/tmp/akr-<uid>` (`src/config.ts:267-275`), and direct seat tests inherit it. `run-check` deletes only its own `run-*` root in `finally` (`src/run-check.ts:151,199-201`); reconcile removes dead-owner `run-*` dirs, but keeps the rest of a leaf's scratch while a pane is live (`src/reconcile.ts:411-447`). Everything a direct test, a killed test, `bunx` or a browser profile writes at the top of TMPDIR therefore lives until the test cleans it, the tab ends, or reconcile can remove the whole leaf dir. Schema-capture alone now has 1,757 top-level entries in its leaf temp (live `find` count).
- Biggest surviving file classes are real test working sets turned leftovers: repeated ~216 MB `csp-spine-*` scratch repos, 913 MB `site-*` and 774 MB `cfm-*` build trees, repeated 134 MB workerd binaries inside per-run `bunx-*` installs, and 86 `page-measure-*` browser profiles totaling ~7.6 GiB across `/tmp` and leaf roots (live `find`/`du` at 07:30). Page-measure removes its runtime dir only in `closeBrowser` (framework `page-measure.mjs:392-396`), so killed runners strand both profiles and browsers.
- The rest was process memory, also stranded in part: seat harnesses (dozens of pi/codex processes at ~0.4-0.7 GiB RSS each in the 07:35 slice census), live test/browser trees, and orphan roots. Even after the drop, at 07:35 the slice held 967 processes and two orphaned node servers alone at 3.5 GiB and 2.6 GiB RSS (ppid = user systemd, live `/proc` census). Orphan browsers are proven for the evening: 57 roots / 935 processes / ~19 GB anon+shmem at 20:39 (forks/browser-cost.md amendment), with 12-28 back in 20 min; overnight browser leaves kept recreating that class (36 crashpad-only orphan roots still present this morning).
- Not a contributor to the *gate*: Mission Center. Admission reads only `akrogon.slice/memory.stat` (`src/admission.ts:69-73`); a desktop app in app.slice cannot move that number, so the bounded-lane review's "close Mission Center" action (review-B.md:52) could free host RAM but could not open this gate.

## Q3. Which changes since 2026-10-11 caused the regression?

- **Memory admission (`e1da855`, 23:13) is the overnight blocker.** It replaced a count guarantee (a permit is eventually granted) with a state guarantee nobody could satisfy: aggregate slice memory had to fall below 48 GiB before *any* check could start, while the memory was held by seats, direct runs, orphans and files that admission neither owns nor frees (evidence in Q1/Q2). The 30 s spacing (src/admission.ts:60-68,124-128) is minor next to multi-hour waits (framework timings.jsonl:991-1113: waits to 5.15 h).
- **The run permit (6968997/67c905f, 12:46-12:52) was the daytime regression and tonight's setup, not tonight's mechanism.** Framework timings before 12:46 show no waits; by 14:19 a cheap check had waited 2.34 h (timings.jsonl:671). It created the bypass/backlog and the long foreground waits, but it was deleted before midnight.
- **`2c3a0af` leaf TMPDIR on tmpfs (10-11) is a latent amplifier, not a sufficient cause.** It predates the "worked" days the operator cites. It became load-bearing only when seat scopes/slice charged that RAM to akrogon.slice (13:09 stack) and admission started counting shmem. Before that, the same bytes were host RAM/swap pressure but no gate read them.
- **Scopes (f0c7f88) cost no runtime speed by themselves; the slice they feed did.** A scope adds no CPU/memory properties (src/scope.ts:69-84); the costs were CPUQuota=1600% until 51f9a67 (21:11) and MemoryHigh throttling once memory crossed 64G, plus one-time adoption/close on restore (src/next.ts:436-445,510-528). Scopes are also the only reason last night's memory and today's orphans are attributable per leaf at all.
- **Bus cut (`ebe23a7` run env, f0c7f88 seat placement) caused the auth class only.** Favicon's first failure and merge-push failures from ~13:00 are this; seat-wide placement was already removed at 23:10 (4e2752c) and akrogon's own git/gh regained the bus in 04577a4, so it explains none of the memory stall after midnight except favicon's first pass. It did, however, make slice accounting real by keeping Chrome from self-scoping out — removing it would lower the gate number by hiding browsers, not by freeing RAM.
- **Serial-solo (df88689) is not a host regression.** It removes workers for single-unit-wave plans and forbids overlap for those runs; that lowers concurrent demand and can lengthen one leaf's wall time while A waits on checks, but no overnight failure cites it, and the worst leaves were delegated/browser-heavy. At most it made admission waits more visible as idle seat time.
- Also today, not in the list: max_active went 20→6→12 (237208f, then operator revision in dispatch-wip Taken) and nine browser/test-cost leaves were handed off in the evening, so the overnight workload was unusually browser- and check-heavy. Workload mix is a real confound for every day-over-day comparison above.

## Q4. Smallest set to restore throughput, keeping test-cost

1. **Remove the admission denial and the 30 s spacing from `src/admission.ts` (keep records, nesting token and `wait_ms`=0 semantics or record observed usage only).** Memory becomes a signal again (status/census), not a start gate. This alone reopens every blocked leaf; MemoryHigh/MemoryMax in systemd/akrogon.slice:5-9 remain the emergency brake.
2. **Move leaf temp off tmpfs to a short disk path**: change the default root in `leafTemp` (src/config.ts:267-275) from `/tmp/akr-<uid>` to a short home-disk root with the same two-level hash (e.g. `~/.akr`, 29 chars vs 27, on btrfs per `df -T`), preserving the Chrome socket-length fix that motivated 2c3a0af. One-time operational cleanup of dead-owner `/tmp/akr-1000` and `/tmp/page-measure-*` dirs then drops the standing shmem baseline instead of waiting for seats to end.
3. **Nothing else in akrogon.** Keep scopes and the slice, keep CPUQuota already removed, keep seat bus as restored by 4e2752c with the cut only inside run-check (src/run-check.ts:56), keep serial-solo and worker-test-duty. Framework test-cost leaves proceed as charted — they are the durable fix for why a single leaf can create 7 GiB of scratch and dozens of browser profiles in the first place.

## Disagreements with A's view

- A1: "30-42 GiB of leftovers" overstates what the records prove. Surviving tmpfs file blocks are 3.1 GiB by 00:38 rising to ~11 GiB by 04:30 (with deleted files unknowable), while seats, live browsers and orphan processes made up much of the 49-62 GiB. Tmpfs leftovers prolonged the block; they were not its whole mass at midnight.
- A2: Temp folders do not only go when the seat ends. RunCheck deletes its run root in `finally` (src/run-check.ts:199-201) and reconcile removes dead-owner `run-*` roots (src/reconcile.ts:429-432); what accumulates is top-level scratch from direct seat/test processes and killed runs, a narrower class with a different fix (test cleanup/browser lifetime, already in framework leaves).
- A3: "Seats started bare runs around admission" happened, but it is not the main loop: several seats explicitly did the opposite (schema-capture killed its bare runs as non-evidence, report.md:50; bounded B stopped only its own queue PID, review-B.md:46). The deadlock is structural — the gate blocks the checks that would let leaves finish and release seats/temp — and would have held even with perfect seat discipline while baseline memory stayed above 48 GiB.
- A4: The permit is not tonight's regression; it was replaced at 23:13. Conflating permit (eventual grant) with admission (possible indefinite starvation) hides the one change that must be reverted first.
