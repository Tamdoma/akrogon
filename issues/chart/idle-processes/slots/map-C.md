## Forks
- F1 Status scope: O1 default becomes all repos (simplest; every status call scans 10 repos and gets long/slower for seats that only need theirs); O2 `--all` flag, cwd default stays (small; operator habit that caused I1 still misses leaves); O3 cwd repo detailed + one-line leaf/failure counts for every other repo, plus global slug lookup with an ambiguity error (keeps focus, answers "where is it?", costs a state-file scan per repo). Also decide whether `--charts` follows the same scope. Lean O3.
- F2 What counts as leaked: O1 ownerless = ppid is user systemd and process is in a leaf slice but not in a live run unit, not the pane shell's ancestor chain and not the seat agent (catches busy leaked browsers, the 57-browser case; false-hits deliberate daemons like wl-copy and long-run background checks between tool calls); O2 CPU-idle = ownerless plus near-zero CPU over a sample window (misses the worst case: orphaned browsers were burning ~6 cores, intake/browser-cost evidence); O3 resource-ranked = ownerless roots reported by anon+shmem/CPU-delta/age with no idle claim (honest signal, operator reads a list). "Idle" must not mean CPU-idle alone.
- F3 Signal surface (I2): O1 census only inside `akrogon status` (read cgroup procs + /proc per leaf on demand; no daemon; two samples or cpu.stat deltas make status slower and a 0.5-5 s wait); O2 census in existing `next` passes, persisted first-seen timestamps + status reads records (catches leaks while operator is away; writing state from status/next paths needs the usual lock discipline and scenario tests must not read the real host cgroups — needs a proc/cgroup root override like AKROGON_PROC_ROOT at src/scope.ts:21-26); O3 new watcher daemon (fastest signal, first long-lived akrogon process, itself a leak/lifecycle risk — reject unless O2 demonstrably misses).
- F4 When leftovers die: O1 only at boundaries akrogon already owns (run exit via run-units; merged: after tab close/reconcile stops the leaf slice; failed: report only, leaf may resume); O2 boundary + age/resource reaper on next passes for open leaves (kills the crawl-run-binding class mid-leaf; risks killing a deliberately backgrounded long-run check whose seat will read its exit file next pass); O3 manual only (`akrogon clean <slug>` after status flags it; safest, relies on the operator noticing — the original I2 failure). Under no-caps, O2's thresholds are a kill policy, not an admission cap, but they still need operator-set age/memory numbers.
- F5 Kill mechanism: O1 `systemctl --user stop <unit>` (systemd.kill(5) KillMode=control-group kills the whole cgroup; correct for run units and whole leaf slices, suicide if ever aimed at a live pane scope — it contains the seat, src/scope.ts:53-90); O2 signal the enumerated root trees inside a pane scope, then re-scan that scope's cgroup.procs and escalate (preserves the seat; fork race between scan and signal, PID-reuse needs pid+start_time check as in src/permit.ts:41-46); O3 freeze-then-kill for run units (closes the fork race, dangerous anywhere a seat/agent shares the unit). Herdr tab/pane close is not a kill mechanism for detached work: scopes have no main process and live while any member lives (systemd.scope(5), local man systemd 262); herdr help states no process semantics (herdr pane/tab close --help, read today), so akrogon must verify emptiness itself after any close.
- F6 Zombies and intentional persisters: O1 report-only with parent named (a zombie is already dead; only its parent can reap it, wait(2) man7.org read 2026-10-13; killing the parent would kill a live seat/test); O2 treat zombie count per parent as a bug signal routed to the owning leaf's report, never a kill target. Persisters (wl-copy, blepsis daemon, dev servers, worker supervisors) need classification by recorded owner/run record, never by comm-name allowlists that rot.

## Practitioner questions and pitfalls
- Q1 What false-kill is acceptable: killing a live long-run background check loses 12+ min of proof and can corrupt a fixture mid-write; is "owner dead + 30 min + reported once" the bar, or must a human confirm outside run units?
- Q2 Which sample proves busyness: per-process CPU ticks over what window, and memory by cgroup anon+shmem (not summed RSS, which double-counts shared Chrome pages)?
- Q3 Who owns a process whose leaf slug was closed and later reused — slice names are sha256(repo/slug)[:12] (src/scope.ts:13-15), so a reopened slug inherits the old slice; compare process start against the leaf's created/prompted times before blaming or sparing it.
- Pitfalls: scan→kill races and PID reuse; status/next scenario tests on this host must never census or kill real slices (fixture AKROGON_HOME does not isolate cgroups); stopping a leaf slice during reconcile can abort a merge seat that is mid-push in another pane of the same leaf, so terminal cleanup must key on phase=merged plus no live pane, as mergedWorktree already checks (src/reconcile.ts:243-267); counting loaded empty slice/scope units as leaks will cry wolf; CPU-idle tests with real timers (playback, motion) look idle in short windows.
