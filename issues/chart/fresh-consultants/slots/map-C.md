## #99: fresh consultant sessions

### Settled direction
- Do not reopen `/clear` versus restart. The operator chose `herdr pane close`, the same split sequence, then `herdr agent start`; the live help confirms close takes a pane ID, split returns a new pane, and start takes the harness, pane and original args. The restart comment from `gh issue view 99 -R Tamdoma/akrogon --comments` also proves Codex starts with no session and `peer-wait` can adopt the one that appears later (`peer-wait.ts:139-155`), so no warm-up turn is needed.

### Material forks
- **Reset boundary.** “At door open” alone does not fix the reported same-pass growth: the cause explicitly includes missing resets “between charts or doors” (`issues/seeds/99-chart-issues-consultants-keep-one.md:31-41`), and Drain can move among several charts in one door (`SKILL.md:43-47`). Prefer replacing consultants immediately before each chart's opening map, and again when a previously left chart is resumed, after its prior peer exchange has ended. Resetting only once per door leaves later charts carrying earlier charts; resetting before every exchange discards useful context within one chart and adds avoidable pane churn.
- **Who may be replaced.** The existing lock says the door arranges only panes it created; the live rule says supplied panes are never moved or resized (`SKILL.md:25-27`, `assets/questions.md:44-46`). Closing a supplied pane would be a stronger violation. The contract must therefore choose between (a) automatic close/recreate only for door-created consultants, with supplied peers remaining operator-managed, or (b) obtaining explicit authority to replace supplied peers. Without this distinction, the fix can destroy an unrelated terminal.
- **Failure after close.** Close/split/start is not atomic. Choose whether a failed split/start drops that consultant and continues, or stops the chart until the peer is restored. Continuing matches autopilot's existing per-consultant drop behavior, but silently reducing an attended peer set would violate the named-peer exchange. The behavior and operator report need to be explicit. `herdr pane split --help` and `herdr agent start --help` expose no transaction or rollback; the test harness already models split and start failures (`tests/fake-herdr.ts:55-68,171-192,224-245`).

### Practitioner questions and lifetime pitfalls
- Preserve each seat's letter, harness, launch args and lowercase agent name while replacing only pane/session identity. The live restart rejected uppercase names; the fake Herdr enforces the same name grammar (`tests/fake-herdr.ts:224-234`). Losing args can silently change model or runtime behavior.
- Never close a pane while its exchange is open. The current exchange contract keeps A in-turn until collection and requires an idle wait before prompting (`assets/questions.md:46-52`); replacement belongs between chart activations, not inside `peer-ask`/`peer-wait`.
- Update the seat record with the replacement pane and eventual session. Current records append only when a session ID changes (`SKILL.md:37`), but restart also changes pane IDs. Codex's first exchange legitimately starts with `session: null`; forcing a warm-up recreates the bug class the operator rejected, while `checkIdentity` already adopts a later ID (`peer-wait.ts:143-155`).
- A consultant dropped for the rest of an autopilot session must not be revived by the next chart's restart; that would contradict the drop rule (`SKILL.md:139`).
- Tests should cover restart order, retained kind/args, new pane IDs, Codex null-session first exchange, supplied-pane non-interference, and split/start failure. `peer-ask` seeds identity before prompting (`peer-ask.ts:46-75,112-129`), so changing that script is unnecessary if restart happens before the exchange.

## #100: true chart windows and Pi measurement

### Material forks
- **Window representation.** Fixing only `opened` is insufficient over the chart's lifetime. A chart can be left while waiting and resumed after another chart (`SKILL.md:43-47`), so one start/end envelope can still include unrelated work. Prefer chart-owned active spans, opened before each chart pass and closed when the door leaves it; the script should sum records in those spans. A single corrected `opened` is smaller but breaks on interleaving and on later reruns. The current record defines one never-reset `opened` value (`assets/shapes.md:161-174`), and the script has only that lower bound plus optional `until` (`chart-usage.ts:342-361`).
- **Backward compatibility.** The operator requires running the fixed script on historical `base-red`, whose record has only `opened` and seats (`issues/chart/base-red/seats.yaml:1-14`). The new shape must therefore read that old form with the supplied/historical end while new charts use explicit spans. Requiring migration would make the required baseline impossible.
- **Comparable call/context definition.** Use one provider model response as one call. Claude already deduplicates streamed rows by `message.id` (`chart-usage.ts:153-172`); Codex exposes one `last_token_usage` per `token_count` event, while its `input_tokens` already includes cached input; Pi exposes one `message.role == assistant` record with `usage.input`, `cacheRead`, `cacheWrite`, `output` and `durationMs` per call (inspected the recorded Pi session from `base-red/seats.yaml:11-14`). Context per call must avoid double-counting Codex cached tokens: Codex context is `input_tokens`; Claude/Pi context is uncached input plus cache-read plus cache-write/creation input. A naive `input + cached` formula overstates Codex.
- **Pi session lookup.** Herdr records Pi as an absolute JSONL path (`base-red/seats.yaml:14`), unlike Claude/Codex IDs. Prefer validating and reading that exact recorded file instead of basename-searching the session tree, which can become ambiguous. Current `locate` rejects every non-Claude/Codex harness (`chart-usage.ts:103-118`), and dispatch otherwise routes every non-Claude result through the Codex parser (`chart-usage.ts:371-381`).

### Practitioner questions and lifetime pitfalls
- Pi turns and minutes should retain the documented meaning, from a user prompt through the final assistant response, rather than summing only API `durationMs`; current reporting defines work by completed turn spans (`chart-usage.ts:432-445`; `docs/guide/chart.md:162-164`). Otherwise Pi minutes are not comparable with Claude/Codex and omit tool time.
- Pi parsing must validate timestamps, model, thinking level and every usage field before counting. Real inspection found assistant records carrying `model`, `provider`, `thinkingLevel`, `durationMs`, and usage; the session also contains `custom`, `compaction`, `context_edit`, tool-result and system records, which must not become calls. Missing/malformed data should keep the existing per-seat `usage unmeasured`/`outcome partial` behavior (`chart-usage.ts:363-385,456-488`), not emit a plausible zero.
- Multi-session seats and multiple active spans must not double-count boundary records. Existing tests already cover adding sessions, excluding both sides of a window, and refusing counter resets (`tests/chart-usage.test.ts:226-319`); add Pi fixtures plus adjacent/disjoint span cases and exact-boundary cases.
- The savings criterion is nonblocking but concrete: run the fixed script on `base-red` and on the #99 and #100 charts; print one row per chart and seat with calls, average context/call, input, cache-read, output and working minutes. For consultant seats B and C, report `(new average - baseline average) / baseline average` separately by matching harness/seat, not a pooled total. This follows the operator's “compare per call, not totals” instruction and avoids chart-size bias.
- The baseline is recoverable: direct inspection of the historical Pi window yielded 59 calls, 308,376 input, 4,453,716 cache-read, 42,208 output and about 80,713 prompt-context tokens/call; the existing script currently reports it only as unknown Pi (`issues/chart/base-red/USAGE.md:22-34`). This is evidence for the parser contract, not a merge threshold.
