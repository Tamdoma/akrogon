# Getread B: flake-zero

Read at reset-flake head 37a37b4b. (H) marks what I ran on this host on 2026-11-24 in a private throwaway hc session (`akr-probe-b7`, removed), hc 0.1.22, 48 busy loops on 32 cores. Nothing in the repo changed.

1. O1 is sound for a predicate that reads only the state. The get is the same kind of observation as the snapshot, taken later. Every `waitForTerminal` caller has such a predicate (door-reset `:89, :131`, `tests/e2e/watch-live.e2e.ts:179, :565, :590`, `tests/e2e/watch-consults-body.ts:286`).
2. It is not sound for agy's task wait. That predicate reads the line and sends (`src/seat.ts:150-162`), and a get has no line. The start proof needs no get, because its stream opens before the seat runs.
3. So put the get in `waitForTerminal`, not in `waitFor`, and not in door-reset alone: watch-live's `turnDone` is the same wait as the rename. `waitFor` goes back to main's body. `waitForTerminal` takes `(t: Seen) => boolean` and becomes `events = waitFor(...)`, `read = terminal(...).then((t) => (until(t) ? t : events))`, and it returns the first of the two. No `listed`, no bounded read, no flag.
4. That closes F1 (nothing is merged with the get) and F2 (the loop never awaits the get). F3: a get that fails hands over to `events`, with a logged warning when the failure is not `not_found`. F4: accept it. A check that the stream is still open can pass and the core can stop right after.
5. Probe (H): a turn end is a `status` idle event and then a `turn` event with the next seq. `hc send` answers with the turn count from before. In 2,002 subscription starts on a terminal ending a turn every 8 ms, 67 starts lost events. In 2 of them the idle was lost and its `turn` event delivered. Main then holds working with the new turn count, so the rename wait and `turnDone` run out their bound. No snapshot was cut between the two events (0 of 2,002), so a get sees both and O1 returns.
6. Probe (H): a new subscription's snapshot was the true state at its seq in 1,603 of 1,603 starts while labels changed (14,878 events on a complete stream). 167 starts lost events. Each loss was a run directly after the snapshot's seq, and none came after the first delivered event.
7. Race left, L1: a predicate over two facts, where one change is lost at the start and never sent again, and the other turns true after the get. Both paths stay false until the deadline. No caller has one today, because `turn` comes again with every idle.
8. Race left, L2: the get can be true while the events already show a later state, such as idle from the get and working from a queued event. Main has the same when it returns on an idle event with a working event queued behind it.
9. If a later round finds a hole in the get, the exact fix is a second subscription opened after the first one's snapshot arrives. Its snapshot is a read with a seq (point 6), and the reader already drops events at or below a snapshot's seq (`src/hc.ts:388-404`). It costs a second stream and holds events back until that snapshot arrives, so I would not start with it.
