## Q2 — Which hand-offs leave the line

- **Pick**: **Every hand-off that needs a seat leaves the line to `check.repair` (red verify, gate refusal, mechanical rebase conflict / dirty worktree); command handles push retries (`land.ts` keeps 1 automatic `restack` on non-fast-forward, re-queues back to `merge` on a 2nd non-fast-forward, and moves fatal push errors — auth/network/hook — to `failed` off-line).**
  - **Reason**: Eliminates all seat work from the merge line — including the **17 `solo_conflict` attempts (5.87 lane-h, 0.88h of B resolving conflicts on the line)** since 2026-11-14 — and makes `akrogon land` the **sole** owner of `state.batch`, merge-scope verify, and `git push`. That deletes the entire seat-owned merge / `attempt solo` / `rerun` path, which **eliminates Defect D1** (`batchPush` `applied: false` vs `mergeTurn` race, ~61–97m lost in 2 Nov 18 incidents — exists only for seat-owned batches per `map-merged.md`) and **eliminates Defect D2** (2h dead-lane stall on a lost B seat) from the merge line by construction. Matches GitHub Merge Queue evicting on merge conflicts as well as check failures.
  - **Cost**: A leaf conflicting on a hot file (e.g. `package.json`) resolves conflicts off-line in `check.repair` and re-enters `merge`; if another leaf changes that same file in the interim, it could conflict again (mitigated by Q4 preserving `merge_stamp`). Also updates `skills/merge-issue/SKILL.md` to retire `attempt solo` and seat-run `merged` instructions (broadcast-only or manual fallback).
  - **Consumers whose behavior changes**: `src/next.ts` (`mergeTurn` `:1024-1042` evicts `!staged.ok || !applyTop` to `check.repair` instead of dispatching `solo`; `dispatchMergeLeaf` and `mergeContext` shrink/disappear), `src/land.ts` (`handOff` `:67-80` and `land` `:82-109`: `red`/`gate`/`rebase` -> `check.repair`; 2nd non-fast-forward -> clear `batch` and re-queue in `merge`; fatal `push` error -> `failed`), `src/phase.ts` (`phaseCommand` `:921-949` no longer needs seat-owned `merged`/`batchPush` except operator recovery; `commitMove`), `src/status.ts` (`note`), `skills/merge-issue/SKILL.md`, `skills/check-issue/SKILL.md` (`## check.repair` owns conflict resolution + retired-lesson re-removal + missing `Test-Change:` trailers).

## Q3 — Off-line retest & flake triage

- **Pick**: **Narrow `akrogon run-check` of the failing test file/script (never a full merge suite), with flakes told apart by seat B's judgment (no seatless auto-requeue from `akrogon flaky`).**
  - **Reason**:
    1. *Why narrow `run-check`*: Lock 2a forbids a second concurrent full suite until N2 passes, AND an off-line full verify against an old base is wasted whenever another leaf lands ahead of it (receipt tree becomes non-fast-forward). Narrow `run-check` isolates flakes and verifies mechanical/conflict fixes in seconds (Chromium CQ isolated single-test retry pattern) and eliminates the **23 wasted extra full verifies (3.87h)** B ran before `check.fix` bounces since 2026-11-14.
    2. *Why B judgment over seatless `akrogon flaky` requeue*: Chronological simulation on framework `verify-runs.jsonl` (`2026-11-14..21`, 0 missing `failures` fields) showed `akrogon flaky` matched all failures on only **11 of 43 true flakes (25.6%)** while misclassifying **3 of 14 matches (21.4%)** that actually needed `check.fix` — two via nameless `(script)` collisions (`first-paint-reuse` on `(script) test:sb-hero-first-paint`, `reject-literal-removal` on `(script) test:motion-probe`) and one on real flaky titles (`gate-rerun-supersede`). Even restricted to real titles, seatless requeue misses 74.4% of flakes, adds flaky-matching + retry-counter state to `land.ts`, and risks burning a full line turn on a leaf that genuinely broke a known-flaky test. B already wakes on reds today (token cost does not grow, and Q5 reduces B wakes during main-red streaks) and judges 100% of flakes against `git diff "$AKROGON_BASE"...HEAD`.
  - **Cost**: ~11 repeat-flake runs/week still spend one short off-line B turn + narrow `run-check` (overlapped with the next leaf's `land`) instead of zero tokens; load-only flakes that pass narrowly off-line still pay one full `land` run on re-entry.
  - **Consumers whose behavior changes**: `src/verify.ts` (`verify` `:856` and `verifyCaller` `:449` enforce `leaf`-only scope in `check.repair`), `src/run-check.ts` (`runCheck` `:208-217` already refuses `merge_checks` argv), `skills/check-issue/SKILL.md` (`## check.repair` directs B to read `akrogon log` of `merge_exit.red` and run narrow `akrogon run-check`), `skills/merge-issue/lifecycle-rules.md` (`## Red check with no cause in the leaf's diff` replaces merge's full `akrogon verify --attempt <id>` retry with narrow `run-check` off-line).
- **Rejected options**:
  - *No off-line retest (`none`, log read only)*: leaves B unable to verify mechanical repairs (8–10/week) or resolved rebase conflicts (17/week) before re-entering the line, or to reproduce unfamiliar failures locally — causing avoidable red line turns.
  - *Full suite off-line*: breaks Lock 2a until N2 passes; even if serialized by `full:` in `admission.ts:147`, it indirectly blocks the merge line AND produces stale-base receipts once `main` advances.
  - *Seatless requeue from `akrogon flaky`*: only 25.6% recall on flakes, 21.4% false positives before script-filtering, adds machinery to `land.ts`, and can waste a full line turn on a real regression in a flaky test.
- **Evidence**:
  - `better-than-training` · chronological simulation over framework `issues/verify-runs.jsonl` & `issues/merge-attempts.jsonl` (`2026-11-14..21`, 0 missing `failures` rows, run 2026-11-21) · `all_in_flaky=True`: 11 flake, 3 `check.fix`; `all_in_flaky=False`: 32 flake, 43 `check.fix`, 10 `b_fix`, 13 `known_red`.
  - `better-than-training` · framework `issues/timings.jsonl` (`2026-11-14..21`, read 2026-11-21) · 17 of 43 `wake_red -> check.fix` attempts burned 23 extra full verifies (3.87h) before bouncing.
  - `practitioner` · Chromium Commit Queue / LUCI CV docs (`chromium.googlesource.com` / `chromium.org`, read 2026-11-21) · isolate and retry the failing test/shard alone rather than re-running the whole build to separate transient flakes without masking real bugs.
  - `better-than-training` · GitHub Docs & GitLab Merge Trains docs (read 2026-11-21) · an evicted PR tested off-line against an older base cannot fast-forward once the queue advances.
- **Pitfalls & removals**:
  - *Stale skill text making B try full verify*: `skills/merge-issue/lifecycle-rules.md:25` currently mandates `akrogon verify --attempt <id>` on merge retries. **Removal**: update `lifecycle-rules.md` and `skills/check-issue/SKILL.md` in the same leaf; `verifyCaller` (`src/verify.ts:449`) and `runCheck` (`src/run-check.ts:208`) mechanically refuse full merge-suite invocations from `check.repair`.
  - *Load-only flake passes narrow repro, then flakes repeatedly on `land`*: **Removal**: Q4's bounded priority-return cap stops head-of-line looping after 2 returns.

## Q4 — Re-entry queue position

- **Pick**: **Return at its first-entry place (`merge_stamp` preserved) ONLY when returning from `check.repair` (no code change by A) and within a bound of 2 priority returns per leaf; after the bound — and on any return through `check.fix -> check.review -> merge` (code changed by A) — reset `merge_stamp` to the back.**
  - **Reason**: Directly optimizes Lock 1a (first entry into `merge` to landed, failed rounds included). Innocent flake victims (43/week) and conflict victims (17/week) avoid paying an extra 60–120m queue-depth wait (today >1-entry leaves have p90 **294.2m** vs **197.7m** for 1-entry; `checker-command` is at 11h05m) and avoid hot-file repeat rebase conflicts caused by aging at the back of the queue. Meanwhile, the original 2026-10-05 reason for resetting `merge_stamp` ("never inserted into an already-recorded batch", `merge-turn/forks/turn-release.md` Q3) disappeared when batches were deleted in `6e7a33ff` (2026-10-19). Bounding priority returns to 2 and resetting on `check.fix` prevents a persistently broken or chronically flaky leaf from thrashing at turn 1 and starving healthy leaves behind it.
  - **Cost**: One counter `merge_returns` (non-negative int, default 0) on `stateSchema` (`src/state.ts`), incremented on `check.repair -> merge` when `merge_exit` is set. A leaf returning after a genuine A fix (`check.fix`) still re-enters behind leaves already waiting in `merge`.
  - **Consumers whose behavior changes**: `src/state.ts` (`stateSchema`: `merge_returns`), `src/phase.ts` (`commitMove` `:230`: preserve `recorded.merge_stamp` when `recorded.phase === 'check.repair' && recorded.merge_exit !== undefined && recorded.merge_returns < 2`, else `new Date().toISOString()`; increment `merge_returns` on preserved return, reset to `0` on `check.fix`), `src/turn.ts` (`mergeQueue` `:113-129` already prefers `leaf.state.merge_stamp` over `log.jsonl`, and sorts active `batch` holder `:120` and `dependentCounts` `:121` ahead of `merge_stamp`), `src/status.ts` (`TURN` automatically reflects preserved place).
- **Rejected options**:
  - *Always at the back (today)*: punishes flake and conflict victims with full queue wait (hurting Lock 1a p90/max) and compounds rebase conflicts on hot files after Q2 conflict eviction.
  - *Always at first-entry place (unbounded, including `check.fix`)*: invites head-of-line starvation / priority inversion — a leaf with an unresolved load flake or recurring test bug grabs turn 1 every cycle and stalls the whole queue behind it.
- **Evidence**:
  - `better-than-training` · framework `issues/log.jsonl` (`2026-11-14..21`, 201 merged leaves, read 2026-11-21) · 1-entry leaves (n=161) med 63.0m, p90 197.7m; >1-entry leaves (n=40) med 90.7m, p90 294.2m, max 493.0m; merge-entry counts: 161×1, 34×2, 5×3, 1×4 (cap of 2 covers 97% of leaves).
  - `better-than-training` · `issues/chart/merge-turn/forks/turn-release.md` Q3 & commit `6e7a33ff` (2026-10-19) · original reason for resetting `merge_stamp` was stacked batches, now deleted; `src/phase.ts:230` already preserves `recorded.merge_stamp` while outside `merge`.
  - `better-than-training` · `src/turn.ts:120-128` (2026-11-21) · active `batch` holder is never preempted by a returning leaf's older `merge_stamp`.
- **Pitfalls & removals**:
  - *Counter never resets after `check.fix`*: a leaf that had 2 early flakes, later fixed a real bug in `check.fix`, and hits a fresh flake would be stuck at the back. **Removal**: reset `merge_returns = 0` when `commitMove` moves to `check.fix` (since `check.fix` already pays a back-of-queue reset on re-entry).
  - *Two returning leaves with `dependentCounts === 0` tie*: `turn.ts:128` breaks ties deterministically by `merge_stamp` then `slug`.
- **Unasked question**: Does a `check.repair -> merge` return after a **rebase conflict** (mechanical git conflict, zero test fault) consume one of the 2 priority-return slots, or should conflict returns and red-verify returns share the same cap of 2 (simpler, prevents hot-file infinite loops)? ## Q5 — Red where every failing unit is an unresolved red on main

- **Pick**: **Have `land` accept it from the ledger on the first turn with NO rerun and NO new base run**, guarded by four strict conditions:
  1. Every failing command on the head finished (`setup === 0`, not blocked) with **real test titles only** — never `(script) ...`, `(unnamed)`, `(no test name)`, or `(log gone)`.
  2. Every failing test title is present on an **unresolved `main-red` base run** in `verify-runs.jsonl` (same command name & string, completed with `setup === 0`, `notice` covers as `pending`/`shown`, `baseRun.sha` is an ancestor of `built_on`).
  3. **Flake exclusion**: none of the covered test titles appears in `flakyLines` (`src/flaky.ts`, same-tree red->green flip).
  4. **Per-unit resolution**: a base-red cover for `unit.test` closes as soon as ANY later completed run on a landed main commit (`isAncestor(baseRun.sha, run.sha)` and `isAncestor(run.sha, tip)`) EITHER exits 0 on that command **OR** completes that command with real-title failures that do NOT include `unit.test` (and no nameless `(script)`/`(no test name)` crash).
  - **Reason**: **Load-bearing companion to Lock 5a** (without it, a broken main under 5a + 2a causes a queue-wide eviction storm because `check.repair` cannot run a full base suite off-line). Eliminates massive measured waste: one broken test (`skills-typecheck-switch`, 2026-11-15..17) cost **60 merge verify runs (41 head + 19 base = 10.03 verify hours)** across 13 leaves and bounced 9 leaves to `check.fix`. With Q5, leaves #2..#13 land on turn 1 (~11.5m instead of ~33m, zero extra B tokens) while strictly enforcing Lock 1a ("no leaf adds a **new** test failure to main" — any leaf adding even one uncovered failing test is still rejected and evicted). Aligns with operator 2026-10-10 precedent (`base-red/forks/red-base-policy.md`).
  - **Cost**: Keeps the accepted `base-red` precision trade-off (a second distinct bug inside the *same* already-red test title can land unseen while main is red); adds per-unit resolution + `flakyLines` filtering to `src/verify.ts` and a cover check before `handOff` in `src/land.ts`.
