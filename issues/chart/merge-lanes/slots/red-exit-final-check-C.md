# Final-shape check: red-exit (slot C)

Checked `slots/red-exit-final-shape.md` against `src/` and `forks/signposts.md` `## Taken` (2026-11-21). No misstatements of slot C's positions or dissents. Four concrete build/contract defects in the proposed shape:

1. **Item 5 (`akrogon flaky` cross-rebase flips) — cannot be computed retroactively after git GC, and false-positives on main-red fixes**:
   - *GC defect*: After an evicted leaf rebases onto a newer `main` (`applyTop` moves `refs/heads/<slug>`), the evicted red `run.sha` becomes an unreachable dangling commit and disappears on git GC; `verify-runs.jsonl` (`src/verify.ts:53-92`) stores only `sha` and `tree`. Reading "own commits unchanged" from git objects in `src/flaky.ts:106` (which scans full ledger history) will fail or miss once GC runs. The verify write path must persist a leaf-change fingerprint (e.g., `patch_id` or pre-rebase `holder.head`) on the `verify-runs.jsonl` row at run time.
   - *False-positive defect*: As written ("red on one leaf's merge run and green on that leaf's next merge run, with the leaf's own commits unchanged"), any leaf that fails on a broken `main` and passes after a fix lands on `main` has unchanged own commits and falsely logs a real `main-red` bug as a flake. Exclude units that were covered by (or resolved from) a base-red between the two runs.

2. **Item 7 (`Main-red cover`) — `requireGreenReceipt` (`src/verify.ts:428`) must accept the ledger cover, not only `land.ts`**:
   - `src/land.ts:94,102` calls `landGates` (`src/phase.ts:690` `recordTested`) and `landPush` (`src/phase.ts:761` `batchPush`), both of which call `requireGreenReceipt(repo, head, 'merge')` (`src/verify.ts:428-435`). Today `knownRedReceipt` (`src/verify.ts:195-231`) requires `run.compares === head.run && run.sha === mergeBase` (`:213`) and reads logs via `failedTests` (`:209,219`) instead of stored `entry.failures`. Item 7 must update `requireGreenReceipt` / `knownRedReceipt` (reading stored `entry.failures` first, matching `newRedUnits` at `src/verify.ts:325`, so closed/packed base runs stay cheap and reliable) or `landGates` and `landPush` will reject the covered head.

3. **Item 8 (`First observation`) — triggers wasted base runs after `check.fix` edits and on nameless mixed reds**:
   - Item 8 says "when a returning leaf's land run fails **a** named unit that its previous exit run also failed" without restricting to unchanged `check.repair` returns. A leaf returning from `check.fix` whose edit failed to fix its own bug repeats the same named unit (observed in framework `verify-runs.jsonl`, `2026-11-14..21`: `satellite-spread-copy` repeated `build gate refusal` and `scriptless-menu upgrade path` across edited runs) and would burn a wasted full base suite in the line.
   - Also, if the current run has any nameless failure (`(script)`/`(unnamed)`/`(no test name)`), `knownRedReceipt` cannot pass it even after a base run. Restrict Item 8 to: leaf returned unchanged from `check.repair` (not edited in `check.repair` or `check.fix`) AND every failing unit on the current run is a named test title, at least one repeating from the leaf's previous exit run.

4. **Item 1 + Item 4 (`exit record` missing `top`/`sha`)**:
   - Item 1 defines the exit record as `(reason, red run id or refusal text or base)` while Item 4 requires `src/phase.ts:443` (`check.repair -> merge`) to compare `HEAD` against the evicted `top` (`the red run's sha`). Including `top` (`sha`) directly in the exit record avoids scanning `verify-runs.jsonl` inside `transition` and cleanly identifies unchanged returns for Item 4 (and Item 8 if passed/checked via `verify-runs.jsonl`).
