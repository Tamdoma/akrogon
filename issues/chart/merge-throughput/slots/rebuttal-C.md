# Rebuttal C (disagreements only)

D4, hold clear on green proof (B). The proof B wants already exists at no extra cost: when main moves, the holder's restack prints `rerun` and B reruns the gate on the new base (src/phase.ts:644, merge-issue:47). A separate "green proof on the new base" before any holder is dispatched is one extra full gate run per red-main episode on the serial turn, the resource we are protecting. Auto-clear on main move, then the normal holder rerun, is the same proof one run cheaper. If the rerun is red again on the new main, the hold re-latches on the new sha, so a half-fixed main costs one run, not a cascade.

D5, count only attributable bounces (B). The command has no attribution signal. Rebase conflicts never reach check.fix: a conflicting member is restored and marked solo (src/next.ts:1179-1181), a conflicting holder is prompted solo and B resolves by hand (src/next.ts:1152-1171, merge-issue:49-55). After the hold exists, every remaining `merge -> check.fix` is by construction "gate red on the leaf's head while the same command is green on main". That is attributable to the leaf's head, including semantic drift after a clean rebase, which is the leaf's to repair anyway. "Attributable" as a separate rule can only be a B prose judgment at merge-issue:65, which is the prose-drift pitfall the map already names. Every post-hold bounce is the mechanizable rule.

D2, A's `git clean -fd` (rank 3). It does not cover the general class. Without `-x` it leaves ignored content (build caches, generated outputs, `node_modules` state) that hides failures the same way; with `-x` it deletes `node_modules` and pays `setup` on the turn like B's fresh checkout. For the one seen case (empty folders a test expected, seed 63) the framework fixed the test forward. Either option adds a per-run cost on the serial turn for a once-seen framework defect. Keep off route with a reopen condition.

Item 1, where the hold is checked. "The merge turn waits" must gate `mergeTurn` entry (src/next.ts:962, the same place pause is checked), not only `dispatchMergeLeaf` (src/next.ts:1204-1219). Otherwise the pass still builds and applies a stack, moving every member's live branch to new tips (src/next.ts:1116, 1136-1146) while nothing can run, and every member's worktree sits on a rebased head its seat did not make.

Item 4, where the split record is written. The split path saves state and prints a line but returns before any `logMove` (src/phase.ts:788-798, `committed = true` with no transition). The attempt record for a split has to be appended at that site; adding fields to `logMove` alone records nothing for splits, which are the runs seed 66 could not count.

Item 5, A's "wait for item 4 data" before touching batch size. The current first batch is the whole queue with an undefined limit (src/next.ts:1020) and the halved limit dies with the holder (src/phase.ts:154). A floor and persistence across holders need no data to justify; only the growth step does. Landing a repo-level persisted limit with a floor now and leaving the increment for data keeps A's caution without keeping the whole-queue first batch.

Missing from the map: `solo` persists only while the leaf stays in `merge` (src/phase.ts:153) and is never cleared by a successful solo rebase. Under any batch window a solo leaf costs a whole turn every time it comes up. The map's "attempt-scoped solo" (item 5) should state the clear point: on the holder's green `merged` after a solo run, or on a clean restack of that member.
