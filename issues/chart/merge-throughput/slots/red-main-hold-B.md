## Q1. When does the hold clear?

1. **Pick:** require completed green proof of the held failing command(s), with the same arguments, scope, setup and material conditions, on the current fetched main SHA. Main moving makes recovery proof eligible, not the repo healthy. Cost: one recovery proof and a durable record binding command, evidence and SHA. Keep the final full integration gate before every landing. A narrow recovery proof establishes that the held cause cleared, not that every suite is green.
2. **Reject:** clear on any main movement. An issues-only commit or an unrelated code commit can leave the defect intact. Also reject repeated automatic health checks until green: the existing lock forbids retry-until-green and new polling. Reject requiring a changed SHA in all cases: shared external conditions can recover without code moving. A named owner can explicitly request one comparable proof on the same SHA after recording the changed condition. This is a new recovery action for operator choice, not an implied automatic retry.
3. **Evidence:** operator tier, `forks/first-package.md`, Taken, read 2026-10-09: exact rejected-command proof is approved for bounce repairs, not all-leaf full gates. Better-than-training tier, `issues/chart/test-runs/forks/base-red-rule.md`, Taken: completed comparable runs, recorded shared cause, no automatic rerun of incomplete runs. `skills/check-issue/SKILL.md:61` implements this. `issues/chart/merge-turn/forks/issues-only.md`, Taken: record-only main commits need not change tested code. Practitioner tier, Martin Fowler, [Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html), published 2024-01-18, read 2026-10-09: health follows a reference-environment build, and broken main requires repair priority. This supports proof rather than movement as the release condition.
4. **Pitfalls and removal:** stale proof → clear only under a lock after confirming remote SHA still equals proved SHA. Main moves during proof → keep the hold and report the unproved new SHA, never claim recovery. Flaky base → completed exits alone do not prove shared cause or remove flakiness, so record the causal judgment and use the explicit owner-led recovery action. Manual repo pause → clearing health must never clear the operator's pause or automatically bypass it. Recovery remains visible until an allowed dispatch occurs.
5. **Missing question:** does an existing unrelated main change trigger one owner recovery prompt through an existing dispatch event, or does the owner explicitly request every proof? Pick one event-driven prompt per newly observed SHA, persisted to survive repeated events, plus explicit same-SHA recovery. No new timer. This prompt is for proof only, not a full gate for every waiting leaf.

## Q2. Who repairs main, and how does the repair pass the hold?

1. **Pick:** the operator names one new fix leaf for a code defect, or themselves for an external/configuration recovery. Record that owner in the hold. The named fix leaf alone may take a solo merge attempt through the health hold, with the normal complete final gate and exact tested-top push guards. Other leaves stay in merge without repair counts, queue-stamp changes or prompts. Cost: an attended ownership step and a narrowly scoped repair override in holder selection AND phase authorization. The first detector names the blocker and exact next action. It does not silently acquire a second implementation scope.
2. **Reject:** freezing every automatic repo action. That repurposes repo-pause and can stop the fix leaf from reaching merge. Reject automatic repair by an arbitrary holder B: applied-stack B cannot commit, and a defect in delivered work is locked to a new fix leaf. Reject automatic reopening of delivered leaves or automatic batch revert. Reverting can be the operator's chosen new fix, but the command lacks authority to undo multiple completion owners. Reject a repair override that skips tests or carries unrelated leaves.
3. **Evidence:** operator tier, `issues/chart/failed-leaf-routing/forks/fix-routing.md`, Taken, read 2026-10-09: operator charts the fix, merged work remains terminal, new leaf over reopen. `issues/chart/repo-pause/forks/boundary.md`, Taken: operator pause freezes automatic paths but manual commands run and never clear it. Better-than-training tier, `skills/merge-issue/SKILL.md:41` forbids applied-stack commits, while `:55` allows fix-forward in solo form. The fork must reconcile that default-branch sentence with the dedicated fix-owner route explicitly. `src/phase.ts:770-783` recomputes FIFO holder before checking attempt identity, so selection-only bypass would still reject the fix leaf. Practitioner tier, Chromium infrastructure team, [CQ documentation](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/infra/cq.md), read 2026-10-09: tree closure has a narrowly justified repair bypass. Its test-skipping/revert options are not adopted here.
4. **Pitfalls and removal:** hold created with a carried batch → restore members and holder to saved heads, invalidate the attempt, and stop its stale seat from pushing before admitting the repair. Do not halve the batch window for a base-attributed failure. Deadlocked override → authorize the same named owner in dispatch and phase calls, bypass only health and normal queue position, retain dependencies, readiness, operator pause and tested-top guards. Repair owner fails → keep hold and expose the exact blocker for operator reassignment. Stale repair nomination → bind owner to the hold generation/base and reject departed owners. Restart → persist hold, nomination and proof state.
5. **Missing question:** who may nominate, replace and cancel the owner? Pick explicit operator commands, with owner slug and hold identifier, not arbitrary seat nomination. Also decide what happens to leaves already failed before the feature lands. Pick no automatic revival: operator selects those whose recorded blocker is this repaired base, then recovery rebases and verifies them. Preventing future bounces does not itself recover old failed stock.

## Q3. Who judges the base comparison?

1. **Pick:** B judges whether the base failure explains the candidate failure. The command mechanically validates required evidence references, completed results, command identity, base/candidate SHAs and current attempt, then owns the hold and its routing. Cost: one comparable base run for an unexplained gate failure plus recorded causal reasoning. Attempted comparison uses the actual failed candidate's integration base first. Fetching newer main must not silently replace that base: record both SHAs, and prove the currently fetched main before holding that current SHA if it differs.
2. **Reject:** automatic attribution from two nonzero exits or matching test names. Shared names can have different causes, and different names can share one cause. Reject comparing every red run indiscriminately: first inspect whether the diff plausibly causes it, using the existing judgment trigger. Reject parsing agent prose for exact verdict words. Reject routing incomplete execution as proven base failure. The locked incomplete-run stop remains explicit unless separately reopened.
3. **Evidence:** better-than-training tier, `skills/check-issue/SKILL.md:61`, read 2026-10-09: causal judgment is never automatic, same command/args/scope/setup/conditions, own exit status and terminal result, names need not match. `src/state.ts:43-49` already stores attempt, built_on and tested_main. `src/phase.ts:781-784` rejects stale attempt IDs. Practitioner tier, Chromium CQ team, same source/date as Q2: repeats exact configurations and compares with/without patch. It warns that isolated reruns can behave differently. Its policy permits unrelated base failures to be ignored, which conflicts with Akrogon's green final gate. Adopt comparison discipline, not permission to land red.
4. **Pitfalls and removal:** both base and leaf have independent defects → B records all observed causes, hold main only for the shared base cause, preserve leaf findings for repair after recovery. Added leaf defects must still fail its final gate. Batch failure before splitting → compare base first where the judgment trigger applies, so proven BASE neither splits innocent members nor spends their budgets. Evidence refers to future main → bind every result to the SHA actually run. Machine/environment errors → distinguish incomplete execution from completed test failure, without inventing a base-code defect.
5. **Missing question:** what is the command's evidence boundary? Pick schema-validated result records with exit status, terminal completion, exact invocation, base/head SHAs, log paths and B's causal finding. Mechanical validation proves completeness/identity, not that the causal finding is correct or that a seat truly ran a command. A full check runner would be separate scope. This separation also matters to the next bounce-counting fork: a hold filters proven base failures, not every infrastructure failure.

## Does this increase merging speed?

Yes, when a broken main would otherwise reject more queued leaves and the named repair happens promptly. It saves repeat failed gates and keeps innocent leaves out of repair. It does not shorten a healthy gate, increase parallel merge turns, or make leaves land while main remains broken. If nobody owns repair, a hold saves compute but leaves throughput at zero.

Measured evidence, read 2026-10-09: framework `issues/log.jsonl`, records from 2026-10-07 through 2026-10-09T11:25:11.219Z, contains 54 merge completions and 46 merge-to-check.fix transitions. These are phase exits, not gate attempts or timed runs. Deliverable-obligations bounced at 02:16:53 (`:2144`), stopped twice on the same old base (`:2145,2155`), and re-entered at 03:08:37 (`:2163`). That is about 50 and 52 minutes off the merge queue respectively, not measured test runtime or guaranteed savings. Deliverable then bounced again (`:2172`), so recovery from the base alone does not establish leaf correctness.

The intake's 9 BASE bounces out of 34 are unverified classification, not a demonstrated percentage throughput gain. Current log lacks gate start/end and split history (`src/log.ts:9-22`, `src/phase.ts:788-799`), so no honest merges-per-hour uplift can be computed for the proposed hold. The net change depends on failed runs avoided minus comparison/recovery costs, plus repair delay and batch yield. Confirm it with durable attempt records and landed leaves per elapsed hour, retaining failures and main regressions. Do not use time actively testing as the only denominator, because the hold introduces waiting.
