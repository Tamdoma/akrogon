# Env source: independent round B

This round settles how a leaf worktree uses the registered checkout's env without copying secrets or changing existing consumer commands. Reading through an alias and saving a newly produced key are separate operations. The taken key-creation 2a requires the latter to update the declared repo's file.

### 1 · Should each leaf worktree have an env symlink, receive only the registered root path, or use another loading mechanism?

Today `ensureWorktree` creates a plain Git worktree (`src/next.ts:242-273`), and seats start there (`src/next.ts:343-353`). Framework's `readSecret` reads `process.env`, not an env file. Giving a seat a root path therefore does not, by itself, make existing scripts or checks see the values.

Research: operator · [intake](../INTAKE.md) and taken [readiness-contract](../forks/readiness-contract.md), [key-creation](../forks/key-creation.md), [key-sheet](../forks/key-sheet.md), read 2026-10-02 · Inputs have declared holding repos, operator inputs arrive before proofs, and a producing leaf stores only its authorized named value in the declared repo's env. These locks require shared storage and repo-specific destinations, without choosing a file-loading mechanism.

- **1a (recommended): link for loading, canonical path for writes.** At worktree preparation, create an ignored `.env` symlink to that repo's declared canonical env source. Also give the seat the registered root and declared destinations as non-secret context. Existing Bun commands run from the worktree can load the shared file. A producing leaf saves its key at the declared canonical destination, never by replacing the alias. This keeps one file and avoids changing every consumer entry point.
- **1b: canonical path only.** Supply the registered root and require each secret-consuming command to load the declared source explicitly, for example through the documented Bun env-file flag. No worktree alias exists. This makes source selection explicit, but needs all checks, scripts and transitive launchers to honor it. A path in a prompt is insufficient for `readSecret`, and a framework-wide source must not be applied to client processes. Choose this if implicit loading is unacceptable and the consumer command surface can be made consistently explicit.
- **1c: a dedicated env-aware runner.** A command wrapper selects the declared repo source and starts each consumer with it. This could centralize loading and persistence, but introduces another command surface that existing scripts and checks must consistently use. It solves no demonstrated need beyond 1a and risks becoming the broker the standing design rejects.

Copies, hardlinks and secret values injected into the seat's tab environment are not recommended alternatives. Copies drift, hardlinks do not follow atomic file replacement, and tab injection creates a long-lived snapshot with broad inheritance. Copying and tab injection are already excluded by this fork's Carries.

Pitfalls: a symlink provides a loading path, not proof of presence, authority or permission. It also provides access to the shared file, so write authorization must remain restricted to the named producer output. Linking the framework source does not supply per-client inputs.

Reply `1a`, `1b`, `1c`, or give a different mechanism. This round recommends a choice and does not record one as taken.

## Proposed behavior under 1a

1. Resolve the registered checkout using akrogon's existing repo identity. `src/config.ts:100-119` matches shared Git common directories against registered roots and rejects multiple matches. Use that root, rather than guessing the first entry in `git worktree list` or deriving it from directory depth.
2. Prepare the link before seat launch, for newly created and reused worktrees. Validate that an existing entry is the expected link. Refuse a regular file, a tracked path, an unrelated link or an unignored alias rather than replacing it with `ln -sf`. Check the canonical destination's ignore and tracked status too. This is setup validation, not an alternative source fallback.
3. Keep the source path explicit in the contract and seat context. The local alias is for that worktree's own repository. Inputs held by another client repo keep that client's destination. The registered root path contains no secret value and can appear in instructions and status.
4. Preserve the locks' timing. Operator-supplied inputs are completed during charting before real-identity proofs. Dispatch checks the declared sources for missing or empty inputs. A dangling alias cannot count as readiness. A future producer output remains declared as produced by that leaf, and its dependent's handoff waits for delivery and proof as key-sheet requires. Creating a link must not manufacture an empty source file to appear ready.
5. Save a produced key only at its authorized canonical destination. The implementation must preserve unrelated entries and file permissions, avoid lost updates from concurrent writers, never echo the value, and revoke the newly produced key if saving fails. Atomic replacement must target the canonical file, with the temporary file beside that target. The symlink continues pointing at the same pathname after replacement.
6. On removal, remove the worktree and its alias, never the resolved source. Existing cleanup uses `git worktree remove --force` (`src/next.ts:610-616`). Do not add a cleanup operation that resolves the alias and deletes its target. A moved registered checkout needs explicit reconciliation of its links and contract paths.

These are implementation requirements for the proposed choice, not changes made by this round.

## Pitfalls and security exposure

- **Shared authority:** every seat and ordinary Bun process that can read the linked source can receive its contents. A symlink is neither a sandbox nor narrower credential authority. The contract authorizes operations and writes, but it does not technically hide unrelated credentials in the same source. This exposure also exists with explicit full-file loading under 1b.
- **Producer writes versus existing rules:** `skills/implement-issue/SKILL.md:45`, `skills/check-issue/SKILL.md:31` and `skills/merge-issue/SKILL.md:29` currently prohibit env writes. Taken 2a requires a narrow authorized producer-write exception and a permitted implementation mechanism. A link cannot resolve this conflict. Do not silently change deny rules or route around a deny to implement that exception.
- **Effective identity:** a shared file does not mean a shared process snapshot. Existing processes retain loaded values. Fresh consumers after a producer's save must use the correct source without stale inherited credentials. Mode/local overlays can also change effective values. Real-identity proofs must exercise the relevant launch path.
- **Per-client destinations:** the same variable name can refer to different clients' keys. Keep each holding repo, identity and target distinct. Preserve the fleet's stripped child environment. Do not aggregate client secrets into the framework source or link client paths to it.
- **Output exposure:** secret-env redacts values registered through its helpers. It does not register every automatically loaded variable. A generic environment dump, raw headers or unregistered value logging can leak secrets despite using the library. Emit only result and presence information.
- **Ignore and lifetime:** ignoring an alias does not protect a tracked canonical source. Cleanup must unlink the alias without deleting the source. Source removal or rotation can still invalidate later operations, so dispatch presence is not a durable guarantee of scope or validity.

## Challenge check and limits

The strongest challenge to 1a is implicit exposure: existing Bun commands can load all credentials in the shared file, and a seat capable of writing that source can damage more than its authorized key. If the operator requires technical per-seat secret isolation, neither 1a nor full-file 1b meets it. That would reshape the standing storage design rather than justify a hidden wrapper here.

Under the taken shared-env design, 1a removes cwd-related false absence with fewer changes than making every consumer honor a new loader. Canonical-path writes and per-client source selection remain mandatory. Before handoff, the actual launcher and checks still need the existing required operation proofs. A synthetic non-secret symlink can test alias writes, deny matching, ignore status and removal without opening a real env file. No runtime experiment or env read was performed in this round.
