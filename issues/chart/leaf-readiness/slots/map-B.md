## Material forks, in reshaping order

Recommendations are proposals, not taken decisions. The fixed `.env`/no-vault standing design is not reopened.

1. **D1. Should readiness remain an attended chart audit, or become a structured contract that dispatch also validates?** O1: strengthen the existing semantic handoff audit only. O2: add one minimal non-secret prerequisite contract consumed by that audit and dispatch. O3: rediscover readiness at each lifecycle phase. **Recommend O2** if the requested outcome includes prevention at dispatch: declared env names and source repo, required local inputs, named identities/targets, operation-proof references, and scoped authorization are checked together before seat work. The agent judges whether the inventory and proofs cover the actual flow; code checks valid state, supplied inputs and referenced evidence, never exact prose. No provider plugin framework and no provider admin token in akrogon. O1 is smallest but the same rule already failed here. O3 recreates scattered checks. Requirements produced by a dependency must name that producer instead of being demanded before it exists. Changed identity, target or operation invalidates the affected proof. Revocation, external outages and newly discovered behavior remain possible after any check.
2. **D2. How should all seats reach the same env source: explicit registered-root path, worktree symlink, copied files, or wholesale harness environment injection?** **Recommend explicit registered-root path** supplied as non-secret dispatch/config context and used for checks and operation processes. Reuse common-directory registration. Resolve required registry/fixture paths explicitly too; do not silently run branch code against arbitrary main-checkout code. Keep per-client secrets in that client's own env. Symlinks create write-through paths, copies create stale secret stores, and harness injection exposes every loaded value to every child for the session. A path creates none of those copies and leaves operation loading explicit.
3. **D3. Who provisions credentials that do not exist yet: an operator batch before handoff, or agents using already-held creation authority?** **Recommend agent provisioning where a scoped existing identity can create the required credential, with quiet persistence to the correct consumer `.env`; otherwise one complete operator batch before handoff.** This requires an explicit write-policy decision: the standing acceptance authorizes reads, not unrestricted env edits, and phase skills currently forbid writes. Never add token-provisioning authority just to make an unrelated seat autonomous. A dashboard-only first grant stays operator-owned. Provider secrets returned once must go directly to the authorized file, not chat/artifacts. Prove creation, use and revocation with that same identity. Reject a general credential broker and broad admin bootstrap token.
4. **D4. What does up-front live authorization cover: named account/zone/repo operations plus cleanup, or blanket permission for the epic?** **Recommend named operations and targets, including fixture creation and cleanup, in one attended batch.** A provider credential grants capability, not operator consent. Keep production scope separate from throwaway proof targets. New targets or materially different mutations need new authorization. This removes repeated approval of already-authorized work without turning every future live change into an accepted action.
5. **D5. How should retained proof resources be handled: disposable isolated fixtures with complete teardown authority, or approved retained resources with named ownership and expiry?** **Recommend disposable fixtures by default**, created and deleted with the same sufficient scoped identity. For a genuine retention proof, choose an isolated test bucket where lock removal is explicitly authorized, or an explicitly retained bucket with cleanup owner/date. Never relax a real backup lock for test convenience. Existing operation-proof rules require checked cleanup; a known retained resource must be resolved against that rule before handoff, not called “cleaned up.” Account/token expansion is not the default answer to a mistaken fixture owner.

## Security result and limits

- **R1. Preserve one secret store per actual consumer repo.** Explicit paths expose no secret values in state/prompts, avoid copied credentials and avoid session-wide injection. Operation processes still have secret access already accepted by standing design. No same-user design here creates OS containment or prevents trusted branch code from reading the root file.
- **R2. Preserve authority boundaries.** Scoped existing identities, exact authorized targets, and create/use/delete proof remove predictable credential/scope/cleanup surprises without broadening provider grants. Autonomous minting can broaden authority through a provisioning credential; use it only when already available and explicitly authorized. Never claim a readiness marker proves current scopes indefinitely.
- **R3. Preserve confidentiality of evidence.** Store variable names, identity references, operation results and redacted failure reasons, never token values, authenticated headers, env dumps or secrets in exception bodies. Agent read acceptance does not authorize printing, committing or transmitting credentials. Removing global protection for unrelated repositories or loosening production retention would widen exposure and is not recommended.

Recommended direction: make the existing pre-handoff rule complete and reviewable, give seats one explicit env source, and validate declared readiness before dispatch. Keep provisioning and mutation authority scoped, then record unexpected failures through the failure state that already exists.
