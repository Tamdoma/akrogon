# Key creation: disagreement-only rebuttal B

1. **R1. A’s reason for rejecting 1b does not establish that 1a is the general answer.** The operator’s correction requires every need to be known up front. Both options satisfy that. B permits issuance only from an already-held credential whose full authority is explicitly approved, and does not recommend adding a broader creating credential to remove a smaller prerequisite gap. A’s exposure objection is a valid reason to reject a particular parent credential, but does not distinguish using an already-approved parent from keeping that same parent under 1a. The short-lived case also changes the feasibility of “one batch before handoff”: GitHub installation tokens expire after one hour, while the signing private key can issue tokens for every installation and does not expire automatically. B therefore treats the durable issuer as the declared prerequisite and the short-lived token as a declared output produced when needed. This is a conditional contract rule, not a proposal to introduce GitHub Apps or issuance machinery without a current need. **Evidence:** B options 1b/1c, S10 and P3; [GitHub installation-token documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), [GitHub private-key documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps), consulted 2026-10-02. Keep 1b conditional on approving the parent’s entire reach and declaring the need before handoff.

2. **R2. Q2 adds an implementation requirement that B did not recommend.** “B P4 compatible” is accurate for a declared destination and a write that preserves unrelated values. It does not support requiring “one akrogon command” to persist the secret. B P4 requires an explicit credential-write policy, the exact declared consumer env destination, no unrelated rewrites, and cleanup if creation succeeds but persistence fails. The provider-neutral question should decide who creates and stores a declared leaf output, with those constraints. Choosing a new akrogon writer is a separate implementation decision. The merge also omits explicit write authorization and the failed-persistence cleanup case. **Evidence:** B P4 and the taken readiness contract’s separation of declared producer outputs from pre-existing dispatch inputs. Knowing that a leaf produces a key does not itself authorize every agent to mutate the holding repo’s env.

3. **R3. The merged contract description drops the proof required to establish that a credential is usable.** Listing its name, permissions, source and holding repo is necessary, but does not prove its actual identity, target or permitted operation. A nonempty value can still be expired, tied to the wrong account or repository, or unable to perform cleanup. B requires the chosen provider operation to be proved with the real credential against the exact target, including cleanup, before claiming readiness. Akrogon checks the declared evidence and input presence without making live provider calls. For a declared producer output, the producer must establish that proof before its dependents proceed. **Evidence:** the taken readiness-contract lock requires live grants and identity/target proofs; B S2, P3 and its final evidence boundary. Restore those requirements alongside the key inventory and produced-by relationship.
