# Key creation: independent round B

Research date: 2026-10-02. Read intake, key-creation Question/Carries, and the taken readiness-contract lock. No other slot files read. No env file opened, printed or written. Public documentation only, no authenticated provider calls.

## Question and carries

Q1. Who creates an API key that a leaf needs but does not exist yet: the operator in one batch before handoff, or an agent using an already-held key that can create keys, writing the new key into the consumer `.env`?

Carries: readiness-contract 1a is taken. The door records env names/source repo, required files, granted live changes and proofs tied to identity/target. `next` checks readiness, `status` lists gaps, and akrogon makes no live calls. Every secret stays in the consumer's gitignored `.env`, with no vault/broker. Standing acceptance of agent reads does not settle credential writes. Intake expressly includes creating/providing keys.

## Options and recommendation

- **1a. Operator creates every missing credential in one batch.** The door supplies exact provider, principal, account/repo, permissions, lifetime, env variable and obtaining steps before handoff. Seats consume credentials and cannot create them. Smallest policy change and no provisioner secret added to agent-readable storage. Downside: it also prevents routine renewal of API-minted short-lived credentials without an explicit exception.
- **1b. Agents create any needed credential whenever an existing credential can do it.** No new bootstrap authority is granted, but possession of an existing provisioner is enough to permit issuance and writing. Removes some operator work. Reject as a default: possession is not authorization, the provisioner can exceed the leaf's intended scope, and an existing GitHub PAT cannot mint another PAT through the current GitHub.com API.
- **1c. Operator owns bootstrap; agents issue credentials only under an explicit existing grant. Recommended.** Missing durable credentials and absent provider creation authority are one operator batch before handoff. An agent may issue a credential only when the door records the existing provisioner identity, its full reachable authority, permitted child permissions/resources/lifetime, exact env destination, and cleanup/revocation authorization. No automatic addition of token-management permissions or GitHub App setup. The policy permits a narrowly reviewed existing GitHub App's routine installation-token issuance without treating every new provider grant as agent-owned.

Reason: the two providers have different creation mechanisms. Separate granting authority from exercising authority already granted. This preserves the taken readiness gate and avoids placing a new, more powerful credential in `.env` simply to remove a smaller credential gap. “Already held” is insufficient if its full reach includes unrelated accounts, repositories or production capabilities. Where that reach is outside approved scope, use 1a for that credential. No evidence in this round establishes what provisioners are currently held.

## Provider findings

| Provider/credential | API creation and creating authority | Exposure from holding the creator |
|---|---|---|
| Cloudflare user API token | `POST /user/tokens`, accepted permission `API Tokens Write`. Dashboard terminology is User > API Tokens > Edit, obtained through the Create additional tokens template. An ordinary Workers/DNS token is not automatically a token creator. | Can issue additional access grants, not merely use the one child intended by the leaf. User-owned access is bounded by the owning user's authority. The inspected docs do not establish that a proposed child's narrow resource policy caps the creating credential's issuance power. Treat the entire allowed issuance surface as exposed until verified. |
| Cloudflare account API token | `POST /accounts/{account_id}/tokens`, accepted permission `Account API Tokens Write`. Current dashboard docs require Super Administrator or API Token Provisioning capability and say account members may grant only a subset of their own account permissions. | Account-bound provisioner authority is distinct from leaf product permissions. Creating a narrow child does not remove the parent from agent-readable `.env`. Account tokens persist independently of the creating member. Verify actual issuance and token-management limits, not just the child's scope. |
| GitHub personal access token | Current GitHub.com documentation uses account settings to create PATs. No supported PAT-to-PAT creation endpoint was found. The old password-authenticated `/authorizations` API was removed in 2020. Pre-filled creation URLs reduce operator typing but still require human generation and possibly organization approval. | There is no documented “PAT minting PAT” authority to give an agent. A classic PAT can expose broadly accessible repositories through its scopes. A fine-grained PAT narrows owner, repositories and permissions. Creating another token does not create account membership or bypass organization controls. |
| GitHub App installation access token | `POST /app/installations/{installation_id}/access_tokens`, authenticated by an app JWT signed with the app private key. The app must already be registered, granted permissions and installed on the target. Request `repositories`/`repository_ids` and `permissions` to reduce access; omitted restrictions inherit installation access. Tokens expire after one hour. | The private key can authenticate the app across all its installations. Narrowing one token request does not narrow possession of that private key. It does not expire automatically. Theft permits repeated issuance until the private key is revoked. An app client secret alone is not the signing key for installation tokens. |

GitHub OAuth/user-token exchanges are another flow, with prior user authorization and appropriate app credentials. They are not general PAT creation and do not eliminate the initial consent boundary. A read token for one owner also cannot clean up a fixture under another owner. Credential type, principal and target must remain explicit.

- **S10 · better-than-training ·** [Generate installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), inspected 2026-10-02. Finding: signed JWT, existing installation, bounded requested permissions/repositories, one-hour expiry. Sign-only vault storage is stronger than environment storage. Practitioner synthesis: Cloudflare's token designers and GitHub's integration practitioners favor narrow service identities, limited resources and independent rotation. GitHub Apps support safe short-lived issuance only when the app's total authority and signing-key handling are appropriate. Their advice does not justify an unrestricted provisioner in a shared env. 1c adopts their scope/identity recommendations while retaining this project's storage lock and avoiding an unsolicited authentication migration.

## Pitfalls and security exposure

- **P1. Creator scope is the critical boundary.** The narrowest child token does not reduce a provisioner already accessible to seats. A command wrapper or “door only” instruction also does not isolate a parent secret held in the same readable env. 1b exposes that full parent reach. 1c is eligible only when that reach is itself approved. Do not call a proposed Cloudflare child-policy restriction an enforced parent ceiling without evidence.
- **P2. No credential creates missing human authority.** Cloudflare's first provisioning grant and GitHub's app registration/installation, PAT generation or organization approval may need the operator. Complete those before opening a leaf. The planned batch must include transitive fixture creation and cleanup permissions as well as the leaf's direct API calls.
- **P3. Expiry changes what readiness means.** An installation token minted at chart time may expire before dispatch or during a long proof. Record the durable approved app identity and its issuance prerequisite, then obtain the derived token when needed through the authorized agent operation. The contract names the credential producer. `next` still makes no live calls. A non-empty expired token is not proof of readiness for a live operation.
- **P4. Persistence requires a taken write rule.** If 1c is selected, permit only the named newly issued value to be persisted to the correct consumer's gitignored env, without printing it or rewriting unrelated credentials. Existing phase prohibitions must be reconciled explicitly. Root env access does not authorize writing a client's token into the framework env. Failed persistence must report the error and resolve the newly created provider token, rather than leave an untracked grant.
- **P5. Keep secrets out of proof and failure artifacts.** Token-creation response bodies contain credentials. Record provider IDs, identity/target, permissions, expiry, result and revocation/read-back evidence. Redact secrets from body/error logging. 1a keeps additional creation authority out of agent storage, but its supplied operational tokens remain readable under the standing design.

## Evidence boundary and next proof

This round proves documented mechanisms and security consequences, not that any existing identity can create an intended token. No env names or values were inspected and no provider resource was changed. There is no claim of handoff readiness.

Before handoff under 1c, the chosen provider/credential path needs its required real creation, intended-use and revocation proof with the actual provisioner, smallest approved target and recorded limits. For Cloudflare, verify the accepted child grant and the actual issuance ceiling. For a GitHub App, verify installation/repository permissions and cleanup capability, including the incident's repo-deletion operation if needed. A refused or impossible sufficient probe holds that handoff. The operator answers this fork first; a provider migration or new creating authority is not implied by selecting the readiness contract.
