### 1 · Should proof fixtures be disposable by default, with their full cleanup proven using the declared leaf identities before handoff?

In the consumer, a private GitHub fixture was invisible to the registry token and undeletable by the `gh` login, while an R2 bucket reported empty later proved to contain 32 objects (`emdash-launch/implementation/report.md:72–73,243–247`). The same report later records successful object-first deletion and authenticated absence checks, and deletion of the old personal repo through existing authorized credentials rather than added scope (`:313–315`). Gruntwork recommends separate test accounts and nightly sweeping there, but this recommendation does not introduce a broad sweeper into the consumer's live accounts.

Research: operator · `issues/chart/leaf-readiness/INTAKE.md`, P7/I7/I12, read 2026-10-02 · cleanup was a repeated prerequisite failure, making disposal capability part of readiness. Practitioner · Gruntwork's Terratest maintainers, who run real infrastructure tests and describe their own nightly test-account cleanup, [Cleanup](https://terratest.gruntwork.io/docs/testing-best-practices/cleanup/) and [Testing environment](https://terratest.gruntwork.io/docs/testing-best-practices/testing-environment/), read 2026-10-02 · cleanup must run after errors, and broad sweeping assumes isolation, making bounded leaf-owned recovery the recommendation here. Better-than-training · `skills/chart-issues/SKILL.md:53–55`, `src/state.ts:35–58`, `src/next.ts:614–621`, and [GitHub repository deletion](https://docs.github.com/en/rest/repos/repos#delete-a-repository), read 2026-10-02 · operation proof already includes cleanup, state has no fixture contract, akrogon's existing cleanup removes local worktrees rather than cloud resources, and GitHub deletion needs admin access plus the appropriate token permissions, making explicit proof references necessary rather than a new cloud executor.

- **1a (recommended)** Treat each fixture as disposable unless question 2 explicitly retains it. Before creation, the readiness contract names its cleanup sequence, required inputs, verified identity and account for each operation, and authenticated read-back that will prove absence. Use the creating identity for cleanup by default. If the provider requires different identities, declare and prove every one before handoff rather than discovering an operator-only cleanup step later. Include transitive resources, contents and configuration changes, not just the top-level resource. The door proves the smallest representative create/use/delete cycle with the identities the leaf will use and records the limits of that proof. Each live pass records created IDs under the existing grant and attempts safe cleanup on both success and failure. Deletion results plus authenticated absence checks are required before claiming cleanup. Unremoved disposable resources remain a blocker with exact IDs, error, owner and next action in the pass artifact. Recovery stays within the taken grant and phase ownership. This wins because creation access alone repeatedly failed to supply disposal access.
- **1b** Default to operator cleanup after the proof. List the resources and operator steps up front and record actual deletion and absence evidence before claiming cleanup. This can keep delete permission off the leaf's credential, but repeats the operator dependency from I7/I12 and cannot replace the existing pre-handoff operation-proof requirement.

Pitfalls: Create success, a delete exit code, an incomplete listing or a private-resource 404 without authenticated visibility proves too little, so absence checks must cover the actual account, pagination and child resources. An interrupted seat cannot guarantee disposal, so preserve its IDs and both proof and cleanup errors for authorized recovery without unplanned credential expansion or resource transfers.

### 2 · May a fixture remain after its proof only when its owner, deadline and eventual cleanup are agreed before creation, while real backup protections stay intact?

Gruntwork permits keeping infrastructure between local validation runs by preserving stage outputs, so immediate deletion after every invocation would prevent useful reuse ([Iterating locally using test stages](https://terratest.gruntwork.io/docs/testing-best-practices/iterating-locally-using-test-stages/)). The consumer fleet proof deliberately left a backup bucket under a 30-day lock, listed fixture credentials missing from the client checkout, and warned that Wrangler's apparent delete success did not prove deletion (`emdash-fleet-backup/implementation/report.md:49,59–62,75,109,143–145`). A retained fixture therefore needs both an agreed lifetime and a usable cleanup route, and its environment must match the actual client child process rather than a temporary service override.

Research: operator · intake I12 and the taken `key-sheet.md`, `env-source.md` and `live-change-grant.md`, read 2026-10-02 · inputs, target ownership and consent must be settled before proof, making retention an up-front fixture choice. Practitioner · Gruntwork's Terratest team, [Iterating locally using test stages](https://terratest.gruntwork.io/docs/testing-best-practices/iterating-locally-using-test-stages/), read 2026-10-02 · saved IDs support repeated validation without redeployment, making bounded retention a legitimate exception. Better-than-training · consumer `emdash-fleet-backup/implementation/report.md:49,59–62,75,109,143–145` and Cloudflare [Bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/) and [Delete buckets](https://developers.cloudflare.com/r2/buckets/delete-buckets/), read 2026-10-02 · locks outrank object expiration and current R2 emptying requires removing lock rules, making an expiry date insufficient evidence that a bucket will disappear.

- **2a (recommended)** Allow deliberate retention only when the contract names the purpose, resource set, named owner who accepts responsibility, review or deletion date, cost and exposure, required inputs, cleanup identity and sequence, and which proof needs the resource alive. The pass artifact records actual IDs and separately labels resources retained by agreement and disposable resources still awaiting deletion. Stop temporary jobs and other ongoing effects when their proof ends unless continued operation is expressly needed. Never weaken a real backup's lock or retention to make cleanup pass. A separate test fixture may use shorter retention only when the property under test permits it, with that limitation stated. If the proof requires the real retention duration, keep that duration and agree its eventual disposal route, including any test-only lock-rule removal after retention expires. An agreed retained resource does not satisfy a criterion requiring deletion, and neither retention nor a shorter test lock waives the door's required operation proofs. If no safe sufficient proof exists, hold the affected handoff. This wins because it supports necessary reuse and protected-data tests without disguising residue as successful cleanup.
- **2b** Allow no retention exception. Every fixture must be deleted before its proof can close. This minimizes outstanding resources, but a real retention test holds the affected work until lawful cleanup is possible. It does not justify shortening a required retention period or weakening a real backup lock.

Pitfalls: A date does not delete anything, so the named owner needs valid recovery access and grant lifetime, or an explicit later human action agreed before creation. Unexpected cleanup failure cannot become approved retention after the fact, and the fixture client's missing inputs and denied credential writes remain in the open `blocker-record` fork.
