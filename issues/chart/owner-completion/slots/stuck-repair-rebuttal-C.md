# Rebuttal, slot C: stuck-repair

R1. Point held, order of source closing: close #282/#285 after the move and pack, not first (B). Closing a GitHub source posts the `delivered by pool-parity` comment and is the one outward-facing, effectively irreversible step; reopening after a failed local repair is noise on the source. Every local step before it is rerunnable and inspectable in the framework tree, so GitHub should only be told "delivered" once the local completion is verified (pack done, sample logs read back, status clean). If the close then fails, say GitHub is down, the remaining work is exactly two rerunnable `akrogon close` commands and nothing local is half-done. B's stop-on-failure benefit buys little: a failed close first still leaves the surgery undone, and a successful close first spends the irreversible step before the risky one.

R2. Disagreement on the mid-move interruption removal: no manifest or byte comparisons (B). The git index is already the manifest. `git mv` stages each tracked rename as it goes and renames the directory on disk, carrying the git-ignored loose logs with it (verified in a scratch repo, 2026-10-19), so after any interruption `git status` and the surviving open folder show exactly which of the six folders moved and which did not. Byte safety is also already covered downstream: `packFolder` refuses differing bytes for a shared archive member and reads every packed member back through `locate`/`readMember` before unlinking a loose log. A hand-kept manifest duplicates both records for a six-folder move.
