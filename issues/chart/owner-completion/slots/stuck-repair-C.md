# Blind notes, slot C: stuck-repair

Question: How does the one stuck framework twin (open satellite-plan-fit, 6 merged leaves, GitHub #282 and #285 still open) get finished: move its leaves into the closed satellite-plan-fit once, or rename it and rewrite its recorded log paths?

## 1. Pick

Move the wave-2 leaves into `issues/closed/satellite-plan-fit` once, as a door step on framework main, using only commands that exist today. No rename, no recorded-path rewrite, no dependency on the two code leaves landing.

Steps, in order:

1. Recheck preconditions: all 6 open leaves `phase: merged`, no `.closing` marker, child-folder overlap with the closed owner is `EPIC.md` only, no framework `next`/merge run active.
2. `git mv` the six child folders (replay-cases, hub-child-links, dilutor-fit, neutral-identities, pool-parity, persona-text-bounds) into `issues/closed/satellite-plan-fit/`. Append the wave-2 entries to the closed `EPIC.md`, drop the wave-2 line "Earlier leaves page-draw-preview and brand-override are closed", delete the open `EPIC.md`, and remove the now-empty open owner folder.
3. Run `akrogon pack issues/closed/satellite-plan-fit`. This folds the 708 loose wave-2 logs into the existing `evidence.tar.zst` (89 wave-1 members today, 0 name overlap with wave-2 logs) and verifies every member through `locate`/`readMember` before unlinking any loose log.
4. Verify locally: `akrogon log` returns bytes for one recorded wave-1 path and one recorded wave-2 path taken from `issues/timings.jsonl`; `akrogon status` shows no open satellite-plan-fit leaves and no `Unpacked:` line for it.
5. Close the two open sources with the existing command, which posts exactly the locked witness: `akrogon close Tamdoma/tamdoma-framework#282 --by pool-parity` and the same for #285. Verify both CLOSED with `gh issue view`.
6. Commit on framework main staging only the satellite paths (moved folders, merged `EPIC.md`, rewritten archive, deleted open folder). The framework tree is dirty with other charts' work, including `issues/timings.jsonl` and `issues/verify-runs.jsonl`; this route never touches those files.

Reason: the owner name never changes, so every recorded log path in both waves stays true and both waves become readable again (wave-1 archived logs are unreadable today, see evidence). The two risky operations, GitHub closure and archive union, run through existing tested commands instead of hand work. The only manual parts are moving six disjoint folders and merging one index file, both fully visible in one `git diff --staged`. It also conforms to what wave 2 already says about itself: its `EPIC.md` presents one epic whose earlier leaves closed first.

Cost: the closed wave-1 folder gets edited after closure, and the repair is a one-time manual append that future readers must not copy as a supported operation. The twin guard from owner-reuse 1a is what makes "once" true. There is also no `epic complete` line and no broadcast for wave 2, but the rename route has the same gap: a completion retry calls `completeOwner` with `justMerged=false`, which prints no completion line.

## 2. Rejected options

- Rename the open twin (for example `satellite-plan-fit-2`), rewrite its recorded log paths, then let the fixed `completeOwner` finish it on retry. The rewrite is the problem: 708 recorded wave-2 log paths in `issues/timings.jsonl` and 49 in `issues/verify-runs.jsonl`, in append-only tracked files that are dirty right now from other live work, where wave-1 records share the same `satellite-plan-fit/` prefix and must not be touched. Leaf record files (`return-u1..u4.md`, `review-B.md`, `plan.md`) also cite `issues/open/satellite-plan-fit` paths; rewriting them edits the record, leaving them leaves broken citations. The route also waits on the close-witness leaf merging and installing before the retry can close sources, pack and rename, and it needs an operator-chosen new name. Its one real gain is model purity, two lifetimes in two folders, for a topic nobody will reopen, plus a live end-to-end proof of the fixed retry path.
- Wait for the code leaves and retry with no folder surgery. Cannot work under the locks: the destination throw in `completeOwner` stays as the backstop, so a same-name retry still fails after close-witness lands. Some manual step is unavoidable; the fork is only which one.
- Rename the closed wave-1 folder instead and let wave 2 complete under the original name. Same recorded-path breakage, moved to wave 1: its 89 archived members were recorded under `satellite-plan-fit/brand-override` and `page-draw-preview` paths in the same jsonl files, and its archive is git-tracked. Strictly worse than renaming wave 2.
- Close #282 and #285 by hand on GitHub and leave the folders. Fixes the two open issues and nothing else: status still lists six merged leaves as open, wave-1 logs stay unreadable, and pool-parity keeps its worktree and tab.

## 4. Pitfalls

- P1: Packing while the empty open owner folder still exists. `packFolder`'s verification and `readLog` both take the first existing owner dir in open, closed, parked order, so a leftover empty `issues/open/satellite-plan-fit` makes verification read an archive that is not there. Removed by step order: delete the open folder in step 2, pack in step 3.
- P2: Interruption between the move and the pack. The closed folder then holds 708 loose logs and possibly a `.closing` marker. Removed by the existing recovery surface: `akrogon status` prints an `Unpacked:` line naming `akrogon pack issues/closed/satellite-plan-fit`, and rerunning pack is safe because loose logs unlink only after archive verification.
- P3: Interruption between local completion and GitHub closure, or the reverse. Each step is separately rerunnable: `closeSource` returns early on an already CLOSED issue, and the folder state does not depend on GitHub. Removed by the step 5 verification (`gh issue view` on both numbers) before the commit in step 6 is called done.
- P4: Another framework session runs `next` during the surgery and reconcile acts on half-moved state, for example removing pool-parity's worktree or tab. All six leaves are merged, so no dispatch work exists under the twin, and pool-parity's worktree is no longer needed as a witness under close-witness 1a. Residual risk is a confusing error in the other session, not data loss. Reduced, not removed, by step 1's no-active-run check; there is no lock to take.
- P5: Staging too much in a dirty framework tree. Unrelated modified files include the two jsonl records and other charts. Removed by staging explicit satellite paths only and reading `git diff --staged --stat` before committing. No `git add -A`.
- P6: After the move, pool-parity's state still records its worktree and tab under the closed folder. Reconcile treats a closed merged leaf as removable (the keep-worktree branch is only for an open leaf whose owner completes), so the next framework `next` pass cleans both up. Removed by checking the worktree path is gone after that pass; do not delete the worktree by hand during the repair.
- P7: The manual append reads as permission to reuse names. Removed by recording the repair in the chart as a one-time step tied to this twin, with the dispatch guard as the mechanism that prevents a second case. No code learns to append.

## 5. Question the fork does not ask

When should the door run the repair relative to the two code leaves? The move route can run today, but then the chart's real stuck case is gone before the leaves land, and the fixed retry path (slug witness, twin guard) gets proved only on test fixtures, never on the live twin that motivated it. Keeping the twin stuck until the leaves merge and install preserves that live proof, at the price of wrong status output and unreadable wave-1 logs in the meantime. Does the operator want the twin kept as the leaves' end-to-end proof case, or repaired as soon as this fork is taken?
