# Leaf review, slot C

## twin-guard

T1. Missed consumers: `discover` is not a dispatch-only inventory, so excluding twin leaves there "the same way" as duplicate slugs breaks more than the design's Consumers list covers. Evidence in `src/next.ts` at HEAD: `activeCount` adds `inventory.unreadable` to the active total and `allocate` refuses a new tab at `max_active`, so if twin exclusion increments `unreadable` like duplicate exclusion does, every twin leaf (six in the live case) permanently consumes a capacity slot and can block other owners, against criterion 3. `reconcileRepos` passes `discover(repo, invocation).leaves` into `reconcile`, whose per-leaf worktree and tab rules iterate that list and the `leafBySlug` map built from it (`src/reconcile.ts` `reconcile`), so excluded twin leaves get no merged or failed cleanup and their store worktrees fall into the kept "unknown directory" branch. `paneOwners` resolves the hook pane's leaf through `discover`, so an excluded leaf's agent can no longer be matched to its pane. Most importantly, dependency resolution reads the same list: `unmergedDeps` (`src/turn.ts`) looks up each `blocked-by` slug in the leaves passed from `discover` (via `blockDetail` in `dispatchLeaf` and `eligibility` in `mergeQueue`), and a slug absent from the list but present on disk comes back labeled `unreadable`. A merged twin leaf excluded from `discover` therefore blocks its dependents in other owners forever, even though its code landed. That contradicts the brief's "covers only that owner's leaves". The design must say which of these the chosen placement avoids and how; mirroring duplicate-slug exclusion does not.

T2. The first Open-for-the-plan item settles now, and it is not free. `selectLeaves` (`src/next.ts`): with the twin leaf excluded, `selected` is empty for both the slug and the `issues/open/...` path forms. It returns the empty selection quietly only if `inventory.unreadable > 0` (or unknown/foreign); otherwise the slug form throws `missingLeafMessage` ("Missing leaf: <slug>"). So criterion 1's required stderr for `next <slug>` is met cleanly only by incrementing `unreadable`, which is exactly the capacity cost in T1, or the pass also prints a misleading missing-leaf error. Related factual gap in the design's Interface: `report` de-duplicates by `${repo}/${path}` plus a slug identity, and duplicate-slug reporting passes `leaf.path`, so reporting per twin leaf prints one JSON line per leaf, not the "one error per pass" the brief's What requires. One line per pass happens only if the report path is the open owner folder, shared by all its leaves. Both choices belong in the design, not the plan.

T3. The second Open-for-the-plan item settles now, against the design's suggested escape. A twin cannot appear mid-life through akrogon itself: `parkCommand` (`src/park.ts`) refuses when the destination name exists and moves the whole owner, and the only writer of `issues/closed/<name>` is `completeOwner` renaming that same open owner. So a twin leaf can be in `merge` only if it was already in flight when the guard first installs, or was driven there with `akrogon phase`, which this leaf leaves unchanged. For that narrow case there are three placements and the design names the wrong one: exclusion in `discover` also drops the leaf from `mergeTurn`'s `reconcileBatch` loop, which iterates `discover` leaves with a batch, so an applied batch whose holder is a twin never reconciles; refusal only inside `dispatchLeaf` keeps the twin at the head of `mergeQueue`, and `mergePass` processes only holder `[0]` and returns while it stays in `merge`, stalling every other owner's merges; and the design's fallback, refusing only leaves not already in `merge`, contradicts the Taken text ("refuses to dispatch any leaf") and lands the leaf's code into a `completeOwner` throw that is guaranteed. My settlement as implementer: refuse every phase, and keep twin leaves out of merge-queue eligibility so other owners' merges proceed, accepting manual recovery for a pre-guard applied batch. Whatever the door chooses, the brief's criteria cover only a plan-phase dispatch, so this behavior is currently unbound and untested.

T4. No criterion or design line states the exit code, and code settles it: any `report` call adds to `invocation.skipped`, and `nextCommand` ends with `if (invocation.skipped.size > 0) process.exitCode = 1`. So a `next --all` pass that refuses the twin and successfully dispatches another owner (criterion 3) exits 1, and the test being flipped (`tests/next.test.ts` "closed owner name does not block an open same-name owner") currently expects code 0 for both its calls. Bind exit 1 in criterion 1 and 3, or the implementer and the checker will pick different answers. Criterion 4's closed-path dispatch in the same fixture would also report the twin during its `discover` calls (discover scans the whole repo regardless of the target), so that call exits 1 too while still dispatching the closed leaf; the criterion says only that it "still dispatches", which holds, but the flipped test must not keep expecting 0 there either.

## slug-witness

S1. Criterion 1 cannot be proved inside the stated owned surfaces as written. It requires completion "on retry through `akrogon next`", but the design's Owned surfaces list `tests/phase.test.ts` plus criterion-3 text matches. The existing worktree test in `tests/phase.test.ts` ("sourced completion without worktree context fails before rename without a fabricated commit") drives `cli(f, ['phase', 'missing', 'merged'])`, which is `phaseCommand`, not the `next` merged-leaf branch (`dispatchLeaf` calling `completeOwner` for a `merged` leaf, `src/next.ts`). The `next` retry surface and the other two assertions of the old comment live in `tests/next.test.ts`: "next recovers only merge-phase work by ancestry..." and "next awaits sourced completion after a failed rename..." both expect `--comment merged ${head}`, and "startup retries closure before cleanup..." is the existing `next --all` sourced-retry test. Updating those two assertions is arguably criterion-3 work, but adding or flipping the criterion-1 proof in that file is not clearly owned. Either add `tests/next.test.ts` to Owned surfaces, or change criterion 1's proof route to the phase command, which reaches the same `closeSources` through `completeOwner`.
