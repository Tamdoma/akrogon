## Material forks and recommendations

### D1. Source, installation, and session delivery

Options: edit installed files directly, maintain personal clones in the customization repo, or change herdr-app upstream. **Recommend personal clones in the customization repo.** Direct edits are overwritten or rescued as `*-edited` at startup. Upstream changes add a release dependency for behavior already supported by mods. The manual's **Layouts: `layouts/<name>.json`** explicitly requires cloning shipped code before changing it.

Clone `files` and `changes` as personal mods, including their assets. Clone `tabs` because it hardcodes Files/Changes buttons and panel restoration. Keep the existing personal `flat`, `agents-by-tab`, and `session-status` rather than cloning them again. Write Tasks, inbox, and decision UI new. Clone Spaces only if a reproduction proves its implementation needs changing. Leave workspace-chrome, pane, and worktree shipped unless their actual behavior must change. A worktree selection control is not a reason to clone worktree's create/remove workflow.

Committed source flows through a targeted copy to `~/.config/herdr-app`, then the session launcher's personal-path links. Existing links propagate edits, but **new mod folders are not linked into already-running session homes until that launch-link step runs**. Include all three named sessions in installation verification. Never use `session stop` to refresh links because it stops programs. New mods should use `mod.json` `place: "none"` and enter through the agreed layout, avoiding automatic docking.

`shared.json`, per-mod localStorage, and `layouts/.state` are runtime state, not shared source. Existing sessions do not recopy main-home `workspace.panels` on each launch. Changing that main file alone cannot deploy Tasks to every session. Do not edit `.state`. The full customization installer also installs packages, rewrites theme settings, and selects board (`install.sh:296`, `:316`), so it is not a neutral live-update command.

### D2. Screen composition and default panel

Options: flat sidebar plus right stack, the existing top agent board, or show both status surfaces. **Recommend flat as the primary layout, with Tasks first in the right stack and a bounded inbox above Agents.** Keep the existing board layout available without automatically converting it into a second copy of every surface. Ask the operator whether both layouts need feature parity before assigning that work.

Put the decision strip directly below the terminal block and keep it absent when there is no current decision. It must not reserve a permanent empty strip. Limit the inbox's initial height and scroll its items so Spaces and Agents remain usable. Make the right panel resizable and hideable. “Shown by default” should mean first use of a space, followed by respecting the operator's later choice, unless the operator explicitly wants always-open Tasks.

The shipped tabs mod remembers closed/active panel per space and knows only Files/Changes (`mods/tabs/main.js:22`, `:82`). Merely adding a Tasks child or changing `stack.active` will not implement the requested default. Its personal clone needs Tasks button wiring and a defined first-use policy without discarding existing remembered choices.

### D3. A3 context: follow focus versus inspect a selected worktree

Options: always follow focused cwd, pin a checkout globally, or make the selection explicit per space. **Recommend per-space “Follow focused terminal” plus an explicit checkout selection shared by Files and Changes.** Identify the repository through Git's common directory, not the first pane's name. Discover real checkouts with `git worktree list --porcelain` instead of constructing `~/.akrogon/worktrees/...` paths. Akrogon can override that store, and the shipped worktree mod uses a different store (`mods/worktree/main.js:17`, `:31`).

Key inspection state by session/machine/space/repository. Show repository, branch, and selected path in the panel header. Selection changes must invalidate older async results so a slow diff from checkout X cannot appear under checkout Y. The Files clone already has a context-generation pattern worth preserving (`mods/files/main.js:50`).

“Open as pane” should create a **mod pane**, via `pane.split {mod, props}`, with the selected root/file/comparison captured in props. It should not create a new worktree, start a shell, or keep following unrelated focus changes. Clicking that new mod pane gives `focused().cwd === null`, which must not erase its explicit source. See manual **The model: spaces, tabs, terminals** and **UI**.

### D4. A1 git review and mutation

Options: retain broad commit, implement selected-path commit, or remove commit. **Recommend removing commit controls and their handlers from the personal Changes clone.** `commit()` currently executes `git add -A` and then commit (`mods/changes/main.js:145`). Selected files still do not protect against somebody else's pre-staged changes or another agent changing those files between review and commit. A read-only review panel removes that whole failure class.

Use three clearly separate scopes: working tree including staged/unstaged/untracked state, committed branch delta from the merge base with the configured default branch, and a selected recent commit. `git diff base...HEAD` represents committed branch work, while `git diff HEAD` represents working changes. Show the resolved base and commit IDs. Use `default_branch`, not a universal literal `main`. Do not automatically fetch, checkout, stage, discard, or rebase from a review action. Git's [diff documentation](https://git-scm.com/docs/git-diff) defines these endpoint semantics. The [VS Code team's history UI](https://code.visualstudio.com/docs/sourcecontrol/history) also separates inspection from checkout.

Define merge-commit inspection before implementation. Combined diff and first-parent diff answer different questions. Recommend an explicitly labeled first-parent comparison for a selected merge commit, with no claim that it shows every parent.

### D5. A2 file search, Markdown, and “recent”

Options: filter only loaded rows, search repository paths, or full-text search. **Recommend a repository-wide filename/path filter over tracked and nonignored untracked paths.** Filtering only expanded rows is easy to ship but misses files and would mislead the operator. Full-text search is a different feature and needs explicit scope.

Render Markdown with `TextView.markdown`, retaining a way to inspect its raw source. Keep ordinary code previews read-only. The installed kit supports Markdown and link callbacks (`gpui-kit.d.ts:20701`), whereas Files currently creates only an Editor (`mods/files/main.js:120`). Relative links must resolve against the selected file and checkout, not whichever pane later takes focus. Surface binary/large-file limits rather than looking empty.

“Changed recently” is underspecified. Options are filesystem modification time, recent Git commits, or events observed since the UI started. **Recommend recent Git history plus current uncommitted files**, labeled with those facts. Checkout/rebase changes make filesystem mtimes a poor measure of recent authored work, and an in-memory event list disappears on restart. Ask for the desired time window or commit count.

### D6. A4 authoritative all-repo Tasks data

Options: reconstruct state from JSONL in the mod, parse rendered `akrogon status`, or expose a machine-readable akrogon snapshot. **Recommend a small read-only JSON status contract in akrogon**, reusing existing scanning, schema validation, required-seat routing, and queue logic. This is a necessary producer outcome in the chart, not an already-existing API. `src/akrogon.ts:46` accepts only `--charts` for status today. Both config and status currently produce human output.

Snapshot content should cover registered repo identity/root, open leaf identity/path/state, active required seats and their completion, blockers/stopped/paused/failure state, phase-entry timestamp and its provenance, worktree, actual merge queue, recent successful merges, per-repo read failures, and terminal identity once the port defines it. Do not put full transcripts or timing logs in the snapshot. Reuse `mergeQueue` instead of sorting phase=merge rows by age. Keep queues per repository. Distinguish the merge queue from the separate full-run admission line shown by status.

Use the registry resolved by `readGlobal()`/`globalHome()`, honoring `AKROGON_HOME`, and the canonical registered checkouts. Repositories may share slugs. Use `(registered repo, slug)` as a leaf key. Nested epic leaves and foreign/duplicate/broken states already have scanner rules (`src/state.ts:172`, `:204`). Parse the JSON snapshot once at the mod boundary.

Take a complete initial snapshot. Then use local `watchFolder` events on the relevant issue directories and registry/config parent to request a fresh snapshot, coalescing saves and avoiding overlapping refreshes. Watch transitions as well as `state.yaml`, timing, moves between open/closed, and queue-affecting controls. A log-only watcher misses important state changes. Use app live subscriptions for terminals, not polling. Remote folder watches are not supported by this API. Remote repository fleet data would be an extra scope decision.

The producer also removes a concrete size problem: `readTextFile` is limited to 1 MiB (`herdr.d.ts:23`), while akrogon's current `timings.jsonl` is already 2,969,099 bytes. Do not read ever-growing full logs into every hidden panel.

For “red past normal,” show elapsed phase time first and only show a comparison when a defined baseline exists. Elapsed wall time includes paused and dependency/queue waiting. Phase revisits matter. The status TIME column currently measures since the first delivered prompt, not time in the current phase (`src/status.ts:128`, `:186`). The existing verify slow-merge detector is for eligible verification runs, not a universal phase baseline (`src/verify.ts:367`). Choose the baseline population/minimum evidence with the operator instead of inventing a red threshold. Missing baseline should remain explicit.

### D7. A4 leaf-to-terminal mapping and the pending hc port

Options: infer by tab title/cwd, add a legacy herdr adapter, or depend on a stable identity produced by the pending port. **Recommend the port's explicit identity contract and no legacy adapter.** The migration intake's **How I picture it** commits to space-per-repo/tab-per-leaf through `herdr.space` and `herdr.tab`; its **Open questions** explicitly leaves slot storage and session mapping unresolved. Today `state.pane`/`state.tab` still describe old herdr. They are not hc addresses.

Agree with that chart on semantic terminal identity for repo, slug, and slot, preferably explicit hc labels, together with core session and machine identity. The existing herdr labels locate a terminal in a UI tab but do not establish which leaf/seat it belongs to. Address `t7` is unique only within its core. A terminal name can help look up a replacement after restart, but the lookup must also confirm the semantic labels and that the live foreground is the intended agent rather than a recovered shell.

Join snapshot leaves with live `terminals()`/`agents()` in the current core. Show A and B separately when both are active. Focus an explicit address with `run("agent.focus", {terminal})`, which includes agents without panes. Use peek when the chosen operation is inspection of a child. Do not map a consultant to a leaf just because it inherited a tab. Sources: manual **The model: spaces, tabs, terminals**; `herdr.d.ts:64`, `:137`, `:209`; installed `hc schema` Terminal.

**Cross-session navigation is a real fork:** a global filesystem board can see every registered repo, but a mod's live terminal list is not every independent `HC_SESSION`. Recommend keeping all-repo visibility and having the producer expose target session identity. Before promising global one-click jumps, probe a session-targeted app command and window activation in infra/personal/mdconsultingny. Unavailable, stopped, old-herdr, and other-session targets need distinct visible states. Never send a bare hc address through whichever core happens to be current. If the operator accepts local-session jumps only, name that reduced behavior explicitly. Otherwise navigation completion depends on the migration identity/session decision and this probe. Do not silently ship fuzzy matching.

### D8. A5 Needs-you source and reply transport

Options: scrape every screen, use hc's reported question metadata, or add harness-specific structured question producers. **Recommend hc metadata for the wait identity/kind, with screen text displayed as a screen excerpt, and a producer probe before promising complete question text.** On a relevant status change, capture terminal/core/turn plus `report.kind/msg/title`. `msg` may be a short status message, not the whole question. `hc read --json --lines 0` supplies a passive current screen. Honor `complete`/`why`; a blocked full-screen app may have an incomplete view. Do not synthesize missing text or claim that this is the last assistant reply.

A prose question may end in idle rather than blocked, and permission/auth dialogs are also blocked. Test all of Claude, Codex, pi, and Antigravity with actual question and approval states. If complete ordinary questions are required across all four, chart the necessary structured producer contract explicitly. A structured pending-question artifact is cleaner than four unrelated transcript scrapers, but it changes agent instructions/integrations and requires operator agreement.

Bind the reply draft to the exact source terminal/turn, preserve it on unrelated focus changes, and revalidate the live target before sending. An ordinary idle chat reply uses `hc send --if idle`. A blocked question requires `--force`, which should only follow the operator's explicit submission to that identified question. Permission/auth dialogs should open the exact terminal for its native controls unless a tested dedicated interaction exists. Plain text plus Enter is not a universal answer API for numbered/arrow-key dialogs. These distinctions follow installed `hc send --help` and `hc --skill` **Status, recovery, and cleanup**.

Inspect and display send errors and `started` rather than treating a successful process exit as proof the agent accepted the answer. Never retry a reply blindly because duplicate input can answer the next question. The migration intake's **Things hc got wrong in testing** supplies concrete prompt-delivery counterexamples. hc also wraps cross-terminal messages, so native slash commands do not belong in the reply mechanism.

### D9. A6 reliable coded options

Options: regex the terminal viewport, parse harness conversation formats, or require a structured current-decision record. **Recommend a structured record produced alongside the assistant's normal question.** The record needs terminal/core identity, turn/request identity, exact question/option labels and reply tokens, grouping, and single/multiple-selection rules. Mechanical parsing validates the machine record, not the assistant's prose formatting.

Terminal text alone cannot reliably identify the last assistant reply. It can contain copied prompts, quoted examples, previous questions, code, wrapped lines, or a partly rendered answer. Recognizing `1a` or `O1` is not evidence that the agent is currently offering that choice. The installed hc schemas contain no message-role/choice model. Harness transcript parsers add format and session-binding dependencies, including the missing agent-session mapping already raised in the migration intake.

If the operator rejects a producer contract, the honest alternate scope is explicitly best-effort suggestions that only fill an editable draft. Do not call that reliable detection. It must never send on token click. Recommend buttons build a visible draft such as `1a | 2b`, enforce the producer's group rules, then send once on an explicit Send action. Invalidate on a new turn, target change, exit/recovery, or question resolution. The decision UI can reuse A5's identified-target send logic without depending on its sidebar placement.

### D10. Theme, logos, and Spaces behavior

Options: brand-colored panels/new theme, new raster logo assets, or reuse the program table and existing theme. **Recommend the existing program table and theme tokens.** Draw `svg(program.icon)` tinted with the local foreground when `program.tint`, otherwise `image(program.icon)` preserving its colors. Do not infer Claude/Codex/pi from tab names, recolor a full-color icon as a mask, or download replacement logos. The personal board and agents list already demonstrate the pattern. Source: manual **Programs: `programs.json`**; `herdr.d.ts:137`; `gpui-kit.d.ts:20274`.

Concrete proposed beauty criteria: preserve `settings.json`'s Omarchy theme and terminal font/size, flat terminal panes and existing separators. New panels use chrome/background/surface, border, foreground/muted/dim, accent, and semantic status tokens. Use aligned 14–16px program marks, 28–32px compact rows, one clear title and muted metadata per row, stable spacing, visible hover/focus/selection, and labels as well as status color. Keep hierarchy consistent between Tasks and inbox. Long paths get truncation plus accessible full text, question details wrap, and narrow panels remain usable. Use native spinners rather than frequent JS redraws. These are reviewable proposals, not a claim of visual approval without an in-app review.

Spaces should have a smaller bounded region, its fixed header/New control outside a vertically scrolling list, and Agents should get the remaining height. Preserve native wheel/trackpad scrolling, a stable scroll-container id, and drag/reorder behavior. Do not use wheel handlers to switch spaces. The installed GPUI kit says to use native overflow scrolling rather than `on_scroll_wheel` for scrolling (`gpui-kit.d.ts:785`). Its existing Spaces scroll container lacks an explicit id (`mods/spaces/main.js:375`), so retaining position across re-renders is a concrete probe before deciding to clone it. Test many spaces, long names, expanded worktrees, rail mode, short windows, and sidebar resizing. Active offscreen spaces must remain reachable without snapping the list back on every render. Ask whether keyboard navigation should reveal the selected row.

## Intake corrections and missing decisions

- **M1. Repository routing is missing.** Most implementation belongs to omarchy-customizations, which is not registered. Seat A must settle how leaf contracts are hosted/registered there and how W5 is handed to akrogon. Do not put user UI source in akrogon merely because this chart door runs there.
- **M2. The proposed A4 data feed is insufficient.** Transition logs alone cannot provide live seats, authoritative current state, queue eligibility, pause/stop controls or navigation. A small producer API is justified by existing code ownership and the file-size limit, not as a new general dashboard platform.
- **M3. A5/A6 currently promise more than the APIs establish.** “Blocked,” “has asked a question,” “latest assistant answer,” and “offers coded options” are different facts. Settle the producer contract or narrow those promises before handing work off.
- **M4. “Slot” and “red past normal” need definitions.** A transition's slot is not the current seat, both A/B may be required, and wall time is not working time. Do not hardcode historical phase/seat rules in the UI.
- **M5. Visual scope needs approval through concrete states.** Preserve the current theme, reuse existing icons, and have the operator review populated narrow/wide states. A7 remains excluded. Remote fleet support, terminal multiplexing changes, worktree creation/removal, a full git client, and unrelated customization cleanup are outside this request.

The useful first delivery is a trustworthy, read-only review surface with correct checkout context and usable Spaces. Reliable fleet navigation and replies should follow explicit data/identity contracts, not assumptions about terminal prose.
