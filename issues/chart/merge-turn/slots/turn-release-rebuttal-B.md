- **F1:** A's pre-push check does not yet remove the old-publisher risk (`turn-release-merged.md:13`). If the lock is released after checking, the holder can become failed and cleanup can run before its delayed push. The command must own the push itself and serialize it with revocation and cleanup, using the recorded batch attempt identity. Checking only that members are in merge also lets an old attempt pass after those leaves reenter merge. Today's check and push are separate operations (`skills/merge-issue/SKILL.md:47-49`, `src/phase.ts:330-333`). I accept replacing stopped-process proof for publication with complete command-owned fencing, but not this check alone.

- **F2:** Blocking publication does not make branch restoration safe while the old attempt can still rebase or edit those worktrees. Q2 restores every member as soon as the holder leaves merge (`turn-release-merged.md:12-13`), potentially racing its unfinished stack operation. Command-owned worktree mutations need the same attempt ownership and serialization as restoration, or recovery must establish that those operations stopped. The settled design already makes stack building command-owned (`forks/turn-release.md`, Carries), so extend that ownership through cancellation and cleanup rather than assume a failed label stopped all work.

- **F3:** Q1 says three prompt failures occur “in the same pass” (`turn-release-merged.md:6`), but the code counts failures across passes and makes one delivery attempt before recording failure (`src/next.ts:436-468,539-565`). Preserve that existing retry policy. Once a pass actually commits the capped failure, it can reconsider the next holder immediately without retrying the same holder three times in that pass.
