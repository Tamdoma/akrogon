The last fork settled that one leaf at a time holds the merge turn and carries the waiting leaves in one batch, with one check run on the top of the stack. That stops leaves from knocking each other out. One thing can still move main during that single run: you. When you commit your notes and records (`add issues`, or `akrogon sync`), main moves, the batch's push is refused, and the 35-minute run would start again even though no code changed. This round settles what the batch does in that case, and which folders count as "records, not code".

### 1 · When main moved only by record commits during the batch run, does the batch run its checks again?

A record commit is one that only touches files like charts, briefs, logs and lessons. Example from 2026-10-05: the push of `lane-orphan-check` was refused because of commit `e612d10ee` (`add issues`). The seat rebased, then proved that nothing outside `issues/` differed between the commit it had tested and the new one (`git diff --exit-code 3700fc48e HEAD -- . ':!issues'` exited 0), reused its green run and pushed (`fw:issues/open/skill-rewrite-tooling/lane-orphan-check/review-B.md:139-147`). A second seat did the same on its own (`fw:.../spec-mutation-anchors/review-B.md:113`). No rule told them to. The skill only says reuse is allowed "when neither code nor integration changed" (`skills/merge-issue/SKILL.md:51`), and nothing defines that. A leaf branch can never contain `issues/` files (`src/phase.ts:274-279`), so a leaf and a record commit can never touch the same file. Your answer decides whether a record commit costs a few seconds or a full run.

Research: practitioner · Mergify merge queue docs (https://docs.mergify.com/merge-queue/, read 2026-10-05), GitLab merge trains (https://docs.gitlab.com/ci/pipelines/merge_trains/, read 2026-10-05), plus the two seat records above · Mergify has "Direct Merge: Skip the queue CI run when nothing relevant moved". GitLab shows the other side: a direct merge past the train cancels and restarts every run in it. Tools skip a run only when they can prove nothing relevant changed · It turned the seats' improvised proof into option 1a and showed that 1c is the known expensive default.

- **1a (recommended)** Reuse the green run when the code is proven identical. After a refused push the command restacks the batch on the new main and compares the tested top commit with the new top commit. If every file outside the record folders is the same, the push goes ahead with no new run. If anything else differs, the checks run again. It wins because the proof is one git command with a yes or no answer, and the code that lands is exactly the code that was tested. Cost: the pushed commit has a different id from the tested one, because your record commit sits under it. The earlier lock says checks run on "the final rebased commit" (`issues/chart/check-reruns/forks/check-scheduling.md:24`). Picking 1a means you accept "same code, different id" as meeting that lock for record commits only.
- **1b** Hold record commits back while a batch is running. `akrogon sync` refuses or waits while a leaf holds the turn. Cost: it cannot stop a plain `git commit` and `git push`, which is how `add issues` commits are made today. You would have to remember not to commit during merges, which is today's workaround.
- **1c** Always rerun. Simplest rule, and the tested commit is always the pushed commit. Cost: about 35 minutes per record commit that lands during a run. On 2026-10-05 three such commits landed in 90 minutes (15:16Z, 15:53Z, 16:41Z, from the intake), so a batch could lose its run again and again.

Pitfalls avoided: A seat deciding by feel whether "nothing changed" is how mistakes get in, so in 1a the command does the comparison and prints the result, and the seat only acts on it. This fits the settled shape, where the command already builds the stack. A commit that mixes records and code, or a second commit with code behind the record commit, fails the comparison and gets a full run, because the comparison looks at the final files and not at commit names. The trailer check (`merged --check`) still runs on the new top, since it takes seconds. A done-criterion for the leaf: a record-only commit pushed during a batch run leads to a successful push with exactly one check run in total, and a one-line code commit pushed the same way leads to a second run.

### 2 · Which folders count as records?

The comparison in 1a needs a fixed list of folders it ignores. Three facts shape the list.

First, `issues/config.yaml` lives inside `issues/` and it is the list of checks itself (`issues/config.yaml:7-11`). A change there must never be skipped over.

Second, your record commits usually include lessons, which live outside `issues/`. In akrogon the commits `a2e8241`, `e99801d`, `8ebb3f6` and `b1bdde3` (all `add issues`) each changed `learnings/LESSONS.md` and a file in `learnings/history/`. In framework, `55f002467` (`add issues`, 2026-10-05) also touched `learnings/`. After the last fork, seat B writes its lessons there before every merge, so these commits will keep coming.

Third, I looked for checks that read these folders. akrogon's tests build their own throwaway folders and write their own `issues/config.yaml` there (`tests/config.test.ts:10`), its formatter only covers `src tests skills/chart-issues/scripts` (`package.json:8`), and framework's linter only covers `.claude`, `integrations` and `shared` (`fw:biome.json`). Framework scripts mention `learnings/` only in comments (`fw:.claude/skills/dev-cf-workers-deploy/scripts/libraries/unchanged-output.ts:38`). I found no check that reads tracked files under `issues/` or `learnings/`. This was a search of the two repos, not a proof for every check script.

Research: better-than-training · inspected `src/sync.ts:109-119` (sync stages only `issues`, so a `sync issues` commit is records-only by construction, but it does include `issues/config.yaml`), `src/phase.ts:274-279`, the git history above, and Nx affected docs (https://nx.dev/ci/features/affected, read 2026-10-05) · Nx treats a change to a file that configures the build as affecting everything, which is the same reason `issues/config.yaml` cannot be on the ignore list · It added the config exception and the `learnings/` folder to the recommended list.

- **2a (recommended)** Records are everything under `issues/` except `issues/config.yaml`, plus everything under `learnings/`. The list is fixed in akrogon, with no setting. It wins because it matches what your `add issues` commits really contain, so they stop costing a run. Cost: it becomes a rule for every repo that uses akrogon that no check may read tracked files in those two folders. A repo that breaks the rule could land a commit whose checks would have failed.
- **2b** Records are only `issues/` except `issues/config.yaml`. Lessons count as code. Cost: every `add issues` commit that includes a lesson forces a full run, which is most of them, so the saving from question 1 mostly disappears.
- **2c** Each repo lists its own record folders in `issues/config.yaml`. Cost: a new setting to document and get wrong, for a need no repo has shown yet.

Pitfalls avoided: The check list changing under a running batch is removed by the config exception: any change to `issues/config.yaml` fails the comparison, so the batch reads the new list and runs again. A check that secretly reads these folders is handled two ways. The door runs a probe before handoff: search the check commands of both registered repos (akrogon and framework) for reads of tracked `issues/` or `learnings/` files, and record the result in the fork. This probe is pending. The rule is also written where a new repo meets it, in the setup guide next to `checks` and `merge_checks` (`docs/guide/setup.md:53-54`), as a done-criterion. A leaf may itself change `learnings/LESSONS.md` on its branch (akrogon commit `0cd981b` did), and the file already merges line by line without conflict (`.gitattributes`: `learnings/LESSONS.md merge=union`), so restacking over your lesson commit does not stop on it.
