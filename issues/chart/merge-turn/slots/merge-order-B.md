### 1 · How should competing merges in one repo be ordered?

`skills/merge-issue/SKILL.md:37-49` runs checks before Git rejects a losing push, and `src/next.ts:625-628` dispatches each eligible merge seat independently. If two leaves pass review together, the later one must either wait before integrating or test a candidate that already includes the earlier one. `issues/chart/check-reruns/forks/check-scheduling.md:23-24` requires the final integrated candidate to pass its merge checks before publication.

Practitioner · Yaron Minsky, Jane Street, [Making “never break the build” scale](https://blog.janestreet.com/making-never-break-the-build-scale/), published 2014-07-06, read 2026-10-05 · his build-bot experience shows that serial integration avoids independently tested branches invalidating each other, but limits throughput, which favors one active merger here rather than more concurrent suites. Better-than-training · Zuul maintainers, [Project Gating](https://zuul-ci.org/docs/zuul/latest/gating.html), read 2026-10-05 · cumulative speculation preserves ordered integration but rebuilds downstream candidates when a predecessor fails, shaping the alternative's cost.

- **1a (recommended)** The command keeps a durable first-in-first-out order of leaves becoming eligible for merge and admits one merger per repo. Only that leaf fetches, rebases, runs the required checks and pushes, with ownership lasting through confirmed publication. Other repos and earlier phases keep their parallelism. This removes the competing-leaf race with the fewest new mechanisms. Cost: every waiting leaf waits for earlier merge turns, and publication throughput is limited by one check run at a time. Repair and crash handling are settled in turn-release.
- **1b** Use an ordered speculative train. Check the first leaf on main, the second on main plus the first, and so on, then publish in order. This can increase throughput when checks have separate execution capacity and usually pass. Cost: correcting or removing an earlier leaf rebuilds later candidates, more simultaneous suites compete on this machine, and the command must manage candidate heads and invalidation. It cannot promise complete avoidance of reruns.

Pitfalls avoided: The implementation must prove that concurrent hooks, targeted dispatch and restarts cannot admit competing mergers or reorder existing entries accidentally, and that exclusion covers integration and checks through push rather than just the push. Both options retain fast-forward publication and check any conflict resolution before landing, as `skills/merge-issue/SKILL.md:41,49` requires. Neither uses the global state lock for the duration of checks or adds polling or timed ownership expiry.

### 2 · Where should a waiting leaf wait, and should it keep its tab and active slot?

A reviewed leaf already enters `merge` through `src/phase.ts:246-250`. `src/next.ts:305-317` counts its live tab or worktree panes against the global `max_active` limit even when its seats are idle. Waiting can therefore preserve the existing session, or close its panes and leave its saved code and review artifacts queued for later allocation.

Research: better-than-training · `src/next.ts:305-338,625-628`, read 2026-10-05 · current capacity follows live allocation, making retained tabs a real capacity cost and making tab release a change to allocation semantics. Practitioner · Will Smythe and Lawrence Gripper, GitHub engineering, [How GitHub uses merge queue to ship hundreds of changes every day](https://github.blog/engineering/engineering-principles/how-github-uses-merge-queue-to-ship-hundreds-of-changes-every-day/), published 2024-03-06, read 2026-10-05 · their production queue removes manual shepherding, supporting command-owned waiting without an agent repeatedly checking whose turn it is. Their account does not establish whether local tabs should be retained, so that recommendation comes from the inspected implementation.

- **2a (recommended)** Wait in `merge` with the existing tab, panes, worktree and `max_active` slot. Do not prompt B to start merge work until admitted. This preserves session context and current capacity accounting with the smallest change. Cost: idle waiting leaves consume capacity across repos and can prevent new implementations from starting until slots free up.
- **2b** Wait in `merge` with saved worktree and artifacts, but close the waiting leaf's tab and panes and free its active slot once both seats have finished their current passes. Reallocate and resume B when its turn and capacity permit. This lets other work use the capacity. Cost: session recovery and allocation become part of the change, and newly active work can delay the queued merger unless admission gives it the next available slot.

Pitfalls avoided: Under either option, waiting preserves reviewed code and artifacts and does not count as a failed or repaired leaf. Done-criteria must prove that a waiting B receives no merge prompt, a released tab has no surviving active seat, and an admitted waiting sibling wakes without a false `blocked-by` dependency, since `src/next.ts:681-691` currently wakes only dependents. Under 2b, reserved admission and capacity allocation must not allow fresh work to overtake the admitted merger indefinitely.
