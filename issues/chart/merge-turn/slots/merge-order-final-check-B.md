## Answers to “Open for the check”

1. **Batch size:** No numeric cap is established by the operator's `1d` choice. I would retain the stated fixed snapshot of all eligible waiting leaves rather than invent a number. Eligibility must be resolved first: `src/next.ts:585-619` excludes hand-built leaves, unmet dependencies and missing inputs, whereas “every leaf in merge” includes them. `max_active` is not a batch-size cap because it counts live allocations, not every merge record (`src/next.ts:305-315`). If a cap is desired, selecting it is an operator choice about throughput and the amount of work repeated after a red batch, not an implementation default justified by this code.

2. **Guards and cleanup:** Yes, the proposed per-leaf range check requires code changes. `requireTestChangeCitations` compares against the configured remote, not the previous stack tip (`src/phase.ts:282-295`), so it checks a cumulative range and can let an earlier member's trailer satisfy a later member's change to the same path. `requireClean` checks the target leaf's recorded worktree irrespective of which B invoked the command (`src/phase.ts:225-228`), so acting from the holder does not bypass another member's dirty worktree. `requireNoIssueFiles` likewise checks cumulative ancestry against the remote (`:274-279`), and needs explicit retained semantics when stack ranges are introduced. Moving another leaf as slot B is currently allowed because the command validates a required slot, not the caller's pane ownership (`:211-215`). New turn enforcement must permit the batch holder to preflight and finalize recorded members, without granting every member independent ownership. Branch deletion is not inherently broken by the stack: every prefix tip is an ancestor of the published top. However, cleanup uses ordinary `git branch -d` in repo.root without explicitly proving ancestry against the configured target (`src/next.ts:652-658`), so the contract needs a safe deletion check using confirmed published tips rather than assuming the registered checkout's HEAD or branch upstream proves landing. Do not replace refusal with unconditional deletion.

3. **Owner:** The holder's B should remain the agent responsible for interpreting checks, recording evidence and sending completion broadcasts. The command should own the mechanical snapshot, branch ranges, rebase-or-abort/drop operation and publication reconciliation. The current skill gives B one worktree and one leaf artifact folder (`skills/merge-issue/SKILL.md:10-16`), and the command owns state/dispatch (`:25`). Making B an informal coordinator of multiple mutable worktrees leaves crash recovery and member authorization unspecified. Mechanical stack building must run outside the long-held global lifecycle lock (`src/phase.ts:330-333`), with a durable attempt record and short locked state updates. Command ownership does not mean the command should send Discord messages: that remains the merge seat's own task (`skills/broadcast-issue/SKILL.md:10,14`).

## Disagreements and missing pieces

- **F1. Red dissolution does not restore independent leaves.** Shape `:12` leaves branches stacked, then calls them solo. A later member's HEAD now contains earlier members, including a possibly failing predecessor, so its solo attempt can test or push more than its own reviewed change. Save original heads and explicit patch bases before stacking, and specify how each unpublished member is restored to its own patch before solo retry. `skills/merge-issue/SKILL.md:37,43` currently assumes one leaf branch and routes its red check to that leaf's repair. Preserve original ranges for outside-push restacking too (shape `:13`), so prior stack ancestry cannot be mistaken for a member's own work.

- **F2. Derived holder conflicts with carrying and dropping members.** Shape `:6` refuses non-holder `merged --check`, but `:10-11` requires those operations for every carried member. Shape `:9` can drop the earliest holder and continue the batch while that leaf remains earliest in merge. Shape `:11` marks the holder merged first, changing the derived owner before its B finishes later members. Record ownership of a fixed batch attempt separately from next-turn selection, and authorize its holder for its recorded member/range set until publication reconciliation finishes. `src/routing.ts:35` and `src/phase.ts:199-215` model only individual merge transitions today.

- **F3. Red/conflict solo status must survive another dispatch.** Shape `:9,12` promises later solo turns but supplies no state that prevents the next holder-start snapshot from rebatching the same leaves. `src/state.ts:35-58` has no batch attempt or solo-retry record. Also decide whether a conflicting holder may let later leaves publish first or ends its own batch and resolves solo now. Keeping its FIFO place while publishing later members is an actual departure from strict publication order, not merely a rebase detail.

- **F4. Capture all members before touching their worktrees.** Merge phase alone does not prove the former review seat has stopped using its worktree. `src/phase.ts:246-250` can move into merge before the seat ends its pass, and dispatch currently observes live panes separately (`src/next.ts:589-594`). Check that no member seat can edit concurrently, validate its recorded worktree, and apply dependency/readiness/hand-built restrictions to every member, not just the holder. A member's grants do not become the holder's grants automatically (`skills/merge-issue/SKILL.md:31`). Dirty, missing or unready members need an explicit refusal/exclusion outcome rather than accidental consumption of their changes.

- **F5. Batch completion is a recoverable multi-leaf operation.** Every `phase merged` commits one member's state before closure and logging may fail (`src/phase.ts:127-140`). After the top push succeeds, a crash or closure failure can leave some landed members still in merge. Save the tested top, member tips and original ranges before publication, reconcile ancestry before retry, and finish outstanding member transitions without rebuilding or repushing already-landed work. `skills/merge-issue/SKILL.md:49` supplies the existing ancestry rule, but not batch progress. Never dissolve an already-published batch into solo source retries.

- **F6. Completion hooks can remove the active coordinator's resources.** Shape `:11` marks the holder merged before the remaining work. `src/next.ts:737-740` can sweep merged leaves, and `cleanupMerged` closes a merged tab even while its issue remains open (`:652-655`). Idle/exit hooks also close the holder's merged tab (`:845-854`). Protect the actual batch coordinator and the worktree carrying the checked top through finalization and required supplied-context reads. A carried top leaf's idle B is not the active coordinator. Existing per-leaf cleanup must not remove its worktree while the holder still needs it.

- **F7. Broadcast inputs and completion signals are not safely retained.** Gather every distinct completion owner's briefs and evidence before the first phase move, as the single-leaf skill already requires (`skills/merge-issue/SKILL.md:53`), because `completeOwner` moves completed folders (`src/phase.ts:146-180`). Broadcast once per completed standalone issue or whole epic, not once per printed child-issue completion: `completeOwner:178` prints “issue complete” for an issue inside an unfinished epic, while `skills/broadcast-issue/SKILL.md:10` defines the allowed broadcast owners. A lost phase reply after its state was committed can also lose the printed completion trigger. Define recoverable completion ownership without automatically resending Discord, which the sender explicitly forbids (`:41-43`).

- **F8. “Check once” needs a finalization rule.** If a per-leaf trailer guard adds a commit after checking, predecessor tips and downstream stack heads can change. `skills/merge-issue/SKILL.md:47` currently demands another check after that remedy. Preflight unchanged member ranges before the expensive top run where possible, and invalidate the tested top if a later correction changes it. Refresh AKROGON_BASE for the actual top worktree, not the holder's original worktree (`:37`). One top push proves the final combined tree, not that every intermediate prefix passes separately. Record that distinction in evidence and do not claim each prefix independently passed the full suite.

## New material operator questions

- **Q1. After a red batch, must unpublished leaves be restored and merged strictly solo, even if one depends on another member's changes?** The shape needs explicit independent patch reconstruction and durable solo eligibility. “No bisection” does not answer whether earlier source must land before a later member can pass.
- **Q2. If the earliest holder conflicts, may the remaining batch publish ahead of it, or must the holder resolve solo first?** Continuing later members changes FIFO publication order. This choice affects starvation and how the turn-release fork treats a retained earlier queue place.
- **Q3. Does batching authorize the holder to operate across all eligible members' worktrees and grants, and should mechanical stack/finalization operations be command-owned?** Today's single-worktree seat contract does not supply that ownership. The choice must be carried into the affected skill and command contracts before handoff.

Q2 about waiting tabs remains unanswered in the proposed shape. It directly affects safe member capture, coordinator/worktree retention and capacity. A numeric batch cap is an additional operator question only if “all eligible waiting leaves” is changed. No unsupported cap or new capacity rule is recommended here.
