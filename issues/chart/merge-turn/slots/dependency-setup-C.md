### 1 · Who installs a worktree's packages, and when?

The install has to match the worktree's own lockfile, which is the file that lists the exact package versions. That file can change in three ways after the worktree is made: the leaf adds a package, a rebase brings in someone else's package, or the batch stacks several leaves and the top commit has a lockfile none of them had alone. So "install once when the worktree is created" is not enough. Checks are run by seats and their workers from the list in `issues/config.yaml` (`skills/implement-issue/SKILL.md:41,55`, `skills/check-issue/SKILL.md:85`, `skills/merge-issue/SKILL.md:37`). akrogon has no setting for a setup command (`src/config.ts:28-49`).

I measured the cost in a scratch folder with framework's `package.json` and `bun.lock`. A first install took 0.44 seconds (599 packages, linked from Bun's shared cache). A repeat install with nothing to do took 0.009 seconds. The result included `markdown-it`.

Research: better-than-training · my measurement above (Bun 1.4.2, 2026-10-05), plus Bun install cache docs (https://bun.sh/docs/install/cache, read 2026-10-05) and Claude Code worktree docs (https://code.claude.com/docs/en/worktrees, read 2026-10-05) · Bun links packages from one shared cache, "so the contents of the package only exist in a single location on disk", which is why an install is this cheap. Claude Code says "A worktree is a fresh checkout, so initialize your development environment there" · Installing is cheap enough to do before every check, so there is no need to work out when an install is needed. That made 1a possible.

- **1a (recommended)** Every check command installs first. Each line under `checks` and `merge_checks` in a repo's own `issues/config.yaml` starts with the install, for example `bun install --frozen-lockfile && bun run hooks:parity`. It wins because the install then happens in the same place, at the same moment and on the same commit as the check, whoever runs it: a seat, a worker, a rebased leaf, or the batch run on the stacked top. Nobody has to detect a lockfile change. The rule carried from the batch decision ("install again when the top commit's lockfile differs") is met without any code. **New in akrogon: no code and no setting.** New elsewhere: the prefix in two repos' config files, one sentence in the setup guide next to `checks` (`docs/guide/setup.md:53-54`), and one sentence in the init skill so new repos get it (`skills/init-akrogon/SKILL.md:20`). Reused: the `checks` list and every place that already runs it. Cost: the same prefix is repeated on every line (six lines in framework), and a line added later without it brings the old bug back for that one command.
- **1b** One new setting, `setup`, written once per repo. `akrogon config` puts it in front of every check command it hands to seats. Same effect as 1a with no repetition. **New: one config key and one small change to what `akrogon config` prints.** Cost: the command a seat runs is no longer exactly what the config file shows.
- **1c** One new setting, `setup`, and akrogon runs it itself when it creates a worktree and after it stacks a batch. **New: one config key, two call sites, and a failure path for a setup that fails or hangs.** Cost: worktree creation runs under the global lock (`src/next.ts` dispatch), so a slow install would block every `akrogon` command. It also misses a rebase done by a seat and a package added by the leaf, so seats would still need a rule.
- **1d** Skill text only: each seat is told to install before its first check. **New: sentences in three skills.** Cost: a seat that forgets brings the bug back, and nothing notices.

Pitfalls avoided: An install that silently changes the lockfile would test something other than the commit. `--frozen-lockfile` refuses to do that and fails loudly when the lockfile and `package.json` disagree. `akrogon phase` refuses a dirty worktree (`src/phase.ts:225-226`), and an install must not trip it. Both repos already ignore `node_modules/` (`.gitignore:3`, `fw:.gitignore:9`), and 11 framework worktrees already hold their own installs. Workers get only the changed-tests command (`skills/implement-issue/SKILL.md:55`). Under 1a that command carries the install too, which a "first check installs" variant would miss. Done-criteria for the leaf: in a new worktree with no `node_modules`, the first check command a seat runs passes without a separate install step. A batch whose carried member adds a package passes its single check run. A lockfile that does not match `package.json` makes the check fail with the install error.

### 2 · Should worktrees keep sitting inside the main checkout?

This is the root cause in the fork: because a worktree sits inside the main checkout (`worktree_root: issues/worktrees`, `src/config.ts:31,128-130`), a missing package is looked up one level higher and found there, old or not. After question 1, each worktree has its own full install, and its own packages are found first. One narrow case remains. A leaf imports a package that is not in its lockfile, but the main checkout happens to have it. Checks pass in the worktree and fail on a fresh clone.

Research: better-than-training · inspected `src/config.ts:128-130`, `src/init.ts:53-55` and `docs/guide/setup.md:56,69`, 2026-10-05 · `worktree_root` is an existing setting. The code resolves it against the repo root and already handles a path outside the repo (the ignore line is only added when the path is inside) · It showed that moving worktrees needs no new setting, so the choice is about risk and effort, not about building something.

- **2a (recommended)** Leave worktrees where they are. **New: nothing.** It wins because question 1 already removes the failure you hit, and the case left over needs a leaf to import a package it never declared. Cost: that case can pass checks and land. It would show up at the next clean install.
- **2b** Move worktrees outside the checkout by changing the existing `worktree_root` setting, per repo. **New: nothing in akrogon. Reused: the setting.** A missing package then fails at once, in every phase. Cost: existing worktrees must be moved and their recorded paths fixed by hand before the next dispatch (`docs/guide/setup.md:69`). Seats would work in a folder outside the repo while writing their records inside it, which may trigger permission prompts in the agent tools. That needs a trial with one leaf before switching.
- **2c** Share the main checkout's packages on purpose with a link. Already ruled out (`CHART.md` Off route): one leaf's package change would spill into every other leaf.

Pitfalls avoided: Choosing 2a does not hide the leftover case. It is named here, and the fix for it is 2b, which stays available at any time because it is only a config value. If you pick 2b, the trial with one leaf is a named step for you before the other repos are switched.
