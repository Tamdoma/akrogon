### 1 · How should merges in one repo be ordered, so that one leaf landing cannot throw away another leaf's check run?

Today the merge seat fetches, rebases, runs every check and then pushes (`skills/merge-issue/SKILL.md:37`), and "ordinary git non-fast-forward refusal serializes competing pushes" (`SKILL.md:39`). The refusal arrives after the run, so the loser has already spent 35 minutes. On 2026-10-05 six framework leaves entered `merge` within 19 minutes (`fw:issues/log.jsonl:1547-1560`). `lane-orphan-check` ran the full suite five times after clean rebases, each `framework:verify:core` taking 1830 to 1848 seconds, and each time the push was "rejected non-fast-forward" because a sibling had landed (`fw:issues/open/skill-rewrite-tooling/lane-orphan-check/review-B.md:85-128`). Every one of those reruns was green. The command has no rule between two merging leaves: `src/next.ts:627` prompts every required seat as soon as a leaf is allocated, and the only cross-leaf rule is `blocked-by` (`src/next.ts:607`). The answer decides whether the order is made before the check run or after it.

Research: practitioner · bors-ng README (https://github.com/bors-ng/bors-ng/blob/master/README.md), Jane Street "Making never-break-the-build scale" (https://blog.janestreet.com/making-never-break-the-build-scale/), GitLab merge trains (https://docs.gitlab.com/ci/pipelines/merge_trains/), Zuul gating (https://zuul-ci.org/docs/zuul/latest/gating.html), all read 2026-10-05 · Every one of them puts an ordering authority in front of the test run and lands exactly the tested commit, and none keeps a rebase-and-retry race once the suite is slow. They differ on speed: Jane Street states that one at a time costs "at least m * n minutes", bors batches to cut that, and GitLab and Zuul test in parallel on spare machines · It ruled out keeping the race, and it showed that a turn removes the repeated runs but not the wait, which is why 1b is a separate option. The GitHub merge queue docs returned 404 and were not read.

- **1a (recommended)** The command gives one leaf per repo the merge turn. A leaf that reaches `merge` while another leaf holds the turn is not prompted. The holder fetches, rebases, checks and pushes as the skill says today. Order is first into `merge`, first served. It wins because no leaf can land during another leaf's run, so the tested commit is the pushed commit, which is what the check-scheduling lock already demands (`issues/chart/check-reruns/forks/check-scheduling.md:24`). It needs no clock, because every phase move already runs under one lock (`src/phase.ts:330`). Cost: the wait stays. Six leaves at 35 minutes means the last one merges about 3.5 hours after the first starts, close to what `lane-orphan-check` waited on 2026-10-05. Total runs drop from about one per leaf per round to one per leaf. A second cost is that one stuck holder now holds up every merge in that repo, where today leaves are independent.
- **1b** Batch. All leaves waiting in `merge` are stacked into one candidate, the checks run once on the top commit, and main fast-forwards to it. Six leaves cost one 35-minute run. Cost: a red batch has no owner. `SKILL.md:43` sends "the leaf" to `check.fix`, and a batch needs a rule for which leaf is put out, or a bisection that reruns the suite. One seat must own an integration of several leaves, which no skill describes. Each leaf's `review-B.md` would cite a commit that contains other leaves. The trailer guard reads `<target>..HEAD` (`src/phase.ts:293-296`), which in a stack includes the leaves below.
- **1c** Keep the race and make losing cheaper, for example by fetching again right before the run. Cost: it removes no rerun for a sibling that lands during the run, and watching the remote during a run is polling, which is locked out (`issues/chart/leaf-run-stalls/forks/red-criterion.md:34`). It does not meet "avoid that completely".

Pitfalls avoided: A turn that only the skill text describes would be a lock that an agent seat holds across many tool calls, and a seat that dies would hold it forever. 1a puts the turn in the command, under the existing lock, so no seat holds anything. Operator pushes and hand-built leaves (`src/next.ts:585`) cannot be made to take a turn, so the fast-forward-only push and its retry at `SKILL.md:49` stay as the backstop, as a binding part of 1a. Parallel suites slowing each other (9 at once, per the intake) cannot happen with one holder. The turn is per registered repo, and `src/config.ts:118` already refuses two registered checkouts of one git folder. A done-criterion of the leaf: two leaves put into `merge` together produce exactly one check run each and two fast-forward pushes, with no rejected push.

### 2 · While it is not a leaf's turn, where does it wait, and does it keep its tab and its `max_active` slot?

A leaf enters `merge` from review with both panes already open. Seat B's session is the same one that did the review: `lane-orphan-check` shows session `01a10c08-ecbb…` on its review move and on its `merged` move (`fw:issues/log.jsonl:1554,1608`). `max_active` (default 3, `src/config.ts:15`) is only checked when a leaf has no live tab (`src/next.ts:334-337`), and a leaf counts as active while it has a live pane and is not `merged` or `failed` (`src/next.ts:309-312`). So a waiting leaf that keeps its tab keeps its slot, and a leaf that gives up its tab must win a slot again before it can merge. The stall notice only fires for a busy pane (`src/next.ts:210-215`), so an idle seat that was never prompted is not reported as stalled.

Research: better-than-training · inspected `src/next.ts:305-337,627`, `src/routing.ts:35`, `fw:issues/log.jsonl:1554,1608`, plus GitLab merge trains (URL above, read 2026-10-05): "the extra merge requests are queued until a pipeline completes" · Queue tools keep a waiting item as a visible queued entry that still holds its place, and they do not tear it down. The inspected code shows that tearing down the tab costs the review context and puts the turn behind the capacity check · It ruled out releasing the tab (2c). No practitioner source about agent seats waiting for a merge turn was found.

- **2a (recommended)** The leaf stays in phase `merge`, unprompted, and keeps its tab, both panes and its `max_active` slot. `akrogon status` names the holder and shows each waiting leaf as waiting, with its place. It wins because nothing new exists: no phase, no migration of leaves already in `merge`, and seat B starts its turn with the review still in its session. Cost: waiting leaves hold capacity, so with the default of 3 a queue of three stops new leaves from starting. That is also useful, because a leaf started while three are queued would only join the back of the same queue.
- **2b** A new phase before `merge`, such as `merge.wait`, with the tab and slot kept. The wait is visible in the phase name and in `issues/log.jsonl` without any status change. Cost: a new entry in `src/routing.ts:2-13`, every skill and guide page that lists phases, an extra move per leaf, and a decision for leaves already in `merge` when the change ships.
- **2c** The waiting leaf's tab is closed and its slot freed, then the tab is made again at its turn. New leaves can start during a long queue. Cost: seat B loses its review session. `allocate` wipes the leaf's scratch folder when no tab is live (`src/next.ts:369-370`). The leaf whose turn it is can be refused a tab by the capacity check, so the turn holder may be unable to start.

Pitfalls avoided: A wait that the operator cannot see looks like a hang. 2a makes the status line a done-criterion: with two leaves in `merge`, status shows one holder and one waiting leaf with its place. A waiting leaf must not be flagged as stalled, and the inspected rule already covers it because only busy panes are timed (`src/next.ts:210-215`); a done-criterion confirms no busy notice for an unprompted seat. First-served order needs the time a leaf entered `merge`, and `state.yaml` holds no such value today (`src/state.ts:35-58`), so the leaf records it at the move rather than reading it back from the log. The next leaf must be prompted when the turn passes, and today a completion only wakes `blocked-by` dependents (`docs/guide/limits.md:11`, `src/next.ts:681-692`); that wake is the subject of `forks/turn-release.md` and is pending there.
