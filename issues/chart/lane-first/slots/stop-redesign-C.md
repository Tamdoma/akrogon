# Slot C review — stop redesign proposal (`lane-first`, `5debd8b9`)

Removing `SIGSTOP` eliminates F11/F12/F13 cleanly, and keeping the land hold alive after `land` dies solves F10 without ever freezing locks or holding the line indefinitely. However, three concrete breaks remain in the proposed design as stated:

## Break 1 — Land hold record has no verify-pass unit name, and `systemctl` in `live()` breaks sync callers and stalls `lineLock`

- `src/land.ts:184-196`: the land hold record stores only `run` (its own random UUID) and `attempt`; it carries no verify-pass unit name. One `landAttempt` (`src/land.ts:213-225`) launches multiple passes over time (head verify at `:216`, base verify at `:224`, post-restack reruns), each with its own `akrogon-verify-<uuid>` (`src/verify-pass.ts:56-58`, `src/verify.ts:1045-1058`).
- `src/admission.ts:88-89`: `live(record, boot)` is synchronous and called inside sync exports `liveRuns()` (`:106-118`), `lineRuns()` (`:136-158`), `nested()` (`:94-104`), and `callerScope()` (`:277`), and every `POLL_MS = 1000` inside exclusive `lineLock(repo)` (`:161, 170-175`). Checking systemd (`systemctl is-active`) inside `live()` breaks sync callers and blocks `lineLock`.
- **Fix:** Check pass liveness synchronously from disk via `listPassRecords()` (`src/verify-pass.ts:72-81`) matching `entry.record.repo === record.repo && entry.record.caller.attempt === record.attempt && passLive(entry.record)` (`:100-105`; `pending: true` is written before `launchPass` at `src/verify.ts:1059-1067` and bounded by `PENDING_MS = 30_000`, so a mid-launch kill cannot strand the hold forever).

## Break 2 — Liveness = `land PID || verify-pass` still reopens F10 once `verify-pass` stops before its detached check scopes finish or fail to stop

- Every check launched by `verify-pass` runs in its own detached `akrogon-run-<run>.scope` in `akrogon-land.slice`, NOT inside `akrogon-verify-<id>.service`. Non-`full` checks (e.g. `framework`'s `verify`, since `framework/issues/config.yaml` has no `full:` list) do NOT stay in `lineRuns()` on their own once `state === 'live'` (`src/admission.ts:144-147`).
- `src/stop.ts:103` stops `passes` **before** `live` check scopes (`stopUnits([...passes, ...live.flatMap(matched)])`). Once `land` is dead (from the slice stop) and `akrogon-verify-<id>.service` stops, BOTH `land` PID and `verify-pass` are gone — while `akrogon-run-<check>.scope` is still stopping (up to 5 s) or failed to stop (e.g. `Access denied`, awaiting retry).
- At that point `live(hold)` flips `false`: `lineRuns()` (`src/admission.ts:144-150`) stops seeing the hold and `sweepStale()` (`:251-265`) deletes the hold file, admitting the next repo run beside the still-running check scope (reopening F10).
- **Fix:** A land hold record (`record.land === true`) must remain live while **its own PID is alive OR any live pass with `repo === record.repo && caller.attempt === record.attempt` exists OR any live non-land run record in `runs/` with `repo === record.repo && attempt === record.attempt` exists** (checking non-land records by direct PID/start_time only, so `live()` never recurses).

## Break 3 — Round-4 stop order (`cancelLeafRuns` before slice stop) lets a cancelled land hold admit new checks AND lets `land` react to cancelled waiting checks as a red verify

Two races occur if `cancelLeafRuns` runs before `stopUnits([leafSlice])`:

1. **New check admitted under a cancelled land hold (`src/admission.ts:122-130, 175-195, 233-235`):** while `stopUnits([leafSlice])` is stopping `land`, `verify-pass` (still alive in `akrogon-land.slice`) can finish check 1 and start check 2 (`checkedRun` → `withAdmission` → `awaitTurn`). Neither `holds()` (`:122-130`) nor `holding()` (`:178-180`) inspects `hold.cancel === true`, so `awaitTurn` promotes check 2 directly to `state: 'live'` (with `cancel: undefined`). Check 2 launches a new `akrogon-run-*.scope` outside `cancelLeafRuns`'s `live` snapshot and escapes `stopLeaf`.
2. **Cancelled waiting check wakes `land` into `repairExit`, and `land` can launch a fresh pass (`src/admission.ts:174, 234`, `src/verify.ts:973-981, 1067`, `src/land.ts:216-235`):** `cancelLeafRuns` immediately sets `waiting` records to `state: 'cancelled'` (`src/admission.ts:234`). If `verify-pass` has a waiting check when `stopUnits([leafSlice])` fails (or lags past `POLL_MS`), `awaitTurn` throws (`:174`), `verify-pass` exits `1`, and `land` (still alive in `leafSlice`) reads exit `1` (`src/verify.ts:980`) and runs `repairExit`. Similarly, snapshotting `passes` before `stopUnits([leafSlice])` completes misses any pass `land` calls `launchPass` on (`src/verify.ts:1067`) before exiting.

- **Fix:**
  1. In `awaitTurn` (`src/admission.ts:171-195`), if any live land hold for `record.repo` with `hold.attempt === record.attempt` has `hold.cancel === true`, cancel/reject the incoming run (`writeRecord({ ...record, state: 'cancelled' })` and throw) instead of admitting it.
  2. In `stopLeaf` (`src/stop.ts:88-114`), order as: `endSeats` → **`stopUnits([leafSlice])` first** (if it fails, throw immediately — nothing was cancelled and `land` was never provoked, while Break 1+2's liveness keeps the hold alive if `land` died with a pass/check running) → `cancelLeafRuns` (no `pause` callback; `land` is already dead, so it cannot launch new passes or react to a cancelled check, and every run of the leaf including any promoted during the slice stop is cancelled/collected) → snapshot `passes` and run `stopUnits([...passes, ...live.filter((r) => r.land !== true).flatMap(matched)])`.
