# Names rebuttal — Slot B

1. The merged zero-match rule is attributed too strongly to B. My notes recommend preserving the parked-leaf diagnostic and discovery errors, but explicitly leave empty-owner recognition and its no-leaves diagnostic open. Exact correction: restrict the existing missingLeafMessage rule to no recognized candidate with no relevant discovery error. Ask whether an owner with no valid leaves is recognized, and what happens when its leaves are all unreadable. `src/next.ts:1197-1201` already distinguishes discovery failure from an ordinary miss, while `src/state.ts:146-158` only diagnoses leaf names, not empty owners.

2. I retain refusal for distinct same-name owner/leaf candidates, while accepting A's factual point: identical selected sets cannot start the wrong group in that invocation. The case against collapsing them is the explicit intake contract and unstable meaning as the issue grows. #59 asks for refusal when a leaf slug and issue name collide. An issue with one leaf and that leaf can select the same work today, but adding a second leaf makes them select different work. Set-based collapsing would make a formerly successful command ambiguous after that addition, despite neither entity changing its name. Rejecting the distinct candidates consistently makes that boundary explicit from the start. The cost is real: docs/guide/parts.md documents same-name issue/leaf folders as normal, so existing users need a path. Present both options and this cost to the operator. Do not treat the intake's collision requirement as already satisfied by equal-set collapsing.

3. The operator also needs to settle owner recognition, not only stores and precedence. Deriving owners from valid leaf ancestry avoids imposing new index-file requirements (`src/state.ts:114-129`, `src/status.ts:174-182`), but cannot identify an empty owner from leaves. Decide whether empty folders/indexes are candidates or whether this feature recognizes only owners containing discoverable leaves. Preserve unreadable-record errors either way. Without that decision the implementer must choose the behavior for an empty or entirely unreadable owner.

4. Clarify the names-win alternative's path escape. My notes use ./ and absolute paths as examples of explicit path syntax, not the only valid forms. Slash-containing relative paths such as issues/open/<epic>/<issue> must remain supported under the intake's path-compatibility requirement. Existing path selection is at `src/next.ts:1173-1195`.
