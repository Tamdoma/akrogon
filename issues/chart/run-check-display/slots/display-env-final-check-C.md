# Final-shape check: display-env, slot C

## Problem 1: `[C2]` and `[C4]` — `UnsetEnvironment=` in `launchLand` regresses post-reboot automatic merges from `akrogon-listener.service`

- **Fact**: `systemd/akrogon-listener.service` is `WantedBy=default.target` with `After=basic.target` and no `After=graphical-session.target`. At login/boot, `default.target` starts `akrogon listen` *before* `graphical-session.target` imports `DISPLAY` and `WAYLAND_DISPLAY` into `systemd --user`. Until `akrogon-listener.service` happens to be restarted later, `akrogon listen`'s own `process.env` lacks `DISPLAY` and `WAYLAND_DISPLAY`. Making `launchLand` pass `-p UnsetEnvironment=DISPLAY -p UnsetEnvironment=WAYLAND_DISPLAY -p UnsetEnvironment=XAUTHORITY` whenever its caller lacks them actively strips the live user manager's display variables from `akrogon-land-<attempt>.service` and the `akrogon-verify` pass it starts.
- **Evidence**:
  - Tier 1 (live host read, 2026-11-25): `systemctl --user show -p ActiveEnterTimestamp default.target graphical-session.target` reported `default.target` active at `Tue 2026-11-24 13:58:14 CET` vs `graphical-session.target` at `Tue 2026-11-24 13:58:17 CET` (3 s later). `systemctl --user show -p ActiveEnterTimestamp,After,WantedBy akrogon-listener.service` showed `WantedBy=default.target`, `After=home.mount app.slice -.mount basic.target home-ivan.mount`, and `ActiveEnterTimestamp=Wed 2026-11-25 00:03:56 CET` (the live listener only holds `DISPLAY`/`WAYLAND_DISPLAY` right now because it was restarted 10 h after login).
  - Tier 1 (source read, 2026-11-25): `systemd/akrogon-listener.service` (`WantedBy=default.target`), `src/next.ts:1067,1175` (`akrogon listen` invokes `launchLand`), `framework/issues/config.yaml:7` (`pass_env: [DISPLAY, WAYLAND_DISPLAY, XDG_RUNTIME_DIR]`).
  - Tier 1 (probe, 2026-11-25): `check-probe-c-unsetenv2-1795569154849-6883.log` confirmed `systemd-run --user -p UnsetEnvironment=DISPLAY -p UnsetEnvironment=WAYLAND_DISPLAY -p UnsetEnvironment=XAUTHORITY` removes all three from the transient service despite them being present in `systemd --user` manager env.
- **Consequence**: After any reboot (or compositor restart) until `akrogon-listener.service` restarts, every automatic merge launched by `akrogon listen` loses display access — breaking Q2b and regressing existing repos like `framework` whose `pass_env` already relies on `akrogon-land` inheriting `systemd --user`'s display variables (conflicts with Signpost 6a). Remove `UnsetEnvironment=` from `launchLand` (emit `--setenv=` only when the caller defines the variable, and update `[C4]` so `launchLand` asserts no `--setenv=` and no `UnsetEnvironment=` when absent). Keeping `UnsetEnvironment=` on `launchPass` alone does not hit this race because `akrogon-land` inherits the live manager env before invoking `verify`.

## Problem 2: `[C2]` — `"Never --setenv=NAME= with an empty value"` conflicts with `launchPass`'s `passForwarded` loop on empty-string caller values

- **Fact**: `[C2]` specifies both `"passForwarded gets the names from the shared list"` and `"Never --setenv=NAME= with an empty value"`, while `launchPass` (`src/verify.ts:925,939`) emits `--setenv=${name}=${env[name]}` for every `name` in `new Set([...passForwarded, ...repo.config.env, ...repo.config.pass_env])` where `env[name] !== undefined`. If the caller sets `DISPLAY=''` (empty string, which is `!== undefined`), `launchPass` emits `--setenv=DISPLAY=`, setting an empty `DISPLAY=` in the service. Worse, if the three names stay in `passForwarded` (or appear in a repo's `pass_env`) alongside a separate `UnsetEnvironment=` helper that treats `''` as absent, `launchPass` would emit both `--setenv=DISPLAY=` and `-p UnsetEnvironment=DISPLAY` for the same unit.
- **Evidence**:
  - Tier 1 (source read, 2026-11-25): `src/verify.ts:925,939` (`names.filter((name) => env[name] !== undefined).map((name) => \`--setenv=${name}=${env[name]}\`)`).
  - Tier 1 (probe, 2026-11-25): `check-probe-c-unsetenv2-1795569154849-6883.log` confirmed `systemd-run --user --setenv=DISPLAY=` sets `DISPLAY=` (empty string) in the service environment rather than unsetting it.
- **Consequence**: Implementers face an ambiguity/bug on `DISPLAY=""` (or `WAYLAND_DISPLAY=""`, `XAUTHORITY=""`), especially in repos whose `pass_env` also lists those names. Clarify `[C2]` by choosing one consistent rule: either handle the three non-runtime display names outside `launchPass`'s generic `names` filter (excluding them from `names` even when listed in `pass_env`) with a single helper checking `value !== undefined && value !== ''` (and specify that `''` is treated as absent for the three display names), or clarify that `"Never --setenv=NAME= with an empty value"` only forbids `?? ''` synthesis on `undefined` (as `launchLand` uses for `PATH`/`HOME`).
