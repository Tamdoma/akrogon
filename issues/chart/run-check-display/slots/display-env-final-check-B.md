# display-env final-shape check, slot B

## P1. [C1] leaves a hole that undoes its own purpose: `XDG_SESSION_TYPE` and `WAYLAND_SOCKET` still reach verify and land payloads

Fact: [C1] excludes `XDG_SESSION_TYPE` and `WAYLAND_SOCKET` from the copied list "keeps every headed proof on the probed X11 path", and [C2]'s `UnsetEnvironment` rule covers only `DISPLAY`, `XAUTHORITY`, `WAYLAND_DISPLAY`. But the exclusion is unenforceable on the service path, in both directions:

- The user manager's environment carries `XDG_SESSION_TYPE=wayland` on this host (along with the whole login-session block: `XDG_SESSION_DESKTOP`, `XDG_CURRENT_DESKTOP`, `XDG_VTNR`, `XDG_SEAT`…). The verify-pass and land services inherit it. Probed 2026-11-25 (`systemd-run --user --pipe env`): full block present. This part C2 does not need to fix for the other names because the manager rarely carries caller-created variables — but `XDG_SESSION_TYPE` is a manager-carried name by definition.
- Worse, inheritance re-applies at every layer: probed 2026-11-25, `systemd-run --user --pipe --setenv=DISPLAY=:99 systemd-run --user --scope env` — a scope launched inside a transient service that itself was stripped of `XDG_SESSION_TYPE` still shows `XDG_SESSION_TYPE=wayland` (plus the corrected `DISPLAY=:99`, confirming `--setenv` propagates as expected). So even if the launchers unset it, `runUnitArgv`'s own `systemd-run --scope` inside the service re-injects it into the checked command's environment unless the scope launch also unsets it. The same applies to `WAYLAND_SOCKET` only insofar as a caller ever holds it; unlike the display names it is never legitimately forwardable, and run-check never copies it.

Evidence: `better-than-training`, two live `systemd-run` probes on this host 2026-11-25 (control env block, nested scope test); D's probe as recorded in the merged file that `XDG_SESSION_TYPE=wayland` makes a default Chromium launch pick native Wayland.

Consequence: as written, verify/land payloads receive `XDG_SESSION_TYPE=wayland` while run-check payloads never do. A headed Chromium proof then selects ozone-Wayland under verify and ozone-X11 under run-check — a display-path divergence between the two doors, which is exactly the failure class Q2b exists to remove, and it contradicts C1's stated purpose of keeping every headed proof on the probed X11 path. (The X11 path was probed green by all four slots; the default-launch Wayland path was probed only as a selection observation, not a green window.) The correction needs one addition, and it must sit in `runUnitArgv` or `constructedEnv`'s shaping for the service path, not only in the launchers: `XDG_SESSION_TYPE` and `WAYLAND_SOCKET` are unset unconditionally — for every caller, since no caller value is ever forwardable — at the innermost layer that re-injects them. Concretely the run scope launch needs `-p UnsetEnvironment=XDG_SESSION_TYPE` (multi-name form carries `WAYLAND_SOCKET` too) or an `env -u` entry beside the existing `-u XDG_RUNTIME_DIR` handling; the launcher-level unset alone is proven insufficient by the nesting probe. Done-criterion 3's argv assertion should cover this unset as well.

No other problem. Checked and holding:

- [C2]'s per-name conditional `--setenv`/`UnsetEnvironment` shape matches probed systemd behavior: `UnsetEnvironment` removes the manager-inherited value entirely (probed 2026-11-25), applies after `Environment=` so the two rules never fight, and is never emitted for a name the caller holds. Signpost 1a/2a/3a/6a compliant.
- [C3] is not ideal but sound: the payload `XDG_RUNTIME_DIR` divergence (verify always carries it, run-check only with the caller) is theoretical on systemd hosts, because pam/systemd guarantees the real runtime dir for any session that can launch user services at all, and `runtimeDir()`'s `/run/user/$UID` fallback converges to the same path there. Docs stating it, as the shape requires, discharges the honesty cost. The criterion-4 assertion (`launchLand` carries one `XDG_RUNTIME_DIR`) matches the dedup pitfall already recorded.
- [C4] testability holds: `FAKE_SYSTEMD_RUN_LOG` captures the launched argv in the existing harness (tests/helpers.ts fake-systemd-run seam), free and hermetic per signpost 2a.
- The dropped headed-launch leaf proof is a scope choice, not a conflict: criterion 1 tests the exact mechanism being changed (the copy) at the real CLI, and the headed integration was already demonstrated by the charting probes; akrogon having no Playwright dependency makes a suite-level headed test unjustifiable. No problem.
