# Rebuttal: shell-sweep, slot D (disagreements only)

Against fork-shell-sweep-merged.md. Code re-checked 2026-11-25 at this checkout.

## Q1

R1. I disagree that option a alone satisfies the lock, on the merged reason "the decision's second sentence, word for word". The lock has two sentences (seed-decision.md section "Taken"): a seat whose turn ended counts as idle for delivery even with a background shell running, and leftover shells end when the phase advances. The first is the outcome; the second is the mechanism. A alone leaves the post-advance tail shell (merged Q1 cost line) with its turn ended and no delivery, failing the first sentence. Consequence if the literal reading stands: the leaf can close while a known trigger of the seed stall remains, covered only by the busy notice that already failed to save the incident leaf (INTAKE.md section "Observation": 4h50m, found by hand).

R2. I disagree with B's quiet period as listed under option c: 30 to 60 min from `busy_since`. `src/next.ts:observeBusy` sets `busy_since` when a seat is first observed `working`, which is before its phase call, and `src/phase.ts:commitMove` preserves it on ordinary advances. A turn that ran longer than the quiet period before advancing has the period already spent, so the first pass after the advance sweeps immediately. Consequence: the race every slot used to reject b (sweep lands while the seat's own `akrogon phase` follow-ups still run inside the seat scope) returns inside option c. The base must be phase entry, not busy start.

R3. I disagree with C's cost against c, "adds a time number with no named source", as a deciding argument. The codebase already carries such constants with equally thin sourcing: `STALL_MS` (1h busy notice) in `src/next.ts:observeBusy`, `RETRY_MS` and `PASS_DEADLINE_MS` in `src/listen.ts:listenCommand`. The quiet bound also has a derivation: it must exceed phase follow-up plus tool-shell exit (seconds) and beat the 1h notice. Consequence if the purity argument stands: the tail-shell case is dropped for violating a standard the surrounding code does not meet.

## Q2

R4. I disagree with C's signal plan as merged ("TERM to the whole collected set, a short wait, then KILL survivors") under option a. A seat's phase move runs under the global lock (`src/phase.ts:phaseCommand`, the `withLock` around `transition`); a wait inside commitMove's sweep holds that lock for every repo and delays the agent's own phase tool result. The merged note is right that pure a has no later sweep to KILL survivors; the consequence of C's plan under a is either that lock-held wait, or TERM-ignoring shells that never get a KILL and never flip claude to `done`, so the stall persists in exactly the case where TERM was not enough. KILL needs a delivery-time recheck of already-TERMed processes, which needs no quiet period. That is part of c's machinery, and a cannot borrow it for free.

R5. I disagree with the B,C scope of the match: shells anywhere in the seat scope. Classifying every scope process kills shells inside helper subtrees (codex's `codex-code-mode-host` or `node_repl` running code through a shell is plausible for a code-execution host; unobserved, low confidence), which is the helper harm used to reject option b, one level down. Its only gain over direct shell children of the harness is a shell that has been reparented away before the sweep, which requires its intermediate parent to have already exited; at the advance, the tool shell that launched a leftover is normally still alive, so the descendant walk already collects it (census 2026-11-25: the working claude seat's whole shell tree hung off one direct bash child). Consequence if scope-wide stands: larger kill surface, and classification of processes whose owner is a helper, bought with an unobserved case.

## Q3

R6. I disagree with C's "one shared predicate also used by `activeCount`/`liveSeat` (capacity hold) and by `broadcastInProgress`". Two facts. First, `activeCount` does not call `liveSeat`; it counts leaves from its own hc terminal listing by label (`src/next.ts:activeCount`). `liveSeat` has exactly two other uses (`src/next.ts:allocate` and the observeBusy pass in `dispatchLeaf`). Second, sharing the lost-seat predicate through `liveSeat` changes `allocate`: a recovered shell seat counts as not live, so allocate runs `capRefusal` before relaunching it, while `activeCount` still counts that same leaf as active because its recovered terminal is live and labelled. Consequence: on a repo at cap after a reboot, a recovered leaf waits on capacity it is itself holding, and never reaches the lost-seat path that would replace it. `broadcastInProgress` (`src/reconcile.ts:broadcastInProgress`) is the same error in the other direction: it currently keeps cleanup stalled while a merged leaf's B seat is not idle/done, status null included; filtering the recovered shell out of its live list lets reconcile proceed over a broadcast that will now never be sent, silently. The recovered-shell evidence belongs in dispatchSlot's lost branch only, where the replacement is.

## Open questions

R7. I disagree with "Option a still ends their shells, so the fix stays harness-independent" for codex and agy. Option a ends shell processes; whether that unblocks a codex seat depends on where codex's background work runs. The resting codex helpers in evidence (`node_repl`, `codex-code-mode-host`, census 2026-11-25) are exactly the processes codex would run background code work in, and option a deliberately spares them. If codex masks through them, no shell dies that matters and no flip happens. Consequence if "harness-independent" stands in the merged record: the chart can close believing codex covered, and a later codex stall gets misfiled as a new defect class instead of the already-named unobserved case.
