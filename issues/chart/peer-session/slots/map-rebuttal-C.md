## D1. How the session is found, and A's anchor

A's anchor removes the weakest parts of my pick. Anchoring the co-location check on A's agent session value instead of the caller's pane id removes the stale HERDR_PANE_ID concern (cross-session-reads: herdr injects it on focus), and removes most of my FG4 duplicate-refusal cost, because a duplicate A pane id in another session no longer blocks a clean peer hit. A's supporting claim is still overstated: live recheck 2026-10-24 (read-only pane lists) shows workspace w8 in both infra and mdconsultingny, but its full pane ids are disjoint there (infra w8:p18, w8:pNP, w8:pV5, w8:pV6 and others; mdconsultingny only w8:p1), and 55 panes across 3 running sessions had no duplicated full pane id. "Collisions refuse often" is not supported; exact-id collision is a real but so-far unobserved case, most likely on a young session's sequential ids.

A's anchor does not remove the objection that the mechanism must be supplied and kept fresh. It renames the explicit input instead of eliminating it, and it fails closed in cases my pane lookup handles:

- F1 Supply. Only door-reset already receives A's harness session (door-reset.ts:159 usage, checked at :169). peer-restart and peer-create receive A's pane only (peer-restart.ts:134,137; peer-create.ts:50). peer-ask and peer-wait receive neither A's pane nor A's session. So the anchor must arrive as a new argument everywhere (the argv and skew cost merged D1 assigns only to B), or scripts must read seats.yaml, which before the chart folder exists is kept with the door's temporary files, not at a path any script knows (SKILL.md:39), and peer-create runs at open. A's map names neither route.
- F2 Fresh or rotated A. A says codex showing no session until its first exchange is irrelevant because A is the anchor. That is backwards for a fresh codex door creating peers at open: the anchor value is the thing not yet shown (SKILL.md:29, codex shows `none` until its first exchange). A pi door's session value can also change without the pane changing; peer-wait's identity check deliberately ignores pi session changes for that reason (peer-wait.ts:139-154). And after door-reset, seats.yaml holds the old A's session; A says the fresh A "re-anchors with its new session id" without naming how the fresh A learns that id. Seat entries are appended from peer outcome lines and restart lines (SKILL.md:39), not from A's own reset. In all three cases the anchor scan finds zero hits and refuses a healthy door, where a pane lookup succeeds.
- F3 Wrong, not just absent. A's rule as written picks the session holding a pane whose agent_session.value matches, without requiring that pane to be A's pane. If A's recorded session is stale and that harness session has been resumed in a pane in another herdr session, the scan uniquely selects the wrong session, and the peer check that follows is existence of the peer pane ids in that session, which a same-id pane satisfies. The anchor proves where an instance of that harness session lives, not where A is. What removes this is anchoring on the pair (A's pane id and A's agent session value together), which neither A's map nor the merged D1 states. "An id herdr cannot repeat" is also unproven as stated: herdr reports a harness-supplied value, and the same harness session resumed in two panes would report it twice. That case refuses safely under zero-or-several, but it is a refusal cost A's map does not count.

Updated D1 position: the pair anchor (A pane plus A agent session, one hit required) is a better co-location anchor than my caller-pane anchor, and I would take it over mine where the supply route in F1 is settled and F2's fresh-A case has a named route. Until then it does not beat bare pane lookup outright; it trades my duplicate-refusal cases for anchor-absent cases. One further point the anchor raises and no map takes: for reusability across D2, the same trick anchors a peer on the peer's own recorded agent session where one exists (seats.yaml per SKILL.md:39, and the exchange already carries it for peer-wait), which works even for a cross-session peer. It is unavailable at first contact with a supplied pane and unreliable across peer-restart, whose purpose is to replace that session, so it cannot be the only mechanism.
