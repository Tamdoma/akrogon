## Findings and confidence

- **F1 — Confirmed, high confidence:** at 2026-11-04T12:33Z, `hc get t15 --json` reports `state: live`, `status: null`, `reported: true`, `status_ms: 1793735801327` (2026-11-03T19:56:41.327Z), foreground Claude PID 2943990. `hc ls --json` lists t15 as bash without status while ak-slot-b/t4b and ak-slot-c/t4c, both parented to t15, report working. Other Claude terminals report idle, done and working. This is a missing parent status, not evidence that the parent finished.
- **F2 — Strongly supported cause, exact failing layer unproven:** the job's `state.json` says `template: bg`, `backend: daemon`, `state: working`, detail `docs leaf handed off; now on agent-status-stale chart`. Its `createdAt` is 2026-11-03T19:56:41.307Z, just 20 ms before hc's last status timestamp. `recap.trigger` birth is 19:56:45.793Z. Two live Claude processes, PIDs 201921 and 201946, have `CLAUDE_JOB_DIR=/home/ivan/.claude/jobs/acb047ee`, `HC_SESSION=infra`, `HC_TERMINAL_ID=t15`. The visible foreground process started earlier, on November 3 at 09:07 local time. Background execution and terminal status diverged at the same transition. These checks do not prove whether Claude stopped emitting OSC, its frontend stopped forwarding it, or core mishandled the transition.
- **F3 — Confirmed display mechanism:** `mods/agents-by-tab/tree.js` deliberately synthesizes a parent row with `status: null` when only its children appear in `agents()`. In `main.js`, `render()` ranks the family by the maximum parent/descendant rank. Null has rank zero, children map done to idle, and the section builder maps a zero rank to Idle. Thus children can move the family into Working, then back into Idle without any knowledge of the parent's work. The parent badge itself uses the parent's status, independently of family placement.
- **F4 — Confirmed ownership and test limit:** `~/.config/herdr-app/mods/agents-by-tab` links to `/home/ivan/Work/infra/herdr-setup/mods/agents-by-tab`. Its origin is `Tamdoma/herdr-setup`. Existing `tests/agents-by-tab.test.js` verifies structural ancestry, including silent parents and live/finished ancestors. It does not verify family urgency, missing-status presentation, or daemon-to-terminal status relay. Keep those existing structural guarantees.
- **F5 — Evidence limits:** the screenshot independently shows c-akrogon in Idle while Claude displays `Spinning…`. The displayed age comes from the mod's localStorage state-change tracking, not directly from `hc.status_ms`. A long age alone cannot establish failed reporting because a valid idle state may last indefinitely. I did not reproduce the transition, change a terminal, or inspect Claude/core implementation. I did not confirm the intake's CHILD_SESSION/SESSION_ATTENDED environment claims in the inspected processes.

## Practitioner questions

- **Q1:** At the transition, does Claude emit an explicit status reset, or does emission cease? Does the attached frontend receive worker state but fail to forward it? A captured isolated transition decides Claude versus core ownership.
- **Q2:** What is the intended status contract for a background job viewed in an hc terminal, including blocked, idle, exit, detach, reattach and a replacement foreground process? Which process owns OSC emission?
- **Q3:** Should the sidebar expose the parent's unavailable status separately while the family remains in a child's urgent section? Decide the user-visible meaning before choosing text, color or a new section.
- **Q4:** Is there a supported foreground-only launch mode, and does it survive later interactive backgrounding? If not, O4 is only a written operator rule, not an enforced repair.
- **Q5:** Can one generic missing-status treatment cover all silent ancestors without reading harness-private files? Can the root relay fix likewise cover foreground-to-background-to-foreground transitions without a second status source?

## Pitfalls and proof

- **R1:** Do not infer work from a spinning screen, a live PID, a terminal title, old status age or idle children. The screen supports this incident, but the documented status interface is OSC 7501.
- **R2:** `reported: true` is compatible with `status: null` in this live record. It cannot establish current reporting health. Do not freeze the last working state as a substitute for a current report.
- **R3:** Do not flatten the family or remove the synthesized ancestor to fix its classification. Existing tests intentionally preserve one parent row, including children with their own panes. A no-children case also needs checking because `topLevel()` currently discovers silent parents through reporting descendants.
- **R4:** Keep display proof separate from transport proof. A unit case for a silent parent and idle children proves only presentation. Root-fix proof needs an isolated reporting Claude, background transition, work with idle/no children, completion, blocked state and reattachment, checked through hc. Use an isolated core/session, never t15.
- **R5:** Do not land a Claude job-file watcher in the mod, a legacy-herdr hook, or a temporary akrogon polling bridge. Those add ownership and lifecycle problems while the existing reporting path remains broken. No tests were run because this is a read-only map, not an implementation.

## Recommended split

**D1:** Treat the background-job transition as the strongly supported trigger and missing terminal reporting as the confirmed failure. Seek the root relay repair upstream, first identifying whether Claude or core drops the signal. The upstream repository URL and exact implementation owner remain unresolved by this map. Do not label a herdr-setup-only change as restoring the main agent's status.

**D2:** If the chart includes a locally deliverable change, put truthful missing-status presentation in `herdr-setup`, and state its narrower promise. Keep any proven foreground launch rule in the surviving akrogon herdr-app start path, coordinated with `issues/chart/herdr-app/INTAKE.md`. Follow the taken signposts: written rules before new refusals, whole-family repair only when it adds no parts, new work only, and no dependency on legacy herdr. Do not make the full herdr-app port a prerequisite for investigating the upstream relay.
