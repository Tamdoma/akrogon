One edge case to close in `knownRedReceipt` (`src/verify.ts:218`):

- **`heads` in `knownRedReceipt` (`src/verify.ts:218`) must also require `sameCommands(run.commands, expected) && run.commands.some((item) => item.exit !== 0)` (matching `redRun` at `src/verify.ts:148-152`).**
  - *Evidence (`src/verify.ts:159-165, 218-225, 460-466`)*: If `knownRedReceipt` judges one `head` row at a time where each `expected` command is either `exit === 0` or covered by a linked base run, but `heads` (`src/verify.ts:218`) does not require `sameCommands(run.commands, expected) && run.commands.some((item) => item.exit !== 0)`, then a completed all-green run whose command list is a **superset** of `expected` (e.g., a 2-command `[c1, m1]` run when checking 1-command `[c1]`, or after removing a command from `config.yaml`) will fail `greenRun` (`sameCommands` length mismatch at `src/verify.ts:129`, so `verify`'s fast path does not reuse it) **yet pass `knownRedReceipt` with zero red commands and no base run** (`entryOf(head)?.exit === 0` for every `item` in `expected`), recreating a gate-passes / verify-reruns disagreement.
  - Requiring `sameCommands(run.commands, expected) && run.commands.some((item) => item.exit !== 0)` on `heads` in `knownRedReceipt` (`src/verify.ts:218`) makes `heads` identical to `redRun` (`src/verify.ts:148-152`) and guarantees `knownRedReceipt` never passes a 0-red row.
