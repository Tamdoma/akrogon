# merge-reuse rebuttal: seat C

R1. Open question on retired lessons names the wrong actor and overstates frequency. The fixup is made by the command at the turn's start, only when a rebase resurrects a retired line, before the land run verifies that top (`skills/merge-issue/SKILL.md`, `## merge`). Merge B does not commit it before verify. Reuse misses only for those rare tops, which is correct behavior, not a defect to design around.

R2. D's "33 of 50 reused while c00246dd was live" supports only whole-run cross-scope reuse. Stitching arrived in fbac86c6 (2026-10-25 00:18) and scope was restored in 9aaed138 (2026-10-25 00:38), twenty minutes later (git log, 2026-11-01). Cross-scope stitched coverage (O-cover) has never run live, so that data point should not sit under Q1 accept for both options. Related omission: O-cover does not merely unify two rules, it extends the looser one to verify's fast path. Today the fast path needs one whole green run (`src/verify.ts:157-167`) while the gate stitches (`src/verify.ts:462-465`); under O-cover, verify exits 0 on entries spread across runs that never shared one setup or checkout. The test O-cover cites (`tests/verify.test.ts:1271`) seeds that split by hand; a real pass sequence writes a whole row through `runOnce` per-command reuse. That makes O-whole stronger and O-cover's "keeps the member-receipts gate" weaker than the merged notes present.

R3. B's reason for keeping red scope-bound does not hold. The link between a red head and its base comparison is `compares === head.run` plus sha (`src/verify.ts:232`); scope adds no linkage. Keeping `run.scope === scope` in `redRun` (`src/verify.ts:149`) and the `knownRedReceipt` head filter (`src/verify.ts:218`) while dropping it for green only makes merge `--known-red` re-execute a head already shown red at leaf scope. It cannot recreate the 2026-10-25 disagreement, because the gate and verify both fall back to the same `knownRedReceipt` function (`src/verify.ts:466`, `src/verify.ts:897`). The red decision is rerun cost only, not correctness, and the merged notes should say so.

R4. Missing from both Q2 options: neither takes the newest evidence. The gate passes if any completed run on the tree holds a command green (`src/verify.ts:465`, `some`), and `greenRun` returns the first match in file order (`src/verify.ts:159`, `find`). A later completed red of the same command on the same tree does not invalidate the earlier green under O-cover or O-whole. With merge reuse, that means a leaf green followed by a same-tree red rerun still merges on the old green. The two red merges in the data were exactly red-after-green on one tree. Whether newest-per-command should win is undecided and unmentioned.
