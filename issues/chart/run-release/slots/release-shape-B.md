# Slot B: release-shape blind notes

Q1 — Machine state location

1. Pick, reason, cost: Keep today's state home, found through one stable installation pointer independent of `toolRoot` and cwd. This separates execution from workspace edits without migrating live coordination state. Preserve explicit `AKROGON_HOME` overrides. Cost: the workspace remains required for state, and moving it requires updating that pointer.
2. Rejected option: Moving state to `~/.akrogon` is a reasonable separate migration, but unnecessary for the approved runtime separation. It introduces a cutover between old and new writers and locks, plus rebasing relative repo paths. Do not combine that risk with replacing the runtime.
3. Evidence: `operator`, intake and run-location Taken/carries, read 2026-10-16: operation from the main folder and workspace-held records must survive; this does not require moving machine state. `better-than-training`, `src/config.ts:195–210,238–245`, read 2026-10-16: state defaults to the code root and relative registrations resolve against state home. `src/sync.ts:26` and `src/admission.ts:40–46,84–99` put coordination and live-run lookup there too. These consumers make preserving the existing home the smaller change.
4. Pitfalls and removal: Two homes mean separate locks and invisible live runs; require installed commands, release helper scripts and development invocations to resolve the same home before operating. A missing pointer must fail clearly, never silently initialize another home in a release. Keep state and registration unchanged during activation and rollback. Define the pointer outside the immutable release and independent of the caller's directory.
5. Missing question: What exact shared discovery interface do `akrogon`, `bun src/akrogon.ts`, and skill scripts importing `src/config.ts` use, including when launched outside the workspace? Settle that interface, not just the directory name.

Q2 — Old release deletion

1. Pick, reason, cost: Keep current, the previous successfully activated release, and every older release still in use; remove other completed releases only after proving them unused. A rollback target remains available while long commands survive multiple deploys. Cost: retention is not a hard disk-count cap, and release use needs explicit lifetime tracking.
2. Rejected option: A fixed count alone can delete a release still used by a long invocation. Adding the same live-use exemption makes it another retention preference, not an alternative safety mechanism. Retaining everything avoids premature deletion but leaves unbounded storage without a cleanup rule.
3. Evidence: `operator`, run-location Taken, read 2026-10-16: immutable releases and pointer rollback are already chosen. `better-than-training`, `src/akrogon.ts:54–56,141–148` and `src/reconcile.ts:257–287`, read 2026-10-16: commands load modules dynamically, while the existing process helper observes only cwd/fds, not which release an invocation will still need. `src/admission.ts:23–36,137–176` records admitted runs, not every CLI or skill-script consumer. Neither existing mechanism proves release quiescence.
4. Pitfalls and removal: Do not interpret “no process runs inside” as no cwd/fd match. Pin a concrete release for each consumer and protect its lifetime; serialize acquiring that protection with release selection/deletion. Pin all imports to that release rather than resolving `current` again midway. Retain when use cannot be established safely. Count previous activation, not previous failed build. The tracking mechanism needs a concurrency proof before deletion is authorized.
5. Missing question: Which consumers must hold a release alive: ordinary commands, admitted children, plugin callbacks, and agent sessions retaining absolute paths to old skill scripts? Who releases each claim after normal exit or a crash? Without that boundary, neither deletion option is complete.

Q3 — Failed release preparation

1. Pick, reason, cost: Keep the existing validated release active and continue dispatch; report the failed stage immediately and retry at the next normal trigger. Include attempted revision when known, active revision and the actual error. Cost: a failed deployment delays new behavior and may need operator repair, but an unrelated install/network failure does not stop existing work.
2. Rejected option: Stopping dispatch on any candidate-build failure makes a healthy installation depend on every update attempt succeeding. Reserve refusal for having no usable active release, not failure to prepare its replacement. First installation has no last working release and must report failure rather than pretend activation succeeded.
3. Evidence: `operator`, intake's requirement that workspace edits never block or undo deploy, read 2026-10-16. `better-than-training`, `src/self-update.ts:223–232,258–260` and `src/next.ts:1383–1413`, read 2026-10-16: update failures already report and dispatch continues. `src/self-update.ts:192–201` applies some links before reporting conflicts/reload failure; `src/install.ts:63–66` also changes external links and registrations. Those side effects must not be treated as harmless staging.
4. Pitfalls and removal: Build and validate the candidate without changing active code, dependencies, state or active links; activate only a complete candidate. A pointer flip alone does not undo partial external link/plugin/systemd changes. Define which such operations are one-time installation versus release activation, and their failure recovery. Keep deployment independent of record sync and workspace checkout movement. A failed retry must preserve both current and the rollback release.
5. Missing question: What is the activation boundary for links/plugin/systemd, and can the previous release still read shared state after the new one writes it? Rollback and overlapping old/new invocations need a compatibility rule; an atomic code pointer does not provide it (`src/config.ts:23–30` uses a strict global schema).

Scope: permitted context and repository code only. No peer notes read, tests run or live probes performed. The release-use mechanism and activation transaction above are proposed requirements, not existing proven capabilities.
