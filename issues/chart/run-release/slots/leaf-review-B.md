F1 — The cutover mechanism does not satisfy the single-home lock.
Evidence: `/home/ivan/.claude/jobs/6a0d8d81/tmp/rr/state-home/design.md:25–31` takes only the old global `.lock`, then leaves old-process writes as “show it is harmless or carry it over.” But old admission writes use `runs/locks/<slice>`, not that lock (`src/admission.ts:43–46,160–176`), and old `globalHome()` keeps resolving the tool root (`src/config.ts:195–198`). An old verify can start another checked command after the copy, creating a live admission record only in the old home (`src/verify.ts:154–168`). New commands then cannot see it. Two new commands sharing a migration lock, as brief criterion 4 tests, do not prove the binding promise that old and new writers never operate two homes.
Required correction: make old-writer cutover a delivered mechanism and criterion, covering an already-running command that admits another run and ends it during migration. Specify how those writers drain or share the new authority before cutover completes. “Harmless or carry it over” cannot remain an unowned exception to the single-home decision.

F2 — Rollback depends on code that its target release does not contain.
Evidence: `/home/ivan/.claude/jobs/6a0d8d81/tmp/rr/release-rollback/brief.md:11–12` requires both the previous release's entry point to perform rollback and subsequent `next` to honor the hold. Yet the rollback verb and hold reader are introduced only by this leaf (`design.md:22,25,29`), after release-deploy (`state.yaml:6–7`). The first previous release built by release-deploy therefore has neither. Today's CLI confirms there is no rollback verb (`src/akrogon.ts:222–225`). After switching back to that predecessor, its updater can immediately redeploy the held commit because its immutable code cannot read the new hold.
Required correction: put the recovery entry point and hold-consumption protocol in the prerequisite release-deploy contract, or define a recovery/deployment component outside the selected release that owns both. Prove rollback to the actual predecessor without this leaf's code, rather than building two fixtures that both already contain rollback support. The broken-current guarantee cannot rely solely on an arbitrary older entry point.

F3 — Rollback omits the skill-link consumer of the pointer change.
Evidence: `/home/ivan/.claude/jobs/6a0d8d81/tmp/rr/release-deploy/brief.md:12` explicitly handles added/removed skills, while rollback is specified as only a pointer flip (`release-rollback/brief.md:10`, `design.md:22–29`). Installation creates individual skill links (`src/install.ts:20–24`). If release B adds skill x and removes skill y, flipping back to A leaves x dangling and y unavailable unless links are reconciled too. Existing install only creates absent destinations (`src/install.ts:48–52`), so the pointer alone does not perform that reconciliation.
Required correction: give rollback ownership of restoring the target release's link set through the release-deploy link mechanism, including its failure handling, and add an observable added/removed-skill rollback criterion. Include this consumer in the recovery path required by F2.
