# Slot C blind notes: release shape

## Q1. Where machine state lives

- Pick: move it to `~/.akrogon` with a one-time migration; `globalHome()` defaults there, `AKROGON_HOME` still overrides. Reason: state in the code tree is the coupling that created this chart (src/config.ts:195-198 makes state home follow whatever tree runs); a pointer back to the workspace keeps the running release permanently dependent on workspace layout and keeps a machine config tracked in a code repo. Cost: one migration done while no akrogon process is live, plus a bootstrap path for a missing config (below).
- Rejected: stays in the workspace, found by fixed pointer. Every pointer form has a failure the move does not: `AKROGON_HOME` in the environment is absent from some entry point (herdr hooks, systemd, a bare shell) and a bare invocation then invents a second state home inside the release; a pointer file in `~/.akrogon` is a second source of truth that can point at a moved workspace; stamping the workspace path into the release at build time ties a supposedly immutable release to one machine layout. All three leave the tracked `config.yaml` anomaly in place forever.
- Evidence (primary code and live disk, 2026-10-16): `globalHome()` consumers are `config.yaml` (src/config.ts:206), the global `.lock` taken by next/park/pause/phase, `paused.yaml` (src/pause.ts:20), `stopped.yaml` (src/stop.ts:18), `runs/` admission records (src/admission.ts:40,90-101) and `reconcile/` reports. On disk the whole state is a few KB: `config.yaml` 1201 B (tracked in git, `git ls-files` confirms), `held.yaml`/`paused.yaml`/`stopped.yaml` 2 B each, `reconcile/` 44 KB, `runs/` 4 KB. Machine state already partly lives in `~/.akrogon` today: `worktrees/` (1.6 GB), `run.lock` and `framework-tests.lock` are there, so the move unifies two existing state homes instead of inventing a third.
- Pitfalls and what removes each: (1) Two state homes during the flip, if a long process started under the old code keeps locking the old `.lock` inode while new invocations lock the new path, removing mutual exclusion. Removed by migrating while akrogon is paused with no seats running, in the same step that flips `current`, since every state access goes through `globalHome()` and flips atomically with the code. (2) Bootstrap: `readGlobal()` throws when `config.yaml` is absent (src/config.ts:206) and `install()` reads it first (src/install.ts:57), so a fresh `~/.akrogon` cannot self-create today. Removed by the migration copying the file before the first release runs, and a first-run path that writes a minimal config instead of throwing. (3) The tracked workspace `config.yaml` cannot be deleted from the repo until the release that defaults to `~/.akrogon` is the one running, or the still-running old code loses its config. Removed by ordering: migrate files, flip, verify, only then remove the tracked copy in a later change. (4) Dev runs from the workspace (`bun src/akrogon.ts`, operator carry) must hit the same state: they do, because the default no longer depends on which tree runs.
- Question the fork does not ask: what may still write into the workspace tree at runtime after the move (for example anything addressed via `toolRoot` rather than `globalHome()` today), and is the answer enforced or only audited once? A missed writer recreates state in the release folder, where a later cleanup deletes it.

## Q2. When old release folders are deleted

- Pick: keep the previous release, delete older ones at flip time once no process is running from them. Reason: previous is the rollback target (one flip, run-location Taken), anything older is reproducible from git history on demand, and unbounded retention is real disk: a release is roughly 98 MB (measured today: `node_modules` 66 MB, `skills` 32 MB). Cost: the deletion check needs a trustworthy "running from this release" signal, which is not free (below).
- Rejected: fixed number of recent releases (say five) deleted purely by count. Deploys happen per merge, several on a busy day, while a single `akrogon verify` can run for hours, so count alone can delete the tree a live process loaded from; the count also keeps stale releases long after they stop being plausible rollbacks, at ~98 MB each.
- Evidence (primary code and live measurement, 2026-10-15/16): akrogon processes are short except `verify` and `run-check`, which write admission records under `runs/` (src/admission.ts:40,90-101). A running akrogon process cannot be attributed to a release by `/proc` cmdline: a live `akrogon verify` measured on 2026-10-15 showed argv as the `~/.local/bin/akrogon` symlink path, not the resolved tree, and Bun does not hold its `.ts` sources open, so neither cwd nor fd scans prove which release a pid loaded.
- Pitfalls and what removes each: (1) The un-attributable process above. Removed by the process stamping itself: at startup a release writes a run record (pid, boot id, release commit, the `ownerSchema` shape already used for run dirs) under the state home and deletes it on exit; deletion checks those records with the existing dead-owner test, and a crash leaves a record a dead pid clears. Without that record, "no process runs inside" is unimplementable as stated and the pick degrades to keeping previous plus deleting older by count after all. (2) Deleting a tree out from under a process that lazy-imports (src/akrogon.ts dispatches by dynamic import) fails only if deletion happens mid-process; deleting only at flip time, only releases at least two deploys old, and only with the record check removes the realistic window. (3) `current` must flip by rename of a temporary symlink, not unlink-and-recreate, or invocations in the gap resolve nothing.
- Question the fork does not ask: who flips back on rollback, and what stops the next self-update pass from immediately flipping forward again onto the release that was just rolled back from: is there a pin a person sets, and where does it live?

## Q3. When building a new release fails

- Pick: `current` stays on the old release, the failure is recorded where a person will see it, and the build retries at the next trigger; dispatch never stops for a failed build. Reason: the old release is known-good by construction (it built the same way), while stopping dispatch can deadlock its own repair, since the fix for a broken build usually lands through a leaf that itself needs dispatch and merge. Cost: the system can run stale code for as long as the build stays broken, which is the risk the visibility requirement exists to bound.
- Rejected: stop dispatching until a person acts. It converts a transient fetch or registry failure into a full work stoppage, blocks the workspace use the operator explicitly kept ("run everything from the main folder"), and protects against a state (running old code) that is the normal state between every pair of deploys anyway.
- Evidence (primary code, 2026-10-16): today's self-update already implements the stay-and-retry shape for its git stage: fetch and push failures return a printed line ending "retried at the next trigger" (src/self-update.ts:220-223), and install failures return a line rather than throwing (src/self-update.ts:189-205,225). Nothing persists that line; it exists only in the output of the pass that produced it. `bun install --frozen-lockfile` is the one build step with a network dependency; fetch already happened for records in the same pass, so a fetch failure is observed before any build starts.
- Pitfalls and what removes each: (1) A half-built `releases/<commit>` directory left by a failed install makes the retry either collide with it or, worse, flip to it believing it complete. Removed by building into a temporary sibling name and renaming to `releases/<commit>` only after install and link checks pass, so the flip target's existence means complete. (2) A failure only printed in a merge pass is read by a seat, not necessarily the operator, and repeats identically every trigger. Removed by persisting the last deploy result (commit attempted, stage, error line, time) in the state home and surfacing a non-current deploy in `akrogon status`/`leftovers`, so staying stale is a visible, dated fact rather than console noise. (3) The flip and the record-checkout move must stay independent: `checkout pending` for records (src/self-update.ts:246) must not block the release flip, and a failed release build must not block record sync, or the original incident reappears with roles swapped.
- Question the fork does not ask: how many failed builds, or how many commits behind `origin/main`, turns "stay on the old release" from accepted lag into a stop-the-line event, and who is told at that threshold (a number in status, a notification, or nothing until a person notices)?
