# Slot C rebuttal: release shape

Only Q1 is contested. Q2 and Q3 as merged state my position accurately, including the per-process record Q2 needs and the temp-sibling build Q3 needs.

- Q1, keep the move to `~/.akrogon`. I concede the merged pointer is stronger than the forms I rejected: a fixed file at `~/.akrogon/home`, independent of cwd and environment, with a clear error when missing, does answer my split-home objection for every entry point. It still leaves two couplings the move removes and the pointer cannot. First, machine config stays a tracked file in a working tree that akrogon itself rewrites: `config.yaml` is tracked (`git ls-files` lists it, with `held.yaml`, `admission.lock`, `runs/last-start`), and every `akrogon init` writes the global config back into it (src/init.ts:88), so routine registration dirties the workspace and can recreate the exact overlapping-edit block on the records move that started this chart. Second, the running release would read its config from a tree whose branch self-update moves under it for records (src/self-update.ts `moveCheckout`), so a records move can swap slots, harnesses and the repo registry under live seats; state under `~/.akrogon` is untouched by any branch move. The move's costs are one-time and bounded by the evidence in my notes: the whole state is a few KB, every `repos:` entry in the live config is an absolute path (read today), so the relative-path base change in src/config.ts:210 changes nothing for this machine, and the migration runs once while paused next to the flip that has to happen anyway. The pointer is the smaller change this week and a permanent runtime dependency on the workspace forever; that trade is the wrong side for a fork whose purpose is separating running code from the workspace.
