## Material forks

1. **D1: Eligibility.** Options: a fixed akrogon/test rule, restore configurable `full`, or identify suites from argv. Pick the fixed rule using the registered repo identity and check name already passed to `withAdmission`. It fulfills the one-repo scope without a new public config field or command parser. Restoring `full` adds activation and rollback ordering because config is strict. Argv matching becomes fragile when shell/setup wrappers change. The fixed rule requires a code change if the repo or check is renamed. A narrower run labeled `test` also waits, and an unlabeled full suite escapes. Keep that naming contract explicit. [E1, E3–E5, E7]

2. **D2: Queue and lock boundary.** Options: restore the short atomic queue promotion with akrogon-only membership, hold a lock throughout the suite, or lock all of verify. Pick the first, reusing admission records and `withLock`. Register a waiter before sleeping and select/promote under the same queue lock. Preserve admission-lock ordering and release locks before polling or running commands. A long-held admission/slice lock can delay unrelated checks and cleanup. A verify-wide lock unnecessarily queues setup and format. Define ordering by registration with a deterministic tie-break, rather than promise exact wall-clock arrival ordering. Other repos must not join the selection set. [E2–E5]

3. **D3: Nested admission.** Options: exempt every inherited token, exempt a queued suite only when its ancestor already holds this same line, or make every child queue. Pick the second. Current `nested` would let akrogon/test under format bypass the line. Making a child test queue behind its own test parent deadlocks. An inherited holder from another repo must not grant akrogon's exemption. Preserve existing token-hash and process-identity checks, and compare queue membership as well. Descendants sharing a holder remain inside one admitted run, not independently serialized child suites. [E2–E4]

4. **D4: Status.** Options: show only when there are waiters, show whenever test runs, or emit an unrelated new display. Pick the existing renderer, visible only while waiting, following the earlier operator correction. Show holder first, then ordered waiters, with repo, leaf, check, state, age and run ID. The ID makes the mandated stop command usable. Respect current-repo filtering, and derive displayed order from the admission selector. Keep `wait_ms` distinct from execution duration. [E1–E4, E6–E7]

5. **D5: Cancellation.** Options: support waiting runs through `stop-run`, expose an uncancellable queue, or rely on manually killing wrappers. Pick `stop-run` support within its current ownership boundary. Merely adding waiting records to its candidate list is insufficient: their units and guards do not exist yet. Define an explicit cancellation transition checked under the admission lock so cancellation cannot race promotion or resurrect a removed waiter. Print the run ID before waiting. Waiting cancellation exits without executing the command. This is necessary queue behavior under the stopping lock, not adjacent process-management cleanup. [E1–E3, E6]

6. **D6: Release boundary.** Options: retain ownership through ordinary unit shutdown and accept the old crash residual, or add unit-state probing before every admission. Pick the existing normal cleanup sequence and retain the documented crash residual explicitly. `ended` must still occupy the line until shutdown and final removal finish. Restoring only `liveRuns()` as the queue source would release too early. On wrapper death the existing guard removes the record before scope shutdown, so strict zero overlap after crashes is not guaranteed. Do not call that guarantee achieved without changing this choice. [E2–E4, E6–E7]

## Lifetime pitfalls and proof targets

- **R1: Invisible waiters.** Queue records must participate in the relevant liveness consumers. Audit reconciliation's slice protection and state-home migration, not only status. Leaving their current state filters unchanged can make an active waiter invisible to cleanup or cutover decisions. Keep existing PID/start/boot checks. Prove stale waiters leave the queue and live waiters retain ownership. [E3, E8]
- **R2: Queue recovery.** A stopped head waiter can stall FIFO indefinitely. Preserve the visible-head/no-auto-timeout policy from the earlier accepted residual, but provide D5's working cancellation route. The earlier missing-record rewrite must not undo intentional cancellation. Prove cancellation of both head and non-head waiters, then progress of the next waiter. [E1–E3, E6–E7]
- **R3: Wrong scope in regression tests.** The removed two-repo test asserted host-wide blocking and must be inverted. Prove two akrogon test runs across different worktrees queue, another repo's `test` starts, and akrogon's format/typecheck or targeted labels start. Also cover ordinary verify routing, FIFO, nested-under-format, same-line nesting, and status appearing/disappearing with the queue. Use fixture commands and handshakes, not extra heavy suite copies or fragile timing thresholds. Preserve existing timeout/retry/test locks. [E1–E5, E8]
- **R4: Overstated benefit.** Serialization removes overlap among participating akrogon suite runs, while other repos still contend for the host. It neither repairs existing test failures nor proves every individual run finishes sooner. Keep receipt reuse intact and assess waiting plus execution time if judging throughput later. No new benchmark project is required for this small change. [E1, E4, E9]
