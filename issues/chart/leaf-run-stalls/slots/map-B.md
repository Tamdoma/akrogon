## Practitioner questions and pitfalls

Q1. Which accepted output can a downstream leaf consume after an independent merge? Inspect each dependent's actual calls/files before changing blocked-by. Same-skill naming and shared files alone do not prove a dependency.
Q2. Did each interrupted worker exhaust the existing retry policy, with which model/provider and effective settings? Read session retry/error events. Distinguish transient 503, permanent rejection, budget exhaustion and an actual successful but incomplete return.
Q3. Which commands are safe to repeat against retained state, and which external mutations need inspection first? A fresh child does not authorize duplicate imports, deletions, uploads or commits.
Q4. Is C1 green on the exact base in a clean isolated checkout after normal setup? Compare complete failures, not just unchanged source files. Keep this proof separate from the leaf's residue.
Q5. Does a passing proof exercise the advertised route and preserve its artifact? B found fixture-only inputs concealing real registry lookup (L/review-B.md:28-34), and no retained browser trace (:12). Extra unit counts cannot replace missing route proof.
R1. Splitting mechanically can add more plans/reviews and duplicate slow runs. Prefer independently mergeable outcomes and the existing spine, not arbitrary worker-to-leaf promotion.
R2. Repeated fresh workers cannot solve a persistent provider outage. Keep API retry bounded, preserve retained work and expose final failure. Do not silently switch model or provider.
R3. Broad “base red” waivers erase real leaf regressions. Conversely forcing unrelated baseline repair inside every leaf breaks ownership and repeats costs.
