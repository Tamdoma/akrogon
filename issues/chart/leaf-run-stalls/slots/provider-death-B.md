## Q1. Retry budget and its owner

Pi already retries overloads. U11 recorded four 503 responses before stopping (S/2026-09-30T22-09-33-884Z_01a0f45d-a8bc-74d7-ad65-507a4975b90b.jsonl:254-260), and later attempts still recorded 503 (S/2026-09-30T22-40-04-239Z_01a0f479-968f-74d7-ad65-507ffa510608.jsonl:6). Defaults are three agent retries with 2000ms initial backoff and a documented 60000ms cap, and user settings currently contain no retry override (DOC:123-131; ~/.pi/agent/settings.json, parsed retry key absent).

Research: practitioner · Marc Brooker, [Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf), read 2026-10-01 · bounded retries at one layer avoid multiplying load, and jitter reduces synchronized retries · keep Pi's existing agent retry owner and provider retries at zero, instead of stacking an akrogon retry client. Research: live implementation · DOC:123-131 and PI/child-session.ts:583, read 2026-10-01 · children load settings with their own cwd and the agent directory · check project overrides and actual child settings, not just global defaults.

- 1a (recommended): modestly extend the existing Pi agent budget as an operator settings change: `retry: { enabled: true, maxRetries: 12, baseDelayMs: 2000, maxAgentDelayMs: 60000, provider: { maxRetries: 0 } }`. Under the documented capped exponential schedule, waits are 2+4+8+16+32+60+60+60+60+60+60+60 = 482 seconds, or 8m02s, across 13 total requests. Cost: slower terminal failure during an outage and more requests. This is a chosen tradeoff for the observed error span, not a measured optimal budget or evidence of continuous outage.
- 1b: retain defaults: `enabled: true, maxRetries: 3, baseDelayMs: 2000, maxAgentDelayMs: 60000, provider.maxRetries: 0`. Waits total 14 seconds, plus four request durations. Cheapest and fastest failure, but ordinary multi-minute overloads lose the child context quickly. Pair with Q2 recovery.
- 1c: longer coverage with `maxRetries: 20` and the other 1a values. Waits total 62+15×60 = 962 seconds, or 16m02s, across 21 requests. More chance of surviving a longer overload, but more time before surfacing a persistent outage. No observed evidence makes this preferable to 1a.

Pitfalls: these totals count scheduled sleeps only. They are not wall-time limits, and successful responses reset retry streaks. Server-directed delays, requests, streaming and tool execution can change elapsed time. All workers and A can fail on the same provider. The locally installed extension development SDK has uncapped exponential code (PI/node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js:2297), whereas Pi 0.99.1 docs expose a cap. Verify the loaded runtime before claiming 482 seconds. Do not raise the budget against an uncapped implementation: 12 retries at 2s would sleep 8190 seconds, or 2h16m30s. Keep warnings and the last provider status/body/child/transcript context visible. No custom jitter subsystem is proposed.

Lock decision: explicitly confirm that bounded backoff inside the existing API client remains permitted. This interpretation does not permit elapsed-time leaf recovery or a watchdog. If the no-clock lock literally forbids even existing API retry sleeps, Q1 requires reopening it by name rather than silently claiming an exception.

Before handoff: in a throwaway worktree, launch a tiny real Pi parent and child using the configured model/identity and record effective retry settings and resolved runtime versions without secrets. Make one minimal live provider call from each to prove settings/identity propagation and ordinary successful execution. Separately run the real session/client against a controlled HTTP endpoint returning 503 for two requests then success, and an always-503 endpoint to exhaustion. Record requests, retry warnings, intervals, final status/body and parent failure/transcript delivery. Use the selected full budget once to prove the cap and total sleeps, then remove the throwaway worktree. A live success does not prove overload recovery, and deliberately overloading the real provider is unnecessary. These probes are proposed, not performed in this round.

## Q2. Recover without authoring another contract

A currently must inspect the retained tree and write a new remainder brief, explicitly never using the original again (AK/skills/implement-issue/worker-protocol.md:17). The child error and transcript survive, but terminal children cannot be steered (PI/manager.ts:479-483,845-850).

Research: practitioner · Malcolm Featonby, [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), read 2026-10-01 · a lost response does not prove that a mutation did not happen · recovery must reconcile state before repeating commands. Research: live implementation · PI/manager.ts:845-850 and AK/skills/implement-issue/worker-protocol.md:17, read 2026-10-01 · code and transcript survive but the contract is re-authored · remove duplicate contract authorship first.

- 2a (recommended): after provider exhaustion, start one fresh child in the retained worktree with the same absolute original brief and a short recovery instruction: inspect status, diff, commits and prior evidence, read relevant transcript findings when needed, map completed work to the original criteria, then finish only what remains and return the normal report/commit. Change protocol line 17 specifically for provider failures. Cost: a fresh child may need to reconstruct investigation, but no new harness API or hand-written remainder contract is needed.
- 2b: add failed-child transcript continuation to pi-extensions. Preserve reasoning context and continue the original contract. Cost: a new lifecycle path must correctly restore the session, original cwd/settings and cancellation ownership, exclude concurrent children, and distinguish prior tool effects from unfinished work. It needs real runtime proof, not merely loading transcript text.
- 2c: retain remainder briefs. The parent explicitly scopes the unfinished work, but repeatedly pays the inspection and writing cost that caused this intake.

Pitfalls: the original brief is authoritative, not an instruction to rerun every step. Confirm the old child has retired before granting a replacement write access. Inspect detached commits as well as dirty files. Completed external mutations need receipts or real-state inspection, not just git status. Keep budget/output-limit stops and successful-but-incomplete returns separate from provider failure. A still checks criteria and revises a brief for a genuine mismatch. Never silently switch provider or model.

Before handoff: use a disposable repo and an actual child that writes one file, then receives a controlled provider error before committing/reporting. Dispatch recovery with the original brief, confirm retained edits survive, completed mutations are not duplicated, the report names remaining work, and A integrates exactly once. Test failure after commit too. Exercise cancellation/retirement before reusing the worktree.

## Q3. Commit partial steps?

Today a worker returns one chunk commit and A cherry-picks it before removing the worktree (AK/skills/implement-issue/worker-protocol.md:11). Uncommitted edits already survive a provider failure (:17), so step commits do not recover the missing reasoning or report.

Research: primary documentation · [Git cherry-pick](https://git-scm.com/docs/git-cherry-pick), read 2026-10-01 · explicit commit sets/ranges are supported, but integrating several commits is a different selection obligation · checkpoint commits would require changing A's pick/report contract, not merely telling workers to commit earlier. Research: live implementation · AK/skills/implement-issue/worker-protocol.md:11,17, read 2026-10-01 · retained trees preserve edits already · no checkpoint policy is needed to prevent the observed edit loss.

- 3a (recommended): retain one verified chunk commit. Preserve the worktree on failure and recover its state under 2a. Cost: recovery inspects dirty edits, which it must inspect for correctness anyway.
- 3b: allow commits at coherent verified steps, then squash the chunk to one final commit before return. Intermediate state becomes easy to identify in Git without changing A's single-commit pick. Cost: more commits, checks and recovery bookkeeping, plus careful squashing of the detached worker's own history.
- 3c: return and cherry-pick a bounded ordered commit range per worker. Keeps checkpoints visible, but expands the protocol, conflict handling and restart verification. It is unnecessary for this incident unless the operator wants independently retained step history.

Pitfalls: committing every edit freezes invalid intermediate states and does not make them acceptable. A death can occur between the last write and commit regardless of policy. No force removal or automatic pruning of a retained worktree. A changed commit policy must specify the starting commit and exactly what A picks, otherwise earlier partial work may be omitted or applied twice.

Before handoff: if 3a is taken, Q2's dirty-tree and committed-tree probes suffice. If 3b/3c is taken, interrupt between checkpoints and prove final integration contains every intended change exactly once, with clean lane and passing changed tests.

## Q4. Repeated provider death

U11's replacement also encountered repeated 503s (S/2026-09-30T22-34-03-945Z_01a0f474-1729-74d7-ad65-507cf7863060.jsonl:6-34). Rewriting the brief or relaunching indefinitely cannot repair provider availability, while the existing failed path records a reason and announces the leaf (AK/src/phase.ts:48-75).

Research: practitioner · Marc Brooker, [Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf), read 2026-10-01 · capped backoff still needs a finite retry count and a surfaced failure · allow one worker recovery, then terminate rather than build an outer infinite loop. This exact one-recovery threshold is an operator policy proposal, not a number derived from AWS.

- 4a (recommended): after the first terminal provider death, do Q2's one recovery. If the same unit exhausts provider retries again during this implement/check.fix pass, A records both failure/transcript references, retained worktree/commit and unfinished criteria, runs `akrogon phase <slug> failed --reason "<unit> provider retries exhausted twice; see <artifact>" --slot A`, and ends. Cost: persistent outages need operator action, but no repeated remainder loop, clock or new state field is needed. Record the recovery in the existing pass artifact so A compaction does not reset the allowance.
- 4b: fail on the first terminal exhaustion. Minimum request/reconstruction cost. More leaves need operator recovery even when a fresh child would succeed.
- 4c: keep replacing children until one succeeds. Could survive an arbitrarily long outage, but recreates the overnight loss and has no finite stopping rule. Reject.

Pitfalls: count exhausted worker runs, not each HTTP 503, and do not spend leaf review fix_rounds on provider recovery. Stop launching new workers after deciding failure, settle already running siblings, and preserve all retained work. The same-unit rule is not a claim of a global outage circuit breaker. Provider switching requires an explicit operator choice.

Seat limitation: 4a needs a functioning A. If A's own provider is exhausted, A cannot author the artifact or invoke failed. Current re-prompt suppression uses a two-minute elapsed grace (AK/src/next.ts:410-416), so it is not a zero-clock recovery guarantee. Do not add another seat timer or rely on that grace to promise no overnight stalls. A mechanically guaranteed terminal seat-failure action would require explicit event-based harness/lifecycle work, with pi-extensions owning truthful failure signaling, and separate authorization of that scope. Pure silence stays outside the chosen lock (AK/issues/chart/seat-stall-detection/forks/no-akrogon-detector.md:20-23).

Before handoff: with a healthy parent and controlled failing child provider, exhaust two runs, verify exactly one recovery launch, retained evidence/worktrees, actual failed phase and announcement, and no subsequent worker dispatch. Separately exhaust the parent provider and observe the real seat status/event delivery. If terminal failure is reported only as idle and triggers unbounded re-prompting, record that as an unresolved seat mechanism rather than claiming this worker protocol fixes it.

## Challenge check

D1. Does the operator accept existing bounded API backoff under the no-clock lock, and 1a's 8m02s of scheduled waiting per exhausted streak? This does not bound elapsed execution or prove recovery from all outages.
D2. Is fresh-child recovery with optional transcript reading sufficient, or is preserving the child's full reasoning worth a pi-extensions continuation feature? The evidence supports removing remainder authorship now, not declaring continuation unnecessary forever.
D3. Does “no overnight stalls” mean finite worker recovery while A is alive, or a guaranteed transition even when A dies? The former fits 4a and existing artifacts. The latter requires resolving terminal seat signaling separately. Neither can guarantee detection of a silent hang without reopening the existing lock.
Ownership: Q1 is an operator Pi settings step after runtime proof. Q2/3/4a are akrogon worker-protocol/implement instructions. Q2b and any demonstrated retry/runtime or seat failure signaling defect belong to pi-extensions. No framework code change is proposed by this fork.
