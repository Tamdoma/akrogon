# B: finish prerequisites with fewer repair trips

**F1 — Constraint.** The strongest candidate is the time needed to produce an accepted prerequisite, especially its repair handoffs. Available execution capacity is being starved of ready work. M3 gives 5.6/24 = 23% average slot occupancy, while M4 shows genuine dependencies waiting through hours of prerequisite repair. Accelerating that repair helps both the producer and its descendants. This is a lead-time diagnosis, not proof of a single saturated resource. A's three-loop account is useful, but dependency waiting amplifies the other delays rather than representing three independent savings opportunities.

**F2 — Do not add the measurements.** M2 sums to 11.72 h, above M1's 9.8 h mean. Its phase totals therefore need reconciled boundaries or denominators before becoming a lead-time budget. Likewise, 15 × 19/42 = 6.79 h of prerequisite waiting per completed leaf is not an additional 6.79 h on top of M2. The completed cohort also excludes unfinished long-running leaves. Little's law needs the same population and system boundary for WIP, throughput and elapsed time. M3 excludes planning, so combining it with M1 would be invalid. Source: CMU's primary teaching material, [15-829 Lecture 7: Little's Law, Open Systems, Closed Systems](https://www.cs.cmu.edu/~harchol/Tools/Notes/lectures/lec7.pdf), undated, accessed 2026-10-15.

**F3 — What would change my view.** Measure, from existing logs after the 10/14 changes, the accumulated time that an otherwise ready dependent waits solely for its prerequisite's repair/merge tail. If its median falls below 30 minutes while runnable leaves still spend hours waiting for a seat or checks, dependency release is no longer the first target. Separately measure check exit → agent continuation. A median below 30 seconds would remove polling from my top three. Sustained runnable demand above capacity would change the capacity conclusion. Today's load of 2–4 alone does not establish historical CPU or memory contention, and a 44% red rate does not establish flakiness.

## Dependency choice: smaller producer first, stacking selectively

**D6 — Do not replace “merged” with “passed review” globally.** Current eligibility requires merged dependencies in `src/turn.ts:11–18` and `src/turn.ts:38–49`. A review visit is not necessarily an accepting verdict: M5 says nearly every first review finds fixes. M4's “passed check.review” needs clarification before treating its 5 h as a safe overlap window. For genuine stacking, the relevant input is a particular accepted producer head and usable output, not a phase name. A branch cannot supply a live artifact that has not been produced.

**D7 — Prefer D2 where a complete useful producer can land separately.** Only 3/25 examined edges are shared-file-only. Removing those helps, but the other 22/25 consume real code/data and cannot be wished away. Six of those also touch shared test files: file overlap can be handled during integration without pretending the underlying data dependency disappeared. An interface-first leaf must include enough working behavior and proof for a consumer to use it. A declaration or stub alone does not release that dependency.

**D8 — Stacking can be worth it for a stable code-only pair; it is not the default next change.** Its net gain is overlap recovered minus descendant repair, restack and revalidation time. For a pair with 5 h of otherwise idle waiting, one hour of restack/revalidation still leaves four hours worth recovering. For a 1.3 h wait, the same overhead nearly consumes the benefit. Use measured pairs, not a universal switch. Parent changes must update the child's base/diff and invalidate affected evidence. The current refresh rule rebases onto main (`skills/implement-issue/SKILL.md:40`), so stacking is a lifecycle change, not just a different checkout command.

**S1 — Stacking evidence and its limit.** Andrade's experience supports small reviewable stacks, but does not establish that this repo's cross-seat dependencies are stable enough. Graphite's own [Restack Branches](https://graphite.com/docs/restack-branches), undated, accessed 2026-10-15, documents why parent changes require dependent restacks and conflict resolution. Meta's Source Control team, [Branching in a Sapling Monorepo](https://engineering.fb.com/2025/10/16/developer-tools/branching-in-a-sapling-monorepo/), 2025-10-16, explicitly describes cases where very large stacks are impractical. I would change D8 toward routine stacking if stable code-only pairs retain multi-hour waits after D1/D2, with low measured parent churn. Neither Shopify's vendor-reported throughput gain nor Meta's scale supplies a local saving estimate.

Removing all those omissions might still leave every affected leaf needing repair. Independent B review remains necessary, consistent with Rajasekaran's experiments cited in F4.

**D10 — Allow B to correct an expectation only against an explicit external oracle.** The brief/design must state the expected behavior clearly. B records the old assertion, the cited contract, the correction and its evidence in the existing review entry and test-change commit. Where the corrected assertion was the only acceptance evidence, another seat must assess that narrow change before acceptance. That reduces the eligible nine handoffs, which is why D1's 0.53 h is an optimistic scenario.

## Infra, merge and boundaries

**S3 — Provision credentials outside agent reasoning.** Anthropic's platform team describes provisioning Git access into the execution environment so the agent can use Git without handling tokens in [Scaling Managed Agents: Decoupling the brain from the hands](https://www.anthropic.com/engineering/managed-agents), 2026-04-08. That supports D4's responsibility boundary, not a migration to their service. This repo already has remote-read preflight (`src/preflight.ts:47–59`), so adding more repeated read probes would not prove write authorization or repair the identity mismatch. M8's auth logs need that specific diagnosis before choosing a provisioning change.

**S4 — Keep merge validation, limit queue ambition.** GitHub's Will Smythe and Lawrence Gripper describe automated, integration-tested grouping in [How GitHub uses merge queue to ship hundreds of changes every day](https://github.blog/engineering/engineering-principles/how-github-uses-merge-queue-to-ship-hundreds-of-changes-every-day/), 2024-03-06. Uber's newer production report in F4 shows how speculative cancellation itself creates repeated work. Together they support the approved simple batching direction and caution against speculation without sustained demand. Neither gives reason to sacrifice the exact combined-tree gate for M9's small direct queue saving.

**N1 — Would not increase seats, CPU caps, admission locks or forced WIP limits.** M3 supplies no capacity case, and the operator already removed the admission gate. Do not optimize host utilization as the goal.

**N2 — Would not target a green first review by suppressing defects, accepting self-authored evidence alone, or retrying until green.** Yield is a diagnostic. The required behavior and independent acceptance remain the target.

**N3 — Would not introduce a speculative branch forest, ML test selector, universal evidence format or another self-review ceremony.** Each adds maintenance without addressing the demonstrated ownership and run-shape problems.

**N4 — Would not promise additive hour savings or count already-landed work again.** Compare the next post-change cohort using the same start/end boundaries, track unfinished leaves as well, and inspect the critical prerequisite path. The recommendation is D1 first, D2 next, D3 as the small execution fix, with D5 already proceeding.
