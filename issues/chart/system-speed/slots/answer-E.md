## Q3. Dependencies: Stacked Branches at `check.review` vs. Contract-First Leaves

### Recommendation: **Do NOT branch dependents off unmerged `check.review` branches; use Contract-First charting + fix `D-Wake` instead.**
1. **Why stacked branches at `check.review` are a trap in this system (`[D-STACK-TRAP]`)**:
   - **0% first-pass yield at `check.review` (`M5`) means the parent branch always rewrites**: Out of 47 `check.review` visits, **all 47** entered `check.repair` and **31 (66%)** returned to `check.fix` (including `6` plan/design changes and `33` code defects). If Dependent $Y$ branches from Prerequisite $X$ at `check.review`, $X$ is guaranteed to add repair commits and then rebase onto `origin/main` at `merge` (`src/batch.ts:75`).
   - **Git/Akrogon mechanics break when parent SHAs rewrite**: In Akrogon, `requireNoIssueFiles`, `requireTestChangeCitations`, and `frozenRecord` (`src/phase.ts:282-284, 327, 348`) diff `target(repo)...HEAD` (`origin/main...HEAD`). If $Y$ branches off $X$ before $X$ merges to `main`, $Y$'s branch contains $X$'s commits. Once $X$ rebases and squash/fast-forwards onto `main` with new SHAs, $Y$'s old parent commits diverge from `origin/main`, causing `git diff "$AKROGON_BASE"...HEAD` in $Y$ to attribute $X$'s files and `Test-Change:` trailers to $Y$, triggering false phase-gate refusals and 3-way rebase conflicts across worktrees.
   - **Once `L1–L3` + `O1` land, the post-review tail is short**: In `M4`, the `~5 h` median gap between `check.review` pass and dependent start was dominated by pre-10-14 merge bounces (`63%` merge green rate), 48 GiB admission blocks, GitHub auth halts, and the **`0.6 h` median (`0.1–10 h`) post-merge `D-Wake` bug**. With `85–92%` green merges + `O1` batching + `D-Wake` fixed, the time from passing `check.repair` to `merged` is **`~12–18 min` (`0.2–0.3 h`)** — far too small to justify cross-worktree rebase-cascade machinery.
2. **The simpler, higher-leverage way (`[D-CONTRACT-FIRST]`)**:
   - **Eliminate false edges (`3/25` shared-file only in `M4`)**: Enforce `skills/chart-issues/SKILL.md:45` and `assets/shapes.md:142` (*"Independently checkable outcomes can run in parallel, even when files overlap"*).
   - **Convert `code/data consumption` (`16/25`) and `shared spine` (`6/25`) edges into Contract-First parallel leaves**: `skills/chart-issues/assets/shapes.md:184` already requires `design.md` to state `literal interfaces`, and `skills/chart-issues/SKILL.md:36, 85` allows the chart door to land a small preparatory step on `main`. When Leaf $B$ consumes Leaf $A$'s output or function, lock the TypeScript interface / JSON schema / recorded fixture shape in `design.md` (or land the 20-line type/fixture stub on `main` during charting). Then $A$ (producer proven against the contract) and $B$ (consumer proven against the contract fixture per `standing-design.md:15`) run **100% in parallel (`blocked-by: []`)**!
   - **Fix `D-Wake` (`src/next.ts:964, 1135, 1152`)**: For the remaining true runtime prerequisites (e.g., where $A$ generates a live credential or recording $B$ cannot stub), call `dispatchDependents` (sweeping all leaves where `eligibility === null && tab === undefined`) directly inside `mergeWake` (`src/next.ts:1135`) and `reconcileBatch` (`src/next.ts:964`), eliminating the `0.1–10 h` post-merge orphan wait.
3. **Practitioner sources**:
   - **Martin Fowler, *Branch By Abstraction* (2014, `https://martinfowler.com/bliki/BranchByAbstraction.html`) & Danilo Sato, *Parallel Change (Expand and Contract)* (2014, `https://martinfowler.com/bliki/ParallelChange.html`)**: Establish that locking an abstraction/contract boundary first lets producer and consumer implementations land independently on trunk without long-lived dependent branches.
   - **Graphite Documentation, *Stack-Aware Merge Queue & Rebase Cascades* (2025, `https://graphite.dev/docs/merge-queue`)**: Shows that stacked branches require automated upstack restacking (`gt restack --upstack`) and stack-aware queue eviction whenever a lower branch is modified during review; without automated upstack rebase-cascade support, mutating lower branches breaks upper branches.
   - **Donald G. Reinertsen, *The Principles of Product Development Flow* (2009, Celeritas Publishing, Principle B15 / Ch. 5)**: Demonstrates that decoupling batch dependencies at interface boundaries reduces critical-path variance far more reliably than overlapping unstable upstream batches with high rework rates.

## Q5. Check-Wait: Stopping 9-Minute Polling Sleeps & Why `test_changed` Took 16 Min

### 1. `[CW-WAIT]` Simplest way to stop 9-minute (`540–590 s`) sleeps and `121` tool timeouts (`M6`)
- **Root cause of the 540–590 s sleeps (`skills/implement-issue/SKILL.md:45`)**:
  - The Pi bash tool times out at `~600 s` (`M6`). To avoid killing checks >10 min, `skills/implement-issue/SKILL.md:45` tells agents to run `nohup sh -c '<cmd>; echo $? > "$0/exit"' "$d" > "$d/log" 2>&1 &` in one bash tool call and wait in subsequent tool calls.
  - Because Unix `wait <pid>` **fails across separate subshells** (`wait: pid N is not a child of this shell`), agents cannot use `wait`. Instead, to obey *"never sleeps a fixed interval and then reads the log"*, agents either run an unbounded `while kill -0 $pid; do sleep ...; done` loop that hits or nearly hits the `600 s` tool timeout (`540–590 s`, `121 tool timeouts`), or sleep `540 s` outright!
- **Simplest fix (`akrogon wait-run <run-id>`, deleting the `nohup` recipe)**:
  - `src/admission.ts:22-37, 154` already writes a live run record (`~/.akrogon/runs/<hash>.yaml` with `run`, `pid`, `start_time`, `boot_id`) and prints `run <uuid>`, and `src/run-check.ts:210` records `exit` and `log` in `issues/timings.jsonl`.
  - Add `akrogon wait-run <run-id> [--timeout 240]` (~35 LoC): it polls `/proc/<pid>` (`live()`, `src/admission.ts:74`) every `200 ms` up to `240 s` (safely below Pi's `600 s` and Claude Code's `300 s` tool timeout). The instant the process exits, it reads the `check_end` / `verify-runs` record, prints `exit <code> <log>`, and exits with `<code>`. If still running at `240 s`, it prints `running <run-id> elapsed=<n>s` and exits `0` so the agent immediately calls `akrogon wait-run <run-id>` again.
  - **Delete** the `mktemp -d` / `nohup` / `$d/pid` / `$d/exit` prose from `skills/implement-issue/SKILL.md:45`.
- **Practitioner source**:
  - **Anthropic Claude Code Documentation / Issue Tracker & *Effective Harnesses for Long-Running Agents* (2025, `https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents`)**: Highlights that raw background shell polling inside fixed-timeout tool calls causes timeout cascades and quantization delay; harness-native bounded wait commands with structured status returns eliminate blind polling.
