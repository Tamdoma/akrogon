# B: red-notice

## 1. Pick, reason and cost

**Q1: one herdr notice per observed incident, with stored delivery status. No automatic GitHub issue or repair leaf.** This preserves the explicit October 10 notice decision and cut of automatic repair/seed machinery (`issues/chart/red-base-wait/forks/red-record.md:26`, `:27`, `:30`). Use the existing receipt store for the minimal notice metadata if that satisfies the taken no-red-record-file boundary. Storage location does not remove the need to define an incident and its recurrence.

An incident is a failing unit under the same command/scope and equivalent material configuration until fresh eligible evidence observes it passing. Keep base revision/tree as provenance, not the sole incident identity. If every new base tree starts a new incident, ordinary unrelated landings can repeatedly notify for one persistent failure. Conversely, once-ever deduplication can suppress a later recurrence after repair.

Notify only for base failures established by the taken comparison rule. The body should identify repo, command, unit, tested base, evidence location and the next action: chart a repair. Group units discovered together into one readable notification while retaining their separate identities. Repeat observations join silently after successful delivery. Receipt reuse alone neither discovers a new failure nor proves resolution.

Cost: delivery bookkeeping and recurrence detection remain maintained behavior. The notice does not assign an owner or guarantee the operator sees it. Main may remain red and each affected leaf still pays the accepted fresh comparison cost. Deduplication is for operator attention only, never acceptance evidence or a work gate.

**Q2: no additional clock rule, seam or lint in this issue.** The demonstrated expiring bound is already replaced by expectations derived from the observed time (`tests/timing-report.test.ts:511`, `:535`, `:539`). Known-red continuation tolerates some failures, it does not prevent decay. Deferring new prevention accepts future repair work, but avoids a broad change without another concrete brittle assertion to fix.

## 2. Rejected options and future consequences

- O1 **Notify on every known-red verify:** simplest implementation, no incident deduplication state, but repeated leaves repeatedly interrupt the operator about the same work. That conflicts with the earlier explicit “joins silent” decision and can make useful notices easier to ignore. It remains a valid smaller option if that repetition is deliberately accepted, not an equivalent implementation of one notice (`red-record.md:27`, E3).
- O2 **Automatically file a GitHub issue once per incident:** reject. This adds an external write, authorization/proof and issue identity/reconciliation without removing incident deduplication. Filing is intake, not repair ownership. It also reverses the explicit no-seed cut (`red-record.md:27`, `:30`). Later issue closure must not be mistaken for passing checks.
- O3 **Reports/status only:** reject as the sole notification route. The taken policy relies on a notice to initiate repair, while reports require the operator to seek the information. Keep durable evidence accessible, but do not call passive visibility a delivered notice. Current verify receipts already hold command logs (`src/verify.ts:27`), not incident delivery (`:16`).
- O4 **Plan-skill clock rule:** not selected. It can remind authors to avoid expiring expectations but cannot mechanically prevent the failure. A blanket prohibition on time-relative expectations would reject the valid landed repair. A targeted future rule should distinguish fixed clock inputs from expectations bounded around observed time.
- O5 **General clock seam or Date.now lint:** reject this scope. Real time is also used for synchronization deadlines (`tests/sync.test.ts:253`). A grep-based prohibition cannot distinguish that use from a brittle calendar expectation. A seam is useful where a concrete behavior needs controlled time, not as an unmeasured repository-wide rewrite. E4 supports explicit test inputs, not blanket clock freezing.

## 4. Pitfalls and what removes each

- R1 **Repeat spam or silent recurrence.** Keep unit/command/scope/configuration identity distinct from revision provenance. Resolve only on completed, comparable passing evidence on landed main, including the same revision after an environment repair. A passing candidate counts only after that exact revision lands. Missing output, an issue close or a new SHA cannot resolve it (`red-record.md:26`). If the implementation cannot prove equivalence, it must not silently merge unrelated incidents.
- R2 **Two writers send the first notice or stale evidence clears a newer failure.** Select/update notice and incident generation under the existing mutation lock, re-reading before mutation. Prove concurrent discovery and older-green/newer-red cases. No command gate reads notice delivery as permission to pass. Prior requirement: `red-record.md:26`, existing receipt lock: `src/verify.ts:174`.
- R3 **Delivery reported as success when suppressed or failed.** Preserve the provider's `shown`/`reason` and error context. A failed notification is an operational error, not a test result and not a reason to mark the leaf failed. Save valid comparison evidence independently. Retry delivery at subsequent relevant command activity, with no timer or side effects in status reads. The exact retry/error presentation must be contracted before implementation (`src/phase.ts:97`, `:104`, `:113`, `:166`).
- R4 **“Exactly once” claimed across process failure.** A crash after external display but before local delivery acknowledgement can leave an uncertain outcome. Accept a possible duplicate on recovery rather than silently losing the notice, unless the provider's idempotency behavior is actually proven. `shown` also does not prove human acknowledgement. The current response schema provides no acknowledgement field (`src/phase.ts:97`).
- R5 **Old notification proof reused beyond its limits.** The October 10 proof used `--sound none`, while the current failure path uses `--sound request`. The door must prove the selected actual call with its execution identity before handoff. No notification is sent by this peer task (`red-record.md:34`, `src/phase.ts:94`).
