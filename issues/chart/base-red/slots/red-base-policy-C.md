# Fork notes C: red-base-policy Q1

## Pick

O1: option (c), known reds pass, in reduced form. Judge a leaf by the failures it adds, computed by the command, not by seat comparison prose and not by restoring the deleted trio.

Shape: after the existing same-head retry stays red and the seat judges no cause in the diff (the judgment gate already at skills/implement-issue/SKILL.md:40 and skills/check-issue/SKILL.md:69), `akrogon verify` runs the base fresh in the same pass (no receipt reuse on the base side), extracts failing units from both logs (src/flaky.ts:10 `failedTests` already does this extraction), and passes the gate when every red unit on the head is also red on the base, both runs complete with setup 0. `requireGreenReceipt` accepts that head+base pair wherever it accepts a green receipt today (check.review move, merge `--check`, direct-guards), so lifecycle and direct follow one rule. The first fresh red base receipt for a tree+scope+unit sends the one operator notice; later joins are silent. Repair of main is ordinary charted work from that notice. Nobody waits, nothing resumes, no leaf goes `failed` for a base red, and the false skill sentence "never handed off as a base defect" is deleted.

Reason: this removes the whole class the intake names. No wait state, no resume mechanism, no shared incident record acting as a gate, no repair owner needed to unblock anyone, no manual `phase` per leaf. It also matches the standing operator decision of 2026-10-10 ("why does it have to wait for the main?"; waiting-leaf Taken: a pre-merge leaf never stops, waits or fails because main is red). dc2e2b0 (2026-10-14) reversed that decision and restored absolute-green gating; I found no operator choice recording that reversal, and the intake flags the same gap.

Cost: one fresh base verify per leaf that hits a persistent unexplained red, only while main is red (about 150 s here; the earlier chart priced 7-15 min on framework). New receipt semantics to build and test where `requireGreenReceipt` is used. Main can stay red while clean work lands, so repair urgency rests on the notice and operator charting, with no forcing function. A new break inside an already-red unit can hide behind the subset rule; the seat reading both logs under the no-cause judgment is the mitigation, and it is judgment, not proof. Invites later: pressure to reuse base receipts to save the repeated base runs, which reopens the stale-evidence class the 2026-10-10 "cut" closed; and a lingering red makes every later leaf pay a base run until someone charts the repair.

## Rejected options

(a) Keep today's per-leaf fail. Measured, not hypothetical: 3 incidents in 10 days, each leaf paying a full verify (149-163 s receipts on 2026-10-17), a `failed` stop, then operator diagnosis, hand fix and one manual `phase` per leaf. It also keeps a skill premise ("every commit passed verify, so never a base defect") that has now been false three times, and invites seats to repair outside their owned diff to get unblocked. Breaks nothing new, which is its only merit, and removes nothing.

(b) One shared incident, leaves wait, resume on fresh green. Most machinery of the three: an incident record with identity and generation rules, a wait state or failure cause, notice dedupe, a repair-owner exemption so the fixer is not blocked by its own wait, and a resume trigger at command events. It directly contradicts the operator's 2026-10-10 rejection of waiting, and it blocks unrelated leaves for the whole repair latency, which under parallel load is the seed's stated pain. Invites later: a stuck incident when a repair is abandoned, stale-clear races (the exact 2026-10-10 red-main-hold lesson came from this shape of record), resume storms, and disputes over whether two reds are one incident.

(c) Full old form: seat-written comparison records, a red-record file, an `akrogon base-run` verb. Same policy as O1, rejected only in this shape. dc2e2b0 deleted 3,242 lines building it; verify receipts plus the existing unit extraction now carry the same facts, and a subset check in code is exact where a seat-written record validated form only. Restoring the trio re-adds three surfaces for one rule.

(d) Unlisted hybrid: differential before merge, absolute green at merge. Rejected. A leaf proven to add no failures does not make main redder by landing; the same units stay red until repaired either way. Holding only at merge moves the pileup to the serialized merge queue, which is the #67 pattern (red main stalls the queue), and adds rebase churn for stacked leaves. It buys "never land on red" as a slogan at real throughput cost.

## Pitfalls, and what removes each

P1. Stale green receipt makes the base look green, so the leaf blocks and (c) silently stops working. Removed by forcing the base side fresh in the differential path only; ordinary gates keep reuse. This is the 2026-10-10 cut, restated.
P2. Timed-out, crashed or short-circuited base run read as "unit not red on base" or worse as known-red. Removed by construction: subset passes only on a completed run with setup 0 where the unit is present and red; absence blocks (comparison Taken Q2, 2026-10-10).
P3. Load or clock drift between the head run and the base run changes results. Reduced, not removed, by running the base immediately after the red retry, same command set, scope and configured timeout. A unit that flips green on the base blocks the leaf, which is the safe direction; flaky records identify repeat offenders separately.
P4. Two seats run the same base concurrently during one incident. Cost only, no correctness issue: receipts are append-only under the existing verify record lock. Coalescing equal in-flight base runs is an optimization to add only if load timeouts appear; building it now reopens shared-result questions for no measured pain.
P5. Notice spam or silent recurrence. Removed by deduping on tree+scope+unit from the receipts themselves: first red base receipt notices, joins silent, a unit red again after a green landed run is a new notice (red-record Taken, 2026-10-10).
P6. The repair is never charted and the red becomes permanent background every leaf pays for. Partly removed by the notice plus cheap visibility (known-red units are countable from receipts, e.g. a status line, no new record). The rest is accepted: the operator owns charting repairs, and the forcing alternative is tree closure, already rejected.
P7. Decay stays invisible while head runs keep reusing green receipts, so no base run ever triggers. Not removed by O1; it is the receipt-reuse question (map Q3), separate from this fork. O1 neither worsens nor hides it: the first fresh red run surfaces it as today.
