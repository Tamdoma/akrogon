# B: red-base-policy

## 1. Pick, reason and cost

**Pick (b): one shared incident, one repair owner, affected verification waits, then automatic resumption after fresh passing evidence.** Preserve each leaf's phase and completed work. Do not describe the leaf as failed merely because an unrelated shared check failed. Block only advancement that needs the affected evidence, not every active seat or unrelated task.

Reason: this addresses the observed duplicated diagnosis and manual phase recovery while retaining the current green-evidence requirement. The incident is a coordination fact, not a passing check. A repaired base lets affected leaves refresh and finish their own verification. It does not turn their earlier red receipts green (`src/phase.ts:291`, `:295`, `src/verify.ts:78`).

Cost: unaffected changes can still wait for a shared repair. Incident identity, repair ownership, wait/resume and concurrent updates become real maintained behavior. If repair needs a human, the wait can last indefinitely. This does not guarantee literally one initial check: concurrent leaves may already be verifying when the first incident is established.

This recommendation requires an explicit policy reversal. The earlier operator decision forbade waiting on base red (`issues/chart/red-base-wait/forks/waiting-leaf.md:43`, `:51`). The later `dc2e2b0` replaced known-red acceptance with green receipt gates. Neither artifact proves what the operator wants now. Choosing (b) must acknowledge the wait cost rather than present it as an uncontested restoration.

## 2. Rejected options and future consequences

- O1 **(a), per-leaf repair/failed:** reject. It adds little machinery, but preserves the demonstrated failure cascade and manual resume. A leaf may have no authority to change the failing surface, so assigning it the repair does not supply a repair owner. Repetition invites duplicate fixes or pressure to widen leaf scope. Evidence: `issues/log.jsonl:1032`, `:1033`, `issues/open/autopilot/any-consultants/implementation/report.md:31`, `skills/implement-issue/SKILL.md:38`.
- O2 **(c), validated known-red continuation including merge:** reject as the default, but keep it as a legitimate operator option. It avoids waits and has Chromium production precedent. It changes acceptance from “required checks passed” to “no attributable new failure.” A new defect inside an already-failing unit can remain hidden, and persistent exceptions can reduce pressure to repair shared failures. The prior contract itself records that residual risk (`issues/chart/red-base-wait/forks/merge-gate.md:23`). Correct implementation needs completed per-unit comparisons, protection of the leaf's own criteria and shared repair ownership, not “base exited nonzero, ignore leaf red.” Prefer (c) if the operator explicitly values continued integration over an all-green gate and accepts that remaining attribution limit. No measured local cost comparison establishes that tradeoff for them.

## 4. Pitfalls and what removes each

- R1 **Unexplained does not mean base-caused.** Require a fresh run on the exact comparison base, equivalent command/configuration, completed results and matching failing units. Review causal changes, not just touched filenames. Unknown, interrupted or setup-failed evidence does not establish a shared test defect. Prior functional distinction: `issues/closed/red-base-wait/known-red-leaf/brief.md:4`, `:7`, `:9`.
- R2 **Shared wait prevents its own repair.** Give one owner an explicit scoped repair path that remains runnable through the incident. No automatic grant of credentials or live-change permission. A generic failed-otherwise retry is not a substitute for that path (`skills/watch-issues/SKILL.md:40`, `:41`).
- R3 **Old evidence clears a different incident.** Identify the affected command/configuration/unit and evidence generation, not just base SHA. Resolve against fresh evidence under the mutation lock. A new commit, issue close or older green receipt is insufficient. Precedent: `issues/closed/red-base-wait/known-red-leaf/brief.md:30`, `:31`.
- R4 **Resume skips leaf verification or user controls.** Resume only work waiting for the resolved incident, with pause/stop and active-seat checks retained. Refresh onto a landed code fix where necessary, then verify that leaf's resulting revision before advancement. Use existing command events, no new polling. Evidence boundaries: `src/next.ts:749`, `:750`, `src/phase.ts:291`, `skills/watch-issues/SKILL.md:41`.
- R5 **Lifecycle fixed, direct landing still blocked separately.** Apply the same disposition and evidence policy to both. A direct attempt has no leaf state to move out of failed (`skills/chart-issues/SKILL.md:110`, `issues/verify-runs.jsonl:122`). Its resumption mechanism needs an explicit contract.
