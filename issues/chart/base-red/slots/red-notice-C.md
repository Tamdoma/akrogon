# Fork notes C: red-notice (Q1 notice, Q2 prevention)

## Pick

Q1: one herdr notification per incident, deduplicated from the verify receipts themselves, with delivery stored on the differential receipt. Two changes to the option as stated in the fork:

1. Drop `tree` from the incident key. Incident identity is scope + command (name and command string as recorded on the receipt) + unit, within the repo's own receipt file. While main is red, leaves keep landing, so the main tree changes with every landing; a tree-keyed incident re-notices on every landing and dedupe is lost. This matches the 2026-10-10 red-record identity (command/args/scope/conditions per unit, no sha). Tree and base sha are recorded as evidence, not identity.
2. Delivery lives on the differential receipt record the taken policy already adds, not in a new record file. When `verify` finalizes a known-red pair, it scans earlier receipts in file order: a unit is new when no earlier pair for the same incident recorded `notice` shown since the unit last resolved. All newly red units in one pair go in one notification (count plus first names plus receipt id when there are many). The pair records the herdr reply reason or `error`, mirroring `failure.delivery` (src/phase.ts:83-104). An incident resolves when a later base-side run no longer has the unit red: a later differential base run without it, or a completed verify of the default-branch tip green for that command. A green run on a leaf head never resolves, because that leaf may have edited the test locally while main stays red. Notice failure never fails `verify`: record the error, print a line, and the next pair for an unresolved incident retries.

Reason: the taken policy's accepted cost already says main "stays red until the operator charts the repair from a notice", so a notice is the remaining half of that decision, and the operator settled its shape on 2026-10-10: one notice per new entry, joins silent, no auto seed, no repair owner. Receipts are the record that survived dc2e2b0, so computing incidents from them adds no new file or store, only a field on a record the policy leaf creates anyway.

Cost: receipt schema grows by the notice field; a sequence scan and a decide-then-send step join verify's finalize path, under the existing record lock discipline (src/verify.ts:176-187 rewrites under lock); the sender must be decided under that lock so two pairs finishing at once do not both notify. Desktop notices are still transient: `shown` means herdr accepted it, not that the operator saw it. Invites later: pressure for a durable queue (a status line, an issue) if a notice is ever missed and a red lingers; that is a separate ask, not this fork.

Q2: one test-proof rule line, nothing in `src`, no lint. Rule shape: an expectation over a clock- or date-derived value either injects the time or computes the expected value from the time observed in the same run (the before/after pattern of 0dfae20); a fixed numeric bound on such a value is a defect in the test. It belongs in the test-proof rules that plan-issue writes criterion tests under and check-issue already routes wrong criterion units to (skills/check-issue/SKILL.md:69). Cost: one line of prose in one place, enforced by the reviewers who already read those tests. It covers only the clock class; environment decay (the #76 kind) has no such rule and stays absorbed by known-reds-pass plus the Q1 notice.

## Rejected options

Q1(a) Notice on every known-red pass, no stored state. While an incident lasts, every affected leaf passes verify at implement end, at check end and at merge, so the operator gets the same desktop notice many times a day on the same channel and sound as `failed` leaves (src/phase.ts:83-104). That trains ignoring the channel that also carries real failures. Its one merit, implicit retry, the pick keeps through the delivery field.

Q1(b) as stated, with tree in the key. Rejected only on the key: see the pick. Tree-keyed dedupe degenerates to per-landing notices exactly while known-reds-pass is doing its job.

Q1(c) GitHub issue per incident. This is the auto seed the operator foreclosed on 2026-10-10 (red-record Taken Q2 cut; Foreclosed: auto seed, owner link). It also puts a network write and a `gh` credential in the verify path of every consumer repo, needs duplicate search that the seed skill does by agent judgment over bodies (code cannot do that honestly), and the signal only arrives when the operator next runs `akrogon pull`, later than a notice. Invites: machine-filed duplicates in consumer inboxes that the operator must triage, and verify slowing or erroring on GitHub outages. Reversing the 10-10 foreclosure is the operator's call to make explicitly, not a side effect of this fork.

Q1(d) No notice; seat report and `akrogon status` show it. Seat reports are per-leaf artifacts nobody reads routinely, and `status` today prints nothing about base health (src/status.ts prints leaf state, Missing lines, history), so this option is really "no signal plus a status feature to design". Main then stays red silently and every affected leaf keeps paying a fresh base run with no forcing event, which is the lingering-red cost the taken policy accepted only in exchange for a notice.

Q2 clock seam in `src`. The product reading the clock was correct in the seen case: backlog age as of now is the behavior (src/timing-report.ts). The defect was the test bounding that value against fixed numbers, and 0dfae20 fixed it inside the test with no product change. A blanket `now` injection across 19 `Date.now()` sites in `src` is a wide refactor that invites threading a clock through call sites that only measure elapsed time, where the real clock is right.

Q2 lint. Fixed date literals are legitimate fixtures all over the suite (16 test files use the real clock, most of them fine); the defect pattern is a fixed bound on a clock-derived result, which a lint cannot distinguish from a correct relative computation without understanding the assertion. New lint machinery plus false positives, to catch what one review rule catches at the point tests are written and reviewed.

Q2 none. Defensible, since known-reds-pass absorbs decay and the one case is fixed. Rejected because the rule is one line against a recurring tax: every future date-rot repeats the incident, the base runs, and the repair charting, and red-first proof at plan time cannot catch it, since it shows a test is sensitive to the change, not stable over time (INTAKE.md, suspected cause).

## Pitfalls, and what removes each

P1. Two differential pairs finalize at once and both send. Removed by deciding the sender inside the verify-runs lock when the pair record is written (mark the pair as the notifier for its new units), then sending outside the lock and recording delivery in a second locked update.
P2. Herdr is unavailable where verify runs (outside a herdr session) and the notice throws the leaf's verify red. Removed by construction: the notice attempt is caught, `notice: error` is recorded with the error text printed, verify still returns its differential pass. Unlike `announceFailed`, nothing rethrows.
P3. The operator never sees the one desktop notice. Not removed. `shown` is herdr's acceptance, not a read receipt. The residuals are durable but passive: the receipt sequence and each seat's report recording the known-red judgment. Accepted for this fork; a status surface is a separate ask (see Q-a below).
P4. A unit fixed inside a leaf resolves the incident while main is still red, silencing a later recurrence. Removed by the resolution rule in the pick: only base-side runs and default-tip verifies resolve, never leaf-head runs.
P5. A suite-wide environment break makes hundreds of units new at once and the notice body explodes or herdr truncates it. Removed by form: one notice per pair carrying the count, the first few unit names and the receipt id; the full list stays in the receipt and logs.
P6. The same test runs under both `checks` and `merge_checks` and notices twice under two scopes. Accepted: scope is part of the identity because the command sets differ, and a second notice at merge scope still tells the operator the merge gate is passing on a red. If it proves noisy, keying on command string alone is a one-line change later, with data.
P7. The Q2 rule duplicates into several skills and drifts. Removed by placing it once in the test-proof rules the other skills reference by name, the same reference check-issue:69 already uses for routing wrong criterion units.
P8. A fresh base run proves units red, but the pair does not pass (a head command has no extractable units, or the head adds a unit), so no pair is finalized and no notice fires, while main is in fact red. Not covered by my pick as written; see Q-b below.

## Questions the fork does not ask

Q-a. Is a transient desktop notice enough as the only operator signal, with no durable queue? A derived `akrogon status` line (known-red units from the receipt sequence, no new store) would make a missed notice recoverable at the next status glance. The fork offers status only as the no-notice option; notice plus a status line is a third shape worth one line of scope, in or out.
Q-b. Should the notice fire on any fresh base run that finds red units, or only when a differential pair passes? Under pair-only, the P8 case (leaf blocked for its own additional failure while the base is also red) leaves the operator unaware of the base red until some other leaf passes differentially.
Q-c. Notice sound and wording: `--sound request` like a failed leaf, or quieter? It asks for the same class of operator action (chart work), but it is not blocking anyone, which argues for a distinct, lower-urgency signal. The fork does not say.
Q-d. Q2 looks forward only. The current suite has 16 files using the real clock; some may already carry fixed bounds that will rot on a future date. Does the operator want one audit pass over existing tests now, or let each surface as a noticed incident under the new rule?
