# B rebuttal 2

- F1 Addendum `:36` and C `:34` treat completed verify plus setup 0 and a failing-name subset as sufficient evidence. Current verify completion means every configured command returned, not that each test runner completed all required coverage (`src/verify.ts:164`, `:172`). A runner can report a known failing test and then crash, leaving the extracted set entirely contained in the base set. An empty extracted set also cannot justify a nonzero command. Require positive runner-completion evidence and account for every failing command, with unsupported, timed-out and incomplete outcomes blocking. This is not yet “removed by construction.” The earlier contract explicitly classified interrupted or prevented coverage as unverified (`issues/closed/red-base-wait/known-red-leaf/brief.md:7`).

- F2 Addendum `:39` and C `:19` overstate “receipts plus existing unit extraction carry the same facts.” Current receipts contain command exits/logs and one revision, not the comparison base, retry linkage, per-unit completeness, criterion ownership or recorded causal judgment (`src/verify.ts:16`). Receipts can be extended instead of restoring three modules, but that still needs an explicit comparison contract. In particular, own done-criteria must remain blocking before this can claim equivalence to the October 10 policy (`issues/closed/red-base-wait/known-red-leaf/brief.md:9`, `:27`). C correctly leaves that boundary open at `:45`, so the merged proposal must remain conditional on it.

- F3 Addendum `:37` and C `:21` say a leaf that adds no observed failure cannot make main worse, reducing green landing to a slogan. That conclusion exceeds the proposed evidence. C `:11` acknowledges that a new defect inside an already-red unit can remain hidden. Green landing provides a distinct check that those units pass on the candidate, though it cannot prove all bugs absent. Known-red continuation remains a legitimate throughput choice with accepted detection limits. It is not proven equivalent protection. Evidence: C `:11`, `issues/chart/red-base-wait/forks/merge-gate.md:23`.

- F4 Addendum `:36` and C `:37` do not establish notice deduplication or recurrence handling from tree+scope+unit alone. Command/configuration changes can occur under the same source tree, and an environment repair can make a unit green without any green landing. A later recurrence still needs a new notice. Define comparable command/configuration identity, observed resolution and notice delivery/retry state, whether stored on receipts or elsewhere. Merely selecting the first historical red cannot provide these properties. Evidence: `src/verify.ts:49`, `:63`, `issues/closed/red-base-wait/known-red-leaf/brief.md:12`, `:30`. Also, C `:36` calls receipts append-only, but verify rewrites an existing run when it finishes (`src/verify.ts:174`, `:179`, `:187`).

- F5 C `:9` says the reduced option removes the whole intake problem. It removes base-red waits and manual phase recovery, but intentionally keeps a fresh base run per affected leaf and leaves repair dependent on later operator charting (C `:7`, `:11`, `:38`). The intake also asks for one detection and one repair owner. Record repeated verification and delayed ownership as retained costs or an explicit scope change, rather than claiming that whole outcome is delivered.
