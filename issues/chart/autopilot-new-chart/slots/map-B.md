# Territory map B

## Destination
A handed chart that needs a separate new chart leaves a concrete yes/no proposal, waits for the operator, and lets autopilot finish other runnable handed work without extending its own authority.

## Locks
O1 is settled: wait on the affected chart and move on within the handed list. The proposal before waiting is also settled. Neither needs another option round.

## Material forks
F1 · What distinguishes a needed new chart from normal chart growth?
- O2: use repo boundaries alone. Simple, but unrelated goals in the same repo can become hidden scope expansion, while one outcome spanning repos can be misclassified.
- O3 (pick): judge the promised outcome and actual dependency. New questions refining the handed outcome stay forks; an independently provable prerequisite serving that outcome can be a leaf; a separate destination needing operator scope approval triggers the proposal and wait. Merely useful unrelated work is recorded only.
- Reason: this uses Drain's existing destination judgment and Handoff's dependency audit. A different repo is evidence to inspect, not a complete definition. Do not bundle a separate goal just to avoid waiting.

F2 · Where does the proposal live?
- O4 (pick): put the goal, why needed and waiting chart in the current chart's existing Autopilot wait record, with a link to supporting findings if needed. Show that same concrete decision in the pass-end account.
- O5: create the proposed chart folder before approval. This invites phantom open charts, duplicate detection conflicts and accidental inclusion in handovers.
- O6: add a proposal queue, schema or dedicated file type. This creates another record to synchronize and another resume mechanism.
- Reason: one existing chart record survives compaction and handover without creating unhanded work. Add no mandatory proposal file or lifecycle state.

F3 · What does the later yes/no answer authorize and what clears the wait?
- O7: treat yes as permission to create, run, hand off and start the new work. This silently merges scope approval, charting mode and execution authority.
- O8 (pick): the proposal states the exact new-chart scope and whether approval adds it to this door's handed list. Yes approves only that stated change; record any list update through the existing Mode record. Other grants and execution retain their existing rules.
- O9: require a second confirmation even after a concrete proposal is approved. This defeats the requested yes/no morning decision.
- Reason: reuse existing authorization and mode changes. Keep the original chart waiting until its actual prerequisite is satisfied or the operator explicitly resolves its scope; approving a new chart does not deliver its output. A no leaves the unresolved dependency visible, rather than silently narrowing the outcome.

## Lifetime pitfalls and removing steps
R1 · A soft wait gets a terminal Held marker, releasing duplicate protection. Remove it by recording wait under Autopilot with no Held, Closed or Handed off marker; existing spans close on waits.
R2 · A waits for an immediate operator reply and blocks the overnight batch. Remove it by writing the proposal before switching to the next runnable handed chart using existing Drain/Handover behavior; end the pass when none remain runnable.
R3 · Fresh A forgets the proposal or reopens the same question. Remove it by keeping the proposal and exact next action in the waiting chart, preserving that chart in the remaining handed list and existing handover records.
R4 · A emits a dependent leaf naming a chart or nonexistent leaf in blocked-by. Remove it by leaving the chart unhanded until the existing preflight can resolve real leaf prerequisites. No placeholder state or cross-chart scheduler.
R5 · Consultants agreeing is mistaken for operator authority. Remove it by allowing consensus to sharpen the proposal, never to approve a new scope or change the handed list.
R6 · A proposal is mistaken for completion or clears itself when approved. Remove it by keeping approval, chart creation and dependency satisfaction distinct observed facts in the same record.
R7 · A blanket same-repo prerequisite rule absorbs a different product goal. Remove it by comparing the proposed work to the handed Destination before choosing leaf versus new chart.
