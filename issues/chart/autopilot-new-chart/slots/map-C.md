# Territory map, slot C: autopilot-new-chart

## 1 · Destination

Under autopilot, a handed chart that cannot hand off without a separate new chart parks as an operator approval wait carrying a ready yes/no proposal in its own record, A finishes the rest of the handed list, and the operator's later yes or no in the door pane alone resumes it.

## 2 · Material forks

- **F1 Trigger: what counts as "needs a separate new chart".** Options: (a) both tests pass: the found work is its own destination (own observable outcome, per Drain "one chart folder per destination") AND the handed chart cannot hand off without it; (b) any second destination found, needed or not; (c) different repo only. Pick (a): it reuses the existing destination test and the door's case split (not depended on = recorded only; same-chart dependency = prerequisite leaf). Breaks: (b) parks charts that could finish, recreating the overnight stall the operator asked about; (c) lets two same-repo destinations be smuggled into one chart; a vague (a) still invites A to over-split to avoid hard forks, so the "cannot hand off without it" half must be stated, not implied.
- **F2 What kind of wait the park is.** Options: (a) name the operator's yes/no an approval wait; (b) add a fourth wait kind everywhere; (c) use the `Held` marker. Pick (a): Drain move-on, Open span closing, shapes `seats.yaml` spans, Handover trigger, and Autopilot mode-persistence all already key on "approval, need or prerequisite", and questions already keeps approvals operator-only under autopilot, so (a) adds no mechanism. Breaks: (b) means editing every list that repeats the trio and one missed list silently desyncs; (c) mode ends only on `Handed off`/`Closed` and no resume rule exists for `Held`, so the chart would keep the mode on forever with no way back; (a)'s risk is confusion with grant approval, removed by stating it is not a grant.
- **F3 Where the proposal lives.** Options: (a) one new line kind in the waiting chart's `## Autopilot` section, next to its existing `wait:` line: proposed chart goal, why needed, which chart waits; (b) create the new chart folder as pending; (c) a new PROPOSAL.md file; (d) printed in the pane only. Pick (a): shapes already records waits there, every line is a `- ` item so nothing parses as a chart marker, and fresh A after handover or compaction reads CHART.md. Breaks: (b) is extending the handed list in effect, claims the new destination in duplicate detection, and collides with the Handover folder-with-pending-Destination meaning; (c) adds a file type nothing reads; (d) is lost overnight.
- **F4 When A parks.** Options: (a) as soon as the separate destination and the dependency are sharp enough to state goal/why/waiting chart, having recorded findings so far; (b) finish all remaining forks first, park at handoff. Pick (a): answers reshape later forks (Take), so forks taken under a destination the operator may split are likely rework. Breaks: (b) can hand the operator a near-done chart whose split decision undoes it; (a)'s cost is a thinner proposal, bounded by the sharpness test in (a) itself.
- **F5 What yes means.** Options: (a) the operator's yes in the door pane is a handed-list change, recorded with the existing `changed list` mode entry, and A then charts the new chart under the same autopilot session; (b) yes only permits a future attended door. Pick (a): Autopilot already says changing the handed list keeps the mode on, so the resume path exists today. Breaks: (b) breaks the lock's point (operator only says yes or no) by making them restart the work; (a) invites chained proposals (the new chart proposes another), bounded because each chain link needs its own operator yes.
- **F6 What no means.** Options: (a) no = one chart, not two: A resumes the handed chart with the found work in scope as forks/prerequisite leaves, recording the operator's override; (b) no = drop the found work: A narrows the handed chart or records why it now cannot hand off; (c) no = drop the handed chart. Pick (a): it matches the door's O1 wording ("the operator decides one chart or two") and always leaves A a next step. Breaks: (b) can strand the handed chart unhandoffable and force a second morning decision; (a)'s cost is one chart holding two destinations by operator order, which is the operator's call to make; (c) discards handed work the operator never said to drop. This is the fork where the intake is thinnest, see Fog.
- **F7 Scope: autopilot only, or attended too.** Options: (a) rule lives in `## Autopilot` only, plus at most one precedence clause there ("the handed list wins over one folder per destination"); (b) also give attended doors a proposal step. Pick (a): attended, the operator is present and Drain's split already runs by asking. Breaks: (b) adds a record step that duplicates the live round; leaving the Drain/Autopilot contradiction unstated (neither) is the current F4 defect.

## 3 · Pitfalls, each with the step that removes it

- **P1 Fresh A re-enters the parked chart and re-proposes.** Removed by F2+F3: the proposal/`wait:` lines in CHART.md are the record fresh A resumes from, and an approval-wait chart is by existing Drain wording not the next runnable chart until the wait clears.
- **P2 Duplicate proposals for the same found work across passes.** Removed by one proposal line per proposed destination, updated in place (same pattern as one `wait:` per wait in shapes).
- **P3 The park looks like a stall in the morning record.** Removed by existing machinery: the pass ends with one line per chart and the printed footer's `Next:` names the blocker; docs/use/autopilot.md "What still waits for you" must gain this bullet or the user doc contradicts the skill.
- **P4 Proposal read as approval, or consultants' consensus treated as yes.** Removed by F2: an approval under autopilot is never A's to record (questions, Autopilot), and the proposal line states it awaits the operator's yes/no. This also forecloses the operator's original consensus-creates-charts idea exactly as O1 locked.
- **P5 Overnight wait inflates the chart's measured work time.** Removed by F2(a): approval waits already close the seat span (Open; shapes `seats.yaml`), so no span edit is needed.
- **P6 After yes, the waiting chart names `blocked-by` leaves that do not exist yet.** Removed by existing preflight (shapes: refuse missing blocked-by targets): the waiting chart can only hand off after the new chart's leaves are written, so A charts the new chart first, then resumes the waiter. No new ordering rule needed beyond stating that sequence.
- **P7 Proposal goes stale while other handed charts land.** Removed by existing destination checks on resume (Handoff checkpoints re-pull and re-check seeds); no expiry mechanism needed.
- **P8 The parked chart's Destination quietly grows to claim the new work.** Removed by F3: Destination stays unchanged, the proposal lives under `## Autopilot`; claiming it would also poison the other-door same-outcome hold in Autopilot.

## 4 · Evidence (better-than-training unless stated)

- **E1** The contradiction is real: `skills/chart-issues/SKILL.md` Drain says "Write one chart folder per destination" and, under autopilot, Drain "imports nothing new"; `## Autopilot` says the door never extends the handed list. Neither states precedence.
- **E2** The approval-wait trio is repeated as the move-on/park trigger in Drain, Open (span closing), `## Autopilot` (waits list, mode persistence), `## Handover` (trigger), and `assets/shapes.md` Chart records (`seats.yaml` spans). One classification sentence reuses all five; a new wait kind must edit all five.
- **E3** The yes-path already exists and the intake's door findings do not mention it: `## Autopilot` keeps the mode on when the operator changes the handed list, and shapes Mode record already defines a `changed list` entry. Surprising: no new mode machinery is needed at all.
- **E4** `assets/shapes.md` Autopilot lines already define `wait: <exact missing need, approval or prerequisite> — next: <next step>` and a `pending step:` line that records opening a future chart door, the closest existing precedent for F3(a).
- **E5** Surprising against the door's case split: its archetypal separate case is "different goal or repo", but `blocked-by` cannot express a cross-repo prerequisite — `src/next.ts` `dispatchDependents`/`sweep` resolve `blocked-by` slugs only within one repo's discovered leaves. After a yes, a cross-repo dependency has no command-level ordering; the waiting chart's brief can only state it in prose. Charts have no lifecycle state for the command to read (`src/status.ts` `lastStage` reads only the Handed off/Closed/Held markers).
- **E6** The seam was explicitly left open by the designing chart: `issues/chart/autopilot/forks/boundary.md` Taken: autopilot "pulls in nothing new during the run. Where new incoming work enters is not assigned here". This chart is that assignment, so F5(a) completes a stated gap rather than reopening a settled fork.
- **E7** No mechanical check covers any of this: `tests/chart-shapes.test.ts` tests only that shapes' `readiness.yaml` example parses and draft gaps work. Wording drift between SKILL.md, shapes.md and docs will not be caught by tests; the leaf's proof is inspection, and an exact-wording test would be the wrong fix.
- **E8** No live wait example exists to copy: `issues/chart/config-walls/CHART.md` `## Autopilot` (an actual autopilot run, handed off) has no `wait:` line. `learnings/LESSONS.md` has no autopilot or handed-list lesson (searched: autopilot, new chart, handed list, extend — no matches).
- **E9** Contradicting a quick reading of the intake: the mode-end rule (`## Autopilot`) ends the mode only when every handed chart is `Handed off` or `Closed`, so a parked chart keeps the door in autopilot across pass end by default; the operator's overnight worry is answered by Drain move-on within the handed list, not by any new overnight rule.

## 5 · Split, scope, off route, fog

- **Leaves: one leaf.** The change is one rule stated once and mirrored in the record shape and user doc; splitting invites the three copies to drift (E7). Nothing here is independently checkable apart from the rest.
- **Scope files:** `skills/chart-issues/SKILL.md` (`## Autopilot`: trigger test F1, approval-wait classification F2, park point F4, yes/no effects F5/F6, precedence clause F7); `skills/chart-issues/assets/shapes.md` (Chart records, Autopilot lines: the proposal line kind); `docs/use/autopilot.md` ("What still waits for you", "Read the record"). `assets/questions.md` needs no change if F2(a) is taken — its approvals-stay-operator-only exception already covers the yes/no.
- **Off route:** `src/next.ts` and all other code (E5: no consumer reads proposal lines; cross-repo `blocked-by` is a separate destination if ever wanted); `tests/chart-shapes.test.ts` (E7); attended-door behavior (F7); any score, timer or watcher change (already off route in `issues/chart/autopilot/CHART.md`).
- **Remaining fog:** (i) F6 is inferred from the door's O1 wording, not from operator words about "no" — the intake records only "ok, go" for the proposal step; (ii) whether one handed chart proposing two separate charts parks once with two proposal lines (assumed yes, P2) is unstated; (iii) after a yes to a different-repo chart, what "the waiting chart resumes" concretely waits for, since no `blocked-by` can order it (E5) — may be acceptable fog for the implementer to state as a prose dependency, or may need its own fork.
