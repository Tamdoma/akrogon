## Q1. What does the reporting leaf become, and what shared record is written?

1. Pick, reason and cost: keep its existing phase and add a structured base-red wait referencing a shared repository incident. The reporting seat ends its pass without a failed transition or successful verdict. Store the repository, exact command/arguments and scope, tested base SHA, completed comparison evidence, material run conditions, reporting leaf/seat/head and incident identity. The leaf's wait links to that incident and preserves the phase to resume. This separates a broken base from leaf failure and avoids a new phase with a saved return phase. Cost: dispatch, phase advancement, status and watch must recognize the wait. Existing phase bookkeeping must distinguish an ended blocked pass from a completed review, without marking the red proof green.
2. Rejected alternatives: `failed` plus a base-red failure subtype reuses today's stop machinery but keeps failure recovery and watch cycling attached to waiting, contrary to the requested behavior. A new `held` phase adds return-phase routing and special handling across every phase consumer although the work has not changed phase. A repo-wide pause blocks unrelated work and the repair, and manual next bypasses pause. Shared notice alone preserves repeated failures and manual recovery.

Store incident plus waiter consistently under the existing mutation lock, with recoverable ordering for partial writes. Preserve worktree changes and review artifacts. Do not clear independent failures, operator pause, repair counts or unrelated wait reasons. Remove the stale-clear race by following learnings/history/2026-10-10-red-main-hold-stale-clear.md:6-8. ## Q2. What does another leaf do when its same-command, same-base run goes red?

1. Pick, reason and cost: after its own fresh completed red run, the seat judges whether the existing active incident explains that failure with no plausible cause in its diff. If exact command/arguments/scope, tested base and material conditions match, attach this leaf to that incident and end the pass in the same phase without another base run or failure notice. Reuse only the established negative base comparison. Keep its own leaf log and explanation with the wait. Cost: an explicit equivalence judgment remains necessary. The second leaf still pays for its own run and may need a base run when evidence does not establish equivalence. This does not promise to prevent already-started concurrent runs.
2. Rejected alternatives: always repeat the base comparison wastes the established result and misses #76's requested saving. Attach solely on command text plus SHA can hide a different leaf defect or reuse evidence after an environment repair, the #77 mechanism. Stop every leaf before it runs merely because a matching command appears in configuration can also stop the very leaf fixing that command and adds a command dependency model. Treat every red run as attributable to the base would conceal real leaf regressions. Skip the configured leaf proof and call it successful violates checks and done-criteria. The proposed wait is not success.
3. Evidence: operator tier, INTAKE.md #76 records multiple independent comparisons on the same base. Its #77 report records a root node_modules repair outside git and explicit fail-fast saved-log reuse. better-than-training tier, skills/check-issue/SKILL.md:63 requires both terminal results, equivalent command/scope/conditions and an explanation of why base failure explains leaf failure, while allowing different failing names. skills/implement-issue/SKILL.md:38 has the same attribution boundary. src/phase.ts:142-153 does not make old logs fresh after recovery. operator tier, check-reruns/CHART.md:14 rejects a general check-record runner because safe reuse needs declared inputs. These support narrowly reusing active negative evidence, not a general cache or text-only match.
4. Pitfalls and what removes them: a new failure under the same command is not necessarily the recorded defect. Require the seat's explanation against its actual output and diff, not identical failure names or no touched paths alone. A nested checkout and detached checkout can behave differently through ancestor dependencies, as recorded in Slot B map F2/R1. Record the conditions that mattered and decline shared attribution when they do not transfer. An incomplete run establishes no base defect, per the existing skills. Do not silently wait on a missing/incomplete evidence reference. Concurrent join/release must reread the same incident identity under the mutation lock before attaching. If it changed, re-evaluate instead of recreating an expired incident from old logs. Expiry rules are a dependency on the separate evidence-expiry fork.
5. Extra question: when equivalence is not established, should the seat perform today's one base comparison and register a distinct incident if that is red? Recommend yes, retaining the existing attribution rule. What may the seat do when it is deliberately fixing the recorded base defect? It needs a repair route that permits fresh proof rather than automatic attachment. Settle that route before handoff. Also distinguish suppressing another base comparison from suppressing an entire broad leaf suite, which this question's post-failure trigger cannot achieve.

## Q3. How are two different red commands recorded and announced?

1. Pick, reason and cost: one repository health record containing separate active command incidents, each with its own evidence and linked waiters. Keep distinct commands and distinct materially different comparisons separate. Concurrent reporters add or join an incident rather than replacing the repository record. Announce each newly recorded command incident once, including the command, base, evidence location and current known affected leaves. A later new command deserves a new notice that also lists the other outstanding commands. Joining an existing incident is silent. Cost: one repo may produce more than one notice when new defects are discovered. The initial notice cannot list a command not yet discovered without a forbidden delayed batching timer. “Once” therefore means once per distinct incident, not one notice forever per repo.
2. Rejected alternatives: today's one-command last-write record loses the first failure and its waiters. First-write-wins hides the second command and prevents separate release judgments. One notice for the whole repository's first red period hides later defects unless an already-shown notice can be updated, a capability not established here. Per-leaf notices reproduce today's noise. Inferring shared incidents by failure-name text can merge different commands or split equivalent failures, contrary to the skills' causal comparison.
3. Evidence: operator tier, INTAKE.md #76 names C8 selftest and motion-probe together on main 5cb74c3c6, so multiple records are a present requirement. better-than-training tier, src/hold.ts:10-21 permits one Hold per repo and :59-60 replaces that entry. src/phase.ts:857-878 writes and announces one command. src/next.ts:1062-1072 checks and clears that one hold inside its lock. operator tier, learnings/history/2026-10-10-red-main-hold-stale-clear.md:6-8 proves overlapping CLIs can otherwise erase a newer hold. These support additive incident records and identity-aware mutation, with no claim that current notification APIs can update an existing notice.
4. Pitfalls and what removes them: clearing one command must not clear another command or another base's incident. Release only associated identities and let a leaf remain waiting while any of its linked incidents stands. Record notification delivery separately from evidence so a delivery failure cannot lose the wait. Deduplicate incident creation under the lock before attempting the external notice. Define how an unconfirmed notice is retried on an existing event or explicit command, with no timer. Do not claim exactly-once delivery across a crash between showing and recording delivery. Persisted deduplication can prevent ordinary duplicate reports, but a delivery acknowledgement gap needs an explicit policy. Preserve the current merge hold's fix route and all-mode gate when sharing the record infrastructure. Do not silently widen pre-merge waiting into a repo-wide freeze.
5. Extra question: does the operator want one notice per newly discovered command, or one per repository red period with later commands visible only in status? Recommend the first because the second hides necessary repair work. Before handoff also settle how early-phase incidents coexist with merge's current holder/attempt/fix fields. Those are merge coordination, not required identity for a pre-merge incident. Use one shared truth for the same confirmed defect, without fabricating batch metadata or introducing two independently clearable holds.

Result: recommend phase-preserving typed waits, narrowly shared completed negative base evidence, and multiple additive command incidents with one notice per new incident. Release triggers and evidence expiry remain undecided. No implementation or lifecycle command run.
