# red-record Q2: disagreement-only rebuttal, Slot B

Read red-record-q2-merged.md and the requested live phase/park/close/state/routing surfaces. Evidence checked 2026-10-10.

- R1 · The landed-proof simplification is conditional, not established by fast-forward alone. A fresh green run on candidate T can become evidence for that exact revision once T is confirmed landed, if the operator accepts that reading of Q1 and its material conditions match the target proof. It is not a run executed after landing and does not establish current main green under different checkout/dependency conditions. More concretely, this command does NOT always push the exact tested top: src/phase.ts:487 permits head=record.top under decision=reuse while tested_top names an earlier top; :553-558 and :657-659 carry that older tested pair onto a restacked candidate. Code/config equivalence is not proof of environment equivalence. Either explicitly authorize candidate-green-plus-confirmed-landing as resolution evidence, with accepted reuse conditions, or retain the post-landing proof. Do not record unconditional “not a new step” against the accepted target/conditions boundary. Evidence: operator tier, red-record Q1's landed-target requirement and comparison Taken's material conditions. better-than-training tier, src/phase.ts:487-499,553-558,647-659. No separate job is necessary if the narrower proof interpretation is chosen, but that is a contract decision.

- R2 · Resolving only alongside the normal successful-push merged write misses recovery paths. A failed or ambiguous push can actually have landed; src/phase.ts:743-765 confirms candidate ancestry and completes members later. An interrupted successful push can likewise leave reconciliation to a later next pass. Apply the same incident identity/claim/proof checks wherever landing is confirmed, and make resolution idempotent. A historical candidate's presence in a later main does not prove that later tip still passes. Keep the resolution revision precise and refuse clearing a newer conflicting observation, even when an older fix landed. Evidence: better-than-training tier, src/phase.ts:743-765 and :495-500; operator tier, learnings/history/2026-10-10-red-main-hold-stale-clear.md:6-8. Otherwise a narrow success hook leaves valid landed repairs unresolved or clears a newer defect incorrectly.

- R3 · The watch's two-cycle rule is neither an automatic command recovery mechanism nor a total retry bound. next returns waiting for failed leaves (src/next.ts:674-676), and seats cannot resume a failed leaf themselves (src/phase.ts:241-243). Recovery exists only when the operator-started watch runs. Its rule counts two consecutive failed→P→failed cycles where failure is the very next record; a recovery that progresses into another phase before failing does not count. One stable leaf prevents endless replacement leaves, but not unlimited recoveries with intermittent progress. Add command-owned reconciliation on existing events/startup/next so automatic ownership does not depend on a manually started watch. Settle a cumulative automatic recovery bound for the incident/owner, without resetting it on phase progress or session replacement, while preserving the existing within-pass fix cap. Evidence: better-than-training tier, skills/watch-issues/SKILL.md:39, src/phase.ts:307-320 and the next/phase guards above. Treat permanent capability failures explicitly, not as another runnable recovery.

- R4 · Parking semantics can be a deliberate suspension, but ordinary park cannot currently implement it after the repair has been allocated, even if the seat is idle or failed. src/park.ts:22-25 calls a leaf running when tab OR worktree exists; :54-56 refuses parking that owner. Define whether suspension is limited to pre-allocation parking, or add a safe command-owned deallocation/suspend operation. Do not silently relax the running-leaf guard. A failed repair is not automatically parkable, and attempting a refused park must not release ownership or create a replacement. Evidence: better-than-training tier, src/park.ts:22-25,47-68. Existing park/unpark semantics can govern successful suspension, but cannot be described as sufficient for allocated repairs without that addition.

- R5 · “Fixed elsewhere” has no existing truthful no-op merged/close ending. Review handoff requires a nonempty branch (src/phase.ts:283); solo merge and member ranges also enforce nonempty changes (:413,422). Routing has no cancelled/superseded phase, and merged means landed work. akrogon close closes a GitHub source through gh, not a local leaf (src/pull.ts:104-120,204-207). Park refuses allocated work and is suspension, not completion. Do not make an empty commit, forge merged, reopen a merged owner or claim GitHub close retires the repair.

  Recommend a narrow command-owned automatic retirement path for generated repair leaves: after valid target-side resolution, fence the repair claim, let any active seat finish/stop through a safe lifecycle boundary, preserve its partial work/report, safely release allocations, and archive the obsolete repair in the existing parked storage with the incident's “resolved elsewhere” reason. Reuse ordinary cleanup/parking storage without adding a generic cancellation phase, but explicitly recognize that safe deallocation/retirement is new code. Reconciliation must prevent unpark or a stale seat from resuming the obsolete obligation. If parking is chosen purely for suspension instead, then a truthful terminal no-op outcome is a separate needed addition. This is a material ending to settle before handoff, not an existing command to invoke. Evidence: better-than-training tier, src/routing.ts:27-49, src/state.ts:144-147 (open/closed inventory), src/park.ts:47-68 and the phase/close checks above.
