## Q1. How does a seat get per-test outcomes from arbitrary commands?

1. Pick, reason and cost: the seat reads complete run evidence and records a structured comparison of actual outcomes, with an evidence reference for each classification. Use a native report already produced by the check as evidence when available, alongside logs. Do not require a new configured reporter for every check or build a universal stdout parser. Record exact command/args/scope, counterpart/head revisions, material conditions, each test's identity (runner/stage, file/suite and full test name when exposed), actual result on each side and log location, plus run completeness and anything unaccounted for. Explicit pass is needed to say a failing test passed without the change. Absence is not pass. Cost: the seat must judge extraction and causality. An ambiguous result remains unverified rather than becoming known-red. Mechanical checks validate record presence, valid states and evidence references, not guessed semantics or exact prose.
2. Rejected options: a mandatory configured reporter per check makes this policy depend on consumer migrations and integrations for custom validators, browser probes and nested shell commands. Bun-only JUnit does not describe those outcomes. A machine parser treating every error-looking log line as a failed test misreads expected negative fixtures and nested processes. Unstructured prose or command-exit comparison alone cannot prove that every leaf failure has a matching base result. A fabricated test named after an entire command would restore the command-level exemption the operator rejected. “Both” is acceptable only as native evidence plus seat judgment, not as a new reporting configuration system by default.
3. Evidence: operator tier, waiting-leaf.md Taken requires per-test attribution and treats absent/renamed/unparseable outcomes as unverified. INTAKE.md names C8 and motion-probe, proving heterogeneous failures matter now. better-than-training tier, src/config.ts:49-50,265-267 represents checks as arbitrary strings and wraps setup separately. Consumer issues/config.yaml:8-16 includes a short-circuit `&&` pair and a broad merge command. Consumer package.json:8,10,158,162-166 mixes Bun tests, a contracts script, motion-probe, parallel stages and sequential commands. better-than-training tier, [Bun Test Reporters](https://bun.sh/docs/test/reporters), checked 2026-10-10, documents JUnit for bun test, written at run end, with no individual-test stdout/stderr. It helps only the Bun portion and cannot replace causal log evidence. Existing skills/check-issue/SKILL.md:63 requires both terminal results and an explanation, not merely equal exit codes.
4. Pitfalls and what removes them: duplicate short test names are separated by runner/file/suite identity. Interleaved parallel output needs stage provenance or remains unverified. Expected-error output counts only when the enclosing test actually failed. Every nonzero command exit must be explained by accounted outcomes or a separately recorded incomplete/non-test failure. Keep raw status before any reporting pipeline. Preserve original evidence instead of overwriting it with a summary. A base missing a newly added/renamed test needs the leaf's outcome proof and review, not automatic attribution. Explicitly update skills/check-issue/SKILL.md:59's blanket command-red blocker and :63's allowance for differing failing names so they implement the binding policy consistently.
5. Extra question: must every configured check's required coverage be established before acceptance, even if known base reds short-circuit an earlier stage? Recommend yes under the binding incomplete-verification rule. Also settle identities for custom named cases and whether partial evidence may prove individual outcomes without proving the whole check. The record should distinguish those two claims. Base record identity belongs in red-record, and reuse validity in base-evidence-reuse.

## Q2. What happens with unnamed or incomplete outcomes?

1. Pick, reason and cost: record an explicit non-test failure or incomplete/unverified run with command, stage, revision, status/signal, error evidence and the missing verification. Do not assign blame to the leaf without evidence, and do not permit handoff on an assertion that it added no failures when required coverage is missing. Completed identifiable test failures can still be compared individually, but they do not make an interrupted suite complete. A named validator case with demonstrated terminal results can be a comparison unit. A build/setup/crash diagnostic alone cannot stand in for all tests it prevented from running. Repair an attributable leaf defect through the normal path. When required verification cannot be completed within authorized scope, use the existing incomplete-verification stop with the exact cause, not a red-main hold or wait. Cost: unrelated broken tooling can still prevent acceptance through missing proof. This is the binding boundary, not the old rule stopping on every established base-red test.
2. Rejected options: ignore matching command exits or matching crash text on both sides. Neither proves downstream coverage or no new regression. Turn every diagnostic into a synthetic failing test and exempt the whole stage. That hides missing results. Treat missing tests as passed on either side. That violates Taken. Automatically retry crashes, timeouts or setup failures until green. That changes the current incomplete-run rule and confuses infrastructure termination with a completed test failure. Require every base test green. That reinstates the explicitly rejected main-health prerequisite.
3. Evidence: operator tier, waiting-leaf.md Taken F1/F2 explicitly keeps done-criteria and incomplete verification blocking and forbids treating unexecuted/absent outcomes as pass or known-red. better-than-training tier, skills/implement-issue/SKILL.md:36,38 and skills/check-issue/SKILL.md:59,63 distinguish criterion proof and terminated base runs. Consumer issues/config.yaml:11-12 has short-circuit commands, while package.json:162-166 uses nested parallel/sequential runs. Process exit alone therefore cannot establish which required stages completed. Practitioner tier, [Chromium CQ](https://chromium.googlesource.com/chromium/src/+/master/docs/infra/cq.md), checked 2026-10-10, describes configured test results and separately routes build/infra faults for investigation. It provides no rule treating an infrastructure failure as complete regression evidence.
4. Pitfalls and what removes them: an ordinary completed test failure that produces nonzero exit is not an interrupted run merely because it is red. Conversely, a process terminating normally can still skip required downstream tests. Record completion against declared command/stage scope, including skipped stages. Logs must show actual terminal outcomes, not only a runner summary. If required stages were skipped, obtain their missing proof through an explicitly declared command with equivalent conditions, or stop as unverified. Do not silently narrow the base comparison to one test: today's skills require matching command/scope, and altered execution can change behavior. Keep incident publication distinct from incomplete evidence, so a crash does not falsely create a known-red test record.
5. Extra question: does a complete, matching non-test build/validator failure ever qualify for continuation, and what independent proof replaces the tests it masks? The proposed conservative rule says no automatic exemption. If the operator wants that extension, it needs an explicit acceptance criterion rather than an invented “test name.” Who repairs an external setup/infrastructure defect belongs in red-record's ownership question, with incomplete records kept separate from confirmed base reds.

## Q3. Retry with the change once before the without-change run?

1. Pick, reason and cost: yes, one bounded same-command, same-scope, same-configuration retry after a completed test failure. No code or environment repair between attempts. Retain both results. A fully green retry is recorded as inconsistent with-change evidence, not known-red-on-base, and does not need a base run solely for that original failure. Review still judges any concrete defect and required proof. If the retry is red, compare its actual remaining failed tests against one without-change run, respecting Q1/Q2 and existing allowed base reuse. New failure identities on retry need attribution too. Cost: one additional command run, potentially another broad verify. INTAKE.md reports about 15 minutes for a full framework verify, an approximate observed case rather than a universal runtime estimate. This is a new policy choice beyond the operator's already-approved base comparison.
2. Rejected options: no with-change retry is cheaper but can label a one-off leaf failure a regression when base happens to pass, or attribute accidental simultaneous failures to base. It retains today’s simple one-base-run approach but sacrifices the flake distinction motivating this question. Retry until green permits arbitrary hiding of regressions and unbounded cost. Retry only the failing test without preserving its original execution scope can change shared state/order and produce irrelevant green evidence. Automatically retry incomplete/crashed runs contradicts Q2 and today's explicit stop rule.
3. Evidence: practitioner tier, Chromium CQ team, [CQ documentation](https://chromium.googlesource.com/chromium/src/+/master/docs/infra/cq.md), checked 2026-10-10, retries failing shards with unchanged configuration before comparing without the change, and warns that isolated-test retries can behave differently. Its flakiness section acknowledges the tradeoff that retrying can admit flaky changes while reducing unrelated disruption. That supports a bounded retry, not a proof of determinism. better-than-training tier, skills/check-issue/SKILL.md:61,63 currently allows specific-concern reruns but does not mandate this with-change attempt. Consumer package.json:162-166 shows why choosing an isolated failing case from a broad command can change scope. operator tier, INTAKE.md makes repeated broad-run cost material.
4. Pitfalls and what removes them: the retry budget is one per compared head/command/scope attempt, recorded in evidence so session replacement does not reset it. A repair or environment change starts a different comparison and cannot be called a same-conditions retry. Apply only to commands whose existing grants/fixture lifecycle allow another execution, and complete required cleanup between attempts without changing material conditions. A green retry is not evidence that base is red, nor permission to dismiss a independently reproduced review defect. Preserve both outcomes to expose newly introduced flakiness rather than erasing the first failure. No base-red record is created from inconsistent with-change results alone.
5. Extra question: may a green same-conditions retry satisfy the failed check while retaining the first failure as inconsistent evidence, or must that inconsistency itself block? Recommend that it may satisfy the check, as an explicit bounded flake policy, while concrete defects and outcome criteria remain independently binding. How are inconsistent results recorded and owned without declaring a base incident? Add that to red-record if it intends to own those cases, otherwise keep it as leaf verification evidence. Also ask whether the operator accepts the extra broad-run cost before adopting this rule.
