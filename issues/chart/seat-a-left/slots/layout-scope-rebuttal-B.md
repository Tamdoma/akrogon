# Layout scope rebuttal — Slot B

1. Failure cleanup needs its own failure outcome. The proposed sequence prevents duplicate replacements only if closing the new A succeeds. If swap/verification fails and pane close also fails, the new pane remains unrecorded, so the next allocation can split again (`src/next.ts:414-435`). Exact fix: require confirmed absence of the new pane before claiming recovery to “A absent.” If cleanup fails or absence cannot be verified, preserve the new pane ID and both errors in the reported blocker, and prevent another allocation until that retained pane is reconciled. State the mechanism in the leaf design. Do not claim unconditional no-orphan recovery from an attempted close.

2. Focus restoration is not yet a complete preservation guarantee. The probe proves tab/workspace restoration, but explicitly says restoration can undo an operator tab switch during the swap/restore window. It also does not establish focused-pane preservation when the operator was already in the affected leaf tab. Exact fix: present unconditional restoration's known focus-stealing window as an option cost before locking it, and define whether preservation covers tab/workspace only or the selected pane too. Record the focused pane in the disposable proof, including a same-tab case, before claiming full focus preservation. The existing allocation supplies --no-focus (`src/next.ts:402`), so replacement should not silently weaken that behavior. If the operator accepts unconditional tab restoration, carry that limitation into the leaf contract rather than treating it as a solved trap.
