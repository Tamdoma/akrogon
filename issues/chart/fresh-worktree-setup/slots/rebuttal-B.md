# Rebuttal B: fresh-worktree-setup

## 1. Misreads in the merged map

- **M7 (merged) is imprecise about `npm ci`, and the correction cuts in both directions.** It says pi-extensions' setup "deletes `node_modules` every run". Observation RB1 below (npm 11.20.0, 2026-11-25): `npm ci` deletes extraneous top-level entries (a stray `MARKER.txt` was removed) and *replaces* package directories (the `node_modules/d1` dir inode changed), but a nested untracked file inside a package (`d1/lib/extra.js`) survived and file contents are hardlink-reused from the cache. There is no wholesale missing-`node_modules` window; the concurrent-reader hazard is a shorter per-package replacement window (my probe with 2000 reads caught zero missing samples on a 1-package fixture, but multi-package reinstalls widen it). So the wipe hazard under a working sibling is real but narrower than every map, mine included, assumed — it is racy corruption of lazy module resolution, not guaranteed destruction. This weakens the wipe argument everywhere it appears and leaves the *cost* argument (below) as the decisive one.
- **M9 understates my F10**: not "queues behind a land hold (deadlock risk)" but a hard AB-BA deadlock — `land` holds the repo admission for the whole attempt while repeatedly taking the home `.lock` (`landClaim`/`landGates`/`landPush`/`repairExit` in src/land.ts, all `withLock(resolve(globalHome(), '.lock'))`), so a `next` pass holding `.lock` while blocked in `withAdmission` behind that land deadlocks both until `PASS_DEADLINE_MS` SIGKILLs the pass (src/listen.ts). Severity correction only; the conclusion (never `checkedRun` at dispatch) is unchanged.
- **Correction to my own map, prompted by C's pitfall 4** (verified in src/config.ts `setupCommand` and src/shell.ts `spawnFiles`): my recommendation to reuse `setupCommand(repo.config, 'true')` verbatim shells out to `akrogon guard own-modules`, which resolves whatever `akrogon` is on `PATH` — the installed release, not the running binary. During rollout that can be an older guard, and in the test fixture it resolves outside the dev tree entirely. The in-process `guard(worktree, ['own-modules'])` call after a plain install is the correct composition; the flock-plus-install part of `setupCommand` is the part worth reusing.

Under (a) B's delivery runs pi-extensions' setup — 4 sequential `npm ci` reinstalls, minutes of home-`.lock` time for zero changed input, each one replacing package dirs (RB1) under A's in-flight processes. Inputs: any pi-extensions leaf entering `check.review`; wrong state: A's lazy `require` hits a replaced or partial package tree mid-turn, and every other repo's phase moves stall behind the lock. The marker trigger's miss cases (a seat's own dependency edits mid-turn) are already covered by check-time wrapping and the implement-issue flock rule.

## 3. The must-weigh point: stale marker coinciding with a working sibling under Q1b

**Yes, but only through two of the four triggers — and the dangerous one is structurally incapable of it.**

Path where the coincidence exists: the config-change trigger (or the manual missing-`node_modules` trigger). Inputs: pi-extensions leaf in `check.review`, seat A mid-turn (reviews are long); the operator edits the `setup` string in `issues/config.yaml` (or `node_modules` is removed); seat B ends a turn silently or crashes and `dispatchSlot` takes its replacement branch (src/next.ts, the `silentEnd`/lost-seat paths around lines 717–757) → `startSeat`. Nothing anywhere in the delivery path checks the sibling's status, so B's stale-marker setup fires while A works: per-package `npm ci` replacement (RB1) lands under A's in-flight module resolution. Same shape for a re-prompt if the turn boundary lines up.

Path where it cannot exist: the `move` invalidation. `git reset --keep` runs only in the merge turn or restack, and entering `merge` at all requires every required slot recorded `done` before the move commits (src/phase.ts `transition`: `required.every((s) => recorded.done.includes(s))` — with a `fix` verdict the leaf goes to `check.repair` instead, and `merge` is entered by the later move, again seat-driven and done-gated). So when the marker is deleted no seat holds a live turn, and by the `check.repair` delivery the sibling is idle at worst. The one invalidation that carries real dependency changes can never meet a working sibling; the two that can meet one almost never carry real dependency changes (config-string drift, manual wipe). D's live-skip gate is still wrong in the other direction: seats are never ended at phase moves (`commitMove` clears `prompted` but keeps `seat`, src/phase.ts), so a persistent idle seat would suppress setup exactly at the restack-repair delivery and recreate the #158 hole. The correct shape is Q1b plus, at most, a *working*-sibling skip — never a live-sibling skip.

The systematic version of the same hazard is the decisive evidence against pure Q1a: there the coincidence needs no invalidation at all — every pi-extensions `check.review` starts B's install seconds after A's re-prompt, every time.
