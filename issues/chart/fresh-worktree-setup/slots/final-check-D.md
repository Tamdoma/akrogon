# Final-shape check, slot D: fresh-worktree-setup

Blockers only:

- B1 (item 2, busy test values): "live with status not `idle`/`done`" counts an `error` seat as busy. The codebase's own busy semantics differ: `src/next.ts` `observeBusy` treats only `working` and `blocked` as busy, and `src/seat.ts` `ended` treats `status.state === 'error'` as an ended seat. Inputs: a `check.review` leaf (`src/routing.ts` `requiredSlots` gives `['A','B']`) where B's terminal is live with status `error`, A has no seat, and the marker is missing or stale. Every pass then waits without an error and A never starts, where today `dispatchSlot` starts A independently. The test should name `working`/`blocked` (and null status, conservatively) as busy, not everything except `idle`/`done`.

- B2 (items 2 and 4, placement and ordering): as written, both the busy test and the setup step live in `ensureWorktree`, but `src/next.ts` `ensureWorktree(repo, leaf, live)` receives only the terminal-alive boolean; the seat `Seen` values with `status` exist only as `found` in `allocate` (from `leafSeats`). Implemented inside `ensureWorktree` alone, the gate can only use `live`, which F2 says reopens #158 after restack. The same ordering problem hits item 4: `allocate` calls `ensureWorktree` before `ensureLeafTemp`, so a `constructedEnv` scratch dir under the leaf temp does not exist yet on first allocation. The shape needs allocate to compute busy from `found` and pass it in, and the scratch dir (or leaf temp) created before the setup step.

- B3 (item 5, removal site): "extending the existing remove-on-failure in `createSparseWorktree`" cannot be where the setup failure removal goes. `createSparseWorktree` is shared with the excluded paths: `src/verify.ts` `runOnce` calls it and only then `emitEnvFile` plus its own `checkedRun` setup, and `src/batch.ts` `buildStack` calls it for a git-only scratch worktree. Any setup or setup-failure logic added there runs in verify (before `.env`, and twice) and in stack builds, breaking item 10. The removal must be new code around the setup step in `ensureWorktree`, reusing the catch's pattern (`withLock(worktreeLock(...))` plus `git worktree remove --force`) rather than living in `createSparseWorktree`, whose current catch covers only add, sparse-checkout and checkout failures and composes cleanly with `tests/first-allocation.test.ts` if left untouched.

Checked with no blocker: `src/batch.ts` `move` (`git reset --keep`) is the only akrogon code path that changes a leaf worktree's tracked files after creation; every other match for checkout, reset or rebase in `src/*.ts` targets the registered checkout or a scratch worktree, and recreation or replacement in `ensureWorktree` produces a fresh git dir with no marker.

Most important point: B1 and B2 both sit in the busy gate. The final shape should state the busy values (`working`, `blocked`, null) and that `allocate` computes the gate from the seats it already found.
