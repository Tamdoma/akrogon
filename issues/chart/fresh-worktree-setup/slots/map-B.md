## Findings

- F1. **The dispatch path, including worktree creation and every seat start, already runs inside the machine-wide home `.lock`.** `nextCommand` wraps `dispatchLeaf` in `withLock(resolve(globalHome(), '.lock'))` (src/next.ts `nextCommand`); `allocate` → `ensureWorktree` and `dispatchSlot` → `startSeat` all execute inside it. `seatCommand` takes the same lock. `akrogon phase` moves and land runs take it too. So a setup inserted anywhere in this path stalls every pass, every phase move and every land in every repo for its duration. But network operations already run inside this lock today: `checkBase`/`remoteBase` in `dispatchLeaf` and `git fetch` in `finishPush`/`mergeTurn`. The lock is not a clean fast section now.
- F2. **`ensureWorktree` is called on every dispatch pass for every leaf, not just at creation** — it is idempotent re-validation (path mismatch, branch state, `.env` rewrite). `state.worktree` stays set even when the worktree is deleted mid-leaf (reconcile.test.ts:373 recreates it sparse on the next dispatch). So neither `state.worktree === undefined` nor `existsSync(path)` distinguishes "setup never ran here".
- F3. **Every delivery to a seat funnels through exactly two shapes**: a fresh start (`startSeat`, called from `dispatchSlot` and `seatCommand`) and a re-prompt of a live idle seat (`dispatchSlot`'s `deliver`). Seats persist across phases, so a restack repair often reuses a live seat — a fix hooked only into `startSeat` misses it.
- F4. **The restack path mutates the leaf worktree's checkout under a live lifecycle.** `restack` (src/phase.ts) → `applyTop` → `move` (src/batch.ts) runs `git reset --keep <new top>` in the leaf worktree. `node_modules` is untracked, so it survives untouched while `package.json`/`bun.lock` may change underneath it (observed: `git reset --keep` never touches untracked files — standard git). If main bumped a hook dependency, the repaired seat meets the exact #158 failure class again: hook blocked by a missing package. Frequency is low but the class is identical.
- F5. **The direct route adopts.** `skills/chart-issues/assets/direct-route.md` step 27: a direct-attempt worktree is created by plain `git worktree add` and `ensureWorktree` *adopts* it at lifecycle handoff. A creation-only trigger keyed on akrogon-created worktrees never fires for adopted ones.
- F6. **`setupCommand` composes correctly for reuse**: `flock "$(git rev-parse --git-path akrogon-install.lock)" sh -c <setup> && akrogon guard own-modules && sh -c <cmd>`. Observed (free observation O-A below): `git rev-parse --git-path` in a worktree resolves inside `.git/worktrees/<name>/`, so the install lock is **per-worktree** — serializing concurrent installs in the same worktree, never across worktrees. With `'true'` as the command it is exactly "run setup and verify" with nothing after. The guard hard-fails a `package.json` checkout without `node_modules` even when no `setup` is configured — its own error text says setup is meant "in each fresh checkout" (src/guard.ts), so creation-time setup is the documented intent, currently unimplemented.
- F7. **Two registered repos have `package.json` and no `setup`** (mdcny-ghl-data-pulls, clinique-la-roya; observed in each repo's `issues/config.yaml`, 2026-11-25). For these, `setupCommand(config, 'true')` reduces to the bare guard: green whenever `node_modules` exists, red when it does not — correct behavior, not a false positive. pi-extensions' setup is a shell loop over nested lockfiles: it is not `bun install`, so no design may assume bun semantics or a root `node_modules` as proof of success.
- F8. **Cost measurements** (observation O-B): framework's real install (`bun install --frozen-lockfile`, 804 packages, bun 1.4.5): warm cache, no `node_modules`: **1.95 s**; repeat with `node_modules` present: **~10 ms**; fully cold cache: **33.5 s** — but the cache is machine-wide and shared with the operator's interactive use, so cold is effectively once per machine per dependency set, not once per leaf. akrogon's own: 64 ms cold-node_modules, 3 ms repeat. Verify worktrees already pay the 1.95 s on every verify pass today, so leaf worktrees paying it once per delivery-attempt is the same order of cost the system already accepts.
- F9. **bun auto-loads `.env` from cwd — including for `bun install` and its lifecycle scripts** (observation O-C). akrogon writes the leaf `.env` in `writeLeafEnv` during `allocate`, strictly before any seat delivery. So a setup run at delivery time with cwd = worktree sees the same registry/env values as the seat's own bun commands. Ordering constraint: setup must not run before `writeLeafEnv`.
- F10. **A run-check-scoped setup is the wrong tool for allocation.** `checkedRun` passes through `withAdmission`; a land run "holds its repo for the whole attempt" (src/admission.ts comment, #147), so a new leaf's setup launched as a checked run during a land would wait minutes — inside the global lock. It would also force the full capture/timing/systemd-scope machinery onto what is bookkeeping, and `runSlice` systemd units for a 2-second install. The existing `run-check` mechanism must stay the check-side wrapping; allocation setup should be a plain spawn.
- F11. **The listener bounds a hung pass crudely**: `PASS_DEADLINE_MS` 20 min SIGKILLs the whole pass process group (src/listen.ts). A hung install inside the locked dispatch section therefore risks killing mid-dispatch state writes of *other* leaves — but only after 20 minutes, and `bun install`/`npm ci` have their own network retries. Worth a named open question, not a design driver.
- F12. **Sparse checkout never excludes dependencies**: `/*` + `!/issues/` leaves `package.json` and the lockfile checked out and drops `issues/config.yaml` (observation O-D). Setup must therefore be read from `repo.config` (parsed at the registered root), never re-parsed inside the worktree — which is how all existing code already does it.
- F13. **Partial installs are real states**: a SIGKILLed install leaves a partial `node_modules` whose mere existence proves nothing. Any trigger shaped as "skip when `node_modules` exists" can permanently strand a broken tree. Correctness requires either unconditional reruns or content proof, and content proof (lockfile hashing) cannot express multi-lockfile setups like pi-extensions' loop.
- F14. **Disk cost is multiplied but pre-existing**: framework `node_modules` is ~1.4–1.6 GB with `--backend=copyfile` (observed); per-leaf copies already arise today from seats running wrapped checks. git itself is fine with it: `git worktree remove` succeeds on a worktree holding only ignored untracked files, no `--force` needed (observation O-E).
- F15. **The failure is hook-specific, not harness-specific**: framework blocks `Write`, `Edit`, `Skill` and chrome-mcp tools with `onFailure: block` (its `.claude/settings.json`); `Read`/`Grep`/`Bash` hooks also exist without block. Any claude-harness seat in framework is dead on arrival in a fresh worktree. Non-claude harnesses (pi, codex, agy) have no repo-hook channel but hit the same class the first time any repo command needs dependencies.

## Forks

### K1. When setup runs

- K1-O1. **At worktree creation only.** Breaks/invites: setup failure leaves a created worktree the trigger never refires on — either the worktree must be torn down on failure (new coupling) or the leaf is permanently skipped (silent stall). Adopted direct-route worktrees (F5) and mid-leaf recreations where `state.worktree` was already set (F2) are missed. Restack staleness (F4) unaddressed. Cheapest runtime, highest state complexity.
- K1-O2. **At every seat start.** Covers creation, adoption, recreation, restarts. Misses the restack gap whenever the repair prompt is re-delivered to a live idle seat (F3) — which is the common case. Misses nothing else that matters: a seat already working is covered by the implement-issue rule (flock + setup before dependency-using proofs).
- K1-O3. **Before every delivery — start or re-prompt — in the leaf worktree, unconditionally.** Covers every case K1-O2 does plus the re-prompted repair seat after a restack (F3+F4), upgrade-time in-flight leaves as soon as any new task reaches them, manual `node_modules` wipes, and partial installs (F13). Needs no state, no stamp, no migration — signpost 3a is satisfied by adding nothing. Cost: one idempotent no-op install (~3–15 ms warm) per delivery; deliveries are rare events (seat start, phase prompt). Invites: unconditional execution depends on setup idempotence — already the contract, since verify reruns it constantly; a non-frozen setup that mutates the lockfile (varhop's `bun install`) leaves the worktree dirty before the seat starts, surfacing a repo misconfiguration earlier and louder (arguably correct, but a behavior change to name).
- K1-O4. **On demand (today).** The reported bug. Rejected.
- K1-O5. **After every restack/rebase, hooked into `move`/`applyTop`.** Targets F4 precisely but covers nothing else; combined with K1-O1 it approximates K1-O3 with two hooks and detection state instead of one hook and none. Also runs in the land path where no seat is involved yet — earlier than needed, same cost.

### K2. Where it runs (lock, scope, env)

- K2-O1. **Inside the home `.lock`, plain spawn, scrubbed env.** Today's architecture: the whole dispatch section is lock-held (F1), and network fetches already stall it. Warm-cost serialization is milliseconds; the once-per-machine cold install (~33 s) is a bounded, visible pause. The refactor to escape the lock means splitting `dispatchLeaf`'s state reads, allocation and delivery across lock boundaries — the system's most delicate concurrency code — for a rare seconds-scale stall. Simplicity says stay inside; the lock already tolerates worse.
- K2-O2. **Outside the home `.lock`.** Removes the stall class but invites: lock-boundary restructuring of `dispatchLeaf`/`allocate`/`dispatchSlot`; interleavings between passes that today cannot exist. High risk, low measured benefit. Rejected unless the stall proves real in operation.
- K2-O3. **Inside a run-check scope.** Rejected by F10: admission coupling to land runs, systemd-scope machinery for bookkeeping, and `implementation` capture ownership semantics that do not exist at allocation time.
- K2-env. **Env: mirror `constructedEnv` (src/run-check.ts) minus run-unique keys** — copy `HOME`, `PATH`, `XDG_CACHE_HOME`, `AKROGON_HOME`, repo `env`/`pass_env` names, set `TMPDIR` to the leaf temp dir (created by `ensureLeafTemp` in `allocate` before any delivery), and *strip* the forbidden set (`NODE_PATH`, `BUN_OPTIONS`, `BUN_INSTALL_CACHE_DIR`, …) rather than refusing: the automatic passes inherit the systemd user manager's environment (observed: the listener's own env carries no BUN/NODE pollution), and a stray var must not block dispatch machine-wide. Reusing `constructedEnv`'s exact copy list keeps check-time and delivery-time installs byte-identical in behavior. Open detail: `DBUS_SESSION_BUS_ADDRESS`/`displayEnv` are irrelevant to installs; simplest is to reuse the helper as-is, harmless.
- K2-lock. The per-worktree `akrogon-install.lock` flock already inside `setupCommand` (F6) serializes the delivery-time install against any concurrent wrapped check install in the same worktree (a seat mid-check while its re-prompt is being prepared). Required, already exists, free.

### K3. What a failed or slow setup does to dispatch

- K3-O1. **Throw, report, skip, retry next pass.** The error propagates exactly like a `startSeat` failure today: `dispatchLeaf` catches, `report()` prints one JSON line, the leaf is skipped this pass, nothing is recorded, the next pass retries. With the K1-O3 trigger there is no poisoned state because the trigger refires unconditionally — this is what makes the simple failure semantics sound. A persistent failure (frozen-lockfile mismatch committed on the leaf branch; network outage) blocks only this leaf's delivery; other leaves in the same sweep continue (the throw is per-leaf inside `dispatchLeaf`'s try). Invites: a leaf with a permanently broken setup retries forever with journal noise only — same visibility as today's worktree-creation failures; acceptable because the cause is operator-actionable repo state, and `PASS_DEADLINE_MS` never engages for a failing-fast install.
- K3-O2. **Fail the leaf.** Wrong: transient network failure would kill healthy leaves; recovery needs operator action for a self-healing condition.
- K3-O3. **Detach (systemd service, dispatch waits on completion).** New record kinds, lifecycle, failure recovery — signpost 3a/1a violation for a 2-second job. Rejected.
- K3-slow. Slow is the cold-cache case: ~33 s worst measured, once per machine per dependency set, inside the lock. No timeout mechanism exists on installs in checks today either; adding one here but not there is inconsistent, and adding one at all is a guard rather than a fix. Named as an open question (Q4), not recommended.

### K4. Records and upgrade behavior

- K4-O1. **No new state.** Unconditional delivery-time setup needs no `setup_ran` stamp, no schema change, old records parse trivially (signposts 3a/6a satisfied by absence). The `setup` timing row idea (kind `check_start`-like) is optional observability; stderr evidence on failure rides the existing `report()` line.
- K4-O2. Stamp in `state.yaml` (lockfile hash). Saves ~10 ms per delivery, costs a schema field, multi-lockfile ambiguity (F7/F13), and reintroduces every skip-detection hazard. Rejected.
- Upgrade gap: leaves in flight when the fix ships have worktrees without setup. Under K1-O3 the next delivery to any seat repairs them automatically; seats mid-turn at upgrade time are the only residue and are already broken in the way the operator has been working around by hand. No migration needed (6a).

## Practitioner questions and pitfalls over the work's lifetime

- P1. **`setup` must stay idempotent and non-interactive under repetition** — now at every delivery, not just per check. `bun install --frozen-lockfile`/`npm ci` are; a repo config that is not (varhop's bare `bun install` can rewrite the lockfile, dirtying the worktree before the seat starts) misconfigures itself into `akrogon phase`'s dirty-worktree refusal. Pitfall for docs/reference/config.md, which today says only "runs before check commands".
- P2. **Delivery-time setup must run with cwd = the leaf worktree** (bunfig discovery, `.env` auto-load F9, `git rev-parse --git-path` resolving to the worktree's own lock F6) and after `writeLeafEnv`. Getting cwd wrong silently installs into the registered checkout.
- P3. **Never detect "already installed" by `node_modules` existence** (F13: partial installs; F7: pi-extensions has no root `node_modules` at all — its guard passes trivially and its correctness rests entirely on rerunning its loop).
- P4. **Retry poisoning is the design hazard, not install failure.** Any trigger narrower than every-delivery must answer "what refires after a failed first run"; every-delivery answers it structurally.
- P5. **Hook dependencies change over a leaf's life.** main advancing under a leaf can add or bump hook imports (framework's `frontmatter-utils.ts` importing `js-yaml` is the live example). The restack path (F4) is where this lands mid-leaf; the implement-phase rebase is covered only by the seat's own discipline. Nothing akrogon-side can cover a seat mid-turn; do not try.
- P6. **Docs contract changes**: `docs/reference/checks.md` ("`setup` runs first … before any check command") and `docs/reference/config.md` ("Akrogon runs it before check commands") become incomplete — setup gains a second, earlier duty. The init-akrogon skill's proposal rules need no change (the same commands fit).
- P7. **Verify/buildStack/worktree internals need nothing**: `buildStack` (src/batch.ts) is pure git; verify self-installs (F-introduction). Do not widen scope into them.
- P8. **Lesson retirement**: the lesson claims coverage for "its tests run outside `checks`, or its typecheck" — delivery-time setup covers these only insofar as the seat receives a task before running them, which is the lifecycle's shape (seats exist to receive tasks). The hand-authored worktree a human uses outside akrogon is out of scope and should stay out.
- P9. Model knowledge, no stronger source found: bun's exact cache-concurrency guarantees under parallel installs in distinct worktrees are undocumented in what I inspected; observed behavior (verify passes install concurrently in separate worktrees today without incident) is the operative evidence. Searched: bun docs lines I hold are release-note level; nothing stronger found in-repo.
- P10. Model knowledge: `npm ci` deletes `node_modules` wholesale before installing, so an interrupted `npm ci` leaves a strictly worse partial state than bun's — reinforcing P3/P4; not re-verified locally (pi-extensions is the only npm consumer and its loop is per-package).

## Recommended direction

**R: setup before every delivery to a leaf seat (start or re-prompt), unconditional, plain spawn inside the existing global-lock dispatch section, cwd = leaf worktree, env = `constructedEnv` minus run-unique keys with the forbidden set stripped, command = `setupCommand(repo.config, 'true')` — reusing the per-worktree flock and `akrogon guard own-modules` verbatim. Failure throws per-leaf: report, skip, retry next pass. No new records, no schema change, no timeout machinery. Docs contract updated; check-side wrapping in `withSetup`/`verify` untouched.**

Shape: one helper invoked at the head of `startSeat` (covers fresh starts and `akrogon seat`) and in `dispatchSlot`'s `deliver` path before the send (covers re-prompted live seats). Two call sites, one mechanism, both inside the lock the dispatch already holds. The `ensureLeafTemp` ordering in `allocate` already precedes both.

Cost: ~3–15 ms warm per delivery plus 1–2 s once per leaf creation (per-repo dependency size dependent); a once-per-machine cold-cache install (~33 s measured worst) serialized against all passes — accepted, bounded, visible, and cheaper than the lock-surgery alternative. Disk: no multiplier beyond what checks already create.

Why this removes the class (1a) rather than guarding it: the invariant becomes "no task reaches a seat before setup has run against the current checkout" — enforced at the single funnel all tasks pass through, not at creation time (which is only correlated with first use) and not by detection state (which partial installs corrupt). Every narrower trigger reintroduces a provable gap: adoption, recreation, restack, upgrade, wipe.

## Free test at the real boundary

The existing harness reaches everything: `tests/hc-fixture.ts` + temp git repos + the real CLI (`tests/first-allocation.test.ts` is the template). Concrete proofs, all free:

1. **First allocation**: fixture repo with `setup: <append one line to a proof file in the fixture home>`; `akrogon next build`; assert the proof line exists, `node_modules`-equivalent side effect present in the *worktree* (not the root), and the seat start was delivered. Ordering proof: make setup fail on first pass (proof-file gate), assert no seat start and exit non-zero; ungate, re-run, assert delivery — proves retry without poisoning.
2. **Re-prompt path**: complete a phase boundary in the fixture (or re-prompt the live idle seat as the existing hc-fixture phase tests already drive) and assert setup ran a second time before delivery — covers K1-O3's distinct claim.
3. **Adoption**: pre-create the worktree by hand with correct branch (direct-route shape), dispatch, assert setup ran.
4. **No-setup repo**: config without `setup` and no `package.json` — delivery proceeds, no setup side effect; with root `package.json` and no `setup` — delivery is refused by the guard until dependencies exist, proving F7 semantics rather than regressing them.
5. **Lock concurrency**: overlap a wrapped-check install with a delivery install in one worktree (the flock makes them serialize; assert no corruption — honestly this is the weakest proof and may be to observing serialized lock order).
6. Negative cost check: count setup invocations across a multi-pass fixture run to prove no per-pass repetition (only per-delivery).

Estimate: these are variations on existing fixture tests; no new harness machinery. Nothing here needs a paid model launch (2a holds).

## What I would ask that the intake does not settle

- Q1. Is the once-per-machine cold-cache stall (~33 s measured for framework-sized deps, inside the global lock) acceptable as-is, or must the design include a per-install timeout/ceiling? My recommendation: accept and revisit only if observed; the alternative lock surgery is disproportionate.
- Q2. Should a *persistent* setup failure surface beyond the per-pass `report()` JSON line — e.g., a notice or a wait reason — after N consecutive failures? Recommendation: no new record kind; the leaf visibly never progresses and the journal line names why. But the operator-visible surface is thin today.
- Q3. Non-frozen setups that mutate the lockfile (varhop's `bun install`) will now dirty worktrees eagerly, before any seat acts. Is that an acceptable early surfacing of a repo misconfiguration (my read: yes, it already happened inside the first check), or should dirty-after-setup be a distinct loud error? Leaning: distinct loud error is a guard; the existing dirty-worktree refusals already catch it.
- Q4. Does any consumer run `setup` commands requiring env names present only in the root `.env` but not declared in `env:`? Today check-time setup inherits process env, not `.env`; delivery-time setup in a bun context auto-loads `.env` (F9) — a small behavior difference favoring delivery-time. No consumer in the registered set depends on either, but the contract should state one.
- Q5. Worker worktrees of implement-issue (`-u<N>`): same fresh-worktree class, owned by the skill's sub-brief instructions, not by akrogon dispatch. In scope for this chart or a named exclusion? My read: exclusion — the seat instructs workers, and the implement-issue flock rule already exists; but the chart should say so explicitly.
