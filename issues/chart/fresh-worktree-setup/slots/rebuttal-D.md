An idle recipient seat is "live" too, so my gate would skip the post-`move` repair install that M4 needs. The gate must be no seat busy, not no seat live (see section 3).

## 3. Q1b and a working sibling seat: yes, the paths exist

A stale or missing marker can coincide with a sibling seat working in the same worktree, and under Q1b as forked (marker decides, no busy gate named) a wiping setup runs under it. Two concrete paths:

1. Per-delivery call site (Q2a): pi-extensions leaf in `check.review`, A mid-turn working, B's terminal finished. First pass after the fix ships (no marker exists yet in any in-flight worktree), or the `setup` string was edited. `akrogon next` takes `src/next.ts` `dispatchLeaf`, whose slot loop calls `dispatchSlot` for A (busy, returns with no delivery) then for B (finished seat, start path). Setup at the head of the start path fires on the missing or stale marker and runs the `npm ci` loop, deleting each package's `node_modules` while A's processes still import from them. A's next check or hook then fails on missing modules mid-turn.
2. `ensureWorktree` call site (Q2b) without a busy gate: same inputs, earlier point of failure. `allocate` calls `ensureWorktree` before either slot is examined, so the wipe runs under busy A even in a pass where B is never delivered at all.

The install flock inside `setupCommand` (`src/config.ts`) does not prevent this: `flock <lock> sh -c <setup> && guard && sh -c <cmd>` holds the lock only for the setup command itself, so it serializes other wrapped installs, not a working seat's own `bun`, `tsc`, or hook reads of `node_modules`.

The gate that closes both paths without reopening M4 is busy, not live: run setup at `ensureWorktree` only when every recorded seat is absent, finished, or idle (the `status` read `dispatchSlot` already uses, where a seat is promptable only at `idle` or `done`), never from the `live` flag `allocate` computes today. Under that gate the post-`move` repair case still works, because the recipient B seat sits idle while setup refreshes its tree, and the busy-A case defers setup and B's start to a later pass instead of wiping under A.

Most important point: Q1b is unsafe as forked unless the leaf contract names the busy gate explicitly, and my merged "skip while a seat is live" wording is the wrong version of that gate.
