# Blind fork notes: window-and-calls, slot C

## Q1 · Chart windows

1. **Pick, reason and cost.** Use door-recorded active spans, stored as half-open `[start, end)` windows and summed by the script. Open a span when work starts on a chart, close it before work moves to another chart, and append a span on re-entry. This covers A's long-lived session and disjoint chart work. Charge a shared opening map once to the chart that stores its map artifacts, here `fresh-consultants`, and label that span `shared opening map`; otherwise the fixed tables still overlap and cannot be added. Cost: every chart switch becomes a small durable record update.

2. **Rejected options.** One corrected open/close pair cannot represent a chart resumed after another chart used the seats, so it includes the intervening chart or drops later work. Consultant sessions alone cannot measure A, whose session spans every chart, and cannot separate the old base-red consultants because the same B/C sessions appear in all three old seat files.

3. **Evidence.** `operator` · `issues/chart/usage-windows/INTAKE.md`, read 2026-10-17 · the requested result is per-chart windows and an approximate old-versus-new comparison. `better-than-training` · `chart-usage.ts`, `shapes.md`, and `issues/chart/{base-red,loop-counts,failed-cause}/seats.yaml`, inspected 2026-10-17 · the script has one `opened` value and filters every recorded session from it through one `until`; all three old charts have the same opening time and sessions. `better-than-training` · `fresh-consultants/forks/restart-rule.md`, read 2026-10-17 · consultants restart on chart entry and re-entry, but A does not, so session identity is useful evidence but not the accounting boundary.

4. **Pitfalls and removals.** Half-open spans prevent a call on a switch timestamp from counting twice. The skill must close the current span before another chart or a consultant restart begins and permit only the current chart's last span to be open; a usage run caps that open span at its explicit `until`. Read legacy base-red as one span from `opened` to an explicitly supplied end, using the committed `USAGE.md` end `2026-10-17T09:04:40.067Z` for the savings check and labelling it a legacy pass-wide baseline. Never let a legacy comparison default to today's time or infer its end from the sessions, which contain other chart work.

5. **Question missing from the fork.** None after shared-map ownership and the legacy endpoint are made explicit.

## Q2 · Calls and context

1. **Pick, reason and cost.** Define a call as one completed model response, not one operator or peer turn. Claude: one unique assistant `message.id`, using the final usage counters and maximum streamed output for that id. Codex: one `event_msg` `token_count` record; derive its usage from `last_token_usage` when present or from the cumulative counter delta. Pi: one assistant message with `message.usage`, plus one compaction entry with `usage`. Context per call is Claude `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`, Codex `input_tokens` because its cached input is already a subset, and Pi `input + cacheRead + cacheWrite`. Average context is total context divided by calls, weighted across sessions. Cost: the reader needs one explicit parser per harness and schema drift makes that seat unmeasured.

2. **Rejected options.** Counting `task_started`, user messages, or peer exchanges calls a tool-heavy exchange one call even when it made dozens of model requests. Counting raw Claude assistant records double-counts streamed records sharing a message id. Excluding Pi compaction hides a real summarization request and biases the old long-session case in favor of the behavior being replaced. Pi `/clear` custom records and context-edit records have no model usage and are not calls.

3. **Evidence.** `better-than-training` · real Claude, Codex and Pi transcripts named by the five `seats.yaml` files, inspected 2026-10-17 · Claude repeats message ids while streaming; Codex emits one `token_count` per response with cumulative totals and, in the newer rollout, `last_token_usage`; Pi assistant messages carry `input`, `cacheRead`, `cacheWrite`, `output`, and `totalTokens`. The old Pi session's exact committed base-red window contains 59 assistant calls with about 80.7k prompt-context tokens per call, close to the operator's rough 63/~84k figure. Its compaction entry carries separate usage and completed at `08:17:02.991Z`, just before that window. `better-than-training` · `tests/fixtures/chart-usage/README.md` and `chart-usage.test.ts`, inspected 2026-10-17 · the fixtures preserve real usage fields and already require Claude message-id grouping and safe Codex cumulative-counter handling.

4. **Pitfalls and removals.** Never add Codex cached input to `input_tokens`; show it as the cached subset. Sum only calls whose completion record falls in a chart span. A cumulative decrease inside a Codex span, a missing usage field, or an ambiguous transcript keeps the existing `usage unmeasured` result rather than silently losing calls. Include compaction input and output in Pi totals and call count, but not `tokensBefore`, which describes the pre-compaction context rather than provider usage.

5. **Question missing from the fork.** Clarify in the contract that reasoning tokens remain a separate field and are not added to output or context; the observed Pi and Codex totals already treat reasoning as part of provider output accounting rather than extra prompt context.

## Q3 · Savings report

1. **Pick, reason and cost.** Add per-seat columns to every usage run: calls, average context per call, provider input, cache read, output, and working minutes. Keep comparison out of the script. The leaf's nonblocking done-criterion runs the fixed script on base-red with its explicit legacy end and on the final #99/#100 windows, then records those three rows side by side with the percentage change in B's and C's average context per call. This makes each normal chart report useful without adding a one-off command mode. Cost: `USAGE.md` becomes slightly wider.

2. **Rejected option.** A separate compare mode adds multi-chart argument parsing, output persistence rules, and alignment behavior for one requested observation. It also invites hard-coded baseline paths or stale comparisons after an individual chart is rerun.

3. **Evidence.** `operator` · verbatim savings-check text in `window-and-calls.md` and `INTAKE.md`, 2026-10-17 · the operator asked to run the fixed script on base-red and #99/#100, print those fields side by side, compare per call rather than totals, and keep the result nonblocking. `better-than-training` · current `chart-usage.ts` and `USAGE.md`, inspected 2026-10-17 · normal runs already write per-seat token and minute figures, so calls and average context belong in the same table; no compare interface exists.

4. **Pitfalls and removals.** Finalize or explicitly cap every compared window before reporting. Show `n/a` for a zero-call or unmeasured seat rather than manufacturing a percentage. Label the figures approximate and observational: different charts have different work, and the check does not prove that restarting caused the change or that quality held. The done-criterion reports numbers even when they show no saving and never gates merge.

5. **Question missing from the fork.** Does “average consultant context” mean separate B and C percentage changes, or one pooled B+C number? Prefer separate percentages because the harnesses encode input differently and pooling can hide one consultant's regression; add a pooled, call-weighted figure only if the operator explicitly wants one headline number.
