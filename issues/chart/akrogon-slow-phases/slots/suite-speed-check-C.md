# Suite speed shape check, slot C (disagreements only, nothing rerun by me)

- X1. The split shape does not deliver what 1a says. 1a: limit 8 "configured in `bunfig.toml` so every seat and worker gets it" (`forks/suite-speed.md:17`). In A's shape only `checks.test` gets 8. Workers and work-as-it-lands runs use the `test_changed` command, and ad hoc runs use plain `bun test`, so they run at 20. Those are the runs that overlap most (up to 3 workers per leaf, `max_active: 12`). If the limit stays, `test_changed` needs the same flag.
- X2. The load data does not show that 8 is safer than 20. 1 failure in 8 suites against 0 in 12 is too few runs to separate (Fisher exact p is about 0.4). Wall time under load was the same, 28-29 s (prompt line 12). The limit costs about 5 s per quiet run (15.0-15.8 s against 10.2-10.8 s) for an unproven gain.
- X3. The one failure was bun's 5000 ms per-test timeout on a 0.57 s test, not a wrong result. The limit does not remove that cause. Load was 4 suites, and real overlap can be higher, so the same timeout can hit at limit 8 too. The direct guard is a longer per-test timeout (`bun test --timeout <ms>`, or a bunfig `[test] timeout` key if the 1.4.2 parser takes it, which A's key list at prompt line 11 does not show and I did not verify).
- X4. Two places for one setting (bunfig for concurrency, `issues/config.yaml` for the limit) is one more thing to drift, and one of them is an operator-only edit.
- Recommendation: take the alternative at prompt line 18. `concurrentTestGlob` in `bunfig.toml`, the two `test.serial` edits, no limit anywhere. Add a longer per-test timeout only if a loaded run fails again. If the operator keeps limit 8, put the flag on both `checks.test` and `test_changed` and record that 1a's "in bunfig" wording could not be met because bunfig has no limit key.
