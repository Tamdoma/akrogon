# Slot C blind notes: state cutover gate

## Pick, with reason and cost

Replace `foreignProcess` (src/state-home.ts:85-110) with an akrogon-writer scan, keep everything else in `migrateStateHome` as is (tool-root global lock plus every existing slice lock, second `settled()` after the copy, src/state-home.ts:118-160). `settled()` becomes: no live tool-root run record (unchanged, :122) and no *old-code akrogon process*, where a process counts only if its cmdline invokes akrogon (argv contains the `~/.local/bin/akrogon` link path or any `*/src/akrogon.ts`), its environment does not set `AKROGON_HOME`, it is not this process, an ancestor or a descendant, and its code predates the state-home change: started before `src/state-home.ts`'s mtime in its own tree, or its tree has no `src/state-home.ts` at all. Cwd inside the tool root no longer counts for anything.

Reason: criterion 4 (state-home brief.md:13) only needs to prove no *command* can write tool-root state after cutover, and the writers are enumerable: state is written only through `globalHome()` paths by akrogon code (config, locks, pause/stop, admission records, reconcile reports), by processes that either hold the global `.lock` or a slice admission lock while writing, or hold a live admission record. The migrate already serializes the first two classes and rechecks live records after copying; the only unserialized writers are akrogon processes already loaded with pre-cutover code, whose `globalHome()` is frozen to the tool root. Shells, harness sessions and editors sitting in the root write none of those files, so the cwd test proves nothing and blocks everything. Cost: one `/proc` cmdline+environ scan replacing the current scan, same order of work, and the start-time/tree test must be read from `/proc/<pid>/stat` start time, which `liveRecords` already parses (src/state-home.ts:31-46).

## Rejected options

- Keep `foreignProcess` and wait for a quiet host: measured today, 31 processes have cwd inside the tool root (interactive shells, chart seat sessions, peer-wait, `herdr agent wait`), several of them permanent session processes, so the gate opens only when the operator closes the chart sessions that are the normal working state. It also misses the actual writers (next bullet).
- Drop `foreignProcess`, keep only locks plus live records: the locks split at cutover (old code flocking the tool-root `.lock`, new code the state-home `.lock` copy, a different inode), so an old-code process queued on the old lock or about to admit a run writes tool-root state after cutover with nothing detecting it. This is the one failure criterion 4 exists to forbid.
- Scan by open files under the tool root (fd targets) instead of cmdline: catches an editor holding `config.yaml` open, which the pick does not, but misses the common writer that opens, writes and closes per call, and still requires deciding which processes matter; strictly weaker for akrogon writers, and an editor save after cutover only edits the dead tracked copy, harming nothing that reads state.
- Gate on akrogon cmdline alone, any age: every routine `akrogon next` queued on the global lock is an akrogon process, and on an active host some invocation is almost always alive; without the code-age test the gate becomes a race to find an idle second instead of a proof.
- Operator-run manual cutover command (pause everything, move by hand): works tonight, but abandons criterion 3's automatic first-command move (state-home brief.md:12) and leaves every future host to rediscover the stuck gate.
- Make the tool-root paths symlinks into the new home at cutover so late old writers land in the right place: the tracked `config.yaml` cannot be replaced (criterion 4 protects tracked files), and the atomic-rename writers (kept reports, state saves) replace a symlink with a regular file on first write, silently un-forwarding themselves.

## Evidence (tier, source, date)

- Primary code, main after `git fetch`, 2026-10-16: gate composition `liveRecords(...) === 0 && !foreignProcess(toolRoot)` at src/state-home.ts:122, called before the copy and again after it (:125-141), all inside the tool-root `.lock` plus every existing `runs/locks/*` slice lock (:146-160); `migrateStateHome` runs at every CLI start (src/akrogon.ts:10); `globalHome()` falls back to the tool root only while the state home has no `config.yaml` (src/config.ts:197-202), which is why a pre-cutover invocation is safe to let finish writing the old home.
- Live measurement, this host, 2026-10-16: 31 processes with cwd inside the tool root, including chart seat claude/codex/pi processes, interactive bash, `peer-ask`/`peer-wait` bun processes and `herdr agent wait`, none of which writes state files; the actual akrogon invocations present were two `bun /home/ivan/.local/bin/akrogon next` processes blocked on the tool-root `flock`, i.e. writers-in-waiting are already serialized behind the lock the migrate takes, and an akrogon cmdline is visible verbatim as the symlink path, never the root path (intake F4, confirmed).
- Test surface: tests/state-home.test.ts:144-159 pins deferral by a `sleep` process with cwd in the tool root, which is the false-positive class itself; the same file's overlap case (:202-299) proves the lock and live-record parts against a real nested run-check, so only the foreign test needs a new fixture (an old-code-shaped akrogon process), not new machinery.
- Criterion text: state-home brief.md:13 requires that an already-running command, including one admitting another checked run, ends with its records visible after cutover and that no command writes the tool root after; it does not require the host to be free of shells or sessions.

## Pitfalls, and what removes each

- A new-code process that starts after the last `settled()` recheck but before the config write resolves `globalHome()` to the tool root (fallback, src/config.ts:197-202) and can write an admission record there in that window; the slice lock it needs may not exist yet to be held. What removes most of it: the recheck is already after the copy (src/state-home.ts:134), so the window is one `writeYaml`; what removes the rest is that any such record names a pid whose liveness the new home re-derives from `/proc`, so a stranded copy is stale-but-harmless, while a stranded *live* record is the only real loss and needs the scan to be the last thing before the write, not after the copy. Order inside `move` should be: copy, scan, write config, in that sequence with nothing between scan and write.
- Start-time comparison can be fooled by a checkout move refreshing `src/state-home.ts` mtime after an old process started (records move updates mtimes). What removes it: the tree test is primary (no `src/state-home.ts` in the process's own tree means old code at any start time); mtime only decides processes running this tree's code, where a refreshed mtime errs toward calling a new process old, which only defers.
- An old-code process in a leaf worktree (`bun <worktree>/src/akrogon.ts` from a branch predating state-home) has an akrogon cmdline and no state-home file, so it blocks the gate while it runs. That is correct while it can write, but its test invocations almost always set `AKROGON_HOME` (tests/helpers.ts), and the environ check is what keeps test suites from holding the host gate closed for hours.
- Reading `/proc/<pid>/environ` and cmdline of other users' processes fails; this host is single-user and unreadable entries must count as "not a writer" only when the process is another uid's, since a same-uid writer is always readable. What removes it: skip by uid first, as `procTargets` in src/reconcile.ts already does, never skip a same-uid process for an unreadable cmdline.
- The gate opens more often once narrowed, including mid-chart; the migration line prints to stderr (src/state-home.ts:143-144) and copies a few KB, but the same pass then reads config from the new home, so a config edited in the workspace minutes before (slots, harnesses) must be in the copied file, not an editor's unsaved buffer. Nothing removes that; it is the same exposure as any config read today.

## Question the fork does not ask

What proves a process that started as new code, resolved the tool root through the fallback, and is still running at the flip (a long `verify` whose admission record was copied mid-flight) finishes its writes in the new home rather than the record path it captured at admission; and if the answer is "its record update is lost in the old home", is that inside criterion 4's "every record it wrote visible to commands after cutover", or is the criterion silently only about commands that start after the flip?
