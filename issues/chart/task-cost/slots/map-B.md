## Material forks and practitioner pitfalls

- **Q1. Is this change limited to the chart door or allowed to change lifecycle defaults too?** Recommend chart-first, with separately approved lifecycle config changes. The request names charting, while F1/F2's main execution controls are lifecycle-wide. Pitfall: a global effort change affects every registered repository and still misses manually launched chart panes.
- **Q2. May a named B review only substantive decisions and the final contract, rather than every intermediate round?** Recommend retaining blind opening maps and final contract review, with intermediate peer exchange required when a decision changes behavior or leaves a real disagreement. Keep operator answers binding and unresolved questions visible. Pitfall: deferring a foundational disagreement creates downstream rework. Measure removed exchanges against later contract corrections, not output length alone. Evidence: F3 and the historical catches at `process-review-claude.md:59`.
- **Q3. Should medium effort and inline implementation become the defaults for this repository?** Recommend medium for supported models and inline as a bounded trial using existing controls, retaining both reviewers and all checks. Pitfall: changing `slots` affects new launches only (`src/next.ts:431`), while long-lived seats keep their current setup. Inline also grows B's context. Compare complete-task usage including repairs before broad rollout.
- **Q4. Who chooses the stronger model after the same reasoning failure repeats?** Recommend an explicit operator-selected model and a skill-level escalation rule after two evidenced attempts, before inventing automatic routing. Pitfall: the current two models are not an established cheap/strong ladder. Model changes can lose cache and changing config cannot retune an already-running seat. Distinguish repeated defects from new defects and transport errors.
- **Q5. Should compaction be scheduled by the workflow or remain a harness decision?** Recommend keeping harness defaults, with a natural-boundary compaction instruction only when substantial work remains. Preserve decisions, failing checks, paths and unresolved questions. Pitfall: forced phase-by-phase compaction adds summary cost, may lose evidence and rewrites context. No measured cache problem currently justifies a new compaction controller.

## Ranked concrete changes, simplest first

1. **A1. Shorten the chart question contract.** Change `skills/chart-issues/assets/questions.md:27` to require decision, evidence, recommendation and relevant risk by content rather than a fixed presentation. Removes repeated scaffolding while preserving the operator's decision. Expected effect: fewer output tokens per round, with no claimed reduction in substantive review.
2. **A2. Use the existing inline implementation setting for the approved trial.** Change `issues/config.yaml:6`, retaining `SKILL.md:39-47` checks and blind review. Removes worker launches, copied sub-briefs and report-return loops on scoped tasks. Expected effect: lower total task tokens if B can complete the work without additional repairs or excessive context growth.
3. **A3. Set supported medium effort at session start.** Use existing repo overrides (`src/config.ts:45,56-59`) for lifecycle seats and specify effort when launching chart seats. Removes blanket maximum reasoning. Expected effect: lower reasoning output cost on routine work, conditional on unchanged completion quality. Do not apply Claude-specific commands to Pi by assumption.
4. **A4. Remove redundant intermediate peer passes.** Narrow `skills/chart-issues/SKILL.md:47` using Q2, keeping `:35` blind mapping and `:57` implementer contract review. Expected effect: fewer peer turns on settled details. Retain early exchange for consequential forks because late corrections can erase the saving.
5. **A5. Replace repeated unchanged reasoning attempts with an explicit escalation instruction.** Add the agreed Q4 rule to `skills/implement-issue/worker-protocol.md:15-23` and relevant chart guidance, without changing delivery retry counters. Expected effect: avoid a third failed reasoning attempt. Validate with a small complete-task sample that includes chart, both seats and worker usage. Record it in existing reports rather than adding a dashboard or pricing service.

The strongest immediate simplification is removing unnecessary worker handoffs. Preserve early tests, independent initial code review and final contract review. No percentage or dollar saving is established by the available records.
