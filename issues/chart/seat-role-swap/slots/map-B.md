## Material operator forks, in decision order

1. **D1. What exactly is swapped: pane placement or lifecycle jobs? Recommended: put B in the initial left pane and A in the right pane, keeping B synthesis/implementation/repair and A recheck/merge.** This meets the stated B-worker intent and “everything else is the same” with the smallest change. Alternative: keep A on the left and move the worker jobs to A, which requires changing routing, skills, guide, watch and repair artifacts. These are different outcomes, so the phrase “swap roles” cannot settle the choice by itself. (intake.md:3; src/next.ts:324-342; src/routing.ts:29-33,43; F12-F19.)

2. **D2. Should harnesses follow slot letters or existing jobs? Recommended: preserve pi as implementer and Codex as independent reviewer/merger.** With recommended D1, leave `slots.a/b` alone. If jobs are instead swapped, preserving engines requires swapping the configured triples, including any repo overrides, as an explicit part of that outcome. Keeping config keys fixed during a job swap deliberately changes the worker to Codex. A config edit does not retune an already running pane because launch occurs only for `pane.agent === null`. (config.yaml:2-10; src/config.ts:57-67; src/next.ts:221-228,426-427; docs/guide/cheat.md:28.)

3. **D3. Is this for newly allocated tabs, or must already allocated panes move too? Recommended: use the new placement for fresh tabs, retain persisted seat/pane identities for existing tabs, and let the active leaf finish before any true job swap reaches the live command/skills.** This avoids migration code and does not redirect an agent's current task. Moving/relabeling active panes is a separate operational change requiring explicit handling of sessions, done/verdict records and artifacts. (src/next.ts:321-343; src/state.ts:45-57; docs/guide/state.md:64-66; framework record cited in R1.)

4. **D4. Does “everything” include chart-issues peers? Recommended: keep charting A/B/C unchanged.** The requested scope says lifecycle, and charting already starts with its host in the left pane. Renaming the host to B adds an independent protocol change with optional C and attribution consequences, without helping the execution worker's placement. (intake.md:3,16; docs/guide/chart.md:46,162-176; skills/chart-issues/SKILL.md:25,49,61.)

5. **D5. Must the worker remain physically left after a pane is deleted or a tab is rebuilt? Recommended: guarantee the intended placement on fresh/recreated tabs and preserve surviving recorded seat identity during repair.** Current recovery always splits right and treats recorded seats as authoritative. A permanent left-position guarantee after loss of the left pane would need explicit rearrangement behavior, beyond exchanging bootstrap placement. Have the operator choose that stronger promise only if it is intended. (src/next.ts:321-342; tests/next.test.ts:1744-1818.)

A job swap now can reject its old B completion or launch another worker for the same implementation. (src/phase.ts:197-201; src/next.ts:406-417,542-543.)
- **R2. Open does not mean unfinished.** The same issue retains `cadence-apply` and `update-discard` under open, but both are merged. They are update-replay's named prerequisites, not additional implementations to restart. Completion moves the owner only when all its leaves are merged. (`/home/ivan/Work/infra/tamdoma/framework/issues/open/satellite-update-loop/cadence-apply/state.yaml:1-2`; `/home/ivan/Work/infra/tamdoma/framework/issues/open/satellite-update-loop/update-discard/state.yaml:1-2`; update-replay state:6-8; src/phase.ts:140-172.)
- **R3. Config keys select a role's engine, not physical coordinates.** Do not exchange model triples merely to move B left. Conversely, swapping jobs while preserving triples intentionally swaps engine responsibility. Repo overrides resolve per key, not per job, and current agents retain their already started harness. The intake's `~/.config/akrogon config` description is imprecise: the source resolves tool-root config while the broadcast sender separately reads the home env store. (src/config.ts:57-81; src/next.ts:221-228,426-427; config.yaml:2-10; skills/broadcast-issue/SKILL.md:39.)
- **R4. Never relabel only the pane mapping.** Slot identities also attach to reviews, prompt delivery, attempts, busy notices, verdicts and failure records. A true role migration must account for every one and for `review-A.md` merge/repair evidence. Keeping existing mappings is the smaller option. (src/state.ts:45-57; src/log.ts:24-30; skills/merge-issue/SKILL.md:33-39; origin/main:skills/implement-issue/SKILL.md:58.)
- **R5. Completion must follow the merger, not “the first pane.”** If B moves left while A remains merger, the `pane.A` close gate remains correct. If merge moves to B, the gate must follow B. Otherwise an idle worker can close the tab while the merger still owes its broadcast, or the merger's idle hook can fail to close it. (src/next.ts:745-753; skills/merge-issue/SKILL.md:47-51; tests/next.test.ts:1911-1938,2006-2081.)
- **R6. The route table is not the entire contract.** A true job swap also changes A-only repair review, the merge-to-repair `review-A.md` handoff and watch recovery. Keep the first review paired and blind, and retain the configured repair cap. (src/routing.ts:31-43; src/phase.ts:227-244; origin/main:skills/check-issue/SKILL.md:31,53; skills/merge-issue/SKILL.md:39; skills/watch-issues/SKILL.md:34,39.)
- **R7. Installed source and in-memory instructions can disagree during rollout.** The installer links the command and harness skill directories to tool source. The skills explicitly avoid rereading on every later phase prompt. A role swap can therefore update disk contracts while a live agent remembers the previous one. Read new contracts from origin/main for design, but do not assume that reading origin/main updated the installed checkout. (src/install.ts:11-21; origin/main:skills/plan-issue/SKILL.md:6; origin/main:skills/implement-issue/SKILL.md:6; intake.md:5; learnings/LESSONS.md:18.)

(tests/next.test.ts:1744-1818; tests/fake-herdr.ts:105-130; src/next.ts:324-342.)
- **R9. Avoid rewriting history or manufacturing broader work.** Historical review lessons retain the identities that performed them. Chart host A/B/C are a separate exchange. A layout-only decision leaves role tables and phase command examples correct. Do not turn this into global renaming or delayed pane creation by assumption. (learnings/LESSONS.md:3,7; docs/guide/chart.md:46,162-176; docs/guide/phases.md:7-13; src/next.ts:334-343.)
