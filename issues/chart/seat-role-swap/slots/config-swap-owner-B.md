### 1 · Should the leaf deliver the tracked config change with the role change, or should the door edit the live config separately?

Root `config.yaml` is both tracked source and the live config. Its uncommitted operator edit gives A the Codex triple, while the committed file still gives A pi/devin. A fresh leaf branches from origin/main, so exchanging its existing triples without first incorporating that edit would put pi/devin in B instead of the locked Codex values. (`config.yaml:3-10`; `origin/main:config.yaml:3-10` at c39309c; `src/config.ts:70-81`; `src/next.ts:253-256`; `src/preflight.ts:4-5`.)

Research: operator tier, locked answers and correction read 2026-09-29 at `forks/what-moves.md:23-29` and `forks/cutover.md:21-24`. Better-than-training tier, code and Git state inspected 2026-09-29: `git diff -- config.yaml` shows only the operator's A triple changed from pi/devin/max to Codex/gpt-6.1-sol/high, and `git ls-files --error-unmatch config.yaml` confirms tracking. `src/sync.ts:18-33,109-136` commits eligible issue records, rejects a staged root config and rebases with autostash, so a working-copy config edit is preserved but not delivered by sync. This makes a leaf-owned tracked change with a published baseline preferable to an early live-only swap.

- **1a (recommended) The door first commits and publishes the existing operator config edit unchanged, then the swap leaf exchanges the triples alongside its code changes.** Publish only the current config diff as a small prerequisite commit, preserving its contents and all unrelated edits. Make it available on origin/main before allocating the swap leaf. The leaf then receives the real Codex/pi baseline and can deliver the code and final config in the same reviewed branch. Keep the installed checkout on its old roles and unchanged live values while that leaf runs. Activate the delivered checkout only after the leaf's old-role merger has finished its completion call and broadcast. This records the operator's choice, removes the known dirty-config collision, and avoids a separate live config swap at activation. (`config.yaml:3-10`; `src/next.ts:253-256`; `src/install.ts:15-21`; `skills/merge-issue/SKILL.md:43-51`; `src/sync.ts:122-136`.)

- **1b The door swaps the working-copy triples now, and the leaf changes only code.** This needs no baseline commit and leaves origin/main's config unchanged. However, until the new routing reaches the installed checkout, old B still owns implementation and now launches Codex, while old A merges and now launches pi. That changes the models' jobs for the swap leaf, contrary to the locked preservation choice. Existing agents are not retuned by editing config, so whether they have already started also affects the result. The change remains an uncommitted machine edit unless separately recorded. (`src/routing.ts:29-33`; `src/next.ts:221-228,426-427`; `src/sync.ts:109-123`; `forks/what-moves.md:26`.)

- **1c The leaf changes only code, then the door swaps and records the config at local activation.** Keep the current live values until the swap leaf has finished. During the existing quiet window, bring the delivered code into the live checkout, exchange the current model triples, verify the effective config, and commit/publish only the resulting config change separately before releasing other work. This avoids a prerequisite commit and keeps the swap leaf on its existing models, but divides delivery between a leaf commit and an attended door change. Code and values temporarily disagree during activation, so no lifecycle dispatch may occur between them. (`src/install.ts:15-21`; `src/config.ts:70-81`; `src/next.ts:221-228,671`; `src/sync.ts:109-123`; `forks/cutover.md:22-24`.)

Pitfalls: A local baseline commit alone is insufficient for 1a because new leaves branch from the remote tracking ref, not local main. Staging config and running `akrogon sync` is also insufficient: sync rejects a root config in the staged index. Publish the prerequisite separately and verify the branch point includes it before leaf allocation. (`src/next.ts:253-256`; `src/preflight.ts:4-5`; `src/sync.ts:18-33`.)

For 1a, the door owns the unchanged-baseline preparation and the leaf owns the actual swap. The brief should name the exact final triples, limit config edits to those two seat entries, and keep the existing capacity, harness commands and repo registrations intact. Do not merely say “swap origin's values” without the prerequisite. The currently intended change is entirely within `config.yaml:3-10`, while the other configuration is at `config.yaml:1,11-26`.

During the swap leaf's execution, avoid integrating its delivered commit into the installed root until its old A merger has finished. `akrogon sync` fetches and rebases incoming source changes even when its own commit selection is limited to issue records. Updating the linked checkout too soon would make the old merger's `--slot A` completion invalid after merge ownership becomes B. This applies to both a sync-based update and a Git pull into that checkout. (`src/sync.ts:46-47,118-124`; `src/install.ts:15-21`; `src/phase.ts:197-201`; `skills/merge-issue/SKILL.md:47-51`; `forks/what-moves.md:25`.)

Challenge check

The strongest argument against 1a is its extra baseline commit. If keeping the config swap inside lifecycle review is not important, 1c is smaller operationally and also preserves the models' jobs. I recommend 1a because this configuration is tracked and the operator's existing choice would otherwise remain absent from the leaf's base. That preference is a recommendation, not a new lock. (`origin/main:config.yaml:3-10`; `config.yaml:3-10`; `src/next.ts:253-256`.)

Do not claim that every dirty config edit makes an ff-only update fail. A code-only delivery need not overlap the config edit, and sync intentionally preserves unrelated tracked changes. Conversely, if an incoming config change overlaps the uncommitted edit, autostash can leave a restoration conflict after integration. The existing test covers preservation and refusal to push after restoration conflicts, so neither outcome should be guessed from “dirty” alone. (`src/sync.ts:122-135`; `tests/sync.test.ts:80-116`.)

Committing/publishing a baseline or final config must be scoped to this path. The documented gacp function stages the current directory and commits the whole staged index, so invoking it at repo root risks including the unrelated issue/log changes visible in this session. A config-only commit is the appropriate preparation if 1a is chosen. (`docs/guide/gacp.md:30-31`; `src/sync.ts:109-121`.)
