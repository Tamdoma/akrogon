# Blind notes, slot C: permit-release

Question: release at run process exit, or when the run's workload is empty. Read 2026-10-13.

## 1. Pick: release at command exit, held as an in-process flock

The permit is released when the held command's direct child exits, which for a killed holder is simply process death. This is the only release rule compatible with the taken lock as written ("held by the run-check/base-run process, never by generated shell text or a descendant") and with the taken seat layout (per-pane scopes, no per-run units). Cost, accepted and named: a holder killed on its own frees the permit while processes it spawned may still live. That residue is smaller than it reads, below.

### Implementation

- Lock kind: one exclusive `flock(2)` per permit slot, on a file descriptor opened by the run-check or base-run process itself. Bun's fs API has no flock, so call libc `flock` through `bun:ffi` (model knowledge; no flock in the installed Bun types, searched 2026-10-13). Blocking `LOCK_EX` while queued; the waiting process has nothing else to do. Starts at 1 slot per the taken lock; the slot loop (try each slot file non-blocking, otherwise wait and rescan) is the only concession to a future count above 1. A new count key sits in global config beside `max_active` (`src/config.ts:24-30`).
- Location: slot files under `globalHome()` (`src/config.ts:195-198`), next to the existing `.lock` and `paused.yaml`, gitignored the same way. Host-wide falls out of the location: every repo's runs resolve the same akrogon home. Two akrogon installs with different `AKROGON_HOME` would each hold a permit; that is the same boundary every other akrogon state file already has.
- One helper, two one-line call sites. `spawnLogged` has exactly the two permit-bearing callers (`src/run-check.ts:173`, `src/base-run.ts:164`), and in both it is the whole heavy command: setup runs inside the spawned text, not before it (`src/config.ts:312-315`). A `withPermit` helper in `src/run-check.ts` wraps the `spawnLogged` call in each caller. In `runCheck` the `check_start` timing append (`src/run-check.ts:171`) moves inside the permit, so measured run duration never includes queue time; whatever reports queue time belongs to the queue fork. In `baseRun`, worktree creation and removal (`src/base-run.ts:149-155,166-190`) stay outside the permit: git plumbing is not the load being limited, and base copies can prepare while another run executes.
- Nested runs take none, mechanically: after acquiring, the holder writes a sidecar record (pid, process start time, boot id, the pattern `.owner` already uses at `src/run-check.ts:150-161`). Before blocking, an acquirer reads the sidecars and walks its own `/proc` ancestry; if a live holder is an ancestor, it proceeds without acquiring. This covers the real nesting, base-run execing printed command text that itself begins with `akrogon run-check` (`src/config.ts:316-317`, `src/base-run.ts:157-164`). An env marker was rejected for this in earlier forks and stays rejected: any script can set an env var, no script can fake its ancestry.
- SIGKILL of the holder: the kernel closes the descriptor and the flock is gone. No stale lock, no cleanup path, no lease expiry logic. This is the single largest simplicity win in the design and it is only available with a kernel-held lock in the dying process itself.
- The descriptor must never reach the command. `spawnFiles` passes children only their stdio (`src/shell.ts:38-45`), and fs descriptors are close-on-exec, so the test tree and its detached browsers never see the lock fd. A leaf done-criterion should prove it: a run that leaves a `setsid` sleeper behind, then a second run that still acquires immediately.

### Leftovers after a run

Under this pick they are released over, deliberately. A process the command spawned that outlives the direct child's exit stays where seat-scope put it: inside the pane scope, under the leaf slice, measurable and reachable by leaf stop until the pane or tab dies. Nothing in the permit path scans for, waits for, or kills it.

That is acceptable for three reasons. First, the normal case has no leftovers: measurement 2's full suite exited with every browser gone and the scope inactive. Second, the incident's leftovers came from kills, not normal exits, and in every realistic kill path the workload dies with the holder anyway: scope stop kills the whole cgroup, and a seat abort kills the command's process group. The divergence needs someone to kill only the run-check PID, which is no supported stop path; what the supported stop is belongs to the stop fork. Third, the alternative failure is worse: an idle leaked Chrome holding the host's only permit indefinitely, with every later leaf queued behind a process nothing will ever reap on its own. A bounded retry of that argument belongs in evidence, not hope: if timing or scope population later shows runs routinely leaving processes behind, leftover handling earns its own leaf then.

## 2. Rejected options

- Workload-empty, by any mechanism available today: rejected because with per-pane scopes there is nothing to read emptiness from. The pane scope never empties while the seat lives, the run's processes are an unlabelled subset of it, and `runCheck` today does not even retain the spawned child's PID (`spawnLogged` returns only a `Result`, `src/run-check.ts:58-66`; `finishCaptured` awaits the direct child only, `src/shell.ts:57-66`). Defining the set requires per-run systemd scopes and making the permit a count of live scopes, which is a new unit layer, an admission race to solve on top of unit counting, and a reopening of the seat-scope layout the operator just took for low complexity. Defining it by process-tree scans is worse: orphaned descendants reparent away from the dead child, so the set is unobservable exactly when it matters, unless run-check also becomes a subreaper and then must decide wait-versus-kill on a timer, which is a kill policy disguised as a release rule.
- Workload-empty via an inherited descriptor or a watcher descendant: rejected by the taken lock's own words, and it is the original fd-inheritance trap: a detached browser that inherits or outlives the watcher holds the only permit forever.
- `withLock`'s external flock child (`src/state.ts:205-209`): rejected for the permit although it is the codebase's existing pattern. The lock would be held by a spawned `flock` descendant, foreclosed by the taken lock, and its lifetime then depends on pipe behavior when the parent dies instead of one kernel rule.
- PID-file or `O_EXCL` lock files: rejected. SIGKILL leaves a stale file, and safe reuse needs boot id, start-time, and dead-holder arbitration between two waiters racing to steal it. All of that machinery exists only to imitate what flock does for free.
- Self re-exec under `flock -F` (no-fork, lock survives exec, local flock man page): viable fallback if FFI is refused, but it costs re-exec plumbing for two verbs, a marker env, and exit and signal proxying in `src/akrogon.ts`. More parts than one FFI call held for one function.

## 4. Pitfalls, and what removes each

- Surgically killing just run-check frees the permit over a live test tree, because akrogon forwards no signal to the child. Not removed by this fork. The stop fork must define scope stop as the supported kill; if it instead blesses killing run-check processes, this fork reopens.
- Blocking `LOCK_EX` through FFI blocks the process while queued, so the waiter cannot print progress or heartbeat. Removed only if the queue fork needs visibility, by switching to non-blocking tries with a sleep loop; until then blocking is the simpler correct thing and queue behavior is that fork's question. Flock wake order is not a fairness guarantee either; same owner.
- Sidecar holder record goes stale or its PID is reused, making a nested check misfire in either direction (deadlock at one permit, or a free pass). Removed by verifying start time and boot id with the PID, the exact triple `.owner` already records (`src/run-check.ts:150-161`), and by writing the sidecar only after the lock is granted and before the command spawns, so a nested run can never read it early.
- A future change to `spawnFiles` passes extra descriptors to children and a detached browser inherits the lock fd, wedging the permit after a clean exit. Removed by the setsid-sleeper done-criterion above, which fails the day inheritance appears.
- Leftover accumulation inside a long-lived seat: each run leaks a little, nothing reaps it, and the pane scope slowly fills with browsers the permit no longer counts. Not removed here; bounded only by pane and tab lifetime and whatever ceiling-values decides. Removed later only on evidence (scope population before and after runs), per the pick.
- Two akrogon homes on one host double the permits. Accepted, same boundary as pause state; a check at leaf level is not worth a host-global path decision in this fork.

## 5. Missing questions

- Does any current suite deliberately leave a process running after the command exits (a dev server a later stage reuses across separate run-check calls)? Inside one command it is held correctly; across calls this pick would release over it and the next run could collide with it. Framework-fanout may already know.
- When the queue fork sets a wait bound, what wakes or abandons a process blocked in `LOCK_EX`, and is a timed-out acquire a red run, a skipped run, or a failed leaf? The release rule must not silently acquire for a holder that has already been given up on.
- Should a run whose holder was SIGKILLed leave any trace (the `check_end` timing event never fires today), and is that absence enough signal for `akrogon status`, or does the permit helper owe a holder record that outlives it?
