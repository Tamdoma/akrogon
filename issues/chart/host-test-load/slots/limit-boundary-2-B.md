## 1. Pick, reason and cost

**Keep a revised 1a: one shared verification permit, ownership of every seat and run, and prevention of Chrome's automatic migration in both seat and run environments.** The measurement disproves containment as previously assumed, not the value of admission and ownership. Containing only admitted runs still misses the direct worker scripts named in the intake.

**Bus boundary: both environments, using an explicit unreachable session-bus address.** Start contained pane workloads with the door-proven `DBUS_SESSION_BUS_ADDRESS=unix:path=/nonexistent`, and construct every run-check/base-run workload environment with the same value as a reserved invariant. A seat-only setting is dropped by `constructedEnv`; a run-only setting leaves ad-hoc seat/worker launches exposed. Unsetting the variable is not the operation the door proved. Preserve the runtime/display variables needed by the workload, and keep user-manager control on its explicit private connection rather than restoring the ordinary session bus to children.

This is an operational boundary for the supported launch paths, not a security sandbox against scripts deliberately restoring the bus or moving themselves. Before taking the final contract, prove every actual browser family stays owned and that the chosen harnesses, workers and checks still work. If a required workflow needs the session bus, that is a real conflict to resolve before handoff. Do not silently re-enable it for all contained work.

**Resource policy: distinguish throttling from killing.** Prefer an aggregate CPUQuota when the promise is a fixed CPU budget. CPUWeight alone is relative scheduling priority, not an upper limit. Use MemoryHigh as normal memory pressure control and MemoryMax only as an explicit emergency boundary. Neither a memory-pressure setting nor one permit is a browser-count limit. Their values remain a resource-budget decision, not numbers proven by this aborted run. [Systemd 262 resource controls](https://raw.githubusercontent.com/systemd/systemd/v262/man/systemd.resource-control.xml).

**I withdraw my previous requirement to install a hard task ceiling before a successful capacity measurement.** TasksMax=3000 is demonstrably below what this suite tries to create. Do not replace it with an invented “safe” number. Reduce simultaneous browser-heavy branches and browser launches at their consumer boundary, then measure a healthy complete run. A final emergency task cap needs a measured successful footprint plus declared headroom and a clearly recorded resource-termination outcome. Until that decision and proof exist, do not claim a complete guarantee on task count.

This adds necessary framework work: one admitted command already has excessive internal fan-out. Retain the existing selector leaf as the breadth owner. Browser-launch limits supplement the shared permit rather than replacing it.

Cost: medium/high across akrogon containment/admission/environment construction and framework internal concurrency. Blocking the session bus needs harness and browser compatibility proofs. CPU throttling, memory pressure and fewer browser launches can lengthen checks, so current timeouts must be verified against successful bounded runs. There is **no defensible slowdown estimate**: the door stopped the only full-suite attempt after about 2.5 minutes, and no complete duration was measured (`issues/chart/host-test-load/forks/limit-boundary.md:25-29`). ## 2. Rejected options and reasons

- **Unmodified 1a:** Chrome demonstrably migrated outside caller ownership, and the chosen task ceiling generated crashes. Neither behavior can remain hidden behind a containment claim.
- **1b, including run-only bus restriction:** Protects admitted commands but still leaves ad-hoc worker launches outside the bus restriction and run counter. This is the bypass the intake names.
- **1c alone:** A resource ceiling does not queue suites or prevent Chrome migration. Once the migration is prevented, the ceiling is useful protection inside revised 1a, but tight process/task or memory caps can terminate work instead of scheduling it.
- **1d:** Still counts leaves/workers rather than actual browser-heavy operations. It cannot make one already excessive suite safe.
- **CPUWeight/MemoryHigh only:** Useful for responsiveness, but weaker than a fixed resource ceiling. Do not describe that choice as an absolute host CPU/memory/task bound. It wins only if the operator changes the guarantee to giving desktop work priority rather than a fixed upper budget.
- **No resource controls:** One permit removes concurrent participating suites but leaves a single suite's fan-out and bypassed scripts unrestricted. The new measurement supplies direct evidence against treating serialization alone as sufficient.
- **Browser-level limit as the sole boundary:** It addresses fan-out but cannot count all expensive builds/tests or give akrogon ownership of direct scripts, servers and other descendants. A global browser lease spanning Playwright, direct Chrome and every custom caller would need consumer adoption everywhere. Start with inspected framework pools/branches as the necessary complement, not a second universal scheduler.
- **Fake SNAP/FLATPAK_SANDBOX_DIR:** Source explains why those packaging environments skip self-scoping. Pretending a normal process is packaged changes an unrelated environment contract and is not the operation the door proved. Prefer the explicit bus restriction.

## 4. Pitfalls and what removes each

1. **R1 — Seat restriction vanishes at a check boundary.** Set the explicit restriction at pane/seat startup and again in constructedEnv, after caller values are handled. Make it reserved so repo env/pass_env cannot restore the session bus. Verify base-run re-entry and direct worker commands, not just one configured check.
2. **R2 — The controller loses access to systemd.** Prove the selected private-manager connection under the exact restricted environment. Keep XDG_RUNTIME_DIR available to that control path. Separate manager control from child environment construction; do not remove the whole runtime directory or reopen the session bus to make startup work.
3. **R3 — Disabling the session bus breaks a needed harness/test feature.** Prove the actual A/B harness startup, managed readiness, worker launch, check, nested base-run and stop with the restriction. Include desktop/default-handler or portal-dependent flows if they are required by the seat/criteria. If a required bus consumer is found, settle a narrow compatible launch boundary before handoff. No automatic global bus exemption.
4. **R4 — One Chrome probe is promoted to all-browser proof.** Probe the actual installed Google Chrome, Chromium and Playwright headless-shell paths used by the suite, including descendants and normal shutdown/owner death. Read actual cgroup membership during startup and after settling. The door's probe limits are explicit in E2.
5. **R5 — A task ceiling becomes a normal test failure generator.** Do not use TasksMax=3000 again as a successful-run budget. Control launch concurrency before creating expensive children. Choose any emergency task cap only after a healthy bounded footprint is known, and record exhaustion as resource termination rather than a product defect requiring retry/base comparison.
6. **R6 — Soft pressure is sold as an absolute fence.** State the exact guarantee of the chosen setting. MemoryHigh can be exceeded and CPUWeight can use idle capacity. An emergency boundary can kill work and must preserve that cause. Keep quota/pressure choices explicit rather than hiding them in “containment.”
7. **R7 — A full-suite repeat happens before containment compatibility is established.** The next operation proof should be the smallest actual-browser and manager/harness compatibility case. Only then run a bounded suite with an agreed resource policy and consumer concurrency. The operator's “ok, let's continue” is authorization to continue the chart, not evidence that another crashing configuration is acceptable.
8. **R8 — The boundary fixes stop but not fan-out.** Keep one shared admitted run plus independently bounded framework browser-heavy branches/pools. This is new consumer work exposed by the measurement, not a competing implementation of test-changed-shared-files.
