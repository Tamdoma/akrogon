# Blind notes, slot C: framework-fanout
## Pick: later, on named evidence. No framework chart now.
The taken mechanisms already bound what one run can do to the host: one run at a time (permit), 16 of 32 threads in aggregate (CPUQuota=1600%), CPUWeight=20 under contention, memory brake behind that. What fan-out inside the run can still do is hurt the run itself (oversubscription timeouts), and the only full-run sample at current fan-out passed clean: measurement 2, 239 s, 409 Chrome processes, load 40, 0 throttled, 0 dumps, and the ceiling fork's pending proof reruns exactly that shape under the quota before any of this ships. Cost of deferring: if in-run oversubscription does cause flakes, they keep costing comparison and check.fix rounds until the trigger below fires.
Revisit triggers, any one reopens this as a framework chart: (1) the ceiling pending proof fails with browser timeouts under the quota and the quota comes out; (2) two or more known-red comparison records attribute a single admitted run's red to browser or probe timeouts under its own load; (3) slice `cpu.stat` throttling or `memory.events` show the ceiling engaging on ordinary runs. Until then, fan-out is a framework suite-health question (their leaf-speed territory), not this chart's host-safety one.
## Rejected
- Cap now: the work is real and cross-cutting (verify-core branch shape, the site-nav pool, every other pool a grep finds), lands in another repo, and its costs are immediate and certain. Branch parallelism is what makes verify-core a max-of-branches wall time instead of a sum (`framework/package.json:167`: 8 parallel branches, two of them long sequential lists); capping branches lengthens every merge. The site-nav Promise.all is structural, not decorative: the code states sequential capture of the ten fixture sites runs an order of magnitude past the harness timeout (`framework/.claude/skills/dev-render-satellite/test/site-nav-e2e-run.ts:552-563`), so a pool cap there first requires raising that timeout or splitting the stage.
- Never: too strong. One run still peaks at load 40 on 32 threads and 6138 tasks; only the fixture site list is fixed (10 hardcoded sites, `:42-44`), branch and suite counts grow with the repo, and the quota halves the cores that fan-out was tuned against. Today's pass is one sample, not a law.
- Cap browsers only, branches untouched: split answer. Playwright suites already run `workers: 1` (motion-probe and mpa-navigation playwright configs), so browser count multiplies across suites and pools, not inside them; a browser-only cap chases the same cross-suite accounting as branches while touching more files.

## Pitfalls
- Deferral quietly becoming never: removed only by writing the triggers into this fork's Taken and leaving framework-fanout as a named off-route line in CHART.md with them attached, so a future flake investigation finds the door already built.
- Misattributing the next load complaint to fan-out when the actual cause is ad-hoc runs sharing the slice outside the permit, which the quota already caps in aggregate but which no suite-internal cap would have prevented either.
- If a later cap is set from process counts instead of measured load, it repeats the TasksMax error at suite level: 409 Chrome *processes* is roughly a few dozen browsers (multiprocess Chrome, model knowledge), and a cap aimed at the scary number throttles the wrong unit.
