# Blind notes, slot C: limit-boundary

One question in this fork. Notes follow the five peer parts. Read 2026-10-13.

## 1. Pick: 1a, with two parts of the option made explicit

Pick 1a: host-wide permit in `run-check` and `base-run`, starting at 1, plus every seat inside the akrogon slice. Reason: it is the only option that puts both the counter and the containment below the agent layer. The permit caps compliant runs before they start, and the slice is what makes an ad-hoc run visible and stoppable instead of invisible. Cost: it is the most machinery of the four options, it is Linux and systemd only, and its seat-scope half cannot be built at the point a seat is launched today (below). It also only answers the fork question as worded ("no ad-hoc script can exceed it") if the slice carries a resource backstop (`TasksMax`, and a CPU or memory ceiling): 1a as written makes ad-hoc runs measurable and stoppable, but a slice with no properties does not stop one from using the whole host until someone stops it. Setting properties on the one slice is inside 1a's text; 1c's ceiling is a component here, not the whole answer.

### Seat launch today, and scope feasibility

Akrogon never spawns a harness itself. `launch()` parses the configured harness template, requires its first word to be the harness name, and returns only the remaining arguments (`src/next.ts:268-276`). Dispatch then runs `herdr agent start <name> --kind <kind> --pane <id> --timeout 30000 -- <args>` (`src/next.ts:631-647`), and `herdr agent start --help` (read today) defines `--kind` as a closed list of canonical executables (pi, claude, codex, and others). Tabs and panes are created by herdr with only cwd and env passed (`src/next.ts:456-471`). So there is no argv anywhere in akrogon where a `systemd-run --scope` prefix can be inserted: the template check at `src/next.ts:274` forbids it, herdr's kind list forbids it, and `systemd-run --help` shows no option to adopt an existing process.

Feasible paths, in order:

1. Adopt after launch. Scopes exist for this: scope units "manage externally created processes" and are created through systemd's bus interfaces (local `systemd.scope` man page). After herdr reports the agent running, create a transient scope from the seat PID under the leaf's slice. This needs two things akrogon does not have today: the seat PID (its herdr pane record carries no pid, `src/shell.ts:134-144`), and a D-Bus transient-unit call instead of the `systemd-run` CLI. A probe by the door must prove both before handoff; until then this half of 1a is pending, and if the probe fails, 1a collapses to 1b and the fork should reopen rather than ship the collapse silently.
2. Type a `systemd-run --user --scope ... pi ...` line into the pane instead of `herdr agent start`. Works mechanically but gives up the herdr readiness and failure contract dispatch relies on (`src/next.ts:647-652`), and puts shell quoting of model and effort back in play.
3. A PATH wrapper named `pi` or `codex` that execs itself under a scope. Fragile, depends on how herdr resolves its canonical executable, and hard to name per leaf. Not recommended.

Granularity correction inside 1a: the unit that survives must be a per-leaf slice, with one scope per seat launch under it. A scope's lifecycle is "bound to the existence of at least one process in the scope" (`systemd.scope` man page), and a leaf has two seats started at different times (A and B panes from `src/next.ts:470-527`), either of which can restart. One scope per leaf would vanish when the first seat exits and cannot be reused by the second seat's later start. Per-leaf slice plus per-seat scope keeps the same measurement and stop target (the slice) with units whose lifetimes match the processes. Seats that akrogon did not launch, such as a manually prompted or standalone pane, never pass through `src/next.ts:631`, so they stay outside the slice; that is a named boundary of 1a, not a surprise.

### What counts as a heavy run

Default: every execution through `run-check` and `base-run` is heavy, and a repo config can name checks as light. The check name already arrives with the run: printed commands carry `--name <check>` from config generation (`src/config.ts:316-324`) into `runCheck` (`src/run-check.ts:136-145`), and the run also knows its leaf, unit, and scope (leaf, worker, base) from `src/run-check.ts:100-130`. Default-heavy is rot-safe: a new check someone forgets to classify takes a permit instead of bypassing the pool, the same refusal direction the framework selector uses for unowned scripts. The cost is real: at a limit of 1, a seconds-long check queues behind a full suite until someone declares it light. Declaring light must be an explicit per-name list in repo config, never argv sniffing inside akrogon, which would put consumer knowledge (`test:changed`, `playwright`) in the wrong repo and rot silently. Unnamed runs (`--holder`, `--leaf`, criterion proofs routed through run-check) default heavy for the same reason; that is the hole a name-based opt-in would leave.

### Nested acquisition

`base-run` does not call `run-check`; it execs the caller's command directly (`src/base-run.ts:157-164`). But the command a seat replays through base-run is normally the printed check text, which itself begins with `akrogon run-check` (`src/config.ts:316-317`), and that inner run-check resolves the base worktree as scope `base` (`src/run-check.ts:119-130`). If base-run takes a permit and the inner run-check takes another, a limit of 1 deadlocks permanently. The same shape occurs for any printed command invoked inside a printed command.

Remove it with membership, not a token: before acquiring, a run checks whether it is already inside an akrogon run scope by reading its own cgroup path. Already inside means the outer run holds the permit, so it proceeds without acquiring. An environment token is the weaker version: `constructedEnv` builds the child environment from a whitelist (`src/run-check.ts:44-56`), so a token would need explicit pass-through at every layer, and any script can set an env var, which makes the bypass forgeable by the exact ad-hoc runs the fork is about. Cgroup membership cannot be forged by setting a variable. Permit acquisition belongs before spawn (`src/run-check.ts:173` is where the command starts), which also covers setup, since setup runs inside the spawned command (`src/config.ts:312-315`).

### Lock fd inheritance by detached browsers

Where the permit is held decides this. If the permit were a shell `flock` wrapper in the generated command text (the existing setup pattern at `src/config.ts:315`, and the framework workaround's shape), the lock fd sits in a shell process whose descendants inherit open fds; the flock man page ships `--close` for exactly "a child process which should not be holding the lock". A detached, unref'd browser down that chain (blepsis `scripts/cdp-core.mjs:628-629`) can then keep the permit held after every runner is dead, silently shrinking a pool of 1 to 0. Hold the permit instead as an flock taken inside the `run-check` or `base-run` process itself: its spawner passes children only the stdio file descriptors (`src/shell.ts:38-45`), so the test tree never sees the lock fd, and the permit's lifetime is the wrapper process, which akrogon already tracks. The existing `withLock` helper is not that shape; it holds the lock in a spawned `flock` child (`src/state.ts:205-209`), fine for short state locks, wrong for a run permit. The reverse risk (wrapper killed, permit released, browsers still alive) is handled by stop ordering in the stop fork, not here; under 1a those browsers are at least inside the seat's scope where the slice backstop and a later stop can reach them.

## 2. Rejected options

- 1b (permit only, per-run scope): rejected because the incident itself is the counterexample. Of the six top-level runs named in the intake, one went through `run-check`; the rest were direct `bun run test:changed` or worker scripts. A permit only in run-check would not have prevented the event this chart exists for, and naming that as a "known limit" makes the limit the whole problem. Its per-run scope reaping is good and is carried into 1a through the seat scopes. 1b is the right first leaf to build, but the wrong fork answer.
- 1c (slice ceiling only, no counter): rejected as the only mechanism. A CPU quota does not stop 1,900 processes from existing inside the quota; it makes every concurrent run slow together, which pushes browser suites into their own timeouts and manufactures the load flakes that cost check.fix rounds. `TasksMax` failures surface as fork errors inside tests, which read as reds. And a ceiling has no queue: nothing decides that the merge run goes first. As a backstop under 1a it is correct; alone it converts an overload into a slower, flakier overload.
- 1d (lower `max_active` or worker counts): rejected because it counts the wrong thing at the wrong time. `max_active` counts leaves with live panes (`src/next.ts:412-443`), is 20 in live config (`config.yaml:1`) against 7 live leaves in the incident, and never sees in-process workers or runs. Even set to 3 it allows 3 leaves times 3 workers times an internally parallel suite. It also throttles cheap planning and review seats along with heavy tests. It is a one-line mitigation the operator can apply today, not an enforcement boundary.

## 4. Pitfalls, and what removes each

- Seat adoption races the seat's first children: a test started before adoption finishes sits outside the scope. Removed by a door probe proving the full tree can be moved and re-scanned until stable, and by adopting at agent-ready time before the first prompt is delivered (`src/next.ts:654` onward), when the seat has no children yet. Pending that probe.
- Limit of 1 deadlocks on nested runs. Removed by the cgroup-membership check above, named here as a binding part of 1a, not an implementation detail.
- Permit held past the runner's death by an inheriting browser, pool stuck at 0. Removed by holding the flock in the run-check or base-run process, never in generated shell text.
- A queued run is indistinguishable from a hang, so a seat aborts and restarts it. Not removed by anything in this fork; it belongs to the queue-behavior question and needs a visible waiting state there. Named so it is not forgotten.
- Two locks in series: framework keeps its local flock workaround after the pool lands. Removed by deleting the consumer lock in the same handoff that lands the permit; owner is the akrogon leaf plus the framework config edit.
- Sizing the slice backstop before one full run has been measured alone turns the ceiling into a flake source. Removed by a door measurement of one full framework run on an idle host before any `TasksMax` or quota number is written into a leaf.

## 5. Questions this fork does not ask

- When the permit is held, who waits and in what order (merge before implement before base-run, or strict arrival), and is a waiting run's time bounded? The scope and phase fields in `src/run-check.ts:100-130` would support a priority, but this fork never asks.
- Does the pool need to separate "runs" from "browsers"? One admitted run can still launch an internally parallel core; if the measured single run is itself too much, the limit unit is wrong and this fork reopens.
- What happens to an admitted run when its seat is stopped: is the run scope stopped with the seat scope, and is that run recorded as incomplete rather than red?
- Should standalone and direct-route work, which akrogon never launched into a pane, be able to join the slice and pool voluntarily through run-check alone, accepting that their ad-hoc commands stay outside?
