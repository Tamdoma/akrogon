# Slot B: permit-release

Blind notes for Q1, 2026-10-13. No other seat's permit-release notes read. Read-only inspection, no lock or process-lifetime probes run. Paths below are relative to akrogon.

## 1. Pick and cost

**Pick release with the run-check/base-run owner's lifetime, accepting the orphan-workload residual explicitly.** On normal command completion, the owner releases after collecting its terminal result. If the owner is killed, the kernel releases its noninherited lock descriptor when the process exits. Do not keep a dead owner's permit through a stale record or require a supervisor to survive it.

This is the lowest-complexity choice consistent with the taken process-held permit and per-pane ownership layout. The guarantee is one admitted top-level verification execution at a time. It is **not** a guarantee that only one workload's surviving descendants exist. Killing the runner can free capacity while its browsers remain. Their pane scope still provides an exact leaf-owned stop target under the locked bus cut; it does not make them disappear automatically.

**Lock implementation:** use an exclusive Linux `flock(2)` on one stable, local, per-UID host file, proposed `/run/user/<uid>/akrogon-runs.lock`, shared by every participating repo/worktree and by both entry points. Keep the descriptor in the owning Bun process, mark it close-on-exec and do not pass it to command children. Keep the file inode stable. The file's existence is not a held permit and it should not be deleted to “recover” a lock.

The literal Taken rule says the run process holds the permit, never a descendant. Akrogon's existing `withLock` actually launches a flock helper child (`src/state.ts:205-208`), so it cannot satisfy that literal ownership rule unchanged. A narrow native flock binding through the existing Bun runtime is the direct implementation candidate. Installed `bun:ffi` declarations support loading libc symbols with integer arguments/return values (`node_modules/bun-types/ffi.d.ts:453-462,563-589`), and `/usr/lib/libc.so.6` is present. This is inspected feasibility, not a proven binding. No new npm package, lock daemon, lease database or native build system is required by this candidate.

Use nonblocking native acquisition in the asynchronous waiting path so a waiting runner can process cancellation; do not block Bun's event loop in a long synchronous FFI call. The queue-order/wait-bound fork owns scheduling policy. Only contention is a wait condition; library, fd, permission and syscall failures retain their real context and fail. No alternate lock kind is used silently.

**Leftovers:** retain the current per-pane scopes as the cleanup boundary. If a killed or completed command leaves heavy descendants, the operator's leaf stop can terminate its boxed work; its exact command and state fence remain the open stop fork. Do not invent per-run attribution from the leaf's temporary-directory names or stop the entire pane automatically after every command. A pane may still contain its shell, the active harness and sibling workers, all legitimate work.

Cost: a narrow kernel-lock boundary and explicit nesting proof, with no new run units or persistent orphan scheduler. The material cost is manual leaf-level cleanup after an abnormal runner death or leaked browser. If the operator requires capacity to remain unavailable until those descendants are gone, choose the stricter option below and authorize its additional ownership/recovery mechanism. I would not present process-exit release as equivalent to that stronger guarantee.

## 2. Rejected options and reasons

- **Release only when a run's workload is empty, using the current pane scope:** not implementable by that emptiness test. The shell and harness remain alive, and sibling workers share the scope. Whole-pane emptiness would hold the only permit throughout the seat session or wait for a leaf stop, including after a successful check.
- **Workload-empty release with new per-run units:** offers a stronger invariant, but requires moving the command into distinct ownership before it forks, retaining run-to-unit records, handling holder SIGKILL while capacity remains occupied, and retiring abandoned units before another admission. Since the taken holder cannot pass its lock to descendants, an external survivor or durable admission/recovery protocol is needed after holder death. This is a real additional design, not a different finally block. It is justified only if the stronger guarantee is worth that cost.
- **Pass the permit fd into descendants so the final child releases it:** violates the taken holder rule. A leaked browser can hold capacity indefinitely, and nested/background spawn behavior determines the lock's lifetime instead of the command owner.
- **PID files, mkdir locks or expiring leases:** substitute stale-owner repair, PID-reuse decisions or clock expiry for an OS-owned lock. A time-based expiry can admit new work while the old workload still runs. The host already has the required kernel primitive.
- **Unchanged withLock helper or flock in generated check text:** conflicts with literal process ownership; generated text also misses arbitrary base-run entry paths. If the operator chooses logical ownership by a helper instead, that is an explicit correction to the lock, with its stdin-EOF/SIGKILL lifecycle proven, not an unnoticed implementation substitution.
- **Close every live process in the pane after each run:** kills the controlling agent and unrelated sibling work. Without per-run ownership, that is an emergency leaf stop, not routine command cleanup.

## 3. Evidence, tier, source and date

All sources inspected on 2026-10-13. No claim below substitutes for the actual implementation's lifetime probe.

1. **E1 — Operator tier: locked lifetime boundaries.** `issues/chart/host-test-load/forks/limit-boundary.md`, final Taken, specifies one permit held by run-check/base-run, with nested calls acquiring none and no descendant holding it. `forks/seat-scope.md`, final Taken, assigns one scope per pane shell generation inside allocate. The permit-release fork is still open. These locks explain why whole-pane emptiness and child-held locks are not interchangeable with the approved mechanism.
2. **E2 — Better-than-training: kernel lock semantics.** Exclusive flock is associated with an open file description. Duplicated/inherited descriptors can retain or release it; closing all references releases it. It is advisory and does not detect deadlock. [Linux flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html). The close-on-exec facility prevents a descriptor from remaining in an executed child. [Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html). With a descriptor kept solely in the owner, SIGKILL cannot leave a live kernel holder. A leftover filename needs no stale-lock deletion.
3. **E3 — Better-than-training: current helper differs.** `src/state.ts:205-224` starts a flock child, waits for its acquisition message, executes the callback, ends its stdin and waits for that child to exit. It is existing useful machinery, but the actual kernel holder is not the calling Bun process. Its normal finally path is not evidence of what happens when the calling process receives SIGKILL.
4. **E4 — Better-than-training: Bun native mechanism exists.** Installed declarations define `dlopen` and typed function signatures (`node_modules/bun-types/ffi.d.ts:453-472,563-589`). Official Bun documentation describes calling native library symbols. [Bun FFI](https://bun.sh/docs/runtime/ffi). This supports a small direct libc binding as a candidate; exact error/errno handling, descriptor flags, wait cancellation and child noninheritance remain proof obligations.
5. **E5 — Better-than-training: current completion is direct-child completion.** `spawnLogged` calls spawnCaptured (`src/run-check.ts:58-67`), and finishCaptured waits on `child.exited` (`src/shell.ts:54-64`). The spawner controls standard streams but defines no per-run cgroup (`src/shell.ts:24-46`). Run-check copies its log and records check_end after that result, then removes its run directory (`src/run-check.ts:171-188`). Nothing here establishes that every browser has exited.
6. **E6 — Better-than-training: both entry points need the boundary.** Base-run calls spawnLogged directly after preparing its checkout and constructed environment (`src/base-run.ts:147-164`). Its finally removes temporary paths and updates the base record (`src/base-run.ts:167-190`). A change only inside runCheck misses direct base-run execution. Neither finally is an orphan-process reaper.
7. **E7 — Better-than-training: nesting is expected, not hypothetical.** withSetup prints checks wrapped by `akrogon run-check` (`src/config.ts:310-324`), and base-run executes arbitrary supplied argv with `exec "$@"` (`src/base-run.ts:157-164`). Passing a resolved check to base-run can therefore enter run-check inside an already admitted execution. Opening the same flock file again does not make a separate acquisition reentrant (source E2).

Neither path automatically supplies one stable host resource identity across independent installations/worktrees. The proposed per-UID runtime file makes that identity explicit.

## 4. Pitfalls and what removes each

1. **R1 — Capacity is freed while descendants survive.** Name this accepted residual in the operator choice and leaf contract. A boxed leaf stop removes those descendants; process-exit release alone does not. If unacceptable, take workload-empty release with explicit per-run ownership and death recovery instead.
2. **R2 — A browser secretly retains the descriptor.** Use a close-on-exec owner descriptor, never include it in child stdio or generated shell commands, and prove the real Bun spawn path plus a detached descendant. The taken rule means a killed owner frees the kernel permit even if that descendant is still alive.
3. **R3 — Separate installations or worktrees use separate locks.** One stable local per-UID path for both entry points and all registered repos. Do not derive it from cwd, TMPDIR, worktree git dir or each installed tool root. Do not remove/recreate a live lock inode.
4. **R4 — Pane cgroup membership is mistaken for nested admission.** Sibling workers share the same pane scope. Membership in that scope cannot show that one is inside an admitted run. Nested reuse needs proof of the live admitted owner, its boot/start identity and the caller's actual relationship to that execution. An environment boolean or pane membership alone would let concurrent siblings bypass the only permit. Carry the required context explicitly through constructedEnv (`src/run-check.ts:44-55`), without inheriting the lock fd.
5. **R5 — A nested caller releases its parent's permit.** Only the top-level owner opens/releases the kernel lock. Nested base-run/run-check reuse that owner's admission and preserve their own command/log/result behavior. Owner death ends that admission; an old marker is not reusable capacity.
6. **R6 — Queued work blocks cancellation or is reported as a failed test.** Avoid a long synchronous native wait. The queue fork must define wait/cancellation behavior and distinguish not-started work from a completed test failure. Library/syscall errors are surfaced, not treated as contention.
7. **R7 — Current record-cleanup locks are reused as the resource gate.** Use a separate resource lock. Short state/base-record locks keep their existing responsibilities; never hold the global lifecycle lock while waiting for long-running verification capacity. Base-run already updates records under its own short lock (`src/base-run.ts:140-142,173-190`).
8. **R8 — Cleanup is inferred from directories or root exit.** Per-pane cgroups supply leaf ownership, not exact run ownership. Preserve that distinction in status/reporting and do not scan TMPDIR to kill apparent leftovers. The future stop operation must use the leaf's owned units.

Required implementation/proof cases: two repo/worktree callers serialize, a normal completion releases, holder SIGKILL releases despite a surviving detached child, the child has no permit descriptor, nested base-run/run-check does not deadlock, sibling workers in the same pane do not both bypass admission, and queue cancellation launches nothing. The exact native binding and local path also need the door's smallest real operation proof. No such operations were run here.

## 5. Missing questions

1. **Q2 — Residual acceptance:** Is process-exit release plus leaf-level stop acceptable when a killed runner leaves browsers alive, or must capacity stay occupied until every descendant is retired? That stronger requirement entails machinery absent from the per-pane layout.
2. **Q3 — Literal ownership:** Must the kernel descriptor belong to the Bun run-check/base-run process exactly, as Taken says, or may the existing flock helper own it while its parent controls lifetime? The latter may reduce code, but changes the stated ownership and needs its own SIGKILL/EOF proof.
3. **Q4 — Standalone calls:** What cleanup guarantee applies to run-check --holder invoked outside a boxed leaf pane? It should still share admission, but the per-pane leaf stop cannot be claimed for an unowned caller's descendants. Resolve this boundary before promising a stop for every possible invocation.
4. **Q5 — Capacity setting:** Is this contract strictly one permit, or must its first implementation support a configurable count greater than one? A single exclusive flock implements one. Do not silently add a generalized semaphore or claim one file implements multiple slots.

The low-complexity recommendation is process-lifetime release, with the surviving-descendant limitation stated plainly and leaf-level stop as its cleanup route. Workload-empty release is a different, more expensive guarantee.
