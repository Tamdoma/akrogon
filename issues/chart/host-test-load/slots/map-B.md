## Material forks

### D1 — Where must resource admission apply?

- **D1.O1: Config-resolved checks only.** Smallest change and easy rollout. Leaves direct package commands, custom criterion proofs and direct base-run spawning outside the guarantee. F3/F4 show those boundaries.
- **D1.O2: A common host gate plus consumer adoption at heavy entry points.** Config checks, worker tests, lane checks, criteria, retries, comparisons and merge verification share admission. Direct supported framework entry points reach the same gate. Costs an explicit boundary contract and consumer wiring, but survives additional leaves and harnesses.
- **D1.O3: Gate every shell command or globally reduce agents.** Avoids classifying tests but serializes coding and unrelated operations. A wrapper command can still start parallel children internally. It also gives pi responsibility for guessing arbitrary shell intent.

**Recommendation: D1.O2.** Akrogon owns one shared admission mechanism across registered repos for this operator's host. Framework declares the heavy operations and routes its supported direct entry points through it. Pi supplies ownership/cancellation, not command-string classification. Arbitrary scripts launched outside the supported boundaries are not covered merely because a prompt requests compliance. If the required promise includes those scripts, D4 needs containment at the seat/worker boundary as well.

First decide whether “host-wide” means this UID's workloads or all users' workloads. A per-user lock is not a system-wide multi-user budget. Cost: medium, with most risk in covering entry points rather than implementing a mutex.

### D2 — What admission policy is proportionate now?

- **D2.O1: One concurrent heavy run, using an OS-owned lock.** Small mechanism, crash release follows ownership, no stale token database. It sacrifices overlap and does not inherently guarantee FIFO fairness. Descendants retaining the lock can prolong ownership.
- **D2.O2: Multiple slots or weighted CPU/browser tokens.** More throughput if measured capacity permits it. Incorrect weights or nested acquisitions recreate oversubscription or deadlock. Recovery and fairness become part of the scheduler's contract.
- **D2.O3: Admit from CPU load or pressure.** Reacts to outside activity, but sampling and already-running bursts can admit too much. Load does not directly specify browser capacity. Current pressure recording is merge telemetry, not admission: `akrogon/src/next.ts:1063-1084`, `akrogon/src/attempts.ts:82-89`.

**Recommendation: D2.O1 initially.** One shared heavy-run permit is a defensible starting point, not evidence that one run fits the host. Keep cheap operations outside only where their resource behavior is inspected. No daemon or adaptive scheduler is needed for this initial outcome. Queue cancellation and visible owner/wait state are necessary behavior. A retry or base comparison must queue like any other run, not hold a permit while requesting another.

Every nested entry must either be inside the admitted run or acquire admission once. Do not layer independent locks at config, package and script levels. GNU make's jobserver explicitly accounts for inherited capacity and requires exact token return, useful precedent rather than a drop-in shared service for independent pi seats. [GNU make job slots](https://www.gnu.org/software/make/manual/html_node/Job-Slots.html). Flock does not detect deadlock and background children can retain its lock. [util-linux flock manual](https://man7.org/linux/man-pages/man1/flock.1.html). Cost: low for one permit, medium for correct cancellation and nesting.

### D3 — How much parallelism may one admitted run create?

- **D3.O1: Bound only whole test commands.** Fastest admission fix, but F4 shows a single invocation can still create ten capture browsers alongside other suites.
- **D3.O2: Bound browser-heavy suite branches and explicit browser pools.** Preserve independent cheap work, cap expensive children, and measure one isolated run before allowing more. Longer suite duration can hit existing runner timeouts.
- **D3.O3: Serialize every test or force every Playwright runner to one worker.** Simple but broader than the defect. Playwright's worker setting does not control direct Chrome launches or `Promise.all` pools such as F4.

**Recommendation: D3.O2.** Framework owns the suite/pool bounds. Start browser-heavy operations conservatively, then select a measured bound with desktop headroom. Do not choose “32 CPUs means 32 browsers.” Playwright recommends one worker for CI stability and permits higher parallelism on a suitably provisioned host. [Playwright CI guidance](https://playwright.dev/docs/ci), [parallelism](https://playwright.dev/docs/test-parallel). Cost: medium because reduced parallelism needs real duration checks, not just a changed setting. Site-nav's capture comment specifically says parallelism was introduced to fit the harness timeout, so silently replacing its pool with sequential capture is not yet a proven fix: `framework/.claude/skills/dev-render-satellite/test/site-nav-e2e-run.ts:552-554`, `framework/.claude/skills/dev-render-satellite/test/site-nav-e2e.test.ts:33,81`.

### D4 — What lifetime boundary survives runner failure?

- **D4.O1: Strengthen existing process-group cleanup only.** Reuses pi machinery and is portable to its current Linux/macOS support. Still cannot catch a child that changes sessions, and a cleanup callback cannot execute after its owner is SIGKILLed. Existing limitation: `pi/worker-shell.ts:156,216-218`.
- **D4.O2: Linux cgroup ownership, managed through systemd, plus normal application cleanup.** Covers descendant processes despite parent changes and session detachment, provided they stay in the owned cgroup. Requires a proven launch/stop/recovery contract and local user-manager availability.
- **D4.O3: Scan process ancestry, cwd or temporary-directory command lines after failure.** Useful incident diagnosis, but ownership can disappear through reparenting or cwd changes and broad selection can hit another run. Do not make emergency pattern matching the normal stop mechanism.

**Recommendation: D4.O2 for this Linux host.** Assign each owned run a unique unit/cgroup, keep the permit until its workload is empty, preserve logs/status, and stop the unit's whole membership before freeing resources. A seat/worker ownership boundary also contains direct ad-hoc commands. In-process workers cannot be stopped by killing a nonexistent worker agent PID, so shell lifetimes need their own ownership while their manager remains alive.

The kernel documents inherited cgroup membership and recursive cgroup kill. [Kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html). Systemd documents control-group termination and TERM-to-KILL escalation. [systemd kill source](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.kill.xml). Merely starting a service or scope does not establish cancellation when its waiting caller dies. Prove owner death handling and abandoned-unit reconciliation explicitly. A scope can retain descendants after its initial command exits, while a supervised service has a different lifecycle. Also, `--wait` cannot be combined with `--scope`. [systemd-run source](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd-run.xml).

Read-only host checks found systemd 262, unified cgroup membership and a responding but degraded user manager. No transient unit or control setting was tested. This is feasibility evidence only. Cost: medium/high, with exact stdout, cwd, environment and exit-status preservation part of the proof. No silent process-group fallback if cgroup containment is the agreed guarantee.

### D5 — What should Pause and Esc stop?

- **D5.O1: Preserve pause and waiter cancellation as today.** No compatibility change, but does not meet the report's expectation of emergency stopping. F5/F6 establish that mismatch.
- **D5.O2: Make pause terminate current repo work and make parent Esc cancel its active/queued children.** Matches the report's stated expectation, but changes a documented dispatch-only operation and removes the ability to cancel a wait while leaving intentional background children alive.
- **D5.O3: Preserve pause, add an explicit owned-work stop, and make operator parent abort cancel owned workers.** Separates dispatch suspension from termination. Requires a clear stop/resume state and pi's operator-abort integration, without treating every normal agent settlement as cancellation.

**Recommendation: D5.O3, subject to the operator's choice of pause semantics.** The stop must first prohibit new owned launches and automatic result-triggered turns, cancel queued requests, then terminate running descendants and confirm cleanup. F6's automatic child-result delivery triggers a parent turn: `pi/index.ts:104-113`. Killing browsers while workers can continue is not a complete stop. Preserve low-level waiter-only cancellation for intentional background use if operator abort can be distinguished from cancelling a wait. Do not assume an extension abort event exists without inspecting/proving the actual pi API. Cost: medium, spanning akrogon and pi-extensions. Adopting D5.O2 instead needs explicit guide/command behavior changes, not a hidden implementation choice.

### D6 — Should verification responsibility change to reduce repeated suites?

- **D6.O1: Keep worker changed tests and A's integration checks, gate their actual resource use.** Preserves current proof ownership and parallel coding. Broad selections still cost time, but cannot overlap beyond the agreed bounds.
- **D6.O2: Workers run targeted unit proof and only A runs broad leaf verification.** Removes repeated broad runs at their source. Needs a reliable targeted command per unit and explicit handling when a change affects shared infrastructure. An arbitrary file subset can hide real failures.
- **D6.O3: Remove worker testing or disable delegation globally.** Reduces launches but gives up current worker proof or coding parallelism without proving either caused the resource failure.

**Recommendation: D6.O1 for this chart.** Let the existing framework selector leaf reduce breadth. Reuse valid earlier evidence under the existing rule, rather than adding new blanket reruns: `akrogon/skills/implement-issue/SKILL.md:65`. D6.O2 can be taken only if the operator wants a separate verification-ownership change and the targeted runner contract is resolved. Neither D6.O2 nor D6.O3 should silently reopen F8's settled wave policy. Cost: low policy change for O1, substantial contract/selector work for O2.

3. **Q3 — Process lifetime.** Does stop catch normal children, a setsid child, a child after root timeout, and children after owner SIGKILL? 4. **Q4 — Queue semantics.** How long may admission wait, what does status show, does cancelling a queued run prevent it from ever launching, and is FIFO or merge priority actually required? Grounding: F3 and [flock manual](https://man7.org/linux/man-pages/man1/flock.1.html). Queue timeout must not be recorded as a failing product test. No fairness guarantee is inferred from flock.
5. **Q5 — User control.** Should pause remain dispatch-only, and must Esc stop every owned child or just the current wait? What is the resume behavior for committed work and retained worker worktrees? Grounding: F5/F6, `akrogon/skills/implement-issue/worker-protocol.md:21,29`, `pi/tools.ts:175`. This is a product choice, not something outside documentation can decide.
6. **Q6 — Containment versus throttling.** Is cgroup ownership sufficient, or is a hard aggregate CPU/memory/task ceiling also required for ad-hoc scripts? A task cap includes threads, not just browser root processes, and CPUQuota percentages are relative to one CPU. Those settings can produce test timeouts or launch failures instead of orderly queueing. Grounding: [systemd resource-control source](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.resource-control.xml). Numeric quotas and their transfer to this host remain unproven.

## Lifetime pitfalls and what removes them

1. **R1 — Separate per-repo limits still multiply on one host.** One shared admission identity across participating repos removes this. A lock inside each worktree does not. Existing setup locking is per worktree: `akrogon/docs/guide/setup.md:70`.
2. **R2 — Nested gate acquisition deadlocks, or forged ambient ownership bypasses the gate.** Define one acquisition boundary and a verifiable inherited ownership contract before consumer adoption. Do not rely on arbitrary command text or a caller's self-declared environment flag. This is a proposed invariant, not a current implementation finding.
3. **R3 — A permit is released while browsers remain alive, or deleting/recreating a lock file creates two independent locks.** Tie release to confirmed workload retirement and retain one stable lock identity. Validate owner crash, inherited descriptors and restart rather than cleaning locks by pathname deletion. Source for inherited-lock behavior: [flock manual](https://man7.org/linux/man-pages/man1/flock.1.html).
4. **R4 — One admitted suite still overloads the host.** Bound its internal browser/suite concurrency and measure it. F4 establishes both layers. Browser subprocess counts are not browser-session counts, so measure both without treating them as interchangeable.
5. **R5 — Stopping a parent only wakes another worker/parent turn.** Fence launch/delivery before cancellation and confirm empty owned workloads before acknowledging stop. Existing automatic delivery and waiter behavior: `pi/index.ts:104-113`, `pi/manager.ts:1301-1306`.
6. **R6 — Throttling creates new reds and retry storms.** Gate retries and base comparisons, distinguish queue/cancellation/setup outcomes from completed test failures, and verify revised suite duration against real runner limits. Current retry/base-run behavior is `akrogon/skills/implement-issue/SKILL.md:38`; direct base spawning is `akrogon/src/base-run.ts:164`.
7. **R7 — Normal finally cleanup is mistaken for a crash guarantee.** Keep graceful close for artifacts, add a lifetime owner outside the killable runner, and prove abandoned-run cleanup. F7 shows the graceful paths and their limits.
8. **R8 — Competing fixes reopen settled selector/wave work.** Adopt the existing selector leaf and serial-solo lock. Do not make “CPU is a shared resource” serialize every planning wave, because that would eliminate coding parallelism rather than control test execution. Existing path/resource grouping and locks: `akrogon/skills/plan-issue/SKILL.md:59`, F8.
