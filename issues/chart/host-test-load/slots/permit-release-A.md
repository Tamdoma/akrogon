# Notes A: permit-release (before reading B/C)
Pick: release at run-check/base-run process exit. Permit = an exclusive kernel file lock on one host-wide file under ~/.akrogon, taken by the run-check process itself on an fd opened close-on-exec, so the check's children never hold it. The kernel drops the lock when the holder exits for any reason, SIGKILL and crash included, so a dead holder can never wedge the queue and no stale-lock cleanup code exists. Nested runs see an inherited marker env (set in constructedEnv) and skip the lock.
Leftovers: no per-run tracking. Anything a run leaves behind stays inside its pane box (seat-scope Taken) and is ended by the leaf stop. The ceiling (ceiling-values) bounds what leftovers can take.
Cost: a leaked browser tree can run next to the next permit holder. Measurement 2 saw no leftovers after a clean pass (0 app scopes, run exited cleanly); leaks come from killed runs.
Rejected: release when the workload is empty. Needs a per-run unit or process-group tracking plus a watcher, and one stuck browser holds the only permit host-wide until someone stops it, which is the queue-wedge class the kernel lock removes. Also rejected: `flock(1)` wrapping the command, since its fd is inherited by children, so a leaked browser silently holds the permit (workload-empty semantics by accident).
Optional small add: run the check in its own process group and kill the group when the check exits. Catches ordinary leftovers for near zero code. Detached (setsid) children escape it and stay with the pane box.
Evidence: src/run-check.ts:136-188 (single spawn, finally block), src/config.ts:310-324 (setup flock is per worktree, unrelated), Linux flock(2) lock released on last fd close (man flock.2), measurement 2 in forks/limit-boundary.md.
Pitfalls: Bun has no flock API, so the implementation needs a verified way to take flock on a CLOEXEC fd from Bun (FFI or a tiny helper holding the lock for the parent PID). Proof required. Lock file on a local filesystem only.
