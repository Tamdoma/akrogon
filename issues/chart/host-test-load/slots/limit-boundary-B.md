## 1. Pick, reason and cost

**Pick 1a, with a required correction: the common slice needs an explicit aggregate resource ceiling.** A scope provides ownership, accounting and a stop target. It does not limit CPU, memory or task creation merely by existing. Without the ceiling, 1a limits participating commands while an ad-hoc script inside a seat can still start unlimited concurrent tests. This does not satisfy Q1 as written. The ceiling values belong to the next resource-budget decision, not an assumed number here.

The corrected boundary is: one host-shared admission pool across participating repositories, starting at one admitted verification run, plus all akrogon-owned seat and run workloads under the same bounded user slice. Direct scripts started by those seats inherit the resource boundary even when they bypass admission. They are bounded by the slice, not magically serialized by the permit. This preserves parallel coding while protecting the desktop from the aggregate workload. A resource ceiling can throttle work or reject launches, so it cannot replace orderly admission and internal browser bounds.

**Define the initial permit boundary mechanically: every `run-check` or `base-run` execution participates.** Do not infer heaviness from a check name, elapsed time or shell text. The existing schemas have arbitrary command strings and no resource declaration (`src/config.ts:49-54`). A command called `test_changed` can select the entire parallel core suite (`framework/.claude/workflow/scripts/run-test-changed.ts:121-122,196-202`, `framework/package.json:165`). Current framework config also locks a command named `cheap`, so that name is not an admission exemption (`framework/issues/config.yaml:11-15`). Serializing lightweight configured checks is the explicit initial cost of avoiding an unproven classifier. If only a declared subset should participate, that declaration needs its own settled contract before implementation.

Cost: medium/high. Besides a small admission mechanism, the work needs seat containment before launch, run ownership and retirement, nested admission, restart/recovery handling and exact command-result preservation. This is not a config-only wrapper change. Cgroup containment does not require changing pi's wave size or duplicating the framework selector leaf.

The promise must mean akrogon's workloads for this UID across registered repos, including ordinary descendant scripts. A user scope is not a limit on unrelated host processes, other UIDs, or a deliberate same-UID request to the user manager to move work outside the akrogon slice.

## 2. Rejected options

- **1b:** Too narrow for the supplied intake. It explicitly leaves direct worker scripts outside admission and containment. It can make supported checks safe, but does not deliver the requested stop/load boundary for everything a seat starts.
- **1c:** Useful as the mandatory outer protection in corrected 1a, insufficient as the sole mechanism. It allows many whole suites to compete inside the same quota, increasing latency and creating quota-induced launch failures or test timeouts instead of queueing expensive runs.
- **1d:** Counts the wrong resource. Akrogon limits new leaf allocation, not test launches, and existing allocations continue (`src/next.ts:411-443`, `docs/guide/limits.md:7`). Pi's concurrency is three per parent manager (`pi/manager.ts:288`, `pi/index.ts:96-103`). A single framework site-nav capture already starts ten browser sessions through `Promise.all` (`framework/.claude/skills/dev-render-satellite/test/site-nav-e2e-run.ts:550-563`). Fewer seats cannot guarantee a safe single run.

I also reject **uncorrected 1a** as a complete answer to the literal question. Measurement and stop ownership are valuable, but neither enforces a resource ceiling or counts bypassed runs.

5. **E5 — Better-than-training: nested execution is a real interface possibility.** Effective checks are printed as `akrogon run-check ... -- sh -c ...` (`src/config.ts:310-324`). Base-run accepts arbitrary argv, sets up a detached checkout, then executes those arguments using `exec "$@"` (`src/base-run.ts:101-107,153-164`). 6. **E6 — Better-than-training: file descriptors are part of lock lifetime.** Linux flock locks refer to an open file description shared by fork/dup, and release requires explicit unlock or closing every descriptor referencing it. [flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html). `flock --close` closes the lock descriptor in the command child while the holder remains. [flock(1)](https://man7.org/linux/man-pages/man1/flock.1.html). Detachment changes process/session ownership, not those lock semantics. A browser can retain a permit only if the actual launch chain preserves that descriptor. Do not claim the incident browsers did: no fd trace was inspected. Blepsis normal launch is detached (`/home/ivan/Work/infra/blepsis/scripts/cdp-core.mjs:628-629`), but that alone proves neither lock inheritance nor this incident's launch chain.
7. **E7 — Better-than-training: scopes are lifetime groups, not completed-test verdicts.** Scope units have no main process and remain alive while any member exists. Program exit status is the launching parent's responsibility. [systemd 262 scope documentation](https://raw.githubusercontent.com/systemd/systemd/v262/man/systemd.scope.xml). Systemd-run scope mode preserves the caller's execution environment, while `--wait` is incompatible with `--scope`. [systemd 262 systemd-run documentation](https://raw.githubusercontent.com/systemd/systemd/v262/man/systemd-run.xml). Resource-control properties supply ceilings separately. [systemd 262 resource-control documentation](https://raw.githubusercontent.com/systemd/systemd/v262/man/systemd.resource-control.xml).

## 4. Pitfalls and what removes each

1. **R1 — A common slice with no ceiling leaves ad-hoc overload intact.** Record corrected 1a as both admission and an aggregate CPU/memory/tasks boundary. Resolve its values separately. Keep ordinary bypassed descendants within that boundary and do not claim they obey the run counter.
2. **R2 — Scoping the Herdr request rather than the pane workload.** Prove containment of the actual pane shell and harness before first prompt, using E2/E4's boundary or an explicitly supported launch-prefix interface. Do not bypass Herdr startup/readiness tracking with unverified shell injection. If PID adoption fails and a Herdr launcher change is needed, name that real prerequisite destination rather than silently widening akrogon's leaf.
3. **R3 — Adoption after work starts misses existing children.** Establish containment before new seat startup. Existing seats need a separately verified transition that covers all already-running work, or a controlled stop/relaunch preserving their committed state. A scope containing A must also contain B or have a recorded B scope, not leave the second pane outside. PID identity and ownership must be revalidated before adoption.
4. **R4 — Base-run takes a permit, then waits forever for nested run-check.** One top-level execution owns admission. Nested wrappers join that execution's verified ownership and neither acquire nor release another permit. Carry that ownership explicitly through constructedEnv and validate it against the current process's admitted run membership. An arbitrary environment boolean is not proof. The child terminal result, logs and base comparison must stay unchanged. Exact nested invocation and deliberate invalid-ownership probes are required before handoff.
5. **R5 — A detached child holds a descriptor forever, or holder death frees capacity while its workload survives.** Keep the lock descriptor in a supervising holder, close it before spawning arbitrary workload children, and hold admission until that run's owned workload has retired. On holder death, next admission must reconcile the abandoned run before granting new capacity. An fd-close fix alone solves descriptor leakage but not early release. Preserve a stable lock identity rather than deleting/recreating its path.
6. **R6 — Per-leaf stop misses admitted runs moved to sibling scopes.** Scopes do not nest. If per-run scopes are used to distinguish run retirement, record their leaf ownership and stop all that leaf's units. Keep every unit under the same bounded slice. Stopping only the seat scope is not enough after its child was moved elsewhere.
7. **R7 — Success is inferred from an inactive scope or a killed runner.** Preserve the exact command's exit/signal result and artifacts, and distinguish resource termination, cancelled wait and completed red tests. A quota-induced incomplete base comparison must not become a base-defect verdict (`skills/implement-issue/SKILL.md:38`). Scope inactivity alone carries no test verdict (E7).
8. **R8 — One permit is mistaken for one browser.** Keep the separate internal-pool decision. A single admitted run can select all core branches and ten site capture browsers (`framework/.claude/workflow/scripts/run-test-changed.ts:196-202`, `framework/package.json:165`, and the site-nav source under rejected 1d). Do not raise capacity above one without a measured single-run footprint and desktop headroom.

Required later proofs: two repositories/worktrees sharing admission, nested base-run/run-check completion, cancellation while queued, descriptor noninheritance, owned setsid descendants, holder/seat death, second-seat containment, unchanged Herdr readiness, sibling-run stop and unaffected unrelated workloads. These are required handoff/runtime proofs, not tests run in this blind pass.

## 5. Questions missing from the fork

1. **Q2 — What exactly is guaranteed?** Is the promise one admitted supported verification command plus a ceiling for bypassed seat descendants, or an exact browser/run count for every arbitrary script? Corrected 1a delivers the former. The latter needs heavy-entry adoption or a browser admission interface and is not supplied by scopes.
2. **Q3 — What counts as heavy?** Can the initial implementation gate every run-check/base-run execution, accepting serialized lightweight checks? If exemptions are required, who declares them and how do unnamed criterion commands participate? This needs an explicit answer rather than implementer guessing.
3. **Q4 — How are active seats brought under ownership?** Before first launch, shell-PID scope adoption is plausible. What is the agreed transition for already-running A/B seats, replaced panes and their descendants? The no-repo-edit/no-unit brief prevents proving that route here.
4. **Q5 — What ceiling and failure policy accompany 1a?** Aggregate limits must protect the desktop, but task exhaustion and memory termination can fail suites. Values, treatment of resource failures and internal browser bounds remain open. Do not infer a safe ceiling from 32 threads or the incident's peak counts.

The pick is corrected 1a. Plain 1a provides containment and a participating-run limit, but the resource ceiling and actual seat-launch integration must be explicit before its guarantee is presented as settled.
