# Slot B: queue-order

## 1. Pick, reason and cost

**D1: Accept unspecified acquisition order, without FIFO or merge priority.** Use the taken single in-process flock, with `LOCK_EX | LOCK_NB` attempts separated by a fixed short asynchronous delay, proposed 250 ms. Retry only contention. This counts admitted runs without introducing tickets, a scheduler, priority classification or a recovery protocol for dead queue heads. A newly arriving run may acquire before an older waiter. Starvation freedom is not promised.

**D2: No akrogon admission-wait deadline.** Wait until admitted or the waiting process is cancelled/stopped. The operator can inspect the holder and stop its leaf using the Taken stop command. A run returning because a command/tool deadline expired before admission has not run a test. Do not count that as a suite red, automatically retry it, compare it against base, spend a fix round or move its seat to failed merely because capacity was unavailable. The leaf phase stays unchanged. The seat needs to retry the verification later or resolve the cancellation through its existing workflow.

There is therefore no internal “queue timed out” outcome in this pick. An outside tool's deadline may still cover both waiting and execution. It must actually end the waiter before reporting cancellation. Merely abandoning a tool wait can leave the process alive and able to launch later. If cancellation races admission, distinguish “not launched” from “launched then interrupted”. Never report a suite result for a command that did not start. Pi Esc's existing worker-wait policy remains unchanged.

This is the lowest-complexity choice if the operator accepts an unbounded acquisition wait and unspecified fairness. The 239-second measurement makes six single requests roughly twenty minutes of work before the last starts. It is not a twenty-minute bound: worker requests multiply the contenders, commands differ in duration, and later requests can overtake earlier ones.

**D3: Show the live holder and waiters using the already required per-run owner metadata.** Extend that metadata with run ID, repo/leaf, run kind/name, worker unit or seat when known, request time and waiting/admitted state. Reuse the PID, kernel start time and boot ID required by permit-release. Publish one record per top-level contender alongside the shared permit identity, and update that record on admission. Status groups waiting calls under their leaf and identifies the host holder, including another repo's holder. Show elapsed wait, not queue position or ETA. Nested reuse points to its admitted owner and creates no second permit contender.

Metadata is an observation of a live process, never admission authority. Remove a caller's own record on ordinary completion/cancellation. Dead records left by SIGKILL are excluded using live identity checks and do not block another caller. A metadata-read failure is reported as unknown/error, not an empty queue. Use the same record for nested-owner validation and status, rather than adding a second queue database. The unresolved lock-path choice remains with the leaf design.

**D4: Record admission delay per run, separately from command duration.** Add a request/end event pair keyed by run ID to the existing timing stream. The end records admitted or cancelled-before-launch and elapsed wait. Start `check_start` only after admission, as permit-release settled. Base-run uses its existing run ID and records admission delay separately from its worktree preparation, command and cleanup. Its existing record start is not an execution start.

Keep the existing phase elapsed/prompted definitions. Render admission waits as per-run details, alongside executed checks, including in an open visit. Do not turn one worker's wait into the existing leaf-wide `wait` state or subtract summed worker waits from phase time: sibling calls overlap and other leaf work can continue. A killed process may leave an unmatched admission event. Mark that history incomplete rather than fabricating an end time, successful test or timeout. Existing timing writes are best-effort, so live status must not depend solely on the event log.

**Cost:** a short async acquisition loop and reporting fields/events on existing ownership and timing surfaces. A 250 ms retry can delay pickup by roughly one interval when an uncontested permit becomes free, in addition to runtime scheduling delay. There is no queue-order guarantee, acquisition deadline or preemption. Neither a stuck live holder nor continual overtaking is fixed automatically. A stuck holder requires the already selected operator stop. This choice adds no daemon, durable scheduling queue or fairness repair.

## 2. Rejected options

- **O1: Strict arrival order.** Correct FIFO needs ordered request identity, a shared decision boundary and live/dead-head handling across processes. Timestamp display or sorting status rows does not establish that order. This adds a second admission mechanism without evidence that ordering is needed to meet the host-load limit.
- **O2: Merge verification first.** It needs trustworthy classification across run-check, base-run, workers and nested calls, and a rule preventing ordinary verification from starving. `mergeTurn` chooses a merge leaf and prepares its stack, but it does not acquire the test permit. Prefer a single unclassified admission policy until merge delay is measured as a distinct problem.
- **O3: A fixed 20-minute wait deadline.** One measured four-minute suite times six requests is not a worst case. A timeout could reject healthy work during the intended serialization and trigger retry/base-run amplification if presented as a test red.
- **O4: Add timeout configuration or an automatic retry queue now.** This introduces policy, outcome handling and re-admission machinery that an unbounded, cancellable wait avoids. If bounded waiting is required, choose its duration and no-execution outcome explicitly, separately from command execution timeout.
- **O5: Call blocking flock directly on Bun's JS thread.** It prevents asynchronous cancellation/reporting work in that process from progressing while the native call blocks. LOCK_NB plus a timer keeps those paths available without a helper process or native worker thread. `threadsafe` does not make an FFI call asynchronous.
- **O6: Acquire while holding akrogon's global `.lock` or the base-run record lock.** The holder and stop/dispatch operations can need those locks. Never wait for run capacity inside these unrelated critical sections. Admission must not freeze status, stop or the dispatcher.
- **O7: Reuse the leaf-wide timing wait reason for permit contention.** Several workers and both seats may have different admission states simultaneously. A single leaf-wide wait interval cannot represent their queue delays accurately.

## 4. Pitfalls and what removes each

- **R1: Status promises FIFO or a place that the lock does not enforce.** Display elapsed waits and holder identity only. State unspecified order. If fairness becomes mandatory, reopen D1 and pay for a real ordered queue.
- **R2: Ordinary capacity wait creates false test failures and more work.** No internal admission deadline. Distinguish outside cancellation before launch from executed failure in output/history, and prove no retry/base comparison is launched merely because a waiter was cancelled.
- **R3: The caller stops waiting but the command later launches.** Keep the admission process alive only while the actual request is live. Prove cancellation removes that waiter, and stop kills queued processes along with the leaf slice. A pi subagent_wait abort alone is deliberately insufficient.
- **R4: Waiting blocks stop behind the global lock.** Place admission outside the global dispatch lock and base record locks. Prove status and stop complete while another run holds the permit and several callers wait.
- **R5: A dead PID's record is mistaken for a live holder.** Share permit-release's boot/PID/kernel-start validation, use caller-owned record identity and remove only that caller's metadata. Dead metadata has no scheduling effect. Prove SIGKILL and PID-identity mismatch do not retain admission or show a live queue item.
- **R6: A lock/configuration error is retried forever.** Retry only EWOULDBLOCK. Capture errno at the native boundary and propagate other failures with the lock path and operation. Prove an invalid descriptor/path does not appear as contention.
- **R7: Concurrent worker waits distort phase timing.** Key admission pairs by run ID and report overlapping spans separately. Keep check duration after admission and retain existing phase elapsed accounting. Prove two simultaneous worker waits do not turn an active sibling into a leaf-wide wait or inflate elapsed totals.
- **R8: A queued run survives a stop/start cycle and launches with obsolete context.** The Taken leaf stop must terminate its waiting processes before restart. Check the stopped fence at the run launch boundary, and prove stop versus acquisition races. An old queued request is cancelled, not silently transferred to the restarted seat.

Required proof: two worktrees and two repos contend for one permit, JS timers remain responsive during contention, nested runs reuse admission, and queued cancellation launches nothing. Kill a holder and prove another contender acquires. Exercise stop with both a holder and waiters, then start with no old request revived. Verify live status, cross-repo holder reporting, open-visit queue timing, overlapping worker spans, base-run delay, and incomplete history after SIGKILL. Assert exclusivity and outcomes, not a particular acquisition order under D1.

## 5. Missing questions

- **Q2: Is lack of starvation freedom acceptable?** Unbounded waiting plus unspecified acquisition order is an explicit cost. If the operator needs eventual service under continual arrivals, the low-complexity flock policy is insufficient.
- **Q3: Which effective harness/tool deadlines cancel the process, and which merely abandon the wait?** Akrogon's inspected config supplies none. Verify the actual pi/codex caller path before claiming that its timeout prevents a later launch. This does not require changing pi Esc.
- **Q4: Must permit waiting be excluded from existing leaf-speed phase metrics?** My pick keeps those metrics' elapsed definitions and adds per-run details. Changing a phase/cohort metric under overlapping workers is a separate policy choice, not an incidental new wait label.
- **Q5: Is a live holder stuck forever an acceptable operator-managed condition?** Process-exit release prevents a dead owner's stale lock. It does not terminate a live process whose command never ends. The Taken stop is the recovery route, and its working proof is required before an unbounded wait is described as usable.
