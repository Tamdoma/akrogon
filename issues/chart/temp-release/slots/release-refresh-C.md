## Refresh facts (what changed since the fork was written)

- Leaf-path lock no longer matches on place or shape, still matches on idea. Locked (2026-10-02): `/tmp/akrogon-<uid>/<hash12>`, 12 hex of sha256(repo.root + "\n" + slug), derived by `leafTemp`, created 0700. Today: `/var/tmp/akr-<uid>/<4 hex of sha256(repo.root)>/<8 hex of the same leaf hash string>` (src/config.ts:263-285), still derived never stored, still forced 0700 (src/config.ts:292-310), plus an absolute-path env override `AKROGON_LEAF_TEMP_ROOT`. Two commits replaced it: 2c3a0af (2026-10-11) split and shortened the name (`/tmp/akr-<uid>`, 27 bytes) for the 107-byte Chrome socket limit, and c698170 (2026-10-14) moved the root to disk-backed `/var/tmp` because tmpfs files in leaf temp counted as slice memory and held admission closed overnight (commit body). Consequence for this fork: the intake's "RAM freed" is now mostly about processes, not files; leaf temp files sit on disk. Measured today: `/var/tmp/akr-1000` holds 496 MB in 10 leaf dirs, the largest 450 MB; `/tmp` itself is 1.3 G used, 29k inodes, against the intake's 11 G and 532k inodes.
- Delivered since, by worktree-cleanup (#93, all six leaves `merged`): finished-leaf-processes, scratch-copy-removal, kept-status (its surface since moved to `akrogon leftovers`), test-isolation, stacked-member-close, store-sweep.

## Q1. On release, stop processes, confirm exit, delete scratch for every outcome?

- Pick: yes for every outcome, completed as follows. (a) Take what #93 delivered as the base; (b) add the one missing outcome, parked, as an explicit release like finished; (c) before deleting any leaf temp, confirm exit negatively: slice empty or stopped, no live run owner, no same-uid process with cwd or an open file inside. Cost: a parked leaf resumes cold (browser profile and temp caches gone; dependencies live in the worktree, not temp), and one extra `/proc` scan that reconcile already computes once per pass.
- Already delivered, so not part of the pick: for a `merged` or `failed` leaf whose tab is proven gone, reconcile stops its slice outright (`systemctl stop`, guarded by own-slice, live-run and live-tab checks, src/reconcile.ts:420-439,152-175) and later in the same pass deletes its temp when no pane is inside, no run inside is kept, and the slice holds no process (src/reconcile.ts:956-973, slice rechecked with `sliceHasProcess`); deletion of any item goes through `dropChecked`, which vetoes on pane list unavailable, live pane inside, any same-uid process with cwd or an open file inside (`pidsInside` over one `/proc` scan, src/reconcile.ts:275-306,702-726), or a live contained owner. Dead-owner `run-*` dirs are removed even for active leaves; a leaf whose tab vanished without finishing also loses its temp under the same checks. Closed owners are the merged case (`allLeaves` spans open and closed, src/state.ts:153-155).
- Still open: parked leaves are invisible to reconcile's leaf map, so a parked leaf's temp falls into the unowned branch and is deleted only opportunistically when no leaf of the repo is running (src/reconcile.ts:903-909,987,729-750), never as a named release, and its slice is never stopped by the per-repo step (the host step stops an unmatched slice only when its cgroup already holds no process, src/reconcile.ts:762-766). No post-stop verification exists for a slice `systemctl stop` reported success on (src/reconcile.ts:168-175 trusts the exit code), and the per-pass `/proc` snapshot is cached at first use (src/reconcile.ts:483-485), so a process entering the temp after the scan is seen by neither check in that pass.
- Rejected: keep merged-only deletion. Already superseded by #93 on main; reinstating it would resurrect failed-leaf leftovers the operator asked to clear. Rejected: delete scratch at the phase transition itself (`akrogon phase ... failed`/`merged`). The seat making that call runs with TMPDIR inside the folder being deleted (src/next.ts:474 sets `TMPDIR=<leafTemp>` for the seat) and its tab is by definition still live; release belongs to reconcile, which already owns tab, slice and process judgement in one pass. Rejected: age-based expiry for the parked case, foreclosed by store-hygiene's "nothing is deleted for age".
- Evidence (primary code at main ab3c889 and commits, read 2026-10-16): src/reconcile.ts:420-439 (slice step order), :956-973 (temp deletion), :702-750 (checked and unowned drops), src/state.ts:153-155 (no parked leaves in `allLeaves`), src/park.ts:55-77 (park only renames the folder and refuses running leaves; no slice stop, no temp step), commits 2c3a0af and c698170 above.
- Pitfalls: a process that escaped the leaf slice (Chrome in its own app scope is the recorded case) survives the slice stop; the `/proc` veto in `dropChecked` is what removes this pitfall, and it must stay a veto, never a kill list. A process under another uid is invisible to the scan (same-uid only, src/reconcile.ts:285): accepted on this single-user host, named as a limit. Deleting temp under a just-stopped slice in the same pass is safe only because `systemctl stop` returning 0 is taken as exit; the `sliceHasProcess` recheck before deletion is what removes doubt, and it should also run when the stop happened this pass, not only when the slice was left loaded.
- Question the fork does not ask: is a tab that vanished while its leaf is unfinished a release at all? Today it is, silently (temp deleted, leaf still dispatchable, temp recreated on allocate). If the tab vanished because herdr restarted, every active leaf loses its temp in one pass; should dispatch or status at least name that it happened?

## Q2. Does a failed leaf release right after its evidence is saved?

- Pick: no. Keep today's shape: the failed leaf keeps its tab and temp until the operator closes the tab or retries the leaf, and release then happens through the Q1 path. Reason: the failed tab is the resume vehicle, not just a viewer: on failure the tab is renamed `<slug> failed` (src/phase.ts:108) and operator recovery renames it back and resumes the same seats (src/phase.ts:162,247), whose shells hold `TMPDIR=<leafTemp>` (src/next.ts:474); deleting temp under a live tab breaks the seats' writes (the a77c260 lesson) and closing the tab throws away the diagnosing seats' context to save disk that is no longer RAM (leaf-path refresh above). Cost: an ignored failed leaf holds its tab, its slice processes and its temp indefinitely; they stay visible as a failed leaf in status, which is the existing attention surface.
- Rejected: release immediately after evidence is saved (close tab, stop slice, delete temp, keep worktree). It frees processes fastest and the evidence that matters is mostly outside temp (failure record in state, leaf artifacts and kept check logs under `issues/`), but it converts every failure into a cold restart: recovery dispatches fresh seats that re-derive what the failed seats knew, any browser state and un-copied captures in temp are gone, and a failure the operator could have cleared by talking to the seat now needs a full re-dispatch. It also has to define "evidence is saved" mechanically, and nothing today marks that moment (the `failed` transition writes state and renames the tab, src/phase.ts:104-108,146).
- Rejected: stop the slice but keep tab and temp. The seats themselves run adopted into the leaf slice, so stopping it kills the seats and leaves a dead tab; not a coherent middle state. Rejected: delete temp but keep the tab, for the TMPDIR reason above.
- Evidence (primary code, 2026-10-16): failed is already `finished` for the slice step, but a live recorded tab is an explicit keep reason (src/reconcile.ts:152-166 `sliceKeepReason`, :426-439), and temp deletion for a failed leaf is already wired the moment the tab is gone (src/reconcile.ts:956-973); `akrogon stop` exists for the operator who wants the slice stopped without closing the question of the tab (src/stop.ts `stopCommand` stops the slice and records the leaf stopped, `start` resumes it). So the release Q2 asks about needs no new mechanism, only a decision to trigger tab close at failure.
- Pitfalls: an operator-closed failed tab must not be mistaken for abandonment of the worktree or branch; Q1's release deletes temp and stops the slice only, and the failed worktree already follows its own rule in the sweep (removed only when clean and reachable or kept with a reason). A failed leaf whose tab the operator keeps open for days also keeps its slice's background processes; what removes that pitfall is that `akrogon stop <slug>` already exists as the deliberate middle action, and status names the failed leaf until acted on.
- Question the fork does not ask: should `akrogon phase <slug> failed` distinguish "blocked, will resume here" from "done, evidence complete" (the failure record already carries `cause: blocked | attempts`, src/state.ts failure schema), releasing only the second kind? If release-on-failure is ever wanted, that distinction, not the failed phase alone, is the safe trigger.
