# Fork notes, seat C, door-cost fork carry-rules, 2026-10-26

## Q1. Start prompt alone, or prompt matching a Mode record handover entry?

Pick: prompt matching the entry, no match means attended in no chart. Reason: fresh A on entry pulls, imports, restarts consultants and writes files, so there is real authority to protect against a stale or re-sent prompt pointing at a chart another door has taken. The entry also names the outgoing mode on disk, so a later reader can tell attended continuation from autopilot. Cost: old A writes one entry (creating the next chart's folder when absent, as autopilot already does) and shapes.md stops treating the Mode record as autopilot-only.
Rejected: prompt alone. Its only copy lives in pane text the reset wipes, nothing on disk proves which chart, mode or consultants were handed over, and a mismatch is undetectable after the fact.
Evidence: better-than-training, SKILL.md sections Open, Drain, Autopilot and shapes.md Chart records, read 2026-10-26. Better-than-training, issues/chart/config-walls/CHART.md and orphan-pane/CHART.md: two live handovers with this record-and-match shape, 2026-10-22.
Pitfalls: a queued reset that never fires leaves a stale handover entry as the latest mode line. Removed by the match rule itself: a later normal attended open has no matching prompt, so it starts attended and appends its own entry, superseding the stale one. Fresh A must never invent the session id in the entry it appends (shapes.md already states this).
Unasked: does the match expire? A prompt delivered hours late matching an old entry would enter a chart the operator may have since worked elsewhere. The fork should state a bound or state that the operator speaking in the pane first kills the match.

## Q2. Where do chat-only operator instructions go?

Pick: old A writes them verbatim into the next chart's records before queueing the reset, and the prompt points at them. Session instructions ("only these charts today") go in the handover entry's detail. Consultant choices already ride the handover entry's surviving-consultants list. Scoped approvals belong in the fork or readiness record that governs them, where Take already required them when given. Fresh A carries session instructions forward into the next handover entry when it hands over in turn. Cost: one deliberate write step in old A's last turn.
Rejected: verbatim in the prompt only. The prompt is pane text sent through herdr, the reset wipes the pane, and nothing durable remains to check, carry forward or audit. Rejected: reference to existing records only. It fails exactly the case in the question, instructions that exist nowhere on disk yet. Writing them down before queueing is what turns them into a referenceable record.
Evidence: operator, INTAKE.md provenance rule that operator words are copied verbatim and kept separate from agent findings, 2026-10-26. Better-than-training, SKILL.md sections Autopilot (handover entry names remaining list and consultants) and Take (operator answers and reasons recorded in fork files), read 2026-10-26.
Pitfalls: old A paraphrases and quietly narrows or widens an instruction. Removed by requiring the operator's words verbatim, as in INTAKE sources. Pitfall: an instruction covering several charts is written only in the next chart and lost at the following handover. Removed by the carry-forward duty above. Pitfall: fresh A cannot know what old A forgot to write. Partly removed by making the handover step name its contents (next chart, consultants, session instructions, pending steps) instead of "write the records".
Unasked: what if a chat-only approval was given for the outgoing chart's undelivered work, not the next chart? It belongs in the outgoing chart's records before its span closes, and Q2's text should say so rather than only naming the next chart.

## Q3. Accept the turn-gap risk, or change door-reset.ts?

Pick: change the script. At queue time the parent records a boundary in A's session record (transcript byte length for claude, rollout byte length for codex, session file byte length for pi). The child aborts and logs a superseded result if a new turn starts after that boundary (new user entry, new task_started turn_id, new user-role entry), checked while waiting and again at the existing identity recheck before sending the reset. Reason: attended mode is the case where someone is at the pane and can type ahead or send a follow-up the moment A's turn ends. Autopilot never had this exposure. A warning in the footer does not stop input already typed. Cost: one bounded script change plus tests. The pieces exist: door-reset already parses codex rollout turn ids and peer-wait already uses a byte boundary per exchange for codex and scans the claude transcript for the last prompt.
Rejected: accept and document. It makes a surprise session wipe a known behavior in the one mode where the operator is present to be surprised. Rejected: shrink the 600s bound. The child is queued mid-turn, so the queuing turn's remaining length is unknown and a short bound breaks legitimate long turns. Rejected: fire only on the first observed open-to-ended poll transition. With 500ms polls and instant type-ahead, the ended state between two turns can be missed entirely for claude and pi, so the hole stays.
Evidence: better-than-training, door-reset.ts (detached child, 600s turn bound, 500ms polls, identity recheck step, codex rollout turn parsing) and peer-wait.ts functions claudeTurnOpen, codexRollout, codexEnded (byte boundary then bound turn id), read 2026-10-26. Better-than-training, a live pi session file under ~/.pi/agent/sessions, entries carry type, id and message role, checked 2026-10-26.
Pitfalls: an aborted reset leaves old A alive after the footer said "handover queued", and the only record is the log. Removed by naming the log path in the handover entry (the autopilot entry form already carries it) so old A or the operator can read the superseded result. Pitfall: the boundary is captured when old A runs the command, partway through its own turn. Entries after the boundary include the rest of the queuing turn, so the abort test must look for a new turn start, not any new entry, or every handover aborts. Pitfall: three harnesses, three markers, one of them (pi) relying on session file format the akrogon repo does not own. Removed by the fail-closed rule the script already uses: an unreadable marker means log and send nothing, the same shape as identity changed.
Unasked: should the same superseded protection apply to autopilot handovers? The script cannot tell the modes apart, so the change protects both. The fork should say that plainly instead of scoping Q3 to attended.

## Q4. A floor on attended handover, or reset at every switch?

Pick: reset at every chart switch, no floor. Reason: any floor needs a measure A cannot see at decision time. A has no reliable read of its own context size, and outgoing chart length does not predict it, since intake finding F2 says context runs 120k to 150k per call in charts of any size because carried history dominates. A returned-to chart is also already the accepted pattern for consultants, who restart on re-entry and re-read, and CHART.md is designed to resume from the selected fork without a full reread. Cost: a switch-heavy pass pays the 61k fresh baseline plus opening reads per switch, and two very short charts in a row can cost more than carrying on. Seats, spans and usage records will show this, and a floor can be added later from that data.
Rejected: skip when the outgoing chart was short. Short is undefined in any unit A can observe (minutes, turns and tokens give different answers) and judging it each switch spends turns, which F5 says is what cost tracks. Rejected: skip when returning to a chart worked earlier in the pass. That keeps the intervening chart's full context loaded, exactly the waste F2 names, and a second return compounds it.
Evidence: operator, INTAKE.md findings F2 and F5, 2026-10-26. Better-than-training, SKILL.md section Open (consultants restart on entry and re-entry), shapes.md Chart records ("On resume, CHART.md points to the selected fork"), read 2026-10-26. Better-than-training, skills/chart-issues/scripts/chart-usage.ts counts session activity inside recorded span windows, read 2026-10-26, so per-switch cost is measurable after the fact if fresh A records its seat and opens its span before other opening work.
Pitfalls: silent cost inversion on switch-heavy passes with no tripwire. Partly removed by the usage record above, but only if someone reads it. The leaf should not add a watcher; the handoff review already shows usage lines per chart. Pitfall: every-switch resetting trains old A to rush record writing at chart end. Removed by the agreed trigger wording: records written, consultant turns collected and span closed come before the reset is queued.
Unasked: is a switch back to the immediately previous chart in the same pass (A chart, B chart, A chart) common enough in past passes to price either way? The spans in past seats.yaml files could answer this from data instead of argument.

## Q5. Conflicting corrections in one reply: A resolves, or back to the operator?

Pick: a conflict in substance goes back to the operator before any batched check is sent. Under autopilot A resolves it as a recorded A pick, with dissent carried, as Autopilot already provides. A resolves wording and format conflicts while drafting the shape without asking. Reason: peers checking a shape built on A's silent resolution wastes the whole round trip when the operator meant the other branch, and a passed check would lend A's guess an authority it did not earn. One short operator turn is cheaper than one peer round trip against the wrong shape. Cost: the round pauses for the operator even when A is fairly sure which correction wins.
Rejected: A resolves and lets the check catch it. The final-shape check is a check on the shape, not a substitute operator answer, and questions.md bars recommendations and silence from supplying one outside autopilot. A peer can flag an inconsistency but cannot know which correction the operator would keep. Rejected: send both branches in the shape for peers to check in parallel. Peers check two contracts in one return, the fork records neither cleanly, and the operator question still waits at the end.
Evidence: better-than-training, SKILL.md sections Take and Autopilot, questions.md section Blind peer exchange (focused check before A records a mechanism or contract change), read 2026-10-26. Operator, INTAKE.md findings F3 and F5 on round trips and turns driving cost, 2026-10-26.
Pitfalls: A labels a real conflict "wording" to keep moving. Removed by a plain test in the leaf text: if the two readings would write different fork Taken lines, criteria or contract lines, it is substance. Pitfall: the conflict is between a new correction and an existing lock or Taken answer rather than between two new corrections. Same treatment, and the fork text should say so, since Q5 as asked covers only correction against correction.
Unasked: none beyond the lock conflict case above.
