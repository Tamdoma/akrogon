## Material forks, ordered by reshaping power

These are proposed questions, not taken decisions. Each answer changes the scope of subsequent questions.

### 1. What must be green before a leaf lands, and when does the full suite run?

- **1a. Keep full verification on every rebased leaf**, with a shared heavy-run limit. Preserves the current pre-push gate and avoids introducing a new integration owner, but keeps unrelated suite cost per leaf and per rebase retry.
- **1b. Affected tests and cheap global invariants gate leaves; full verification runs on an immutable main revision before publication/release. Recommended if the operator accepts this main-health boundary.** Removes unrelated full-suite work from each leaf while retaining a complete delivery gate. Main can temporarily contain a regression the selector missed. A main run cannot prove what was checked before a preceding push.
- **1c. A serialized integration candidate or batch gets a full run before main changes.** Appropriate if main itself must remain fully verified. It can amortize suite cost over several leaves, but introduces a queue, candidate ownership and rules for invalidating/rebuilding batches. Existing fast-forward pushes do not provide this test queue.

Recommendation: settle 1 first. Prefer 1b for the stated timing problem, paired with the release gate in fork 5. If “main must never receive an unchecked integration” is a requirement, choose 1c or retain 1a. Do not claim post-submit checking is equivalent to the existing pre-push promise. Research: S2/S3/S4, evidence F1/F12.

### 2. Who defines affected tests, and at what granularity?

- **2a. Agents choose folder/single-file commands from each diff.** Easy to start, but omissions and disagreement are likely for shared data, dynamic imports, hook wiring and cleanup paths.
- **2b. The consumer owns an executable selection rule over changed inputs and affected consumers; akrogon runs its declared command. Recommended.** Keep cheap global invariants, use the rebased base/head, and include templates, fixtures, configuration and dependencies as inputs. Explicit global inputs select broad checks. Unmapped impact must be resolved or conservatively covered before granting a narrower gate. Akrogon need not understand Bun, skills or the consumer’s dependency graph.
- **2c. Install a general monorepo build graph or predictive selector.** Established tools can model dependencies and reuse tasks, but migration/maintenance is not justified by this single incident alone. Learned selection trades completeness for measured recall and needs historical data.

Start with meaningful consumer suite boundaries, not a large graph platform. This incident particularly needs a cheap template contract separated from browser integration where their input dependencies justify the separation. Do not assume splitting the file proves that the browser path cannot consume the changed template. Validate that dependency. An agent audits the mapping and criteria; mechanical tests verify actual selection behavior rather than prose wording. Research: S3/S4, evidence F6/F7.

### 3. What resource is limited, and where is the limit enforced?

- **3a. Lower max_active or forbid overlap globally.** Reduces activity but unnecessarily stops unrelated work and still permits two seats or workers within one leaf to run expensive commands. It also misses manual or other-repo runs.
- **3b. One enforced host-wide heavy-run slot, used by leaf proofs, merge suites and base diagnostics. Recommended initial bound.** Cheap work can continue. Waiting for capacity is visible waiting, not a failed test or consumed repair round. Scope the reservation to the shared machine, not a worktree or leaf slug. Hold it until the command and its browser/server children have actually ended. Same-host manual commands only participate if they use the same entry point.
- **3c. Move heavy suites to independent CI runners with explicit job concurrency.** Provides isolation and scalable execution if inputs and runner resources are ready. It does not bound local seat runs unless those runs are also moved or coordinated. Sharing many jobs on one self-hosted machine recreates the contention.

The numeric initial bound of one is a conservative operating choice, not a measured optimum or proof of overload. The minimal enforcement location is the command execution path shared by the heavy callers, not next’s prompt loop. Decide whether that entry point belongs to akrogon or a consumer-owned runner before designing it. Avoid an adaptive load-average scheduler: load is not reliable evidence of headroom or an explanation of a timeout. Research: S5/S6/S7, evidence F8/F9.

### 4. What qualifies as red on base, and what follows an inconclusive run?

- **4a. Preserve the current one-run rule for any nonzero or killed base attempt.** Simple, but conflates base code failure with resource loss, timeout and incomplete execution.
- **4b. Require valid comparable execution before a base attribution; otherwise retain an explicit unresolved execution failure. Recommended.** Compare command/scope, input/dependency/runtime versions, actual exits and failure evidence under the same reserved resource regime. Different failures do not prove a common code defect, and equal test names alone do not prove causality. A criterion still failing remains blocked. No “base also red” waiver creates a green result.
- **4c. Retry until green, raise every timeout, or quarantine the browser suite automatically.** Can hide real defects and multiply host work. Not recommended.

Fork 4b may permit one expressly chosen diagnostic rerun after correcting an identified execution condition, preserving the original evidence. It must not become an automatic retry loop or generic fallback. Distinguish completed assertion failure, test timeout, external process kill and waiting for capacity. Do not invent a new lifecycle state before the operator settles the behavior. The current stop rule remains authoritative until changed. Research: S1/S2/S8, evidence F3/F5/F10/F13.

### 5. If full verification moves out of leaves, who owns its completion and failures?

- **5a. One consumer integration job proves a specific revision before release/publication. Recommended with 1b.** A full-suite failure blocks that delivery and gets an accountable owner, revision and evidence. A leaf’s affected verification and push completion remain distinct from repository integration health. Prove the exact revision being published, not a mutable checkout or an arbitrary older green run.
- **5b. Run the full suite only at epic completion or on a timer, with publication independent.** Amortizes work but can publish unchecked revisions and leaves independent changes outside epic ownership. Suitable only for an explicitly nonblocking audit, not as the replacement delivery gate.
- **5c. Retain full pre-main integration approval through a merge queue.** Use this with 1c, including batch failure isolation and handling a moving base.

If full jobs are coalesced, a later run must include all changes since the last proven revision. A canceled or superseded run is not green for its own SHA. Do not delete merge_checks.verify before its replacement owner, trigger, evidence and gate work. CI portability, browser installation and nonsecret/secret input requirements still need checking. The standing no-off-machine-credential rule prevents casually moving required local secrets into a new hosted runner. Research: S4/S6/S8, evidence F12 and standing design lines 9/15.

## Pitfalls

1. **P1. Timing changes without scope changes preserve the expensive work.** #48 already moved the full suite to merge. Serializing it protects capacity but does not remove per-leaf redundancy. Conversely, affected selection does not prevent two necessary browser runs from contending.
2. **P2. Folder filtering misses noncode dependencies.** F6 is a concrete counterexample. Templates, shared scripts, fixtures, lockfiles and config can affect other consumers. Deleted/renamed files and a changed rebased base must also influence selection. Cheap hooks/contracts currently repeat under several checks entries; that is measurable duplication, not a reason for unrelated cleanup in this task.
3. **P3. Test-resource independence includes host capacity.** Separate worktrees isolate files, not CPU, memory, browser process capacity or shared provider limits. Reserving only the main verifier misses its diagnostic/base copies. A per-repo lock can still contend with another repo on the same machine.
4. **P4. Increasing test parallelism can introduce a new failure class.** FW deploy-core.test.ts:895-910 mutates and restores shared env, fetch, spawn and sleep for each test. Do not add blanket Bun concurrency or apply Playwright runner flags to this suite. Browser reuse, timeout increases and capture rewrites are separate fixes requiring evidence, not automatic chart scope.
5. **P5. Nondeterminism is not proof of harmlessness.** A load-sensitive production concurrency bug can pass in isolation. Preserve criterion checks, timeout evidence and original failures. Diagnose outside owned leaf surfaces without silently weakening a gate or declaring that no leaf change could ever repair the cause.
6. **P6. Base comparison is evidence about one execution, not immunity for a diff.** Capture actual child exit, signal/timeout, failing identities, command/scope and execution conditions. The extracted suite in F10 does not certify the entire wrapper. The artifact/result discrepancy in F13 must stay visible.
7. **P7. Evidence reuse is revision- and input-bound.** A competing merge changes the integration target. The current merge rule deliberately reruns then. Any reuse optimization must show unchanged relevant inputs and environment. A pre-rebase green run, an incomplete background run or a later green SHA cannot certify another integrated revision by name alone.
8. **P8. Full-on-main needs a real trigger and delivery hold.** Existing release publication runs immediately after main pushes. A scheduled audit, successful leaf transition or canceled workflow is not an integration gate. A queue must also avoid canceling required cleanup, and release must publish the revision actually tested.
9. **P9. Do not conflate waiting, unavailable prerequisites and failed behavior.** Capacity waits should not consume repair rounds. Missing credentials/browser prerequisites are not test assertion failures. Preserve exact reasons without secrets. Avoid automatic stale-lock breaking while live child processes still own resources.

## Proposed destination split and real dependencies

Propose two destinations, AK and FW. The following are provisional independently checkable outcomes, to be refined after the forks settle.

- **L1 · AK or an explicitly chosen shared runner destination: heavy execution admission.** One shared host reservation for participating heavy commands, visible waits, actual process completion and preserved command outcomes. This can proceed independently of affected selection once fork 3 selects ownership and semantics. If all heavy execution moves to isolated CI, replace this outcome with CI concurrency rather than building both mechanisms without need.
- **L2 · FW: affected leaf verification.** Consumer-owned input/consumer selection, cheap invariant checks, justified cheap/browser suite separation and integration into declared leaf checks. Prove included and excluded real cases, including the two-line template change and hook consumers. No dependency on L1 if it remains ordinary declared commands. Wiring to a new L1 command API creates a real L1 → L2 dependency.
- **L3 · FW: full integration ownership and publication gate.** An immutable revision gets full verification with adequate resources and recorded failure ownership before its release. The existing full verifier supplies the command already. L3 need not wait for L2 to establish the gate, but **removing the old leaf full-suite gate must wait for both L2 selection and L3 coverage**. If L3 uses L1’s local runner, L1 → L3 is real. If it uses independent hosted runners, that edge does not exist.
- **L4 · AK: base-result policy and phase skills.** Apply the selected valid-run/attribution contract consistently in implement, review, repair and merge, keeping failing criteria blocked. If fork 4 requires L1 outcome fields or controlled execution, L1 → L4 is real. A prose-only clarification of incomplete-run evidence does not intrinsically depend on a selector or a CI job.

Do not order L2 and L3 just because they both edit package/config, or AK leaves just because they edit the same skill. The activation dependency that matters is replacing a pre-push full gate only after affected coverage and the new full integration gate both work. A confirmed browser/capture defect belongs in an additional FW repair only if investigation establishes it, not as speculative refactoring in these outcomes.
