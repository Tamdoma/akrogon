## Q1. Drain

Pick: zero open leaves in every registered repo when the engine leaf merges. "Open" means any `state.yaml` under `issues/open`, whatever its phase, plus no live land or verify run for one. Handoff and dispatch freeze until the engine leaf has deployed and its first smoke pass has run. The engine leaf's landing brief carries a done-criterion listing the inventory count per registered repo, checked immediately before its merge, not at chart time. Any leaf still open then either finishes on the old engine before the freeze lifts the merge, or the operator explicitly stops or abandons it through today's paths; there is no third state.

Reason: the engine leaf changes the state it must read: pane ids and the session-valued `prompted` are replaced by address, turn, and transcript path under strict schemas (`src/state.ts:86-106`), and the new engine contains no old-herdr call with which to prompt, close, or even identify an old seat. It also deploys to every repo at once on merge (`~/.akrogon/current`), so there is no per-repo sequencing available. Today the precondition already happens to hold: I counted 0 open `state.yaml` files in each of the 12 registered repos on 2026-11-07, but that is a fact about this week, not a property of the merge moment. Cost: a standstill window whose length is the slowest open leaf, and chart handoffs queue behind it.

Rejected: carry leaves over by translating their state and restarting seats on hc (that is a compatibility migration: new code reading old records, old tabs it cannot close, and seat contexts silently discarded while the leaf claims to be the same attempt; signpost 2a forbids the layer, not just its name). Let open leaves finish on old herdr while the new engine is live (impossible as stated: the old plugin invokes the installed `akrogon` binary, which is the new engine after the flip, and the old engine no longer exists anywhere to drive them).

Evidence: operator signposts 2a/6a and the intake's one-cutover words; better-than-training: `src/state.ts` strict schema, identity Taken state fields, deploy-on-merge via `~/.akrogon/deploy.yaml`, my live count above.

Pitfalls: the old plugin is still enabled at the flip (`~/.config/herdr/plugins.json` points into the current release today, checked 2026-11-07), so its next event would invoke the new `akrogon next` against old-shaped input. Removed by ordering inside the engine leaf: its install disables or unlinks the akrogon herdr plugin as part of the same deploy that installs the listener, and the smoke pass runs with the old plugin already inert. A chart door actively charting another epic on the old door scripts is not an open leaf but is live work the flip can strand; the freeze announcement covers doors too, and the inventory check names chart folders with uncollected consultant turns. A merged-but-still-open owner folder counts as open until old-engine completion moves it, which the inventory does naturally.

Not asked: who may declare a leaf abandoned at the freeze — the operator alone, presumably — and is an abandoned leaf's worktree preserved as evidence or reconciled away by the new engine's first sweep?

## Q2. Rollback across the cutover

Pick: `akrogon rollback` never crosses the cutover boundary. Rollback between releases on the hc side works as today; rollback whose target is a pre-engine release is refused by the rollback command itself in every post-engine release. The refusal is mechanical: a release carrying the listener unit under `systemd/` is post-cutover, one carrying `plugin/herdr-plugin.toml` is pre-cutover, and rollback compares current and target trees on those sentinels before it flips anything. The refusal text names the way back that does exist: pause the repos, hold the bad commit as today (`writeReleaseHold`, `src/rollback.ts`), and fix forward, using the manual previous-release install path only within the hc side.

Reason: rollback across the boundary is not a release flip, it is a second cutover in reverse: the old release would need the old plugin relinked and integrations reinstalled (`src/install.ts:146-147` in the old tree, which the running new binary will never execute for it), the new listener units disabled, and every state record written by the new engine read by strict old schemas. Building that reverse path, testing it, and keeping it alive is exactly the dual support the operator excluded. The protection rollback gives today is instead bought before the boundary: the zero-open drain, the freeze, and the 2a full-life proof happen while nothing real depends on the new engine yet. Cost: after cutover, a catastrophic engine defect is repaired live with the estate paused rather than by going back; that is the accepted one-way door, and it is why Q1's freeze and proof order matter.

Rejected: rollback allowed until old herdr is physically removed (the state-schema and plugin/listener problems exist from the first new record, long before removal; the binary merely being present does not make the old release able to run the estate). Rollback allowed until the first real leaf runs (the same problems arrive with the listener install and the first new-format timing and log records, and "first leaf" is not a thing the rollback command can verify from deploy records alone). Silent manual symlink flips (possible for the operator with shell access, by definition unsupported; the command's refusal is what keeps the supported path honest).

Evidence: better-than-training: `src/rollback.ts` (flip, hold, install, record), `src/release.ts` deploy records, `docs/reference/commands.md:61`, `~/.akrogon/deploy.yaml` current/previous fields; signposts 2a/6a.

Pitfalls: rollback invoked from a checkout or an older release binary would not contain the refusal. Removed in practice because the installed `akrogon` the operator runs is always the current release; the manual README recovery path for a broken release must gain one line naming the boundary. A failed rollback halfway (flip done, install conflict) keeps today's retry property (`src/rollback.ts` hold refresh on retry), unchanged on the hc side. Pre-cutover releases remain on disk under `~/.akrogon/releases` until pruning; their mere presence lets a hand flip resurrect the old plugin against removed state, which is a reason the final sweep explicit-prunes them (Q3), not a reason to keep them as a fallback.

Not asked: does the boundary also refuse *forward* re-deploy of a held pre-cutover commit through any other verb (install from an old checkout), or is `rollback` the only guarded door?

## Q3. Removal: owner and order

Pick: three owners, sequenced after the 2a proof, and nothing deletes the old binary before its own uninstall commands have run.

1. Akrogon's final sweep leaf, landed through the new engine: deletes `plugin/`, the integration-install and plugin-link calls, `tests/fake-herdr.ts`, old fixtures, and current wording (Q4). Its brief carries operator steps to run while `~/.local/bin/herdr` still exists: `herdr plugin unlink` for akrogon and `herdr integration uninstall <kind>` per harness, verified by `herdr plugin list` and `herdr integration status`.
2. An omarchy-customizations leaf: removes the `herdr/` patch bundle, its post-update hook, and the desktop shortcut pointing at the local binary; its operator steps disable and delete the installed units (`herdr-patches.path/.timer`, `herdr-claude-rules.path`, the services) and `~/.local/share/herdr-patches/`. This must precede binary removal: the path unit watches both herdr binaries and exists to rebuild and restore one.
3. Operator steps, last: confirm no old session holds work worth keeping (`herdr session list`, the running `app-Hyprland-herdr-*.scope`), stop the old sessions, remove `~/.local/bin/herdr`, then `~/.config/herdr/`, then prune pre-cutover akrogon releases. If `/usr/bin/herdr` exists it is a package-manager decision for the operator, not a file delete.

The source checkouts stay: `infra/herdrdev/` (upstream and patched trees) and `infra/herdr-plugins/` become unmaintained archives, evidence for the upstream reports already filed, with no runtime path left that can resurrect them once units and hooks are gone. Deleting the multi-GB worktrees and caches is an operator disk decision, not a cutover gate. Old skill folders are already gone by then (herdr-skill Taken replaces them at herdr-setup install), including herdr-setup's own backups of them, which this order's last step sweeps.

Reason: each piece is removed by the repo that installed it, which is where its tests and install records live, and the ordering respects the two hard constraints: uninstall commands need the binary alive, and the patch machinery resurrects the binary unless disabled first. The running old server is the operator's own live surface (it may hold panes no leaf owns), so stopping it is an operator act, not a leaf's. Cost: removal spans two repos and a manual step, so the chart needs a small cross-repo checklist in the sweep brief; and the archives keep several GB of old source on disk until the operator chooses otherwise.

Rejected: akrogon's sweep leaf reaching into systemd units, omarchy hooks, and `~/.config/herdr` itself (one leaf owning four installation domains is how half-removed states happen, and its tests cannot cover the other repos). Deleting the binary first and cleaning up after (plugin and integration state become unremovable except by hand-editing their registries, and the path unit fires a rebuild against a missing target). Deleting the source checkouts as part of "removal" (they endanger nothing once decoupled; they are the only evidence for what the patched old herdr did and why).

Evidence: better-than-training: live `systemctl --user list-units '*herdr*'` (path units waiting, timer elapsed, one running herdr scope), `herdr plugin --help` and `herdr integration --help` (unlink/uninstall exist), omarchy-customizations `herdr/README.md` (installer, path unit, hook, atomic binary replacement), `~/.config/herdr/plugins.json`, sizes by `du` (herdrdev worktrees about 4 GB), all 2026-11-07.

Pitfalls: the post-update omarchy hook (`ensure-herdr-after-omarchy-update`) can reinstall patch machinery after the sweep if the omarchy leaf lands second; removed by landing it before the binary steps. Harness settings that mention herdr outside integrations (Claude permissions and hooks in `~/.claude/settings.json`) survive `integration uninstall`; they are inert once the binary is gone and are the operator's own settings to prune or keep, so the sweep lists them and touches none. `herdr integration uninstall` per kind must run for every kind install ever touched, not only the kinds in today's config, verified by `integration status`.

Not asked: is there a `/usr/bin/herdr` from a package on this machine today, and if so does removing the package belong in step 3 or is the packaged binary left unused?

## Q4. Wording: history exempt

Pick: current text is rewritten everywhere; dated history is exempt untouched. Current text is README, `docs/`, `src/` (including AREA files), `skills/`, tests, and the active lines of `learnings/LESSONS.md`; in those, standalone `herdr` survives only inside the proper names `herdr-app`, `herdr-core`, `herdr-setup`, the global `herdr` skill, and the `"herdr"` module import in akrogon's own herdr-app mods. Exempt: `learnings/history/**`, `issues/closed/**` and closed chart folders, and append-only record files (`log.jsonl`, `timings.jsonl`, verify and merge-attempt records) up to the cutover moment. The two active LESSONS lines naming old-herdr mechanics are handled as lessons, not prose: the stderr-parsing lesson generalizes to external command output (`hc` included) or retires through the lesson rule, and the plugin-cwd lesson retires with the plugin.

Reason: current documentation must never instruct an agent to use a removed system — that is the intake's plain ask, and agents read docs and AREA files as instructions. History has the opposite duty: a dated case file saying the old plugin ran with the wrong cwd is evidence about 2026-09, and rewriting it falsifies the record the lesson system exists to keep; learn-issues already has a retirement path for lessons whose world ended, which is the honest way for the active list to forget them. The final sweep's done-criterion is one grep with the exemptions and proper names spelled out. Cost: a reader landing in history meets dead instructions in past tense; the date, folder, and the current docs carry that context.

Rejected: rewrite history too (destroys provenance for the migration's own evidence, including this chart's intake, which quotes old-herdr behavior throughout). Leave "historical" mentions inside current docs where they read as background (agents do not reliably read tense; a state-and-phases table saying "the herdr tab" is an instruction-shaped falsehood after cutover). Blanket search-and-replace `herdr` → `hc` (several mentions are about mechanisms that do not map 1:1, e.g. delivery "as herdr reported it"; each current mention gets reworded to the new mechanism or deleted).

Evidence: operator intake ("no herdr wording in docs"), signpost 2a; better-than-training: live grep 2026-11-07 (active mentions in `docs/reference/state-and-phases.md:90-118`, `docs/reference/checks.md:79`, `docs/start/install.md:26,76`, `learnings/LESSONS.md:11,21`; 11 files under `learnings/history/`), the map's warning that removing "herdr" must keep the new skill's name and the mods' `herdr` import.

Pitfalls: closed owner folders are packed into `evidence.tar.zst`; exempting them avoids rewriting archives, but the sweep's grep must run against the working tree with archives excluded or it will never pass. Generated text (release notes under `~/.config/herdr`, old chart records in other repos' `issues/`) is history by the same rule and outside akrogon's tree to rewrite. A lesson retired wrongly (mechanism still true for hc) loses a real guard; the stderr lesson is the case to generalize rather than delete, named in the sweep brief.

Not asked: does "current text" include other registered repos' own docs that describe akrogon behavior (framework's references to herdr panes), or is the wording sweep bounded to repos this epic lands in, leaving each repo to its own later pass?
