# Fork notes, cutover — slot C (Claude Fable 5.1), 2026-11-07

Fact first: the deploy that installs the engine release runs the previous release's code. `deployStage` (`src/self-update.ts:215-288`) builds, flips `current`, reloads systemd and then runs `herdr plugin link <current>/plugin`, throwing when it fails; the doc order is the same (`docs/reference/releases-and-updates.md:42`). An engine release without `plugin/` therefore fails its own deploy at the link step after the flip, with no listener started (the old code knows none), and `akrogon status` shows `deploy failed` until a later success. Twelve repos, zero open leaves today (`ls <repo>/issues/open` over `~/.akrogon/config.yaml` repos); `stopped.yaml` holds one stopped leaf (`framework/relay-obrazac`).

## Q1 Drain

Pick: zero leaves in progress in every registered repo when the engine release deploys, as an operator step recorded in the engine leaf's handoff review (owner, `akrogon status` per repo, done before the merge is approved), plus one small prerequisite leaf, `deploy-on-hc`, landed before the engine: `deployStage` and `install` relink the herdr plugin only while the release has a `plugin/` folder and install, enable and restart the listener unit when the release ships it. The engine leaf lists it in `blocked-by`. The new engine never migrates state: a leaf whose state carries pane ids fails the strict parse with "state predates hc: stop it and hand off again", never dispatches. Reason: the deploy is one flip for all twelve repos at once, so nothing can be half-way; the prerequisite is the standard "deploy the deployer first" step, and it also removes the plugin relink from the engine leaf's deploy path; old seats live in herdr panes that hc cannot see, so there is nothing to carry. Cost: one extra tiny leaf and a `plugin/`-conditional that the sweep deletes; the operator pauses new handoffs until the engine lands (today's `akrogon pause` per repo, or just not handing off: no open leaves exist now).

Rejected: leaves finishing on old herdr (after the flip the old plugin still fires `next`, which is now the hc engine, so old seats would be dispatched into hc or ignored, and two engines on one state is the "both supported" period the intake forbids); carrying leaves over (a pane-to-terminal migration for a one-time event with nothing to migrate today); a land-time guard "no open leaves anywhere" (new machinery for one merge, when the handoff review already records human prerequisites with completion, shapes.md "Known human-only prerequisites have a named owner and recorded completion").

Evidence: operator 2a, 6a, intake "One cutover"; code above and `src/rollback.ts` (runs `install()` of the running release after `flip`); `~/.akrogon/deploy.yaml` (`previous` kept, `replaced` list); `docs/reference/releases-and-updates.md:34-44` (what starts a deploy, held commits); `docs/reference/commands.md:28,30` (`pause`, `stop --all`); engine-shape Taken (listener installed and restarted by install/self-update, restart only after a completed deploy). Practitioner: akka.io "in-flight work during deployment" (pause intake, drain before release), Microsoft runbook-worker drain window, erikevenson migration-cutover (big bang only for small estates with a window, check queue depth first), read 2026-11-07.

Pitfalls: (a) the prerequisite's own deploy runs the oldest code and relinks `plugin/`, which the prerequisite release still has: fine, by construction. (b) Between prerequisite and engine, old herdr keeps working unchanged (relink continues while `plugin/` exists). (c) The engine's deploy under the prerequisite code starts the listener at once; the listener's first `pull --all` and `next --resume` meet zero leaves: proven by the e2e in the tests fork. (d) A leaf handed off between drain check and merge: the review records the check time; the operator step is "no handoff until status shows the engine release".

## Q2 Rollback

Pick: `akrogon rollback` refuses to cross the cutover: when the previous release has a `plugin/` folder (pre-hc) it stops with "previous release runs on old herdr; fix forward". Reason: rollback flips `current` to the old release and then runs the new release's `install()` (`src/rollback.ts:36-37`), which would link the old release's skills, start no plugin relink, and leave the hc listener running `akrogon next` of a release that calls `herdr`; a hybrid that never worked, and old herdr's integrations are being removed underneath it. The window is short by itself: the next merge after the engine makes the engine release the `previous`, and from then on rollback works as today. Cost: one guard, deleted by the sweep once `~/.akrogon/releases` holds no pre-hc release.

Rejected: rollback allowed until old herdr is removed (it produces the hybrid above even while herdr runs, because `install()` is the new one); rollback never, in general (today's behavior stays for hc-to-hc releases; the direction forbids breaking what works).

Evidence: `src/rollback.ts:20-39`, `src/release.ts:86-130` (deploy record), releases doc line 15 (previous kept until the next deploy); practitioner: no source endorses refusing rollback outright; the sources agree big-bang rollback is the hard case and advise fixing forward after verification (AWS cutover guidance "do not finalize on cutover night; run a full cycle first"; privatedevops "big bang is a single attempt"), read 2026-11-07.

Pitfalls: (a) a failed engine deploy (not rollback) leaves `current` on the engine release with `ok: false`: the prerequisite removes the only known failing step; if another fails, the fix is a new commit, as the doc says ("retried at the next trigger"). (b) The guard must read the previous release's tree, not the record: `existsSync(<releases>/<previous>/plugin)`.
