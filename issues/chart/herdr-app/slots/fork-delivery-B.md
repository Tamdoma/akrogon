## Q2. Later task delivery and retained guards

1. Pick: plain hc send without --force or --if idle. A successful SendResult with its turn is a transport-submission receipt for the recorded address; started=true adds evidence of observed activity. Record the receipt against the current seat/phase even when start is false or unknown, so an automatic event pass cannot blindly resubmit it. Keep busy-target refusal, current-instance ownership, required-seat/done/phase guards and the existing informational busy notice. Replace offset proof and prompt-until-working loops with native receipt/turn semantics. Cost: submitted-but-unstarted work needs inspection and an explicit recovery decision, not a guessed success or failure.
2. Rejected options:
   - Require immediate turn advancement for delivery: hc increments turn when status leaves working. A correctly submitted long-running task can remain on its delivery turn.
   - Retry on started=false, timeout or an unreadable reply: input may already be queued/submitted. Inspect first. Native blocked refusal is different from an uncertain post-submission outcome, and never authorizes --force.
   - --if idle on every send: hc distinguishes done from idle. The intake already observed valid completed seats being refused by that exact-state guard. A normal new task still needs the engine's busy guard, whereas a report intentionally sent to its working door is a different permitted interaction.
   - Port session-file byte offsets, parse screen text in engine code, or use elapsed grace as proof that resending is safe. These duplicate weak evidence instead of using hc's receipt. Keep the 60-minute notice informational, without adding polling or treating age as a crash.
3. Evidence:

This is another implementation's contract, not a feature claimed for hc.

## Q3. Silent stop, detection and bounded recovery

1. Pick: treat native turn end as a wake to inspect the expected outcome. For a consultant, the door uses one hc wait for its outstanding children as the safety net, matches actual reports to its recorded exchange/instance, then reads the returned work. A child ending without its expected report triggers inspection. For a leaf, an event wakes the engine/watcher; durable phase/slot state decides progress. Missing work is judged by watch-issues before explicit resumption. Cost: a silent end needs a thinking agent to distinguish unfinished work, a lost callback, a real blocker and an already committed phase. A missing callback alone must not rerun completed work.
2. Rejected options:
   - Accept done/idle or turn advancement as completion: the observed E failure directly disproves it.
   - Repeatedly wait on an already stopped child, poll its file/status, or blindly repeat its original task: these either spin without progress or risk duplicate side effects.
   - A universal Stop hook that forces continuation until a report appears: introduces new harness-specific machinery and can loop through permission, budget or missing-access stops. Reuse the existing door/watcher decision points and explicit own-report instructions.
   - A receipt acknowledgement alone as the cure: E received its task and read a file. Its failure happened after delivery, so changing submission alone cannot remove this case.
3. Evidence:
   - Practitioner: the picklog experiment above observed queued input running later and combined submissions, demonstrating why unknown receipt must be inspected before replay. It does not establish a universal task-completion detector. The vde-tmux API separately exposes run response after run completion, supporting a separate check of the returned work rather than accepting a transport/status receipt as the result.
   - Operator and live local evidence: INTAKE.md:196 explicitly asks to stop recurrence. Its new :200 finding says agy E received the N2 pointer, read one file and ended with only an icon, no file or report; hc returned done/turn 12 and children wait settled. Delivery worked. The missing work/report must be detected by the receiver.
   - Better-than-training, native: `hc schema`, terminal.wait, documents startup/launch-task tracking and that a message interrupts the wait. Process each arriving report, then wait only for still-outstanding work. A completed wait does not itself contain or validate that work.
   - Better-than-training, inspected workflow: `skills/watch-issues/SKILL.md:40` currently sends idle/absent unfinished seats through next, :43 bounds failed recovery using logged cycles, and :44 permits one corrective steer before escalation on recurrence. Do not claim an existing dedicated silent-stop detector or a logged bound for no-phase idle retries: those are not present in the inspected rule. The carry's intended watcher judgment needs to be made explicit in the port.
4. Pitfalls/removals:
   - Complete artifact, failed callback: inspect the expected artifact and current instance/exchange; if complete, ask only for the missing report or record the recovered evidence. Do not repeat its substantive task.
   - Task genuinely unfinished: let the door/watcher send one evidence-based continuation of the same brief, preserving completed work. Record that recovery in the existing chart/session recovery account. If it stops silently again, expose it and follow the existing consultant-drop/notify policy rather than run an endless retry loop. Unknown recovery history or human prerequisites stays notify-only.
   - Turn ended but phase already committed, or a late report arrives: re-read current phase and instance before acting. Do not reopen or repeat an already completed phase, and ignore a replaced instance's late report.
   - Detector never exercised: approved proof deliberately ends a real fixture turn without work/report, then proves the door detects it; separately prove the leaf watcher detects no-phase completion, performs bounded recovery, and stops on recurrence. Also prove a valid blocked question is not treated as a silent success/failure. These checks test behavior, not exact prose, icons or file ordering.
5. Missing question: what existing durable record counts silent-stop continuation across compaction and watcher ticks, and who owns marking a consultant dropped? The present failed-cycle log does not count idle turns without phase. Also settle statusless/backgrounded agents: native waits cannot identify their silent turn ends from status they never report. Any promised support needs a herdr-setup capability proof, not a guessed timeout.

Priority: reject one get with working/turn>=1 as delivery proof, preserve the receipt before recovery, and explicitly judge the completed turn's required work/report.
