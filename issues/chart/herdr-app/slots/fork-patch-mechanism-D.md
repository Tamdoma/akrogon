## Q1. What counts as a herdr-setup patch?

Pick: Only files on public surfaces, in this order: mods, layouts, keys, settings (the app live-applies and preserves personal files across updates, shipped files are moved aside rather than silently edited, clones record `cloned_from`), `bin/` named helpers that speak public commands (`hc`, `hc connect`, `herdr-app do`), and the linked skill. That is the whole definition. Not patches: wrappers that shadow `hc` or `herdr-app` on PATH, direct writes to private files (the stored document file instead of `doc.set`), binary edits, and source patches. A source patch becomes a possible category only if the operator later proves herdr-core/herdr-app source exists to build from and accepts running self-built binaries; that is a new decision, not part of this mechanism, because no such source is on this machine today (fork facts) and both binaries auto-update (the app downloads its own updates and updates the core on first start after, AGENTS.md "Settings"), so a locally built binary would be silently replaced unless updates are also pinned off.
Reason: the three patches already taken (weights by `doc.set`, notices in `session-status`, the herdr skill) all fit the public-surface list, so the narrow definition ratifies what the chart already chose instead of inventing a bigger machine. Named helpers like `bin/herdrapp` are the proven shape: a new name wrapping session selection, linked by install, trivially attributable in an error. A same-name PATH wrapper is the opposite: who hits it depends on each caller's PATH and environment (systemd units pin their own, the app finds its core through the login shell path and settings, mods `exec` a bare name), it must fake version answers and exact JSON/exit-code behavior, and an interposed process endangers caller/parent detection hc uses for sends and children. Cost: some gaps are simply unpatchable under this definition (anything needing a new core or app behavior, like codex's status reporting). Those wait for upstream (Q3) or the feature degrades the way its own fork already wrote down; that is the price of patches that cannot silently break someone else's call.
Rejected: source patches in the old herdr style as the default route (the precedent is real — `/home/ivan/Work/infra/herdrdev/herdr-patched` carries fix commits and a version bump so the patched binary "supersedes upstream installs", git log 2026-11-07 — but it rested on a source checkout of the old herdr, manual rebuilt releases, and an updater model akrogon controlled; none of those three exists for the new binaries). PATH shadowing (above). Treating akrogon-side workarounds as patches (signpost 3 assigns gaps to herdr-setup; akrogon keeps thin call sites so a patch swap touches one function).
Evidence: operator (signpost 3 verbatim, directions: closest to today, fewest parts); better-than-training: herdr-setup `install` and `mods/AREA.md` (link model, clones with `cloned_from`, mods cannot import each other, mod edits do not hot-reload in a session window), AGENTS.md update behavior and shipped-file protection, `git -C herdrdev/herdr-patched log`, `ls -la ~/.local/bin` (both new binaries prebuilt, `hc -> herdr-core`), read/run 2026-11-07.
Pitfalls: (a) A "public surface" quietly stops being one (`hc connect` document shape is opaque JSON with no schema promise). Removed per patch by strict boundary schemas and the Q2 check, never by trusting the shape. (b) Patch creep into `session-status`, itself a clone of a shipped mod: every added handler deepens drift from upstream's status bar. Removed by the existing clone discipline (diff against the shipped copy after updates) and by preferring a named `bin/` helper over a mod handler whenever the caller is a program, as the weights helper already does. (c) A helper invoked by name from akrogon breaks when herdr-setup is not installed on a fresh machine. Removed by install-time presence checks on the akrogon side for exactly the helpers its call sites name (config fork owns the check).
Not asked: does the operator actually have, or expect to get, herdr-core/herdr-app source (a private repo would change the source-patch answer), and if so is running self-built binaries with app/core auto-update off an accepted posture or a last resort?

## Q2. Surviving updates: noticing breakage, retiring on upstream delivery

Pick: Three layers, all existing patterns. First, one herdr-setup manifest (`PATCHES.md` or a section of the README) listing per patch: the gap, the surface it stands on, the akrogon-facing contract, the hc and herdr-app versions it was last checked against, and its upstream feedback (Q3). Second, one herdr-setup check command the operator runs after any app or core update (updates are operator-visible restart offers, so there is a natural moment): `bun test` over the pure modules, `herdr-app check` for each touched mod, a `cloned_from` diff of each clone against the newly shipped copy, and an `hc schema` spot-check that the methods and fields the patches use still exist; `./install` prints a loud warning when the installed versions differ from the manifest's last-checked ones, but still links (files on preserved surfaces are safe to have in place). Third, akrogon's own runtime strictness is the between-checks net: boundary schema parses fail loud, notice files age visibly in `akrogon status`, and a weights failure is a reported degradation, not a silent one. When upstream ships the missing piece, retirement is a herdr-setup leaf that deletes the helper or handler and flips the matching akrogon call site to the native command in the same landing window, marking the manifest entry retired with the upstream version; until that flip, patch and native feature coexist harmlessly because akrogon still calls only the patch's contract.
Reason: nothing on this machine can run code at upstream-update time (there is no public post-update hook in the AGENTS.md surfaces read), so "notice automatically" was never on offer; the honest mechanism is a recorded last-checked version plus a five-minute check at the moment the operator already acts on an update. The clone-diff step is already herdr-setup practice (`mods/AREA.md`), as is the mod test layout (`tests/*.test.js` over pure modules). Cost: an unchecked window exists between an update and the operator's check run, during which a patch can be broken; runtime strictness bounds what that window can silently corrupt (toasts stall as pending files, weights report unequal) rather than eliminating it.
Rejected: nothing until it fails (a stalled notice handler or a renamed schema field would surface as confusing leaf behavior weeks later, against "nothing that works today may break"). Version pinning that blocks updates (refusing security and fix updates to protect patches inverts the dependency; also the app installs a waiting verified update on next launch after a crash, so a pin is not even reliably enforceable). Akrogon's listener running herdr-setup's checks (a systemd service shelling to a bun test suite is a new moving part with mail-no-one output; status surfacing already exists). Auto-retirement when a version number crosses a threshold (version numbers do not say a specific gap closed; the manifest review against upstream release notes does).
Evidence: better-than-training: herdr-setup `tests/`, `mods/AREA.md` clone-update procedure, `learnings/LESSONS.md` (symlinked mod folders do not hot-reload, so a check must run against a copied mod or a fresh window), AGENTS.md update flow and last-good behavior for invalid files (`layout.error` etc., `herdr-app status` surfaces mod errors), identity Taken's schema-pinned test pattern; read 2026-11-07.
Pitfalls: (a) An update lands mid-chart and the session-status clone stops matching a shipped rename, so notices stall while a door runs. Removed by the pending-age visibility from the notices fork and by the guidance, recorded in herdr-setup's README, to run the check at the update restart the app itself offers. (b) `herdr-app check` only loads a mod's initial description (AGENTS.md), so a handler broken only on its event path passes. Removed by Q3's live contract probes in a throwaway session as part of the check for notice/weights behavior, not syntax only. (c) The manifest drifts from reality. Removed by putting contract and versions in one file the check command itself reads (the schema spot-check takes its method list from the manifest), making the manifest load-bearing for the check.
Not asked: who is woken when the check fails — the operator is the only actor in this design, so a failed check after an update simply sits in terminal output; is that acceptable, or should `akrogon status` carry one line ("herdr-setup last checked against hc X, installed is Y") as pure information, never a gate?

## Q3. Upstream reporting and where contracts are tested

Pick: Yes, every patch is reported upstream as a condition of existing. The patch's herdr-setup leaf includes a feedback draft file (reproduction, versions, what the patch does meanwhile), which the operator sends through `herdr-app feedback` (it only drafts; the person sends, AGENTS.md) or consciously declines; the manifest records drafted/sent/declined with dates. The precedent for report quality is on this machine: `herdr-plugins/herdr-registry-durability/REPORT.md` isolates root causes past the seeded symptoms with raw-protocol proof. Contracts are tested on both sides, split by what each side can prove: herdr-setup tests prove its half in isolation (pure-module tests for doc transforms and notice-file handling, `herdr-app check` per mod), and akrogon proves the behavior it depends on end to end (notice file in, deletion-as-shown out; start a consultant column, weights read back equal; `/herdr` loads per harness), run in a throwaway HC_SESSION with its own app home where herdr-setup is linked in, inside the signpost 7a paid-probe budget where a live agent is unavoidable. Akrogon's unit tests fake the contract (tests fork) so the normal suite needs no window.
Reason: a patch with no upstream report is a permanent local fork by default; reporting is what makes "survive updates" a temporary posture instead of an identity, and upstream has a dedicated intake for exactly this. Splitting tests by side keeps each repo's suite honest about what it controls, and matches the notices Taken wording (contract pinned by an e2e test in both repos). Cost: every small patch pays a feedback draft and two test layers, which is real overhead for a five-line mod handler — accepted, because untested patches are how the old skill and script pile accumulated.
Rejected: patch-first, report only if it proves long-lived (the report is cheapest while the reproduction is fresh, and several current gaps, like codex `working` while asking, are only fixable upstream at all). Contract lived only in akrogon's tests (herdr-setup could then break the contract in its own refactor with green tests). Contract lived only in herdr-setup (akrogon would learn at runtime in production leaf work, the most expensive classroom). Copying the old REPORT-only route with no patch (correct for unpatchable gaps, wrong as the default for patchable ones; the report accompanies the patch, it does not replace it).
Evidence: operator (signpost 3, 7a proof budget, 2a e2e before deletion); better-than-training: `herdr-plugins/herdr-registry-durability/REPORT.md`, AGENTS.md on `app.feedback` (draft for the person, never auto-sends) and `herdr-app check`, INTAKE's already-reported codex status gap as the worked example, herdr-setup `tests/` shape; read 2026-11-07.
Pitfalls: (a) The operator never sends drafts, and patches quietly become permanent. Removed only by visibility: the manifest's drafted-not-sent state is printed by the Q2 check, so staleness is seen at every update. (b) E2e tests that need a real window are flaky in throwaway sessions (stale `herdr-app shot` frames behind another window, INTAKE). Removed by asserting on files, `hc` state, and document weights rather than screenshots wherever the contract allows. (c) A patch's contract changes shape mid-flight between repos. Removed by versioning the contract in the manifest entry and landing contract changes herdr-setup-first with backward-compatible readers (notice files already tolerate this: the mod deletes, akrogon folds deletion into records).
Not asked: when upstream fixes a gap differently than the patch (their weights API takes a ratio, ours writes weights), who judges equivalence before retirement — my assumption is akrogon's e2e passing against the native path in a throwaway session, recorded in the manifest, but the fork never names the judge.
