## Q1. First task at start: hc templates or direct `hc run`?

Pick: Direct `hc run <harness argv> "<task>"` for every role. Start then verifies, bounded at 60 s inside the start command: wait until `hc get` shows `working`, or `turn >= 1`, or `blocked`/`error`/exited, and record the observed turn as `prompted` (identity Taken). Timeout, blocked, or a process that is not the harness is reported as started-unproven with the address; the caller reads the screen with `hc read` and never re-sends the first task blind (the task is process argv, so a second copy can only duplicate it once a startup dialog clears).
Reason: templates cannot express akrogon's existing config. Harness argv is built per start from a config template line with `{model}`/`{effort}` substituted per slot, with per-repo seat overrides (`src/config.ts:27`, `src/next.ts:294-302`), and consultants run operator-chosen kind/model argv from the seat record, including agy, which has no `harnesses:` entry. One template file per kind bakes one command (including model, per `hc --skill`); covering slot, repo, and chart variation means generated template files per combination in a machine-global folder, where parallel doors race and stale files accumulate. Direct runs keep one argv source (config for leaves, seat record for consultants) and today's engine shape (start with argv, then prove, `src/next.ts:786-839`). The proof is weaker than template `first_message`: `working`/`turn >= 1` proves the harness began a turn whose only initial prompt is the argv task; it does not prove the text got past a startup popup. Cost: start implements the bounded readiness wait itself (the one place code is allowed), per-kind startup timing must be probed, and leaf env still needs an `env K=V` argv prefix or `terminal.run` env (start-and-pane record), which template commands would not solve either since leaf env values vary per leaf.
Rejected: templates for all starts (above; plus install writing `~/.config/herdr-core/templates/` collides with the operator's own templates, and template body text is merged into the first message, changing prompt content akrogon treats as exact). Templates for leaf seats only, direct for consultants (two start and proof mechanisms; the start command was supposed to exist once). Direct run with a single immediate `hc get` (races startup: turn 0 and no status is the normal first reading, so one get proves nothing either way). Direct run with no verification (intake: a start prompt has sat unsubmitted while the substrate reported success).
Evidence: better-than-training: `hc schema` FirstMessage {sent, started, turn} reported only for template runs and `hc --skill` template section (60 s readiness retry), `hc templates` empty and no templates dir on this machine (run 2026-11-06); `src/config.ts:27`, `src/next.ts:294-302, 786-839`; intake first-task-in-argv 9/9 across kinds and the unsubmitted-prompt incident, read 2026-11-06.
Pitfalls: (a) A trust or setup popup holds the first turn (codex popup swallowed 10 prompts, intake). Removed by the blocked/error branch of the verify plus probe per kind; recovery is keys through the dialog after `hc read`, never a resend. (b) `turn` semantics differ per kind and codex miscounted with `/new` (intake). Removed by probe per kind recording status/turn sequence from start to first idle; leaf/consultant flows never send slash commands from outside (kill-restart replaces them). (c) Slow first paint over 60 s false-fails a healthy start. Removed by probe-set timeout per kind and reported-unproven (not killed) as the timeout outcome.
Not asked: if a template with an empty body works and its `first_message` proof is much stronger in probes, should leaf seats alone switch to generated templates per (repo, slot) written by install, accepting the file management? I say no unless direct proof fails a probe, but the fork should record the trigger for revisiting.

## Q2. Later tasks by `hc send`: proof, blocked, surviving guards

Pick: Keep dispatchSlot's guards, translated. Busy refusal survives: prompt only when the seat's hc status is `idle` or `done`; `working`, `blocked`, and null/unknown all mean hands off, with no attempt counted, mirroring `busy()`/`idle()` at `src/next.ts:213-218, 765`. Plain `hc send` (never `--if`: its values exclude `done`, intake; never `--force` from the engine). Delivered means the send result reports `started` with a turn, recorded as `prompted` with the address, replacing prompt `--wait --until working` plus session-file proof. `started: false` or a refusal records `delivery_error` and `attempts + 1` exactly as today (`src/next.ts:724-758`), and the next pass resettles by turn: if the seat's turn is now past the recorded turn and it is or was working, the prompt landed; otherwise one send per pass, attempts bound unchanged. `observeBusy` survives on hc status with one change: the 60-minute notice (`STALL_MS`, `src/next.ts:220`) accrues on `working` only, since `blocked` is already surfaced by herdr-app and null status (backgrounded Claude) must neither accrue nor clear. Session-file proof is deleted with `src/session-file.ts`: hc gives no session id, and the file was only reliably resolvable for pi-shaped refs anyway (`src/session-file.ts:11-31`). For consultants the same send is plain skill text: a blocked refusal means the door reads the screen and surfaces the question to the operator, never `--force` (antigravity takes forced Enter as menu choice 1, intake).
Reason: this is today's state machine with turn substituted for session-file bytes, so timing records, grace (`PROMPT_GRACE_MS`, 2 min), attempts, and watcher behaviour carry over. Turn proof is weaker than exact-text-in-transcript: it proves a turn began after our send, not which text began it; an operator typing in a leaf pane could in theory fake it, which is already outside the contract (leaf panes are engine-driven; the ownership check and status surfaces show it). Cost: one extra `hc get` resettle path and per-kind turn probes, and codex `working`-while-asking still accrues stall time and will eventually post a busy notice for a waiting question, as today; judging that belongs to the watcher by screen, not the engine.
Rejected: trust `started: true` alone (intake records started lies). Waiting for turn end before recording delivery (conflates delivery with completion; a long turn would look undelivered and be re-prompted). Keeping session-file proof by discovering transcripts per harness (session-id fork rejected four format bets). `--if idle` as the busy guard (refuses `done` seats, which are exactly the seats waiting for their next task). `--force` through blocked (answers dialogs blind).
Evidence: better-than-training: `src/next.ts:213-221, 724-839`, `src/session-file.ts`, `hc send --help` (`--if` values, `--force`), live send results this session (`{"started":true,"status":"working","turn":…}` on every `hc send t15`), intake send findings (done seats, force on blocked, codex turn counting), read/run 2026-11-06.
Pitfalls: (a) Race between the guard's `hc get` and the send: seat turns `working` in between and the send lands mid-turn as a queued message. Removed by recording the send's returned turn: if it is not a new turn past the guard reading, treat as not delivered and resettle next pass instead of believing it queued. (b) A seat that ends its turn by printing a question (pi does this, intake) looks idle and gets re-prompted over its question. Removed only partly by design: skills must route questions through phase-failed-blocked or the question tool (blocked), and the watcher's screen judgment sees the printed question; the engine alone cannot tell it from a silent stop without reading screens, which engine-shape forecloses. (c) Resettle across a seat restart compares turns of different incarnations. Removed by identity's pairing of turn with the current address; a new address means not prompted.
Not asked: should the door's consultant prompts record turn/address per exchange in seats.yaml (the consultant mirror of `prompted`), so a mid-chart replacement door can tell which exchanges a restarted consultant actually received?

## Q3. Silent stop: catch and recover, leaf seats and consultants

Pick: Success evidence is artifacts, never turn end. Leaf seats: on the listener's turn-end wake, the pass finds the seat idle/done, the phase unmoved, the seat not in `done`, and the seat's turn past the recorded `prompted` turn; that is one silent stop. The engine re-prompts as today (after grace an idle unmoved seat is prompted again, `src/next.ts:765-839`) but counts silent stops per seat per phase separately from delivery attempts, since successful delivery resets attempts to 0 (`src/next.ts:711`) and would erase the count. At two silent stops the engine stops re-prompting, records them (timing outcome and status), and leaves the seat idle for the watcher to surface to the operator. Consultants: the door collects by artifact, not by wait: a seat counts only when its return file exists at the brief's path and its report came from its current address. A finished wait with a seat done/idle and no file is a silent stop: the door reads its screen, re-sends the brief pointer once with the return path and report line repeated in the send text, and waits again; a second silent stop drops the consultant for the session under the existing drop rules, recorded as silent-stop.
Reason: the live case proves delivery and completion are different facts: agy slot E received the brief, read one file, ended its turn printing only "⚙️", and `hc wait --children all` returned all-done with the report missing (INTAKE 2026-11-06). Leaf infrastructure already re-prompts unmoved idle seats; what is missing is the bound, because today that loop is unbounded and only watcher judgment or the operator breaks it. Two re-prompts matches the watcher's existing two-unproductive-cycles bound (watch-issues SKILL.md, failed-otherwise), keeping one recovery philosophy. For consultants nothing catches it today except the door's own bookkeeping, and the artifact rule is the smallest change: the door already knows each return path. Cost: a new per-phase silent-stop count in leaf state (or a timing-derived count, state is simpler), a watcher-facing status surface for "prompted, silent ×2", and door exchanges take one extra wait round when a seat silently stops. Nothing can stop a harness from ending a turn empty; this bounds the damage and makes it visible per kind, so a repeatedly silent harness can be swapped by config.
Rejected: treat turn end plus idle as completion and advance (the E case would silently lose the work). Re-prompt unbounded as today (a paid loop; each re-prompt is a real model turn). Immediately failing the leaf on first silent stop (one empty turn is a known transient; the live E seat completed later rounds after being re-prompted). `hc wait` with a budget as the consultant catch (the wait cannot tell done-work from done-nothing; the file check can). Reading screens in the engine to judge why a seat stopped (engine-shape keeps the engine off screen text; that judgment is the watcher's and the door's).
Evidence: operator (chart the silent-stop fix, INTAKE source 2026-11-06 after E); better-than-training: live finding on `ak-slot-e` (INTAKE, read 2026-11-06), `src/next.ts:711, 765-839` re-prompt and attempts reset, watch-issues SKILL.md two-cycle recovery bound; model-knowledge: terminal-driving tools (expect-style, tmux send-keys automation) verify by screen or side-effect, never by input acceptance alone. No practitioner source found (no web from this seat).
Pitfalls: (a) A seat that did the work and moved `phase` in the same turn is miscounted if the pass reads state before the phase commit lands. Removed by phase-runs-next (engine-shape Q3): the commit itself runs the pass, and the silent check requires phase and `done` unchanged on a fresh state read. (b) A consultant writes the file but its `hc send` report fails (sandboxed codex socket, intake). Artifact rule covers it: file present counts, report missing is noted, not a silent stop; the reverse (report without file) is judged by reading the seat before any re-send. (c) Re-sent brief pointer makes a consultant redo finished work into the same return path. Removed by the screen read and by briefs already naming one return path; overwrite is the existing contract. (d) The two-stop bound interacts with the watcher's Waiting rule, which runs `next` for idle unfinished seats. Removed by the bound living in dispatch itself: `next` at the bound records and does not prompt, so the watcher sees a stable non-progressing seat to notify on, not a fresh prompt each fire (watcher fork carries the text).
Not asked: should a leaf seat's silent-stop count survive a watcher recovery (`phase` back to the failed phase resets attempts today, `src/phase.ts:210`)? My assumption: reset on any phase move, since a new phase is a new task.
