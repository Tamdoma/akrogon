## Q1. What wakes the watcher
1. Pick: both. The 20-minute cron stays exactly as today (`skills/watch-issues/SKILL.md` Invocations: `*/20 * * * *`, prompt `/watch-issues tick <root>`, 7-day expiry, operator-created). Added: the listener sends `hc send <watch terminal> "/watch-issues tick <root>"` after an event the watcher acts on: a leaf seat terminal `finished` or lost (crash), a leaf seat `status` blocked, a pass that moved a leaf to `failed` (silent-stop bound, delivery errors), and a pass that showed the 60-minute busy notice. The watch terminal is found by label: the skill's start step runs `hc label $HC_TERMINAL_ID akrogon.watch=<repo>` and stop removes it (`akrogon.watch=`); the listener runs `hc ls --json --label akrogon.watch=<repo>` and sends to each match, none means nobody is watching, as today without a cron. The message text is the job prompt itself, so one skill rule covers both wakes: "a cron fire or an `<hc>` message carrying `/watch-issues tick <root>` runs one check; several queued ticks run one check". Reason: a crash today waits up to 20 minutes; with the wake it waits one turn of the watch session, through hc's own message path (the operator's direction), with no new state and one `hc send` in the listener. The cron stays because the Busy rule watches a seat that emits no event (a loop is a `working` seat for an hour) and because a dead listener must not silence the watch; both practitioners above keep a timed check for the same reason. Cost: an occasional double check when a cron fire lands near a wake; checks are idempotent (observe, then guarded `next`/`phase`).
2. Rejected: cron only (today's gap: a crash at minute 1 waits 19 minutes, against "no waiting"); events only (loops emit nothing, listener death is silent, and the 7-day cron is the only thing that checks the listener itself); the listener running the judgment (engine-shape 1a: judgment from skill text, not code; the Busy rule reads screens and logs); a wake on every turn end (the engine's `next` already handles turn ends; the watcher would mostly read and do nothing).
3. Evidence: operator, signposts 4a and the 2026-11-06 directions; better-than-training, `skills/watch-issues/SKILL.md` Invocations/Judge/Never, `hc send --help`, `hc events --help` (`--label`, AND-only), `hc ls --help`/`hc label --help`, `hc --skill` "Talk, wait and collect" (a message typed into a working terminal is held, then delivered), engine-shape Taken Q2, 2026-11-06.
4. Pitfalls: the watch session is mid-tick when the wake arrives (removed: hc pastes once the input is quiet and Claude runs it as the next turn; the collapse rule makes repeats cheap); the watch session is gone (removed: a finished terminal is not in `hc ls`, so no send; `akrogon status` already shows listener liveness and gains the watch terminal's address or "no watch" from the same label read); two watch terminals for one repo (removed: the skill's start step refuses when `hc ls --label akrogon.watch=<repo>` already lists a live terminal, the same one-match rule it applies to cron jobs); a wake sent from the listener service carries no `from` terminal (removed: the rule keys on the text, the job prompt, not on the sender); a wake arriving for a paused repo (removed: today's paused rule, the check observes nothing).
5. Question: does the operator want the wake for `blocked` seats, which hc also surfaces as attention in herdr-app? I would include it, since the watcher's needs-you notice is today's path.

## Q2. Observe and act on hc
1. Pick: `observe.ts` keeps its line format and replaces `herdr agent list` by one `hc ls --json --label akrogon=1 --label akrogon.repo=<repo>` in the resolved session (status word, turn, labels, pid, address per terminal); seats come from each leaf's state addresses (identity Q2), status is hc's `status.state` (`-` when null), `busy=` from `busy_since` as today, `log<seat>=` from the `akrogon.session` label (session-id: a transcript path, `-` when absent), `session=` prints the hc session name. `log-tail.ts` is unchanged (it takes a path). Read: `hc read <t> --lines 80` for idle seats, `hc read <t> --lines 0` for working ones (hc returns only the screen while working anyway). Stop and resteer: `hc interrupt <t>` replaces `agent send-keys esc` plus `agent wait --timeout 10000` (it presses the stop key and reports the effect within 10 s), then one `hc get <t> --json` confirms idle at the same address, then `hc send <t> "<evidence>; the brief wants <target>; next: <step>"`. `esc` by `hc keys <t> esc` only where a probe shows `interrupt`'s stop key is not what that harness needs. Notices: `akrogon notice "<repo>/<slug> needs you" --body "<body>" --sound request` per the notices Taken. `akrogon next`/`phase` unchanged, still never under a Bash timeout. Never list: "kill an agent process" stays as no `hc kill`; "close a pane" becomes no `terminal.park`; "esc twice" becomes no second `interrupt`.
2. Rejected: `hc get` per seat instead of one `hc ls` (N calls for one list; `ls` returns the same records); judging from `hc events` streams inside the tick (a tick is one observation, not a subscription; events belong to the listener); dropping the log tail (session-id Taken keeps the path, the Busy rule's loop evidence depends on it); `hc send --force` to a blocked seat (the Never list's "answer a seat").
3. Evidence: better-than-training, `skills/watch-issues/scripts/observe.ts:6,90-107,211-245` (herdr list, session line, entries map), `log-tail.ts:425-426` (path argument), `hc interrupt --help` (stop key, 10 s effect watch), `hc keys --help`, `hc read` semantics in `hc --skill` "Talk, wait and collect" (working: screen only), `hc schema` Terminal (`status`, `turn`, `labels`, `pid`), session-id and notices Taken, 2026-11-06.
4. Pitfalls: `hc interrupt` presses a stop key that does not fit a harness (probe P1 per kind: interrupt a working seat, status goes idle, input empty); a steer sent to a seat whose address changed since observe (removed: the `hc get` before the send compares the address recorded in state, identity's ownership check); `hc ls` listing another repo's seats (removed: the two labels AND together; `akrogon.repo` is set at start); a `done` seat read as idle (removed: today's `idle(pane)` already counts `done`, `src/next.ts:216-218`, observe keeps the word).
5. Question: none.

## Q3. Where it runs, who starts it
1. Pick: as today, an operator-started Claude Code session, in an hc terminal of the repo's herdr-app session so it has `HC_TERMINAL_ID` to label and to receive wakes; the skill refuses to start outside hc the way it refuses without CronCreate ("This watch needs an hc terminal"). After a reboot the cron and the session are gone, as today; the operator starts it again. The listener never starts it. Reason: "started and stopped only by the operator" is the skill's contract and 4a keeps the workflow; a listener-started watch is a paid agent nobody asked for, and the label makes its absence visible in `akrogon status` instead. Cost: an unattended machine that reboots has no watcher until the operator returns, as today.
2. Rejected: the listener starting a watch session at boot or on the first event (new feature, paid, and the operator's "started only by the operator"); the watch as a non-agent systemd timer running `akrogon` commands (the Judge rules need an agent reading screens); running outside herdr-app in a plain hc terminal (works: wakes need hc, not a window; the operator may do that, it is still an hc terminal).
3. Evidence: operator, skill description "started and stopped only by the operator"; better-than-training, `SKILL.md` Invocations (CronCreate gate), INTAKE "Why it stopped" (`HERDR_ENV=1` gate replaced by `HC_TERMINAL_ID`, map item 10), 2026-11-06.
4. Pitfalls: the label survives the Claude session ending inside a kept shell (removed: `/watch-issues stop` removes it, and a terminal whose program ended is not live in `hc ls`; a kept shell is, so the start step's one-match check names it and the operator kills it); the 7-day expiry outlives the listener's knowledge (removed: nothing in the listener depends on the cron).
5. Question: should `akrogon status` show the watch's last tick time? It would need the skill to write a line somewhere; I would not add it now.

Probes: P1 `hc interrupt` per harness kind; P2 a leaf seat killed by hand wakes the watch within one turn and the tick restarts it through `next`; P3 a wake during a running tick runs one more check after it, not two; P4 a stopped watch (label removed) gets no sends.
