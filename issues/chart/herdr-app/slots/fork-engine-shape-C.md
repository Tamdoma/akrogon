## Q1. Does 1a bind the engine's own hc calls?

1. Pick: no. 1a splits steps an agent performs (door, consultants, watcher: plain `hc` in skill text) from steps no agent is present to perform. The engine has no agent in the loop: `dispatchSlot` composes the prompt from `routing[phase].skill`, slug, slot, phase and leaf path (`src/next.ts:974-977`) and delivers it; nobody else can type that `hc send`. So the engine keeps a thin hc client with exactly the verbs it needs (`run` with the first task, `send`, `get`/`ls`, `kill`, `label`), and the start helper is the one shared entry for `run`. Cost: more hc code than the literal sentence, so the fork must record this reading as the operator's.
2. Rejected: (a) literal 1a, engine prompts come from skill text (seat A's skill ends with `hc send <next seat> "<prompt>"`). It moves prompt composition, the busy and `PROMPT_GRACE_MS` guards and `delivery_error` recording (`next.ts:704-776`) into prose four harnesses must follow, changes the workflow (carry), and still needs code to start B with the first task. (b) A resident agent as engine: costs tokens for a loop that is deterministic.
3. Evidence: operator tier, signposts Taken 1a and "workflow unchanged" (forks/signposts.md, 2026-11-06); practitioner tier, `hc --skill` "Put the first task in `run`: a send to a booting agent can be dropped" and "hc itself notifies you when a child cannot report" (both describe an agent parent, not a daemon); code tier `src/next.ts:974-980` (prompt built by code), `:704-713` (busy and grace guards).
4. Pitfalls: engine hc verbs sprawl back to the 20 old call sites. Removed by a done-criterion on the engine leaf: one module exports the hc client, `grep -rn "'hc'" src` matches only it, and the verb list is in the leaf's design.
5. Question not asked: may the engine read `hc read` (screen text) at all? Today `log.ts` and watch-issues read screens; I would forbid it in the engine (status words only, manual: "Do not guess status from screen text") and leave screen reads to the watcher.

## Q2. What wakes the engine, who installs and restarts it?

1. Pick: one systemd user service `akrogon-events.service` per hc session, installed by `akrogon install` the way `akrogon.slice` already is (`src/install.ts:36-39`) and restarted by `self-update`'s `reload` step in place of `herdr plugin link` (`src/self-update.ts:276-288`). It runs `akrogon pull --all` and `akrogon next --resume` first (the catch-up pass), then follows `hc events --json --label akrogon=1` and runs `akrogon next` for the owner of each `status`, `turn` or `finished` event, single-flight with coalescing (one dirty flag, rerun once). `Restart=always` with a short backoff; a stream end (core restart) is an exit, so systemd restarts it and the catch-up pass covers the gap. `HC_SESSION` comes from akrogon config (fork identity decides the key). Cost: a resident process the operator must see in `akrogon status` (listener liveness line), and a unit file in the repo.
2. Rejected: (a) herdr-setup installs or restarts it: the unit runs akrogon's binary through `~/.akrogon/current`, so its lifecycle is akrogon's deploy, not a herdr-app patch; herdr-setup's `install` links app files only (`herdr-setup/install`). (b) A mod: dies with the window; the old plugin ran with the server. (c) Nothing resident, seats self-advance: no crash or exit signal (4a). (d) A systemd `.path` unit on hc state files: hc exposes a socket, not files; `hc events` is the push surface.
3. Evidence: code tier `plugin/herdr-plugin.toml` (startup pull and resume, four events), `src/install.ts:37`, `src/self-update.ts:283`; command tier 2026-11-06: `hc events --json` first prints a full snapshot then one JSON-RPC line per change (`type` seen: `title`, schema lists `status`, `turn`, `finished`, `labels`, `cwd`); `hc events --json --label akrogon=1` printed nothing in 3 s with no matching terminal (filter works, low confidence that a snapshot arrives once one matches). `hc events --help`: filters only, no cursor or replay. The core runs as transient `hc-serve-<id>.service` (systemctl list), so no stable unit name to `After=`; the listener must tolerate an absent core. Practitioner tier: docker-gen regenerates all configs when its events channel is reattached "to avoid missing events in between" (nginx-proxy/docker-gen PR #156, read 2026-11-06); Kubernetes informers list, then watch, then resync (model knowledge). Terminal-multiplexer orchestrators found (tmux `wait-for` with a Stop hook, crystl.dev and developertoolkit.ai, 2026-11-06) are agent-to-agent rendezvous, the hc equivalent of `hc wait`, not a resident engine; none runs a job engine off multiplexer events.
4. Pitfalls: P1 missed event during a listener restart, removed by the catch-up pass and `next --all` being a full re-read (it already is, `next.ts:1665-1700`). P2 the listener's `hc` starts its own core because `HC_SESSION` is unset in the unit (intake 2026-11-05 codex case), removed by a probe: `systemd-run --user -E HC_SESSION=infra hc ls` reaches the running core. P3 event storm (title events every spinner tick) runs `next` in a loop, removed by filtering on `status`, `turn`, `finished` only and coalescing. P4 deploy flips `current` while the listener runs the old binary, removed by `systemctl --user restart` in the reload step and a test that asserts it. P5 label filter never matches because the start helper forgets the constant label, removed by the start helper owning labels (settled) and a test.
5. Questions not asked: one listener per machine following every session, or one per hc session? With spaces per repo in one session (fork identity lean), one unit is enough; a per-session unit needs a template `akrogon-events@.service`. Does the operator want the listener visible in herdr-app (a terminal with a pane) or silent under systemd? I lean silent, with liveness in `akrogon status`.

## Q3. What advances a leaf on success?

1. Pick: the same flow as today. The seat runs `akrogon phase` in its turn; the move commits and wakes only merge work (`src/akrogon.ts:76-96`, `mergeWake`); the seat's turn ends; hc emits the seat's `status` change (`idle` or `done`); the listener runs `next`, which prompts the next seat (`dispatchLeaf` to `dispatchSlot`). `akrogon phase` does not dispatch. Cost: advancement waits for the running seat's turn to end, as now.
2. Rejected: (a) `phase` dispatches the next seat directly: when the next seat is the same terminal (plan to implement is A to A), `hc send` pastes a prompt into a still-working agent, which queues it mid-turn (manual: send "waits for a person to pause"), a behavior the old flow never had and the busy guard (`next.ts:704`) exists to prevent; when the next seat is the other terminal it is faster by one turn-end but splits advancement across two paths, so a crash in either leaves no single place to reason about. (b) Both: adds the mid-turn case for no gain the operator asked for.
3. Evidence: operator tier, "I don't want to change how the workflow is done" and "no polling" (engine-shape Carries); code tier `src/akrogon.ts:79-96` (phase wakes merge only), `src/next.ts:1740-1775` (status event to `dispatchLeaf`), `:704-713` (busy and grace guards), `observeBusy` `:223-266` (stall notice on long `working`). hc manual: `status` is `idle`, `working`, `done`, `blocked`, `error`; `done` = finished while unseen. The listener must treat `done` as not busy (today `idle(pane)`), and `blocked` as not idle.
4. Pitfalls: P6 codex reports `working` while asking a question (intake 2026-11-03), so no advancement event arrives and `STALL_MS` would fire a busy notice at 60 min; removed by the watcher judging screen and log, and the engine never reading duration as a stall for codex until hc reports `blocked` for it (herdr-setup feedback item). P7 a backgrounded Claude seat reports `status: null` (intake 2026-11-04); removed by the rule "unknown status means hands off" and an operator step: no `/background` in seats. P8 `done` is reported only once and flips to `idle` when the operator looks; a listener down at that moment sees neither, removed by the catch-up pass reading current status, not events. P9 a seat exits (closes its harness) after `phase`: the `finished` event reaches `next` as `pane_exited` does today; removed by mapping `finished` to the same handler and a probe that `hc events` reports `finished` on exit and on `hc kill`.
5. Question not asked: should `akrogon phase` print the next step it expects (seat and phase) so the operator reading the seat's pane sees why nothing happened yet? Cheap, no workflow change, helps the watcher's judgment.
