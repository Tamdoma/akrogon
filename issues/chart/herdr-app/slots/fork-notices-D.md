## Q1. Which channel shows a notice?

Pick: akrogon's existing `tasks` mod, extended with a notice drain. One akrogon enqueue function (engine-internal, exposed to agents as one `akrogon notice` CLI verb for phase/watcher skill-text callers) writes the notice as a file; the tasks mod follows that folder with `watchFolder`, posts `notify()`, and acks by file (Q2). No second mod.
Reason: the toast must appear where the operator now works, with herdr-app's own look, click, and sounds (Q3), and the tasks mod is already akrogon's installed presence in that window (`src/install.ts:29-48`), already `exec`s akrogon and follows folders without polling (`herdr-app/tasks/main.js:116,173`, `watchFolder` at `herdr.d.ts:403`). It is one mod to install, test, and keep working per session. Cost: notices become a small file protocol with a mod lifecycle precondition: a tasks copy must be alive in the session's layout for toasts to drain (a copy lives while its block is in the layout, shown or not, AGENTS.md "Mods"); with no copy or no window, notices wait as pending files.
Rejected: a herdr-setup mod (the protocol, call sites, records, and tests are akrogon's; splitting the poster into herdr-setup adds cross-repo version skew for zero user gain — signpost 3 covers gaps in hc/herdr-app, and `notify()` is a public mod API akrogon already uses from its own mod). A second akrogon mod just for notices (another lifecycle to keep present in layouts; tasks is already there). `notify-send` (leaves herdr-app's toast/click/sound system, click cannot focus the seat's pane, sound is notification-daemon hints, and engine contexts that cut the session bus would fail sends that work today; fewest parts but a visible behavior change). Something hc carries (a label or event reaches programs and the listener, not the operator's eye; `hc send` to the operator's terminal types into their agent's input, which is communication to the wrong reader). Deriving notices inside the mod from `akrogon status --json` state (the four notices are events with once-per-episode records; a state-derived mod re-toasts on every reload and layout switch and must reimplement each caller's dedupe).
Evidence: better-than-training: `herdr.d.ts:365-375` notify (title, body, level, timeout, icon, action; shown by the toast mod, click runs the action), `herdr.d.ts:39-41` playSound, `herdr-app commands` has no notification command (checked 2026-11-06), `src/install.ts:29-48`, `herdr-app/tasks/main.js`, call sites `src/next.ts:249-262, 1043-1080`, `src/verify.ts:325-360`, `src/phase.ts:98-122`; operator directions (behavior like old akrogon, no polling, fewest breakable parts).
Pitfalls: (a) Two windows or two tasks copies drain the same spool twice. Removed by per-session spool (in the resolved session's app home, never inside the symlinked mod folder, which is the release tree) plus atomic claim-by-rename before posting. (b) The mod must learn its own app home; the session-to-home convention is herdr-setup's and `default` has no sessions folder (start-and-pane correction, config fork). Removed by probe: from a mod in a named session and in default, `exec` sees the right `HERDR_APP_HOME`. (c) Layout without tasks silently stalls all notices. Removed by `akrogon status` showing pending notice count and oldest age, so a stalled drain is visible like a dead listener.
Not asked: when herdr-app is closed entirely for days, should anything reach the operator out-of-app (desktop), or is queued-until-open the correct equivalent of old herdr with no client attached? My pick assumes queued.

## Q2. Hand-off and learning it was shown, including window closed

Pick: A file spool with ack files, reusing today's record shapes. Enqueue writes one JSON file atomically (tmp plus rename) to `<session app home>/akrogon-notices/pending/<id>.json` holding title, body, sound, level, optional seat terminal for the click action, and a deterministic id per notice episode (busy: repo/slug/seat/busy-since; failed: repo/slug/failure time; merged: repo/slug/merge stamp; verify: run id). Enqueue returns `pending` at once; callers record exactly that (`busy_notified` at enqueue so no duplicate, verify's existing `notice: pending` reservation, phase `delivery: pending`). The mod claims by rename, calls `notify()` (returns an id) plus `playSound` per Q3, and writes `shown/<id>.json` with reason `shown`, or `error` with detail if posting threw. Engine passes reconcile acks into the existing records (verify run `notice`, failure `delivery`) and delete acked files; an `error` ack is retried by the same next-run paths that retry today, re-enqueueing the same id, and a watcher notice with an id already pending or acked is a no-op. Window closed: files wait in pending; the first tasks copy to start drains them, and the engine deletes a pending file when its condition has cleared before being shown (busy seat went idle, failed leaf recovered), which old synchronous `show` never needed.
Reason: this is the only hand-off that preserves today's shown/pending/error records without polling anyone: the mod is woken by `watchFolder`, the engine learns on its next event-driven pass, and verify already models exactly this two-step (pending reservation, then reason-or-error replacement, retry on later runs). Synchronous shown is impossible through mods: `nextCommand` delivers a bare string to shown copies with no reply channel to a CLI caller (AGENTS.md "Mods"). Cost: shown becomes eventually-known, so `phase`'s follow-up can no longer fail a committed move because the toast failed (`src/phase.ts:118-134` today) — strictly fewer failure paths, but a stated behavior change; and delivery is at-least-once if the mod dies between `notify()` and its ack write.
Rejected: shared state via `shared.json` (the app owns and rewrites it; engine writing it is editing a private file, with no ack direction). Mod `exec`s a new `akrogon notices` command on a timer (polling, and the spool watch already wakes it). Fire-and-forget with records dropped (breaks verify's retry-until-shown and the watcher's `delivery != shown` re-show rule; notices silently lost while the window is closed). Engine waits inside the notice call for an ack file (a timed wait standing in for a signal, blocked on window state, against the no-waiting direction; callers in dispatch would stall passes).
Evidence: better-than-training: verify's pending/reason/retry records (`src/verify.ts:325-360` and AREA.md run-record description), `src/phase.ts:98-122` delivery, watch-issues SKILL.md:42 re-show keyed on `delivery`, `watchFolder` semantics (`herdr.d.ts:396-403`: changes since the last call return at once, none missed), all read 2026-11-06.
Pitfalls: (a) Crash between claim and ack strands a file in claimed. Removed by the mod re-draining claimed files at init (accepting at-least-once duplicates over loss). (b) A burst of stale toasts when a long-closed window opens. Removed by the condition-cleared deletion above plus ack reason `expired` if the notice's own record no longer wants it; verify notices persist until shown, as today. (c) Ack reconciliation races a retry that re-enqueues the same id. Removed by idempotent ids: enqueue is create-if-absent across pending and shown. (d) `notify()` returns an id even if the operator replaced the toast mod with one that shows nothing. Accepted: shown means posted to the app's notification surface, the same meaning old `shown` had inside herdr.
Not asked: does `busy_notified` still mean "the operator was told" when it now records enqueue time? My pick redefines it as queued-or-shown; if the operator wants the old meaning, the ack reconcile must be what sets it, and duplicate suppression needs the pending file check instead.

## Q3. Sound and click actions

Pick: Both stay, mapped onto the mod APIs. Sound travels in the spool file exactly as call sites pass it today: `request` → `playSound("blocked")` (the attention sound, honoring the operator's `settings.json` replacements), `done` → `playSound("done")`, `none` or absent → silent. Titles and bodies are byte-for-byte today's, including merge's `next: akrogon phase <slug> merge` body. Click: where the notice names a seat terminal (busy, failed, merged, watcher needs-you), the toast's action runs `agent.focus`/`pane.focus` for that terminal; repo-level notices (main red, merge slow) get no action. This is the one herdr-app improvement over old `notification show`, which had no action argument (`herdr notification show --help`: title, body, position, sound only).
Reason: `notify()` has no sound field, but mods carry `playSound("done" | "blocked" | mp3)` (`herdr.d.ts:39-41`), and old herdr's sound values are the same families (`none|done|request`), so the mapping is one line per notice and verify's deliberate silence survives. The toast mod already runs `action` on click and dismisses (`mods/toast/main.js:17-20`, read 2026-11-06), so focus-on-click reuses shipped behavior and aligns with the board-focus direction, while the text an operator reads without clicking is unchanged. Cost: the mod must know sounds the operator configured only by the done/blocked names (no `request` sound name exists in herdr-app; if the operator wants a distinct request sound it becomes an mp3 path in settings, an operator step), and a clicked stale toast may focus a terminal whose leaf has moved on.
Rejected: silent toasts for everything (loses the request/done distinction callers deliberately pass; main-red silence was chosen against request elsewhere). Desktop sound via a separate player exec (bypasses the app's sound settings and mute behavior). Click that runs the suggested command (the merge body names a step for the operator to run; executing `akrogon phase` from a toast click would cross from notice into action the operator did not take in a terminal — focus only, never run work). Herdr-app's own agent done/blocked sounds as the whole story (they fire per agent status, not per akrogon episode; main red and merge slow have no agent).
Evidence: better-than-training: `herdr.d.ts:39-41, 365-375`, `mods/toast/main.js`, `herdr notification show --help` (run 2026-11-06), call-site sound values (`request` at `src/next.ts:1055-1056`, `src/phase.ts:112-113`; `none` at `src/verify.ts:340, 353`; absent at `src/next.ts:249-256`).
Pitfalls: (a) The busy notice passes no `--sound` today; old herdr's default for an absent sound is unverified, so my silent mapping may change what the operator hears hourly. Removed by a one-shot human probe against the old herdr in a scratch session before old herdr is removed. (b) `playSound` after a long-closed window bursts sounds for drained toasts. Removed by design: sound only when the notice was enqueued recently (its file timestamp), toasts still post silently when stale. (c) `agent.focus` on a terminal in another session's window (the toast lives in the repo session's window, so same-session by construction of the per-home spool).
Not asked: toast timeout and position: old herdr took `--position`; no call site passes it, and `notify()` offers `timeout` instead. I assume the toast mod's defaults, but the operator may want failed/needs-you toasts to persist until clicked rather than time out.
