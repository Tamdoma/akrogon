# Fork notes herdr-skill: slot D

External practitioner sources: none reachable from this seat (local read-only commands only, no web reading of harness docs). Harness behavior below is from installed skills and configs on this machine, read 2026-11-07, and my own session as a pi agent with this skill list loaded.

## Q1. Shape

Pick: A small owned `SKILL.md` (front matter with only `name: herdr` and a trigger-rich `description`, body roughly 40 lines). The body's first step checks `HC_TERMINAL_ID` is set, then routes: coordinating terminals and agents means run `hc --skill` now and follow it; changing the window means `herdr-app --skill`, then `$HERDR_APP_HOME/AGENTS.md` (default `~/.config/herdr-app/AGENTS.md`) and `herdr-app commands`; `hc <command> --help` beats memory. The body itself carries only the stable facts an agent needs before that first read: your address is `$HC_TERMINAL_ID`; terminals you start are your children and report to you; `<hc from=...>` messages are terminal reports, not the operator; report to your parent with `hc send` when a task says to; only your own sends to yourself arrive unwrapped, so a slash command sent from another terminal does not execute; codex needs `--no-daemon`; never `hc server stop` unsasked; the old `herdr` binary and `HERDR_ENV` are legacy and not this system.
Reason: herdr-app's own guide funnels to exactly these pointers (`~/.config/herdr-app/AGENTS.md:932-936`), and the manuals are printed by the same binaries the agent then runs, so they cannot drift from the installed version the way a copied skill can. This is also the only shape of the three that stays correct across an app or hc update with no refresh step: AGENTS.md is rewritten every start anyway (AGENTS.md head), and `hc --skill` tracks hc. Cost: the agent spends one command and some context on first use (260 lines for `hc --skill`) and could skip the read; the body's routing and its short fact list are the counterweight, and direct `/herdr` invocation still loads only the small body.
Rejected: plain symlink `SKILL.md -> AGENTS.md` (every working skill on this machine is discovered by front-matter name and description; AGENTS.md has none, so at best it is undiscoverable, at worst discovered with no trigger description, and loading it injects 951 lines of layout and mod authoring for an agent that only needed `hc send`; a probe could prove a given harness tolerates it, but even then it teaches the wrong layer first). Generated copy refreshed on update (a generator plus a refresh trigger that must itself survive updates, stale between refreshes, and still the wrong size for a trigger-loaded skill; the binaries already generate this text on demand). Inlining the whole `hc --skill` text into the body (same staleness, and hc on other machines via `--on` may be a different version than the text).
Evidence: operator (signpost 5a: content from herdr-app's AGENTS.md, symlink proposed as a question, not a settled mechanism); better-than-training: AGENTS.md:932-936 and its size (951 lines, `wc -l`), `hc --skill` 260 lines, front matter on every installed skill (`~/.claude/skills/herdr/SKILL.md`, `skills/chart-issues/SKILL.md:1-4`, agy's `~/.gemini/config/skills/diagnose-crash/SKILL.md`), read 2026-11-07.
Pitfalls: (a) A description that reads like the old skill's ("only when the user explicitly mentions Herdr... Do not use merely because a task could benefit from delegation", current `~/.claude/skills/herdr/SKILL.md:3`) actively suppresses triggering; removed by writing the new description against the Q3 triggers and probing them. (b) Extra front-matter fields can fail strict loaders in some harness; removed by keeping exactly `name` and `description`. (c) AGENTS.md line 936 promises "a small herdr-core skill you can install" inside `hc --skill` output, but hc 0.1.18 prints no such section (fork facts): if a later hc ships it, this skill should point to it rather than grow; recorded so an update probe checks for it.
Not asked: should the skill be named `herdr` at all, given the old binary is also `herdr` until cutover removes it? The operator proposed `/herdr`, so I keep it, but during the overlap period the description must not send agents to the old binary by name alone — the body's legacy warning covers it.

## Q2. Owner, homes, and when the old skills go

Pick: herdr-setup owns the source (one `skills/herdr/` in `/home/ivan/Work/infra/herdr-setup`) and its `install` links that directory into all five user skill homes: `~/.claude/skills`, `~/.codex/skills`, `~/.pi/agent/skills`, `~/.agents/skills`, and `~/.gemini/config/skills` (agy). It lands first, before the akrogon cutover, and the same install run removes the old skills by replacement, since the old text actively sends agents to the dead binary and gates on `HERDR_ENV=1`.
Reason: the skill teaches herdr, not akrogon; herdr-setup is the repo that already installs this machine's herdr-app setup, and its `link()` helper moves an existing real file or folder to a timestamped backup before linking (herdr-setup `install`), which is exactly the replacement the three old real-directory skill copies need — akrogon's installer instead reports such destinations as conflicts to remove by hand (`src/install.ts:130-143`). Agy's user home is real and uses the same symlink-to-SKILL.md shape (`~/.gemini/config/skills/*` are symlinked skill dirs, listed 2026-11-07), so including agy costs one link and closes the "agy unconfirmed" gap by construction, pending the load probe below. `~/.agents/skills` is a real root (a skill from it, dev-browser, is loaded in my own pi session), so it gets the link too; if two homes feed one harness and produce a duplicate listing, that is a probe outcome, not a reason to skip a home blind. Edits to the source apply everywhere at once through symlinks, with no akrogon release involved. Cost: a third installer now writes into skill homes (herdr-setup joining akrogon and omarchy), so ownership boundaries must stay recorded: herdr-setup owns `herdr`, akrogon owns its lifecycle skills, and neither installer prunes the other's links (akrogon's stale-pruning only walks its own `skills/` names, `src/install.ts:52-76`, so the herdr link survives akrogon installs untouched).
Rejected: akrogon owns it under `skills/herdr/` (zero new link machinery, since `planSkillLinks` links every `skills/` directory to the four roots at `src/install.ts:25-43`, but the skill would vanish on akrogon uninstall and ride akrogon releases for content that is substrate documentation; also one root short, since akrogon has no agy root). Operator step by hand (what produced today's three drifting real-directory copies). Removing old skills at akrogon cutover instead of now (the old skill already caused a door refusal in herdr-app, INTAKE 2026-11-01; leaf agents do not need the old skill to run because the old engine drives herdr itself, so nothing working depends on keeping it).
Evidence: better-than-training: herdr-setup `install` and README (link with backup, safe to rerun), `src/install.ts:25-76,130-143`, live `ls` of the homes (old skill present as real dirs in claude/codex/pi, absent in `~/.agents/skills`; agy config skills as symlinks), signpost 3 (herdr-side pieces in herdr-setup), all read 2026-11-07.
Pitfalls: (a) A harness that does not follow a symlinked skill directory silently lacks the skill. Removed by probe per home: fresh session, invoke `/herdr` or list skills, before this leaf hands off (signpost 7a budget); akrogon's own skills already ride symlinks into three of these homes, so the unknown is mainly agy. (b) Two homes feeding one harness could double-list `herdr`; if the probe shows it, the fix is dropping the redundant home for that harness, recorded in the leaf. (c) Herdr-setup's backup-on-replace means a stale backup skill copy sits under `~/.local/state/herdr-setup/backup-*`; harmless because no harness reads that tree, and the cutover fork's machine cleanup can sweep it.
Not asked: whether herdr-setup's install should also refuse to proceed while any home still holds the old skill as a real directory after linking (a post-install check), since a harness that prefers a same-named real directory elsewhere ranks unknown.

## Q3. Is description-triggered loading enough awareness?

Pick: The skill is the whole global mechanism, and its description carries the triggers explicitly: running inside a herdr-core terminal, receiving a message in `<hc>` tags, being asked to start, message, inspect, or wait on other terminals or agents, or to change the herdr-app window. The body's first act is the gate: with `HC_TERMINAL_ID` unset and no `<hc>` context, say you are not inside herdr-core and do not inspect or control a session from outside (today's old-skill stance, kept), while still being allowed to read the manuals. Nothing more reaches agents akrogon starts through this skill, because those agents already get awareness from akrogon itself: the start task and every brief carry the report line and the seat's own standing skill (leaf lifecycle skills, chart briefs) names its hc steps, so the global skill only has to cover operator-started sessions, which is the gap the intake names.
Reason: this matches how skills actually load here (descriptions are in context every session; the body loads on a judged match), and the `<hc>` tag is a strong in-context trigger an agent sees at a turn boundary, when it can still load the skill before acting. It is not a guarantee — description matching is model judgment, the same limit the old skill had — but the failures degrade to the agent asking or reading `hc --help`, not to wrong actions, because akrogon-driven communication never depends on a seat spontaneously knowing hc: every akrogon task text already spells its `hc send` report line (my own briefs in this chart all did). Cost: an operator-started agent that never triggers the skill can still try the old `herdr` binary once (command-not-found after cutover is a loud teacher) or drive tmux-style from training; nothing in this design can do better without touching the global files the operator froze.
Rejected: a one-line pointer in global CLAUDE.md/AGENTS.md gated on the env var (signpost 5a forecloses it, and it would load in sessions outside herdr-app exactly as the intake refuses). Relying on herdr-app's AGENTS.md being auto-read (only happens for agents whose cwd is the herdr-app home and whose harness reads AGENTS.md there; a leaf seat in a worktree never sees it). Having start inject the skill text into every akrogon seat's first prompt (duplicates the manual into every chart and leaf context; briefs already carry the one line that matters for their role).
Evidence: operator (intake: aware every time inside herdr-core, no global-file pollution, signpost 5a); better-than-training: my own pi session in this chart, where the available-skills list (descriptions only) is present from the start and the old `herdr` skill with its HERDR_ENV anti-trigger wording is what currently matches (read 2026-11-07); `hc --skill` itself tells senders to put the report instruction in the task text (the `reach=` form), so akrogon messages are self-describing; old skill's outside-herdr stop rule (`~/.claude/skills/herdr/SKILL.md`).
Pitfalls: (a) An `<hc>` message can arrive from any terminal, including a leaf agent's, and must never be taken as operator authority; the body states it, and akrogon skills already treat wake text as a hint. (b) With `notes = false`, messages arrive untagged and the `<hc>` trigger weakens; the env-var half of the gate still identifies the situation, and chart-door's Open gate already refuses that configuration for doors. (c) The probe that settles this question: per harness, one fresh session inside an hc terminal given a neutral task plus an incoming `<hc>` child report, checking the agent loads the herdr skill (or answers its address and report path correctly) without being told; a harness that fails twice gets its description strengthened, not a second mechanism.
Not asked: whether `/herdr` should also be listed in herdr-setup's own onboarding for a fresh machine (its install prints nothing about skills today), so an operator rebuilding a machine learns the skill exists from somewhere other than this chart.
