## Q1. What wakes the watcher?

Pick: The listener wakes it with an `hc send` message; the routine 20-minute cron goes. The listener sends one wake per newly actionable edge: terminal lost or exited where a seat was expected (including the keep-shell case found by its own resume sweep), a seat entering `blocked`, a leaf entering `failed` (including delivery's silent-stop bound), a merge/land completing while a leaf sits `failed` (its recovery inputs may have changed), and a busy deadline (60 minutes after a seat was first seen `working`, armed in the listener, which also runs the pass that posts the busy notice). On every listener start it sends one catch-up wake if the sweep finds any leaf in a watcher-actionable state. A watcher check that decides "working normally, judge again later" arms its own one-shot recheck (a one-shot Claude cron with a distinct recheck prompt, or it simply relies on the next edge); there is no standing tick. Every wake runs the same full check as today (status, observe, judge every leaf), so the message text is a hint carrying repo, class, slug, and seat, never evidence.
Reason: the operator's clarification judges timed checks directly, and every watcher rule triggers off a state the engine already transitions through in a pass, except elapsed busy time, which is a deadline armed by an event, not a poll. Level-triggered full checks make lost or duplicated wakes harmless (the same design as the listener's catch-up sweep): a wake sent while the watch session is mid-turn queues as its next input, and a state arising while no watch terminal exists is seen at the next wake, catch-up, or the operator's return. Cost: the listener gains wake classes and one deadline queue, wakes are Claude turns so edges must stay edge-only (never per turn-end), and a state produced with truly no akrogon event (an outside prerequisite fixed by hand) waits for the next edge; human-prerequisite failures are never auto-recovered anyway, so no recovery is lost there. Removing the cron also removes the 7-day expiry and the duplicate-job bookkeeping.
Rejected: cron as today (it is the polling the clarification names, and it does no work the edges do not: Waiting is now driven by phase-runs-next and the listener, not by the watcher kicking `next`). Both, cron kept as backstop (two drivers racing the same full checks; a slow cron still polls and invites leaving wake gaps unfilled because "cron will catch it"). Listener acts itself without the watcher (signpost 4a puts judgment and auto-fix in the watcher agent; the listener is code with no screen judgment).
Evidence: operator (signpost 4a watcher auto-fix, workflow unchanged; clarification no polling/waiting, `<hc>` messages, 2026-11-06); better-than-training: `skills/watch-issues/SKILL.md` invocation/cron and Judge sections, engine-shape Taken (listener events, single-flight, catch-up), delivery Taken Q3 (silent stops fail the leaf with a reason for the watcher's existing failed rules), `src/next.ts:220` STALL_MS; read 2026-11-06.
Pitfalls: (a) The listener is a systemd service, not a terminal: an `hc send` from it may arrive unwrapped instead of as `<hc from=...>`, looking like operator words. Removed by probe (send from a context with no `HC_TERMINAL_ID` in a throwaway session) and by a fixed wake marker line the skill treats as machine input, never as operator instruction or scope. (b) Wake storms when many leaves flap `blocked`. Removed by edge-only classes plus per-repo coalescing in the listener (one wake in flight per repo until the watcher next goes idle; the full check covers the rest). (c) A leaf agent itself can `hc send` a fake wake (it can find the watch terminal in `hc ls`). Removed by construction: the watcher derives everything from observe and its Never list; a fake wake costs one check and grants nothing. (d) The watch session backgrounded with `/bg` reports no status and may not relay typed input the same way (INTAKE 2026-11-04). Removed by the skill refusing or warning when its own session kind is background at start (Q3), probed once.
Not asked: should a `blocked` seat wake the watcher at all, given herdr-app already toasts and sounds for blocked agents itself? Waking makes the watcher name the question in its reply sooner; not waking keeps watcher turns for things it can act on. I include blocked because judging "waiting on a question vs working" is watcher work today via the screen.

## Q2. How does it observe and act on hc?

Pick: Same skill structure, commands translated one-for-one. `observe.ts` resolves the repo's hc session and space with the identity resolver in `src/` (it already imports `src/config` and `src/shell`, `observe.ts:3-11`), pins session env per call, and reads statuses from `hc ls --label akrogon.repo=<repo>` joined to each leaf by labels (`akrogon.leaf`, `akrogon.seat`), cross-checked against the recorded seat address so a replaced incarnation is never judged as the recorded one. Its output line keeps today's fields with terminal address and name in place of pane id, hc status verbatim (`working|idle|done|blocked|error`, missing terminal `-`, null status printed `unknown` meaning hands off). Transcript path comes from the one session-id resolver in `src/` (session-id corrections), only for `working` seats; `log-tail.ts` is unchanged. Screen reads become `hc read <address> --lines 0` for a working seat (history reads return screen-only then anyway) and `--lines 80` otherwise. Steering becomes: `hc interrupt <address>` (presses the stop key and reports the effect), then read to confirm an idle seat with empty input at the same address, else notice instead of prompting, exactly today's confirm-or-notify rule with address in place of "same session"; then one corrective plain `hc send`, sent only to an `idle`/`done` seat, never `--force`. `akrogon next`/`phase`, the paused check, and the Never list are unchanged; the one change there is Never also names `hc kill` and `herdr-app do` (the watcher closes nothing). Notices go through the notices Taken: the watcher writes via the one akrogon verb, and `failure.delivery` comparisons treat a still-pending notice file as in flight, not as a reason to file a second one (deterministic ids dedupe).
Reason: this is the closest-to-today mapping: observe already isolates substrate reads behind one script with a stable line format, and the steer's safety came from the confirm step, which `hc interrupt`'s own effect report strengthens. Keeping the line format keeps every Judge rule text intact except command names. Cost: observe now depends on labels being right on seat terminals (start owns that) and on two hc calls where one `agent list` sufficed; a seat whose labels were tampered with shows as missing and is judged absent, which fails safe (Waiting runs `next`, whose own ownership check arbitrates).
Rejected: watcher judges from `akrogon status --json` alone (status is the board's state summary; observe's per-seat live status, busy ages, and transcript paths are the Busy rule's evidence, and re-deriving them in status duplicates observe). Steering by `hc keys esc` plus a timed `hc wait` (two commands and a wait where `hc interrupt` is one call that reports what happened). Addressing seats by hc name (names are reused per incarnation; identity took the recorded address precisely so a replaced seat is refused). `hc read` history as a transcript substitute (screen text is the fallback today; the session-id resolver keeps real transcripts for three kinds).
Evidence: better-than-training: `skills/watch-issues/scripts/observe.ts` (session resolution, agent statuses, `resolveLog`, stable line format `formatLeaf`), watch SKILL.md Judge/Busy/Never sections, `hc interrupt --help` and `hc keys --help` (run 2026-11-06), `hc --skill` read/status semantics, identity/session-id/notices Takens.
Pitfalls: (a) `hc interrupt` effect differs per harness (a seat may show a confirmation, or codex `/new`-style turn miscounts). Removed by probe per kind in a throwaway session: interrupt a working seat, confirm idle with empty input, corrective send starts exactly one turn. (b) The codex question case: status `working` while blocked on its question tool (INTAKE), so observe prints working and a log path; loop judgment then rests on log-tail and screen, as the session-id notes already say, never on age alone, and today's rule that insufficient evidence means no action is the guard. (c) `hc ls --label` in a resolved session from a watch terminal in another session: env pinning per identity, inherited selectors stripped (the watch terminal's own `HC_TERMINAL_SOCKET` is the trap, same as the engine's). (d) Observe's test fixtures (`herdr-agent-list.json` etc.) are reborn as captured `hc ls --json`/`hc get` output under the tests fork's fake hc; observe tests rename `OBSERVE_HERDR` to the fake hc binary, same override pattern.
Not asked: since the cron is gone, the skill's "Claude Code only, CronCreate required" gate loses its reason. I keep the watcher Claude-Code-only for this migration (judgment rules are tuned there), with the gate rewritten to what it actually needs now (a live hc terminal it can label, Q3); widening harnesses is later work, not this fork.

## Q3. Where does the watch session run, and who starts it, including after reboot?

Pick: Operator-started, as today: the operator opens a Claude Code terminal in the repo's herdr-app space (the live `w-<repo>` tab convention) and runs `/watch-issues`. The skill labels its own terminal `akrogon.watch=<repo>` (one `hc label $HC_TERMINAL_ID` from skill text), refuses to start a second live watcher for the same repo (an existing live terminal with that label is reported, mirroring today's several-cron-jobs rule), runs one check now, and then receives wakes at that address, which the listener finds per wake by the label in the resolved session. `/watch-issues stop` removes the label and deletes any recheck job it armed; closing the terminal also ends the watch, as closing the session ends today's cron watch. After a reboot, nothing restarts it: the core's kept terminal comes back as a shell where Claude was, and the operator starts a new watch session (which re-labels its terminal). What makes this visible instead of silent: `akrogon status` shows whether a live `akrogon.watch` terminal exists for the repo, next to the listener liveness engine-shape already took.
Reason: the watcher is an agent spending the operator's money with judgment authority (phase recovery, steers); the current skill is operator-started and operator-stopped only, and signpost 4a says workflow unchanged. A label, not a name, is the discoverable identity because the operator's terminal already exists before the skill runs and hc terminals cannot be renamed; finding it by label per wake survives address changes across restarts without stored config. Cost: after a reboot or an accidental close there is no watcher until the operator acts, exactly as today; and the operator must start the session inside herdr-app/hc (a Claude session run outside hc has no terminal to label or receive sends), which the skill detects from a missing `HC_TERMINAL_ID` and refuses, as it refuses outside-herdr starts today.
Rejected: the listener starts the watcher when absent (code autonomously starting a paid Claude session in a worktree, choosing its model, and restarting it in a loop if it keeps dying; the operator's start/stop authority was explicit). A dedicated named hc child started by the door at handoff (lifetimes tangle: it dies with the door terminal, start-and-pane Q1, and handed-off work is supposed to outlive the door). Systemd service running a headless agent (`claude -p` style: not watchable or steerable in a pane, against the visible-pane rule, and its turns cannot receive `<hc>` queueing).
Evidence: better-than-training: watch SKILL.md operator-invoked header and Invocations (started/stopped only by the operator, job identity, expiry), live `hc ls` showing `w-akrogon`/`w-framework` watch tabs in repo spaces (2026-11-06), `hc label --help`, start-and-pane lifetime Taken (kept terminals return as shells after core loss), signpost 4a.
Pitfalls: (a) Two stale labels: an old finished watch terminal keeps its label, and the listener must consider live terminals only and treat two live matches as a reported conflict, not pick one. (b) The operator starts the watcher from a terminal in a different hc session than the repo's resolved session; wakes then target a terminal the listener's per-session label search would miss. Removed by the skill checking at start that its own session is the repo's resolved session (space name via the same resolver) and refusing with that named. (c) The label survives in a kept shell after core loss, so status could show a watcher that is now a bare shell. Removed by status checking the labeled terminal's agent/status is a live agent, not just the label. (d) The watch session's own turns cost money per wake; the skill's reply stays at most five lines per fire, as today, and wake edges are the only fires.
Not asked: should there be one watch session per repo (today's shape, my pick) or one for the whole hc session watching every repo in it, since one listener now sees all of them? Per-repo keeps today's contexts and roots separate, but the fork never asks whether the operator wants one combined watcher when away.
