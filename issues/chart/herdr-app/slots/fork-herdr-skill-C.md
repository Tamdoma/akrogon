# Fork notes, herdr-skill — slot C (Claude Fable 5.1), 2026-11-07

## Q1 Shape

Pick: a small owned `herdr/SKILL.md` (front matter `name: herdr`, two-sentence description) whose body is a gate plus three pointers, in this order: `hc --skill` (running, messaging, waiting, status), `herdr-app --skill` (the window), and `${HERDR_APP_HOME:-$HOME/.config/herdr-app}/AGENTS.md` (layouts, keys, mods, only when the task changes the window). Reason: every byte of substance is printed by the installed binary or written by the app on each start, so the skill holds nothing that can go stale when hc or herdr-app update; the operator's "pulls from that agents.md file" is met by the pointer, which the agent follows on match. Cost: one or two extra commands per load (`hc --skill` is 260 lines), and the body must say which manual answers which need so agents do not read all 951 lines of AGENTS.md for an `hc send`.

Rejected:
- Plain symlink `SKILL.md -> AGENTS.md`: the target has no front matter (`~/.config/herdr-app/AGENTS.md:1-3` is a title and an "overwritten on start" comment). pi: "Malformed SKILL.md files and declared skills without descriptions are not loaded" (pi 1.5.0 `docs/skills.md:85`); Codex: "must include name and description"; agy: description required; Claude Code: fields optional, but with no description the listing has nothing to route on. Even where it loaded, the body is 951 lines of which lines 165–931 are layouts, keys, commands, settings and mods, and the hc part is 12 lines (932–944) that itself says "run `hc --skill`". The global file is also not the live one: `~/.config/herdr-app/AGENTS.md` (Nov 2) differs from `~/.config/herdr-app-sessions/infra/AGENTS.md` (Nov 5) by 133 diff lines; each window rewrites only its own home's copy.
- Generated copy of the manuals refreshed on update: needs a generator and a trigger, and nothing runs when a binary updates (herdr-setup `install` fetches via `install.sh`, the app rewrites AGENTS.md itself); a stale copy is the exact failure the operator wants gone, and it adds parts for no behavior.

Evidence: operator (signpost 5a verbatim, INTAKE.md:187); practitioner: pi `docs/skills.md:3,43-45,59-61,81-85` (read 2026-11-07); Claude Code skills doc code.claude.com/docs/en/skills.md ("skill descriptions are loaded into context … full skill content only loads when invoked"; "a `<skill-name>` entry … can be a symlink to a directory elsewhere on disk … loaded once"; combined description text truncated at 1,536 chars) 2026-11-07; Codex learn.chatgpt.com/docs/build-skills.md ("must include name and description"; list "uses at most 2% of the model's context window"; "supports symlinked skill folders") 2026-11-07; Antigravity antigravity.google/docs/skills (description required, name defaults to folder, "On every turn, the agent sees a list of available skills") 2026-11-07; live: `hc --skill | wc -l` → 260, `herdr-app --skill` line 90 names `$HERDR_APP_HOME/AGENTS.md`, `grep -n skill ~/.config/herdr-app/AGENTS.md` → only 934–936, and `hc --skill | grep -i skill` has no installable-skill section (the AGENTS.md claim is wrong for hc 0.1.18).

Pitfalls: (a) the AGENTS.md pointer resolves to nothing in a session that never opened a window (AGENTS.md is written on window start); body falls back to the global copy and says so. (b) AGENTS.md line 936 promises an installable skill that does not exist; the body does not repeat it (operator step: report upstream, not patched). (c) Description length: Codex trims long descriptions first under its 2% budget; keep it under 300 characters (probe: `/skills` in codex lists `herdr` with its full description).

## Q2 Owner and homes

Pick: herdr-setup owns it: `skills/herdr/SKILL.md` in that repo, linked by `./install` with its existing `link()` into `~/.claude/skills/herdr`, `~/.agents/skills/herdr`, `~/.codex/skills/herdr`, `~/.pi/agent/skills/herdr` (the four roots akrogon uses, `src/install.ts:25`) and `~/.gemini/config/skills/herdr` (agy's documented global path, already used on this machine by omarchy's links). Reason: signpost 3 names herdr-setup as the space for everything herdr-app-side that akrogon lacks, `install` already is the per-machine linker and is "safe to run again" (README), and `link()` moves a real folder found at the target aside to a backup before linking, so the old herdr skill folders at the same paths are retired by the same step that installs the new one. Removal timing: at once, when herdr-setup install runs; the old skill is gated on `HERDR_ENV=1`, which herdr-app never sets (INTAKE.md:62), and no akrogon script calls it (chart-issues scripts call the `herdr` binary). Cost: during the overlap, agents in old-herdr panes have no herdr skill for free-form asks; akrogon's old-herdr paths do not use it.

Rejected:
- akrogon install: `planSkillLinks` links only `skills/` of the akrogon release (`src/install.ts:26,40-43`) and prunes stale links against that tree (:76); adding a herdr-app manual pointer there makes akrogon own content about another product, and the skill must exist on machines running herdr-app without akrogon.
- Operator step by hand: five links plus three removals, repeated after reinstalls; `install` already does exactly this kind of step.
- Only the documented minimum (`~/.claude/skills`, `~/.agents/skills`, `~/.gemini/config/skills`): leaves the old `herdr` folders in `~/.codex/skills` and `~/.pi/agent/skills` (both exist, Sep 1), and pi keeps the first skill it discovers on a name collision with a warning (`docs/skills.md:85`), so which `herdr` wins would depend on scan order.
- Removal only at the old-herdr cutover: ties a herdr-setup step to the akrogon epic for no gain; the old skill is not on the e2e-tested path.

Evidence: operator 3, 5a, 6a (signposts Taken); practitioner: Codex user scope `$HOME/.agents/skills` (build-skills.md), pi user dir plus `~/.agents/skills` (`docs/skills.md:59-61`), Antigravity global `~/.gemini/config/skills/` shared by App, CLI and IDE (docs/skills), Claude Code personal `~/.claude/skills/` (skills.md); live: `ls -la ~/.claude/skills/herdr ~/.codex/skills/herdr ~/.pi/agent/skills/herdr` (three old copies, 10746 bytes each, 2026-08-23), `~/.gemini/config/skills` holds omarchy's symlinked skills, `herdr-setup/install` `link()` lines 13-24, README "Run it again after adding a mod or layout". Low confidence: whether Codex 0.167 still reads `~/.codex/skills` (official page lists `~/.agents/skills` only, yet `~/.codex/skills/.system` was refreshed today 10:14); linking both is what akrogon does today, so a duplicate listing there is today's behavior, not new.

Pitfalls: (a) a second copy of the same skill in two homes shows twice in Codex ("does not merge … both can appear") — same as every akrogon skill today; probe `/skills` in codex and pi startup diagnostics once. (b) Claude Code reading `~/.agents/skills` is undocumented; the `~/.claude/skills` link covers it. (c) Pickup: Claude Code watches `~/.claude/skills` live, Codex needs a restart, pi `/reload`, agy `/skills reload` — operator step after install: restart live seats or accept pickup at next start. (d) herdr-setup has no `skills/` folder today; `install` gains a loop like its mods loop (leaf done-criterion: install twice is idempotent and `readlink` of all five paths points into the repo).

## Q3 Awareness

Pick: the description-triggered load is the only harness mechanism, and it is enough when paired with what already reaches every seat: hc sets `HC_TERMINAL_ID`, `HC_SESSION`, `HC_TERMINAL_SOCKET` and `HERDR_APP_HOME` in each terminal's environment (my own `env`), and hc tags incoming messages `<hc from="t3 lead" reach="hc send t3 when done or stuck">` (hc --skill lines 106-118), so the reply path travels with the message. The description names those triggers ("HC_TERMINAL_ID set, a message in <hc> tags, hc, herdr-core, herdr-app, Herdr"), and the body opens with the same check the old skill had (`test -n "$HC_TERMINAL_ID"`, else say you are not in herdr-core and stop; old skill `SKILL.md:10-16` did this with `HERDR_ENV`). Nothing more for agents akrogon starts: their task text and briefs already spell the exact `hc send <door>` command (this brief line 37; signpost 1a keeps hc steps as plain commands in skill text). Cost: no harness forces a skill every session (Claude: none by env; Codex: only explicit `$herdr`; pi `/skill:herdr`; agy slash), so a model can still skip it; the briefs' literal commands are the floor.

Rejected:
- Global CLAUDE.md/AGENTS.md lines: ruled out by 5a and the intake (Claude Code runs outside herdr-app).
- An akrogon-added "read the herdr skill" sentence in every start task: the briefs already carry the command that matters, and the first task of a leaf is a contract brief, not hc tutoring; adding it is a new part with no failure it removes while `reach=` exists.
- `disable-model-invocation`/explicit-only: the operator wants it without reminding; explicit-only is the opposite.

Evidence: practitioner (loading rules above, all four docs, 2026-11-07); live `hc --skill` Talk section (report tagging, `reach=`), `env | grep -E '^(HC_|HERDR)'` in t6d; old skill gate `~/.claude/skills/herdr/SKILL.md:10-16`; chart-door Taken gate `HC_TERMINAL_ID` (CHART.md:18).

Pitfalls: (a) a direct `hc run -- <harness> "<task>"` first message may arrive without `reach=` (templates set it; direct runs unverified) — probe before handoff: start one throwaway seat with a task and read what the agent sees; if untagged, the start verb's task text ends with the one address line, as the chart brief does today. (b) Description triggers on "herdr" outside hc when the operator just mentions the word; the body gate stops action, as today. (c) A seat started before install never sees the skill until restart (Codex, pi, agy); covered by Q2 (c).
