## Q1 codex

Pick: `harnesses.codex: "codex --no-daemon -m {model} -c model_reasoning_effort={effort} -a never -s danger-full-access"`: add `--no-daemon`, keep full access. Reason: `--no-daemon` is hc's stated requirement ("Codex must run with `--no-daemon` (including templates), or its commands execute outside hc", `hc --skill:259-260`; codex help: "Run without the shared background server"), and full access is today's leaf behavior (`~/.akrogon/config.yaml` `harnesses.codex`, settings allow-list line 254 pre-approving `-s danger-full-access` for peers): a leaf seat writes outside its worktree by design (`issues/` at the repo root, `~/.akrogon/runs`, leaf temp), which `workspace-write` blocks, and containment boxes the seat in a systemd scope instead. Cost: consultants started from this line lose the sandbox they had in this chart, which existed only as the classifier workaround (Q3); an operator who wants a sandboxed consultant names the args per seat, as the chart skill allows today.

Rejected: `-s workspace-write -c sandbox_workspace_write.network_access=true` for leaves: a regression for every write outside the worktree, and the network flag is a second thing to forget (INTAKE 2026-11-05: without it every `done` report is lost silently); two codex entries (`codex` and `codex-sandboxed`): a second line nothing in the lifecycle picks; leaving `--no-daemon` out: proven wrong by hc's own rule.

Evidence: operator (config.yaml today; INTAKE.md:46 "9 out of 9" with `codex --no-daemon`; INTAKE.md:179-181 sandbox findings and fix); practitioner: `codex --help` (`-s` values `read-only, workspace-write, danger-full-access`; `-a never`; `--no-daemon`), Codex config docs mirror: network disabled by default under `[sandbox_workspace_write]`, override `-c sandbox_workspace_write.network_access=true` (read 2026-11-07); live: `hc get ak-slot-b --json` argv.

Pitfalls: (a) `launch()` requires `argv[0] === config.harness` (`src/next.ts:296-301`): the line starts with `codex`, fine. (b) A door that types `hc run ... codex -s danger-full-access` by hand is still refused in auto mode: the skill text calls the start verb, never raw `hc run` (Q3).

## Q2 agy

Pick: add `harnesses.agy: "agy --model {model} --effort {effort} --dangerously-skip-permissions -i"`. Reason: `agy --help` has `--effort low|medium|high|xhigh|max`, the same words akrogon's `effort` uses, `--dangerously-skip-permissions` ("Auto-approve all tool permission requests without prompting") is the unattended flag matching claude's, and `-i` keeps the session interactive after the first prompt, which the start verb appends last (live argv `agy --model gemini-4-argon-high --mode auto -i "<task>"`, INTAKE.md:141 proof). One table then serves leaves and consultants, and delivery's "silent stops recorded per harness kind" has a kind to record. Cost: one config line; agy is not put in any slot by this (slots still name pi and codex).

Rejected: leave agy out (consultants would need hand-typed argv every time and seats.yaml's "launch recipe" has no table to come from; the start verb would carry a special case); `--mode auto` in the entry: what the chart used for E works attended, but agy's own help documents only `--dangerously-skip-permissions` as auto-approve, and `--mode` as "execution mode (accept-edits, auto, plan)", whose prompting behavior under an unattended leaf is unverified (probe below).

Evidence: `agy --help` lines 7, 9, 10, 14, 23 (read 2026-11-07); INTAKE.md:140-141 (`agy --dangerously-skip-permissions -i "<task>"` worked, reports `working`/`done`); INTAKE.md:155 (`hc send --force` on agy's question menu picks option 1, so the watcher never forces agy); practitioner search found no official agy flag docs, only third-party guides (`-p` non-interactive, `-i` interactive), so the local help is the source.

Pitfalls: (a) `--mode auto` vs `--dangerously-skip-permissions`: one free probe in the throwaway session with a task that needs a permission (write a file outside cwd) decides which the entry carries. (b) agy's scroll viewer swallows a paste (`started: false`, INTAKE.md:212): delivery Q2 already reads the screen first; the watcher's per-kind stop key probe covers `esc`. (c) agy silent stop (INTAKE 2026-11-06): delivery Q3/Q4 bound it; the kind is now recordable.

## Q3 Permissions

Pick: nothing changes in the harness lines. Leaf seats are started by the listener (a systemd user service), where no classifier exists, so claude's `--dangerously-skip-permissions` stays as today. Consultants are started by the door through the start verb, an `akrogon` command, and the operator's settings already hold the narrow allow rule `Bash(akrogon:*)` (`~/.claude/settings.json` `permissions.allow`, with `defaultMode: auto`), which resolves before the classifier: Claude's docs say allow rules "resolve immediately" (decision step 1) and only broad rules (`Bash(*)`, wildcarded interpreters, package-manager run, `Agent`, `Monitor`) are dropped in auto mode, "narrow rules like `Bash(npm test)` stay in effect". The refusal in INTAKE 2026-11-05 was a raw `hc run ... codex -s danger-full-access`, which no rule covered, so the classifier saw the argv and applied its "autonomous agent loop without approval or sandbox" block. Cost: the skill text names that rule as the one operator step for a door in auto mode on another machine; nothing else.

Rejected: dropping `--dangerously-skip-permissions` for leaves (unattended seats would block on the first prompt; delivery's `blocked` handling is for questions, not every tool call); `--permission-mode auto` for leaves (the classifier's 3-in-a-row fallback "resumes prompting", which stalls an unattended seat; in `-p` runs it silently skips the action); a wider rule such as `Bash(hc run:*)` (the dropped-rule list shows the classifier treats broad execution rules as bypasses, and the verb already gives one narrow entry point).

Evidence: practitioner: code.claude.com/docs/en/permission-modes.md ("broad allow rules that grant arbitrary code execution are dropped", "Narrow rules like `Bash(npm test)` stay in effect", "Blocked by default: launching an autonomous agent loop … started with `--dangerously-skip-permissions`", "3 times in a row or 20 times total, auto mode pauses"), read 2026-11-07; live: `jq .permissions.allow ~/.claude/settings.json` shows `Bash(akrogon:*)` and `defaultMode` `auto`; INTAKE.md:178; engine-shape Taken (listener is the starter); chart-door Taken (consultants through the start verb).

Pitfalls: (a) The docs do not name `Bash(akrogon:*)`; probe before handoff: the door in auto mode runs the start verb for a full-access codex stand-in in the throwaway session and is not prompted. (b) Subagent task descriptions are classified at spawn: the start verb is a Bash call, not an `Agent` call, so this does not apply; the skill text keeps it that way. (c) The allow-list still carries dead `herdr agent ...` rules: cutover step 2.

## Q4 App home

Pick: herdr-setup's convention, as one function in the hc module: session `default` → `~/.config/herdr-app`, any other session → `~/.config/herdr-app-sessions/<session>`, and the home is confirmed, when it matters, by the window socket `<home>/herdr-app.sock` that `herdr-app` creates there (start-and-pane's "no Herdr window at <home>/herdr-app.sock" check). Reason: that mapping is exactly what creates the homes (`herdr-setup/bin/herdrapp:58-64` `use_session`: `unset HC_SESSION HERDR_APP_HOME` for default, else `HERDR_APP_HOME=$sessions_dir/$1 HC_SESSION=$1`), hc's default session is literally `default` (`/run/user/1000/herdr-core/default.sock`), and the core holds nothing else to read: the `herdr-app` document has only `spaces` (`doc.get` keys), the core state folder has no home record. Cost: akrogon depends on a herdr-setup convention; the patch-mechanism post-update check and one akrogon e2e assertion (socket exists under the derived home while the window is open) hold it, and herdr-setup's README states the mapping as its contract.

Rejected: a config key per session (a second copy of a mapping only herdrapp produces, drifting on rename or a new session; today's akrogon has no per-session config and the identity Taken resolves sessions by name); reading the session itself (the window process has `HERDR_APP_HOME` in `/proc/<pid>/environ`, but that is a scan over processes and is absent exactly when the window is closed, which is when notices must still be written to the home).

Evidence: live `ls ~/.config/herdr-app/herdr-app.sock ~/.config/herdr-app-sessions/*/herdr-app.sock` (default, infra, mdconsultingny, personal); `herdr-app --help` ("Home: ~/.config/herdr-app (HERDR_APP_HOME picks another)"); `pgrep -x herdr-app` environ shows `HC_SESSION=infra HERDR_APP_HOME=…/herdr-app-sessions/infra`; `herdr-setup/README.md` Sessions ("`HC_SESSION=<name>` … isn't in Herdr's docs, so a Herdr update could change it"); notices Taken Q2 (notice folder under the resolved session's home); identity Taken Q1 (`HERDR_APP_HOME` pinned per herdr-app call).

Pitfalls: (a) A window started by hand with another `HERDR_APP_HOME` is invisible to the convention: out of scope, herdrapp is the only launcher (operator step: use `herdrapp`). (b) A stale `herdr-app.sock` after a crash: `herdr-app ls` connecting is the truth, the file alone is not (existing start-and-pane rule). (c) The mapping appears in two repos: the e2e assertion fails loudly if herdrapp changes it.
