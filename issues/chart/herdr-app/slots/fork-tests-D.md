## Q1. What replaces fake-herdr?

Pick: One strict fake pair sharing one state file, today's architecture unchanged: `tests/fake-hc.ts` (subcommands run, ls, get, send, wait, interrupt, keys, kill, rm, label, events, connect for `doc.get`) and `tests/fake-herdr-app.ts` (`ls`, `status`, `do tab.rename|pane.focus|terminal.keep|terminal.park`), both driven by the state-file pattern fake-herdr uses, reusing the engine hc module's schemas, emitting captured real JSON (my probe below plus the live-session captures already in earlier forks), and failing any call or event subscription a test did not plan. `isolation.ts` bundles both per worker as it bundles the fakes today; selections stay exe-override envs (`FAKE_HC` state-file variable beside the existing `FAKE_SYSTEMD_RUN`/`FAKE_SYSTEMCTL` pattern). `events` in the fake is a scripted stream: it prints the snapshot line then the test's planned event lines and stays open or ends as the scenario says, so listener restart-and-sweep is unit-testable. `fake-busctl.ts` is deleted with `adoptShell`; `fake-proc.ts` and fake systemd-run/systemctl stay for callerScope and the containment wrapper.
Reason: akrogon's suite is black-box CLI tests (`tests/helpers.ts` invokes the real command in subprocesses, 30 s timeout, `--parallel=4`), and most scenarios are error and race injections a real core cannot produce on demand — `name_taken`, `started: false`, a seat `blocked` on cue, absent terminals, unreadable sessions, identity changed mid-pass. fake-herdr's strictness (planned entries, refusal on surprise calls, multi-session worlds in `session-routing.test.ts`) is what makes those tests mean anything, and the migration must not lose a single one of those behaviors ("nothing that works today may break" applies to the test suite's judgment too). Cost: the fake must grow every time the engine's closed hc verb list touches a new shape, and a fake can drift from real hc; Q2's layered real runs are the drift detector, plus the identity fork's schema-pinned check run against the installed `hc schema` in the e2e layer.
Rejected: a real core for most tests (determinism dies first: 60-second start proofs, turn timing per harness, and unscriptable states; every scenario needing a *reporting* agent needs either a paid model or an OSC-emitting stand-in nobody has built yet; and hundreds of error-path tests would silently stop testing the error). A fake at the hc module boundary in-process (the engine runs as a CLI subprocess in these tests and as the listener service in life; there is no in-process seam to mock without adding a test-only hook to production code, and skill scripts like observe spawn the binary by name). Captured-JSON playback without planned-call strictness (a permissive fake lets the engine grow calls no test noticed, which is how the old surface reached 20 herdr call sites unnoticed).
Evidence: better-than-training: `tests/AREA.md`, `tests/fake-herdr.ts` and `tests/isolation.ts` patterns, `issues/config.yaml` test check, `src/shell.ts` schemas; my free probe 2026-11-07 in `HC_SESSION=akr-probe-d` with scratch XDG: a fresh core auto-starts on any `hc` command (even `hc server status` after a stop resurrected it, confirmed by filesystem), `doc.get` on an untouched core returns `{value: null, version: 0}`, `hc events` first emits a snapshot line then JSON-RPC event lines, and `hc server stop` for that session removed only its socket (cleaned up, user's `infra` core untouched).
Pitfalls: (a) Fake and real drift on shapes nobody re-captures. Removed by capturing fixtures from the real binary per new call (the probe pattern above, free with plain programs) and by the schema check failing in e2e when `hc schema` changes under the fake. (b) The fake's `events` stream semantics (snapshot first, then events; stream ending on core loss) are easy to get subtly wrong. Removed by pinning the fake's snapshot/event bytes to captured real output and by R1 below exercising the listener against the real stream. (c) Auto-start-on-any-command (probed) means a "stopped session" scenario cannot be reproduced by simply pointing a real core down; the fake must model stopped/unreadable sessions explicitly, as fake-herdr does.
Not asked: whether the fake pair should live behind one binary that answers to both names by argv[0], or two files sharing state; I assume two files mirroring the two real binaries, since `herdr-app` failing is itself a scenario (window closed).

## Q2. Real e2e: what runs for real, with what agent, and what proves 2a?

Pick: Two real layers, neither inside the `test` check. R1, free: a dedicated e2e command (not part of the check suite) starts a throwaway `HC_SESSION` plus scratch XDG paths per run, drives a stand-in agent program (a small script akrogon ships in tests that reports OSC status, takes its task from argv, writes its return file, and reports by `hc send`) through: start with first task and proof, later send and delivery, listener waking on events including exit and stream-end restart, kill and restart under the same name, label-minted tab and `tab.rename` with the window closed then naming on open (this layer needs a real `herdrapp` throwaway window for the open cases, run attended), the containment wrapper's cgroup, the notices spool draining in `session-status`, and the weights helper. R2, paid, inside the signpost 7a budget: the per-operation per-agent-kind probes the earlier forks already enumerated (start/send/turn/silent-stop/interrupt/handover per kind, codex popup and sandbox cases), run once at charting and recorded; and the single 2a proof run before the deletion leaf lands: one real leaf taken through its whole life (plan, implement, check, merge) on the new engine in this repo or a scratch registered repo, one chart exchange round with real consultants, one watcher check against the running leaf, with logs saved under the chart. Signpost 2a's "shown working" is that R2 run plus the full unit suite green on the new fakes plus R1 green on the installed version pair; the deletion sweep's brief cites all three with dates.
Reason: the check suite runs inside verify sandboxes constantly, without a window and without anyone watching; putting window-dependent or paid-agent tests there buys flakiness at exactly the gate that must stay boring. R1 covers every mechanism except harness truth (turn semantics, popups, status reporting), which only real agents settle, and 7a already budgets exactly one smallest live run per operation per kind — building a paid regression suite beyond that pays per check forever for coverage the probes only needed to buy once. Cost: R1's stand-in agent is one more test program to keep honest (its OSC sequences must match what harnesses emit, confirmed against the R2 probes), and the window-open cases are attended runs, so they are done-criteria executed by a person or the door, not CI facts.
Rejected: real agents in the normal suite (cost, nondeterminism, and a leaf's own verify would spawn paid sub-agents against the operator's real sessions unless hermetically redirected every time). Fake-only confidence (start-and-pane and delivery took several mechanisms on probe-needed terms: minted tab ids, adoption focus, `env`/wrapper pid behavior, codex turn counting — fakes can only assert what we believed when writing them). A window-driven screenshot suite (stale frames behind other windows are documented in the intake; assert on documents, files, and `hc` state, as the patch fork already judged).
Evidence: operator (signposts 2a e2e before deletion, 7a budget); better-than-training: `hc --skill` test isolation line, my throwaway probe (free core, plain program lifecycle, events and doc shapes, cleanup), intake's live-probe method for throwaway sessions, `tests/run-units.test.ts` precedent that real-machine integration exists but is bounded and named; read/run 2026-11-07.
Pitfalls: (a) The stand-in agent drifts from real status/turn semantics and R1 passes while a real kind differs. Removed by pinning stand-in sequences to the R2 per-kind probe transcripts and re-running one real-kind smoke when hc or a harness updates (patch fork's post-update check). (b) R1's window-open steps drive the operator's actual desktop if session env leaks. Removed by the intake probe discipline (dedicated session home, caller terminal selectors stripped) and a hard refusal in the e2e script when `HC_SESSION` is not its own throwaway name. (c) A killed e2e leaves throwaway cores accumulating (any later `hc` call resurrects them, per my probe). Removed by the e2e command deleting its session state tree, not just stopping the server, and by scratch-XDG containment.
Not asked: does the operator want R1 run automatically after every upstream hc/herdr-app update (patch fork's check could call it), given it needs an attended window for some steps? My assumption is manual, at the update restart.

## Q3. Who ports which tests, in what order?

Pick: Each leaf ports the tests of what it changes, in the same landing, with the engine leaf first building the fake pair at the size its own calls need and porting the core suites with it (`next`, `session-routing` becoming env-pinning, `session-reads`, `seat-containment` onto the wrapper and one cgroup read). Later leaves grow the fakes only for the calls they add: watcher ports `observe` fixtures to captured `hc ls`/`hc get` JSON, chart-door deletes the peer script tests with their scripts and ports `door-reset` tests to the events form, notices work ports `slow-merge` and phase delivery tests onto spool files. The deletion sweep removes `fake-herdr.ts`, its references, and the fixtures last, after the 2a proof, and its done-criteria include `grep` proof that no test names herdr.
Reason: main must keep working after every merge because every merge deploys, and a leaf is only proven when its own tests ran on the new substrate; an up-front test leaf would build fakes for calls the engine leaf has not designed yet (largest surface, built by the door by hand per engine 6a), and a final test leaf would leave the engine, watcher, and door leaves merging unproven, which signpost 2a forbids in spirit. Cost: the engine leaf is big — it carries fake-hc v1 plus the largest test port — which is precisely why it is built first by the door itself and split only if the split fork later says so, never by deferring its tests.
Rejected: one test leaf first (speculative fakes; the identity fork's doc and label shapes were only settled across several forks, and a fake frozen early becomes a second spec to maintain). One final test leaf (unproven merges, above). Porting by find-and-replace of fixture text without re-deriving scenarios (several old tests assert herdr-shaped facts — pane repair swaps, `--session` prefixes — whose new equivalents are different behaviors: env pinning, address identity, label filtering; those tests must be rewritten to the new behavior or deleted with the behavior, per leaf judgment).
Evidence: better-than-training: `tests/AREA.md` test inventory by behavior, tests naming herdr today (`session-routing`, `session-reads`, `seat-containment`, `peer-*.test.ts`, `door-reset.test.ts`, watch fixtures), engine-shape Taken 6a (engine built first by the door, main live on every merge), signposts 2a/7a; read 2026-11-07.
Pitfalls: (a) A leaf ports production code but stubs its fake calls permissively "for now", and the strictness ratchet is lost. Removed by the fake's refuse-unplanned default from its first commit, so permissiveness is the thing that takes extra work. (b) Mid-epic, both fake generations coexist (fake-herdr for unported areas, fake-hc for ported ones) and a test could pass against the wrong fake. Removed by the exe-override seam being singular per area: the hc module boundary means a ported file's tests cannot reach fake-herdr at all. (c) Bytecode bundling in `isolation.ts` caches stale fakes across a branch switch. It already keys per worker from source; the new pair follows the same path (stated so the engine leaf does not invent a second bundling route).
Not asked: whether herdr-setup's half of each contract gets its tests ported in the same landing window as the akrogon leaf that needs it; patch-mechanism put contracts on both sides, and my assumption is herdr-setup leaves land and install first (patch Taken ordering), but the tests fork never sequences the two repos' suites against each other.
