## Q1: wake

- D1 pick: replace the 20-minute cron with wake messages from the existing akrogon listener. Operator start performs one full check now and registers this watcher. Relevant crash/lost/blocked/error facts, failed transitions, the silent-stop bound, dependency/state changes and the busy deadline mark the repo for a check. The watcher still judges every open leaf from current state, as today. No CronCreate/CronList/CronDelete dependency remains.
- Use one pending-check flag per active repo, not a message per raw event. While the watcher works, retain the flag. When it is idle/done, send one `/watch-issues tick <root>` by plain hc send. Reuse delivery's outcome handling: no force, no --if idle, no --wait, no blind resend after started false. Reconcile the send turn before trying again. A message is a request to inspect, never authorization to treat its payload as current leaf state.
- The listener's own watcher terminal, a heartbeat, cosmetic title/size changes and the watcher's check ending must not create a new incident. Clear the delivered batch before sending, so events arriving during the check can request one later pass. Listener restart or a missed/resnapshot event performs catch-up after subscribing, including existing failed/missing seats. An old event for a replaced address cannot steer the replacement.
- Busy coverage needs two distinct signals. At busy_since + 60 minutes, a one-shot listener timer emits the existing busy condition, re-reading state before acting and cancelling on idle/replacement. This is the elapsed-time condition itself, not a periodic status scan. Restore overdue deadlines during startup catch-up.
- Lifecycle facts alone do not preserve today's Busy judgment during a long turn. Use native transcript file-change notifications, tied to the shared resolver's current path, to request checks while it remains working, coalesced through the same flag. Refresh the subscription on transcript reset/replacement and tear it down on exit. No listener-side new loop classifier. Missing/unsupported transcripts still use screen judgment on available native status/progress events and the busy deadline. A live probe must establish coverage for screen-only seats; if native events cannot supply it, this is a substrate signal gap for herdr-setup, not permission to silently lose that coverage.
- Cost: listener registration, deadline/subscription lifecycle and potentially more paid watcher checks than the old cron. Coalescing limits duplicate wakes, not total cost. This cost must be visible in the operator choice. No new repair authority, separate watcher daemon or custom event journal.
- Rejected: cron alone or cron plus listener. Both retain scheduled polling against the explicit direction. Rejected: using hc's 15-second heartbeat as an audit clock. That recreates polling. Rejected: status/turn-only wakes with a claim of full parity. A looping tool can stay working indefinitely without changing those facts.

## Q2: observe and act

- D2 pick: keep observe.ts and log-tail's judgment inputs, port their boundary to the resolved session's hc ls filtered by akrogon/repo labels, hc get for current recorded addresses, hc read, and the shared transcript resolver. Preserve unreadable/foreign inventory reporting and every leaf's evidence. Read failures stay gaps. Null/error/blocked, a lost harness and a live replacement shell are distinct states, not aliases for idle.
- Keep today's Waiting, merged-owner, human-prerequisite, failed-cycle and Busy rules. Before any mutation, re-read the phase, required seats, pause state and current address. Two consecutive unproductive recovery cycles or unknown/malformed history remain notify-only. A crash is a wake for judgment, not automatic permission to reopen a merged owner or answer a credential request.
- Read the visible screen before interruption. Codex may report working at a question; Pi may end its turn after printing a question (`INTAKE.md:153-154`). Never answer or dismiss such a dialog. Busy duration alone, a missing log or a bad read is not evidence of a loop. Native done/status does not establish task success.
- For a justified stop, use exactly one `hc keys <address> esc`, spending that seat's once-per-watch stop budget before issuing it. If it is not yet idle/done, retain the correction intent and finish this check. The later status/turn event resumes judgment. Once a fresh read confirms the same current seat/conversation, idle/done and empty input, send one corrective hc message. No second esc and no automatic resend. Missing identity/history after context loss means notify-only.
- Prefer this exact-key path over hc interrupt for this port: interrupt can choose ctrl+c for an unreported program and has an implicit observation timeout, whereas today's allowed stop is one esc. Do not replace agent wait with an interrupt wait. No mid-turn corrective paste unless separately proven safe; the default correction follows the confirmed stop.

Unsupported log-tail formats, including a readable file its decoder cannot parse, take the existing log-unreadable/screen path, not a false claim of a usable transcript.
- Cost: a stop and corrective send can span two watcher turns. That requires carrying the pending intent and spent-stop budget through normal watcher context handover. The watcher must not keep checking for the stop in a loop or hold a turn open awaiting it.
- Rejected: drop log-tail or judge only native status. Those remove loop evidence. Rejected: raw repeated esc, force, blind prompt resend, killing/closing an agent, phase failed, state edits or answering questions. These violate the existing recovery boundaries. Rejected: automate recovery directly in the listener. It has facts, not the watcher's judgment.

## Q3: location, activation and reboot

- D3 pick: the operator starts /watch-issues in a standalone hc-managed Claude terminal for the repo. It can receive hc messages and survives closing the app window, independently of chart doors. Start registers the current qualified address and repo once; stop unregisters it. Repeated start reports the one live owner; multiple owners are reported rather than silently chosen. Registration is a role label on the terminal, not a cwd guess or a persisted dead PID.
- Keep the current seven-day watch limit as a registration expiry, with one native expiry deadline. This avoids turning a bounded watch into an unlimited paid supervisor merely because cron was removed. Session loss ends the watch. The listener marks an unavailable registration visibly and uses the notices path. It never sends work to a keep shell or silently creates another model session.
- After reboot, the engine listener resumes its own startup/catch-up duties. Automatic watcher recovery is inactive until the operator starts a watcher again, matching today's session-loss boundary. Pending leaf failures remain state to inspect when reactivated. Status must distinguish listener alive, watcher active, watcher busy/pending, watcher unavailable and watch expired.
- Cost: the operator still has to reactivate supervision after session loss/reboot, and the watch must run inside hc. Keep Claude as today's configured watcher harness; removing cron does not justify a harness/configuration expansion in this fork.
- Rejected: listener-spawned paid watcher or automatic reboot launch. That changes the operator-only activation rule and introduces unattended spending. Rejected: a watcher outside hc plus a second push integration. Native hc addressing already solves its communication requirement. Rejected: infer active supervision from a persisted label on a finished terminal or a restored shell.
- Evidence: operator signpost 4a and `skills/watch-issues/SKILL.md:3,7-18`, engine-shape/identity/start-and-pane Taken; S1 permission failure report and S3's session-scoped scheduler limits. Date: 2026-11-06.
- Pitfall/removal: duplicate or stale registration wakes the wrong session. Test duplicate start, stop, terminal exit, app close/reopen, listener restart, expired registration and reboot catch-up. No new watcher is created and no watch is claimed when its terminal cannot receive the task.
- Missing question: does the operator want recovery to resume automatically after reboot? That would be a new explicit activation policy. The listener's existence alone does not authorize it.
