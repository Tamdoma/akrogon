# Start-and-pane: independent notes B

Read 2026-11-06. Binding identity names/state and engine decisions are accepted. No agent launched, pane changed or document written. doc.get was read only. Placement, first-task and lifetime claims below still need the approved operation-by-kind probes.
Practitioner search found a real tmuxinator layout failure and documented native split/spawn patterns, but no published hc deployment proving this combined launch contract.

## Q1. Parent lifetime

1. Pick: leaf seats use explicit --no-parent. Consultants and direct-route reviewers use an explicit --parent pointing to their door, without --outlive-parent. Leaf work must survive the short-lived next/phase command or listener restart. Door helpers remain owned by their door. Cost: parentless leaves produce no native parent notes, so the chosen listener/watcher path must cover their failures and explicit report routing must be settled.
2. Rejected: default parent inheritance for leaves, because phase may launch B from A's terminal and accidentally make sibling lifetime depend on A. Also reject --outlive-parent as the leaf default: it preserves an accidental parent/report destination instead of removing that relationship. Reject making all consultants independent, which leaves more work behind when their door ends. --keep is not a substitute for either policy because it restores a shell, not the task.
3. Evidence:
   - Practitioner: Evil Martians' Andy Barnov and Sergey Alexandrovich describe restarting a Sidekiq worker without restarting its neighboring application processes. This is practical evidence for independent worker lifetime, not an hc guarantee. [First-hand Overmind report, 2017-08-07](https://evilmartians.com/chronicles/introducing-overmind-and-hivemind), read 2026-11-06.
   - Operator: this fork's **Carries** requires old workflow behavior and visible agents. `issues/chart/herdr-app/forks/engine-shape.md:32` makes the listener resident, while :33 also launches through phase. Neither launching process should own a leaf's lifetime.
   - Better-than-training: `hc run --help` documents --no-parent, --parent and --outlive-parent. `hc schema`, terminal.run, says child death follows the parent's program ending. The app window closing is a different event. `hc --skill`, **Status, recovery, and cleanup**, says keep never reruns the original command.
4. Pitfalls/removals: prove listener restart and initiating-seat death spare a leaf in an isolated session. Prove door termination ends only its consultant/reviewer children and leaves unrelated leaves alive. Route parentless crash events to watch-issues and demonstrate that route before relying on absent parent notes. Set parent policy inside the start operation rather than asking callers to remember flags.
5. Missing question: when a door's program exits into its kept shell, should its helpers die immediately or only when its terminal is removed? Native default follows program lifetime. Also decide the explicit recipient of parentless leaf reports. Do not make GUI window closure mean cancellation.

## Q2. Named, unfocused leaf tab with A/B panes

1. Pick: hc-native labeled starts, combined with a narrowly scoped herdr-setup placement/naming operation over the versioned core document. Keep one native tab ID per leaf, its slug name, A left and B right. All launches carry the tab/space labels immediately. The start command succeeds only after the requested document placement is acknowledged. Cost: the generic presentation operation needs a supported schema/version boundary and live write proof. doc.get success does not prove doc.set or launch ordering.
2. Rejected: tab.new --argv/--task as the universal start route, because it requires the window, starts through an interactive shell, and its exposed arguments provide neither native parent policy nor no-focus behavior. Also reject labeled hc run alone as a complete solution: its new tab is unnamed. Reject start-unlabeled then keep/retry, which permits invisible work and violates no polling. No invented tab-name label or pane-resize command is assumed.
3. Evidence:
   - Practitioner: tmuxinator user andho reproduced a saved layout with a wrongly sized pane, then fixed it by applying the layout command explicitly. [Issue 651, 2018-09-05](https://github.com/tmuxinator/tmuxinator/issues/651), read 2026-11-06. That supports observing the resulting layout, not assuming successful process launch proves placement.
   - Better-than-training: `herdr-app commands` lists tab.new with name/space/folder/argv/task/mod/props, no focus or parent parameter; tab.rename needs an app command. Installed AGENTS.md **The model** documents labeled adoption and creation of unknown tab IDs. `src/next.ts:568` currently supplies --no-focus, :585 creates the slug-labeled tab, and :604 splits B right. These behaviors need explicit replacements.
   - Better-than-training, live: the read-only `echo '{"jsonrpc":"2.0","id":1,"method":"doc.get","params":{"name":"herdr-app"}}' | hc connect` returned named tabs with native IDs and row/column trees containing terminal addresses and weights. `hc schema` describes doc.set as atomic, version-checked and document-event-emitting. I did not write it or observe its interaction with adoption.
4. Pitfalls/removals:
   - A document edit overwrites newer operator/app changes. Removal: the herdr-setup operation reads the latest version and transforms only the owned tab/seat nodes. On conflict, reread and reapply that same presentation change with bounded API retries. Never retry the agent launch as part of a document-write retry.
   - The helper steals focus, then “restores” over a newer operator action. Removal: change structure without issuing focus commands. Prove an unrelated active pane remains active while a leaf starts, and prove the named tab exists after reopening a closed fixture window.
   - “Visible in the same step” is treated as a later repair. Removal: probe whether native labeled run binds the pane before the harness can execute its first task. If it does not, herdr-setup must supply a bind-before-spawn capability. Do not claim that checking the tree after launch proves there was no invisible interval.
5. Missing question: with the window closed, does “visible pane” mean a terminal already assigned to its persisted tab tree, ready to show on reopening, or must all starts wait for an open window? I recommend the persisted assignment, matching the old server-owned layout, but the operator must explicitly resolve the wording. Also prove caller-minted tab IDs and native adoption do not replace the desired name/tree during launch.

## Q3. Equal consultant column and replacement position

1. Pick: retain equal shares for every supported consultant count. The herdr-setup presentation operation sets a row with A taking half and one right-hand column taking half, with B/C/D/... in order and equal child weights. A replacement changes the terminal in that seat's existing node rather than rebuilding the tab. Cost: one generic document transformation and write/concurrency proof. No special algorithm for three versus four seats belongs in akrogon's workflow code.
2. Rejected: unequal shares, which contradict the binding intake. Balanced half-splits solve only selected counts. Also reject repositioning by focus/keep plus sleep/list retries, and rebuilding all panes on each restart, which can reorder siblings, disturb unrelated panes and discard existing geometry. A direct whole-document overwrite without version checking is not acceptable.
3. Evidence:
   - Practitioner: WezTerm's maintained pane:split documentation demonstrates thirds using a 1/3 split followed by a half split of the remainder, returning the new pane object. It supplies the missing ratio directly rather than requiring lucky arrival order. [Native split documentation](https://wezterm.org/config/lua/pane/split.html), read 2026-11-06. This is implementer guidance, not field proof for herdr-app. andho's layout-replay failure above is the first-hand warning against assuming geometry.
   - Operator: INTAKE.md **Consultant panes: one column, in order** fixes A at 50%, ordered equal-height consultants, and restoration after restart. Its **Agent findings, 2026-11-06** establishes four-seat half-split ordering but not arbitrary counts.
   - Better-than-training: `skills/chart-issues/scripts/peer-create.ts:33` already computes count-dependent ratios on old Herdr. `peer-restart.ts:216` intentionally restarts in place without changing layout. Current `herdr-app commands` gives terminal.keep only terminal/place and pane.split no ratio. layout.resize sizes layout nodes, not this tab's pane tree. My live doc.get returned a flat consultant column with weights, establishing representation only.
4. Pitfalls/removals: prove three and five consultants have equal shares within ordinary cell/pixel rounding, plus a one-seat replacement preserves sibling order and the A/column split. Apply updates to current node IDs and retain unrelated document fields. A deliberate stale-version write must fail without losing a simultaneous user edit. Copying a tab tree from a prior read and replacing the whole live tree does not meet that criterion.
5. Missing question: after the operator deliberately resizes the chart, does restarting one consultant preserve those current proportions or restore the original equal 50/50 layout? I recommend preserving the existing node on replacement, with equal layout established when the roster is created or changed. Also define behavior when the available window is too small to show the requested roster.

## Q4. One start operation and its actual guarantees

1. Pick: one internal start function exposed to skills by a distinct proposed verb, `akrogon seat-start`, shared by engine, chart door and direct reviewer. Preserve existing `akrogon start <slug>` for resuming stopped leaves. Input names the role, repo and leaf/chart, seat, resolved core/space, brief pointer, and the role's recorded harness/model/effort specification. The operation derives names/labels/parent policy, cwd/env and role placement. Return the actual session/address/tab and observed launch/delivery outcome. Cost: this boundary must own partial-start failures and requires a proved presentation dependency from Q2/Q3.
2. Rejected: separate launch recipes in each skill, optional headless/no-pane flags, or reconstructing restart arguments from hc get's original argv/task. These recreate the omissions already recorded in the intake. Also reject making a later prompt depend on a separate user/agent memory step. First task goes with the launch; later sends and ordinary kill/wait operations remain plain hc in skill text.
3. Evidence:
   - Practitioner: WezTerm's native split operation combines program argv, cwd, environment and explicit split target/size and returns the created pane. [pane:split](https://wezterm.org/config/lua/pane/split.html), read 2026-11-06. This supports a complete launch request with returned identity. It does not justify a new general orchestration framework.
   - Better-than-training: `src/next.ts:294` already expands harness templates with the selected model/effort. `src/config.ts:27` holds those templates. `src/stop.ts:97` and `src/akrogon.ts:158` already own the verb start for leaf resumption. `skills/chart-issues/scripts/peer-restart.ts:160` collects launch information before stopping anything, and :197 rejects context-restoring flags for a fresh consultant restart.
   - Better-than-training, important correction: `hc schema` describes RunResult.first_message specifically as “Template runs: whether the first message went in.” It is nullable. Direct harness argv launches cannot universally be checked with first_message.sent. The native template path can check its sent/started/turn result. A direct launch needs its supported per-kind first-task contract and actual acknowledgement/report, not a fabricated sent=true or a new template solely to obtain that field.
4. Pitfalls/removals:
   - A launch reply is reported as task execution. Removal: distinguish terminal creation, committed pane placement, and first-task delivery. Preserve native negative/unknown outcomes. The approved per-kind probe starts a real brief and observes its own report. A startup dialog, unsent task or missing report cannot become success from status alone. Settle the exact runtime acknowledgement in delivery before promising it.
   - Failure after a process exists causes an automatic duplicate launch. Removal: return nonzero with the exact created address and partial outcome, never blindly replay the task. Define owned cleanup for presentation failure so no newly created agent is left running without its pane. Do not remove unrelated or retained finished terminals to free a name.
   - Centrally spawned harness misses environment or sandbox access. Removal: explicitly supply leaf env and preserve Codex --no-daemon plus sandbox network access; prove cwd, scope and an hc report from each configured kind. `hc schema` exposes terminal.run.env; hc run CLI help has no --env option, so caller exports alone are not a demonstrated injection path.
5. Missing question: where are chart-specific harness selections and original restart specs stored so the helper can use them without taking leaf defaults? Also choose a non-conflicting public verb and the cleanup owner for a partially created launch. Clarify whether “start succeeded” promises a process with a pane or an acknowledged first task. Current native output supports different answers for templates and direct argv.

Do not hand off a universal first_message.sent check: the inspected native schema limits that field's delivery meaning to template launches.
