## Q1. Does signpost 1a bind the engine's own hc calls?

Pick: No. 1a binds only steps an agent performs from skill text (door, consultants, watcher, direct reviewer). The engine keeps its hc calls in code behind the existing `src/shell.ts` boundary, limited to a closed verb set: start, get/ls by label, send (prompt), kill/rm, label, events, plus `herdr-app do` tab/pane placement and close.
Reason: engine hc calls have no agent to type them. Prompting a leaf seat is not a bare `hc send`: `dispatchSlot` re-reads state, refuses if the phase moved or the slot is already done, checks busy, applies a prompt grace, and records delivery/failure with attempts and timing (`src/next.ts:703-770, 813-839`). Moving that into skill text means leaf seats prompt each other and duplicate phase logic per harness, which changes the workflow the operator said not to change. Cost: the engine keeps a real hc client surface that needs a fake in tests, and "engine needs it" becomes an available excuse for growth. The closed verb list above is the counterweight and belongs in the engine leaf's done-criteria.
Rejected: 1a binds the engine too. Then dispatch, status reads, and tab close must be performed by an agent from text, so either a new always-on agent runs the lifecycle (a workflow change, and an agent is the least reliable place for exactly-once prompt records) or leaf seats drive each other (every seat needs peer identity and phase rules, and a dead seat drives nobody).
Evidence: operator (workflow unchanged, forks/engine-shape.md Carries, read 2026-11-06); code `src/next.ts:679-770` dispatch guards and records, `src/shell.ts:226-239` single boundary, read 2026-11-06.
Pitfalls: (a) Boundary creep, engine grows hc features skills should do in text. Removed by leaf done-criterion: engine hc verbs limited to the closed set, new verb needs a named engine-only caller. (b) The shared start command (map fork 4) gets two implementations, one in engine one in skill. Removed by design: one `akrogon` start command, engine calls it internally, skills call it as a command.
Not asked: does 1a also forbid new engine code that reads hc state for display only (status, Tasks board), or is read-only display free?

## Q2. What wakes the engine without the plugin, and who installs/restarts it?

Pick: One systemd user service per hc session (templated unit, `HC_SESSION` pinned), installed and restarted by akrogon install/self-update, not herdr-setup. The service runs a small akrogon listener verb that (1) on start runs the startup pair in plugin order, `pull --all` then `next --resume`, (2) follows `hc events --label <akrogon labels>` and runs a targeted `next` pass for the owning leaf, ignoring `working` as today (`src/next.ts:1609`), (3) exits when the stream ends so systemd restarts it and step (1) re-runs as the catch-up pass.
Reason: the listener executes akrogon code and must match the deployed engine version; akrogon already owns this machinery (`systemd/akrogon.slice`, `src/install.ts:37-38,145`; verify/land already run as user units). herdr-setup deployment creates cross-repo version skew: engine expects listener behaviour herdr-setup may not have installed yet. `hc events` has no replay cursor (`hc events --help`, map-merged), so events can only ever be a wake-up hint and the resume sweep on every listener start is what makes missed events harmless. Cost: a new always-on daemon to operate (journal logs, liveness, one unit per session), and a long-running process holds old code after a deploy flip, so deploy must restart it: `src/self-update.ts:277-288` already daemon-reloads and re-links the plugin on deploy; that step becomes daemon-reload plus try-restart of the listener units.
Rejected: herdr-setup installs it (skew above; herdr-setup owns window setup, and per map-merged it has no patch mechanism today). A herdr-app mod (dies with window/layout, UI lifetime). An hc terminal loop (killable by accident, needs a pane home, and its death is silent). Nothing resident, watcher cron only (violates signpost 4a; crash sits up to 20 minutes and only while the operator started a watch). A systemd timer polling `next --all` (operator: no polling; also pays a full scan per tick).
Evidence: operator (signpost 4a, no polling quote, read 2026-11-06); code `plugin/herdr-plugin.toml` startup/event list, `src/self-update.ts:277-288`, `src/install.ts:145`, read 2026-11-06; `hc events --help` filters with no cursor, run 2026-11-06; model-knowledge: level-triggered reconciliation (sweep on start, events as hints) is the standard controller pattern, and systemd `Restart=` for stream followers likewise. No practitioner source found (no web access from this seat).
Pitfalls: (a) Two listeners alive across an update double-wake every pass. Removed by design: one systemd unit per session plus the existing global lock; listener takes a per-session flock and a second instance exits. (b) Events missed while listener or core is down. Removed by the catch-up sweep on start; probes must include core restart mid-leaf (map probe list). (c) Service environment cannot reach the hc socket (`/run/user/<uid>/herdr-core/`, sandboxed codex failed this in the intake). Removed by probe before handoff: run the listener as the real unit in a throwaway session. (d) Listener starts at login before any window/core exists and crash-loops. Removed by design: restart with backoff, and `akrogon status` shows listener state and last-event time so a dead listener is visible, not silent. (e) `pull --all` ran once per herdr start (roughly daily); under a restarting service it can run far more often. Removed by operator/design decision below.
Not asked: what is `pull --all`'s new cadence, and is pull even a listener job? Also: does `akrogon pause/stop` stop the listener or only dispatch (today pause is checked inside next, so listener can keep following harmlessly)?

## Q3. What advances a leaf on success?

Pick: Both, with split roles. Success path: `akrogon phase` on commit wakes the same targeted dispatch `next` would run for that leaf (dispatchLeaf plus dependents), extending today's pattern where phase only wakes merge work (`src/akrogon.ts:79-96`, `mergeWake` at `src/next.ts:1358-1374`). The listener covers everything phase cannot report: crash, exit, blocked, tab closed, phase process killed between commit and wake, hand-run phase moves, and restart/resume.
Reason: a seat runs `phase` mid-turn and stays `working` until its turn ends, so the event path adds turn-end latency and makes the happy path depend on OSC status being right, which it is not for two recorded cases (codex `working` while asking, backgrounded Claude reporting nothing; intake). The operator's rule "the slot sends the message" is satisfied by `phase` itself: it is the slot's message, in code, with the commit as proof. Turn-end events are still the only signal when a seat dies or blocks without calling phase, so dropping them is not an option under 4a. Cost: `phase` calls get slower inside a seat's turn (dispatch can start an agent and place panes), and wake failure must never fail the committed move, so the wake follows the existing finally/report pattern (`src/akrogon.ts:90-96` already treats commit-then-fail as real via `MoveCommittedError`).
Rejected: event-only (today's flow). Keeps status correctness on the happy path, adds latency, and `hc events` turn-fact shapes are still unprobed (map probes). Also `done` in herdr-app means "finished while not looking" and flips to `idle` when seen (herdr-app AGENTS.md model section), so status events are partly about the operator's attention, not the leaf. Rejected: phase-only. A crashed, killed, or blocked seat never calls phase, and `tab_closed` handling (`src/next.ts:1714-1760`) has no phase caller at all.
Evidence: operator ("slot sends the message", workflow unchanged, read 2026-11-06); code `src/akrogon.ts:79-96`, `src/next.ts:1358-1374` mergeWake, `src/next.ts:762-770` dispatch idempotence guards, read 2026-11-06; intake hc status failures (codex question, backgrounded Claude), read 2026-11-06; `hc --skill` on wait/turn semantics, read 2026-11-06.
Pitfalls: (a) Phase wake and listener event race and double-prompt the next seat. Removed by existing guards (global lock, state re-read, done check, prompt grace at `src/next.ts:762-770`) plus e2e done-criterion: exactly one prompt recorded per seat per phase. (b) Phase wake starts seat B while seat A is still finishing its turn in the shared worktree. Removed by keeping dispatch's per-seat busy gates; the trigger changes, the gates do not. (c) A hung dispatch (pane placement pending) hangs the seat's `phase` call. Removed by design choice: wake launches a detached unit (land already runs as `akrogon-land-<attempt>` user unit, src/AREA.md) instead of awaiting inline; `phase` returns after the launch is recorded. (d) Seat commits phase, then its process is killed before the detached wake launches. Removed by the listener: the seat's exit/turn-end event runs the same targeted pass.
Not asked: should the merge queue's own wakes (`mergeWake`, `landedWake`) also unify into the same detached wake unit, so there is exactly one wake mechanism for phase, land, and events? And: when the operator runs `akrogon phase` by hand from a plain shell outside hc, is auto-dispatch wanted or should hand moves stay manual until `next`?
