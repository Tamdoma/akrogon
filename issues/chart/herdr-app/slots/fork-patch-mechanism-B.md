## Q1: what counts as a patch

- D1 pick: use herdr-setup's owned files on public surfaces for this migration. The chosen weights helper uses doc.get/doc.set, notices extend the existing session-status mod, and the global skill is one owned directory with links. Named bin helpers such as herdrapp are legitimate adapters. None of these three selected contracts needs a replacement hc/herdr-app executable.
- Do not shadow hc or herdr-app on PATH. That would make their documented CLI identity ambiguous, invite recursive invocation and complicate self-update and core discovery. Helpers have distinct names and invoke the actual public command/API. Do not edit shipped mods/layouts or app-generated AGENTS.md; use the existing owned clones and metadata.
- Source patches also qualify under the operator's signpost when an actual required gap cannot be implemented on a public surface and source/build access exists. They must live as a reproducible upstream revision plus minimal patch/build/install steps owned in herdr-setup. Source access and an update-safe delivery path are prerequisites, not assumptions. There is no reason to build that machinery before a selected contract needs it.
- Cost: owned clones and helpers still depend on upstream interfaces and need maintenance. Public accessibility does not make the herdr-app document's internal shape a promised stable API. A future source patch would additionally cost release/rebase work, as S2 demonstrates.
- Rejected: binary string/byte edits, overwriting installed assets and a general PATH interception layer. Rejected: assuming the old herdr source or its Windows artifact can patch hc/app. Rejected: waiting for upstream to supply a required migration feature; signpost 3 instead assigns a local solution, with real source prerequisites if needed. Rejected: a maintained application fork or generic patch framework for gaps already solved by public files.
- Evidence: operator forks/signposts.md Taken, especially 3/2a and the simplicity direction; selected start-and-pane/notices/herdr-skill Taken; S1/S2 first, then S3–S6. Date: 2026-11-07.
- Pitfall/removal: a patch is merely a file that never loads. Done criteria: prove the selected layout actually instantiates session-status in both flat and board; prove the loaded build after a real restart/layout activation; prove default and named app homes resolve the intended owned files. A symlink or passing pure test alone does not establish runtime activation.
- Pitfall/removal: a shipped update wipes a direct edit. Existing clone semantics and installer ownership remove that failure class. Keep cloned_from metadata and compare the shipped source when its baseline changes, rather than copying upstream files back over local changes automatically.
- Missing question: does any selected operation still require modifying hc/app itself? If so, name that operation and establish source availability before promising a source-patch leaf. No new-runtime source access is proven here.

## Q2: surviving updates and retiring patches

- D2 pick: one explicit herdr-setup check entry point owns its patch checks. Run it on installation and after each hc/app update, then run the affected akrogon consumer e2e on the actual version pair before calling that pair verified. Report the hc version, app version and herdr-setup revision with the result. Use existing test and check facilities; no new always-on tester, polling loop or compatibility service.
- Keep detection honest: today's installer does not run after an independent binary update, and native auto-update/restart can bypass bin/herdrapp. Therefore “tests run in ./install” alone is not automatic post-update coverage. My minimal pick makes the post-update check an explicit operator step. If unattended detection immediately after native auto-update is required, this fork must name and prove a real trigger before claiming it. Neither a symlink nor the old patched-release version bump supplies that trigger.
- Check functions, not a broad version allowlist. herdr-app check catches mod loading/render errors; pure tests catch local transformations; the existing strict hc boundary catches malformed responses; integration probes catch semantic changes these cannot see. Record versions as evidence, not as a substitute for behavior. Do not reject every future minor version merely because its number is new.
- On a failing check, report the broken patch/operation and preserve its failure evidence. An affected helper exits nonzero without writing a stale document; the notice consumer must not delete an undelivered file; no old-Herdr fallback or silent success. Keep unrelated terminals running. Do not introduce a blanket pause of all akrogon work merely because a UI customization failed.
- When upstream supplies an equivalent feature, prove the installed feature against the same behavior contract, switch the one caller/owner deliberately, then remove the local patch and its installation hook. Keep the behavior regression test. A release-note claim or a detected version is not authority to auto-delete the patch or choose between two runtime paths.
- Cost: an operator must perform the post-update verification until a real automatic trigger is selected. Owned files survive replacement, but compatibility with arbitrary future binaries is not guaranteed. Claiming no maintenance or immediate automatic detection would exceed the inspected mechanisms.
- Rejected: install-time version check alone, akrogon's e2e alone, no check until a user-visible failure, automatic source rebasing/reapplication after each binary update, or selecting native/local implementations dynamically on version numbers. Rejected: pretending native app auto-update can be disabled or intercepted by an undocumented flag; herdr-app --help establishes none.
- Evidence: practitioner S1/S2; local S5/S6; herdr-setup README Look, mods/AREA.md, install and bin/herdrapp; app AGENTS.md Settings/Mods; identity's strict-schema boundary and start-and-pane's version-conflict rule. Date: 2026-11-07.
- Pitfall/removal: passing tests exercise stale code. Include the symlink reload lesson's loaded-build proof in each live update check. Restart only the disposable test window when needed; never restart the person's core to refresh a mod.
- Pitfall/removal: new upstream document structure causes destructive whole-document writes. A weights-helper contract test uses a changed unrelated tab and an injected version conflict, verifies fresh re-read/recompute, and checks only the intended consultant weights changed. The opaque doc API itself does not protect those semantics.
- Missing question: must update detection be automatic even when the native app updates itself after a crash, or is the explicit post-update operator check acceptable? A strict automatic guarantee needs a concrete trigger, not another version comparison in an installer that never runs.

## Q3: upstream and contract tests

- D3 pick: report an actual upstream defect or missing generic capability that required a workaround, with a minimal reproducer, installed versions and the observed contract failure. Use one operator-reviewable feedback draft per distinct gap, not a report for every ordinary local layout, workflow policy or linked skill. Upstream reporting is independent of having a working local solution and must not block the migration waiting for an upstream release.
- The later responsible leaf may draft herdr-app feedback for the operator to review/send, as the command documents. No automatic submission, no private transcripts or credentials, and no feedback command in this consultation. Existing local fork/leaf evidence can hold the reproducer and eventual upstream reference; no separate patch-registry system is needed.
- Test both sides at different boundaries. herdr-setup tests the implementation it owns, with herdr-app check plus pure tests and relevant disposable hc/app probes. Akrogon e2e tests its use of that implementation: real producer, routing to the resolved app home, observed result and its receipt/state update. Neither repo's mocks alone prove the other side implements the contract.
- Notices: akrogon owns the file contract as already chosen. Test actual producer→session-status→notify/delete→akrogon receipt folding across both installed revisions, including window closed/reopened, stale-condition cancellation, failed posting, duplicate consumers and the pending-file rule beyond the sending PID. Keep one contract owner and compatible fixture/reference evidence, not conflicting protocol prose in both repos.
- Weights: herdr-setup proves the public document transformation and conflict behavior; the chart/start integration proves the visible column, unchanged dragged sizes on replacement and no unrelated-tab/focus change. Skill: herdr-setup proves the one canonical source, links and manifest; the real per-harness probe proves discovery and description-triggered use. No startup hooks are added, per herdr-skill Taken.
- Cost: two repositories' checks and one coordinated real integration proof for each shared behavior. This is not duplicating identical unit suites. Each test must demonstrate something that the other boundary cannot catch.
- Rejected: only herdr-setup pure tests, only akrogon's fake consumer, upstream feedback as delivery proof, automatically sending reports, or copying a second implementation/contract into akrogon. Also reject deleting a patch merely because an upstream issue is closed.
- Evidence: operator no-fallback/e2e-before-deletion direction; notices/herdr-skill/start-and-pane Taken; S4's separate shim and retirement condition, S5's current test coverage, S6's check/status surfaces; herdr-app --help explicitly calls feedback a draft for the person to send. Date: 2026-11-07.
- Pitfall/removal: each repo passes against a different revision of the other. Record the actual paired revisions/versions in the shared integration proof and run the same behavior contract after either side changes. A separate report of “both suites green” is insufficient without that pairing.
- Pitfall/removal: an upstream report becomes an unacknowledged human dependency. A draft's owner is the operator; its unsent status is recorded as unsent and never presented as reported. The implementation can still complete when its local behavior and required tests pass.
- Missing question: which leaf owns the coordinated integration run and records the paired versions, and who performs post-update checks afterward? Assign those responsibilities before handoff so neither repo assumes the other already did them.
