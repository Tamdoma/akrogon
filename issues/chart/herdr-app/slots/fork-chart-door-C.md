## Q1. Consultants: start, ask, collect, net
1. Pick: create and restart only through the start command (consultant role, `<prefix>-slot-<letter>`, `--parent` the door, pane placed by it; restart is `hc kill <name>` then the same start, the door never resets a consultant by `/clear` or `/new`). Ask by `hc send <name> "You are slot <L>. Read and follow <brief path>"`, one brief file per exchange as today. Collect by the `<hc from="<address> <name>">done <L>: <path></hc>` reports, which arrive as the door's next input whether it is working or idle; after sending, the door runs one `hc wait --children all` and nothing else: it returns when a message arrives (the report, processed as input), when a child blocks, errors or exits (hc types that note into the door by itself, `hc --skill`: "hc itself notifies you when a child cannot report"), or when every child stopped working, which is the only way a silent turn end becomes visible; `reason: timeout` is a check-in and the door waits again. When it returns with a report missing, delivery Q4 applies: `hc get <name> --json` says `working` (wait again) or idle/done (nudge once, then drop). Judged against the direction: `hc wait` is hc's own signal path for a child's turn end, not a sleep or a poll standing in for one, and it is what this door ran for this chart; the reports themselves need no wait at all. Scripts: `peer-create`, `peer-ask`, `peer-wait`, `peer-anchor`, `peer-restart` and `door-reset` are deleted; `chart-usage.ts` stays (session-id), `direct-guards.ts` stays. Cost: the door's turn is held in the wait while nothing else happens, which is what a lead does anyway; Claude Code may move the wait to the background when input arrives, and its later notification is the same signal.
2. Rejected: no net beyond reports (a last silent stop produces no message and no note, so the door would sit until the operator speaks; E's case); a per-seat `hc wait <name>` only for a late seat (same wait, more rules); hc's child notes alone (they cover blocked, error and exit, not a `done` turn without a report, the case seen live); keeping `peer-wait` logic ported to hc (its `budget`/`signal` vocabulary mapped nothing one to one, INTAKE line 65, and the wait result already says which child stopped); a timed budget per exchange (a timer standing in for the wait's own return).
3. Evidence: own exchanges (above); better-than-training, `hc wait --help` (`all`: until none working, a message ends it; `any`: next news), `hc send --help`, `hc run --help` (`--parent`, `--no-notify`), `hc --skill` "Talk, wait and collect" and "Delegate a task", INTAKE lines 45-54 and 140-145, `skills/chart-issues/SKILL.md` Autopilot drop rule (line 145), 2026-11-06.
4. Pitfalls: a report from a replaced seat (removed: identity Taken, a report from an address the record no longer holds is ignored; the skill compares the `from` address to the seat record); codex sandbox blocking the hc socket so `done` never leaves (removed: config fork's network flag in the harness argv, INTAKE line 179); two reports for one letter after a nudge (removed: the first return file counts, the second is recorded as duplicate); the door compacting mid-wait (removed: the brief paths and the expected set are in the chart's slots folder, re-read on resume, as today).
5. Question: should the door also receive a one-line `<hc>` "ready <L>" from each consultant at restart before the first brief, as the INTAKE cheap readiness check did? It costs one turn per seat; I would not, since the start command's own proof covers it.
