# Fork notes containment: slot D

External practitioner sources: none reachable from this seat (local read-only commands only, no web). systemd behavior below is from local man pages and live units, dated.

## Q1. Is the per-leaf boxing kept, and for which seats?

Pick: Kept, for leaf seats only, exactly as today. Consultants, direct reviewers, doors, and operator terminals stay unboxed.
Reason: boxing is not an old-herdr feature; it is systemd behavior akrogon relies on in three places beyond the slice limits (CPUWeight 20, MemoryHigh/Max, `systemd/akrogon.slice`). First, `callerScope()` derives run ownership from the caller's own cgroup scope name (`src/admission.ts:206-221`), and verify passes carry that scope so their records stay owned by the starting seat; an unboxed leaf seat's cgroup is `app.slice/hc-hold-<id>.service` (verified live on my own terminal, 2026-11-06), which contains no `.scope`, so its check runs would lose their owner. Second, `stop` and reconcile kill by leaf slice, which reaches descendant processes (dev servers, watchers) that `hc kill` on the terminal program cannot be trusted to reap. Third, the resource behavior itself: unboxed leaf builds would compete at default weight with the operator's interactive work. Cost: start keeps the busctl machinery and a per-incarnation scope name, and every leaf-seat restart must re-box.
Rejected: drop boxing (signpost 2a's drop list was for features only old herdr made possible; removing this silently changes run ownership, stop semantics, and resource behavior, against "nothing that works today may break"). Box consultants and doors too (today they are unboxed; putting charting under the leaf slice's weight and limits is a behavior change with no leaf to own the slice).
Evidence: operator directions 2026-11-06 (behavior similar, nothing breaks); better-than-training: `src/scope.ts`, `src/admission.ts:206-221`, `systemd/akrogon.slice`, live `cat /proc/self/cgroup` → `…/app.slice/hc-hold-105b0ede.service` and `systemctl --user show hc-hold-105b0ede.service` → one service per core (MainPID = herdr-core, cgroup.procs holds every terminal of that core), 2026-11-06.
Pitfalls: (a) A boxed seat at MemoryMax gets its whole slice OOM-killed mid-check; unchanged from today, no new guard. (b) Reconcile's slice-keep logic (`src/reconcile.ts:211-233`) must see the seat scope as occupied through cgroup.procs exactly as today; covered by keeping the same unit naming (`paneScope`, `src/scope.ts:16-18`) with the terminal address standing in for the pane id.
Not asked: does the listener service itself run under `akrogon.slice`? It is small and always on; I assume yes for one accounting home, but its limits then share fate with leaf load.

## Q2. Wrap at start, or move hc's pid after start?

Pick: Move after start, reusing today's `adoptShell`/`inOwnScope` with the pid and start time taken from `hc get` instead of `pane process-info`. Start runs `hc run` (Q3 env included), immediately adopts the returned terminal's `pid` into the leaf slice scope before its 60-second first-task follow (delivery Taken), and verifies with the existing cgroup-suffix check (`src/scope.ts:191-211`). A failed adopt is a failed start (seat killed by start, as a failed placement is, start-and-pane Q4).
Reason: the harness stays hc's direct program, so everything already decided around `pid` keeps working untouched: session-id's transcript resolver reads `pid` first, `hc kill` signals the harness itself, and program/status detection sees the real process. The wrapper alternative breaks that: `systemd-run --scope` does not exec in place — the man page says the command "will be executed by systemd-run itself as parent process" (local `man systemd-run`, and akrogon's own code calls that process the wrapper pid, `src/scope.ts:66-70`). With a wrapper, hc's `pid` is systemd-run and the harness is sometimes merely `foreground.pid`, which during a turn is a tool child, so the session resolver would need a special case and could pick a nested agent run, which session-id's corrections explicitly forbid. Cost of moving: a short unboxed window between `hc run` and the adopt, during which already-spawned children would not follow the move (cgroup moves are per-process); the window is start's own next step, before the first model response can spawn tools in practice, but it is not zero, where today the shell was boxed before any agent code ran.
Rejected: wrap in `systemd-run --user --scope` (above; plus unproven signal forwarding from systemd-run to the harness when hc escalates a kill, and `$`-expansion of argv needing `--expand-environment=no` around task text). Box a shell first, then `exec` the harness inside it through `hc send` (recreates old pane flow but loses delivery's first-task-in-argv and its proof). Move the whole `hc-hold` service (it is per-core, holding every terminal including the operator's doors; moving it would box the world).
Evidence: better-than-training: `man systemd-run` --scope parent-process wording, `src/scope.ts:45-70, 147-211`, live hc-hold unit shape (MainPID is the core, so moving one non-main pid out does not empty or stop the holder), session-id corrections (pid first, foreground only when pid holds no transcript, never a nested run); read/run 2026-11-06.
Pitfalls: (a) Herdr-core may notice its program left the holder cgroup (lost-terminal detection, keep recovery replacing it with a shell back in hc-hold). Removed by a gating probe in a throwaway HC_SESSION before handoff: start a terminal, move its pid to a test scope, then verify `hc get`/`read`/`send`/exit detection and a core restart; if the holder breaks, this pick cannot stand and wrap is the only road, with the resolver cost paid then. (b) Children spawned inside the unboxed window stay outside the slice, so slice-stop misses them. Removed by adopting before the first-task follow and by a probe with a harness that spawns a child instantly, measuring the window; reconcile's existing cwd/process vetoes remain the backstop. (c) Pid reuse between `hc get` and the move. Removed as today: the `/proc/<pid>/stat` start-time check in `inOwnScope` refuses a changed start. (d) After a core loss, keep recovery puts a shell back under hc-hold unboxed; the crash path restarts the seat through start, which re-adopts, and no pass prompts an unboxed live seat because dispatch can re-verify scope with `inOwnScope` as allocate does today.
Not asked: if the move probe fails, is a wrapped start with a resolver special case (harness = wrapper's child in the scope's cgroup.procs) acceptable to the operator, or does containment then wait for an hc-side start-in-slice option filed upstream?

## Q3. Seat env arrival, and `HC_SESSION` in systemd-started work

Pick: Leaf env arrives as an `env K=V …` prefix inside the seat argv. `env` execs the harness in place, so hc's `pid` stays the harness (unlike systemd-run), the argv array needs no quoting, and `launch`'s harness check (`src/next.ts:294-302`) validates the first token after the assignments. Consultants keep getting no akrogon env, as today. For systemd-started akrogon work: do not thread ambient `HC_SESSION` (or `HC_TERMINAL_*`) into land, verify, or listener units beyond what each unit already pins. The engine resolves the repo's session per pass and pins `HC_SESSION`/`HERDR_APP_HOME` per hc call with inherited selectors stripped (identity Taken), exactly as land today forwards no herdr socket and resolves the session itself (`src/land.ts:16-32`, its `--setenv` list is PATH, HOME, DBUS only). Verify passes keep their forwarded-names list (`src/verify.ts:648-665`) without hc selectors, so checks get the default core unless the check itself names a session, which throwaway-session e2e checks already do. Run-check inside a seat simply inherits the seat terminal's own hc env as it inherits everything today, which is correct for commands the seat itself runs.
Reason: one transport already decided stays one: delivery took direct `hc run` CLI starts, and adding a second start path through `hc connect` `terminal.run` only to pass four env values (`AKROGON_BASE`, `GIT_EDITOR`, `TMPDIR`, `NODE_DISABLE_COMPILE_CACHE`, `src/next.ts:569-578`) is a parallel mechanism that can drift from the CLI the skills and probes use. The API's `env` is cleaner in isolation but buys nothing the argv prefix does not, since the values are akrogon-computed per leaf either way. On `HC_SESSION`: ambient session env is precisely what identity forbids trusting, because passes run from a seat of another repo, a listener, or an operator shell; per-call pinning removes the whole class. Cost: `hc get` argv shows the `env` assignments (the pi `--session-id` remains findable in argv), and any external tool parsing seat argv must skip the prefix, as `launch` will.
Rejected: `terminal.run` env through the API (above; also start's CLI form for doors would then differ from the engine's API form for leaves). Writing env into the worktree (`.env` is already a written seat file for declared names, but harness processes do not source it before their first turn). Forwarding the caller's `HC_SESSION` into verify/land units (a verify pass for repo A started from repo B's seat would then poke repo B's core; identity's per-call pinning exists to make that impossible). Setting `AKROGON_SCOPE` in the seat env to replace cgroup-derived ownership (env is mutable by the agent and its tools; the cgroup scope name after Q2's adopt gives today behavior for free).
Evidence: better-than-training: `hc run --help` (no `--env`), `hc schema` `terminal.run` env (start fork record), `src/next.ts:569-578, 294-302`, `src/land.ts:16-32`, `src/verify.ts:648-665`, `src/scope.ts:33-42` (session bus address pinning pattern for systemd-started work), identity Taken env pinning; read 2026-11-06.
Pitfalls: (a) An env value containing `=` or a path with spaces: argv arrays carry both without quoting, but the harness check and any logged argv (delivery_error records command argv today) now include env pairs; harmless, stated. (b) A check inside verify legitimately driving hc against the caller's session would silently hit the default core. Removed by probe/done-criterion in the tests fork: akrogon's own suite uses exe overrides, and any repo check needing hc must name its session in the check itself; if a real check needs the caller's session, adding `HC_SESSION` to verify's forwarded names is a one-line config-fork decision, not a default. (c) The systemd-run units akrogon launches from inside a boxed seat inherit the seat's cgroup only by the `--slice` they name, as today; the listener (a service, not a scope) reaching the user bus for `adoptShell` reuses `sessionBusAddress()`, already the pattern for bus-cut callers.
Not asked: should start set `AKROGON_SCOPE` anyway as a belt over the cgroup name, so run ownership survives if a future hc holds terminals in scopes whose names callerScope misreads? I say no (two sources of ownership truth), but the fork does not ask who owns that invariant.
