## Q1: drain and first activation

- D1 Pick drain before activation, across every registered repo. Freeze new non-migration handoffs/manual dispatch, let existing old-runtime work finish, then pause automatic dispatch. No leaf carrying old pane/turn/session ownership crosses the activation boundary. Cost: a bounded maintenance period and coordination across all twelve repos, rather than implementing state migration.
- O1 Reject carrying running leaves onto hc: old pane IDs, delivery proof and process ownership do not describe hc terminals. Reject letting ordinary leaves finish on old herdr after activation: that requires two supported engines. “Zero open folders” is too broad once this chart emits blocked migration leaves. Require zero old-runtime owners, including outstanding land/verify/broadcast work, and permit untouched pending contracts with no allocated legacy state.
- E1 Practitioner: [GitLab's upgrade procedure](https://docs.gitlab.com/update/plan_your_upgrade/) pauses admission, finishes running jobs and checks the upgrade before resuming. It supports drain, not this repository's exact bootstrap protocol. I searched for a directly matching self-deploying runtime replacement and found no exact practitioner case. Operator: signposts Taken 2a/6a. Better-than-training: `~/.akrogon/config.yaml` lists twelve repos; a fresh enumeration of every registered `issues/open` found no folders. That observation expires when handoff writes them.
- R1 Bootstrap trap: the engine leaf itself may be running under old akrogon, and its merge auto-deploys before its completion owner has necessarily closed. The handoff must specify that transition, not claim literal zero while ignoring its own seats. Treat first activation as an attended, serialized step after bootstrap completion, and prove the choreography on a disposable installation before handoff. The existing install lock and release hold are building blocks, not a complete drain gate: the hold matches one SHA only and a later record push can bypass it. If the normal merge cannot meet the drain condition, the fork must explicitly settle the bounded bootstrap exception or activation prerequisite instead of promising an impossible zero. Evidence: `src/self-update.ts:253`, `src/release.ts:29`, `src/phase.ts` commandMerged/completeOwner, `src/next.ts:1366`.
- R2 Pause is not a deployment barrier. `src/next.ts:876` checks pause only for automatic dispatch; nextCommand runs selfUpdate before dispatch, and mergeWake self-updates before its pause check. Therefore freeze manual next/pull, new main pushes and other deploy callers during the short activation interval. Do not pause live leaves first and then expect them to drain automatically. Preserve the previously paused set when resuming.
- R3 First activation must run the new release's installation/deploy logic, finish recording success, then start/restart the hc listener and prove its catch-up. The old running deploy code still executes `herdr plugin link` after flip (`src/self-update.ts:274-288`), and buildRelease only runs dependency installation (`src/release.ts:56`), not the new CLI's install. Test the transition from the actual old installed release, including failure/resume. A test started entirely on the new version misses this problem. Normal unrelated work resumes only when its new path is usable; controlled migration work can proceed first on hc.
- Q1a Missing question: who owns the exact first-deployment entry point, its release hold and the bootstrap leaf's completion/broadcast? This must be a named part of the engine contract, not left for a merge seat to improvise.

## Q2: rollback floor

- D2 Pick never return through `akrogon rollback` to a pre-hc release after activation, even while the old binary remains pending deletion. Before flipping, rollback must refuse a target release that does not declare the hc runtime in its existing package manifest. Missing declaration identifies a pre-cutover artifact and is refused. This immutable artifact property needs no separate machine epoch/config file. Cost: the first hc release has no compatible rollback target, so a defect holds dispatch for an hc repair instead of restoring the retired runtime.
- O2 Reject allowing old rollback until binary removal: it contradicts the single cutover and can send legacy commands into new state. Reject removing rollback altogether: later hc-to-hc rollback remains useful. Reject a separate machine compatibility flag/epoch file. Clearing `previous` once is insufficient as the only enforcement while old deploy/resume writers can repopulate it.
- E2 Operator: no fallback, all behavior preserved. Practitioner E1 also requires matched application/data restoration for rollback, illustrating why swapping a binary alone is insufficient; it does not prescribe our pointer design. Better-than-training: `src/rollback.ts:25` already refuses null/missing previous before `flip(previous)` at :30, then installs and writes success at :37. Today's deploy record points to an old release and has no runtime boundary. The target-runtime check is a proposed new boundary, not an existing guarantee.
- R4 Put the target refusal before flip, install or listener changes, under the existing install lock. Done-criteria: a legacy target recorded as previous is refused with links untouched, failed/resumed deployment does not bypass that refusal, and a subsequent hc-to-hc rollback still works and refreshes the listener correctly. Test against a real pre-cutover release manifest and an hc release. Do not infer compatibility from the binary still being present.
- R5 A normal code revert or direct execution of an archived old installer is outside the rollback command's guarantee. Freeze the cutover interval and remove obsolete installed release trees after the final proof. Retaining an old executable on disk for proof is not permission to activate it. Existing pruneReleases has a retention window and protects previous, so ordinary pruning is not proof of legacy removal (`src/release.ts:150-168`).
- Q2a Missing question: does the deployment failure policy require any recovery other than holding dispatch and deploying an hc repair? Record the chosen recovery with the first activation instead of implying old rollback remains available.
