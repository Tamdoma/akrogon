## Q2. How the id is known
1. Pick: found afterwards per harness from the terminal's `pid` (`hc get --json`, Terminal.pid, the program hc started, not `foreground.pid`, which is a tool child during a turn): claude from `~/.claude/sessions/<pid>.json` `sessionId` (falls back to nothing); codex from the rollout path open in `/proc/<pid>/fd` (`rollout-*-<id>.jsonl`, kind `path`); agy from the `conversations/<uuid>.db` path in `/proc/<pid>/fd` (id only); pi started with `--session-id <uuid>` minted by the start command (`pi --help`: "Use the current directory's existing session with the ID, creating it otherwise"), file found by today's suffix lookup (`src/session-file.ts:11-34`). One module in `src/` (`agentSession(kind, pid)`), one verb `akrogon seat-session <address>` that runs it and writes the result as label `akrogon.session=<value>` on the terminal (`hc label`); the start command calls it after the start proof and prints the value in its JSON, which is what the door's seats.yaml entry and the engine's state take, as the `session` field of today's outcome lines did. Reason: closest to old herdr, which detected the id itself and handed it to akrogon; detection by pid is exact for codex and agy (the file is open) and for claude (pid file), needs no argv change, and follows a `/new` or `/clear` because it reads live process state when re-run. Cost: Linux-only (`/proc`), which akrogon already assumes (`/proc/pressure`, systemd scopes); one undocumented claude file.
2. Rejected: `claude --session-id <uuid>` minted at start (exists, `claude --help` line 224): exact at start but stale after the door's `/clear` handover, and the door's A entry is re-read live today; `codex -c notify=...` labelling the terminal from a hook: the notify payload carries `turn-id`, not the thread id (codex.danielvaughan.com, third-party), and a hook program is a second code path; codex and agy by cwd plus start-time window: ambiguous when two seats of one kind share a cwd; a herdr-setup patch exposing the id through hc: binaries only, no source (map-merged corrections); claude pid file for all cases without the flag option: it is undocumented, so the leaf pins a test that reads a real file and fails loudly when the shape changes.
3. Evidence: better-than-training, `ls -l /proc/<pid>/fd` on t6c and t6g, `~/.claude/sessions/2197513.json`, `pi --help` (`--session-id`, `--session-dir`), `codex --help` (no session flag; `resume`, `fork` only), `agy --help` (`--conversation` resume by id, no set flag), `hc label --help`, `hc schema` Terminal (`pid`, `labels`), 2026-11-06.
4. Pitfalls: `foreground.pid` names a shell child mid-turn (removed: use `pid`); a harness started through a wrapper (`systemd-run`, containment fork) makes `pid` the wrapper (removed: containment fork must keep the harness as the terminal's program, or the lookup walks `/proc/<pid>/task/*/children` one level, tested); a consultant restart changes pid and id (removed: start re-runs the lookup, label overwritten); claude pid file written late (probe before handoff: measure the delay after `working`; the start command reads it after the start proof); codex rotates the rollout on `/new` (removed: the door re-runs `seat-session` before recording, as the exchange rule did with `herdr agent list`); label lost on core restart? (probe: labels persist across `hc update`, low confidence).
5. Question: does the watcher read the label from `hc get` or the state file? I would read the label, so a seat the engine has not touched since restart still resolves.

## Q3. Unknown id
