# Fork notes A: herdr-skill

## Q1 shape
- Pick: a small owned `SKILL.md` with front matter (`name: herdr`, a description saying it applies inside herdr-core or herdr-app, when `HC_TERMINAL_ID` is set or a message arrives in `<hc>` tags). The body is a few lines: you run inside herdr-core; run `hc --skill` before starting, messaging, waiting on or reading agents and programs; run `herdr-app --skill` before changing what the person sees; read `$HERDR_APP_HOME/AGENTS.md` for layouts, mods and keys; never use the old `herdr` CLI. Reason: the manuals are printed by the installed binaries and AGENTS.md is rewritten by herdr-app on every start (its header), so pointing at them stays correct after every update with no copy to refresh. It keeps the operator's intent (content comes from herdr-app's own text) and the operator's mechanism where it works (the skill folder is a symlink, as akrogon's skills are). Cost: one small file to own.
- Rejected: plain `SKILL.md -> AGENTS.md` symlink: AGENTS.md has no front matter, so the harness has no name or description to list, and its 951 lines are mostly mod authoring, not agent coordination (the agent part is `hc --skill`). Generated copy of the manuals: a copy drifts on every hc or herdr-app update unless a refresh hook runs; an extra moving part the pointer avoids.
- Evidence: better-than-training · `~/.config/herdr-app/AGENTS.md` header and `## herdr-core (hc)` section, `hc --skill` (260 lines, no installable skill section despite AGENTS.md's claim), `herdr-app --skill` opening, `~/.claude/skills/herdr/SKILL.md` front matter · 2026-11-07.
- Pitfall: a harness refuses or ignores a skill without valid front matter or one reached through a symlink. Removed by: probe per harness that the skill is listed and loads (part of the map's "skill discovery per harness" probe).

## Q2 owner and homes
- Pick: herdr-setup owns it: `skills/herdr/SKILL.md` in the herdr-setup repo, linked by `./install` with its existing `link` helper (backup of anything already there) into `~/.claude/skills/herdr`, `~/.codex/skills/herdr`, `~/.agents/skills/herdr`, `~/.pi/agent/skills/herdr`, and agy's skill home once a probe names which `~/.gemini/` folder agy reads. The link replaces the old herdr skill folders in the same install step. Reason: herdr-setup already installs everything herdr-app-specific on this machine (README, `install`); the skill is not akrogon's and must work without akrogon (signpost 5a, operator uses agents outside akrogon). The old skill tells agents to use the old `herdr` CLI, which agents in hc should not reach for, so it goes when the new one lands, not at the old-herdr cutover.
- Rejected: akrogon install (akrogon would own a herdr-wide file; operator runs herdr without akrogon). Operator step (manual links drift across five homes).
- Pitfall: the old herdr session (`infra`) still runs during the port and its agents use the old skill. Removed by: ask the operator whether anything still needs the old skill before the new install; the old herdr is removed after e2e proof anyway (signpost 2a).

## Q3 awareness
- Pick: description only, as the operator chose (5a): every harness lists skill names and descriptions in each session, so an agent sees "inside herdr-core" whenever it starts, and the description tells it when the skill applies. akrogon's own seats need nothing more: their tasks and briefs already name hc commands, and messages arrive in `<hc>` tags. Reason: no global instruction file is touched; no per-harness hook.
- Rejected: a SessionStart hook or a gated line in global files (5a refused the line; a hook is a new part per harness).
- Pitfall: descriptions are a hint, not a guarantee; an agent may not load the body. Removed by: a probe that an agent started by `hc run` in a throwaway session, asked an unrelated hc-shaped task ("start a helper and wait for it"), loads the skill and uses hc. If it does not, the description is rewritten, not a new mechanism added.
- Ask: should the skill also tell agents outside hc (no `HC_TERMINAL_ID`) to do nothing, or say nothing at all?
