# Fork notes, patch-mechanism — slot C (Claude Fable 5.1), 2026-11-07

Fact that changes the map's open question: herdr-app and herdr-core are public, Apache-2.0 repositories (`gh repo view herdrdev/herdr-app`, `herdrdev/herdr-core`: private=false, license apache-2.0, pushed 2026-11-06). Source patches are possible. They are still the wrong default, below.

## Q1 What counts as a herdr-setup patch

Pick: only things built on the surfaces herdr-app and hc promise to keep: mods (clones carrying `cloned_from`), layouts, `keys.json`, `settings.json`, `programs.json`, `bin/` helpers that speak the `hc` CLI, `hc connect` (`doc.get`/`doc.set`, `rpc.discover`) or `herdr-app do`, and linked files such as the herdr skill. Reason: these are the only parts with an update contract: the files table marks them "live" and "yours" (`AGENTS.md` The files), clones "are yours and never updated" and record `cloned_from {name, version}` (Layouts, 197-199), an edited shipped file is moved to `<name>-edited` and restored on next start (204-207), the API is published as JSON Schema (`hc schema`). Every herdr-setup item the taken forks already place there is of this kind: the weights helper (`doc.set` through `hc connect`, start-and-pane F1/F3), the notice handler in `session-status` (notices Q1/Q2), the skill folder (herdr-skill Q2). Cost: a gap that no public surface reaches waits on upstream, with a feedback draft (Q3); none of the taken forks has such a gap left (session id went to per-harness lookup, codex `working`-while-asking is a judgment rule).

Rejected:
- PATH wrappers shadowing `hc` or `herdr-app`: `hc` is a symlink to `herdr-core` and `herdr-app` a symlink into `~/.local/share/herdr-app/` (`ls -la ~/.local/bin`); the app starts and updates the core itself (`app.update_core`, "first start after an app update also updates herdr-core", AGENTS.md 665-669) and would call the real binaries while agents call the wrapper, so two behaviors exist at once, and a wrapper that rewrites arguments breaks the moment the CLI changes, silently. Signpost 2a's "no fallbacks" reads against a layer whose whole job is to be bypassed later.
- Source patches like old herdr's: possible now, but "A build from source never updates" (AGENTS.md:674), so a patched app loses auto-update and the core follow-up, and needs the old machinery back: `omarchy-customizations/herdr/ensure-patches` with a path unit, a timer, `flock`, fingerprints and a toolchain pin (README there, units in `systemctl --user list-units 'herdr*'`), the most moving parts of any option. Keep it as the last resort for a gap proven unreachable from public surfaces, after the feedback draft, and then as a fork rebuilt from the exact release tag, never a binary edit.
- Binary edits: no source of truth, no test, gone at the next update; nobody recommends it (web search 2026-11-07 found no maintainer guidance for it).

Evidence: operator (signpost 3 verbatim; corrections 2026-11-06); practitioner: plugin/override-layer guidance (PKP plugin guide "never modify the main application code", docs.pkp.sfu.ca/dev/plugin-guide; Webasyst apps docs; Claude Code issue 55083 proposing a user override layer "like VS Code user settings and Linux `.d/` drop-ins"), read 2026-11-07; this machine's precedent: `omarchy-customizations/herdr/README.md` and `ensure-patches` (source rebuild per update, 2026-09-19), `herdr-plugins/*/herdr-plugin.toml` (old plugin API, "local plugin (patch)"); live: `~/.config/herdr-app-sessions/infra/AGENTS.md` lines 74-91, 187-215, 663-675; `hc schema` method list; `herdr-app commands` (`layout.clone`, `mod.clone`, `layout.reset`, `app.update`, `app.update_core`); `herdr-setup/mods/AREA.md` ("Clones of shipped mods carry `cloned_from`; after a herdr-app update, diff them against the shipped copy").

Pitfalls: (a) a symlinked mod folder did not hot-reload in 0.1.13 (`herdr-setup/learnings/LESSONS.md`): after an install or edit, switch layouts or reopen the window (operator step already in AREA.md). (b) `HC_SESSION` is undocumented and herdrapp's sessions rest on it (`herdr-setup/README.md` Sessions): a probe after each core update (`herdrapp session list`, `hc ls` inside a session) belongs to Q2's check. (c) A mod cannot import another mod (AREA.md): akrogon-facing handlers stay inside one mod and talk through files and `setShared`.

## Q2 Surviving updates

Pick: no resident watcher. Breakage is noticed by three things that already exist: herdr-app's own surfaces (`<name>.error` files, `herdr-app status` "file/mod errors", the `-edited` toast, "What's new" after an update); herdr-setup's checks in its `issues/config.yaml` (`herdr-app check mods/*`, JSON validity, `bash -n`, `bun test`) run by `./install`, which already is the "run again after an update" verb (README, AREA.md mono icons) and gains two lines: print the installed `herdr-app --version` and `hc --version` next to the versions the repo last passed against (one `versions` file committed by the leaf that verified), and run the checks; and akrogon's side, where every patch's contract is a file or CLI contract pinned by an e2e test (tests fork) and its live records already show a break (a notice file left `pending` with the window open; a weights helper exit code). When upstream ships the feature: the patch is deleted and the caller moves to the shipped surface in the same leaf, no fallback kept (2a); each patch's AREA.md line names the upstream gap, the feedback date and the condition for removal, so the deletion is a check, not a memory. Cost: the operator runs `./install` after an update to get a verdict before the window shows one.

Rejected:
- A path unit plus timer on the binaries (today's old-herdr pattern, `herdr-patches.path`/`.timer`): built for source rebuilds that take minutes and can fail; public-surface patches fail visibly and cheaply, and the timer is the polling direction (b) forbids. If one patch ever needs a source rebuild, that machinery comes back with it, not before.
- A version pin refusing updates: the app updates itself and only a source build stops that (AGENTS.md 665-674); pinning means the rejected option above.
- Nothing until it fails: leaves no removal rule, so patches outlive the gap and drift from shipped code (`cloned_from` versions already lag: `agents-by-tab` 0.1.9 against app 0.1.13).
- herdr-setup tests run by akrogon's e2e: akrogon tests its contract, not another repo's mods (Q3).

Evidence: live `herdr-setup/issues/config.yaml` checks (read 2026-11-07), `install` (safe to run again), `mods/*/mod.json` `cloned_from` versions, AGENTS.md Changing things safely (`<name>.error`, escape hatch), `hc update --help` (`--version X` floor, `--force` for another protocol generation); operator 2a and the 2026-11-06 "no polling" clarification.

Pitfalls: (a) a core protocol-generation jump is not taken by the app's own core update ("of the same generation") — `./install`'s version print shows it; the weights helper and notices run against `hc schema`, so akrogon's e2e is the test. (b) `herdr-app check` validates the initial render only (AGENTS.md); the notice handler's `watchFolder` path is covered by the bun test and the akrogon e2e, not by check. (c) An update arriving mid-session restarts the window only on the operator's Restart; core-side terminals keep running (AGENTS.md 665), so a seat is never lost to an update, but a notice may wait until the restart: already `pending` by design.

## Q3 Upstream and tests

Pick: every gap that needed a patch gets one `herdr-app feedback <text>` draft for the operator to send, recorded in the patch's AREA.md line with the date and "drafted" or "sent"; this is today's practice (codex `working`-while-asking was reported this way, INTAKE.md:154; old herdr's `herdr-plugins/herdr-registry-durability/REPORT.md`). Tests in both repos, each on its own half of a plain contract: herdr-setup tests the mod or helper against the real app (`herdr-app check`, `bun test` over the pure module beside `main.js`, as its four tests do today); akrogon's e2e in the throwaway session tests the contract it depends on (notice file written and gone, weights set and re-read, skill folder linked) against the real hc and herdr-app, failing clearly when herdr-setup is not installed rather than skipping. No shared test code across repos. Cost: a contract change is two leaves, one per repo, landed herdr-setup first.

Rejected: feedback only when the operator asks (gaps then go unreported and the removal condition in Q2 never arrives); a single cross-repo test suite (couples two release cycles for a file-shaped contract).

Evidence: `herdr-app --help` (`feedback <text>` drafts for the person), `herdr-setup/tests/` (four `*.test.js`), notices Taken ("pinned by an e2e test in both repos"), signpost 7a (one smallest live run per operation in a throwaway session).

Pitfalls: (a) a feedback draft the operator never sends: the AREA.md line says "drafted" until the operator marks it sent (operator step). (b) akrogon e2e needs herdr-setup present on the test machine: the tests fork names it as a prerequisite checked at test start.

## Questions this fork does not ask
