## Challenge against intent
- F1 — Remove the global run permit as decided, but do not equate this with eliminating waiting. Excess runnable work waits for CPU, allocation can stall at MemoryHigh, and MemoryMax can kill work. The line can move from visible admission into slower tests and retries. Source: guarantee Taken; systemd/akrogon.slice:7–10; [systemd resource-control](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.resource-control.xml), CPUQuota/MemoryHigh/MemoryMax.
- F2 — One measured core run used 15.9 GB peak, 409 Chrome processes and 8.3 CPUs average; two comparable simultaneous runs would demand roughly 16.6 CPUs on average before seat overhead. Four peak memories sum to ~64 GB, six to ~95 GB, before other seats/cache. These are rough overlapping-workload illustrations, not a safe concurrency calculation: peaks, sharing and GB/GiB differ. Twenty active leaves can each delegate up to three workers. Sources: host-test-load/forks/limit-boundary.md:45–49; next.ts:414–460; implement-issue/SKILL.md:55.
- F3 — The earlier 4.3-CPU slice sample covered existing sequential subsets, not the proposed parallel subsets. Multiplying per-run width while removing admission can invalidate the low-load observation. Keep the resource ceiling, but it does not guarantee short tests, zero OOMs or responsive storage. Sources: system-B.md F4; framework run-test-changed.ts:430–440; systemd/akrogon.slice:6–10.
- D1 — I would NOT restore a host-wide test queue. I WOULD retain a small bounded queue of lanes within each run and a finite active-leaf limit. Those prevent creating excess browser work in the first place and are not another whole-run permit. If “no line” prohibits even these, fast, memory-safe completion under arbitrary concurrent demand is not a promise we can make. Sources: framework package.json:168; implement:55; next.ts:458–460; system-B.md S2–S7.

## Load guard
- O1 — Slice alone, unlimited launch: least code, matches the literal decision, but accepts in-slice reclaim, OOM and timeout/retry costs. CPU cap contains consumption, not the number of browsers. Source: systemd/akrogon.slice:7–10; limit-boundary measurement 2.
- O2 — Fixed bounded lane/browser launch width plus bounded dispatch WIP (pick): fewer moving parts than adaptive control, measurable and compatible with removing the host permit. Must cover full-core and subset execution, because one lane can itself fan out to many browsers. Cost: some idle capacity and pending lanes. Sources: framework run-test-changed.ts:430–440; package.json:168; host-test-load/forks/framework-fanout.md Findings (eight core branches and ten site captures).
- O3 — Scale width from observed CPU/memory pressure: consider only after fixed-width measurements. Independent runs observing spare memory can all launch together; reducing width does not retire already-live browsers. Avoid oscillation with bounded changes and hysteresis, but that is more machinery and still not an atomic memory reservation. Inference from shared limits and absent per-run accounting, system-B.md M6; no tested controller exists in the inspected launch path.
- O4 — Memory-aware start gate: if it waits, it is a queue; if it refuses and callers retry, it can become repeated failed work. Do not disguise either as no-line. A non-atomic memory snapshot cannot guarantee safe simultaneous starts. Inference from concurrent starts, next.ts:429–460 and systemd MemoryHigh/Max semantics.
- D2 — Pick O2 as the approach, NOT a numeric width yet. Agree separately that finite WIP and pending intra-run lanes are allowed. Keep O1 as the explicit cheaper alternative with its failure cost. This reopens host-test-load's framework-fanout no-change decision, not its prohibition on TasksMax. Source: framework-fanout Taken; limit-boundary Taken.

## Dispatch WIP
- O5 — Keep max_active 20: preserves coding overlap, but the counter counts leaves, not simultaneously testing seats/workers. Source: next.ts:414–424; implement:55.
- O6 — Smaller fixed max_active trial (pick before building a controller): compare 4 then 8 active leaves under the same runner widths and comparable work. These are trial points, not claimed safe values; even four leaves can produce twelve workers. Measure merges/hour, oldest unfinished age, test timeouts and memory pressure. Risk: too few active leaves starves tests while agents code. Sources: next.ts:414–460; implement:55; system-B.md E5.
- O7 — Pressure-aware dispatch: can stop adding leaves, cannot stop existing leaves multiplying tests. Add only if the fixed trial shows arrival bursts remain a problem; define resume hysteresis and do not evict existing leaves. It is upstream backpressure and must be named honestly. Source: next.ts:458–460; system-B.md M1.

## Framework test-cost
- D3 — subset-speed: bounded parallel selected lanes, starting with a measured small width, rather than copying unrestricted --parallel or retaining sequential forever. Compare exactly the same selected list/revision under concurrent-run load, preserve exits and isolation, and include browser peak memory. Risk: fixture collisions and multiplicative inner fan-out. Current evidence is 101 selected scripts in 13.76 min versus different all-script runs in 4–4.7 min, not proof of a 3x gain. Sources: framework run-test-changed.ts:430–444; timings.jsonl:9,24,35,547; system-B.md F2–F3.
