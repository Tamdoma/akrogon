# Guarantee — blind notes C

Q1. What must "one heavy test run at a time on this host" mean after this incident, and where is it enforced?

## 1. Pick: 1b, with its scope said plainly

Gate the heavy entry points themselves. "One at a time" after 1b means: a named heavy entry point queues for the permit no matter how it was started (printed run-check command, `bun run test:changed`, or `bun <script file>`), and everything not named stays bounded by akrogon.slice and stoppable, never queued. It does not mean host-wide serialization of anything a seat can type. That residual is written down, same as 1a would write it, but the paths that actually produced both incidents (host-test-load intake and this one) are closed.

- Reason 1: every working version of this gate elsewhere sits in the runner that launches the work, declared on the job/test itself, not in shell convention and not in resource quotas (evidence E2-E5). Bazel's `exclusive` tag, GitLab `resource_group`, GitHub concurrency groups, Jenkins lockable resources all queue at launch. 1b is the only option that puts the gate in a launch path the seat already uses when it improvises: the seat ran `bun run test:changed`, and under 1b that exact command queues.
- Reason 2: 1a's enforcement is seat instructions, and this incident ran through instructions that already existed and were already known. The seat's own brief-4.md:63 contained the exact wrapped command; it still reconstructed the raw form under a self-chosen 300 s timeout, and in the same pass broke two unambiguous rules (log under $TMPDIR, no fixed-sleep polling). Fixing the ambiguous "resolved command" wording is needed under every option, but as the only enforcement it has now failed twice (host-test-load intake: one of six incident runs used run-check).
- Reason 3: the expensive parts already exist. Re-entry reuses the nested path (src/permit.ts:94-98, AKROGON_RUN token verified against the sidecar), the holder/status/timing machinery, and the slice. Framework's heavy paths mostly already funnel through script files: test:changed → run-test-changed.ts (package.json:11), hooks:selftest → run-with-checkout-guard.ts (:8), framework:verify → run-with-root-state-guard.ts + run-verify-stages.ts (:171). run-test-changed.ts already runs its selected lanes sequentially via spawnSync with inherited env, so a gated inner entry point sees AKROGON_RUN and does not queue twice.
- Cost: a second destination (framework), per-repo enrollment forever, and no akrogon-generic guarantee. Other registered repos get nothing until their heavy entry points enroll; akrogon's own test_changed is `bun test --changed` with no script file to gate. Direct lanes (`bun run test:variant-review`, `bun run framework:verify:core` composition at package.json:168) and individual test files stay ungated, bounded only. The guarantee sentence in docs/locks must shrink to named entry points, or 1b repeats limit-boundary's mistake of claiming more than the mechanism does.

## 2. Rejected options

- 1a (keep boundary, instructions + long-run path): rejected as the whole answer, not as a component. Its wording work (write the residual down, define the resolved command) is needed under 1b too. As sole enforcement it re-accepts, one day later, the exact residual limit-boundary foreclosed ("1b run-check only, direct runs bypass as known limit"), and the reason offered is least code. It also silently depends on the long-run fork landing well: that fork is not yet researched or taken, and if it lands as a prose background pattern, 1a has no backstop when the next seat improvises under a tool timeout. Timeout pressure is permanent (pi caps at 600 s, a queued 12 min run plus wait can exceed any cap), so the trigger is not going away.
- 1c (per-run scope + throttled pane scopes): rejected because it does not deliver the sentence being decided. CPUQuota is a bandwidth cap and CPUWeight a share under contention (E6); neither queues anything. 1c gives "one run fast, raw runs crawling beside it", not one at a time, and two browser suites throttling each other is the flake/crash regime already measured (limit-boundary measurement 1: caps turned into core dumps; framework-fanout revisit triggers are browser timeouts under fan-out). It also carries the highest cost: reopens permit-release (per-run units foreclosed, "no per-run units, no process-group kill"), needs new pane quota values through the ceiling-values measurement process, throttles the agent process, builds and cheap single-file tests that legitimately share the pane scope, and still leaks: scope control works from inside the bus cut (proof T7, seat-scope lock), so a same-UID seat can create its own unthrottled scope. Most machinery, still not a fence.
- 1d (considered, proposed and rejected): PATH shims on bun/node placed in seat env, or UID separation (seats run as a user that cannot create scopes or reach the permit lock except through akrogon). Shims break or delay legitimate cheap work (`bun test <one file>`, `bun -e`), are bypassed by absolute paths, and start an arms race inside our own tooling. UID separation is the only option that would make any of this a true fence against the seat, and it breaks the current gh-token, git worktree ownership and herdr pane model; out of proportion to one heavy-run queue on one operator host. Naming it here so the operator round does not mistake 1b or 1c for that class of guarantee.

## 4. Pitfalls, and what removes each

- PF1 Re-entry breaks the operator's plain use: `bun run test:changed` in the framework root checkout re-enters run-check, which throws "No leaf worktree matches cwd" (E7). Removed by a leaf done-criterion, not by hope: direct entry point works from (a) a leaf worktree, (b) the registered checkout root (via the --holder path or an akrogon-side equivalent chosen in leaf design), (c) inside an admitted run with exactly one check_start in timings. Which of those behaviors the root case gets (holder run vs run free) is an operator-visible choice the leaf design must state; silently refusing would break a command the operator runs by hand.
- PF2 Double queueing through compositions: framework:verify calls fast+core, lanes spawn sub-scripts. Removed by the existing AKROGON_RUN check as the only re-entry guard, plus done-criterion (c) above proving one admission. If any entry point spawns children with a scrubbed env, that child re-queues for the permit its own ancestor run-check holds while waiting for it: a deadlock with no wait bound (queue-order lock). The probe in PF1 (c) is what catches this; run-test-changed.ts spawnSync inherits env today (E7).
- PF3 Double setup and evidence drift: the printed checks command includes the install flock and `akrogon guard own-modules` (config.ts withSetup); a direct entry point re-entering run-check with itself as argv does not run install. That matches today's direct behavior, so 1b does not make it worse, but the gated run now looks identical in status/timings (--name test_changed) while its setup differed. Removed only in the evidence fork (does a re-entered direct run count as proof, and must re-entry reproduce the printed command whole, install included?). Flagged here because 1b makes the two paths look the same; this fork must not claim they are.
- PF4 Enrollment drift: a new heavy script added to framework package.json gets no gate, and nothing notices. Removed by deriving the gated list from the repo's checks/merge_checks inner commands at leaf design time and writing the residual (lanes, compositions, single files) into the lock; a mechanical guard (a test asserting each checks inner command's entry file contains the re-entry) is a leaf-level option. Without the guard, drift is a stated cost of 1b, not a surprise.
- PF5 Compositions with no script file (cheap :167, verify:core :168) cannot re-enter; they are reachable directly today (`bun run framework:verify:cheap` is itself a printed check). Removed only by giving them a script-file wrapper in framework (scope cost in that repo) or by naming them in the residual. The operator round should show this list concretely, because "gate the heavy entry points" sounds complete until the composition paths are named.
- PF6 akrogon absent (fresh clone, CI, a seat that strips PATH): the entry point cannot re-enter. Nothing removes this within 1b; the sane behavior is run free when `akrogon` is not on PATH (refusing would break framework for non-akrogon contexts), and that is a named cost: 1b binds the seat that uses the normal tools, it is not a fence against a seat that goes around them. Same-UID residual, stated once here rather than rediscovered.
- PF7 The gated file is editable by the leaf being gated: a framework leaf touching run-test-changed.ts could remove its re-entry and run free. Removed as a practical matter by check-issue's planned-command review and merge_checks rerunning under the permit at merge; not removed mechanically. Acceptable because the failure becomes a visible diff, unlike today's invisible shell choice.
- PF8 Queue blindness gets worse before it gets better: every formerly-direct run now waits, invisibly, behind a 12 min holder with no wait bound (queue-order lock). Nothing in this fork removes that; it is exactly the long-run and queue-visibility forks. 1b must not be sold as fixing the timeout trigger, and shipping 1b before the long-run path exists will increase seat incentive to find the remaining ungated lanes (PF5). Sequencing belongs to handoff, but the dependency should be recorded in this fork's Taken.

## 5. Questions this fork does not ask

- Q-a Where is the heavy/light line for enrollment? heavy-runs foreclosed a per-name light list for run-check, but 1b needs a named heavy list per repo. Is `bun run framework:verify:core` (a composition, ~4-5 min solo) heavy? Is a single browser lane? This fork's options say "heavy entry points" without a test for heavy (wall time? browser fan-out? named in checks?).
- Q-b What does a gated entry point do with no akrogon context at all (operator root checkout, CI, akrogon missing): queue via --holder, run free, or refuse? PF1/PF6 need one answer, and it differs by case; the fork options are silent.
- Q-c Who enrolls the next repo or the next script, and how would anyone know one was missed? There are 11 registered repos; 1b as stated enrolls one. Is enrollment a chart/leaf audit duty, a repo config field akrogon validates, or accepted manual?
- Q-d Should status/timings distinguish a re-entered direct run from a printed-command run (same --name today)? Without a marker, the chart cannot later measure whether seats still reach for the raw form, and the evidence fork cannot tell the two apart from records alone.
- Q-e Is one permit still the right count once direct runs join the queue instead of running beside it? Limit-boundary fixed the count at 1 from a solo load-40 measurement; total heavy demand goes up under 1b, waits lengthen, and queue-order's no-bound rule was taken against run-check-only demand.
- Q-f Does `akrogon stop` remain the only reach for a gated run started from a plain checkout (--holder mode, no leaf slice)? Permit-release Findings already note standalone --holder leftovers sit outside any box; 1b increases that population without asking about it.
