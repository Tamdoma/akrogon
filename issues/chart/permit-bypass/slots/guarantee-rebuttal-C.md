# Guarantee rebuttal C (disagreement only)

- R1 Token removal is incomplete for both gate forms, mine included. Merged: "central validation in akrogon" removes the unvalidated-token bypass. It does not as either form is stated: the decision to skip the gate happens in the framework script, before akrogon runs, and a script-side presence check (my PF2 wording) trusts AKROGON_RUN blindly. The token is readable by any same-UID process from a live holder child's `/proc/<pid>/environ` (my map pass read it), so presence is copyable, not just stale-able. Refuse-form has the same hole in reverse: the script must decide "admitted, run" somehow. The removal needs a named akrogon-side call the script actually makes (a validate verb, or always re-enter and let run-check's nested check at src/permit.ts:93-97 decide, which then needs a loop break for the inner invocation). Until that mechanism is named, neither form should be presented as validating.

- R2 "Refuse (simplest, no changed run semantics)" misstates where 1b-refuse puts its cost. Refusal changes run semantics for every current raw caller at runtime: the 14:38 intake shows that population is live and concurrent (2 workers from different leaves + 1 seat, ~9 permitted runs queued). Those callers fail mid-wave and must be re-briefed leaf by leaf, and the printed command they are told to run still cannot be run by a pi seat inside its 600 s cap against a 12+ min queued run, so refuse depends on the long-run fork landing first in a way re-enter does not. My re-enter root-checkout throw (src/run-check.ts:134) is one defined behavior to pick in leaf design; refuse's failure surface is the whole in-flight worker population. Present both costs, not simple vs convenient.

Record it as undefined-term, not as protocol-prescribed raw.
