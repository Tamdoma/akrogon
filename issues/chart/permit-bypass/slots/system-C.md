# Systems map C — akrogon + framework as one throughput system

Goal: merged leaves/hour. Hard constraint: operator PC usable. Date 2026-10-13.
Sources: practitioner = Goldratt TOC Five Focusing Steps (tocinstitute.org, fetched 2026-10-13), Meadows "Leverage Points" 1999 (donellameadows.org PDF, fetched 2026-10-13), Meta Engineering "Predictive test selection" 2018 (engineering.fb.com, fetched 2026-10-13: in production >95% of test outcomes predicted, a failing test caught for >99.9% of bad changes, large cut in test executions). better-than-training = Little's law L=λW (en.wikipedia.org summary of Little 1961, fetched 2026-10-13), all file:line and records below, read 2026-10-13. Records computed this pass: framework+akrogon issues/timings.jsonl (only ~13 h, timing record is new), log.jsonl (2026-09-11..10-13), merge-attempts.jsonl, kept check logs, slice cpu.stat.

Headline: the operator's PC is not the binding constraint and never was today. At the 14:38 complaint the host was 86% idle (intake, door vmstat) and the slice holds 16 of 32 cores. The binding constraint is permit-minutes demanded per merged leaf, manufactured by broad selection × repeated full-set cycles × invisible raw demand. The permit count of 1 is a policy constraint set far tighter than the physical one: the system already ran 4 full suites concurrently inside the slice without touching the operator's half.

Outflow: merged (framework 92 in last 7 d = 0.55/h, 14 in last 2 d = 0.29/h; akrogon 54/7 d = 0.32/h), failed (framework log `to:failed` 75 of 2575 moves).
- S2 Active seats: capped by max_active=20 (config.yaml, src/next.ts:459-460 counts active leaves only). Uncounted sub-stock: workers, up to 3 per leaf wave (worker-protocol.md:11), each running changed tests. Real test-running population can be several times seat count.
- S3 Queued check requests: ~9 permitted waiters at 14:38 (intake), invisible in status (holder only, queue-order lock). No bound, no dedup, no expiry. Residue: 4 framework check_starts with no check_end in 13 h of timings (dead/killed holders), plus waiters killed by tool timeouts that never appear anywhere.
- S4 Permit-held minutes (the scarce stock under current policy): supply 60/h. Demand per framework leaf at current selection: one full check set = test_changed 731-826 s + selftest ~90 s + cheap ~10-260 s ≈ 14 min; merge verify 332-333 s (merge_covers config.yaml:14 means merge does not repeat the three checks). ## 2. Loops (grounded; [d] = material delay)

Reinforcing:
- R1 Queue → timeout → bypass → contention → queue. No wait bound (queue-order lock) + tool cap 120-600 s (pi shell-timeout.ts:1-8) < 12+ min run + wait, so seats rewrite to raw/nohup (flaky session record, intake). Raw runs share the 16-core quota: holder slowed 731 s solo → 826 s with one raw neighbor (timings), worse at 3 raw (14:38). Slower service → longer queue → more seats hit timeouts. The bypasser gains immediately; the cost is delayed and shared by every queued leaf [d: one service time]. This loop is the incident.
- R2 Contention → flakes → comparison machinery → more runs → contention. Browser/probe flakes under load are a recorded class (ceiling-values T4 playback flake; merge-load-flakes chart records PSI per attempt; framework-fanout revisit triggers). A red with no cause in the diff triggers one same-command retry plus a permitted base-run (implement-issue SKILL.md:38, check-issue SKILL.md:65): one flake costs 2-3 extra check runs' demand. A red merge adds a check.fix cycle with full proof plus exact replay (implement-issue SKILL.md:80,86). Framework merge-attempts: 7 ejected + 1 red of 43, each ejection recycles a leaf into more cycles.
- R3 Leaf age → selection breadth → leaf age. Selection is cumulative: changedPaths = `git diff --name-only $AKROGON_BASE` + untracked (run-test-changed.ts changedPaths), and any unaccounted path selects all 139 lanes (:279). Seats refresh/rebase at pass start and end (implement-issue SKILL.md:40), so the longer a leaf waits (queue, review, merge), the more commits and files its diff accumulates, the wider its next test_changed, the longer it holds the permit. Selected counts in kept logs: 101-106 of 139 typical, all-139 in 3 of 12 sampled, best 59 (older ownership file).
- R4 WIP → burst demand → waiting → more parallel starters. Dispatch allocates up to max_active=20 by active-leaf count alone (src/next.ts:414-460); it does not read permit queue depth, slice throttling, or check demand in flight. By Little's law, at fixed throughput more WIP only lengthens cycle time. Waiting seats are told to overlap work during slow runs (implement-issue SKILL.md:44) and dispatch up to 3 workers per wave, each briefed to run changed tests (worker-protocol.md:11), multiplying S3 demand precisely when the queue is longest.
- R5 Proof freshness × cycles. Evidence is reusable only if run after the latest change to the test and its helpers/fixtures (implement-issue SKILL.md:65); every fix/repair cycle reruns every checks command (implement :86, check-issue :89). Demand per leaf therefore scales with review findings, and findings scale with diff size, which scales with leaf age (R3). Worker runs duplicate A runs: worker runs test:changed in its worktree (brief-template.md:37), then A reruns lane changed tests after each cherry-pick (worker-protocol.md:11) — same selection, paid twice per unit, before implement-end pays it again.
- R6 Safety ratchet on breadth. A missed affected lane surfaces later as a merge ejection or red main, which is expensive and visible; an unnecessary lane costs only seconds, invisibly. So lanes without a detectable owning folder get marked `always` (97/139, S7), shared files map to up to 10 lanes (test-changed-paths.json), and nothing records lane yield (which lanes ever fail), so nobody can ever safely un-mark one. The merged test-changed-shared-files leaf worked as designed (file-level shared map + reference check, framework leaf-speed breadth 2a) and still only moved typical selection from 87%-run-all to ~101-106 of 139, because the floor is `always`, not the map.
- R7 Merge aging. Merge attempts take median 11.2 min wall (framework merge-attempts.jsonl) while verify itself is ~5.5 min; batches in the recent sample carry no extra members, so leaves mostly merge solo. Ready leaves wait for a merge turn → main moves → rebase → conflicts or fresh proof → check.fix cycle (R5) → back of the merge queue. Post-implement time dominating leaf life was already the leaf-speed chart's core finding (90-190 min median after implement, akrogon leaf-speed fix-order Findings).

Balancing:
- B1 Slice ceiling (ceiling-values lock): CPUQuota 1600% + CPUWeight 20 converts overload into throttling inside akrogon.slice, operator's half stays free (proven at 14:40, 86% idle). Side effect: it hides the overload from the operator — the PC feels fine while the leaf system stalls, so the only sensor left is a human reading a watch tab [d: hours, this incident].
- B2 The permit itself: converts excess admitted demand into wait (queue-order lock, wait_ms on check_start). Works only on demand that asks (R1 leaks around it).
- B3 max_active=20: caps seat WIP inflow, but set at roughly the open-leaf count and blind to workers (S2) and queue state, so today it barely binds.
- B4 Merge verify as safety net: merge runs full framework:verify once per batch and merge_covers skips repeating leaf checks (framework leaf-speed breadth lock: "Merge keeps one full framework:verify"). This is what would make a narrower leaf gate safe, and it is currently unexploited: the leaf gate still runs ~75% of the suite per cycle even though merge would catch a miss within the hour [d: until merge].
- B5 Known-red/base-run comparison: drains unrelated reds instead of blocking leaves forever, at the cost of extra runs feeding R2.
- B6 fix_rounds cap (framework config fix_rounds: 8) and `failed` exits: leaves leave the system to the operator instead of cycling forever.
- B7 Operator brakes (pause, akrogon stop on the leaf slice): effective, manual, uninstrumented; feedback path is screenshots.

## 3. Binding constraint, and is permit=1 the right proxy?

- Physical resources are not binding in aggregate: slice averages ~3-4 of its 16 cores over its life, memory 24 of 64 G, host half untouched. They bind only in bursts (30% of cpu periods throttled) — i.e. when several heavy runs coincide, which is a scheduling outcome, not a capacity shortage.
- The binding constraint is serialized heavy-run service time under permit=1, where service time is set by selection breadth (~100+ lanes ≈ 730 s) and repetition (S4: ~33 permit-min per median leaf, 85 min observed tail). Permit supply 60 min/h caps framework at ~1-1.8 merges/h from this constraint alone. Observed 0.55/h (7 d) sits below that cap, so seat cycle time (implement/review/merge seat time, R7) is co-binding; but every raw run and every queue burst pushes the system against the permit cap, and the permit cap is what converts load into the stall the operator sees.
- Permit=1 is the wrong proxy for all three real limits. (a) Shape-blind: a 2 s format check and a 12 min browser suite take the same permit (heavy-runs lock: every run-check, no light list); a varhop `bun test` queued behind framework today. (b) CPU-blind: the limit that set the count was one verify:core averaging 8.3 cores and peaking load 40 (measurement 2) — verify:core runs 8 branches in parallel (package.json:168), while test_changed runs its lanes sequentially (run-test-changed.ts, spawnSync) and many lanes wait on browsers; two test_changed runs overlapped at only +13% duration cost to the holder. One number cannot price both shapes. (c) It ignores the existing physical backstop: B1 already guarantees the operator's PC regardless of permit count. What permit count actually trades is leaf-run duration inflation and flake rate vs throughput — neither of which has been measured per count.
- Goldratt order applied: exploit the constraint (stop feeding it duplicated and over-broad runs: R5, R6), subordinate everything else (dispatch WIP and worker starts should pace to permit queue, R4), elevate last (permit 2, admission by CPU share, quota raise). Today's arrangement does the reverse: WIP is uncapped in practice, the constraint is fed duplicates, and the elevation knob (permit count) is the only thing that was tuned.

## 4. Missing feedback

- M1 Dispatch sees no queue: allocate counts active leaves vs 20 (src/next.ts:459-460); permit depth, wait_ms history and cpu.stat throttling exist in records but no loop reads them. Meadows #6 (information flows) missing at the exact point that creates demand.
- M2 Seats see no queue: status prints holder only (queue-order lock foreclosed a waiter registry). A seat cannot tell a 2 min wait from a 1.5 h wait before choosing foreground/background/raw — R1 is partly an information failure, not only a discipline failure.
- M3 No per-run CPU price: timings record wall duration and wait, never CPU-seconds, lane count, or lane failures (selection causes sit in log prose: "running 106 of 139 leaf scripts"). Without CPU-seconds per check-name, CPU-share admission cannot be priced and L2 below cannot be sized from records.
- M4 No lane yield: nothing answers "which of the 97 always lanes last caught a real failure, and what do they cost per run?" R6 cannot unwind without it. Meta's selection works because outcomes per test are recorded and fed back (practitioner source above); this system records outcomes per check-command only.
- M5 Raw demand is invisible: all 42 framework check_ends in timings are scope=leaf; worker raw runs leave no record at all. The system cannot see S3's true size, so every capacity number in §3 is a lower bound.
- M6 No coalescing: identical work (same leaf, same check, same head) can queue twice; one seat queued its own three checks concurrently today. Records cannot even detect it before admission, because check_start is written inside the permit (src/run-check.ts, timing after admission).
- M7 No aging signal: branch age and diff growth (R3's driver) are nowhere shown to seats or dispatch; a leaf quietly becomes more expensive the longer it waits.
- M8 Flake feedback is per-incident, not per-lane: merge attempts record PSI (merge-load-flakes lock) but flake counts per lane under load are not aggregated, so the cost side of permit=2 cannot be monitored if it ships.

## 5. Leverage points ranked (throughput gain per build cost and risk)

- L1 Workers stop running full test:changed. Prose-only change (worker-protocol.md:11,25, brief-template.md:37, implement-issue SKILL.md:57): workers run the unit's targeted lanes named in their brief; A runs test:changed after the pick, as A already must. Removes the duplicate payment in R5 and most of the raw population in R1/R4 at near-zero build cost. Risk: a bad unit is caught one step later (at pick, not in the worker) — detection delayed, not lost, because the post-pick run already exists. Breaks later: briefs must name lanes honestly or workers run nothing; needs the same "resolved command" definitional fix. Reopens: no code lock; contradicts brief-template's current section-7 design, a skill decision.
- L2 Cut the `always` floor (selection breadth, the big stock). Convert always lanes to folder/read-based ownership using the reads resolver the merged leaf already shipped (.claude/workflow/scripts/test-changed-reads in framework:verify:cheap), prioritized by lane duration × never-fails from M4 mining. If a typical run drops from ~103 lanes to 20-40, service time falls from ~730 s to ~150-300 s and permit demand per leaf falls 3-5×, which dwarfs any permit-count change and also shortens R3's loop. Cost: one or more framework leaves; the mechanism and safety story exist. Risk: a missed lane reaches merge, where full verify catches it same-day (B4) at ejection cost (R2) — bounded, and measurable per lane if M4 ships first. Locks: sits inside framework chart leaf-speed (breadth 2a already taken) and framework-test-scope's open leaf-gate/test-selection forks (akrogon issues/chart/framework-test-scope); verify-speed's "no selector" was about merge verify, not the leaf gate, so no reopen there, but the two charts must not be allowed to contradict.
- L3 Permit 1 → 2, sized by measurement (M-1 in §6), possibly two-class later (sequential lanes vs parallel verify shape). Cheapest elevation: permit becomes N lock slots in src/permit.ts. Expected: up to ~1.7× check throughput for test_changed-shaped runs at +13%-ish duration each (one observed overlap), PC safety unchanged because B1 is the real guard. Risk: two verify:core-shaped runs together saturate the 16 cores and feed R2 flakes; mitigate by watching per-lane flake counts (M8) and by the ceiling-values trigger. Reopens: limit-boundary ("starts at 1" — its load-40 basis was the parallel shape, say so), and heavy-runs if classes exempt small checks from the count. Do not jump straight to CPU-share admission: it needs M3 prices that do not exist; count=2 is the tunable parameter (Meadows #12, weakest form) that buys data for the stronger form.
- L4 Queue visibility, then queue-aware dispatch. Status lists waiters with waited time and depth (information flow, Meadows #6); seats get a wait estimate before choosing how to run. Second step, only with that data: dispatch pauses new leaf allocation while permit depth or recent wait_ms exceeds a threshold, replacing the blind max_active=20 (rules, Meadows #5). Cost: small-medium akrogon change; breaks later: stale waiter entries, flock order is not FIFO so position must be shown as depth not promise. Reopens: queue-order (waiter registry foreclosed), possibly leaf-speed assumptions about max_active. This weakens R1 and R4 without touching enforcement.
- L5 Close the bypass (guarantee fork) + long-run path. Zero direct throughput gain — it will look like a throughput loss as raw demand becomes honest queue demand — but every number above (and any L3 tuning) is meaningless while demand can leak. Sequence it with L4 so newly-queued seats can see what they are waiting for, and with a detached/background whole-command path so the timeout trigger (R1) is removed, not just forbidden. Reopens: as recorded in the guarantee fork (limit-boundary wording; possibly permit-release).
- L6 Coalesce identical admitted work: same leaf + check + head already queued/running joins the existing run instead of queueing again. Attacks R5's A-then-B repetition on unchanged heads. Cost: medium (needs pre-admission identity, M6); risk: joining a run whose conditions differ (env, base) — restrict to exact head+name. Reopens: check-reruns' foreclosed check-record runner, narrowly — that lock's reason was "no savings shown because every logged run was red or on a new head"; under a permit queue, savings are now queue-minutes, which is a new fact pattern to state in the reopen.
- L7 Subordinate dispatch to the constraint by parameter: lower max_active (20 → ~8) as a reversible experiment. At fixed permit throughput, Little's law says cycle time falls roughly with WIP, and fewer concurrent leaves means fewer queue bursts and fewer flakes — merges/hour can rise while seats/h drops. Zero build; confounded by leaf mix, so run as measurement M-4. Breaks: idle seats if set too low while seat-time (not permit) is the day's real constraint. Reopens: nothing (operator config), but contradicts the instinct behind leaf-speed's leaves-as-chunks deferral not at all — it is the same point.

Explicitly low value: raising CPUQuota 1600% (the PC has slack, the queue does not care), raising max_active, shaving selftest/cheap durations (together ~2 min of a 14 min set), merge-seat overhead work before the above (R7 is real but second-order until permit-minutes shrink).

## 6. Smallest measurements that settle the biggest uncertainty

- M-1 Two permitted vs one alone (settles L3 and the permit-proxy question): on an empty-queue window, run framework test_changed solo (baseline exists: 731-733 s), then the same at the same base in two scratch worktrees concurrently (one via run-check, one raw, both inside the slice), sampling per-scope cpu.stat or /usr/bin/time for CPU-seconds, duration, throttled time, exit and any browser timeouts. Repeat once with framework:verify shape if the first is clean. ~35-45 min total, operator present; PC risk bounded by the unchanged slice quota, worst case is today's 4-run state at half scale. Decision it feeds: if concurrent makespan for 2 ≤ ~1.3× solo with no new flakes, permit=2 is justified; if ≥1.8× or flakes appear, permit=1 is a CPU proxy after all and L3 dies.
- M-2 Lane yield and cost mining (settles L2's size, zero runs): parse kept check/verify logs for per-lane durations and failures; rank the 97 always lanes by seconds per run and last real failure. ~20 min scripting over existing logs, no PC load. If the top-cost half of always lanes shows no failures in the record, L2's first leaf has a concrete, evidenced cut list.
- M-3 Selector simulation (settles L2's risk, zero test execution): replay selectionForChanges over the last ~20 merged framework leaves' diffs with always converted to the reads-based set; count lanes selected vs what actually ran, and check that every lane that historically failed for those diffs is still selected. Read-only bun script against git history, ~20-30 min. This is the frozen-pairs style of proof the merged breadth leaf already used.
- M-4 WIP experiment (settles L7): set max_active=8 for one working day, compare merges/h, check wait_ms distribution and leaf cycle time from timings/log against the prior 7 d (0.55 merges/h framework). Config only, reversible in seconds; confound is leaf mix, stated up front. Do not run during M-1.
- M-5 Price a check (settles whether CPU-share admission is even needed after L2/L3): during M-1, record CPU-seconds per check name (test_changed, verify, selftest, cheap) from scope cpu.stat deltas. If test_changed's CPU-seconds ≈ its wall time × ~2-3 cores while verify is × 8+, the two-class question under L3 has real numbers; if all shapes price alike, count-based admission is fine permanently.
