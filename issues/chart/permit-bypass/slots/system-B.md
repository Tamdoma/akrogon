## Loops and delays

R denotes reinforcing, B balancing. These are the loops traceable from inspected surfaces, not a claim to exhaust unknown behavior.

- R1 — **Timeout/relaunch loop, partly observed:** long work or admission wait -> finite tool timeout -> another/background invocation -> more competing work -> longer completion -> more timeouts. Flaky-test-fixes session :47–51 directly establishes timeout then raw relaunch. The first invocation was already raw, so reject the stronger claim that queue delay caused that particular bypass. Pi shell-timeout.ts:1–7 limits tool execution to 120–600 seconds and advises polling. Delays: 2–10 minutes per tool call, then minutes per test. Reliable retained execution plus repeated observation breaks this loop.
- R2 — **Contention/rework loop, plausible but not proven causal here:** overlapping browser work -> timeout/flake -> retry/base comparison/repair -> more test work -> overlap. Retry and repair edges are explicit in implement:38 and check-issue:65,89. Framework timings :11/:13 and :23/:27 show red/green selftest pairs. They do NOT attribute the failures to contention. Full loop needs failure-cause evidence. Delays: check duration, review and repair passes.
- R3 — **Evidence ageing loop:** longer queues -> older worktree relative to moving main -> refresh/restack -> invalidated evidence or conflict -> more checks -> longer queues. Implement:40 binds rerun after refreshed head. Merge:49 binds rerun when tested/pushed equivalence fails. Mechanism exists, incident contribution unmeasured. Delay spans queue plus another leaf's merge.
- R4 — **Selection conservatism loop:** unresolved test reads -> repoAll -> always selection -> more total check work -> slower feedback -> more time before the underlying read boundary is corrected. First three edges are code-backed: framework test-changed-reads.ts:984–988 refuses non-always repoAll and tells authors to mark always. The last prioritization edge is a hypothesis, not logged behavior. No rule retires always after resolution improves. Thus a ratchet is proven, a full human-priority loop is only plausible.
- R5 — **More active leaves -> more requests -> queue** is an accumulation chain, NOT by itself a reinforcing loop. It becomes one only if someone responds to slow merges by starting more leaves. No evidence establishes that response. Do not call max_active alone an instability loop.
- B1 — **Permit:** concurrent requests -> admission wait -> only one admitted execution -> less admitted competition -> service completion frees the permit. `permit.ts:78–97`; 250 ms admission polling, service in minutes. Broken coverage for raw calls, not a broken flock.
- B2 — **CPU/memory controls:** demanded CPU beyond quota -> throttling -> constrained CPU consumption. MemoryHigh pressure slows allocation, MemoryMax provides a hard last boundary. Locks: ceiling-values. CPU enforcement delay is short, but process spawning and browser latency can still suffer inside the slice. This protects the host at the cost of extending S3 residence time.
- B3 — **WIP ceiling:** active leaf count reaches max_active -> new tab allocation stops -> completed/failed leaves eventually free capacity. `next.ts:414–460`. Does not stop existing workers generating checks. Delay until a leaf exits active work can be hours.
- B4 — **Verification and bounded retry:** failures -> repair before merge -> fewer known defects delivered. One retry and base comparison cap blind repetition within a pass, fix_rounds bounds lifecycle repairs. These are quality controls that consume constrained service. Removing them can improve the merge counter while reducing useful output.
- B5 — **Reuse/amortization:** merge_covers avoids rerunning covered checks and equivalent restacks reuse evidence (`merge-issue:41,49`), batching shares a full verification. Existing controls, not missing features. Framework attempts have almost no multi-leaf batches, so benefit is presently limited.
- B6 — **Human stop/pause:** operator sees pressure -> pauses admission or stops leaf -> reduces new/remaining work. Available under host-test-load stop lock. Human observation delay and stopped unfinished work are costs. No such action taken here.

- M2 — Only admitted requests emit check_start/wait_ms (`run-check.ts:173–179`), and status shows holder, not pending/cancelled requests. Raw calls emit no check events. Four unmatched framework starts were observed, one is the current holder and others are not automatically live work. Missing records cannot be counted as active jobs.
- M3 — No durable logical execution identity that a timed-out/replaced seat can reliably reattach to was established. This permits accidental duplicate work and missing exit proof. Fix this before designing content-addressed result reuse.
- M4 — Selection logs expose causes, but there is no measured budget or retirement trigger for always entries. Reference-check correctness is rewarded, broad cost is not. Unknown-read conservatism is required for safety, yet its accumulated cost has no owner beyond future leaf work.
- M5 — No cross-check content/environment equivalence key. Same command name is not identical evidence. Shared fixture state, dirty files, base, environment and revisions matter. Check-reruns deliberately deferred a reusable check-record runner. Do not call every repeated name a duplicate.
- M6 — No per-run CPU/memory peaks, runnable pressure, selected-script cost or desktop latency attached to check records. Slice counters mix all seats/raw/admitted work. A controller based on these aggregate snapshots could raise concurrency at the wrong time.
- M7 — Old branches/queued requests can become obsolete as main advances. Existing rerun/rebase rules drain them by spending more work, not by prioritizing the oldest useful completion. Merge-first ordering remains explicitly deferred, not a forgotten implementation requirement.

2. **L2 — Correct subset execution scheduling.** Selected 101 scripts currently run sequentially while 140 can use eight branches. Trial a bounded scheduling scheme inside ONE admitted run, retaining the CPU/memory cap. Potential high gain with moderate code, but fixture collisions/browser storms and worse timeout tails are risks. Reopens framework-fanout's no-change decision if implementation is chosen. Does not require changing permit count or selecting extra irrelevant tests just to obtain parallelism.
3. **L3 — Complete admission plus long-run execution/wait.** Gate the approved heavy entry-point inventory, preserve valid nested admission, durable exit and reattachment, full configured command, TMPDIR. Essential for predictable service and meaningful measurements. Moderate cost across akrogon/framework/pi as needed. Reopens guarantee coverage only, not automatically permit-release lifetime. Capping raw runs alone protects host resources but leaves competition and missing evidence.
4. **L4 — Remove verified redundant check cycles, not proof obligations.** Compare commands/inputs/revisions within a leaf. Reuse unchanged evidence already allowed, preserve worker-local quick proof plus integration proof where they differ. Fix flaky mechanisms so repair loops actually shrink. Moderate potential gain, low cost for evidenced scheduling corrections, high correctness risk for blanket worker-test removal. Removing required cycles or adding a cache runner reopens check-reruns Q1/Q2. Framework-test-scope forks have blank Taken sections, so they are proposals, not authorization to move full verification after merge.
5. **L5 — Trial two permits under the SAME resource ceiling.** Potential gain when runs wait on I/O or sequential lanes. Low trial cost, moderate implementation cost because sidecar/status assume one holder, risk of in-slice slowdown/flakes and memory pressure. Reopens limit-boundary count=1 and permit-release strictly-one structure. CPU-share/weighted admission is a later option only after cost data exists. Keep ceiling-values until its trigger is explicitly resolved.
6. **L6 — Bound upstream WIP and show oldest pending work.** Trial a smaller active cohort or finish-before-start policy with operator approval. Low operational trial cost, potential large latency improvement, possible throughput loss if over-restricted. Dynamic queue-aware admission/registry is more code and reopens queue-order's registry decision. Lower max_active supplements, never replaces, the locked host resource boundary.
7. **L7 — Amortize full merge verification through existing batches when ready work exists.** Existing batch_limit is 4, almost all historical attempts are solo. Measure simultaneous ready inventory first. Waiting to fill a batch can worsen latency, cross-leaf red attribution/ejections add work. ## Research basis, all read 2026-10-13

- Practitioner/constraint method: Sergio Rattner at Lean Enterprise Institute, [Goldratt's Theory of Constraints](https://www.lean.org/the-lean-post/articles/what-is-the-theory-of-constraints-and-how-does-it-compare-to-lean-thinking/). Identify and exploit the actual constraint, subordinate upstream work, then consider adding capacity. Applied here: reduce check demand and stop bypasses before inventing a resource scheduler. This is an application, not a prediction of savings.
- Primary theory: [MIT queueing text, Little's formula](https://web.mit.edu/urban_or_book/www/book/chapter4/4.4.html). Long-run average WIP = throughput × residence time with consistent boundaries and existing averages. Incomplete nonstationary incident data does not identify those averages.
- Practitioner/systems research: Donella Meadows, [Leverage Points](https://donellameadows.org/archives/leverage-points-places-to-intervene-in-a-system/). Rules, information and delay structure can matter more than a numeric limit. Applied here: always-selection and wait/relaunch behavior deserve attention before only changing permit count.
- Practitioner/CI: Machalica, Samylkin, Porth and Chandra, [Meta predictive test selection](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/). Selection efficiency must be calibrated against regression detection and flakiness. Their large historical-data model is not a recommendation for ML here. Keep the existing deterministic safety contract while removing demonstrably unnecessary scope.
- Practitioner/concurrency: Jason Jacob, [Buildkite concurrency gates](https://buildkite.com/resources/blog/concurrency-gates/), read in B's preceding round. Admit whole runs while allowing controlled internal parallelism. This favors measuring intra-run scheduling separately from concurrent top-level runs.

The recommendations share a constraint: count useful, verified merges per hour, with comparable scope and correctness, while retaining the operator's host limits. A higher merge counter obtained by silently dropping proof or a higher CPU utilization number is not the objective.
