# No-line round — C (blind; own earlier notes reused, merged files not read)

## 1. Challenge to decision 1, against its own intent

- No-line keeps the operator's half safe but moves the blow-up inside akrogon.slice, where it returns as clog. Ceiling is CPUQuota=1600% / MemoryHigh=64G / MemoryMax=96G / no swap (systemd/akrogon.slice:6-10) on 32 threads / 123 GB (host-test-load ceiling-values Findings).
- Memory arithmetic is the binding wall, not CPU: one verify:core peaks 15.9 GB (limit-boundary measurement 2), slice memory.current was already 22.5 GB at a quiet sample today (akrogon.slice/memory.current, read 2026-10-13). Three concurrent core-shaped runs ≈ 22.5 + 3×15.9 ≈ 70 GB: past MemoryHigh, into reclaim. Five ≈ 102 GB: past MemoryMax, kernel kills processes. A killed 12-min run is not a wait, it is lost work plus a rerun — under peak load zero line is slower than a short start delay, which cuts against "fast, no clog" exactly when demand peaks.
- CPU binds second: one core-shaped run averages ~8.3 cores (measurement 2), so two already meet the 16-core quota; slice cpu.stat showed 30% of periods throttled under permit+raw overlap. Throttling lengthens every run, lengthens overlap, raises browser-timeout flake risk (framework-fanout revisit triggers) — a reinforcing loop a queue used to break by accident.
- Peaks align, they do not average out: max_active=20 (config.yaml:1), each leaf may add 3 workers (worker-protocol.md:11), and passes request checks at the same phase boundaries. The 14:38 steady state already had 4 concurrent full runs while a permit existed (INTAKE second report). Remove the permit and the ~9 queued runs from that same snapshot become starters, not waiters.
- My position: no single-file FIFO line, yes to a wide load guard that normally never waits. I would keep a start guard in run-check shaped by the scarce resource: heavy starts proceed immediately while slice memory headroom is healthy, and delay only near the memory wall, e.g. memory.current above a threshold under MemoryHigh or memory.pressure `full` rising (memory.pressure exists on the slice today). If even that is refused, the Taken should say plainly that MemoryMax OOM-kill is the chosen guard under peak, because that is the mechanism that will act.
- Sequencing challenge: do not ship permit removal before load-guard is answered. src/permit.ts:78-125 (in-process flock, sidecar) is exactly the machinery a slots/pressure guard reuses; deleting it now, then rebuilding a guard, pays twice and leaves an unguarded window until the framework test-cost leaves land. CHART.md Destination also still says "holds the run permit" — stale against its own Taken.

## 2. Fork notes

### load-guard
- Options: (a) slice only (current Taken); (b) fixed heavy slots N in run-check/base-run reusing the flock as N slot files; (c) pressure-based start (memory.current/pressure threshold, delay only near wall); (d) per-run width scaling inside framework (subset-speed coupling); (e) per-leaf slice MemoryHigh so one leaf cannot eat the slice.
- Pick: (c) with (b) as the fallback if pressure signals prove too coarse in the concurrency sweep (below); start N/threshold from the memory arithmetic above, i.e. treat ~3 core-shaped runs as the pressure zone, not 1 and not 10. (a) rejected: its degrade mode is OOM-kill. (e) later: leaf slices are created implicitly today (src/scope.ts:17-18 names scopes, Slice= property), per-leaf memory caps need transient slice creation akrogon does not do.
- Breaks later: any run-check guard is bypassed by raw runs, same residual as the permit; it bounds honest paths only, slice remains backstop. Pressure thresholds become a second ceiling-values-style number to defend; page cache inflates memory.current, so threshold on current alone will misfire — pressure `full`, not current, should be primary. A timed-out tool call can leave a pressure waiter orphaned (queue-order fog, unchanged).
- Pitfalls: leaky long-lived servers hold memory and starve all later starts — needs a named escape (operator stop, or wait-cap then start anyway and let slice arbitrate, stated in Taken); nested runs must not double-count (prior token-validation hole: the guard decision must be made by akrogon code, not trusted from env).

### dispatch-wip
- Options: (a) max_active stays 20; (b) static cut to ~8 as a measured experiment; (c) dynamic: allocate pauses while slice memory pressure or heavy-run concurrency is high; (d) count workers in the active budget.
- Pick: (b) now (operator config, reversible in seconds), (c) once load-guard publishes a pressure signal dispatch can read — today allocate counts active leaves vs max_active and nothing else (src/next.ts:459-460). (d) rejected as unbuildable from akrogon: workers are spawned by seats under the skill, akrogon never sees them; worker-duty fork is where that demand is cut.
- Breaks later: too low starves leaves when seat thinking, not test load, is the day's constraint (post-implement seat time dominates, leaf-speed fix-order Findings); dynamic thresholds oscillate (leaves allocated in a burst when pressure dips, recreating the peak). Judge (b) on merges/h and leaf cycle time from timings/log against the 0.55/h framework baseline, not on seat busyness.

### subset-speed (framework test-cost)
- Evidence width is the gap: test_changed runs selected lanes sequentially via spawnSync (run-test-changed.ts) and takes 731-826 s at ~101-139 lanes (timings + kept logs); framework:verify:core runs 8 branches with `bun run --parallel` (framework package.json:168) and finishes 239-265 s (measurements 2/T4). Similar lane mass, ~3× wall difference.
- Options: (a) static lane width (e.g. 4); (b) width scaled to concurrent heavy runs / slice pressure supplied by load-guard; (c) parallelize only classified-isolated lanes, sequential rest. Pick (c) first at width 4, then (b) when load-guard exists. Picking lanes by measured duration (longest-first packing) matters as much as width.
- Breaks later: lanes were written assuming sequential exclusivity — checkout/root-state guards, .temp roots, fixed ports, shared caches, checksums.json handling (run-test-changed.ts CHECKSUMS rules); one browser lane already fans to 10 parallel captures (framework-fanout Findings), so width 4 can mean ~40 browsers per run before other leaves. Interleaved output makes kept logs hard to read without per-lane buffering, which verify already solves via prefixed lanes — reuse that shape.

### always-floor (framework test-cost)
- Pick stands from my systems notes: shrink the 97-of-139 always set using the reads resolver already shipped (test-changed-reads in framework:verify:cheap), ordered by lane cost × never-fails mined from kept logs, safety via merge full verify (framework leaf-speed breadth lock: merge keeps one full framework:verify).
- What breaks later: repo-scanning lanes (validators/scans in the always list) genuinely read repo-wide computed roots — the reads-resolver fix history ("preserve repository-wide computed read roots", framework git log) says part of the floor is honest, not laziness. For those, the fix is incremental scanning (subset-speed territory), not un-marking. Un-marking without lane-yield records reopens silent-hide exactly as breadth 2a foreclosed.
- Pitfall: floor work lands in framework on framework's schedule while the permit can be deleted in akrogon today — do not let the akrogon removal date assume these savings (§1 sequencing).

## 3. Fork to answer next: load-guard

- It decides whether any start-delay machinery exists at all, which reshapes run-check (delete permit.ts or convert it), the width contract subset-speed needs, and the pressure signal dispatch-wip would read. always-floor changes demand size (3-5×) but not the guard's form, so its answer does not invalidate a load-guard taken first; the reverse order (test-cost first) leaves the PC-safety intent resting on MemoryMax for an unbounded framework-side interval.
