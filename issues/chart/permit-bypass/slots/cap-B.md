This explicitly gives up the “half the PC stays free” CPU guarantee, rather than claiming weight replaces it (systemd/akrogon.slice:6–10; issues/chart/host-test-load/forks/ceiling-values.md:22–26; F1 below).

F3. MemoryHigh deliberately throttles allocations through reclaim; zero OOM does not mean adequate performance. CPU weights divide available CPU among active sibling groups, not guarantee desktop latency or reserve idle cores ([kernel cgroup v2, memory.high and Weights](https://docs.kernel.org/admin-guide/cgroup-v2.html)). Hence “apps win” in cap-brief.md:7 needs this qualification.
O1. Upside: remove quota-induced stalls and let idle CPU drain runnable work. Risks: higher peak heat/power, scheduler contention and no fixed desktop headroom; faster concurrent allocation may worsen the already-active memory throttle or reach MemoryMax. Existing memory limits stay, and neither timeout flakes nor faster total completion are guaranteed (F1–F3; cap-brief.md:6).
O2. 2800% is a reasonable rollback/compromise if O1 hurts responsiveness or thermals: permits more work while retaining an aggregate CPU bound, but does not pin four threads for the desktop, can still throttle with spare host CPU, and does not solve memory pressure. No measured result here establishes 2800% as optimal (cap-brief.md:7; kernel cgroup v2 cpu.max).
O3. Keeping1600% preserves the chosen aggregate CPU ceiling and limits peak CPU demand, but prolongs the measured CPU contention, timeout/rerun exposure and time occupied by live browsers. It does not guarantee low heat or prevent memory reclaim stalls, which are happening under that cap now (F1/F2; cap-brief.md:5–6).
