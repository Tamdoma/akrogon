# CPU cap — C

- Pick: **O2 now — raise `CPUQuota` to 2800%, first as a runtime `systemctl --user set-property akrogon.slice CPUQuota=2800%` trial, then change `systemd/akrogon.slice:7` if the trial passes.** It recovers most idle CPU while keeping an absolute blast bound; fully removing the quota gains at most the last 4 threads today but reinstates the foreclosed priority-only design (`issues/chart/host-test-load/forks/ceiling-values.md:22-25`) before browser/memory fixes land.
- Why: my 10 s sample at 20:35 found the slice using 15.5 cores with `throttled_usec` advancing 309 CPU-s, while the host was only 55% busy (17.6/32 threads), so about 14 threads were idle while akrogon work was throttled. CPU pressure inside the slice was `some avg10=89.82, full avg10=47.52` (`.../akrogon.slice/cpu.pressure`). That is quota-created waiting, consistent with A's 206 s → 982/1454 s test-check regression.
- O1 could break: with `max_active=12`, workers/raw runs and ~900 Chrome processes, removing the absolute cap lets a demand spike take every idle thread before weights rebalance; `CPUWeight=20` vs session/app 100 (live `systemctl --user show`) protects shares under sustained contention, not runqueue/memory-bandwidth latency, fan noise or sustained package power. Current package was ~65°C at 55% host load (`sensors`), so heat has headroom but not unlimited headroom.
- O2 could still break: 28 threads is enough to drive allocations into the memory ceiling faster. Memory is already at the brake: slice `memory.current=69.2 GB` against `MemoryHigh=64G` (`systemd/akrogon.slice:8`), `anon+shmem≈61.3 GiB`, `memory.events high=15,703,665`, and memory pressure `full avg10=40.98`. Faster CPU should shorten residence time, but it can convert CPU stalls into reclaim/OOM/flake stalls until the browser fixes land.
- O3 could break: keeping 1600% preserves the measured failure mode — tasks live longer, overlap longer, and hit internal 15 s timeouts, creating red reruns and more browser accumulation. The original quota was explicitly conditional: "if wall time or browser timeouts worsen materially, it comes out" (`ceiling-values.md:17`); the current test timeouts are that signal, even though the formal 4a trigger was later narrowed to `verify:core` (`ceiling-values.md:25`).
- Measurement that changes my pick: during comparable load, trial 2800% for 10 min and record slice cores, Δ`nr_throttled`, CPU/memory PSI, `memory.events`, package temperature, completed checks/timeouts and the operator's desktop feel. If 2800% still throttles materially while ≥4 host threads stay idle, temperatures stay below ~85°C, the desktop is responsive and memory events do not accelerate, remove the quota (O1). If desktop lag, sustained >85°C, or high/max/oom_kill events accelerate at 2800%, return toward 1600% despite the slowdown.
