# Round 16, slot D: waking the warm-up check after claude's late flush

Line numbers are akrogon's main tree (release efd515e1 plus the rounds after it).

## Recommendation: stop discarding hc's heartbeat in this one wait (candidate 4, in concrete form)

The evidence the predicate needs is a file write, but its only wake source is hc facts. That stream already carries a periodic wake that akrogon throws away: herdr-core sends a `heartbeat` line every 15 s on an idle event subscription (`events.subscribe` in `hc schema`), and `follow()` filters it out before any consumer sees it — `src/hc.ts:374-375` ("they hold no fact") and the `continue` at `src/hc.ts:394`. For this wait the heartbeat is not a fact but a re-check tick, and that is all the round-13 predicate is missing: after the done event's failed lookup, the next heartbeat re-runs `answered()` with the unchanged idle snapshot and finds the flushed reply. No assumption about how large the flush lag is (100 ms measured, unbounded in principle: claude flushes the reply with the stop-hook and turn-duration records as a batch, 1ae36dec lines 40-44), and no assumption separates claude from the other kinds.

Shape: an opt-in flag from `waitFor` down to `follow` (`src/hc.ts:444`, `:377`), used only by the warm-up wait (`door-reset.ts:130-136`). On a heartbeat, invoke the callback with the last `Seen` unchanged (the snapshot always precedes heartbeats, so `current` exists; `merged()` is skipped). It must be opt-in, not global: the agy seat-start predicate reads `line.params.type` (src/seat.ts:103) and a `{method:'heartbeat'}` line would throw there. The other two `waitFor` callers (src/seat.ts:98,151 and door-reset's first wait) keep today's behavior. Roughly five lines. Worst cost: a lagging handover waits up to 15 s extra before the start prompt, inside a flow whose other waits are bounded at 600 s. In the operator's terms this is neither polling (the helper creates no timer and reads nothing until the core pushes) nor a watcher (no filesystem subscription, nothing outlives the existing event subscription). It also retires the question for every future "record flushed after done" ordering, in any harness, permanently.

## The other candidates, weighed

- (1) Transient `fs.watch` on the candidate folder: correct and immediate, and `dirname(pre)` is the candidate folder for all four kinds (codex's next rollout even lands in a new date folder only across midnight, and hc events still arrive then). But it is a watcher by mechanism, and it costs more parts than the heartbeat: `waitFor` cannot take an external wake today, so door-reset grows a race loop, watcher lifecycle and its error path, to learn something the core already announces on a timer it owns. Second choice, if sub-15-second confirmation ever matters.
- (2) Bounded re-read after the idle event (fixed grace retries, then back to events): a delay as proof again. It works exactly when the chosen grace exceeds the real lag; made robust it becomes time-sliced re-checking for the whole 600 s bound, which is polling in the plain sense and re-reads candidate transcripts on every slice. The round-12 rule was "remove the race class, not a delay"; this keeps a timing assumption where the heartbeat keeps none.
- (3) Turn-count with the baseline taken when the code's user record is sighted: rejects stray reset turns, but trades the flush-lag assumption for a queue-order assumption — that the prompt record can only be sighted inside the warm-up's own working turn, never while the reset's turn is still the working one (claude records queued input, round-12 evidence, old transcript line 809). It also weakens the proof from "a reply record exists" to "a turn ended after sighting", and agy's steps have no record timestamps to strengthen it with. Two ordering assumptions have now broken in this spot; do not rest the fix on a third.
- `hc send --wait` (core follows the send's own turn): still returns at the same done event, so the lookup after it is early by the same lag. It would need candidate (2) behind it. Not a fix alone.

## Write-after-done in the other kinds

Only claude is measured (door A's probe, and both live incidents). From disk alone the others cannot be cleared: codex rollouts flush promptly (11 completed rollouts today: file mtime within 1 ms of the last record's timestamp, assistant records streamed before `task_complete`), pi's own lifecycle docs put "persist final assistant response" inside the turn lifecycle before `agent_end` (`docs/compaction.md:87-90` in the pi install), and agy commits steps to WAL as they execute (readable live, round-15 probe). All three suggest record-before-status, but none of it is a contract, and the status emitter is a different component from the transcript writer in every harness. That is the argument for the kind-neutral wake above rather than a claude-only patch.

## Fake

In `tests/door-agent.ts` `turn()` (:136-148), claude currently writes the assistant record at :144 and then reports idle at :145 — exactly the order reality inverted. For claude only, swap them with the same 300 ms sleep the turn already uses: `status('idle')`, sleep, then write the reply record. The helper's lookup on the done event (an hc call plus file reads, tens of ms) then deterministically runs inside the gap, so the old helper reaches the bound and the fixed one succeeds — via heartbeat that costs the claude stage case up to one real-core heartbeat (tests run a real herdr-core, `tests/hc-fixture.ts:182,208`), which that one case's time budget should absorb; if it cannot, that is the heartbeat route's stated price, not a flake. Leave codex, pi and agy write-before-idle: that is the only order measured for them, and the helper path under test is the same code either way.
