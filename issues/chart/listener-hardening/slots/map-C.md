## K1 Listener died and stayed dead

- Root cause, two layers. (1) `src/listen.ts:115-121`: every `scan()` rejection goes to `fail`, and `fail` rejects `fatal`, which `listenCommand` awaits (`:127`), so one probe error ends the process. The probe is `src/hc.ts:124-135` `listening()`, which turns only `ECONNREFUSED`/`ENOENT` into "not live" and rethrows everything else; a core closing its socket answers `ECONNRESET`. Count: 207 of the 211 listener exits since 2026-11-07 are `connect ECONNRESET <test socket>` (journal, counted by message); the other 4 are the same error whose stack trace points at `listen.ts:104`. The same `fail` also ends the process on a session stream that ends with an error (`:95`, `follow` throws when `hc events` exits non-zero, `src/hc.ts:391`), on any `wakeWatcher` error (`:50`) and on an `fs.watch` error (`:104`). (2) `systemd/akrogon-listener.service`: `Restart=on-failure` with the manager defaults `StartLimitBurst=5`, `StartLimitIntervalSec=10s`, `RestartUSec=100ms` (`systemctl --user show akrogon-listener`): six exits in 6 s → `start-limit-hit` at 09:24:12, nothing restarts it until a manual start at 09:47:46 (journal). `man systemd.unit` "StartLimitIntervalSec": a unit that hits the limit "is not attempted to be restarted anymore", only a manual start or `systemctl reset-failed` after the interval revives it. The listener is also the only thing that runs `pull --all`, so the deploy path that would restart it never runs.
- Fix (class). (a) `listening()` answers one question, "does something accept on this socket": any connect error is `false`. Nothing else in akrogon wants the distinction (`sessions()` callers at `src/hc.ts:219`, `src/next.ts:207`, `src/transcript.ts:123` all treat not-live as skip). (b) In `listen.ts`, a session's failure is that session's: stream end with or without error → log, unsubscribe, rescan (the success branch already does this, `:90-94`); a wake error → log and continue; `fail` stays only for `fs.watch` on the socket directory, the one error the process cannot work around. (c) The unit carries the last line of defense with what systemd already has: `[Unit] StartLimitIntervalSec=0`, `[Service] Restart=always`, `RestartSec=2`, and `OnFailure=akrogon-listener-failed.service` whose `ExecStart` is the notice verb from notices-on-hc (`akrogon notice --title "akrogon listener failed" --attention`), so a death is seen. `akrogon status` already prints `Listener: live|down` (`src/status.ts:732-736`); keep it.
- Could break: (a) a socket that is live but refuses this client (EACCES, 0.1.17 core under a 0.1.18 client) now reads "stopped" and is skipped silently instead of failing loudly; `resolveSpace` lists it under `skipped_stopped`, which status shows. (c) `Restart=always` restarts after a clean exit too, so `akrogon listen` must never exit 0 on purpose (today it has no such path). The OnFailure unit must not itself fail when herdr-setup's notice handler is absent (the verb writes a file; fine).
- Test that fails before, passes after: in `tests/hc-listener.test.ts` (real-core harness exists, `:164`): while the listener is subscribed to core A, start core B, stop it with `hc server stop` during a scan (its socket resets connections), then end a labelled terminal in A: the listener process is alive and a `next --wake` pass ran. For `listening()`: a Unix server that accepts and immediately destroys returns `false`, a listening server `true`. For the unit: one recorded hand check, kill the listener six times within 10 s, `systemctl --user is-active` says `active` 3 s later; `akrogon status` shows the listener down while it is stopped.

## K2 Test cores share the operator's runtime dir

- Root cause: `tests/hc-fixture.ts:169` gives the core `XDG_RUNTIME_DIR=/run/user/1000`, so hc puts the socket at `/run/user/1000/herdr-core/<session>.sock` (`:184`) and the fixture symlinks it into the scratch runtime (`:203`). The comment (`:3-4`) says the real dir is kept so `systemd-run --user` works in terminals. The core honours the client's environment: `/proc/<core pid>/environ` of the running cores shows the client's `HC_SESSION` (`akt2h4a3-27` etc.) and `XDG_STATE_HOME`, so `XDG_RUNTIME_DIR` passes the same way. systemd clients find the user manager through `$XDG_RUNTIME_DIR/systemd/private` or `DBUS_SESSION_BUS_ADDRESS`; the fixture already links both into the scratch runtime (`:195-196`) and `tests/isolation.ts:71-74` runs akrogon's own `systemctl --user` that way.
- Fix (class): the core gets the scratch runtime (`runtime`, `:190`) as `XDG_RUNTIME_DIR`, so its socket and holder sockets are born under `<scratch>/herdr-core/` and the symlink at `:203` goes. The operator's listener, `sessions()` in every real pass, and the real `hc` in a developer shell never see a test core again. That also removes K1's trigger and the `resolveSpace` refusals below (O1).
- Could break: anything inside a test terminal that reads `XDG_RUNTIME_DIR` for something other than systemd/bus (wayland, pipewire): stand-ins need none. hc's 107-byte socket limit: `/run/user/1000/akt<pid36>-<n>/herdr-core/akt<pid36>-<n>.sock` is about 60 bytes and `:192` already checks. `sweepAbandoned` (`:47-65`) must stop cores through the scratch dir (`XDG_RUNTIME_DIR=<scratch> HC_SESSION=<name> hc server stop`) before removing it; today it removes dead owners' scratch dirs (`:60-64`) without stopping their cores, which is why six `hc-serve-*` units for dead test owners (`akt2h4a2-9`, `akt1ftob-16`, `akt18oo6-15`, `akt2h4a3-13/25/27`, owners not alive) and one `hc-hold` unit are running right now with their sockets gone (`systemctl --user list-units 'hc-*'`, `ps`). `core.stop()` should confirm the core ended (its `hc-serve` unit from `/proc/<pid>/cgroup` inactive) and `discard()` should never run on a reachable core.
- Test: start a fixture core; `/run/user/<uid>/herdr-core/` holds no `akt*` entry and `sessions()` under the real runtime dir does not list it; after `clean()`, no process has `HC_SESSION=<session>` in its environ and no `hc-serve`/`hc-hold` unit names it.

## K3 hc leaks one systemd unit per core

- Root cause: hc 0.1.18 creates `hc-shutdown-<16 hex>.service` at core start, not stop: the serve unit is ordered after it (`systemctl --user show hc-serve-f4c29d88.service`: `After=... hc-shutdown-90fecb01a122098b.service`; the shutdown unit: `Before=hc-serve-f4c29d88.service shutdown.target`, `Type=oneshot`, `RemainAfterExit=yes`, `CollectMode=inactive-or-failed`, `ExecStart=/bin/sh -c :`). It exists so the core stops before `shutdown.target` work; nothing stops it when the core ends, and `--collect` removes only inactive units, so each stays `active exited`. 3,584 are loaded now after the operator's morning clear; the serve unit of the first one listed is already gone.
- Fix (O1, decided): the fixture knows its unit without guessing: core pid from `hc server status --json` → `/proc/<pid>/cgroup` → `hc-serve-<id>.service` → `systemctl --user show -p After` names `hc-shutdown-<id>.service`; after `hc server stop`, `systemctl --user stop hc-shutdown-<id>.service` (collect then removes it). `sweepAbandoned` also stops every `hc-shutdown-*` whose `Before=` names no loaded `hc-serve-*` unit, which clears leftovers of killed runs without touching the operator's cores (theirs still have a serve unit). Upstream removes the class for everyone (the oneshot bound to the serve unit, `BindsTo=`/`PartOf=`, or stopped by the core on exit): one `herdr-app feedback` draft for the operator, per herdr-setup's patch-mechanism rule.
- Could break: one `systemctl` call more per core (50-100 ms on a healthy manager); stopping the shutdown unit of a core that is still running changes its logout ordering, so it runs only after the serve unit is inactive. The 3,584 leftovers are an operator step (Pending), not a test's job.
- Test: `systemctl --user list-units 'hc-shutdown-*'` has the same entries before a fixture core starts and after `clean()`; the unit the serve unit named is not loaded afterwards.

## K4 A test depends on the operator's own core

- Root cause: `tests/hc-identity.test.ts:130` runs `spawnCaptured(['hc', 'schema'])` with the process environment: no `HC_SESSION` pins it, so the answer comes from whatever core the environment names (`default` under verify), and with no core at all hc starts `default` (herdr-setup LESSONS: hc replaces a dead socket and starts a core). `hc schema` is the core's schema, not the binary's: it changed when `default` moved from 0.1.17 to 0.1.18 under the same binary (K4 evidence).
- Fix (class): every `hc` call in tests goes through a fixture core (`core.hc(['schema'])`, `tests/hc-fixture.ts:235`), so the pinned copy is compared with the core the installed binary starts, and the comparison names versions on failure (`hc --version` and a version line stored beside `tests/fixtures/hc-schema.json`): an hc update then fails with "regenerate the pin for 0.1.19", not a diff. A guard in the fixture file: the suite's `PATH` already puts the recording shim first (`:209-211`); make the shim refuse a call with empty `HC_SESSION` instead of passing it to the real hc, which turns any future bare `hc` call into a loud test failure.
- Could break: the schema test now needs a core per run (about 1 s); nothing else.
- Test: the schema test passes with the environment's `HC_SESSION` pointing at a session that does not exist in the scratch runtime (the shim refuses, the fixture core answers), and fails naming both versions when the pinned file's version line differs from `hc --version`.

## K5 (herdr-setup) New tabs open at the end of the tab line

- Root cause: herdr-app inserts a new tab after the shown one and offers no placement: `tab.new` takes `name, space, folder, argv, task, mod, props` (`herdr-app commands`), adoption by labels makes tabs the same way (AGENTS.md:146), `tab.move {id, index}` is the only lever. The draft puts the policy in panel-bar's `render` (`mods/panel-bar/main.js:120-122`) with memory per view (`this.seenTabs`): it runs only where a layout places panel-bar (`layouts/flat.json:82`; `layouts/board.json:35` places the shipped `tabs`), and two windows of one session hold two `seen` sets, so each moves what the other already placed (B's repro). A third defect: `tab.settle` hides a tab from the lists (herdr.d.ts `TabInfo.settled`); if `spaces()` drops it, unsettling makes it "new" and it jumps to the end.
- Fix (class): the policy is layout-independent and window-independent. Home: a mod both shipped layouts already place, `session-status` (`board.json:116`, `flat.json:162`), or one tiny mod listed in both; the routine stays pure (`tailMoves(order, spaces) → {commands, order}` in a routine file, tested by `bun test`). Memory: the arrival order of tab ids per space in `shared()`/`setShared()` (persisted in the session's `shared.json`, "latest change winning", AGENTS.md:88; herdr.d.ts:385-388), not a view field. Rule: a space's tabs are ordered as the arrival list filtered to existing ids, with ids not in the list appended in current order; commands are the `tab.move`s that make the current order equal to that target, which is idempotent, so two windows computing it issue the same moves and the second finds nothing to do. A known id that reappears (unsettled) is not new. Settled tabs are kept in the list (`TabInfo.settled` tells them apart if `spaces()` shows them).
- Could break: a tab the operator drags by hand is kept where dragged only until a new tab arrives in that space (the target order then re-applies the arrival order for the others too); if that is unwanted, the rule becomes "move only ids not in the list to the end" and the list records the resulting order. Two windows writing `shared.json` at once: latest wins, both append the same id, so the lists converge; a lost append re-adds the id on the next render. Remote spaces (`SpaceInfo.machine`): ids carry no prefix in `spaces()`, `tab.move` works per space.
- Test: routine tests: same order plus same spaces in two "windows" give identical commands and the second call after applying them gives none; a tab inserted between others moves to the end in the `board` layout's window; an unsettled tab does not move; a window opened later moves nothing. Live (free, throwaway session, `board` layout): `hc run` with a new `herdr.tab` label while a middle tab is shown → `doc.get` shows the new tab last.

## Other ways a leaf silently stops moving

- O1 Foreign sessions refuse a repo's space. `resolveSpace` (`src/hc.ts:216-260`) reads `doc.get` of every live session; one unreadable session makes "uniqueness unknown", one `sessions()` throw makes "session list failed", and `next` then skips the repo (`src/next.ts:387`, exit 1 only in the journal). Evidence: 10 `uniqueness unknown` and 2 `session list failed` refusals for chart-door-on-hc in the listener log, all while test cores lived in the real dir. K2 removes the trigger; the refusal itself stays correct (a real duplicate must refuse), but it must reach someone: a notice through the notice contract once per cause, cleared when the pass passes, is the same channel the busy and merge-slow notices use (`src/verify.ts:332,352`).
- O2 A hung pass blocks every later pass. `hc()` has no default deadline (`src/hc.ts:93-97`; only `rpc` passes `DISCOVERY_DEADLINE_MS`), and the listener awaits each `akrogon next` child without bound (`src/listen.ts:31-32`) in a single queue. A core that accepts and never answers, or a seat whose `hc send` blocks, leaves the listener "live" in status and never dispatching. Fix: a default deadline on every hc call (the `timeout` option of `spawnCaptured` already exists, `src/shell.ts:31`) and a bound on a pass in the listener (kill, log, run the next one). Test: a fixture socket served by a stub that accepts and never answers makes `hc get` throw `signal SIGTERM`-kind within the deadline; a stuck pass child is killed and a later wake still runs a pass.
- O3 Pass failures are logged only. `{"listen":"pass failed"}` appeared 56 times (48 `next --wake`, 8 `next --resume`) with no notice; `next` exits 1 whenever any leaf was skipped (`src/next.ts:1339`). Same fix as O1's channel: one notice when passes start failing, one when they recover.
- O4 An operator core restart ends the stream with an error. `hc server restart` ("programs keep running", `hc server --help`) closes the events connection; if `hc events` exits non-zero, `follow` throws (`src/hc.ts:391`) and `listen.ts:95` passes it to `fail`: same death as K1 from an ordinary operator action, with no test core involved. Covered by K1 fix (b); add it to the K1 test (restart core A while subscribed, the listener resubscribes and the next turn end runs a pass).
- O5 Stopped leaf after a drain. `akrogon stop <slug>` marks `~/.akrogon/stopped.yaml` and only `akrogon start <slug>` clears it (`src/stop.ts`); the stale mark `framework/relay-obrazac: true` is there now. Not a bug, but `akrogon status` is the only place it shows; the needs-sheet N5 step already names clearing it.
