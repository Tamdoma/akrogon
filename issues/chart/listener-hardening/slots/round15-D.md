## Finding

- F1 (low) One null-payload step anywhere in a conversation makes every read of it throw. `agyStep` requires `step_payload: z.instanceof(Uint8Array)` (`src/transcript.ts`, the schema above `transcriptRecords`), but the real table declares that column as a plain nullable `blob` (`steps` DDL, verified on disk round 14). `transcriptRecords` parses the whole result array with `.parse`, and `answered`/`transcriptByCode` read from position 0, so a single null-payload step — any of the ~140 step types this machine has not produced yet (local survey: 9,069 steps across 65 databases, 0 nulls, only 6 step types seen) — kills the helper mid-warm-up with a ZodError instead of a logged stage, forever for that conversation. The JSONL side of the same reader is deliberately tolerant (a bad line yields `value: undefined`); the agy side should be too: `.nullable()` on the payload with `text: ''`. (`transcriptEnd` is already safe: it selects no payload. The un-closed `Database` on the same throw path dies with the short-lived helper and needs no separate fix.)
