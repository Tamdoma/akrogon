# Round 7: D

## 1. Who writes the flips back to t6x

Disagree with C's automatic desktop-window revert. The writer is the moshi-hook daemon's phone-initiated workspace-focus path; the desktop window does not write this document.

Evidence from the installed binary's call graph (`objdump` over the Go function table in `~/.local/bin/moshi-hook`):

- The only callers of `hc.writeSelection` are `hc.(*Driver).focusHeadless` (0x60cecb), `hc.reselect` (0x60e544) and `hc.(*Driver).documentLayout` (0x6105b2).
- `focusHeadless` is called only by `hc.(*Driver).FocusWorkspace` (0x613a20), the driver method behind the gateway's workspace-focus handlers (`/v1/workspaces/focus`, `/v1/workspaces/layout/focus`). That is a request path: something must ask the daemon to focus a workspace.
- `reselect` is called only by `closeHeadless` and `pruneFinished`; `documentLayout` writes only on its not-found branch, after searching every space/tab/terminal for the recorded selection (search loop 0x610446-0x61052a, write at 0x6105b2). Both are repair paths for a selection whose terminal finished or left the layout. t15 and t6x were live and in the layout throughout (`hc ls --json`: both `state:live`; `herdr-app ls` lists both panes), so neither repair path can explain flips between them.
- The window watcher does not write at all: `hc.watchWindow` (0x612a80) polls the window with `windowCall` on a 2 s ticker and emits events; it contains no `writeSelection` call. The attach followers don't either: `hc.Follow`, `hc.watch` and `hc.(*followSelection).selected` only call `readSelection`. So no host process re-asserts desktop focus into the document, on any timer.
- Timing fits phone activity, not a host timer: gateway prompt log lines alternate panes in step with the flips (t6x prompts 12:06-12:08, t15 prompts 12:09-12:16, t6x 12:18, t6x 12:26:30 then t15 image/text 12:27:08), the desktop window stayed on t6x at every sample (12:18-12:49, including while the selection held t15 for minutes), and the document has been stable at `t6x` v57-59 since 12:28:58 with no phone activity. A host-side revert on a 58-144 s cadence would also have fired during the 12:21:14-12:22:29 and 12:26:34-12:28:58 t15 holds at a regular interval; instead the holds end at operator-paced moments.

What this does not settle: whether each focus request was a deliberate tap or the app re-asserting its last workspace on resume/reconnect. The daemon logs prompts but not focus requests, so host-side evidence cannot separate those two. Cheapest operator test that settles even that: on the phone select c-akrogon (t15) once, then force-close the Moshi app (or airplane mode) for three minutes without touching the desktop. If the document flips to t6x while the app is closed, something host-side writes it; if it holds t15 until the app is reopened, every write is app-initiated.

## 2. The fix

- **O1 (upstream report) is the only option that removes the cause and keeps the features.** The defect is in moshi-hook's follow design: one global selection document per core, broadcast to every follower, and a follower that can only switch by execing a new `herdr-core attach` process. Upstream needs per-session selection (a focus request switches only the requesting session) and/or an in-process attach switch that does not restart the client on every change. Cost until then: tab changes keep repainting.
- **O2 (`HC_SESSION=infra exec hc` picker) disagreed as the primary fix.** It does remove the follower, and `hc --help` confirms bare `hc` is "pick a terminal and attach" with `ctrl+\` detaching. But it costs exactly what the operator uses: changing tabs in the Moshi app/chat view would no longer move the terminal, and the gateway's session binding is built around recognizing a `herdr-core attach <t>` child (`moshi-hook context --mosh-port` resolves the session to a pane that way); a bare picker process has no such child, so sidebar/chat binding is at risk, which C flags only as keyboard usability. It is a reasonable terminal-only fallback if the operator gives up app-driven tab switching, not a like-for-like fix. It is also unproven that the app lets the operator set that command per host; the observed command is hardcoded in the process tree as `moshi-hook hc attach --session 'infra'`.
- **O3 (close stale session, pin Mosh) agreed as interim cleanup, not as a fix.** One of the two 11:37/11:38 mosh sessions was stale (its port 60002 died at 12:25:21 and a new session appeared at 12:25:33 on 60001, while 60003 lives on). Duplicates mean two followers churn on every selection write and the app's context lookup can bind to a dead port (`moshi-hook context --mosh-port 60002` now returns "no UDP listener on port 60002", while 60001/60003 return the live `hc` context). Removing the stale session and pinning Mosh makes the binding unambiguous and costs one reconnect; it does not stop the per-tab-change attach restart.
- **O4:** no simpler local lever exists. `moshi-hook hc attach --help` has only `--session`; `moshi-hook set` has no follow, attach or sidebar setting. Nothing in akrogon or herdr-setup writes or reads `moshi-hook.selection` (`grep -R` over both repos: no hits), so there is no local code change that removes the cause.

Recommendation: O1 now (report with the doc-event/attach-pid correlation as proof), O3 as the interim tidy-up, O2 only if the operator prefers a stable terminal over app-driven tab switching.
