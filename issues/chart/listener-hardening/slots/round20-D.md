# Round 20, slot D: why cleared watchers keep ticking

Short answer: `/clear` never stopped a watch, in either era — that part is not a regression. What is new is a second, akrogon-driven tick source tied to the terminal forever. The reported 19:03 tick was the cron (task `5161d1f8`), not the listener, but over today the listener roughly doubled the tick rate, and it is the part that also follows a repurposed terminal.

## Q1 — The herdr era: cron only, nothing identified the watcher from outside

Before the hc port there was no wake path at all. `git grep wakeWatcher / akrogon.watch` over `6efbd57e^:src/` is empty, and the watch skill of that era (`e82ef65a^:skills/watch-issues/SKILL.md`, Invocations) is cron and nothing else: start = run one check + `CronCreate` with the exact prompt `/watch-issues tick <root>`; tick = one check, never creates a job; stop = `CronDelete`. Its identity rule was already the one that survives today: "The watch never self-deletes: it ends only on `/watch-issues stop`, session loss or the job's own expiry." Nothing keyed on the pane, nothing in the engine knew a watcher existed — the engine prompted lifecycle seats by their herdr session binding, and the watcher was just a claude process the operator ran the skill in. So what kept a cleared watcher "quiet" in the old setup was nothing in akrogon: there was no outside sender. All that could ever arrive was its own cron.

## Q2 — Cron survived /clear then too; w- watchers existed and were cleared

CronCreate tasks are process-session scoped, not conversation scoped — claude's own description in the 2.1.317 binary: "Session-scoped cron tasks (CronCreate, ScheduleWakeup, /loop) that will wake this session later", and `/clear` starts a new conversation inside the same process session. The disk record says this is not new in 2.1.317. Across all 2,915 conversation files under `~/.claude/projects`, 12 are conversations opened by a `/clear` whose first real prompt is a `schedule_wakeup` watch tick — e.g. `…/tamdoma-framework/f9309d6f…` (tick at 2026-10-27T19:05:03Z), `c9af43ac…` (2026-11-02), `8aec0338…` and `3db495a1…` in akrogon itself (2026-11-02), `35a1c7a8…` (2026-11-07T14:27Z, before that evening's hc port commits). Scheduled turns exist from 2026-10 onward (2,068 records in October). So in the herdr era the operator (or the watch itself — a sane context-trimming move for a 20-minute loop) cleared running watchers at least a dozen times and the watch carried on in the fresh conversation, by design or at least by tolerance. The 19:03 tick in `be339658…jsonl` line 14 (`wakeupSource: schedule_wakeup`, `scheduledTaskId: 5161d1f8`, one minute after the `/clear` records at lines 6-9) is the same phenomenon, not a new one.

## Q3 — The regression is the label + wake; the smallest restore depends on which behavior is wanted

Today t6 receives ticks from two independent senders, and the counts on the previous conversation (`51af12b2…jsonl`) are 20 scheduled vs 16 typed (`origin.kind: human`, i.e. `hc send` from `wakeWatcher`, at event times like 17:14, 17:34, 18:50 rather than the :03/:23/:43 cadence). Both new parts of that second path disregard conversation state, which is the exact thing the operator is complaining about:

- The label is terminal property, set on start (`skills/watch-issues/SKILL.md:16`), removed only by `/watch-issues stop` itself (:18). It survives `/clear`, a process restart and a different agent in the same terminal.
- `wakeWatcher` (`src/hc.ts:570-593`, callers `src/listen.ts:88`, `src/phase.ts:218`, `src/next.ts:188`) selects solely by that label plus "reports some status", sends the tick whenever the current occupant is idle/done, and never checks that the occupant believes it is watching.

Door A's candidate (a tick arriving as the conversation's first prompt stops the watch) is the right shape for the operator's stated expectation that clearing turns a watcher off, and it is smaller than deleting the wake: it is skill prose only, and it disarms *both* tick sources at their one shared point — the only place that can delete the cron job is the session itself, since the job lives inside its process. One refinement is needed so it does not misfire: a manually typed one-off `/watch-issues tick <root>` as a first prompt (a documented one-check invocation) must still just run the check. Discriminator: stop only if something pre-exists to stop — CronList finds the exact-prompt job, or the terminal still carries the label. If neither exists, run the check. Two honest costs to record: clearing a watcher to trim its context mid-watch (the herdr-era pattern above, 12 instances) becomes "restart the watch afterwards" instead of seamless; and the first-prompt test is the model's own judgment of its conversation (post-compaction summaries are in-context and identify themselves as summaries, so the confusion risk is low, but it is judgment, not a record check — nothing outside the session can do better, which is the point).

The alternative restore-exactly-the-old-behavior change is deleting the wake path (label + `wakeWatcher` + its three callers + the label lines in the skill), returning to cron-only. That is a deletion, so it wins on part count, but it does not give the operator what the report asks for: the 19:03 tick was cron, and cron ticks into cleared watchers predate hc by at least two weeks of transcripts. It would halve tick volume and end the repurposed-terminal retargeting, at the cost of the event-driven failure wake the hc port deliberately added (max failure-notice latency goes back to the 20-minute cadence, which the herdr era lived with).

So: regression = the label + wake, not the cron. If "old behavior" means what the old system literally did, delete the wake path. If it means what the operator is asking for now — a cleared watcher stays off — that behavior never existed, and the candidate (first-prompt tick with a pre-existing job or label deletes both and stops) is the smallest change that creates it, with no new mechanism: CronDelete and label removal already exist at `SKILL.md:18`, it only adds when they run.
