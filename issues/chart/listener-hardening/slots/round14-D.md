## Operator decision addendum: agy (antigravity-cli 1.5.3), from binary and disk data

The neutral-proof and hc options above are dropped per the decision. What adding agy actually takes:

- Reset command: `/clear` (same word as claude). The binary carries the description "Clear conversation and start a new one" in its slash-command definitions (`slashcommands.GetSystemSlashCommandsDefinitions`), and real use proves reset keys work as needed: `~/.gemini/antigravity-cli/history.jsonl` shows `/clear` typed 4 times, and the next prompt after each lands under a new `conversationId` (rows 5, 47, 75, 78 and their following rows). Whether `/clear` itself runs as a status turn is not observable without a live reset; it no longer matters — the warm-up predicate only needs idle events, and agy reports status (the binary embeds an OSC 7501 emitter, `AGY_CLI_OSC7501`; akrogon's seat start already waits agy to idle, `src/seat.ts:86-89`).
- Storage: one conversation is NOT the summaries database. Each conversation is its own SQLite file, `~/.gemini/antigravity-cli/conversations/<conversationId>.db` (65 on disk), with `steps(idx, step_type, status, metadata blob, step_payload blob, ...)` and `trajectory_meta`. Payloads are protobuf, but prompt and reply text sits inside as plain UTF-8 bytes (verified on `conversations/4b6c381a….db`: prompts in `step_payload`). Empirically on this build `step_type` 14 is the user-input step (its `idx` values 0 and 4 match `last_user_input_step_index` 4 in the summary row, and its payload holds the prompt), 15 is the planner-response step, 132 a tool step; the enum names are `CORTEX_STEP_TYPE_USER_INPUT` / `CORTEX_STEP_TYPE_PLANNER_RESPONSE` in the binary. The shared `~/.gemini/antigravity-cli/conversation_summaries.db` holds `conversation_summaries(conversation_id, title, preview, step_count, last_modified_time, workspace_uris, status, last_user_input_time, last_user_input_step_index, ...)` plus an FTS5 index `conversations_fts(conversation_id, ..., user_body, agent_body)` with prompt and reply text per conversation. Schema confirmed with `sqlite3` on a scratch copy (`bun:sqlite` Opens the same file read-only with no new dependency; nothing in the repo uses it yet).
- The two door-reset reads, re-expressed on the per-conversation db: boundary = `SELECT max(idx) FROM steps` at `started`, replacing the byte length (`door-reset.ts:92-94`); operator input after the handover was queued = a later read finds a `step_type = 14` step with `idx` above that boundary. Warm-up proof: in the candidate file (found as today — byte scan for the code works on the blob payloads), a `step_type = 15` step with `idx` after the first step whose `step_payload` contains the code bytes (`SELECT idx, step_type, step_payload FROM steps ORDER BY idx`, byte-contains in TS; no protobuf decode needed for these two questions). The FTS index could find the holder (`SELECT conversation_id FROM conversations_fts WHERE conversations_fts MATCH '"<code>"'`), but summaries are generated after the fact, so steps are the timely source. `inputSchema`/`replySchema` (:25,51) cannot express any of this; the two call sites (:103-107, :125-131) become per-kind functions instead of line schemas for agy.
- Transcript path and label: name the per-conversation file, `conversations/<id>.db`. That single change keeps every neutral consumer true: `existsSync` in observe (`observe.ts:75`), the differing-path check (a reset really is a new file), seats.yaml recording, and label fallback for a dead seat. Naming the shared summaries db (today's branch, `src/transcript.ts:155`) breaks all of them: same path before and after a reset, and it is a binary file the line parsers choke on. `transcriptFor` should prefer an open fd matching `conversations/<uuid>.db` (one to-verify on a live agy seat: that it holds that file open; the summaries db being open is how the current branch ever matched). Consumers that assume JSONL lines and still need their own agy branch, none of them on the handover path: chart `chart-usage.ts:118-123` (keep its explicit `unknown harness agy` seat error until someone writes the steps-based usage parser) and watch `log-tail.ts:50` (Format union; until it reads sqlite the watcher reports the log unreadable and judges from the screen). `src/log.ts` and `src/next.ts` timing store the string only.
- Smallest change set: `src/transcript.ts` — agy branch returns the open `conversations/<id>.db` instead of the summaries db (:155), `resetCandidates` returns sibling `conversations/*.db` changed since the reset for agy (:164-180; `transcriptByCode` then only needs byte-contains instead of utf8 `includes`), `transcriptKind` learns `conversations/*.db` -> `'agy'` (:226). `door-reset.ts` — `Kind` += `'agy'` (:15), `resetWord.agy = 'clear'` (:20), boundary/input/answered branch on kind with `bun:sqlite` reads as above (:92-107, :125-131); SKILL.md:161 and :165 prose get agy's word and record definition. `tests/door-agent.ts` — a fourth fake kind writing a minimal steps sqlite via `bun:sqlite` (the biggest piece; the fake's other three kinds write text files). Defer chart-usage and log-tail agy parsers as above; they degrade loudly, not wrongly.

Read-only: no files changed besides this note, worktree clean. Agy data was inspected through a scratch copy in /tmp, since deleted; no live agy was started, reset, or labelled.
