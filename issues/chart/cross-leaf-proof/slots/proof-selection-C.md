### 1 · Should every done-criterion be proven by the cheapest test that can catch its failure, and which skills should carry that rule?

Today verification is chosen per leaf with no cost rule. The chart writes done-criteria as "concrete check executable inside this leaf's ownership" (`skills/chart-issues/assets/shapes.md:132`). plan-issue writes "concrete verification" and puts "acceptance criteria before implementation derives tests" (`skills/plan-issue/SKILL.md:55,57`). implement-issue derives tests from criteria (`skills/implement-issue/SKILL.md:41`). check-issue only compares tests with criteria and rejects mocks (`skills/check-issue/SKILL.md:45`). Standing design adds only "No vanity tests" and one E2E artifact per user-visible leaf (`skills/chart-issues/assets/standing-design.md:7,9`).

Example: live-replay defect #15 (`.layout-two-col` never stacks at 360px) is one CSS rule. A renderer test at 360px catches it in seconds. It was found in hour-long rehearsal R8 instead (framework `live-replay/implementation/report.md:232-240`). Under this rule the renderer leaf's plan names a 360px rendered check, and the live run keeps only what no smaller test proves: that real sessions drive the route end to end.

Research: better-than-training · Bazel Test Encyclopedia, https://bazel.build/reference/test-encyclopedia, read 2026-09-29 · every test declares a size (small, medium, large, enormous) with a default timeout of 60 s, 300 s, 900 s or 3600 s, so cost is stated per test, not discovered · this made "plan records each command's size" the concrete form of the rule. practitioner · Mike Wacker, Google Testing Blog, "Just Say No to More End-to-End Tests", https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html, read 2026-09-29 · slow E2E suites find failures late and isolate them poorly, so push each check to the smallest test that catches it. Adrian Sutton (LMAX, https://www.symphonious.net/2015/04/30/making-end-to-end-tests-work/) counters that E2E works when it is fast and run continuously · both support "cheapest sufficient", and Sutton's point keeps the locked E2E line in place. practitioner · Dave Farley, *Continuous Delivery Pipelines* (https://leanpub.com/cd-pipelines) · move common late failures into early fast stages · this supports review checking the level, not just the presence, of tests.

- **1a (recommended)** Carry it in three places, each doing one job. Standing design gets one line: "Each done-criterion is proven by the cheapest test that can catch its failure. A slow or live run names the property no smaller test proves." plan-issue synthesis maps each criterion to one command, its size (seconds, minutes, hours) and its rerun trigger. check-issue records a Fix when a failure the leaf's own code can cause has no test below the slow run, and a Nit for a cost preference. This wins because the chart sets the rule, the plan applies it with live code in view, and review catches the gap. Each stage uses only artifacts it already reads.
- **1b** Standing design only. Cost: the line is reinterpreted per leaf (`standing-design.md:13`), and nothing checks it. That is the same failure as the fixture spine that was never grown (map-merged M2).
- **1c** plan-issue and check-issue only, with no standing-design line. Cost: the chart writes done-criteria before planning. If the chart writes "one labelled live run proves X" as a criterion, the plan cannot shrink it without breaking a locked contract (`plan-issue/SKILL.md:33`, design wins).
- **1d** No rule. Keep today's per-leaf judgment. Cost: this repeats the live-replay case.

Pitfalls: "cheapest" can slide into mocking. The rule must say cheapest *sufficient*, and it keeps existing bans: never mock auth (`standing-design.md:3`), no mocks of the unit under test (`check-issue/SKILL.md:45`), and real invocation for user-visible flows (`standing-design.md:9`). A check-issue Fix must name the uncaught failure, not the test level, or review turns into arguing about test pyramids. Validate the new wording by applying it to the live-replay case (map-merged R6), not by testing prose.

### 2 · Should a leaf's verification carry a numeric time budget, or is the rule in question 1 enough?

No skill records how long verification takes. The implementation report lists "commands run with pasted results" but no duration (`skills/implement-issue/SKILL.md:45`). live-replay's run history records outcomes per run but not stage durations (framework `report.md:691-722`), so no measured basis exists for a number. A budget would read, for example, "blocking `checks` finish in under 10 minutes, and a proof run over 1 hour needs an operator-approved reason."

Research: better-than-training · Bazel Test Encyclopedia (above) · size classes come with fixed timeouts, but Google set those numbers after measuring very large test fleets · a number here has no such data yet. practitioner · Dave Farley, *Continuous Delivery Pipelines* · commit stage under 5 minutes, acceptance stage under 1 hour · this is a reference point, not evidence about this factory's stages. Search for a practitioner source on time budgets for agent-run proof leaves found nothing stronger (2026-09-29).

- **2a (recommended)** No numeric cap now. The plan records each command's size class (question 1), and the implementation report records each verification command's measured wall time. This wins because it creates the data a real budget needs and costs one field. A numeric budget can be charted later from measured durations.
- **2b** Set a number now (for example Farley's under 5 minutes for `checks` and under 1 hour for a proof run). Cost: an unmeasured cap either blocks legitimate live proofs or is waived routinely, and a routinely waived rule trains seats to ignore it.
- **2c** No number and no measured durations. Cost: the next slow leaf has no data either, so this question returns with the same gap.

Pitfalls: recorded durations must not become a mechanical gate that fails on wording or format. Record the number and judge it as content. A size class without a rerun trigger still lets a leaf rerun a slow stage for an unrelated change, so question 1's rerun trigger does real work here.
