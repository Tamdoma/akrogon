- **1a (recommended)** Adopt the principle across the existing workflow. **Standing design** states the general rule once, alongside the unchanged E2E minimum. **Charting** applies it when choosing acceptance scope and locked live requirements. **Plan synthesis** links each criterion to an existing or proposed command, the failure it detects, expected time and external cost where known, and what requires rerunning it. One command may cover several criteria. A slow or live run names the property a smaller practical test would miss. **Implementation** records the actual result, artifact and material difference from the estimate in its existing report. **Review** judges whether that evidence proves the criteria and reruns only for the reasons already permitted. This places the choice before expensive work while keeping responsibility clear.

Pitfalls: “Cheapest” must include the effort to build and maintain the test, not just its runtime, and must not require searching for a theoretical optimum. ### 2 · Should each leaf have a numeric verification budget, or should it justify expensive proof and record its cost?

The inspected run history records revisions and failures, but provides no stage-duration breakdown from which to choose a budget (`LR/implementation/report.md:691-722`). Planning can record an estimate before execution, and implementation already records commands and evidence (`skills/plan-issue/SKILL.md:55`, `skills/implement-issue/SKILL.md:45`). A time limit needs an explicit consequence when a required proof exceeds it because lifecycle seats cannot stop to ask for a new decision (`skills/implement-issue/SKILL.md:31`).

Research: **operator** · `LR/design.md:41-42` and the run history above, read 2026-09-29 · the operator requested less repeated work, but the inspected evidence does not establish an appropriate numerical limit · recommend cost visibility before choosing a bound. **Practitioner** · Dave Farley, drawing on his teams' deployment-pipeline practice, [The Deployment Pipeline, printed pp. 4–5](https://continuousdelivery.com/wp-content/uploads/2010/01/The-Deployment-Pipeline-by-Dave-Farley-2007.pdf), read 2026-09-29 · he separates fast feedback from broader acceptance and treats their balance as empirical optimization · this supports measuring each proof's purpose and cost, not inventing one limit across leaf types.

- **2a (recommended)** Use the named-property rule and cost estimates without a numeric budget. Record actual time for expensive verification in the existing implementation report. A material overrun prompts the agent to explain the cause and choose a smaller sufficient method when the contract allows it. Required proof remains required. This supplies evidence for a later budget without adding an arbitrary stop condition now.
- **2b** Require a leaf-specific time target chosen during charting. Record overruns and their cause, but do not skip checks or fail the leaf solely for exceeding the target. This makes the expectation explicit, at the cost of choosing estimates before reliable measurements exist. A hard stop would need a separate decision about incomplete proof and recovery.

Pitfalls: A target can encourage reducing coverage or underestimating setup and external-session time. Neither option permits relabeling an unfinished run as a pass, waiving a locked criterion, or asking the operator a lifecycle question when a target is exceeded.
