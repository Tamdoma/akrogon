# Blind notes: identity rule — slot C

## Q1. What names does the reader return for a red log?

- **Pick:** **1a** — Per-stream extraction keeping real `(fail) <title>` titles as-is, emitting `(script) <script>` for each failed innermost script whose stream printed no `(fail)` line (including both `Exited with code <n>` for `n >= 1` and `Signaled: <SIG>`), qualifying bare `(fail) (unnamed)` as `(unnamed) <script>` when its stream carries a script prefix and `(unnamed)` otherwise, dropping wrapper scripts, and returning `(no test name)` when none match.
  - *Reason:* Fewest parts that solve 100% of observed consumer cases without stateful line tracking or signature churn. Across `tamdoma/framework`'s 254 readable red logs, `1a` names all 13 `(no test name)` flips (`(script) test:remote-image` ×9 across the `rest-c`→`rest-d` move, `(script) test:variant-parity` ×3, `(script) test:e2e:emdash-kit` ×1), qualifies both `(unnamed)` flips as `(unnamed) test:emdash-kit`, recovers the silently dropped script failures in all 23 mixed parallel runs, avoids colliding `(fail) test` with nameless check `test`, and keeps `failedTests(repo, recorded)` at two arguments with no `format (check) format` stutter in `flakyCommand`.
  - *Cost:* Two bare hook timeouts in different test files inside the *same* script (or in a repo running bare `bun test` with no `bun run` wrapper) share `(unnamed) <script>` / `(unnamed)` and rely on Q2 `2a`'s mandatory two-log seat check to distinguish them.
- **Rejected options:**
  - **1b:** Backward scanning for `<file>:` headers adds stateful stderr parsing and must guess whether a `:`-terminated stderr line came from `bun test` or user code (violating signpost `1a`, a true coarse name over a guessed detailed one); `(check) <name>` widens `failedTests` and all callers to pass `entry.name` while duplicating `line.name` in `flakyCommand` (`src/flaky.ts`).
  - **1c:** Keeping wrapper chains splits `test:remote-image` across shard moves (`rest-c` vs `rest-d`), and emitting `(script) <script>` alongside real `(fail)` titles double-counts every `bun test` flip in `akrogon flaky` and forces Q2 `2a`'s coarse two-log seat check onto every ordinary `bun run`-wrapped test failure.
- **Evidence:**
  - `operator` · `issues/chart/failure-identity/INTAKE.md` (`## Observation`, `## Suspected cause`), read `2026-11-11` · `test:remote-image` prints planted `[FAIL] ... CONNECT cdn.shopify.com:443` on green and red runs alike, while Bun's fan-out exit lines hold for every failed script.
  - `better-than-training` · `tamdoma/framework/issues/verify-runs.jsonl` + 254 readable packed/plain logs via `readVerifyRuns` (`src/verify.ts`) and `readLog` (`src/evidence.ts`), measured `2026-11-11` · 90/90 `(fail)`-free red logs carry `<prefix> | Exited with code <n>`, 23 logs mix `(fail)` on one stream with an uncovered `Exited with code 1` script on another, both `(unnamed)` logs carry `framework:verify:rest-a | test:emdash-kit`, and `test:remote-image` moved between `rest-c` and `rest-d`.
  - `better-than-training` · `bun v1.4.4` local tempdir probes (`bun run --parallel --no-exit-on-error` and `bun test --parallel=2`), run `2026-11-11` · non-zero code exits print `<script> | Exited with code <n>` (`code 0` prints `Done in ...`), and signal deaths print `<script> | Signaled: <SIG>`.
  - `better-than-training` · `src/flaky.ts` (`failedTests`, `flakyCommand`) and `tests/flaky.test.ts`, read `2026-11-11` · existing tests require `'test:owner | (fail) browser owner > dies with run'` to return `'browser owner > dies with run'`, and `flakyCommand` already prints `line.name` before `line.test`.
- **Pitfalls and what removes each:**
  - *Dropping sibling failed scripts under a shared wrapper:* If `rest-a | s1` prints `(fail) x` and `rest-a | s2` exits non-zero silently, `rest-a` also prints `rest-a | Exited with code 1`. Removed by normalizing pipe chains (`split('|').map(trim)`), dropping any failed chain `P` that is a strict prefix of another failed chain, matching `(fail)` coverage on the normalized full chain *before* taking the innermost token, and proving that two-sibling wrapper case in a `failure-names` unit test.
  - *Bare `(fail)` title containing ` | (fail) `:* A naive `^(?:(.+?)\|\s*)?\(fail\) ` regex treats `(fail) a` as a script prefix on `(fail) a | (fail) b`. Removed by matching lines starting with `(fail) ` as unprefixed first, covered by a `failure-names` unit test.
  - *Signal-killed parallel sub-script dropped:* Removed by matching `<prefix> | Signaled: <SIG>` alongside `<prefix> | Exited with code ([1-9]\d*)` in `failedTests` and testing both in `failure-names`.
- **Question not asked:**
  - In `newRedUnits` (`src/verify.ts`), `flakyCommand` prints `line.name` beside `(no test name)`, whereas `newRedUnits` returns `unit.test` alone so `main-red` notice bodies still say `1 new red on main: (no test name)` when `format` or `typecheck` fails (`63` red logs in `akrogon`). Should `newRedUnits` format `unit.test === '(no test name)'` as `${unit.name} (no test name)` in the returned notice strings while keeping `failedTests` on `(no test name)`?

## Q2. What may the seat take as proof that head and base failed the same way?

- **Pick:** **2a** — `knownRedReceipt` keeps its subset compare (`names.every((n) => baseNames.includes(n))`, refusing `(log gone)`), which automatically tightens over `(script) <script>` and `(unnamed) <script>`; `skills/lifecycle-rules.md` (`## Red check with no cause in the leaf's diff`) and `skills/chart-issues/assets/direct-route.md` (`# Direct route`) require the full two-log completeness and causal-fit read whenever **any** red name on the head is not a real test title (`(script) ...`, `(unnamed)` / `(unnamed) ...`, or `(no test name)`).
  - *Reason:* Zero new comparison branches in `src/verify.ts` while closing both the cross-script mechanical cover bug and the `(unnamed)` / coarse-script seat loophole, preserving the 2026-11-09 `known-red-nameless` rule for genuine nameless checks.
  - *Cost:* When a custom script is red on main, the reviewing seat must read both head and base logs whole instead of relying on `(script) <name>` match alone.
- **Rejected options:**
  - **2b:** Violates signpost `2a` and lets two different failing fixtures or an early crash inside the same custom script (`test:variant-parity`, `test:remote-image`) cover each other with no full-log causal check.
  - **2c:** Adds special-case signal mechanics only for `bun run` sub-scripts while top-level signaled commands (exit `143`, `(no test name)`) still rely on the seat's completeness check (`coverage-rule.md` `## Taken`); under `2a`, a signaled sub-script becomes `(script) <script>` and already hits that exact completeness check uniformly.
- **Evidence:**
  - `operator` · `issues/chart/known-red-nameless/forks/coverage-rule.md` (`## Taken`), read `2026-11-11` · locks two-obligation gating (receipt eligibility + recorded seat causal agreement) and non-cover on missing logs or killed/crashed runs.
  - `better-than-training` · `src/verify.ts` (`knownRedReceipt`), `skills/lifecycle-rules.md` (`## Red check with no cause in the leaf's diff`), `skills/chart-issues/assets/direct-route.md` (`# Direct route`), `tests/verify.test.ts` (`'a linked pair fails to satisfy requireGreenReceipt with unnamed or unlinked failing work'`), `tests/docs-links.test.ts`, and `tests/run-units.test.ts`, read `2026-11-11` · confirms three lifecycle skills symlink to `skills/lifecycle-rules.md` and doc tests assert literal `--known-red` and `run-check` substrings.
- **Pitfalls and what removes each:**
  - *Mixed head log skipping full-log review:* In `framework`'s 23 mixed runs (e.g. `dilutor-rebalance`), a real `(fail)` title appears beside `(script) ...` or `(unnamed) ...`. Removed by `2a`'s universal quantifier ("only a head whose red names are **all** real test titles... takes the named branch").
  - *Replacing symlinks or breaking literal doc-contract tests:* Editing `skills/*/lifecycle-rules.md` copies or rewording command literals breaks `tests/docs-links.test.ts` and `tests/run-units.test.ts`. Removed by editing `skills/lifecycle-rules.md` in place and running `bun test tests/docs-links.test.ts tests/run-units.test.ts` as a done-criterion of `failure-names`.
  - *Gone base log:* Explicitly ensure `(log gone)` on `onBase.log` never satisfies `baseNames.includes(name)` (true as long as head refuses `(log gone)`, and worth keeping explicit in `knownRedReceipt`), guarded by `tests/verify.test.ts`.
- **Question not asked:**
  - Both seat files currently require *"that the command ended by its own verdict and was not killed, timed out or crashed"*. When `bun test` times out one hook (`(fail) (unnamed)`), finishes running the remaining files, and exits 1 with its normal summary, the *hook* timed out while the *runner* completed by its own verdict. Should the updated seat sentence clarify that "not killed, timed out or crashed" refers to the check command/script failing to finish its run (not an individual test/hook timeout handled to summary completion by the runner)?

## Q3. Where do stored names live and who reads them first?

- **Pick:** **3a** — One optional string-array field (e.g. `failures?: string[]`) on executed red command entries in `verifyRunSchema` (`src/verify.ts`), written from the live log inside `runOnce` before `newRedUnits` runs; `flips` (`src/flaky.ts`) and `newRedUnits` (`src/verify.ts`) read the stored field first and fall back to `failedTests` when absent; `knownRedReceipt` always reads both real logs with the current reader.
  - *Reason:* Uses the existing locked rewrite of `issues/verify-runs.jsonl` with no new file or lock, eliminates repeated `.tar.zst` decompression on future `flaky` and `newRedUnits` runs (`newRedUnits` currently calls `failedTests` inside a nested `units × runs` loop), keeps historical counts stable across future parser edits, and guarantees `verify --known-red` still refuses missing logs and compares head/base under one parser across upgrades.
  - *Cost:* Because `verifyRunSchema` is a `z.strictObject`, once new rows carry `failures`, rolling `akrogon` back (`akrogon rollback`) to a pre-change release will fail `verifyRunSchema.parse` in `status`, `flaky`, and `verify`; and any write-time parser defect persists on rows written before its fix.
- **Rejected options:**
  - **3b:** Keeps O(archives) zstd decompression on every `flaky` and `newRedUnits` run until evidence is retired (~11s across 254 archives in `framework`), and makes a future parser edit silently rewrite unretired history while retired rows stay frozen on the old names.
  - **3c:** Adds a second ledger file, schema, and lock-ordering surface against `akrogon-verify-runs.lock`, violating signpost `1a` (fewer parts).
- **Evidence:**
  - `better-than-training` · `src/verify.ts` (`verifyRunSchema`, `runOnce`, `knownRedReceipt`, `newRedUnits`), `src/status.ts` (`scanRepo`), and `tests/verify.test.ts` (`'the receipt schema accepts both old entries and entries carrying a reused source run'`), read `2026-11-11` · `runOnce` rewrites `verify-runs.jsonl` under `recordLock` immediately before `newRedUnits`, and `status`/`flaky`/`verify` all parse every row through `verifyRunSchema`.
- **Pitfalls and what removes each:**
  - *Storing names on unexecuted entries (`blocked` or failed `setup`):* In `runOnce` (`src/verify.ts`), `blocked` entries copy `blocker.exit` and `blocker.log`, and when `setup.code !== 0`, non-`full` sequential checks are pushed with `exit: setup.code, log: setup.log` and `blocked: undefined` without ever running. Removed by attaching `failures` **only** at the two `checkedRun` sites where `setup.code === 0` and the command itself ran and exited non-zero, proven by `stored-failure-names` tests covering both `blocked` entries and `setup.code !== 0` runs.
  - *Stored names masking a deleted log in `knownRedReceipt`:* Removed by `3a` (`knownRedReceipt` never consults `entry.failures` and always reads both `entry.log` and `onBase.log`), proven by a done-criterion test seeding head and base rows with matching `failures: ['alpha']` and missing log files on each side and asserting `requireGreenReceipt` refuses both.
  - *Archive corruption tests on legacy rows (`tests/flaky.test.ts`):* Kept intact because rows with `failures === undefined` still traverse `failedTests` → `readLog` and throw `LogError('archive' | 'member')`.
- **Question not asked:**
  - None beyond locking the field name (`failures?: string[]`, non-empty deduplicated array omitted on `exit === 0`, `blocked`, `reused`, and `setup !== 0` entries) in the fork's Taken section so `stored-failure-names` has one exact schema contract.

## Q4. How is a log read that still exists but sits outside the `issues/` path grammar?

- **Pick:** **4a** (with `readLog` tried first and plain-file fallback on `LogError('nomatch')`) — Keep `src/evidence.ts` and `akrogon log` unchanged; inside `failedTests` (`src/flaky.ts`), read the plain path resolved against `repo.root` (`resolve(repo.root, recorded)`) when `readLog` misses (or when outside `locate`), returning `['(log gone)']` only when that plain file is also absent.
  - *Reason:* Fewest parts (a 3-line fallback in `src/flaky.ts`, zero edits to `src/evidence.ts`, keeping the chart at 2 leaves per `slots/map-merged.md` `## Split`), zero risk of cross-repo ambiguity in `readLogAcross` (`tests/log-reader.test.ts`), resolves `akrogon`'s 2 existing `issues/chart/<chart>/<non-direct>/check-test-*.log` rows, and lets `verify --holder <outside-issues> --known-red` read both live logs in `knownRedReceipt`.
  - *Cost:* `akrogon log <path>` still refuses ad-hoc `--holder` paths outside `issues/(open|closed|parked)` and `issues/chart/<chart>/direct` (which are never packed by `akrogon pack` anyway and remain plain files readable directly on disk).
- **Rejected options:**
  - **4b:** Widens `src/evidence.ts` (`readLog` and `readLogAcross`), requires two-tier repo-ownership disambiguation to keep `tests/log-reader.test.ts` green, and adds a third leaf (`slots/map-merged.md` `## Split`) for paths `akrogon pack` (`src/pack-command.ts` `classify`) never archives.
  - **4c:** Leaves `akrogon`'s 2 existing on-disk `issues/chart/*` rows broken as `(log gone)` and, worse, breaks `verify --holder /tmp/x --known-red` (`knownRedReceipt` under Q3 `3a` reads both real logs via `failedTests`, so without `4a` any `--holder` outside `issues/` reads as `(log gone)` and fails `--known-red` even immediately after running!).
- **Evidence:**
  - `better-than-training` · `src/flaky.ts` (`failedTests`), `src/evidence.ts` (`locate`, `readLog`, `readLogAcross`), `src/pack-command.ts` (`classify`), `tests/log-reader.test.ts`, and `akrogon/issues/verify-runs.jsonl`, read `2026-11-11` · `akrogon` holds 2 existing plain logs under `issues/chart/{worktree-cleanup/leftovers-verify,run-release/pending}/` that `locate` rejects as `nomatch`, `pack-command.ts` never archives outside `issues/closed/<owner>` and `issues/chart/<chart>/direct`, and `knownRedReceipt` under `3a` relies on `failedTests` reading live `--holder` logs.
- **Pitfalls and what removes each:**
  - *Relative path or stale worktree copy if `existsSync` runs before `readLog`:* Opening raw `recorded` before `readLog` resolves relative paths against `process.cwd()` instead of `repo.root`, and if a recorded path ever pointed at an inert worktree `issues/` copy that still existed on disk while the real owner moved/packed under `repo.root/issues/closed/`, `existsSync` first would read the wrong file. Removed by calling `readLog(repo, recorded, repo.root)` **first** and attempting `resolve(repo.root, recorded)` (requiring `statSync(...).isFile()`) **only** inside the `LogError` `kind === 'nomatch'` catch branch — proven by a local test covering both an `issues/chart/<c>/other/*.log` file and an external `$TMPDIR` `--holder` `--known-red` run, plus a missing file returning `['(log gone)']`.
- **Question not asked:**
  - Does `4a` lock `readLog`-first-then-`resolve(repo.root, recorded)`-on-`nomatch` (rather than `existsSync(recorded)`-before-`readLog`)? Locking `nomatch`-fallback order gives `4a`'s exact 3-line footprint while preserving B's owner-priority invariant for every `issues/` path.
