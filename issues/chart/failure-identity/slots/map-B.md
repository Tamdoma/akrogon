## Material forks

- D1. **What is an identity, and how is certainty represented?** Options: keep decorated strings as keys, or carry a small explicit distinction between a real named failure, a coarse script/check failure and unavailable evidence. Recommend the latter, sharing one representation and comparison rule across callers. Strings alone invite `(unnamed)` or a script label back into the real-test shortcut. Avoid treating every display label as an equality key or creating a generic runner plugin system.
- D2. **How do named failures and failed script exits combine?** Options: prefer Bun test names globally, report every failed ancestor and descendant, or attribute names to script ownership and retain failed script units that lack a usable named failure. Recommend the third. The first loses F7's mixed failures. The second duplicates one cause and can make a shared parent conceal a different failing child. Settle whether stable ownership includes the whole prefix chain or the deepest script, using real nested logs. Formatting padding is not identity. A real test title repeated under two scripts must not erase its owner.
- D3. **What does a coarse comparison establish?** Options: coarse exact identity participates in the existing head-subset-of-base fact check, or coarse failures always block. Signposts choose the first, with seat causal agreement still required. Never use ancestor overlap, a shared placeholder or equal exit status to cover a positively different failed child. Where no finer fact exists, the configured check remains coarse and the seat decides from complete logs and the diff. `(unnamed)` needs this treatment even when it arrived through Bun's `(fail)` syntax. Preserve missing-log refusal separately from identity availability.
- D4. **When and where do durable identities become authoritative?** Options: store them on each completed real command and use them for reporting, store them in a separate index, or keep deriving them only at read time. Recommend the receipt field. Old rows still derive from readable logs; retired old rows remain unavailable. Known-red must independently require both actual logs even when stored identities exist. Decide whether stored data or a newer parser governs an old stored row. Prefer the recorded identity for reporting so parser updates do not silently regroup history. A second index adds synchronization and retirement failure modes.
- D5. **How is an existing direct log resolved?** Options: read the recorded file first and use current owner/archive resolution when absent, or recognize existing files only outside the issue-owner grammar and retain canonical-owner priority inside it. The first is simplest but could select a stale resurrected open-owner file over current closed evidence. The second preserves current ownership behavior. Inspect the real writer/path contract before choosing. Neither option authorizes Git-history searching, swallowing archive errors or changing cross-repo ambiguity handling.
