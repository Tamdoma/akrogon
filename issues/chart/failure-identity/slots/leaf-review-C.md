1. **`failure-names/readiness.yaml` (`proofs`, third entry) and `stored-failure-names/readiness.yaml` (`proofs`, first and second entries) — unquoted `version: 97e88038` fails `readReadiness` and `akrogon status` validation.**
   - Sentences: `version: 97e88038` in the third `proofs` entry of `failure-names/readiness.yaml` (`operation: existing name reader, known-red covers and refusals, notice grouping, log reader and doc-phrase guards on the base`) and in both `proofs` entries of `stored-failure-names/readiness.yaml`.
   - Evidence: Because `97e88038` consists only of decimal digits separated by `e`, `Bun.YAML.parse` decodes unquoted `97e88038` as IEEE-754 float `Infinity` (`97 * 10^88038`), not a string. Running the pre-handoff `readReadiness` check (`src/readiness.ts`, `readinessSchema` / `proofSchema`, where `version` is `z.string().trim().min(1)`) against both scratchpad draft folders throws `Invalid input: expected string, received Infinity` at `["proofs", 2, "version"]` for `failure-names` and at `["proofs", 0, "version"]` and `["proofs", 1, "version"]` for `stored-failure-names`, which also fails post-write `akrogon status` validation (`shapes.md`, section `Preflight and validation`). Quoting `'97e88038'` makes both `readiness.yaml` files parse cleanly with `gaps(...)` returning `[]`.

3. **`stored-failure-names/brief.md` (`## Done-criteria`, criterion 4) — wrong CLI boundary for the gone-base-log half (`akrogon verify --known-red` vs `requireGreenReceipt`).**
   - Sentence: ``"`akrogon verify --known-red` judges `fail` and gives no receipt when the head log or the base log is gone, although both rows store equal `failures`."``
   - Evidence: In `src/verify.ts` (`verify`), `akrogon verify --known-red` reuses a completed red head row (`redRun`), so removing that recorded head run's log and running `akrogon verify --known-red` reaches `knownRedReceipt` with a gone head log and prints `verify known-red <sha>: fail`. By contrast, `verify` never reuses a red base row: whenever `greenRun` is `undefined` on `baseTree`, `verify` unconditionally runs a fresh `passOnce` on `baseSha` linked with `compares: headId`, writing a new base row with a live log on disk before calling `knownRedReceipt`; `knownRedReceipt` (`src/verify.ts`) loops over all completed `compares === head.run` rows, skips the earlier base row whose log was removed, matches the newly written base row, and prints `verify known-red <sha>: pass` (exit `0`). The boundary that refuses an already-recorded linked pair when the base log (or head log) is gone despite equal stored `failures` is `requireGreenReceipt` / a gated `akrogon phase` move (`src/verify.ts` `requireGreenReceipt`, matching `tests/verify.test.ts` `'a linked pair fails to satisfy requireGreenReceipt with unnamed or unlinked failing work'`), while `akrogon verify --known-red` itself covers the gone-head-log half.

4. **`stored-failure-names/design.md` (`## Leaf architecture`) and `stored-failure-names/brief.md` (`## Done-criteria`, criterion 1) — wrong claim that `runOnce` copies `reused` entries, leaving the `reused` proof/schema rule to guesswork.**
   - Sentences:
     - `stored-failure-names/design.md` (`## Leaf architecture`, `Where it is written:` bullet): `"The entries pushed when setup failed (they copy setup.code and setup.log) and the entries pushed with blocked (they copy the blocker's exit and log) get none, and a reused entry copies none."`
     - `stored-failure-names/brief.md` (`## Done-criteria`, criterion 1): ``"A run written by `akrogon verify` in which a configured check ran and exited non-zero records `failures` on that command entry, equal to the names the reader returns for its log. An entry at exit 0, an entry recorded `blocked`, an entry carrying `reused`, and an entry recorded because setup failed carry no `failures`, and no stored list holds `(log gone)`."``
   - Evidence: In `src/verify.ts`, `runOnce` never writes or copies a command entry carrying `reused`; whole-receipt reuse in `verify` (`greenRun`) exits `0` without writing a ledger row, and `reused` on `commands[]` exists only in `verifyRunSchema` and reader skips (`flips`, `newRedUnits`, `slowEligible`) so historical rows still parse (`tests/verify.test.ts`, `'a same-tree retry re-executes every unblocked command and writes no reused entry'` and `'the receipt schema accepts both old entries and entries carrying a reused source run'`). Because `akrogon verify` can never write an entry carrying `reused`, an implementer proving criterion 1 under `standing-design.md` (*"new behavior shows one deliberate break turning its test red"*) must guess whether `verifyRunSchema` itself is meant to reject `failures` on entries carrying `reused` (and `exit === 0`, `blocked`, `'(log gone)'`, or `setup !== 0` at the run level — whereas `Literal interface` in `design.md` `## Leaf architecture` specifies only `"non-empty and deduplicated when present"`) or whether criterion 1's `akrogon verify` write clause should name only the entry shapes `runOnce` can actually write while `verifyRunSchema` / readers state what happens to `reused`.

5. **`failure-names/brief.md` (`## Done-criteria`, criterion 2) and `failure-names/design.md` (`## Leaf architecture`) — three reader mechanics left implicit on nested Bun logs with wrapper exit lines.**
   - Sentences:
     - `failure-names/brief.md` (`## Done-criteria`, criterion 2): ``"A bare `(fail) (unnamed)` line is listed as `(unnamed) <script>` when its stream carries a script and as `(unnamed)` when it carries none. A real `(fail) <title>` behind a script prefix is still listed by its title alone."``
     - `failure-names/design.md` (`## Q1 names`, items 2–4, and `## Leaf architecture`, `Literal interfaces` / `Input shapes the reader rests on` bullets): `"3. (script) <script> for each failed script, read from <chain> | Exited with code <n> with n not 0, whose own stream printed no (fail) line. <script> is the innermost token of the chain, trimmed. 4. [corr] A failed chain that is a strict prefix of another failed chain is a wrapper and is dropped. Whether a stream printed a (fail) line is matched on the whole trimmed chain before the innermost token is taken."`
   - Evidence: Without altering `## Binding decisions, verbatim`, checking Q1 items 2–4 against the recorded consumer log in `failure-names/readiness.yaml` proof 2 (`framework:verify:rest-a      | test:emdash-kit     | (fail) (unnamed) [7668.89ms]`, `framework:verify:rest-a      | test:emdash-kit     | Exited with code 1`, `framework:verify:rest-a      | Exited with code 1`) exposes three places an implementer could build the wrong behavior:
     1. **Order of wrapper drop vs `(fail)` filter:** If item 3's *"whose own stream printed no `(fail)` line"* filter is applied before item 4's wrapper drop, `framework:verify:rest-a | test:emdash-kit` (and every ordinary nested test failure `grp | sub | (fail) title` + `grp | sub | Exited with code 1` + `grp | Exited with code 1`) is removed first, leaving `framework:verify:rest-a` with no surviving child chain so `(script) framework:verify:rest-a` is falsely emitted beside `(unnamed) test:emdash-kit` or `title`. Because `tests/flaky.test.ts`'s existing prefixed-title fixture omits `Exited with code` lines, `design.md` `## Leaf architecture` should state that wrapper dropping runs over all non-zero `Exited with code` chains before excluding chains whose stream printed `(fail)`, and criterion 2 should cover prefixed `(fail)` / `(fail) (unnamed)` logs that include the inner and wrapper `Exited with code` lines.
     2. **Token-tuple prefix vs string prefix:** `design.md` `## Leaf architecture` should state that `<chain>` is split on `|` into trimmed tokens so `"whole trimmed chain"` is the trimmed token tuple and `"strict prefix"` in item 4 is strict token-tuple prefix (not outer-string `.trim()` / `.startsWith(...)`, under which top-level `test:a` is a strict prefix of `test:ab` and internal padding `rest-a      | test:emdash-kit` stays unnormalized).
     3. **`<script>` in `(unnamed) <script>` under a wrapper:** Unlike criterion 1 (`(script) <innermost script>`), criterion 2 and `design.md` `## Leaf architecture` do not state that `<script>` in `(unnamed) <script>` is likewise the innermost trimmed token of `<chain>` (so proof 2's nested `(unnamed)` line produces `(unnamed) test:emdash-kit`, not `(unnamed) framework:verify:rest-a | test:emdash-kit`).
