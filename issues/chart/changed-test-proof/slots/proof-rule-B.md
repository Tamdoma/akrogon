Include new cases inside existing files and changes to helpers that affect those cases. Pure deterministic tests still need the existing deliberate-break or fail-before/pass-after proof, but not an added stability campaign. This can miss a dependency, so the plan must state why excluded changed cases need no repeated environmental proof.

Only merge-repaired tests is too late: it preserves the first admission gap and gives newly added fragile tests no preventive check. The scope is executable cases, not every fixture path matched by the citation guard.

## Q2 — What execution counts?

1. **Pick and cost:** Pick the first option: repeat the smallest existing command that executes the changed case with the relevant stages and concurrency it encounters at merge. Each counted run must actually reach that case on the current version and preserve its failure result. Prefer fresh command runs for process/browser setup bugs. Cost: realistic sibling stages can be expensive, and a smaller adequate composition might not exist. “Same stages” must mean stages affecting the suspected mechanism, not automatically every unrelated stage in the entire merge gate.
2. **Rejected options:** CPU-injected standalone runs can expose scheduling sensitivity, but cannot substitute for browser visibility, stage overlap, shared state or cleanup behavior. They are useful supplementary diagnosis when justified. File-only `--rerun-each` is useful for local nondeterminism but inadequate alone for the observed integrated failure. No repetition flag by itself proves that the relevant execution conditions occurred.
3. **Evidence:** Better-than-training, consumer commands, read 2026-10-11: `framework/package.json:159` runs playback files, while `:165` runs playback beside other core stages in parallel. Primary docs, [Bun test](https://bun.sh/docs/test), read 2026-10-11, describes rerun-each as repetition and parallel/concurrent execution as separate controls. Primary research, Silva, Teixeira and d'Amorim, [Shaker, ICSME 2020](https://leopoldomt.github.io/assets/pdf/2020-icsme.pdf), search result read 2026-10-11: adds CPU/memory competition to improve concurrency-flake discovery. This challenges dismissing stress as useless, but does not prove CPU stress reproduces this case's failure. Low confidence: its relevance to this exact Chrome/CDP failure remains unmeasured.
4. **Pitfalls and removal:** R4: silently add repeated merge_checks before review. Preserve `skills/plan-issue/SKILL.md:63` and `issues/chart/check-reruns/forks/check-scheduling.md:22-24`. R5: invent a smaller runner during implementation. Settle an existing adequate command during charting/planning, within the consumer-owned selection boundary. The contract must settle this collision before handoff. It cannot both require those conditions and let the implementer replace them with standalone load. Do not silently reopen the scheduling lock or build new proof machinery.

## Q3 — How many runs?

1. **Pick and cost:** Prefer planner-selected counts per proof command, with a stated reason and estimated total runtime. Amend the option's “stated detection chance”: label it unknown unless there is defensible evidence for the per-run failure rate and independence assumptions. Choose the number before the campaign, require more than one completed run, and never reduce it after seeing red. Cost: judgment remains and different planners can select different counts. This is a bounded measurement, not a certificate of stability.
2. **Rejected option:** A universal fixed floor is easy to check but spends the same count on millisecond deterministic runs and multi-minute integrated runs, with no established detection target. A fixed floor could be adopted as an operator's minimum effort policy, but must not be presented as statistically sufficient. I do not recommend inventing a number from the example's eventual replay index.
3. **Evidence:** Better-than-training, workflow, read 2026-10-11: `skills/plan-issue/SKILL.md:61` already maps proof commands to size and rerun triggers. `framework/issues/closed/merge-flow/probe-waits/review-B.md:142` records 20 green earlier runs, which cannot establish the later changed case's failure probability. Primary practitioner docs, [Mozilla Test Verification](https://firefox-source-docs.mozilla.org/testing/test-verification/index.html), read 2026-10-11, uses 10 runs then five fresh-browser runs, repeating the sequence in chaos mode, and discusses long-running verification limits. This is a concrete policy with varied environments, not evidence that its count suffices here. Mathematical inference: with independent runs and an assumed constant failure probability p, detection in N runs is `1 - (1 - p)^N`. Without p and those assumptions, a numerical detection claim is unsupported. The inspected sources do not supply them for this case.
4. **Pitfalls and removal:** R7: turn an assumed p into a measured confidence claim. Name the assumption or report detection chance unknown. R8: keep running until the last N runs are green. Predeclare the campaign and preserve all failures. R9: equate an arbitrary count with coverage of the failure condition. Resolve Q2 before calculating runtime or selecting N.
5. **Missing question:** Will the operator accept a count justified by mechanism and runtime with detection chance unknown? If not, Q3 requires a measurement design that estimates p under defined conditions. That is extra work, not a phrase the planner can fill in honestly from nothing.

## Q4 — What does a failing campaign do?

1. **Pick and cost:** Yes, for a failure attributed to this leaf's changed test or its criterion: retain the failing logs, repair on the owning branch, and complete the planned campaign against the repaired test/helper version. A later green run of the unchanged failing version does not erase that red. Keep the existing one diagnostic retry for unattributed red. Cost: attribution and repair take time, but the failure remains visible rather than being transferred to another leaf.
2. **Rejected options:** `--retry` can turn failed-then-passed into a passing result and is not admission proof. Quarantine can remove the required behavior proof. Retrying unchanged code until green measures selection of a favorable run, not a repair. Conversely, blindly repair every failure in a campaign would violate scope and the existing unrelated-red handling.
3. **Evidence:** Better-than-training, live rules, read 2026-10-11: `skills/implement-issue/SKILL.md:38` reserves the single retry/comparison route for failures with no plausible cause in the diff and never classifies the leaf's own criterion as known-red. `:36` stops an owned criterion that cannot pass within the owned surfaces. `:80` replays the rejected merge commands after repair. Primary docs, [Bun test](https://bun.sh/docs/test), read 2026-10-11, explicitly says retry may report later success as passing. Practitioner, John Micco, Google testing infrastructure, [Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html?hl=de_AT), published 2016-05-27, read 2026-10-11: warns that retry-based acceptance discourages fixing instability and quarantine can conceal actual races.
4. **Pitfalls and removal:** R10: infer ownership because a changed test filename appears in red output. Trace a plausible changed cause and keep the existing comparison rules for unrelated failure. R11: call an interrupted run green. Record completeness and use the existing incomplete-verification ending. R12: let a repaired case reuse its earlier campaign. Restart the affected campaign against the current test/helper version, preserving the earlier red as repair evidence.
5. **Missing question:** When new mandatory stability evidence exposes an infrastructure failure that is unrelated to the diff and its diagnostic retry is green, is the stability obligation complete or still unverified? Preserve existing unrelated-red semantics, but explicitly state whether the failed execution counts toward the requested completed sample. My pick: it does not establish a successful execution of the required changed case; remaining required executions still need recorded completion.
