### Fork 2 (#161): Long-wait policy — foreground wait vs. harness-native background tasks

Question: `INTAKE.md:54` says *"long waits use harness-native background tasks instead of shell loops"*, while `skills/implement-issue/SKILL.md` § `Shared context` (Proof order item 3) says *"A runs the exact printed command once, in the foreground with the tool timeout set above its expected run time"* and `learnings/LESSONS.md:57` records that backgrounding a slow command and ending the turn kills the leaf after 3 turns (`ended 3 turns without reporting`). - **Option 2a (Recommended): Promote "Wait on exit" into `skills/lifecycle-rules.md` as foreground-first, forbidding hand-written shell polling/sleep loops AND forbidding ending a turn while waiting on a background task.**
  - Specifically: (1) never write shell sleep/poll loops (`for`/`while` + `sleep`); (2) run slow commands in the foreground with the tool timeout set above expected run time (or rely on `akrogon run-check` / `akrogon verify` queueing for shared `full` checks); (3) if a harness's own background-task tool is used (e.g. when a command exceeds a single tool-call timeout), keep waiting inside the same turn via the harness's wait/status tool — never end the turn waiting for a background command (`learnings/LESSONS.md:57`).
  - *Pros:* Reuses and unifies the existing `implement-issue` rule across all lifecycle seats (`plan-issue`, `implement-issue`, `check-issue`, workers) with zero contradiction and prevents re-introducing the `LESSONS.md:57` 3-turn failure.
