## Cause and coverage

- F1. Confirmed: admission has no concurrency/resource bound. It sweeps stale records, registers live, and calls the command immediately (`src/admission.ts:142-181`). `81196b3b` deliberately removed memory readings, 16 GiB reservations, spacing and the admission flock. Today's `withAdmissionLock` is shared host-home protection plus a per-slice lock, not host-wide admission exclusion (`src/admission.ts:45-50`).
- F2. Overload is a supported cause, not a proven explanation for every red. The intake reports simultaneous cross-repo CPU consumers and no overlapping framework verifies (`issues/chart/host-run-load/INTAKE.md:60-66`). A quiet-host framework run was not inspected, and load also exposed a real test bug (`issues/chart/host-run-load/INTAKE.md:68,104-107`). Earlier merge-load-flakes required pressure evidence before adding a slot (`issues/chart/merge-load-flakes/CHART.md:15-17`).
- F3. Seat `run-check` resolves repo, leaf/worker/checkout, optional phase, and arbitrary command name, defaulting to `run`; all reach `checkedRun` (`src/run-check.ts:104-161`). Verify setup and every selected check reach the same function (`src/verify.ts:326-340`). Merge selection replaces covered checks and appends `merge_checks` (`src/verify.ts:54-61`). Known-red head/base execution uses the same caller and verification scope, with fresh setup/check admission for each execution. Reused green receipts execute nothing (`src/verify.ts:393-410`).
- F4. Verify knows `leaf|merge`, command name, SHA and base-comparison identity (`src/verify.ts:286-307`). `checkedRun` knows caller scope `leaf|worker` and phase, but receives no verification scope or origin. Admission receives only repo, leaf, check name, run, slice, caller cgroup scope and unit (`src/run-check.ts:185-221`). Its `scope` is a cgroup name, not merge/leaf verification scope. Name alone cannot distinguish a seat's `setup` from verify setup.
