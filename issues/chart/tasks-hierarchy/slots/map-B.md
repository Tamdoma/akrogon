# Tasks hierarchy: independent map B

The useful first decision is what should attract attention: working tasks, tasks needing intervention, or the task the operator is inspecting. Those are different states. Fixing spacing before choosing that order could preserve the same hierarchy problem. This is a design inference from F1–F5, supported by the practitioner's hierarchy principle in S8.

## Concrete hierarchy problems

1. **F1: Working and blocked task titles look equal.** In S2, `fixture-weave-recorder` and `about-identity-title` share foreground title styling. S3 uses the same `S(13)` medium title for every ordinary unmerged leaf. Busy seats change the icon to a spinner, but not title prominence. S4 has busy seats and error/dependency flags, but no selected/current-task field. Ask what “active issue” means before promoting a row.
2. **F2: Structural levels have weak separation.** S3 gives the repository `S(13)` semibold foreground and tasks `S(13)` medium foreground. Group labels are smaller and dim. `repoRows` records leaf depth, but `row` does not use it for indentation. Only group headings indent. S2's `about-titles` reads as a faint label above two equal rows. Improve structure within D19 rather than reopening the locked font baseline. [S3–S5]
3. **F3: Name and status are far apart.** S2 shows a long gap between each slug and its stage. In current S3, a flexible title pushes stage and elapsed time to the column edge, and the cap is `S(880)`, approximately 947.5 logical px at default font size 14. D19 names 760 px. Resolve this discrepancy against the operator rule before inventing a new layout. The screenshot and current source are separate evidence, not proof of identical deployed geometry. [S1–S3, S5]
4. **F4: An advisory precedes the work being inspected.** The first body line in S2 is a long slow-merge diagnostic from another repository, including a run identifier. All alerts render before all repositories, with foreground text, in S3. This gives a background advisory a prominent location even when the visible work belongs elsewhere. Whether that is desirable depends on monitoring versus intervention use. [S2–S4]
5. **F5: Secondary content mixes reasons with history.** S3 joins every tag and the latest move into one muted, truncated line. S4 puts dependencies before delivery errors, failure, and missing artifacts. Thus a reason requiring action can compete with or follow routine history, especially at narrow widths. Expansion uses selected fill but retains the same title weight, and the collapsed row has no disclosure glyph. A new working-row fill could consequently look like expansion or selection. [S3–S4]

## Questions to put to the operator

1. **Q1, resolves T1:** When opening Tasks, should the first thing you notice be work running now, work requiring your intervention, or the task you are inspecting? Show the same two tasks with different emphasis so the answer concerns behavior, not an abstract color preference. [S1–S4, S8]
2. **Q2, resolves T3:** Is the normal use a narrow side panel beside terminals or this full-width view, and roughly how many tasks are normally visible? S2 establishes only the latter with two tasks. Compare the chosen list at both widths before deciding on density. [S2–S3]
3. **Q3, resolves T4:** Should a slow-merge advisory for another repository appear before the current repository's tasks? The concrete example is lingua-relay above framework. Keep actual failure visibility while deciding this placement. [S2–S4]

Treat icons, seat count, spinner behavior, font-size scaling, immediate redraw, removed sections, kept-live-tab behavior, ownership, and D19's theme/controls as settled. Do not spend operator questions on them. D19 also already supplies the title-adjacent count-chip precedent that the current far-right plain count does not follow. [S1, S3, S5–S7]

## Lifetime pitfalls and proof needed

1. **R1: Meanings collapse into one highlight.** Busy seats, phase, dependency waiting, red flags, hover, and expansion already coexist. Compare a working failed/red leaf and an expanded blocked leaf, not just separate happy examples. Keep stage words and readable reasons if colors change. Preserve native spinning rather than adding redraw timers. [S3–S4, S6, S9]
2. **R2: The two-task screenshot overfits the design.** Compare zero work without restoring removed messages, several repositories, deep groups, long slugs, and large configured text at narrow and full widths. Fixed seat and time widths compete with the flexible title. A fixed nested indent or card grid can worsen this as content grows. These cases come from supported model states, not proposed features. [S1, S3–S4]
3. **R3: Muting removes the information needed to act.** Preserve blocked reasons, delivery failures, missing artifacts, and stale-scan warnings in the chosen hierarchy. Do not infer measured contrast from the half-scale image or import the sidebar's literal white values into every theme. The host supports light and dark themes through named tokens. [S2–S4, S6–S9]
4. **R4: Functional tests are mistaken for visual proof.** Existing tests cover model ordering, errors, seat icons/spinning, pill compositing, expansion redraw, cross-repository identity, and panel request sequences. They do not establish visual hierarchy or clipping. Implementation should retain those checks, pass the host mod check, and be reviewed in actual rendered states. Do not add exact-word or pixel-equality tests for a judgment about hierarchy. [S6, S10; operator's function-over-format rule]

Start with Q1. Then compare two small variants of the existing list, using the same data and locked controls. The evidence supports a hierarchy correction before a new panel structure.
