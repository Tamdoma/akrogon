# Slot B: leaf review disagreements

## status-attention-facts

- **F1 Land criterion contradicts sections Taken and misses a recorded-success state.** Brief criterion 2 requires red whenever a command-owned merge unit is inactive. The copied binding decision explicitly says not is-active alone and excludes a finished land awaiting reconciliation. The architecture instead treats owner=command plus inactive as sufficient. `src/phase.ts:batchPush` records candidate and recorded=true after a successful push, before invoking commandMerged. If that move cannot complete, the command can exit with phase merge and owner command still recorded; `src/next.ts:reconcileBatch` can later finish the successful landing. `src/land.ts:handOff` covers the seat handoff paths, not this successful-push path. The criterion and architecture need the same defined completion/handoff rule as sections Taken 3, including the recorded-success case. Merely changing the phrase from push failed to job stopped does not meet the no-flash decision.

- **F2 The literal failed attention phrase assumes an optional record exists.** Criterion 3 covers every failed phase, but the interface only specifies `failed: <cause>: <reason>`. `src/state.ts:stateSchema` permits failure to be absent, `src/status.ts:note` explicitly handles that case, and `tests/status.test.ts` already exercises legacy-failed without a failure record. Define the meaningful attention phrase for this supported state and retain red=true without dereferencing absent cause/reason. This is a missing permitted-state interface, not a request for a broad fallback.

- **F3 The promised text-view agreement has no observable criterion and names no actual attention consumer.** What includes the text view and Why promises agreement with akrogon status, but all criteria describe JSON. The design refers to the text view's red marker; current `src/status.ts:cells` calls note, and style colors phase values, without consuming leafRed or a leaf attention marker. The text overview also prints Failed/Missing separately. Name the real text consumers and specify the observable text result for the new dependency/land facts, so meeting only the JSON criteria cannot leave the promised CLI behavior unchanged. This belongs in this leaf's existing status ownership.

## tasks-sections-board

- **F4 Working duration cannot be met for the live-land state from the agreed producer output.** Criterion 3 requires busy duration for Working; architecture classifies a live land as Working even with no seat busy timestamp. `src/status.ts:leafJson` exposes land as alive/unit only. The current batch has an optional started value (`src/state.ts:batchSchema`), but it is not emitted, and status-attention-facts only promises attention/waits_on. Phase age is not land-job age when the task queued before starting. Give the duration output an owner in the producer contract, or settle the land-only time behavior explicitly. The board cannot manufacture the promised duration within its own ownership.

- **F5 Changed pin state has an omitted real consumer and the named Files path is wrong.** Architecture names herdr-setup mods/files as the consumer of the new issue-folder pin. The actual installed extension is `mods/files-view/main.js:location/refresh`, and the same shared worktree.pin also feeds `mods/changes-view/main.js:location/key/refresh`. Changes resolves the pinned folder's git top level, so switching to Changes after a body click can now show the issue folder's containing repository rather than the task worktree. Record that consequence/decision or an Open for the plan question and name its owner if a change is needed. Files itself already lists the pinned directory before optional git metadata, so its current folder precondition is checkable without assuming a worktree root. Evidence: both consumer location functions, Files refresh, Changes refresh, and `herdr-app/tasks/model.js:pinIntent`.

- **F6 Monochrome asset delivery is an unowned dependency of criterion 8.** The criterion requires unchanged program shapes in the sidebar's monochrome treatment, but architecture leaves app-home mono PNG availability and absence behavior open while owning only the Tasks sources/types/tests. `herdr-setup/mods/agents-by-tab/main.js:icon` reads mono/<basename>.png; herdr-setup install copies that directory and bin/herdrapp copies it to session homes. Akrogon's `src/install.ts` links its mod folders and does not deliver app-home mono. Neither prerequisite status-attention-facts nor tasks-side-open accepts asset delivery. Name a checked existing installation precondition and the supported asset set, or give delivery an owner. An absent asset cannot be solved by silently dropping/changing the locked program icon merely to pass the criterion.

- **F7 The board-shape consumer description is factually wrong.** Architecture says leafRows is used by tick and pin code. `herdr-app/tasks/main.js` does not import it: tick rebuilds via board, and pin/findLeaf use the envelope. leafRows is consumed by the model/host tests. The actual production consumers of the removed model.repos/model.quiet shape are `main.js:render`, including its header count, repository loop and empty-state logic. Name those consumers explicitly when changing board's return shape, rather than treating leafRows as the tick/pin adapter. Evidence: main.js imports/rebuild/tick/findLeaf/render; `model.js:leafRows`; existing Tasks tests' leafRows calls.
