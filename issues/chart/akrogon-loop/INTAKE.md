# Intake: akrogon-new

These are my raw notes for a chart-issues session. Nothing here is decided. It is what I think, what I am afraid of, and what I want, written down so the chart can grill me on it.

## Where I am

I am spending more time fixing the machinery than moving the projects forward, and this is killing me. The current akrogon machinery under issues/.scripts is 82,264 lines of TypeScript in 423 files, 35,541 of them in files named test, spec, or fixture, recounted today. The defects I keep logging are almost all the same kind: some piece of code tries to read what an agent wrote and gets it wrong, and then I add another guard, and then that guard breaks. It never runs out.

I keep coming back to the numbers on the framework repo. In July, with the old skills and me typing every command by hand, 185 issues were finalized. In August, with the automated machinery, 37. That is counted from commits whose subject says "finalize changes", one per landed issue, in the framework repo. Counting real git merge commits instead gives 47 in July and 8 in August, same story. The manual thing was slow for me but the merges came in. The automated thing was supposed to free me and instead it ate me.

### What the last month taught me

I spent close to a month on the machinery itself. What I learned is that I never needed perfect machinery with all the tests. Models change so fast that a big harness built around one month's behaviour is already stale by the time its tests pass, and every layer I added to make it robust produced bugs of its own. What I need is a very simple system, close to the snapshot in this folder, with exactly one addition: I do not type the skill names, the commands, or the paths. That much already worked on the last snapshot before I started piling on automation like the merger tab. The moment it became me maintaining the machinery, the goal was lost.

Sanity check, tier 1, Anthropic's "Building effective agents" by Erik Schluntz and Barry Zhang (anthropic.com/engineering/building-effective-agents): "The most successful implementations weren't using complex frameworks or specialized libraries. Instead, they were building with simple, composable patterns." and "You should consider adding complexity only when it demonstrably improves outcomes." Also on frameworks: "They often create extra layers of abstraction that can obscure the underlying prompts and responses, making them harder to debug." That is a fair description of what I built.

### The hierarchy

One thing stands over every decision in this file and in the chart: simplicity first, then cost, then quality, then speed. All four are important, none of them is optional, but when two of them pull against each other this is the order that wins. Every time I have broken this order in the last month, usually by buying quality or speed with more machinery, it cost me simplicity and then everything else.

### Fixing the fixer

The other place where things went really wrong is the one I nearly repeated today. I started building fixers for the state machine itself. Once that started, I was spending my days managing Claude and Codex as partners, relaying between them, reviewing their fixes to the machinery, and the purpose of the whole thing quietly became keeping the machinery going and fixing it on the go. Not shipping issues. That is the path I am not taking again. The two ideas I put into my system prompt today are the ones I want to hold onto the whole time I am building this: elegance first, meaning before any decision ask what removes the whole problem class instead of guarding one case, fewest moving parts, obvious in a year, and function over form, meaning machine checks look only at whether the content exists and the state is valid, never at exact wording or format, because agents never produce the same output twice and any check on form eventually blocks real work. Those two are the rules for agentic engineering here, and simplicity is why.

### What I take from it

The basic deterministic checks stay. Linters, typecheckers, compilers, and the product's own tests cost me about two hours of stalls in a month and they catch real breakage. Every source I read says the agent needs a check it can run, and these are the cheapest ones that exist, and they are deterministic for real, unlike an agent counting branches by hand. What goes is everything that was built around them: the judge, the proof formats, the coverage review, the gates that spawned their own issues, and above all the parking. Advice I received, open: a leaf runs the repo's own linter, typechecker and tests as part of its verification, the agent reads the result and fixes it, and nothing else in the harness cares about it. A pointer for the chart, not my position yet.

The numbers I want the chart to have in front of it, from the same log, measured 2026-09-07 by me and by codex separately. Checks the agent can run itself, meaning linters, typecheckers, compilers and product tests: 9 stalls, about 2.2 hours in the whole month. Everything that watched the agent instead of the code, meaning receipts, heartbeats, proof shape, question parks and generic parks: 110 stalls, about 74.5 hours. Throughput went from 185 issues finalized in July by hand to 37 in August automated. 10 of the 79 issues in August existed only to fix the pipeline's own gates. 35,541 of the 82,264 lines of orchestration code are tests of the orchestrator. ### The software factory mistake

The big mistake, in one sentence, was building a software factory. What I need is a simple state machine, or whatever this new thing ends up being called, and I wanted to know if anyone had actually studied why factories fail and simple machines hold up. Sanity check, recorded as received. Gall's law, John Gall, Systemantics, 1975 and 1986 (tier 1, named author): a complex system that works is invariably found to have evolved from a simple system that worked, a complex system designed from scratch never works and cannot be made to work, and a temporary patch will very likely be permanent. That is my August. Dex Horthy at HumanLayer, "Why Software Factories Fail", July 2026 (tier 1, first-hand): they ran a lights-off factory from July to November 2025 and reverted it, incidents up, bugs per developer up, review quality down, because tests give feedback in seconds while bad architecture costs show up in months, so no harness catches it. What they kept is humans steering at the front, requirements, architecture, design, then slices. Dennis and others, arXiv April 2026 (tier 2, measured): the whole procedure in the system prompt beat LangGraph and CrewAI orchestrators on three procedural domains, failure rates 11.5, 0.5 and 5 percent in context against 24, 9 and 17 percent orchestrated, and their conclusion is that frontier models made external orchestration unnecessary for defined procedures. Anthropic's building effective agents piece, already in this file, says the same in fewer words. The one counter report I found, on Hacker News under Horthy's post, is someone running a factory for eight months successfully, and their method is heavy upfront specification through an interview that works through every open question, then adversarial review, which is not lights off, it is the shape I am describing here. The nuance I was given: nobody measured state machine against factory as such. What the sources agree on is narrower, grow from a simple thing that works, keep the human where intent and architecture get decided, and put the procedure in front of the model rather than in a framework around it. My phases with a driver that reads only the phase is the smallest version of that I can think of.

### No loop, no state

This is the thought I want to keep in front of me. The two things that bring in most of the complexity are a loop and state of its own. A loop means something has to keep running, so something has to watch whether it is still running, so heartbeats, so watchdogs. State of its own means a second truth next to the files in the issues folder, so reconciling, so drift, so records about records. Everything that hurt in August had both. The status view has neither, it reads and prints and exits, and that is why I trust it. The driver is the one place where I cannot avoid a loop, so it should hold no state at all and the loop should be as dumb as it can be, phase in, prompt out, wait for idle, phase in again. Anything else I add to the new repo I want to measure against this first: does it need to keep running, does it need to remember anything the files do not already say. If yes to either, I want a very good reason.

## The idea

Start from the July 28 skills in a new infra repo, akrogon-new. Keep the debate model as it was. Put a very thin, very dumb driver on top that uses herdr to type the commands I used to type. It reads the phase of an issue, looks up which skill and which slot that phase needs, sends the prompt to a pane, waits for the pane to go idle, reads the phase again. If the phase moved, next step. If not, it retries and then pings me and leaves that issue alone. How many tries was advice, one, and it is open. It tracks several issues at once, across several repos. That is it.

The one thing I feel strongly about, even though I said nothing is decided: the driver should never read what an agent wrote. Not tokens, not footers, not approval sentences. The only thing it reads is the phase, and the only thing that moves the phase is the lifecycle transition command that the skill runs. Every time I let code parse agent prose I paid for it. If a feature needs the driver to parse prose, that feature is probably wrong.

I helped write a driver like this once already, the herdr plugin from July 29 was 319 lines. But it sat on top of a 4,714 line orchestrator that parsed status tokens. This time I want nothing under the driver. A size of a few hundred lines was advice I received, not a target I have set.

### The bridge that herdr fills

What I am mostly concerned about is the bridge, the part herdr fills between the two agents. This has to be discussed from herdr's documentation and API and from what the agents can do on their own. How possible and viable is it for the two agents to talk to each other only when needed, and only in this scope: one calls the other's next skill, the other reads the prose the first one left at the end, what the previous work was and what the next step is, and decides from that what to do. What they can send each other is always limited, it is the skills, and that is deterministic in a way. The July 28 snapshot already has that shape, with the script commands hard coded in the skill text and only the variables changing. Sanity check, tier 2, herdr 0.8.2 CLI reference (herdr.dev/docs/cli-reference), and this repository's own working agreement, which already relays every peer message with herdr agent prompt. The verbs exist: agent prompt targets any pane and types the text plus enter as one submission, with wait and until idle to block until the other side settles; agent wait blocks on a pane with no timeout when none is given; agent read with lines N gives the last N rows of the pane, which is the handoff prose. Two details to respect. The wait on agent prompt is capped at five minutes, so a long pass is waited on with agent wait, not with the prompt's own wait. And a prompt to a pane that is already blocked is refused without sending, which is the never-stack rule for free. So the bridge is two verbs, prompt and read, and the vocabulary between the agents is skill names plus the handoff prose. What is open is who types the next command, a dumb driver process or the agent that just finished its pass, and whether the handoff prose lives in the pane tail or at the end of the plan file. One more thing about that communication: the agents themselves have to figure out which of two things they are sending. Either the deterministic skill command with its variables filled in, the next step for the other pane, or a prose answer with no template at all, when the other one asked a question. Both go through the same herdr prompt, and the judgement of which one is called for sits in the agent, not in a rule. Sanity check, local, tier 2: the two message kinds already exist in the current setup, the skill command is the shape every July 28 skill hard codes with variables, and the question and answer shape is the plain text from the grilling format, so there is nothing new to design here beyond one line in the skill text saying when to send which.

### Two agents at the door

What I really like in consulting is the two independent agents giving their own thoughts. Two blind takes capture more than one, and I definitely want to keep that. The problem is that if I keep create-issue and move one step earlier, where I actually am, there is no duality at the door. So maybe I want both agents during chart-issues and during create-issue too. The way I picture it, and this is potential, not decided: slot A is the agent I talk to. When it hits a question worth a second view, it sends that question to slot B through herdr, the same mechanism as everything else, nothing outside it. Slot B answers blind, it sees only the question and not A's reasoning, so it complements with what A did not think of. A folds that into the conversation with me. Not deterministic, no machinery around it, no ceremony, and especially no checks or harness. A judgement inside the skill, done every time by the agent, with one herdr command. Sanity check, recorded as received. Two independent takes is the voting pattern in Anthropic's building effective agents (tier 1): run the same task more than once to get diverse outputs, and models do better on tasks with several considerations when each gets its own call. Half of what I want already exists: the current chart-issues has a debate decision type where both slots write one independent recommendation without reading the other and I pick, dispatched by hand today. create-issue has nothing like it. And herdr already has the one verb this needs, agent prompt with wait until idle, so slot A can ask slot B mid-interview with a single command and no new mechanism. The one caution I was given: B is only blind if A sends the question and not its own view, and that is a line in the skill text, not something to check. Getting it wrong costs a weaker second opinion and nothing else, which is the kind of failure I can live with.

A bit more detail on how I picture it, with the caveat that I do not know the whole mechanism yet and it gets debated in the chart. Say slot A is Claude. I start chart-issues or create-issue with it, it builds its own version of the route, and as it goes it hands the same thing it is working on to slot B, say Codex, through herdr and nothing else, keeping B up to date on where we are going. B then gives its own pathing, maybe things A did not catch, and A takes that in. So there are really two shapes on the table: B answers single questions blind, or B is kept in step with A's whole picture and answers from that. The second is not blind, B sees A's version, and the sanity check above says that is where the second view gets weaker because B anchors on A. Both shapes cost one herdr prompt and no machinery, so the choice is only about which second opinion is worth more, and that is for the chart.

Where I landed after that: slot A leads, and it feeds slot B nothing of its own. B stays blind. The one question left, and it is a chart question, is timing. Either B goes through the whole thing once on its own and hands all of its input to A at the end, and A takes it into account, or the two run in parallel and B answers step by step along the way. Whichever it is, the skill itself, or the config, has to ask me whether I want slot B in this phase at all. Plain prose, one question, no deterministic machinery around it, so nothing starts growing there.

## Bloat and watchdogs

During all the agent passes the agents themselves kept telling me the skills were too bloated and expensive, mostly because of cache misses and rereads. Every pass reread files it had already read, and every reread was a cache miss and a bill. That is not something I want to keep doing.

The other thing that went wrong when I complicated it: I ended up with several watchdogs. One inside herdr, one on the computer, watching when something happened, watching each other. That is exactly when the problems started, and I can name the moment. The complexity started crawling in the first time an agent told me herdr was not able to do something. From that sentence came the heartbeats, then the watchdogs, then the watchers of the watchers. That is not what I want. I want to use herdr to the max, and when herdr genuinely lacks something, I would rather write a small patch on top of herdr that survives its updates, the way the July plugin sat next to the skills in my own repo and not inside herdr, than invent another mechanism next to it. The one fact I checked: herdr 0.8.2 ships the agent integrations and the socket event stream as built-in surfaces, so the case where it really cannot do something should be rare, and the burden of proof is on the agent claiming it. What I actually need is one simple event: the agent is done. Then the next agent reads its output. Not everything it did, the end of it, where it always says what its last action was and what is next. That is what gets read first.

### Skill files as entry points

The other fear was that the skill files were becoming too bloated, and I am open to the main SKILL.md being an entry point to everything else, broken into smaller files, because my premise is that the agent does not have to read everything all the time. Sanity check, tier 2, Claude Code skills docs (code.claude.com/docs/en/skills): the premise is correct and it is the documented design. Keep SKILL.md under 500 lines, move detailed reference material to separate files, and the reason given is that once a skill is invoked its body stays in context for the rest of the session, so every line is a recurring token cost, while a supporting file costs nothing until the agent reads it. Only skill names and descriptions load at startup. So the shape is overview and navigation in SKILL.md, references read on demand. The July 28 skills are 1,852 lines across eight SKILL.md files with the consult-issue one carrying most of it, so this is a real rewrite, not a rename. I then checked the other two as well and all three do the same thing. Anthropic's own write-up on agent skills (anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills, tier 2) calls it progressive disclosure with three levels, name and description preloaded into the system prompt, the SKILL.md body read only when the skill is chosen, bundled files read only as needed, and says the amount of material in a skill folder is effectively unbounded because of it. Codex (developers.openai.com/codex/skills, tier 2) loads name, description and path at start, caps that list at two percent of the context window, and reads the body only when it decides to use the skill. pi (pi.dev/docs/latest/skills, tier 2) lists skills in the system prompt and loads instructions and reference files on demand through the read tool. So an entry file plus references costs the same in every harness I might use.

### Rewriting for the new models

All the skills have to have maximum information density, no bloat, and they have to be written for the current wave of models, Opus 5, Fable, GPT-5.6 and whatever comes next, because the vendors changed how these models want to be prompted, which probably means the skills have to be rewritten rather than trimmed. Sanity check, tier 2, both vendors' own guides. Anthropic's prompting best practices for the Claude 5 generation: the models follow instructions more precisely and respond more strongly to the system prompt than earlier ones, so prompts written to fight undertriggering now overtrigger, and the fix is to dial back aggressive language. Be specific about the desired behaviour instead of shouting it. Opus 5 verifies its own work without being told. Prefilled responses are gone since 4.6, thinking budgets moved to an effort setting, and the models delegate to subagents on their own. OpenAI's GPT-5 prompting guide says the same from the other side: the model follows instructions so carefully that contradictory or vague instructions are more damaging to it than to older models, it spends tokens reconciling the conflict, and reasoning effort and verbosity are now settings rather than prompt tricks. The guide covers GPT-5, I have not seen one specific to 5.6. What this means for the snapshot skills is narrower than a rewrite from scratch: they have no shouted words at all, no MUST or CRITICAL in capitals, but 85 lowercase nevers and musts across the eight files, and the real work is removing rules that contradict each other and rules that only existed because an older model kept missing them.

### Can herdr do this alone

I checked herdr 0.8.2, tier 2, its own docs at herdr.dev/docs/socket-api and herdr.dev/docs/cli-reference. Yes, all of it.

There is one event, `pane.agent_status_changed`, and a client can subscribe to it over the socket, "Subscribe to events when you need a long-lived stream". No polling. States are idle, working, blocked, done, unknown. `done` is "the same underlying idle state after unseen background work completes", so done is idle for a pane I was not looking at. `blocked` means herdr saw an approval or question UI. On the command line the same thing is `herdr agent prompt <pane> "<text>" --wait --until idle` or `herdr agent wait <pane> --until idle --timeout <ms>`, and `herdr agent read <pane> --lines <n>` gives the tail of the output.

Two caveats from the docs that I should respect. State comes from the harness integration reporting it, "Agent waits observe semantic state, not arbitrary command completion", so the integration for each harness has to be installed or the state is unknown. And "It does not track individual turns. If the agent is already working, completion of that active turn may satisfy the wait", so the advice I received is that the driver only prompts a pane that is idle and never stacks two prompts on one pane. Open, but it reads as a rule rather than machinery.

The advice I received from that, open: one process subscribed to one event could be the whole watchdog, with no second watcher, nothing on the computer watching herdr, nothing watching the watcher.

## Testing

I asked myself whether predetermined test suites are even a good idea for this, and I went and read what people who do this for a living say. The Claude Code best practices page says to give the agent a check it can run, tests, a build, a screenshot, because otherwise "looks done" is the only signal and you become the verification loop. It also says "if you can't verify it, don't ship it." Superpowers says write the test first, watch it fail, write minimal code to pass, per task. Simon Willison does red green TDD on every build, tests written by the agent inside the task. Nobody I found recommends a big suite that tests the workflow harness or grades what the agents write. Everyone recommends a runnable check per change, on the product code.

So I think I was half right. I do need testing, I was wrong to say remove all of it. What I do not need is 34,000 lines testing the harness. The harness should be too dumb to need them. Inline self-tests behind one flag for the driver and scripts, like lifecycle.ts had, was advice I received. I am open on this.

## Quality

I want to be sure the output quality is there, so I checked what the July 28 snapshot already does about it. It has three quality layers, all done by agents, none by code.

### Fidelity audit

In consult-issue, after one slot synthesizes a plan, the other slot audits it against the positions and the planning plan and writes a verdict, faithful or drift. The implementer and the checker both read that verdict. This is the one I trust most because it is a second model reading the same files with fresh eyes.

### Implementer self-check and QA reviewer

implement-issue keeps a Quality Self-Check block in the implementation plan and then must spawn one separate QA reviewer agent before sign-off. The reviewer owns the checklist bookkeeping after verification. So even the old system already used a subagent for review, which fits how I want to use subagents now.

### Advisory quality pass in check-issue

check-issue does the blocking review against the plan, and then a second, non-blocking pass against a 164 line file called advisory-quality-standards.md: cyclomatic complexity per function at most 10, cognitive complexity at most 15, nesting at most 4, function size at most 50 lines, at most 3 parameters, duplication under 3 percent, maintainability index bands, dead code, plus per-language bands for Python, CSS, HTML, web performance, and agent markdown. Every finding gets an AQ- id with method, value, threshold, source, and remedy, and nothing happens with it unless I promote the id by hand. This is the part that smells like the beginning of the machinery I am running away from. Measured numbers with exact report formats, written by an agent by hand-counting decision points. I am not sure it ever changed a merge. The advice I received, open, is to keep the first two layers and ask hard whether the third one earns its place, or whether one sentence in check-issue about complexity and duplication does the same job.

Sanity check, tier 1, same Anthropic piece: "In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop." That is the fidelity audit and the QA reviewer. It says nothing about measured thresholds.

### The challenge on advisory

My point: the advisory pass never blocks. Nothing in the whole system tests deterministically. And yet I still want to quasi-enforce quality, and this pass was good, because at least it was something.

The challenge I got back, and I think it is fair. First, it is not really optional. In the snapshot a skipped advisory pass is a workflow-compliance defect, so every check-issue paid for it whether or not it changed anything. It is enforced as a ritual, just not as a gate. Second, the numbers are not deterministic. The file says cyclomatic complexity "by manual decision-point count", an LLM counting branches by eye. That is a model pretending to be a linter, and it is the least reliable way to get a number. Third, if it never blocks and nobody promotes the ids, the honest question is whether it ever changed a merge.

Where that leaves me, as advice received and open, not my lean. If I want real quasi-enforcement, the deterministic part should be a real tool, not prose: a linter with complexity and nesting rules, a dead-export checker, a duplication check, whatever the repo already has, run by the implementer as part of the leaf's own check and read by check-issue as evidence. That is cheap, deterministic, and it is exactly the "check the agent can run" the best-practices page names, "a linter" is on its list. Whether a finding blocks or advises would be config per repo, not a prose rule. The judgement part, does this design make sense, is it too complex for what it does, stays with the checker as one paragraph, no AQ- ids, no report format. That keeps the "at least it was something" without the hand-counting. A pointer for the chart, not a decision.

### Ponytail

The other thing I keep coming back to is the ponytail skill on GitHub (github.com/DietrichGebert/ponytail, MIT). I like it because it produces the kind of code I actually want inside the repos: the least code that works, standard library first, no abstractions nobody asked for, deletion over addition. My instinct is to make it part of the quality audit rather than a separate thing. The worry is the usual one. Individual skill files get too big, so the skills need reference files in their own folders, which is fine, but I do not want that to be the start of complexity going out of control again. I want the benefits, smaller diffs and less code to review, without forcing myself into hooks or any deterministic wiring.

Sanity check, recorded as received. The skill itself is only text. Its core ruleset is a 56-line AGENTS.md, a seven-step ladder (need it at all, exists already, standard library, native platform, installed dependency, one-liner, then minimal code) plus a few non-negotiables it never simplifies away: validation at trust boundaries, error handling that prevents data loss, security, accessibility, and one runnable check for any non-trivial logic. Its review persona is about 90 lines, prompt only, five tags (delete, stdlib, native, yagni, shrink), one line per finding, ends with action items or "lean already, ship". The hooks in the repo exist only for auto-activation, mode state, and pushing the rules into subagents, none of which I need. The author's own benchmark (tier 2, self-reported, Haiku 4.5, 12 tasks) claims 54 percent less code and 22 percent fewer tokens. The independent test I trust more is Denis Shiryaev at JetBrains, July 2026 (tier 1, 80 paired tasks on Sonnet 5, blog.jetbrains.com/ai/2026/07/ponytail-skill-claude-tested): 15 percent less code at the median, 10 percent cheaper, 11 percent faster, quality unchanged, and installed as an optional skill it never activated on its own in ten sessions. It only worked when its rules were in front of the model every turn. The history matters too: the first headline of 80 to 94 percent was inflated by a chatty baseline, Colin Eberhardt of Scott Logic showed that, and the maintainer rebuilt the benchmark in the open (infoq.com/news/2026/08/ponytail-agent-skill-benchmark, tier 2). In that rebuilt benchmark Eberhardt's seven-word prompt, follow YAGNI and prefer one-liners, got 33 percent less code against ponytail's 54, and dropped one path-traversal guard in twenty safety runs where ponytail dropped none. So most of the effect is a short instruction, and what ponytail adds on top is the list of things it refuses to cut. So if I take it, it has to live in what the implementer and checker already read, not in a skill that hopes to be triggered. The advice I got: two reference files, one for the implementer and one for check-issue, or the 56 lines folded straight into the repo's AGENTS.md, and nothing else. Whether it goes into check-issue's review, into the implementer's self-check, or both, is open for the chart.

So the real dilemma is the seven-word prompt versus the 56-line ruleset. Reducing complexity is my number one, then cost, then better code, then performance. The per-task numbers in the rebuilt benchmark say the short prompt sometimes lands next to ponytail and sometimes still overbuilds, the date picker went 404 to 162 with the short prompt and to 23 with the ladder, and the short prompt was the only arm that dropped a security guard. The advice I got is that both are plain text the agent reads and the difference is 49 lines in one file, the ladder step about native widgets and installed dependencies plus the list of things never to cut, and that the machinery to avoid is the rest of the ponytail repo, not the ruleset. My global instructions already carry KISS and YAGNI, so the short prompt adds little on top. Still open.

## Cost, quality, speed

I still want to optimize for cost, and quality, and speed, and I want to do it on the level of the whole state machine, not inside one harness. Simplicity sits above all three, and between them the order is cost, then quality, then speed. Right now slot A and slot B both run on the highest cost models, and that is not sustainable for me.

One thought is subagents. Slot A and slot B stay the main agents, and the actual building goes to cheaper subagents inside whatever harness that pane runs. I looked: Claude Code subagents run in their own context and can be pinned to a cheaper model, Codex has subagents on by default that inherit the parent's model unless a config overrides it, and pi has none built in on purpose but spawns itself with `pi --print` and a chosen model. Codex's own docs warn that subagent workflows use more tokens in total, so the saving is price per token, not fewer tokens. I will figure that part out myself, it is a conversation between the main agent and its subagent, and I do not want the machinery to know or care.

What I do not want is to depend on any specific harness. Claude Code, Codex, pi today, maybe grok tomorrow, who knows. The driver should only know a pane and a skill name.

Things the state machine itself could own, a list I received as advice: which model tier handles which phase, cheap for drafting positions, strong for synthesis and checking. Running both positions and both rebuttals at the same time. Whether the rebuttal round is needed for every leaf or could be a per-repo flag. One merge at a time. One retry then ping me. I have not weighed any of these and none of them is mine yet.

### Compaction instead of clearing

I am afraid of cache reading and cache writing, and I do not want another layer where herdr or anything else has to clear the agent's context at the right moments. I want to depend on autocompaction. I do not think any one leaf or issue will be a problem for compaction a few times over, even five to ten times, not with the current models. Sanity check, tier 2, Claude Code prompt caching and cost docs (code.claude.com/docs/en/prompt-caching, /costs). Cache reads bill at about a tenth of the input rate. Compaction throws away the conversation cache by design, but while the cache is warm the summarising request reads the whole history from cache, so a mid-session compaction costs a fraction of what the context size suggests, and the turn after it rebuilds a cache for only the short summary. It costs the most when the cache has gone cold, after a break longer than the lifetime, five minutes on an API key and an hour on a subscription within plan usage. An agent working through a leaf keeps its cache warm, so the cost side of my premise holds. The risk is not cost, it is what the summary drops. The docs' own mitigations are compaction instructions in the project instructions file saying what to preserve, and keeping the durable state on disk, which is what the plan file and state.yaml already are. Nothing in the docs asks for an outside process to clear or compact, and clearing between unrelated tasks is a habit for a human session, not a machinery step. I then asked the sharper question, does compaction break the cache, and what happens to a file that was in the conversation. Same docs, plus the context window page (code.claude.com/docs/en/context-window). Yes, by design, once: the summary is a new shorter history that shares no prefix with the old one, so the conversation layer is rebuilt on the next turn, while the system prompt layer stays cached and the project instructions reload from disk. The file's content does not survive as content. The summary keeps the file's name and important snippets, and a mention in the summary is just text, it breaks nothing. Right after compaction Claude Code re-reads up to five of the files the agent read or edited, most recently modified first, so the plan file and state file come back on their own, as one fresh read each, then cached again. Invoked skill bodies are re-injected too, but capped at 5,000 tokens per skill and 25,000 in total, oldest dropped first, and truncation keeps the start of the file. That last fact is a design rule for the new skills: the part that must survive compaction goes at the top of SKILL.md and the whole body stays under the cap, which is another reason for the entry file plus references shape. I checked this for Claude Code only, Codex and pi handle their own context and I have not read how.

### Deploying the scripts to a consumer repo

Updating the scripts on a consumer repo is not elegant today. One repo sits on the machine and distributes everything to the other repos on the same machine, and the deploy commands are flaky, prone to errors, and I do not want to spend time fixing them. My first thought was something like a git submodule or subrepo: the part that needs to be in the consumer repo, the scripts and the setup, gets pushed to GitHub and pulled from the consumer. Food for thought, not a decision. I do not even want to call this machinery, the word alone already sounds complex. They are scripts. Pushing the skills to be global on the machine is not a problem, I think we need that anyway. The problem is deploying the scripts into the individual repos, because that is another piece I have to maintain, and it is what broke before: some files ended up out of sync in the consumer repo and the errors came from there. Sanity check, recorded as received, with one correction I accept. Local, tier 2: the framework repo today tracks 240 script files inside its own issues/.scripts, copied in by sync-payload and committed, so every consumer holds its own committed copy of the scripts, and that copy step is what breaks. Git book on submodules (git-scm.com/book/en/v2/Git-Tools-Submodules, tier 2): after a clone the submodule is empty until init and update, updates leave it in detached HEAD so commits made there can be lost, every update needs a pointer commit in each consumer, and the book says submodules make sense when you actively develop both projects together, otherwise a plain dependency mechanism is simpler. So a submodule turns a copy step into a pointer commit per repo per update, better than copying, but still one copy per consumer. The correction: the elegant option is no copy at all. Claude Code skills docs (code.claude.com/docs/en/skills, tier 2): personal skills under ~/.claude/skills apply to every project, and a skill entry there can be a symlink to a folder elsewhere on disk, so the skills folder in the tool repo gets symlinked once per harness and a git pull in the tool repo updates every project. The driver and lifecycle scripts live only in the tool repo and run from there, pointed at a consumer by the path in the repos block of config.yaml that already exists. The consumer repo holds only its issues tree and its config, nothing to deploy and nothing to keep in sync, and my colleagues never need the scripts because their door is GitHub Issues. I then had the other harnesses checked too, because this is never only Claude Code, it is Codex, pi and whatever comes next. Codex skills docs (learn.chatgpt.com/docs/build-skills, tier 2): user skills live in ~/.agents/skills and the docs say in so many words that Codex supports symlinked skill folders and follows the symlink target. pi docs (pi.dev/docs/latest/skills, tier 2): global skills come from ~/.pi/agent/skills and ~/.agents/skills, and settings.json takes a skills array of extra files or directories, so the tool repo's skills folder can be listed there directly with no link at all. So every harness I use today can point at one skills folder in the tool repo, by symlink or by one settings line, and a new harness is one more link or one more line. The one link per harness is the whole install, and the burden of proof is on the agent claiming a harness cannot do that. What is not open: it has to work for every harness and every agent, the ones I run now and the ones that come later, with no harness getting a special path.

Then the scripts. I asked how they get pushed to the consumer repo, and the answer I received, open, is that they do not get pushed at all. Sanity check, local, tier 2, from the July 28 skill files: the skills call the scripts by a path relative to the consumer repo, bun issues/.scripts/lifecycle.ts, and that relative path is the only reason a copy has to exist in every consumer, which is also most of what init-issues does, copying the scripts with their package.json and lockfile. The advice: the scripts live once in the tool repo and get one command on my PATH, a link in ~/.local/bin to the tool repo's entry script, so a skill says akrogon phase issue <slug> with no path in it, and the command finds the consumer repo from the current directory or from the repos block in config.yaml when the driver names it. Updating the scripts is a git pull in the tool repo and every repo sees it at once, the same as the skills. The consumer repo keeps only data, its config.yaml, its open and closed issues and the gitignore rules for worktrees, so init-issues shrinks to creating that and there is nothing left to fall out of sync. PATH sits under every harness, so this needs no harness-specific setup, and the one link per harness for skills stays the only per-harness step. I think these are good ideas, the global skills by one link per harness and the scripts behind one command with no copy, and I want them on the table, but all of it is a point of contention and one of the decisions the chart has to settle, not something I have settled here.

One more idea for the same discussion, an idea only. I asked whether symlinks could carry everything so the skills never get deployed at all, including their reference files, and whether that has complications. Sanity check, recorded as received. The link goes on the whole skill folder, so the reference files, scripts and assets inside it come along, and a relative path inside the skill resolves in the real folder. Claude Code skills docs (code.claude.com/docs/en/skills, tier 2): a skill entry in the personal, project or enterprise location can be a symlink to a directory elsewhere, Claude Code reads SKILL.md from the target, and if the same target is reachable from two locations it loads the skill once. Codex skills docs (learn.chatgpt.com/docs/build-skills, tier 2): Codex supports symlinked skill folders and follows the target when scanning, and if two skills share a name both appear in the selector. pi (pi.dev/docs/latest/skills, tier 2) takes a list of skill directories in settings and needs no link. The Claude Code issue tracker searched for symlinked skills shows nothing broken on Linux, only Windows junction problems, plus one open issue, anthropics/claude-code 88400, confirming that discovery is exactly one level deep and a deeper SKILL.md is silently ignored. So the shape that works is: the tool repo's skills folder stays flat, one folder per skill, each harness root gets one link per skill folder, and only one root per harness so Codex does not show a skill twice. A single link on the whole skills root is not documented on either harness, and my Claude root holds unrelated skills, so per-skill links are the safe form. Reference files in a skill are addressed by paths relative to the skill folder, never absolute. The folder name synced is reserved under Claude Code roots. The one small piece left is a short idempotent script in the tool repo that makes a missing link for each skill folder in each harness root, run once and again when a new skill is born, and since it links instead of copying it cannot leave anything half synced. Just an idea for the chart.
