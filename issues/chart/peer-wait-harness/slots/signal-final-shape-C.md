# Slot C final-shape check: turn end signal

Disagreements only. Draft items numbered as in `signal-final-shape-draft.md`.

- F1. Item 3 makes a pi session change an error "for every kind", which can false-error a live pi turn. Pi's verdict under item 1 never reads the session; it keys on `agent_session.source` and `screen_detection_skipped`. The reported session value is not a stable identity string for pi: the installed integration reports `agent_session_path` when it can read the session file and `agent_session_id` otherwise, re-evaluated on every report (~/.pi/agent/extensions/herdr-agent-state.ts:94-112), so the same session can present first as an id and then as a path (live list today shows pi as `kind: path`), and a pi `/fork` legitimately continues the same task under a new session file reported through `session_start`. Exact fix: scope item 3's session-change error to the kinds whose reader keys on the session (claude, codex); for pi, a session value change is ignored while the re-read entry still shows `herdr:pi` hook authority, and loss of that authority degrades pi to unproven instead of erroring.
- F2. Item 4 cannot be followed from the wait's output. The outcome line carries only `outcome`, `pane`, `file` and `status` (peer-wait.ts:136-140), but the questions.md rule keys on whether that peer, in that wait, had a proven end signal, which for pi depends on hook fields and for codex on whether the rollout matched. The door cannot derive that from `budget` plus `idle` without re-running `herdr agent list` and re-deciding codex matching itself. Exact fix: add the last turn-check result to the outcome line (for example `"signal": "proven" | "unproven"`, set from the turn check at the final grace check, defaulting to `"unproven"` when no grace check ran), and write item 4's rule against that field: report before rerun when `outcome` is `budget`, status is `idle` or `done`, and `signal` is `unproven`.
- F3. Item 1's pi condition uses a status the draft never has peer-wait read at check time. The schema additions named are `agent_session.source` and `screen_detection_skipped`; the list schema today has no `agent_status` either (peer-wait.ts:16-26). The only status in hand at the turn check is the pre-grace sample (peer-wait.ts:175-180); the grace itself only waits for `working` (peer-wait.ts:185), so a pi peer that goes `blocked` during the 10 s grace would be judged `ended` from the stale `idle` and return `failure` instead of `blocked`. Exact fix: keep `agent_status` (optional) in the list schema, evaluate item 1's pi `idle`/`done` against the entry re-read at the grace check under item 3, and let a re-read status of `blocked` return the `blocked` outcome before the turn check runs.
- F4. Item 1's codex binding does not say what happens when the first grace check cannot bind. "At the first grace check the wait binds the newest `task_started` `turn_id`" plus "no `task_started` found: unproven" reads as a one-shot bind: a rollout that is created, flushed or first matched only after that check would stay unproven for the whole wait even though later grace checks could bind it, and the draft also does not say the bound id is held across later checks rather than re-picked as the newest started. Exact fix: replace that sentence with "the wait binds at the first grace check where a `task_started` is found, holds that `turn_id` for the rest of the wait, and retries binding at later grace checks until then; while unbound the check is unproven".

No disagreement with items 2, 5 and 6, or with the claude and unproven-default parts of item 1.
