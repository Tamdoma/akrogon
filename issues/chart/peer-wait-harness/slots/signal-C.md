## Q1. What peer-wait reports for a non-Claude peer seen idle with no file

Pick F1 (option c, a hybrid): `failure` only when a per-harness affirmative end signal is proven for that peer; every unproven kind waits out the budget, which is option (a) as the default and option (b) where proven.

Proven signals, per harness:

- pi: herdr's own state, but only when hook authority is in effect. The installed pi integration (`~/.pi/agent/extensions/herdr-agent-state.ts`, HERDR_INTEGRATION_VERSION=9 at :5) sets `agentActive` on `agent_start` (:243) and publishes `idle` only on `agent_settled` gated by `ctx.isIdle() === true` (:253-259 in the installed file; same shape in herdr source assets). Subagents, long tool calls and silent thinking all run inside that span, so they cannot produce a hook `idle`. Herdr treats (`herdr:pi`, `pi`) as full lifecycle hook authority and skips screen detection (herdr src/detect/mod.rs:283-292). Live proof today: `herdr agent list` shows the pi peer w8:pPY with `agent_session.source = "herdr:pi"`, `kind = "path"`, and `screen_detection_skipped = true`, status `working` through its tool calls. So for pi, peer-wait needs no transcript reader: it needs to stop discarding the fields that prove the hook is in effect. Its list schema keeps only `pane_id`, `agent` and `agent_session.value` (peer-wait.ts:16-26); it must also read `agent_session.source` and `screen_detection_skipped`, both optional so a herdr without them degrades to "unproven, keep waiting", never to failure. Without hook authority, pi falls back to one screen rule (contains `Working...`, herdr src/detect/manifests/pi.toml:7-13) and its idle is unproven.
- codex: a rollout reader mirroring the Claude one. Herdr's codex state is screen and OSC-title inference only: spinner char in the title means working (codex.toml:14-20), a `Working (… esc to interrupt)` bottom line means working (:59-66), and any other non-empty title means idle (:68-78). Codex is not in the hook-authority list (detect/mod.rs:283-292), so a codex `idle` can in principle appear inside an open turn whenever the title and bottom lines stop matching, for example while long command output owns the bottom lines. The affirmative signal exists in the rollout file: live measurement on the current codex peer's session (`~/.codex/sessions/2026/10/15/rollout-2026-10-15T17-28-58-<herdr session id>.jsonl`) showed 19 `task_started` against 18 `task_complete` event_msg payloads while herdr said `working`, and 19 against 19 minutes later once herdr said `idle`. Reader rule: turn open while the last of `task_started` / `task_complete` / `turn_aborted` in the tail is `task_started` (`turn_aborted` exists as an event_msg payload with `turn_id` and `reason: interrupted` in older rollouts on this disk, e.g. 2026-10-01). The file is MBs (6.3 MB live), so read it the way `claudeTurnOpen` already reads whole transcripts (peer-wait.ts:114-124), only at grace checks.
- claude: unchanged (`claudeTurnOpen`, peer-wait.ts:112-128).
- every other kind, including a returning agy: no failure on idle or done; the wait runs to `budget`. This is the lesson's rule applied as a default: pane status is a turn signal only for harnesses whose status covers subagent work (learnings/history/2026-10-15-peer-wait-antigravity-idle.md, Learning).

What each rejected pure option breaks or invites:

- Pure (a), never failure on idle for anyone: a peer that truly ended without a file (wrote the wrong path, answered in chat, died after its turn) converts every detection into a full budget, and `budget` is the outcome the door reruns at once under the peer-turn lock (forks/peer-turn.md Taken item 3), so a dead peer invites rerun after rerun with no script-side stop. The token cost is near zero (deterministic script), the wall-clock and door-turn cost is unbounded until a human judges. It also throws away fast, correct failure for pi, whose hook idle is exact.
- Pure (b), per-harness checks for pi and codex but current idle-failure kept for the rest: the original bug returns verbatim for the next harness added or the day agy is named again, because `turnOpen` returning false for unknown kinds (peer-wait.ts:130-131) is what manufactured both false failures. Readers are also format couplings: the codex rollout is an internal JSONL that can rename events without notice, and the pi check depends on an integration file herdr overwrites on update (installed file header :1-5). Both must degrade to waiting, never to failure, when their proof is missing (no session id, file not found under a non-default `CODEX_HOME`, hook fields absent).
- Session replacement cuts across all readers: peer identity is read once (peer-wait.ts:156) and `turnOpen` uses that captured session forever. Pi re-reports its session on `session_start` and on extension reload mid-run (installed integration, `session_start` handler), and a peer can be restarted or resumed under a new session while A waits. A reader keyed to the old session sees the old turn's end marker and reports failure for a live new turn; that failure mode already exists for Claude today. Fix inside F1: re-read the peer agent at each grace check (one `herdr agent list` per idle sighting, not per loop) and key every reader and the pi hook test to the current session. That also gives process-exit detection for free (Q2).

## Q2. Should `done` still give `failure` while `idle` does not?

Pick: no. Treat `done` exactly like `idle`. The fork's premise is wrong: herdr's `done` does not mean the process exited.

- Herdr's internal state has only Idle, Working, Blocked, Unknown (herdr src/detect/mod.rs:11-19, Unknown glossed "plain shell or unrecognized program"). The public `done` is Idle plus unseen: `(Idle, false) => Done, (Idle, true) => Idle` (herdr src/app/agent_view.rs:393-398), where `seen` is whether the user has viewed the pane since it went idle (herdr src/pane/state.rs:9). Keying `failure` on `done` would make the outcome depend on whether the operator happened to look at the peer's pane. Live instance today: `herdr agent list` showed the door's own live claude pane w8:pNP at `done` between turns; nothing had exited.
- For an actually exited pi or codex process, herdr has no exited status to report: the pane falls back to a shell (Unknown) or the agent entry disappears. Peer-wait already loops on `unknown` to budget (only `idle`/`done` enter the grace branch, peer-wait.ts:183) and passes a non-timeout herdr error through (peer-wait.ts:167-170). The honest dead-peer signal is the agent vanishing from `herdr agent list`: `readPeerAgent` already throws `No herdr agent on pane` (peer-wait.ts:107), but it runs once at start. Under F1's re-read at grace checks, a vanished agent becomes that thrown error and a non-zero exit to the operator, which is the taken precedence for herdr failures. That is the fast dead-peer path; `done` is not one.
- Test consequence: tests/peer-wait.test.ts:104-112 (`failure on done with a 0-byte return file`, agent kind `fake`) encodes the wrong premise and under F1 becomes: kind `fake` is unproven, so `done` and `idle` both end in `budget`; `failure` needs a proven-kind fixture.

## Pitfalls

- P1. Reader errors must degrade to waiting. Missing session, zero or multiple rollout matches, unreadable tail: each means "end not proven", so the grace check keeps waiting instead of throwing or failing. (Claude's current throw at peer-wait.ts:119-120 and :132 is the exception already in production; do not copy it into the codex reader.)
- P2. A codex peer under a non-default `CODEX_HOME`, or a pi peer without the herdr integration installed, looks identical in `agent list` kind terms to a proven one. Both must land in the unproven bucket by the checks above (file not found; `screen_detection_skipped` not true), or F1 reintroduces false failure on exactly the peers supplied from other setups.
- P3. Pi hook reports can be dropped: the integration retries delivery for 500 ms then 1500 ms and gives up (herdr source asset `sendRequest`). A dropped `idle` report leaves herdr at `working` (safe: longer wait). A dropped `working` report at turn start is caught by peer-ask's prompt guard `--until working --timeout 5000` (peer-ask.ts:19) as a prompt failure, before any wait starts. No mid-turn report exists to drop, since state changes only at start, settled and blocked toggles.
- P4. Budget reruns are the door's behavior, not the script's. Under F1 an unproven dead peer returns `budget` with `status: "idle"` every rerun; the chart skill text that says rerun at once on `budget` should get its one-line bound from the same leaf (an idle-status `budget` repeated with no `working` seen is reported to the operator instead of rerun forever), or F1 trades false failure for an endless polite wait.
- P5. Fake herdr cannot express the cases that matter today. Its `agent wait` returns a scripted status once without storing it (tests/fake-herdr.ts:244-262 area: `result({ agent: { ...target, agent_status: entry.status } })`), its `agent list` emits one fixed agent and session per pane, and peer-wait.test.ts runs with the real `HOME` (setup at tests/peer-wait.test.ts:20-48 spreads `process.env` with no HOME override), so a codex reader scanning `~/.codex/sessions` in a test would read the developer's real sessions. The leaf needs: a persisted per-pane status sequence consumed across both `agent wait` and `agent list`; list entries carrying `agent_session.source`, `agent_session.kind` and `screen_detection_skipped`; a scripted session-value change mid-wait; and a temp `HOME` in the test env holding fixture codex and claude session files. All of that is fixture extension inside existing helpers, not new machinery.
- P6. Kind strings are herdr's, not akrogon's config keys. The live list reports `agy` would-be peers under herdr's manifest id `agy` (aliases antigravity, antigravity-cli, antigravity.toml:1-5) while config harness names are operator-chosen. F1's proven-kind test must match on the herdr-reported `agent` value plus the session `source`, never on a config harness name.
