# Slot B landing rebuttal

F1. A's proposed re-check trigger, “when the rebase changed anything outside the review range,” is not sufficient. Conflict resolution or changed integration can alter the code inside the previously reviewed range. That is precisely where renewed review matters. I retain the simpler rule: B approves the final committed head whenever rebase changes the head, using the prior reviewed head and recorded range-diff. C's content-equivalence exemption could be an explicit optimization, but it needs a defined comparison and must include configuration changes that affect checks. The existing lifecycle reuse rule checks several properties, including issues/config.yaml being unchanged, rather than simply exempting all issues/ changes (skills/merge-issue/SKILL.md:47). Evidence: skills/merge-issue/SKILL.md:53 records old base, prior reviewed head, new target and resolved head after conflict resolution; skills/check-issue/SKILL.md:49 binds review to base and head.

F2. I do not agree to an unconditional “fast-forward local main at root” as part of cleanup. The configured default branch need not be main, and a registered root may hold unrelated operator edits or divergent local commits. Remote delivery does not authorize discarding or rewriting that work. Use the configured branch, preserve unrelated changes, and report any local reconciliation that cannot safely complete. Existing sync already requires the configured default branch and rejects unrelated staged paths (src/sync.ts:10-33), and preserves unrelated edits only through its own checked process (docs/guide/files.md:67). Keep branch/worktree removal after verified delivery, but do not make root reconciliation a silent reset or an assumption that landing updated the local checkout. A root-sync failure after successful code push is a remaining record-publication action, not a failed code delivery.

F3. I retain no broadcast in the first version as the lower-scope recommendation. If the operator selects configured broadcasts instead, the implementation must explicitly extend broadcast-issue's direct trigger and actor. Current instructions require the merge slot after issue/epic complete and supplied completion-owner briefs (skills/broadcast-issue/SKILL.md:10,14). A chart brief is not currently that lifecycle trigger. Reuse the existing sender only after making this new entry point explicit, retaining its retry and failure semantics (broadcast-issue/SKILL.md:41-43). Configuration alone does not remove that contract gap.

F4. I disagree with unbounded automatic non-fast-forward retries. A normal rejection is a concrete stop with preserved work unless the later growth fork chooses a bounded automatic integration cycle. Each cycle must establish a new tested and B-approved candidate rather than simply repeating push. Existing normal-push serialization does not imply permission for an unlimited retry loop (skills/merge-issue/SKILL.md:47,65). The merged notes correctly leave the bound open, so no landing contract should settle it implicitly.
