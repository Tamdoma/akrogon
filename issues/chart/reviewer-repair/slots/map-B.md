## 2. Material forks

**D1. Repair authority: all B Fixes, bounded B Fixes, or A remains the repair owner?** Recommend bounded B repair. A specific local correction with an unchanged contract and a direct proof is a plausible candidate. Examples already observed: a literal shell-command correction (`issues/closed/base-red/base-red-exit/review-B.md:12–33`) and a guide example correction (`issues/closed/review-bar/realistic-review-bar/review-B.md:11–18,42`). Multi-step launch behavior, cross-system changes and missing live acceptance evidence stay with A. This is an ownership decision, separate from whether a finding qualifies as Fix. Do not reopen the settled realistic Fix/Nit bar.

**D2. Qualification: proof and scope, or arbitrary line/time thresholds?** Recommend proof and scope. B must be able to name the already chosen behavior, reproduce the failure, make the smallest correction in owned surfaces and demonstrate that exact behavior afterward. No new policy, dependency, acceptance criterion, schema contract or external permission can be required. A one-line change can alter security or deployment behavior, so size alone is insufficient. Nits remain deferred, not an invitation to reviewer cleanup. Source: `skills/check-issue/SKILL.md:43–51`, `skills/implement-issue/SKILL.md:75`, `skills/check-issue/ponytail.md:15–30`.

**D3. Verification: B tests and approves itself, A checks B's repair, or a fresh evaluator checks it?** Recommend A checks only B's repair against its before/after commits, findings and functional evidence. B still runs applicable checks as repair author. This preserves separation for the new code without adding a third seat. A implemented the original feature, so this does not create an independent full-feature audit, but A did not author B's patch. A new session of B is not equivalent to a different author. Accepting B's own tests as the only gate buys the most speed, but abandons the separation that made B valuable. The strongest production evidence does not demonstrate that autonomous repair plus self-approval is equally safe.

**D4. Timing and concurrency: edit during blind paired review or after its snapshot is settled?** Recommend no editing while either initial reviewer is still inspecting the shared head. Capture both initial reviews against one immutable commit, then choose a repair owner. A's old ready verdict cannot authorize B's newly changed head. A narrow verification turn is cheaper than A reconstructing and implementing the repair, but it is still a turn. This fork decides whether the workflow really reduces work or simply relabels the existing loop. Current paired reviews, aggregation and clean-worktree checks: `skills/check-issue/SKILL.md:33,43,61`, `src/phase.ts:201–205,215–240`.

**D5. A's retained responsibility: implementation owner or displaced worker?** Recommend A retains synthesis, implementation, broad Fix repair, criterion proof and report/doc responsibility. B only owns selected repairs and their evidence. The verifier follows repair authorship, rather than permanently treating B as independent. This is a narrow exception to the worker/reviewer role lock, not another global seat/model swap. It must be explicit alongside `issues/chart/seat-role-swap/CHART.md`.

**D6. Accounting: B repairs consume rounds, bypass the cap, or get a separate budget?** Recommend every repair batch, whoever authors it, consumes the existing repair budget. Otherwise changing ownership creates an unlimited hidden loop. Keep cap 3 and model/effort settings unchanged unless the operator chooses a separate change. Decide whether merge-origin repairs share this budget too: current source counts and caps review-origin repairs only, although older logs show merge entries incrementing counters. Recovery resets rounds and can require both initial reviewers again. Owner and verified head must not be inferred from `fix_rounds`.

**D7. Merge: inline B repair there too, or preserve its existing red-check return?** Recommend keep merge's present checks, rebase and red-check repair route in this destination. B already resolves rebase conflicts and records range-diff. Making arbitrary merge-red repair inline would extend the same authorship/verification issue to a new integration head. If selected later, it must follow the same ownership and accounting rules, not gain implicit self-approval because B also pushes. Source: `skills/merge-issue/SKILL.md:35–47`.

## 3. Practitioner evidence

All sources read 2026-10-02. These are primary sources. Recommendations above are inferences for this repository, not claims that its proposed policy has been tested.

**S1. Google: automate comment resolution while authors retain application.** Alexander Frömmgen and Lera Kharatyan, [Resolving code review comments with ML](https://research.google/blog/resolving-code-review-comments-with-ml/), published 2023-05-23. Google's internal production feature resolved hundreds of thousands of comments annually. Authors applied 40–50% of previewed suggestions. Its stated productivity impact was partly expected and a broader A/B test was still planned. This supports concrete patches over explanations, not reviewer self-approval. [Gerrit suggested edits](https://gerrit-review.googlesource.com/Documentation/user-suggest-edits.html), current documentation, likewise gives reviewers suggestion authoring and authors application into a new patchset. That new patchset can diverge from the author's local commit.

**S2. Google review practice: preserve external judgment, avoid unnecessary round trips.** [Canonical review introduction](https://google.github.io/eng-practices/review/) defines review as someone other than the author inspecting the code, while also accepting qualified pair programming as reviewed. [Speed of code reviews](https://google.github.io/eng-practices/review/reviewer/speed.html) permits approval with minor unresolved comments under stated conditions. This supports making a local fix cheap, but not claiming any reviewer-authored change has received independent review. It also shows that separation need not mean a full repeated review of the whole feature.

**S3. Meta: reviewer repair burden can erase the gain.** Chandra Maddila and colleagues, [AI-Assisted Fixes to Code Review Comments at Scale](https://arxiv.org/html/2507.13499v1), submitted 2025-07-17. MetaMateCR runs in production across four languages and processes thousands of comments weekly. A randomized trial increased TimeInReview 5.5% and TimeSpent 6.7% when suggestions were shown to reviewers. Collapsing suggestions for reviewers while showing them to authors removed statistically significant regressions. Their conclusion favors keeping fix responsibility with authors. This directly challenges bounded B repair: it is justified here only if B's retained context and stronger repair capability reduce total repair-and-verification time. Those gains are not measured yet. Human reviewer workload is also different from two dedicated agent seats.

**S4. GitHub: automate the handoff and batch comments.** [Copilot review feedback with cloud agent](https://github.blog/changelog/2026-05-19-easily-apply-copilot-code-review-feedback-with-copilot-cloud-agent/), published 2026-05-19, offers selected feedback batches, model choice and fixes either directly on the PR or in another PR. This is an established product mechanism for review-to-repair automation. It separates code review feedback from the repairing cloud agent. It is not a controlled result proving that the reviewer should author and approve its own patch.

**S5. Anthropic: generator/evaluator separation helps real software testing.** Prithvi Rajasekaran, [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), published 2026-03-24, reports a planner/generator/evaluator harness with Playwright-based QA, file handoffs and feedback to the generator. It reports self-evaluation leniency and improved outputs from separate evaluation. It is an experiment with substantial extra time and cost, not a production-scale comparison of reviewer-repair ownership. Erik Schluntz and Barry Zhang's [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), published 2024-12-19, frames evaluator/optimizer loops around clear criteria and useful feedback, and urges measuring whether added complexity improves outcomes.

**S6. Agreement, disagreement and the conditions that flip advice.** These sources agree on actionable fixes, explicit criteria and reducing low-value latency. Google/Gerrit and GitHub support supplying or automating patches. Meta's measured trial warns that reviewer involvement in fixes can slow reviews. Anthropic's experiments favor a distinct evaluator. Local, settled corrections with short objective proof favor B repair. Unsettled behavior, weak tests, security or data-loss consequences, external mutation, scarce reviewer capacity, or expensive live proof favor author repair and separate verification. No source establishes that simply removing independent re-check improves end-to-end outcomes.

Evidence gap: searches included `reviewer directly edits author patch code review small fixes Google Gerrit suggestions at scale` and `reviewer repairs own findings agent code review independence controlled study`. They found the production Google and Meta work above and agent-harness experiments, but no directly comparable controlled trial of a dedicated two-seat coding harness where the reviewer repairs and self-approves versus an author repairing and a reviewer checking. No model-memory rule substitutes for that missing result.

## 5. Recommended destination

Create one akrogon destination for bounded reviewer-authored repair with verification by the other seat: once initial review of a fixed head is complete, B may repair a concrete, local Fix whose behavior and proof are already settled, record before/after commits and run the applicable checks, then A verifies only B's patch before B merges. A keeps broad repairs, implementation, live criterion work and report/doc ownership outside B's selected repair. Preserve the realistic Fix/Nit bar, models and cap, count B repair batches against the same budget, and make dispatch follow repair authorship rather than `fix_rounds > 0`. This departs narrowly from Meta's author-repair recommendation and must earn its place through shorter total repair-plus-verification time without unresolved criteria or added defects. It should remove unnecessary repair reconstruction for command and guide corrections, while the EmDash acceptance gap and missing GitHub scope remain explicit contract/evidence and operator-capability problems that a seat change cannot solve.
