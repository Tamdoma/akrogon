## Proposed criterion and pruning bar

**B recommendation, not a settled policy:** A durable test must name an operator/consumer outcome, a separately justified contract, or an important safety invariant with a realistic path and consequence. Name where its expected result comes from. Then choose the least costly proof that detects that failure through the relevant code. Tests copying private calls, current outputs or incidental formatting do not become valid merely by appearing in a criterion. Commands, numeric values and fixed references that execute literally remain legitimate exact checks.

At charting, reject vague requirements such as “all inputs work” and coverage/count targets without a behavioral purpose. At planning, identify the specific failure, existing proof and remaining gap. One proof may satisfy several criteria. A new test needs a distinct detection or diagnostic benefit, not a new function name. A complex pure rule can deserve units. A trivial one-line change retains the existing no-new-test exception.

For an existing suite, record the retained protection and use one of three actions: remove a false/obsolete/implementation-only expectation, consolidate redundant checks, or retain the test but reduce when it runs. Do not demand whole-suite mutation campaigns or new audit machinery to remove an obviously invalid assertion. For material replacement claims, use the real historical defect or a bounded meaningful mutation to establish that retained proof detects it. Multiple removed tests must be assessed together, because individual redundancy is not collective redundancy.

| Proof type | Worth keeping or adding when | Bloat or false-confidence signal |
|---|---|---|
| Focused unit / small sociable test | A consequential computation has many meaningful variations and expected results come from a contract or independently known example. It provides cheap detection and specific diagnosis. | Assertions mirror private structure, call order, mocks or every getter with no distinct risk. |
| Integration / public CLI | Real code must preserve state, schemas, artifacts or consumer behavior across a boundary. This fits our failure-log and status cases. | Only fake return values are verified, or a fake replaces the actual behavior being claimed as proved. |
| E2E / browser / binary | Packaging, navigation, browser lifecycle or cross-component wiring cannot be shown by a smaller check. | Repeats every pure-rule variation through expensive setup or verifies only “did not crash.” Uncontrolled live services obscure the intended failure. |
| Golden / snapshot | Expected data is sourced from an approved contract or representative real capture, and assertions preserve the consequential content. Record provenance and review changes. | Current output becomes its own expected output, blanket regeneration hides regressions, incidental formatting dominates. Existing standing design requires positive outside recordings to be re-recorded, never hand-patched. |
| Property / fault injection | A justified invariant should hold across reachable input/state variation, including security, data loss or concurrency. | An invariant inferred from candidate code is assumed correct, generators never reach the risky state, or both halves of a round trip share the same bug. |

Signals to shortlist a test for review are not sufficient deletion rules: never failed, flaky, slow, unchanged-line coverage, low mutation score or historical co-failure. Never-failed tests may protect stable contracts. Flakes may reveal real races. Line coverage establishes execution, not a valid expectation. Equivalent or irrelevant mutations inflate work. Running fewer tests is a separate decision from retaining fewer tests.

## Complete proposed operator round

This round fixes the test criterion before agents derive tests from it, then chooses how to remove bloat without erasing useful protection. Our own TMPDIR assertion was invalid, while small CLI and browser regressions caught independently established defects.

### 1 · What must a criterion prove before it can require a test?

Today a named scenario still blocks under `skills/check-issue/SKILL.md:55`, even if the requirement itself is weak. The test scope rules cannot fix that after `skills/plan-issue/SKILL.md:65` locks acceptance scope. We need a bar at the chart/brief stage and a route to challenge a bad locked criterion before implementation proceeds.

Research: operator · round2-intake.md, read 2026-10-03 · you asked to fix the criterion itself. Practitioner · [Stack, 2026-09-23](https://stack72.dev/your-agent-written-tests-arent-real-tests/) · independently owned expectations matter more than a green implementation/test pair. Better-than-training · check:55 and plan:65, read 2026-10-03 · the bar must apply before criterion locking.

- **1a (recommended)** Require a named consumer outcome or justified invariant, its realistic path/consequence, and the source of its expected result. Plans select minimum sufficient proof and raise deficient locked criteria to the chart/brief owner for an explicit correction. This closes the upstream route for vanity tests without letting agents redefine success.
- **1b** Keep every written criterion binding and only limit extra reviewer cases. This preserves current ownership but allows invented test requirements to keep blocking.
- **1c** Let the implementing or reviewing agent rewrite deficient criteria while repairing. This reduces handoffs but allows the same loop to change both the product and its success condition.

Pitfalls: a criterion copied from code is not independent just because it was written first. Requiring a production incident would also exclude legitimate security and data-loss prevention. The existing realistic-source rule accepts traced reachable behavior without a production incident.

### 2 · Should we ban unit tests or choose proof by the behavior it catches?

Our useful CLI tests exercise real state and commands. The capture defects require Chromium. Changing framework or filename alone does not change what they prove. A unit ban would reopen `issues/chart/realistic-fix-bar/forks/test-bar.md:47`.

Research: operator · Wu's img-wu.png, date unverified, read 2026-10-03 · favors E2E, integration and real-data goldens. Practitioner · [Beck, 2025-11-10](https://newsletter.kentbeck.com/p/composable-tests) and [Wickström/TigerBeetle, 2025-02-13](https://tigerbeetle.com/blog/2025-02-13-a-descent-into-the-vortex/) · focused lower-level checks can complement wiring/system checks. My recommendation disagrees with Wu's exclusive list because his material supplies no comparative results and these cases preserve useful distinct coverage.

- **2a (recommended)** Prefer the smallest real consumer-boundary proof for application behavior. Keep focused units or properties for consequential pure rules when they add cheaper detection or diagnosis. Require E2E where smaller checks miss browser/runtime/wiring behavior. This keeps useful protection and cuts per-function test inflation.
- **2b** Ban new units and replace existing units with integration, E2E or goldens. This adopts the stronger screenshot position but needs explicit reopening of the lock and may multiply execution/setup costs without strengthening expectations.

Pitfalls: “nothing mocked” confuses mocking the target with fault injection at an external boundary. An E2E test with a self-generated expected result can provide the same false confidence as a unit test.

### 3 · What evidence should let us delete an existing test?

The TMPDIR repair removed one false assertion and preserved isolation checks. Beck's pruning preserves distinct coverage and diagnosis. Cost data can also justify running a valid test less often, which is not the same as deletion.

Research: operator · dwlz's supplied deletion image, read 2026-10-03 · reports a large deletion but no measured outcome. Practitioner · [Beck, 2025-11-10](https://newsletter.kentbeck.com/p/composable-tests) and [Chromium engineers, 2026-02-18](https://groups.google.com/a/chromium.org/g/chromium-dev/c/mI_FaAL4DeM/m/xlSl7brtAQAJ) · prune demonstrable redundancy and check remaining protection collectively. Better-than-training · commit 2dd1106 and proof-order/report:3,8 · one invalid assertion blocked a real seat.

- **3a (recommended)** Delete false or obsolete expectations and demonstrably redundant tests, naming the reason and remaining protection. Preserve meaningful regressions. Assess a batch as a batch. Use known-bug proof when material replacement equivalence is uncertain. This removes bloat by lost or retained behavior rather than test count.
- **3b** Remove tests based on category, never-failed history, coverage overlap or cost thresholds. This is faster but those signals do not establish that the retained suite catches the same failures.
- **3c** Keep valid tests indefinitely and only change scheduling. This limits deletion risk but leaves duplicate maintenance and agent editing costs.

Pitfalls: retaining B makes A individually redundant, and retaining A makes B individually redundant. Deleting both loses coverage. Expensive but unique protection belongs in the execution-scope fork, not in a deletion pile.

### 4 · How should an agent prove that a new test detects the intended failure?

A realistic scenario still needs an assertion capable of detecting its failure. The existing bug-fix rule already asks for before/after proof. Tests of new invariants may instead need a bounded deliberate violation, with the expectation held constant.

Research: practitioner · [Echlin, 2026-08-11](https://www.testmanagement.com/blog/2026/08/ai-written-tests-evidence/) and [Padhye/Antithesis, 2026-09-25](https://antithesis.com/blog/2026/mutation-testing/) · known-broken behavior and meaningful mutations test detection. Better-than-training · implement:57 and failure-log/review-B:48, read 2026-10-03 · existing real-bug fail-first proof works here.

- **4a (recommended)** Keep fail-before/pass-after evidence for real fixes. For new behavior, use a separately justified expectation and show which meaningful failure the selected proof detects. Use a bounded mutation or known-bad case when detection is uncertain, without a universal mutation-score quota. This checks the detector without making every small task a testing research project.
- **4b** Require mutation testing and a fixed score for every changed test or leaf. This standardizes a number but adds equivalent-mutant work and can encourage useless assertions.
- **4c** Accept a green test plus a written scenario as sufficient. This costs less but repeats the self-confirmation seen in the old readiness expectation.

Pitfalls: a red run caused by missing setup or an unrelated crash does not establish detection of the intended defect. A mutation must violate an independently justified property. Do not mutate expectations until the candidate implementation becomes correct by definition.
