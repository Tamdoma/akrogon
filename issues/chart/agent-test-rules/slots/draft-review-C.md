## test-change-check

- C1. "New tests need no citation" and "any edit to an old test file needs a line" will both be in the skills, and they contradict for the common case. test-change-check brief.md:8 requires a trailer when a seat adds a case to an existing test file. test-rules brief.md:7 and design.md:40 say "New tests need no citation", used "the same in every skill". `skills/implement-issue/brief-template.md:13` tells workers to "extend existing tests before adding files". A seat that follows all three adds a case to an existing file with no trailer and is refused. It also makes a new file the path with no friction, which grows test count against the operator's goal. Fix in the drafts: rule 2 wording says "a new test file needs no citation, a new case in an existing file takes a line saying nothing existing changed".
- C2. How a refused seat adds the trailer is not stated, and the two statements in the brief disagree. brief.md:8 accepts a trailer on any commit in `<target>..HEAD`. brief.md:12 says the trailer goes on "the commit that changes it". brief.md:11 says B adds it "to its own merge-time commit", but at merge the change usually sits inside a rebased commit after conflict resolution (`skills/merge-issue/SKILL.md:41`), so there may be no merge-time commit. The implementer must guess between amending (rewrites the reviewed head) and a new commit. State it: a later commit carrying the trailer satisfies the check, and it may be empty.
- C3. The literal interface in design.md:32 loses trailers in two real cases. I ran it on git 2.56.0 in a scratch repo. (a) A `Test-Change:` line that is not in the last paragraph of the message is not returned. (b) A value wrapped onto a continuation line comes back as two lines unless the format adds `unfold`. Both produce a refusal that looks wrong to the seat. Change the interface to `%(trailers:key=Test-Change,valueonly,unfold)` and have the refusal text say the line must be in the final trailer block. The key matched case-insensitively (`test-change:` was returned), which is fine. This call is also the "one real call" `skills/chart-issues/SKILL.md:53` asks for on a CLI command a brief names, and readiness.yaml has `proofs: []`.
- C4. Rollout for leaves already in flight is missing. framework has 11 open leaves (`find framework/issues/open -name state.yaml`). Any of them that already changed an old test file is refused at its next move once this merges, with no trailer in its history and no instruction in its already-loaded skill text. 63% of framework's tracked files match the rule (round5-C.md F3), so this is likely, not a corner case. The brief needs one sentence on it. With C2 settled, the refusal message itself can carry the full instruction, which keeps it automatic.
- C5. brief.md:9 puts the check on "every move that runs today's `requireNoIssueFiles` guard". That includes the operator's recovery move out of `failed`, because `src/phase.ts:224` runs for any non-`failed` destination and `:191-194` only blocks seats. So an operator recovery is refused until someone adds trailers. Say whether that is intended. Either answer is buildable, but the criteria do not cover it.
- C6. Path matching case is not stated (brief.md:6). My round 5 measurement used a case-insensitive match. I found no upper-case variant (`Tests/`, `Fixtures/`, `Specs/`, `E2E/`) in framework, pi-extensions, lens, Himne, blepsis or clinique-la-roya, so exact case works today. State one or the other so the plan does not choose.
- C7. Two leaves add the same check.review rule. test-change-check brief.md:12 and criterion 4 have B "list the `Test-Change:` trailers ... and judge each one". test-rules brief.md:7 and criterion 2 have B judge "each changed existing expectation against the source it cites". Both land in the same check.review paragraph of `skills/check-issue/SKILL.md` from parallel leaves, and "keep both sentences" (design.md:37) leaves one rule stated twice. Give the judging sentence to test-rules and only the "list the trailers" clause to test-change-check.
