## 2. Proposed split

- **D1. Peer answer collection (#91) is one independent chart in akrogon.** Outcome: a running peer is not declared failed from an idle display, while a genuinely ended unanswered turn is still detected. It has no dependency on storage work.
- **D2. Compact complete check evidence (#92) is a separate outcome.** The akrogon chart owns future evidence format, supported readers and publication. A framework migration, if selected, belongs to that destination's own chart/leaf contract because it changes consumer records. Migration depends on the chosen format and compatible reader landing. The live inventory and legacy migration need not wait for #93 research.
- **D3. Reclaim owned worktrees (#93) is another independent akrogon chart.** Verify recovery and worker release may be separate leaves under this outcome once the ownership policy is settled. File overlap with verify/run-check does not make #92 a prerequisite. Evidence must already be durable before disposal, a contract already intended by current verify. Unknown loose command-log folders require an explicit scope choice rather than automatic inclusion in worktree deletion.

All three concern lifecycle behavior but share no single observable success condition. Do not combine them into a general cleanup refactor. Relative speed: #92's writer/reader contract is concrete; #93 needs ownership decisions; #91's accurate agy terminal signal is still research-dependent.

## 3. Material forks per chart

### Peer collection

**Q1. What proves that a peer ended without an answer?**

- **O1. Use a proven terminal signal tied to the prompted session/turn. Pick, conditional on proof.** Preserve the current guarded prompt, foreground bounded waits, blocked/error handling and atomic answer publication. Use the harness's authoritative turn completion only where its meaning has been established. Cost: agy integration research and real lifecycle fixtures. Risk over time: private session formats or enums change; an adapter can mistake a tool/subagent completion for parent completion. Remove that risk through a documented event if available and versioned boundary evidence, not a guessed last-row rule. Unknown or unreadable state must not become “ended.” F1-F5 support the need, not an already selected agy mechanism.
- **O2. Treat the answer file as the only completion signal and keep waiting through idle.** Simple and avoids false idle failures, but a peer that exits or finishes without writing strands A indefinitely across renewed budgets. It removes the existing failure signal. This is a material change to `issues/chart/door-turn-and-stale-tab/forks/peer-turn.md:20-24`, not a harmless implementation detail. Do not pick without accepting that cost explicitly.
- **O3. Increase the grace period.** Cheap, but any longer silent task reproduces the same defect and real failures take longer to surface. Reject as the final mechanism.

An upstream Herdr fix is an implementation destination option if it can expose the authoritative signal. It introduces a dependency on that delivered capability and requires a separate Herdr contract. Do not assume it exists because current agent list has a session ID.

### Evidence size

**Q2. What is the smallest independently readable unit of saved evidence?**

- **O4. One losslessly compressed artifact per completed command, with reader support and a migration path. Pick.** Keeps current run identity and references close to the existing shape. Prefer a standard supported codec after a corpus measurement, not a hard requirement for zstd-19 based on the tar result. Cost: update `run-check`, `flaky`, tests, references and retrieval instructions. Risks: missed legacy evidence, unreadable old links, or deletion before compression completes. Remove through atomic publication, verified byte equality for migration and a single format-aware read boundary. F6-F9.
- **O5. One archive per closed owner.** Better cross-file compression is possible and it covers arbitrary seat-named logs. Cost: extraction/member addressing and changed references; active leaves still grow until closure. Rewriting a large archive later can add large Git objects. It also couples closure to archive publication. Consider only if measured per-command size misses the accepted target.
- **O6. Store evidence outside Git with references in the repo.** Can reduce future clone growth, but adds storage identity, retention, access and availability requirements. A local-only cache is not complete shared evidence. Reject as the default without a requirement for a history-size bound that in-repo compression cannot meet.

**Q3. Does delivery include existing evidence, and which size are we promising?**

- **O7. Future writer plus lossless forward migration of current tracked logs, including legacy names, with a measured evidence-size target. Pick.** Otherwise the observed 945 MiB remains. Cost: a framework destination action after reader support, all-file verification, and handling existing Markdown/JSONL references. Old commits remain unchanged and preserve historical paths. This does not promise a 200 MB installed checkout. F8-F10.
- **O8. Future logs only.** Smaller change, but explicitly leaves the reported backlog unresolved. Accept only if the operator narrows the request.
- **O9. Rewrite history as well.** Can remove old blobs from reachable history after coordinated cleanup, but changes commit identities and affects clones, worktrees and recorded SHAs. This is a separate destructive operation requiring explicit scope and its own proof, not an implicit part of compression. Current measurements do not justify promising the desired whole-checkout size even then.

### Worktree reclamation

**Q4. What authorizes deletion of a detached checkout whose old commits are no longer on a branch?**

- **O10. Dispose of positively owned temporary checkouts using their recorded lifecycle, and preserve unknown work. Pick.** For verify, bind the record to the exact managed path and expected HEAD and prove the run has ended or its owner died. Its existing normal path already uses force removal, so decide whether recovery applies that same disposable-content contract. For workers, record/establish accepted or deliberately superseded output before discarding the detached source. Cost: a reliable worker ownership/release boundary instead of deriving authority only from `<slug>-u<N>`. Risk: stale ownership permits deletion of reused/user-edited paths. Prevent with identity/expected-head checks and no automatic adoption of unknown folders. F11-F16.
- **O11. Replace ancestry with patch equivalence.** Narrowly fixes the ten verified old patches, but leaves workers changed by repair forever, and normalized patch equivalence is not a complete ownership or uncommitted-content check. Cost: additional Git comparison and ambiguous cases. Reject as the general solution; useful evidence for a reviewed legacy cleanup.
- **O12. Force-remove every `<slug>-u<N>` and `verify-*` after merge.** Small code, but names and a merged owner do not prove that someone has not added unaccepted work. It overturns current dirty/unreachable safeguards and can discard conflict recovery data. Reject blanket deletion.

**Q5. When is a checkout released, and what happens to ambiguous leftovers?**

- **O13. Normal owner removes it at completion, recovery repeats that disposal after the owner is dead; merged leaf cleanup runs after the completion seat releases it. Pick.** Matches existing verify finally and worker post-pick instruction, and preserves merge-seat broadcast/read access. Recovery is for interruptions, not the first cleanup attempt. Unknown directories remain reported with a concrete owner/action. Cost: connect durable ownership to recovery and make reporting useful without an open leaf. Main worktree lifecycle remains bounded by the existing completion flow (`skills/merge-issue/SKILL.md:79-83`, `next.ts:1430-1448`).
- **O14. Remove only on a later manual `next` sweep.** Simpler recovery scheduling, but disk use remains until someone acts and ordinary completion leaks by design. Does not meet “right after” unless the operator narrows it.
- **O15. Extend the same deletion policy to loose `*-cmdlogs` directories.** Could cover the ninth item, but the current source has no recorded owner for those names. ## 4. Practitioner questions and lifetime pitfalls

- **R1. “Can a completed child look like a completed peer?”** F4 shows numeric step status is insufficient. - **R2. “Can A read a partially written answer?”** Current success is nonzero file size (F2). Require temporary write then rename in all peer brief publication paths. Do not treat a heading written at task start as a finished answer.
- **R3. “Will old evidence still answer a debugging question?”** `flaky` is a real reader, and old reviews contain relative paths (F7-F8). Verify recovery of each migrated byte sequence and lookup through existing references after open-to-closed moves. A compressed file's existence alone is not proof.
- **R4. “Will compression failure destroy the only log?”** The current run root is unconditionally deleted in finally (`run-check.ts:220-221`). Publish durable evidence before releasing scratch and make failed publication retain recoverable owned evidence with an explicit failure. Do not preserve a green-looking run after losing its required evidence. This is a contract decision, not permission for an unrelated fallback.
- **R5. “Are we measuring checkout bytes, installed dependencies, or Git history?”** F10 proves these differ materially. Set the accepted metric and measure the same population before/after. Do not confuse tar compression ratio with repository-pack savings.
- **R6. “Could cleanup delete accepted work's only source, or unaccepted work?”** F13 distinguishes ordinary accepted workers from conflicting picks. Establish acceptance/disposal before deletion and test interrupted transitions. Preserve unknown or changed identities. Merely retaining all orphan worktrees forever also fails the request.
- **R7. “Can a live command still use the directory?”** Verify records contain PID/boot ownership, worker protection is currently based on leaf state, and panes need not sit inside worker cwd (`reconcile.ts:375-389`). Prove liveness for the owned execution rather than infer it from an empty pane inventory. Do not expand this into a general process-cleanup chart.
- **R8. “What if cleanup fails after a run ended?”** Separate terminal execution evidence from cleanup success and make retry idempotent. A remove error must remain visible and must not turn a passed test into a claim that cleanup succeeded. Exercise failure between record persistence and worktree removal (F12).
- **R9. “Do the old charts forbid the proposed change?”** Keep guarded prompts/no automatic re-prompt and foreground budget renewal (`peer-wait/forks/wait-mechanism.md:29-38`; `door-turn-and-stale-tab/forks/peer-turn.md:20-24`). ## 6. Fog

- **G1. Agy terminal authority remains unresolved.** We know where the incident session lives and why the existing code misclassifies idle. We do not yet know a stable event or schema that distinguishes the parent waiting for child work from a genuinely ended turn. This is the main research blocker for Q1/O1. No need to invent an enum parser at handoff.
- **G2. Why the six verify attempts bypassed ordinary cleanup is not established.** Their records show no completed execution. The exact interruption, persistence error or removal error needs the incident runner evidence. The proven recovery defect can be scoped independently, but claiming to fix all future leftovers needs this cause checked.
- **G3. Historical worker acceptance evidence is incomplete.** The directories are deleted, and the brief says their patches were later repaired. An implementation cannot infer a universal safe-delete rule from that report. Establish what existing artifacts prove acceptance/supersession, then choose the smallest persistent ownership boundary if they are insufficient.
- **G4. The savings target and legacy retrieval contract are not yet numeric/explicit.** Whole-checkout hundreds of MB conflicts with observed dependency and Git size. Decide evidence bytes versus checkout/history, whether every historical path must remain directly readable, and whether the migration includes command logs outside registered worktrees. These choices affect format and destination, not just implementation detail.

The central correction is that these are three separate outcomes: trustworthy peer completion, compact durable evidence, and safe disposal of owned temporary checkouts. The most consequential factual correction is that the named verify leftovers have unfinished records even though normal verify already removes its checkout.
