## Q1 pick, reason and cost

**No option meets the complete strict bar.** New judgment lessons enter the active list, but mechanical-only application gives those that never become guards no exit. Even perfect automatic retirement of guarded lessons cannot guarantee a bounded total stock. Backlog coverage verification and cross-repository edits also require work. No new component does not mean no additional cost. Net savings from avoided rereading or defects are plausible, not measured.

**Least-cost option:** close the checkable-lesson loop through existing charting and guard leaves. The writing seat files linked intake as taken. When charting already reads the active list, it connects relevant lessons to the proposed guard's criteria and retirement edits. The guard leaf verifies coverage and removes its same-repository line with dated history evidence in its existing diff, as taken. If current inspected evidence already proves coverage, charting can own a scoped retirement edit without building a redundant guard. No separate sweep, pass, command, state or file format. Cost: targeted verification, bookkeeping and occasionally a retirement-only outcome. Unrelated backlog and inactive consumer repos receive no guaranteed service. This is a conditional balancing loop, not a complete automatic drain.

- F2: **Pending intake** is a second stock. Taken write-time filing moves information into tracked seeds without removing active lessons. - F3: **Balancing loop:** relevant lesson -> investigated guard contract -> verified delivered protection -> active-line retirement and fewer recurrences. The guard leaf closes the line-removal part locally. Existing guarded lessons need recognition during work already underway. Its strength depends on relevant work being selected and completed, not the number of seed filings.
- F4: **Possible reinforcing loops, not measured here:** more active lines -> more reading/triage -> less capacity for guard delivery -> more unresolved lines. Recurring failures -> repairs and more lessons -> more queued work -> longer prevention delay. Dedupe and removing proven stale lines reduce amplification, but cannot create delivery capacity.
- F5: **Delays and limits:** historical lessons missed by write-time filing remain undiscovered unless existing charting considers them. Cross-repo guard delivery and consumer installation introduce another delay. A guard in Akrogon's source may not run in framework yet. Two repositories cannot retire a consumer line in the same Git diff as a shared guard. Judgment lessons remain permanent active inflow under the current retirement rule.

It needs an explicit operator decision and evidence that planning still finds relevant observations. It does not fix existing backlog or prove zero cost/quality loss.

## Pitfalls and their removal

- R1: Optimizing line count hides unresolved failure mechanisms. Remove by retaining historical evidence and retiring only verified mechanical coverage under the taken rule.
- R2: Repeated promotions amplify intake while delivery lags. Remove duplicate filing through the taken destination search and existing history links. Avoid creating another report solely because the lesson remains active.
- R3: Source delivery is mistaken for consumer protection. Require the actual consuming path and applicable installed guard revision before consumer retirement. Choose an existing consumer owner for the edit. This costs coordination and cannot be disguised as the shared leaf's same diff.
- R4: Opportunistic inspection is sold as complete coverage. State its limit: lessons unrelated to current work can remain indefinitely. Exhaustive backlog service requires explicitly permitted work.

## Questions the fork does not resolve

- Q4: Which existing consumer activity owns cross-repo retirement once installed coverage is proven? If there is no future consumer activity, may the line remain active, or is separately scoped work allowed?
