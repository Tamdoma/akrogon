# Leaf review C, fewer-repeat-calls draft, 2026-10-26

Disagreements only.

- F1. The fake-proc surface cannot deliver criterion 4 as scoped. The design names only `shellPid`, but `expectedSlice` in the same module also calls `createHash`, and `tests/fake-herdr.ts` imports `expectedSlice` from `tests/fake-proc.ts`. Converting `shellPid` alone leaves the top-level `node:crypto` import in the bundle, so the 3.5 ms load stays. Converting both widens the identity surface to slice names, which exist as an independent copy in product code (`leafSlice` in `src/scope.ts`, also `createHash`). The pid half of the stated proof is also circular: tests that expect fake shell pids import `shellPid` from `tests/fake-proc.ts` itself (tests/green-merge.test.ts, tests/seat-containment.test.ts), so fake and expectation move together if the digest changed; only the slice name is cross-checked against product code. "Same pid as on the base" needs a recorded base pid comparison, not the existing tests. (practitioner: C code read of `tests/fake-proc.ts`, `tests/fake-herdr.ts`, `src/scope.ts`, 2026-10-26)
- F2. The proof route for criteria 1 and 2 and the Reuse 4a count report does not exist as described. The fake herdr `.calls` log and `busctl.calls` live inside each fixture home, which `f.clean()` in `tests/helpers.ts` deletes at the end of every test. Existing tests read those logs only inside the test body before cleanup, and no existing test counts `process-info` calls per boxing (the nearest assertion, in tests/peer-restart.test.ts, only checks that some process-info call happened). So "proven by existing scenarios reading the existing logs, no shim written" is wrong: after a normal run there are no logs left to count, and counting inside tests means new call-count assertions, which Reuse 4a rejects. A log-preservation or in-test counting decision is missing and must be made before planning. (practitioner: C code read of `tests/helpers.ts`, `tests/fake-herdr.ts`, `tests/fake-busctl.ts`, `tests/peer-restart.test.ts`, 2026-10-26)
- F3. Missing consumer of the `inOwnScope` change. The design threads the shell pid through `box`, `adoptShell` and the post-adoption checks only. `src/next.ts` also calls `inOwnScope` for each recorded pane in the dispatch step before boxing, and closes the pane when it reports outside. If `inOwnScope` takes the pid as an input, that caller must read and pass it too, or the function must split. Neither appears in owned surfaces or consumers. (practitioner: C code read of `src/next.ts` dispatch and `src/scope.ts`, 2026-10-26)
- F4. Two binding decisions have no home. Proof 2a (three at once, recorded only) appears in no done-criterion, so all six criteria can pass without it ever running. Reuse 2a's branch-tip clause (remove a second branch-tip read inside one decision) has no owned surface and no open-for-plan item; the open items cover `panes`/`tabs`/`workspaces` repeats and root identity only, so a plan that finds those reads in other modules is outside the leaf as drawn. (practitioner: C read of the draft brief and design, 2026-10-26)
- F5. Criterion 5's machinery is misstated as existing. Two copies started together, each in its own checkout, alternating head and base with start load recorded and durations extracted, is not a command the repo has. A base checkout is a fresh worktree with no `node_modules`, where bun builds fail until `bun install` runs (hit in my scratch worktree today). The design says the proof "builds no runner" and in the same breath leaves "the exact proof command" open for the plan. That open item is the runner. It can be a throwaway script, but the plan must budget writing it instead of treating the proof as an existing command. (better-than-training: C scratch worktree build failure, 2026-10-26; practitioner: C read of the draft design, 2026-10-26)

Bottom line: F2 blocks planning. Criteria 1 and 2 are call-count claims, Reuse 4a forbids a call-count test, and the existing logs the design points at are deleted by fixture cleanup. Decide how counts survive a run, or the leaf has no way to show its two main criteria.
