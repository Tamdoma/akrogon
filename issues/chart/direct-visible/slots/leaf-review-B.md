# Leaf review: direct-leaf, slot B

Read the draft as its implementer on 2026-11-25 against akrogon main 085f2f88 (src, skills, shapes.md `## Leaf files` and `## Preflight and validation`, standing-design.md, the Taken decisions, shell-sweep's brief). Defects only.

## D1 — `src/usage.ts` is missing from owned surfaces; the verbs' flags cannot parse, so criteria 1, 2 and 9 cannot be met within ownership

Both new verbs take flags: `--reviewer` (criteria 1–2) and `--chart` (criterion 9). Verb flag parsing is closed over `VERB_OPTIONS` in `src/usage.ts` (read 2026-11-25): `parseArgs` in `src/akrogon.ts` receives `options: optionsFor(verb)`, which is `VERB_OPTIONS[verb] ?? {}` — a verb absent from the record parses no flags at all, and `src/akrogon.ts` exits with `unknown flag` for any flag it does not know. The leaf architecture lists `src/akrogon.ts (two verbs)` but not `src/usage.ts`. Every done-criterion proving the verbs "through the real CLI" fails at parse. One line in owned surfaces fixes it.

## D2 — the create verb's refusal set contradicts itself across Taken, design and brief, and one refusal in the design has no home in any criterion

Binding decision 2 (Taken, verbatim): "First run (state has no seat refs): refuses when the owner folder already exists open or closed, a leaf without the door's files, or outside hc". Read literally, "the owner folder already exists open" refuses exactly the precondition every document states — the door writes the four files under `issues/open/<owner>/<slug>/` and then runs the verb — so the verb can never succeed. The intended reading exists in criterion 1 ("when an owner of that name exists under `issues/closed`, when any of the four files is missing"), but the binding decision as written contradicts it, and the implementer cannot tell which refusals are binding. The design's interface then adds a third set: "refuses a state without `direct`" — i.e. a slug collision with a lifecycle leaf — which appears in neither the Taken text nor any done-criterion, so the audit question "which behavior is proven" has no answer for it. One consistent refusal list, written once and mirrored in the criterion, closes this; the pieces are all present, they just disagree.

## D3 — `direct-drop` is unconstrained in `merge` and strands the batch machinery, including the case where the leaf's commits still land

Criterion 9 and binding decision 3 refuse drop only for a non-direct or `merged` leaf. A direct leaf in `merge` routinely holds `state.batch` — either queueing with `batch.in` set, or inside a running land unit whose unit directory is `<worktree>/.akrogon-land`. The verb then removes the worktree and branch and moves the owner folder out of inventory. Consequences, each reachable in code read 2026-11-25: the land run's follow-up stages (`attemptLand`'s stage loop, `turn.ts` `batchEnd`/`resettle`) resolve the leaf through `leaves()` in `issues/open` — the folder is gone — so the batch dies mid-flight with `StaleLandError` or `no batch for <slug>`; and because the candidate push can already have happened before the drop, the leaf's commits can reach the remote default branch while the operator holds a `Held` chart entry believing the attempt was abandoned, with no record anywhere reconciling the two. Lifecycle has no analogous hole because `stop` keeps the owner folder in inventory, so the batch machinery keeps resolving the leaf, and removal happens only at `merged` through `commandMerged`. One more refusal — a direct leaf in `merge` with a recorded batch, or in `merge` at all — closes it at zero machinery cost; alternatively the decision names the teardown order. As written the criterion's own proof scenario (drop in `check.review`) never exercises the hole, so it would ship silently.
