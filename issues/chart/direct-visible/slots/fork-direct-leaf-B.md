# Fork notes: direct-leaf, slot B

Written blind. Date read for all repository evidence: 2026-11-25.

## Q1. What record carries a direct-route attempt?

### Pick: Q1a — a real leaf under `issues/open/<owner>/<slug>/` whose state.yaml carries one optional door-run field

**Reason.** The lock demands leaf-exact output: phase, seats, runs, merge queue, broadcast. Every one of those renderings is derived from one source: the strict-schema `state.yaml` that `repoInventory`/`readState` parse (`src/state.ts`), read by `src/status.ts` rows, `src/run-check.ts:leafTarget` attribution, `src/timing` log history, `src/turn.ts:mergeQueue` and `src/land.ts`. Signpost 1a says fix the mechanism that fails. The failing mechanism is not status rendering; it is that direct work writes no leaf record (`docs/use/quick-fix.md` "No leaf files are written"). Q1a repairs exactly that mechanism, so status, run-check, timings, log, land and broadcast consume it with zero parallel readers. Signpost 3a says extend existing records with the smallest field, no new record kinds: one optional marker field on the existing strict object satisfies it, and signpost 6a holds because the field is optional — every existing state.yaml parses unchanged (`z.strictObject` with `optional()` additions).

**Cost.** The leaf record invites the whole machine to act on its seats, tab and slice. The one field must buy exclusion from all of it, and that exclusion is the fork's entire implementation risk (grounding below). Second cost: lifecycle fidelity forces `check.review`'s two-slot rule (`src/routing.ts` slots `['A','B']` at initial review), so the door must write a genuine blind `review-A.md` on its own implementation — a review fidelity the direct route does not have today. Third: the door is one terminal, so `observeBusy`-style busy recording will read `working` while the door works on any chart, overstating the leaf's busy time — acceptable because busy display is informational only.

**Grounding — the command paths that start, prompt, rename, close, kill or count a seat or tab for a leaf, and what the one field must stop at each:**

- **dispatch** (`src/next.ts:dispatchLeaf`/`dispatchSlot`, called from every `next`/`phase` pass and `phaseWake`): for a seat-required phase it calls `dispatchSlot` per required slot, which ends the recorded terminal (`end(place.session, ...)`) and calls `startSeat` when the seat is missing, finished or ended silently, sends the phase prompt when idle, and charges `attempts`/`lost` toward `failed`. For a door leaf every one of those would fire at the door's and reviewer's real terminals. **The field must stop: all of dispatchSlot — start, end, prompt, attempt accounting.** What may still run: the `observeBusy` read block in `dispatchLeaf`, since busy display is wanted. Note `observeBusy` consumes `leafSeats()`, which matches terminals by labels `akrogon.repo`/`akrogon.leaf`/`akrogon.seat` (`src/reconcile.ts:leafSeats`) — borrowed door terminals carry none, so seat matching must become address-based from `state.seat[slot].address` for door leaves (labeling the borrowed terminals instead is wrong: labels flip `activeCount`, below).
- **allocate** (`src/next.ts:allocate`): mints the leaf tab `tab: leafTab(repo.name, slug)` and runs the capacity check. The broadcast path calls allocate for every merged leaf with a broadcast. **The field must stop: tab minting — the record never carries `state.tab` — and any capacity charge for seats that are never started.** Once tab is never present, `renameTabs` (next.ts), `renameTab`/`announceFailed` (phase.ts), `closeMergedTab`/`closeLeaf`/`closeTabOf` (reconcile.ts), `tabLive`-gated slice keeps and `unnamedTabs` (status.ts) are all inert by their own existing conditions — the field must keep it that way, structurally, not by luck: nobody may ever write the door's tab id into `state.tab`, or the close paths (`closeLeaf` kills the seat terminals it finds and closes the tab) kill the door.
- **reconcile** (`src/reconcile.ts`): `sliceKeepReason` stops a finished leaf's slice when its tab is gone; `endSeats`/`closeMergedTab`/`endFinishedSeats` kill whatever terminals `leafSeats` finds for the leaf; `mergedWorktree`/`removeMergedWorktree` removes the finished leaf's worktree and branch. Worktree/branch/slice removal is wanted exactly as-is (the direct route's manual steps 8 vanish). **The field must stop: every `end()`/close of a borrowed terminal — `endSeats`, `closeLeaf`, `closeMergedTab`, `endFinishedSeats` — while worktree removal, branch deletion and slice stop run unchanged.** This is the catastrophic pitfall from the merged map and it is fully reachable: `closeMergedTab` runs at `landedWake` for every merged leaf with no broadcast pending.
- **stop** (`src/stop.ts:stopLeaf`): `endSeats` then slice stop then run cancellation. Stopping a door leaf is a coherent operator act — it halts the machine's part (runs, merge eligibility) and removes it from `mergeQueue` — **but the field must stop the `endSeats` kill of the door and reviewer.** Stopped door leaves naturally idle because the door never gets dispatched anyway.
- **renameTabs** (`src/next.ts`) and **status unnamedTabs** (`src/status.ts`): both key off `state.tab`. With tab never recorded they are no-ops; the field's stop is the same no-tab rule as allocate. A row detail like `tab unnamed` can never appear — correct, because the operator's question is which terminals are the seats, and that is the seat record, not a tab.
- **activeCount** (`src/next.ts`): counts unfinished leaves whose `akrogon.leaf` label is live, or by the `seated` fallback (`tab` or `worktree` set). Unlabeled door seats make the live-label count zero; the fallback would still count the leaf once it has a worktree. **The field must stop: counting door leaves toward `max_active` at all** — they start no agents, and charging them capacity double-counts the already-running door. `capRefusal` is consulted inside `allocate` only when no live seat exists, which is always for door leaves; it must not refuse them either.
- **broadcastPass** (`src/next.ts`): the one permitted exception. Today it `allocate`s and `dispatchSlot`s a broadcast-only B seat. For a door leaf **the field must stop allocate and dispatchSlot and replace them with exactly one act: `hc send` (which supports `--if idle`, `src/hc.ts:send`) of the broadcast prompt to the recorded `state.seat.B` terminal while it is idle or done, recording `prompted.B` as the ack.** `prompted.B` is the existing completion predicate (`broadcastPending`, state.ts) so pending/truth display comes for free. Never a start, never a tab.

Two more facts the design inherits: door terminals must not be labeled `akrogon.leaf` (labels flip activeCount and leafSeats matching wholesale), so matching is by recorded address — and since `state.yaml` is chmod 0444 after `saveState`, the door cannot hand-rewrite `state.seat.B` when the reviewer changes; the creation verb needs a seat-update path (Q3a's rewrite requirement, open question OQ1).

### Rejected: Q1b — added lines in CHART.md `## Direct attempt` rendered as a leaf-shaped row

**Reason rejected.** The row is leaf-shaped but not leaf. What status would render: the six leaf columns (LEAF, PHASE, TIME, BLOCKED BY, NOTE, TURN) filled from hand-written prose. What the operator still never sees compared with a leaf row:

- NOTE's machine parts: `busy A/B` from `busy_since`, `A:n B:n` attempts, `fix rounds`, `verdict A:.. B:..`, prompt delivery errors, `land`, `broadcast pending`, `failed <cause>`, `tab unnamed` — every one is command-written into state.yaml (`src/status.ts:note`). Under Q1b the door would hand-write lookalike prose, and prose is unverified: prose drift (the merged map's named pitfall) means the row silently lies, the exact failure mode of issue #153 in a new costume.

A prose row has no unreadable-detection either: a malformed hand edit either breaks status parsing for the whole repo or is leniently misread.
- Runs: attribution "by the holder path" still leaves run records keyed `checkout` (`src/run-check.ts:leafTarget` returns slug `checkout` for `--holder` targets today), indistinguishable across concurrent direct charts and the operator's own checkout runs; fixing that is yet another parallel mechanism.

Cost beyond the missing fidelity: the lock says "exactly like a lifecycle leaf", and this option is defined as an approximation. It cannot satisfy the lock as written; it can only negotiate the lock down.

### Rejected: Q1c — a chart-local machine file `<chart>/direct/state.yaml` with its own reader in status

**Reason rejected.** A new record kind, which signpost 3a forecloses. Every consumer that matters — mergeQueue, dispatch, land, reconcile, run-check attribution, timings, broadcast — reads `state.yaml` through `repoInventory`/`findLeaf` under `issues/open|closed`; a chart-local file is invisible to all of them, so either it stays a display-only replica (inheriting every Q1b defect plus schema drift against the real schema it mimics) or each consumer gains a second read path (a bigger diff than Q1a's marker gates, permanently). It is Q1a with extra steps and none of the reach. The only thing it buys — keeping direct artifacts out of `issues/open` — is not a lock and not an operator requirement.

### Pitfalls and what removes each

- **P1 (catastrophic): a pass kills the door or the reviewer, or closes the door's tab.** Removed by the marker field gating every `end()`/close path (`endSeats`, `closeLeaf`, `closeMergedTab`, `endFinishedSeats`, stopLeaf's endSeats) plus never recording `state.tab`; removal must be a done-criterion proven mechanically: a test leaf in door-run mode driven through merge in the harness's own test rig (signpost 2a — the free boundary is the command's existing tests/ suite) asserting the recorded terminals are still alive and the tab untouched afterwards.
- **P2: double seats — dispatch starts fresh agents on top of the door.** Removed by the same field gating all of dispatchSlot; verified by a test that a door leaf sitting in `implement`/`check.review` across passes spawns zero terminals.
- **P3: phantom tab lifecycle.** Removed by the structural no-tab rule: nothing writes `state.tab` for a door leaf, making rename/close/unnamed paths inert by their own conditions rather than by vigilance.
- **P4: capacity miscount** — borrowed labeled terminals or the worktree fallback charging the door leaf toward `max_active`. Removed by the accounting decision (never counted, since no agent is started) recorded as a binding decision and asserted in the P2 test.
- **P5: locked worktree swept never.** `git worktree add --lock` (direct-route step 1) plus `reconcile`'s unconditional keep of locked rows means the finished leaf's worktree would never be cleaned. Removed by adoption in the creation verb running `git worktree unlock` — the growth-stop handoff already proves the pattern (direct-route continuations unlock before `ensureWorktree` adopts).
- **P6: review-fidelity regress or contract breach.** Initial `check.review` routes to slots A and B (`src/routing.ts`); the door implementing and skipping its own blind A review violates routing, while carving door leaves to B-only review breaks "exactly like a lifecycle leaf". Removed only by an explicit decision — open question OQ2 — not by silence.
- **P7: prose drift across skills/docs.** Removed by Q1a itself: one record kind, direct-guards.ts deleted, direct-route.md reduced to the thin door choreography, and leaf-form skills gaining a small artifact-path rule rather than parallel direct forms.

## Q2. Who lands a direct attempt?

### Pick: Q2a — the command: review-ready moves the leaf to `merge`; the existing merge queue and land run verify, gate, push, close sources, move the owner and record the broadcast

**Reason.** There is exactly one merge machine and it already does everything: `mergeQueue` ordering (`src/turn.ts`), batch build and restack (`src/next.ts:mergeTurn`, `src/batch.ts:buildStack/applyTop`), the land run's verify-gates-push (`src/land.ts:landAttempt` → `verify` → `landGates` → `landPush`), source closing and owner completion (`src/phase.ts:commandMerged`/`completeOwner`/`closeSources`), the broadcast handoff record (`commandMerged` writes `state.broadcast`), merge-attempt receipts (`src/attempts.ts` via appendAttempt) and the repair exits (`repairExit` → `check.repair` with `merge_exit` evidence for B). A second landing mechanism duplicates all of it in prose for one agent to re-enact by hand — the definition of signpost 1a's "fix in the mechanism that fails" being ignored. Worse, two push paths have no shared ordering: a door-pushed direct head invalidates or races every in-flight batch the merge queue holds, a failure mode that cannot exist when there is one queue.

**What the land run needs from a leaf that the direct route does not provide today** (each verified in source):

1. **Leaf identity, phase and batch plumbing**: `landClaim` (src/phase.ts) throws `StaleLandError` unless `findLeaf` returns a leaf in phase `merge` whose `state.batch.attempt` matches; `mergeTurn` builds that batch only for queue-eligible leaves (phase `merge`, `merge_stamp`, no unmerged deps, no readiness gaps) reading `refs/heads/<slug>` and the recorded worktree. Today no leaf exists at all, so nothing of this exists.
2. **Worktree adoption, unlocked**: `mergeHead`/`moveGuards` read `state.worktree`; `ensureWorktree`'s adopt-as-is path (`src/next.ts`) requires the worktree at `worktree_store/<slug>` on branch `slug`, sharing the git common dir — and the direct route creates it `git worktree add --lock`, while `reconcile` keeps locked worktrees unconditionally (`keepLocked`), so the adoption must unlock or the finished leaf's worktree is never swept.
3. **Leaf-scope receipts for the phase gates**: the implement→check.review move requires `requireGreenReceipt(HEAD, 'leaf')` and check.repair→merge re-requires it (`src/phase.ts:transition`); `verify()` picks scope `leaf` only when the caller resolves to a leaf whose phase is not merge (`src/verify.ts:verify` — `caller.phase === undefined` yields merge scope). Today's direct `akrogon verify --holder <chart>/direct` writes a merge-scope receipt keyed to slug `checkout`, so the direct implement/repair forms never produce the receipt the gates demand — the implement form must run plain `akrogon verify` in the worktree exactly like the leaf form.
4. **check.review's two-slot records**: the aggregate move needs `done` covering required slots with verdicts (`src/phase.ts:transition` computes the destination only when every required slot is done); today the direct route collects exactly one verdict — B's out file (`check-issue` `## Standalone review`: B "writes only the file named by out=", "runs no akrogon phase") — and no A review exists at all.
5. **Artifact locations**: the land path itself reads no prose, but the machinery around it does — status deep-links `<leaf>/plan.md`, run-check publishes under `<leaf>/implementation`, the frozen-citation gate reads `state.frozen` which only a `plan.synthesis`→`implement` transition writes (`frozenRecord`). A direct leaf starting at `implement` carries no frozen record, so that gate silently never runs — a known hole to decide, not to discover in production.

**Cost.** Latency and sharing: the direct attempt queues behind other merges and pays a full merge-suite verify on the batch top, where today's door pushes within minutes of B's ready. And when the merge run reds or conflicts, the leaf ejects to `check.repair` — the repair loop must be staffed, which is the lifecycle semantic the lock asks for anyway (`fix_rounds` already exists in both worlds). A red or conflict no longer lands on the door's judgment alone; the taken-8/main-red cover machinery decides, which is stricter and less convenient.

**What Q2a deletes:** direct-route.md landing steps 5–9 wholesale — rebase/verify/known-red judgment (replaced by `verify --attempt` plus the cover logic in `land.ts`/`verify.ts:uncoveredMainRedUnits`/`taken8Trigger`), push with retry (replaced by `landPush`/`restack`/`keepPlace`), source closing (replaced by `completeOwner`/`closeSources`), worktree/branch removal (replaced by `reconcile`), and `direct-guards.ts` in full — its five checks (`requireClean`, `requireNoIssueFiles`, `requireTestChangeCitations`, `requireNonEmpty`, `requireGreenReceipt(merge)`) are literally `landGates`/`batchGuards`/`moveGuards` in src/phase.ts, function for function. The door keeps only chart bookkeeping: `pack`, the CHART.md marker.

### Rejected: Q2b — the door keeps its landing steps and only records the phase and landing

**Reason rejected.** All the costs of duplication with none of the reach: no queue ordering against lifecycle merges (the race above is permanent), the known-red judgment stays a prose protocol an agent re-enacts (direct-route.md step 3 is one paragraph of judgment rules duplicating `knownRedReceipt`/`uncoveredMainRedUnits`/`taken8Trigger` in words), a failed push or red has no machine exit path — the door improvises — and the broadcast is again a hand-run. The recording it adds is the untrusted-prose kind Q1b suffers from. Its only merit — zero command change — is precisely what signpost 1a forbids choosing when the mechanism itself is what fails.

## Q3. How do the seats and the landing broadcast run without a new tab?

### Pick: Q3a — record A = the door's terminal and B = the reviewer's terminal in `state.seat`; the command observes busy on them and sends the broadcast prompt only to the recorded B while idle or done; the door rewrites B when the reviewer changes

**Reason.** The lock says the leaf's seats are the door's and reviewer's existing terminals — real seats, not display props. `state.seat` already exists for exactly this (`seatRefSchema` session+address, state.ts), `observeBusy` already turns a live terminal's status into `busy_since` rows the status NOTE column renders, and the broadcast completion predicate `broadcastPending` (merged + `state.broadcast` set + `prompted.B` unset) already exists with `prompted.B` as its ack. Q3a is the only option where every piece of truth is command-written: pending state shows in status as `broadcast pending`, a stuck broadcast is diagnosable (`akrogon status <slug>` prints the seat address), and completion is the same ack lifecycle merges use. `hc send`'s `--if idle` option (`src/hc.ts`) is the exact primitive for "only while idle or done", so no new send machinery either. Because the rewrite of `state.seat.B` mutates command-owned state (chmod 0444 after every `saveState`), the creation verb must own a seat-update path — small, and it doubles as the adoption mechanism for OQ5.

**Cost.** The broadcast can stall: if the recorded B terminal is busy, the send waits (by design); if it is gone or finished, nothing ever sends — unlike lifecycle, where broadcastPass starts a fresh B seat. The only remedies are the door rewriting B (possibly to itself, since nothing forbids A and B being the same terminal for this purpose) or operator intervention, and `broadcast pending` in status is the visibility that makes the stall honest. This cost is inherent in the lock's "no new tab" constraint, not in Q3a: Q3b "solves" it only by spending the door's attention forever. Second cost: Q3a is impossible without Q1a's marker gates — the moment a borrowed terminal sits in `state.seat`, every kill/close path in reconcile/stop is armed against it, so this option cannot ship half-way.

### Rejected: Q3b — the door sends the broadcast itself and marks it sent through a command; seats are display-only

**Reason rejected.** Three mechanisms where one exists: a new mark-sent verb (the smallest-field signpost already supplies the ack field — `prompted.B`), a door-side memory of whether it broadcast (the failure mode the issue reporter already suspects today — "the operator believes direct landings are not broadcasting" — because a hand-run step leaves no machine trace), and display-only seat records that go stale with every reviewer change yet never affect anything, making them decoration rather than seats. It also keeps the door in the broadcast critical path forever, while Q3a lets the command deliver even when the door is busy charting elsewhere. The one genuine difference — lifecycle merges broadcast through B (the reviewer speaks about what they reviewed; broadcast-issue's SKILL.md already names the door as sender only because today there is no leaf) — cuts against Q3b: "exactly like a lifecycle leaf" means B sends it.

- **P12: dead-B stall.** B's terminal exits after review; the broadcast never sends. Removed by visibility plus the rewrite path: `broadcast pending` shows in status, and the door rewrites `state.seat.B` (the exchange rules already track the reviewer's current address). A door that itself is gone is the same failure a lifecycle leaf suffers when its seats die — the difference is no auto-start, which the lock itself mandates.
- **P13: prompt content mismatch.** The lifecycle broadcast prompt reads briefs from the `closed=` owner folder, but direct context is the chart brief. Removed inside the Q1a design (OQ3/OQ4): the broadcast prompt for door leaves names the chart context, or the leaf folder carries the brief artifacts so the existing prompt works unmodified — either way it is a decided input, not a new mechanism.
- **P14: busy-observation lying.** The door working on another chart reads `busy` on this leaf's seat A. Not removed — informational only, and arguably true signal: the leaf's seat is occupied elsewhere. Named so nobody "fixes" it with a mechanism.
- **P15: rewrite races.** The door rewriting `state.seat.B` while a broadcast send is in flight. Removed by the command owning the write under the same `.lock` every other state mutation uses (`withLock(resolve(globalHome(), '.lock'))` throughout next.ts) — the rewrite path is a verb, never a hand edit (impossible anyway at 0444).
