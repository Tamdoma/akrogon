# Leaf review: slot D, leaf direct-leaf

Defects only.

- F1. Test file named in criteria. Brief criteria 1, 3 and 8 name `tests/hc-fixture.ts`. Shapes `## Leaf files` and `## Preflight and validation` refuse a done-criterion naming a test file.

- F2. No source identities can reach a direct leaf. The literal verb interface is `akrogon direct <slug> --reviewer <address>`, first run starts with no state file, and neither the verb nor the four door files has a defined place for GitHub sources. The design's consumer list also omits them. `src/phase.ts` `completion` and `completeOwner` derive both the broadcast source list and the `closeSources` set only from owner leaves' `state.sources`, and `src/next.ts` `broadcastPass` renders that list into the broadcast prompt. As written a direct leaf lands with no sources, closes none of the issues it delivered, broadcasts `sources=none`, and never appears as a carrier in `src/timing-report.ts` `flowReport`. Criterion 7 asserts the owner move only, so all criteria pass with the delivered issues left open.

- F3. The create verb's first-run and owner rules contradict each other, and the sibling guard has no criterion. Taken item 2 defines first run as a state with no seat refs and refuses an owner that already exists open or closed. The architecture defines first run as an absent state file. Criterion 1 requires the door's files to already exist under `issues/open/<owner>/<slug>/`, so the open owner necessarily exists, and tests refusal only for a closed owner. An implementer cannot satisfy all three texts. The practical loss is the sibling guard: `src/phase.ts` `ownerScope` makes every leaf under the owner part of one completion, so a direct leaf written into a pre-existing owner cannot complete or broadcast until the siblings merge, and `direct-drop` would move those siblings with the owner.

- F4. The two new verbs cannot be wired inside the owned surfaces. `src/akrogon.ts` parses every verb's flags through `src/usage.ts` `optionsFor` and `VERB_OPTIONS` before dispatch, in strict mode, so `--reviewer` and `--chart` are refused as unknown flags unless `src/usage.ts` changes. That file is not an owned surface. Adding the dispatch cases then breaks `tests/command-reference.test.ts` `checkReference`, which requires every dispatched verb and its exact argument contract in `docs/reference/commands.md` and in that test's contract table. Neither file is owned, and criterion 10 names neither, so the leaf cannot pass `checks` as scoped.

- F5. Deleting direct-guards has consumers the design does not list. `tests/receipt-gates.test.ts` invokes `skills/chart-issues/scripts/direct-guards.ts` in three receipt-gate cases, and `tests/docs-links.test.ts` asserts the direct landing text contains the door's known-red command and red names. The standing-design section deletes only `tests/direct-guards.test.ts` with the script, and criterion 10 then cites the existing docs-links check as proof. That check fails on the Taken text changes unless both test files are owned and updated.

- F6. The edited `check.repair -> merge` refusal has no baseline outside a land exit. `state.merge_exit.top` exists only after a merge exit (`src/phase.ts` `commitMove` sets `merge_exit` only entering `check.repair`, fed by `src/land.ts` `repairExit` and `src/next.ts` `mergeTurnExit`). After an ordinary B `fix` verdict there is no recorded reviewed head in state for `transition` to compare, so an implementation that only compares against the red top lets A move from `check.repair` straight to `merge`, unedited or after editing in `check.repair`, bypassing `check.fix` and B's re-check. Criterion 5 tests only the red-top comparison and never a repair-to-merge move on the ordinary fix route.

- F7. The seed decision's runs have no criterion and no named consumer. The brief's Why names runs recording slug `checkout` as part of the defect, and the seed decision requires status to show the leaf's runs, but no done-criterion runs a check from a direct leaf's worktree. The architecture does not list `src/run-check.ts` `leafTarget` or `src/verify.ts` `verifyCaller`, the functions that turn a recorded worktree into the leaf slug and its `implementation` log target, nor the status run line that prints that slug. The leaf can pass every criterion while its own proof runs still attribute elsewhere through a wrong recorded worktree or holder path in the rewritten skill text.

- F8. Criterion 3's proof cannot reach the guards it claims to prove. In the specified setup the recorded terminals carry no `akrogon.leaf` labels, by decision. `src/reconcile.ts` `leafSeats`, behind `endSeats` and `endFinishedSeats`, only ever returns terminals carrying those labels, and `src/next.ts` `activeCount` counts a live leaf only through the same label in its live-session branch; the worktree branch is reached only when the repo session is refused, which the hc fixture resolves. So the seats-untouched and `max_active: 1` tests pass on today's code with the explicit `direct` checks absent. The standing-design section's deliberate-break example is therefore false as written: removing the `direct` check in `endFinishedSeats` ends nothing.

- F9. Drop's live-run cancellation is unproven and its stopping sequence is unnamed. `src/admission.ts` `cancelLeafRuns` only marks live records and returns them for the caller to stop, the sequence `src/stop.ts` `stopLeaf` completes with slice and record-unit stops. The drop interface names no such sequence, its owned surfaces name neither admission nor the stop helpers for the new verb, and criterion 9 sets up a finished run, which cannot distinguish a drop that stops live work from one that removes a worktree under it. The verb also refuses only non-direct and `merged` leaves, so it can be run in `merge` against a live land attempt that the criterion never exercises.

- F10. `broadcastInProgress` cannot see a B in another session. The create verb deliberately finds seat addresses across every live hc session (readiness proof 1), but `src/reconcile.ts` `broadcastInProgress` only scans the `Seen[]` list its callers pass, and the per-repo passes build that list from the repo's one session in `src/next.ts` `repoTerminals`. A reviewer recorded in a different session is invisible there, so the item 13 release rule (B's turn passing the prompted turn) evaluates against no terminal and cleanup is released while that B's broadcast turn is still running. Criterion 8's single-session fixture never reaches this.

- F11. Two skill consumers of the changed routing are outside the owned list. `skills/watch-issues/SKILL.md` states required seats by phase as `check.review` A+B and `check.repair` B, so a watcher judges a direct leaf by lifecycle slots. `skills/plan-issue/SKILL.md`'s proof-command rule still records a direct-route correction in `<chart>/direct/plan.md`, a file the new flow never creates, while check-issue sends B to that rule to judge corrections. Criterion 10 and the architecture's skill list include neither file.
