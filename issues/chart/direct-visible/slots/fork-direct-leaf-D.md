# Blind notes: slot D, fork direct-leaf

## Q1. What record carries a direct-route attempt so `akrogon status` shows it like a lifecycle leaf?

### 1. Pick

Q1a, with two construction rules that remove whole danger classes instead of guarding them: the leaf records no `tab`, and its seats are found by recorded address only, never by relabelling the door or reviewer terminals as leaf seats.

Reason: only a real leaf is read by every existing reader with no second reader anywhere. `repoInventory` under `issues/open` feeds status text and JSON rows, timings, `log.jsonl` phase history, the merge queue, run-check worktree matching, land, and broadcast pending. One optional field in the strict `state.yaml` schema, for example `direct: true`, extends an existing record and old leaves keep parsing with no migration (signposts 3a, 6a). Runs attribute for free: `leafTarget` matches a recorded leaf worktree to its slug, while the direct route today falls through to slug `checkout` under `--holder <chart>/direct`.

Cost: that one field must be honoured at every point where the command acts on a leaf's seats, tab, slice or count. The full list, each of which today assumes command-owned terminals:

- `dispatchLeaf` (src/next.ts): resolves seats, observes busy, then `allocate` plus `dispatchSlot` per `requiredSlots`, which starts a missing seat, ends a finished one, charges attempts and losses, and sends `promptFor` phase prompts. For a door-run leaf it must stop after a read-only busy observation, or not run at all.
- `allocate` (src/next.ts): capacity check, `ensureWorktree` and `.env` write, leaf temp, and it sets `tab` to a leaf tab id when absent. Never called for a door-run leaf. The creation verb does the worktree once, up front.
- `activeCount` and `capRefusal` (src/next.ts): count unfinished leaves with a live leaf-labelled terminal, and when the session is unreadable count every unfinished leaf with a tab or worktree. A door-run leaf holds a worktree but no command seat, so it must be excluded or it consumes `max_active` for a terminal the operator already has open, and blocks real leaves when hc is down.
- `seatCommand` (src/next.ts, the seat start verb): `allocate` plus `startSeat` unconditionally. Must refuse a door-run leaf.
- `phaseWake` (src/next.ts): re-dispatches the leaf after every committed phase move. Same stop as `dispatchLeaf`.
- `renameTabs` (src/next.ts) and `renameTab` in `commitMove` (src/phase.ts, on leaving `failed`): rename the recorded tab to the slug or `<slug> failed`. Recording no `tab` makes both no-ops already, and the field must keep them that way in case a tab is ever recorded.
- `unnamedTabs` (src/status.ts): flags a recorded tab whose name is not the slug. No `tab` recorded, no false `tab unnamed` note on the door's chart tab.
- `reconcile` and `reconcileHost` (src/reconcile.ts): the slice step stops a loaded leaf slice unless `sliceKeepReason` keeps it, and merged or failed leaves go through `closeTabOf`, `closeLeaf`, `endSeats`, `endFinishedSeats`, `closeMergedTab`, plus worktree removal. `endSeats` is inert today because `leafSeats` requires the terminal to carry `akrogon.leaf` and `akrogon.seat` labels matching the recorded address, which door and consultant terminals do not carry. The field must make that exclusion explicit, not an accident of labelling, and must stop tab closing and slice stopping. Worktree removal after `merged` can stay: `foreignPaneInside` and process checks already keep a worktree a live pane sits in.
- `stopLeaf` (src/stop.ts): `endSeats`, stops the leaf slice, cancels runs. `stop --all` also selects leaves by tab or batch. For a door-run leaf, marking stopped and cancelling its runs is a sane operator stop. Ending its seats must never happen.
- `broadcastPass` (src/next.ts): `allocate` plus `dispatchSlot` to B, which would start a new B seat in a new tab. Replaced for door-run leaves by the Q3a address send.
- `landedWake` (src/next.ts): `closeMergedTab` when no broadcast waits. No `tab` recorded makes it return false today. The field must guarantee it stays that way.

Busy display is the one thing the stop-everything reading loses. `busy_since` is written only by `observeBusy`, reached through `leafSeats`, whose label gate will never match the door (a supplied or door terminal) or a consultant (started with only an `akrogon.seat` letter label, no `akrogon.leaf`). So a door-run leaf needs one new read path: look the recorded seat addresses up directly in their session and run the same `observeBusy` on what is found, inside `dispatchLeaf` before the early return. That is observation, not prompting. Without it, status shows phase, verdict, done and fix rounds but never `busy A` or `busy B`, and JSON `waits_on` never clears.

### 2. Rejected options

Q1b, lines in CHART.md `## Direct attempt` rendered as a leaf-shaped row. Status today renders charts only under `--charts`, as `CHART, TAKEN, FOG, STAGE, AGE` from fork Taken counts, the Fog section, the last stage marker and CHART.md mtime. The default view and the JSON `leaves` array come only from leaf inventory. A rendered row could show branch as slug, a hand-written phase word, rounds and review files from the existing `Direct attempt` shape. The operator would still not see, compared with a leaf row: phase time from the `log.jsonl` entry and first prompt timing, `blocked-by`, computed `busy A/B` durations, attempts, verdicts, done slots, delivery errors, the failed reason, `broadcast pending`, merge queue turn or `no merge record`, stopped marks, readiness gaps, and none of the JSON fields (`phase_since`, `waits_on`, `busy_since`, `land` unit and aliveness, `worktree`, `plan`, history, red attention). Runs stay slug `checkout` in the run line unless `leafTarget` also changes. The lines are free prose with no schema, written by hand at every step, so a dead door leaves a stale phase that nothing can check. That fails the lock wording `exactly like a lifecycle leaf` while building a second, weaker reader. Its only strength is zero risk to the door's tab, which Q1a's no-tab rule also gets.

Q1c, a chart-local `<chart>/direct/state.yaml` with its own reader. A new record kind, against signpost 3a. Everything that reads leaves by path under `issues/open` or `issues/closed` ignores it: inventory, `ownerScope` depth rules in phase.ts, `indexSlots` seat resolution in config.ts, merge queue, land claim by slug, run-check capture ownership. Each would need a second path or stay blind, which is Q1b's cost with schema validation added and nothing else gained. It also strands a live-looking record inside a chart folder after Closed or Held.

### 4. Pitfalls

- Reconcile or stop ending the door's or reviewer's terminal, closing the door's tab, or stopping a slice the door's runs use. Removed by recording no `tab`, never relabelling existing terminals as leaf seats, and an explicit field check at `endSeats`, `closeTabOf`, `closeMergedTab`, the slice step and `stopLeaf`, proven by tests at those boundaries, not by the current label mismatch.
- Dispatch prompting the door with a lifecycle phase prompt, or starting a replacement seat when the recorded address is busy or gone. Removed by the early return in `dispatchLeaf` and refusal in `seatCommand`.
- Capacity: the door-run leaf counted in `activeCount` starves real leaves. Removed by excluding the field there, including the session-refused branch.
- Owner invention: a leaf needs `issues/open/<owner>/<slug>/`. `ownerScope` treats the parent folder as the issue, or the grandparent as an epic, and `completeOwner` moves that owner to `issues/closed` and closes its sources. Someone must choose the owner name and the `sources` list at creation. Removed only by the creation verb taking them as explicit inputs from the chart, one new owner with this single leaf, so completion and broadcast behave as for a standalone issue.
- Missing leaf files: status prints `plan.md`, broadcast reads the leaf's `brief.md` and `design.md` from the closed folder, check reads the plan. A bare `state.yaml` leaf breaks those readers in spirit even where code tolerates absence. Removed by the creation verb copying the chart's draft brief and design into the leaf, and the direct plan landing at the leaf's `plan.md` instead of `<chart>/direct/plan.md`. That changes implement-issue and check-issue direct sections and moves run logs from `<chart>/direct` to the leaf `implementation` folder, which completion then deletes as it does for any leaf.
- Phantom rows: a Held chart, an abandoned attempt or a growth stop leaves a live leaf row. Removed partly by existing phases: growth stop or abandon moves the leaf to `failed` with a reason, and lifecycle handoff becomes recovery from `failed` with the field cleared by an operator phase move to `plan.synthesis`. A failed leaf still shows in status until recovered, which is honest, but an abandoned attempt needs a final disposition leaf lifecycle does not have today, such as parking the owner.
- Worktree lock: today's direct worktree is created with `git worktree add --lock`, and reconcile keeps locked worktrees. Removed by the creation verb using the leaf sparse worktree path (`createSparseWorktree`, no lock) at `worktree_store/<slug>` on branch `<slug>`, which is also what `ensureWorktree` and land's branch reads expect. In-flight locked direct worktrees at upgrade stay on the old route, no migration.

### 5. Questions the fork does not ask

- Who or what is `<owner>` for a chart with no single source issue, several sources, or no GitHub source at all, given completion moves the owner folder and closes exactly `state.sources`?
- Does the creation verb refuse when a leaf, branch or worktree of that slug already exists, including a previous direct attempt on the same chart (signpost 4a, one leaf per chart)?
- What is the final record for an abandoned direct attempt, since leaves are never deleted and `failed` rows stay visible?

## Q2. Who lands a direct attempt?

### 1. Pick

Q2a, the command lands it. A ready review is recorded as a phase move to `merge`, the merge queue takes its turn like any leaf, and the land run verifies, gates, pushes, records the broadcast handoff, and completes the owner. Steps 5.1 to 5.9 of direct-route.md and direct-guards.ts are deleted, not kept as a parallel landing.

Reason: landing is the mechanism that already exists and that direct landing re-implements by hand (signpost 1a). Every direct-guards check has a land equivalent. Clean tree and citation checks run in `landGates` through `moveGuards` and `batchGuards`, `requireNoIssueFiles` runs against the leaf path over the built-on range, the merge-scope green receipt is required by `recordTested` and again in `batchPush` against the exact tested top, and non-emptiness is required at `check.review` entry and in `batchGuards` for a record with no top. The push is the tested SHA to the default branch, never forced, with restack on refusal. `commandMerged` writes the `broadcast` handoff in the same save as the move to `merged` when the owner completes, and `completeOwner` closes the leaf's private sources and moves the owner to `issues/closed`, which replaces direct steps 6 and 9's close and record work.

Cost, stated plainly:

- Work the land run needs that the direct route does not provide today. A branch ref named exactly the slug at the tested head, since `mergeTurn` builds the batch from `branchSha(slug)` and `memberBase`, then `buildStack` and `applyTop`. A recorded, unlocked worktree at the store path whose head matches, since `batchGuards` and `mergeHead` read it and reconcile treats locked worktrees as keep-forever. Receipts before `merge` is even reachable: entering `check.review` requires a green leaf-scope receipt on the worktree head (`transition` calls `requireGreenReceipt` with scope `leaf`), and `check.repair` to `merge` requires one again, so the door must run `akrogon verify` in the worktree as part of building, not only the merge-scope verify with `--holder <chart>/direct` it runs today at landing. Phase records instead of review files alone: `check.review` at `fix_rounds` 0 requires both slots A and B done with verdicts before anything moves, and any `fix` verdict sends the leaf to `check.repair`, never back to `implement`. Plan is not a land need: nothing in land.ts or the gates reads `plan.md`. It is a check, status and broadcast need, covered under Q1.
- The repair loop must be mapped onto existing phases with no routing change. `implement` is the door building. At `check.review` the door records slot A's verdict from its own proof runs, then records B's verdict from B's review file, so B keeps writing only the review file and runs no phase command, as check-issue's direct section says today. On `fix`, the leaf lands in `check.repair` where B is the required slot. The door immediately moves it to `check.fix` on the authority of B's review file, repairs there as A, and moves to `check.review` again, where `fix_rounds` is now above 0 so only B's re-check verdict is required. One extra phase hop per round buys a true fix-round count in status and a B re-check of every repair diff. Conflict and dirty exits from `mergeTurn` and land also drop into `check.repair` with a `merge_exit` record, and the same hop routes conflict resolution through `check.fix` and a B re-review, which replaces direct step 5.2's focused re-check with a full one.
- Landing becomes asynchronous. `launchLand` runs a systemd service in the leaf slice, and its exits call `phaseWake`, which for a door-run leaf prompts nobody. The door must stay in its turn watching the leaf leave `merge` (land unit aliveness is already in status JSON and `status <slug>`) and then close the chart. A door that ends its turn after recording `merge` leaves the chart saying `charting` forever.
- Direct step 5.3's door-judged known-red path and its seed-issue filing for agreed base reds are lost. Land has its own cover: `uncoveredMainRedUnits` and the taken-8 base verdict, and anything uncovered exits red to `check.repair`. The stricter command judgment replaces the door's two-log read.
- The two-push-attempt bound is replaced by land's keep-place and restack behaviour in queue order. The direct attempt can also wait behind other leaves in the merge queue instead of pushing immediately. That is the lock working as written: it lands like a leaf.

### 2. Rejected options

Q2b, the door keeps landing and only records phase and landing. With Q1a it does not close: no seat call can move a leaf to `merged`. Routing allows `merged` only from `merge`, where required slots are empty and a seat call is refused, and `commandMerged` is called only from the land push. A door-pushed leaf would sit in `check.review` or `merge` after its code is on the default branch, a phantom row, unless a new verb records merged, writes the broadcast handoff and completes the owner. That verb is land's finish rebuilt a second time, next to a second push path that races the merge queue and holds no batch record of what was tested. With Q1b or Q1c, Q2b is coherent but keeps two landings in the system permanently and the record as display only, which fails the lock's broadcast-like-a-leaf in substance: `broadcastPending` needs phase `merged` plus the handoff only `commandMerged` writes.

### 4. Pitfalls

Removed by the `check.repair` to `check.fix` hop recorded by the door on B's review file, keeping B's hands off the code and A's repair in A's phase.
- A's review verdict becoming a rubber stamp. Removed only by the door recording A's verdict after its own verify and proof runs, which it must run anyway for the leaf-scope receipt. If A finds a defect it records `fix` itself and the same loop runs.

## Q3. How do the seats and the landing broadcast run without a new tab?

### 1. Pick

Q3a. State records `seat.A` as the door's `{session, address}` and `seat.B` as the reviewer's, whoever that is in chart letters (the INTAKE observation had slot D reviewing, and D is recorded as leaf B). The command observes busy by address, as under Q1, and sends the broadcast prompt only to a recorded B that it finds `idle` or `done`, by direct address lookup in the recorded session. It never calls `allocate`, `startSeat` or `end` for these seats, and never charges attempts or losses against them.

Reason: this is the leaf broadcast shape with the start removed. `broadcastPending` already defines the ack: phase `merged`, a `broadcast` handoff, and `prompted.B` unset, with `commitMove` clearing `prompted` so only this send sets it. The existing prompt text (`broadcast-issue <slug> slot=B owner=... closed=... sha=... sources=... leaf=...`) works unchanged because the owner really was moved to `issues/closed`. Reconcile already treats the leaf as broadcast-in-progress by B's address alone in `broadcastInProgress`, which keeps the worktree and slice until B goes idle, with no label requirement. And it survives the door ending: `broadcastPass` runs inside `mergeTurn` on later passes, so a replaced or finished door does not lose the broadcast, which is why lifecycle leaves give it to B in the first place.

Cost: `broadcastPass` needs a door-run branch before `allocate`. It finds B by address in the recorded session, sends once when `idle` or `done`, and records `prompted.B` on a started send or a delivery error otherwise, reusing the send half of `dispatchSlot` without its start, end and counting halves. If B's terminal is gone, finished, in another session, or busy working, the pass leaves the leaf pending and status keeps showing `broadcast pending` until the door rewrites `seat.B`. The door therefore needs a supported way to record and rewrite seat refs: the creation verb records A from the door's own terminal identity and B from a named address, validates both with an hc read at record time, and the same verb in an update form rewrites B when the reviewer changes or restarts to a new address. Rewriting B must not clear `prompted.B` after a send, or a second broadcast goes out.

### 2. Rejected options

Q3b, the door sends the broadcast itself and marks it sent through a command. It works only while the door is in a turn after an asynchronous land, which Q2a no longer guarantees, and a door replaced at handover never sends it. `broadcastPass` would still have to be stopped for door-run leaves or it prompts B as well, so nothing is saved there. Marking sent has no honest field: setting `prompted.B` records that the command prompted B, which did not happen, and a new sent field is a second broadcast record beside the existing ack. The seats become display-only, so busy, waits_on and broadcast pending are all hand-maintained by the one terminal the lock says is doing other work (charting the next chart). Today's direct step 7 is exactly this, and the INTAKE records the operator already doubts those broadcasts arrived.

- Code-read, 2026-11-25, src/next.ts `broadcastPass` and `dispatchSlot`: today broadcast allocates and can start B, sends only to an `idle` or `done` seat, and counts silent turn ends toward failing the leaf, all of which the door-run branch must not inherit.

### 4. Pitfalls

- The broadcast prompt interrupting a reviewer mid-exchange on another chart. Removed by the `idle` or `done` precondition read at send time in the recorded session, the same rule `dispatchSlot` uses, and by leaving the leaf pending rather than forcing delivery.
- A restarted consultant: door-created consultants are killed, removed and restarted at chart entry with new addresses. A pending broadcast recorded against the old address never sends. Removed by the door rewriting `seat.B` when it restarts or swaps the reviewer, and removed in practice because `broadcastPass` runs at the next merge pass, normally while the same B is still up. Status showing `broadcast pending` is the visible residue when neither happens.
- A supplied consultant as reviewer, whom the door must never move, kill or restart. Sending one hc prompt while idle is the same contact the door already makes to ask for a review, and the branch never ends or starts the terminal. Nothing further needed, but the door should expect no report back and must not collect it as an exchange.
- Busy attribution lies: the door terminal works on many things besides this leaf, so `busy A` can show for work on another chart, and a one-hour stall notice can fire for ordinary charting. Not removable while A is a shared terminal. Accepted as cosmetic, since phase, verdict and done stay exact, and stall notices already exist for shared watcher terminals in spirit.
- Worktree kept while B does unrelated long work, because `broadcastInProgress` holds it until B is idle or done. Bounded and self-clearing, and the alternative, removing the worktree before the broadcast reads its config, is worse.

### 5. Questions the fork does not ask

- When the reviewer changes mid-attempt, does B's recorded verdict history stay attributed to slot B even though a different terminal and model gave it?
- Should the creation verb refuse a B address whose hc read shows a different session than the repo's, given `broadcastPass` can only look in the recorded session?
