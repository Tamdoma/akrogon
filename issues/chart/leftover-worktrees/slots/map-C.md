# Slot C map: leftover worktrees (main d0a4bc9)

## Ground facts

- Today the candidate never reaches a removal rule: a registered worktree outside the store and legacy roots is kept as `unmanaged worktree` in the registered loop (src/reconcile.ts:762-767), and any locked worktree is kept before all other rules (src/reconcile.ts:442-447, candidate loop `row.locked !== false`). The guards the intake names already exist but sit behind that keep: `removeWorktree` vetoes on any same-uid process with cwd or open file inside and on live contained owners (src/reconcile.ts:526-545), then `worktreeRemovable` requires clean `git status --porcelain` (ignored files do not block), no rebase/merge markers, and HEAD reachable from some branch or remote (src/reconcile.ts:193-212). That reachability test is satisfied by the worktree's own branch, so it proves nothing about main (intake gap, confirmed at :205-210).
- Measured today: both repos' `git worktree list --porcelain` show only the root checkout; the akrogon root still holds the two leftover branches from the intake, `single-merge` (78b678a) and `worktree-agent-adfa0843775529512` (305545a), both ancestors of `origin/main` with empty `git cherry` ranges (`git merge-base --is-ancestor`, run 2026-10-16).

## Forks, with my picks

### (a) Which unmanaged worktrees may be removed, and what proves nothing is lost

- Pick: only worktrees passing all of: existing guards unchanged (clean porcelain, no rebase/merge markers, pane veto, same-uid process veto, src/reconcile.ts:193-212,526-545,707-730); an attached branch that is not the repo's default branch; HEAD is an ancestor of the fetched `<remote>/<default_branch>`, or `git cherry <remote>/<default_branch> HEAD` prints only `-` lines with no merge commits in the range; and the scope test in (d). Reason: ancestor proves the commits themselves are in main's history; cherry all-`-` is git's own patch-equivalence (the test `git rebase` uses to drop commits) and is the only cheap proof for the rebased case in the intake (16 commits, all `-`, not ancestors). The no-merges condition closes cherry's one blind spot: merge commits get no patch-id, so a unique conflict resolution inside a merge is invisible to cherry.
- What "nothing is lost" does not cover, by construction: ignored files (plain status never sees them, so `node_modules`, build output and any ignored local data die with the folder), the worktree's own index and reflog, and `config.worktree` if set. That is acceptable for scratch agent worktrees (d) and is the main reason it is not acceptable as the only test for an operator's own worktree. Stash is not at risk: it lives in the common dir, not the worktree admin dir, so removal never touches it. Cost: one `git cherry` per candidate per pass until it qualifies; passes run on every `next` and `tab_closed`, so the range must stay small or the result cached by head+upstream sha (see practitioner questions).
- Rejected: tree equality with main (`git diff` empty). It is the only literal nothing-lost proof, but a fully landed rebased branch's tree drifts from main the moment main moves, so the intake case itself would stop qualifying within days. Rejected: ancestor-only, which misses exactly the rebased agent work that produced this chart.

### (b) The Claude Code lock

- Pick: treat the lock as released only when it matches Claude's exact format `claude agent agent-<id> (pid <n> start <ticks>)` and that pid is dead or now has a different start time; every other lock, and a Claude lock whose pid still matches, is honored absolutely. Reason: the intake probe shows the lock names the *parent* Claude Code process, not the finished subagent, so while that session lives the lock is the only durable signal that the session may still send the agent back into the worktree — no pane sits inside it and its tools are transient shell children, exactly the invisibility measured in #94. Start-time equality is already how this codebase proves pid identity for run records (`liveStartTime` vs recorded `start_time`, src/admission.ts:50-82, field 22 of `/proc/<pid>/stat`), so pid reuse is handled with an existing pattern, not a new one. Cost: on a host where the parent Claude session runs for days, cleanup of a same-day leftover waits for that session to end; that delay is the price of never deleting under a live agent.
- Rejected: honor every lock forever (status quo for this class) — the reported leftover was locked, so the automation the operator asked for would never fire. Rejected: ignore the lock when (a) passes — `git worktree unlock` then remove can race a subagent that is between tool calls with a clean tree and patch-equal commits already cherry-picked by its parent, and it teaches reconcile to override the one explicit "in use" signal git provides, which the locks forbid. Rejected: read the Claude transcript to prove the subagent finished — parsing another harness's session format is the fragile coupling this chart should not buy for a same-session cleanup.

### (c) The worktree's branch

- Pick: delete it with the worktree, in the same pass and only after the worktree removal succeeds: `git branch -d` when git accepts it, `-D` only when (a)'s cherry proof passed (never for the default branch, never detached HEAD — detached has no branch to delete and its tip is held only by the worktree reflog, so detached candidates are kept, not removed). Reason: keeping the branch recreates the clutter one level up (the root already carries two such branches, measured above) and, worse, leaves a name a later agent worktree creation can collide with. `-d` alone is insufficient because it tests merged-into-current-HEAD by ancestry and refuses exactly the patch-equal rebased branches this chart exists for; the cherry proof in (a) is the license for `-D`, and either deletion failing keeps the branch and records a kept reason rather than failing the pass, following the merged-leaf precedent (src/reconcile.ts:552-562, only `-d` today).
- Rejected: always keep the branch. Zero commit risk, but the operator's screenshot complaint becomes a growing branch list, and a kept branch with the same name makes the next same-id agent worktree creation behave differently (checkout of an existing branch instead of a fresh one).

### (d) Scope: Claude Code agent worktrees only, or any unmanaged worktree

- Pick: Claude Code agent worktrees only, identified by the triple that must all hold: path under `<repo>/.claude/worktrees/agent-*`, lock text in (b)'s exact format (or that lock already released by pid death), and branch not equal to any leaf slug or the default branch. Reason: the triple is a creator contract — Claude Code itself deletes these worktrees when an agent finishes unchanged (intake probe), so akrogon finishing that job for the changed-and-landed case adds no new concept, matching the operator constraint. A general unmanaged rule has a fatal counterexample no proof in (a) can distinguish: an operator's fresh worktree made minutes ago for work not yet started is clean, has zero unique commits, and passes ancestor and cherry trivially; "nothing is lost" is true and deleting it is still wrong, because its value is intent, setup state and the editor session aimed at it. Nothing in git state separates that from an abandoned worktree, and age may not be used (lock: nothing deleted for age).
- Rejected: any registered unmanaged worktree including the operator's own, for the fresh-worktree reason above; it also expands reconcile's reach to every path on disk any registered repo points at, well beyond the managed roots every other rule is confined to. Rejected: path-only matching without the lock format, because a person can create `.claude/worktrees/agent-foo` by hand and because Claude can change its directory name while keeping its lock text, silently widening or narrowing the rule.

### (e) Leftover branches with no worktree

- Pick: out of this chart, except the paired deletion in (c). Reason: a branch costs no disk and no process safety; it is a bookmark whose intent (kept for backport, bisect, or a PR not yet pushed) git state cannot read, and both live examples happen to be ancestors, which will not be true of the next person's branch. Deleting worktree-less branches is a separate, more dangerous automation (a branch may be the only named ref to work that is patch-equal but whose commit messages and ordering are the record). Cost: the two measured branches stay for a human `git branch -d`, which already works on both today.

## What each option could break or invite later

- (a) Cherry-only proof invites deleting a branch whose patches landed but whose final tree differs from main because main later changed the same lines; nothing is lost from history, but the exact tested tree becomes unrecoverable once reflogs expire. Accepted under the operator's screenshot case (the worktree was deleted by hand on exactly this evidence), worth naming in the rule.
- (a)+(d) Claude-only scope invites the next harness (another agent tool's scratch worktrees) to need its own exception; the guard is that each new scope must bring its own creator contract like Claude's self-deletion, not a looser git test.
- (b) Pid-based release invites a subtle wedge: if the parent Claude process is long-lived and spawns agents for days, every finished agent worktree from that session waits for the session to end. Naming the blocking pid in the kept reason (already the `leftovers` shape) is what keeps that from reading as "automation broken".
- (c) `-D` after cherry deletes the only ref whose reflog could resurrect the original commit ids; if a later investigation needs the agent's exact commits (not their landed twins), they survive only in `removedWorktrees`' recorded head (src/reconcile.ts:548-550) until git gc prunes unreachable objects.
- Any option: a worktree on a branch whose upstream is a remote-only branch (no local branch, detached at `origin/feature`) must stay out — detached is kept under (c)'s pick — because the worktree admin dir may be the only place its reflog and index state exist.

## Practitioner questions this list misses

1. Which ref is "main" for the cherry upstream in a repo whose configured remote or default branch differs (`target()` in src/config.ts), whose tracking ref is stale because no fetch happened this pass, or which has no remote at all — and does a stale tracking ref fail safe (it does: more `+`, kept) in every direction, including a local main that is ahead of origin with the agent's work landed only locally?
2. How is the branch checked out in the root or in a leaf worktree excluded, given git already forbids the same branch in two worktrees but the candidate loop would still try `remove` and `-D` against the root's own branch if the root checkout ever sat on it?
3. What bounds the cost of `git cherry` and the `/proc` scan when a candidate branch is thousands of commits ahead of a stale upstream, on a pass that runs on every `tab_closed`?
4. Claude Code also runs worktree agents in consumer repos (framework is where the intake's agent ran, per the lock probe repo layout): does the rule run for every registered repo reconcile already covers, and are framework's own `.claude/worktrees/` entries in the live list today (none in today's porcelain for either repo, measured above) the common case or the exception?
5. When the worktree's branch was already deleted by Claude but the worktree registration remains (prunable), who owns pruning it — this rule, or the existing end-of-pass `git worktree prune` (src/reconcile.ts, on any removal)?
