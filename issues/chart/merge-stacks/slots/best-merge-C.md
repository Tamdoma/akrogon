# best merge design, no locks: blind notes, slot C

Question: what is the best way to land leaves faster than one-at-a-time solo merges at the same precision, or is one-at-a-time already best and the speed must come from cheaper turns?

Direct answer to the operator's question: one at a time is not the only real option, but today it is the fastest precise option. Every multi-leaf scheme loses at this repo's measured numbers (12-minute verify, roughly 1 in 4 solo attempts red). The speed available now is inside the solo turn: the verify composition and the red rate. After those are fixed and measured, one multi-leaf design becomes worth building: a speculative prefix of depth 2. Batching needs a green rate this repo does not have yet.

## 1. Pick

**Build in this order. All of phase 1 keeps precision identical: same commands, same tree, same receipts.**

**P1a. Move `hooks:selftest` into the leaf check scope (framework akrogon config only).** Today a leaf proves only the 30-second `cheap` suite at check; merge is the first time selftest (about 50 seconds) and the full core suite (about 11 minutes) ever run as a gate on the leaf. Most merge reds are first-exposure failures of exactly those merge-only suites, with direct causes in the leaf's own diff (stale command-list expectations, undeclared runner inputs, seeded-hash and recording staleness, fixture expectations). Running selftest at check moves the fast-stage half of those reds into the check loop, where a rerun costs about 77 seconds instead of a merge attempt plus a check.fix round trip. Merge still runs the full suite on the rebased tree, so nothing is proven less.

**P1b. Rebalance the core verify groups (framework `package.json` only).** A green merge verify is 77 seconds of fast stage plus 666 seconds of core stage, and the core wall is one sequential chain: `framework:verify:rest-b` takes 655-667 seconds in every green log sampled, while `rest-a` finishes in 185-191 and every parallel single suite under 105. Inside rest-b, `test:meta-content-coverage` alone takes 420-426 seconds. Move that one command out of the sequential chain into its own parallel slot and split the rest of rest-b across rest-a/rest-b evenly. Expected core wall about 440-480 seconds, set by meta-content-coverage itself. Same commands, same tree, no precision change. If that one suite later shards internally, the floor drops again, but that is unproven and not counted here.

**P1c. Command-only green path (akrogon).** On an applied top, the command itself runs verify, the receipt check, and the push; the B seat is dispatched only for the solo conflict form, a red that needs cause judgment beyond the recorded policy, or a refused push it cannot restack cleanly. This saves only about 1 minute of wall per landed leaf (measured non-verify time inside a solo merged attempt is median 0.9 minutes), so it is third, not first. Its larger value is removing the agent session as a failure class (the October 13-14 auth and host-stall attempt cluster) and removing per-merge seat cost. Precision cost: none on green; on red, B's judgment calls (inconsistent rerun, known-red, memberless mechanical repair) become policy: red goes to check.fix with the log, except the existing receipt-based known-red check which is already mechanical.

**P2. Later, gated: speculative prefix, depth 2.** While the holder verifies, build the next leaf on the predicted top (current main plus the holder) and verify it in parallel, command-run, no seat. If the holder lands, the next leaf's green receipt is already for the exact tree it will push (receipts are tree-keyed in `src/verify.ts` today), so its turn is push-only. If the holder goes red, the speculation is discarded. This is the Zuul/GitHub/SubmitQueue prefix model and it is the only multi-leaf design that keeps per-prefix precision intact. Build it only when two measured gates pass: the solo green rate after phase 1 is at least about 85% sustained in merge-attempts, and a probe shows two concurrent `framework:verify` runs on this host finish without port collisions or timing-flake growth and with combined wall well under 2x solo.

Estimated effect (model in Evidence, all estimates flagged there): phase 1 brings a landed solo attempt from about 13.0 minutes to about 9-9.5, and all-in attempt minutes per landed leaf from about 18.6 to about 11-13. An 11-leaf queue of green-at-merge leaves drains in about 100 minutes instead of about 143. Phase 2, if its gates pass, estimates a further cut to roughly 75-90 minutes for that queue. Cost of the pick: P1a and P1b are framework-repo changes, not akrogon code, so this chart cannot land them itself; P1c is real akrogon work (a programmatic verify-plus-push path in the merge turn, a smaller merge-issue skill, an explicit new owner for the completion broadcast the merge seat sends today).

## 2. Rejected options

**Batching with split-on-red (bors/Mergify style), any size, today.** At a per-leaf green probability of about 0.75, a pair batch with full splitting costs more verify minutes per landed leaf than solo (arithmetic in Evidence: about 14.3 versus 13.9, before overheads and before interaction failures, which only hurt the batch). Bigger batches are worse: an 11-leaf batch expects 2-3 bad leaves, so bisection runs more verifies than solo would. Mergify's own sizing guide says above a 5% queue failure rate to use batches of 2-3 and treat the failure rate as the real problem; this repo is at about 25%. Batching breakeven in my model is a sustained green rate around 0.82-0.85, and a clear win only near 0.9. Revisit after P1a if the measured rate gets there; do not build the batch machinery now. Precision note: plain batching also lands member prefixes never verified as prefixes, which P2 does not.

**Adaptive batch size from the red rate (Zuul window over batches).** Same math with extra machinery. An adaptive sizer at today's rate converges to batch size 1, which is solo with the batch code kept. If the rate improves, P2's speculative prefix gives the same throughput direction with stronger precision and no culprit problem.

**Affected-only merge verify (test impact selection, disjointness receipt reuse, Bazel/Nx-style input caching).** Unsound here, and the observed reds prove it. The framework suite is full of global scans (skills scan, input-manifest vocabulary, runner-coverage lists, seeded hashes, fixed command-list expectations) whose inputs are effectively the whole tree. Sampled merge reds include a main-side change breaking a leaf through files neither side would call related (main adds `cf_hosting_pool` to a fixture config, the leaf's pin-hash test fails; main adds a build-output guard, the leaf's bring-up test fails). Any path-disjointness rule simple enough to build on bun test plus shell scripts would have wrongly reused receipts in exactly those cases. Google's TAP selection is sound only over a declared build-dependency graph, which this repo does not have; the framework already removed its `test:changed` command. This option weakens the operator's precision condition in the exact failure class that dominates. Rejected for the merge gate.

**Fast-only merge gate, full suite after landing (presubmit/postsubmit split).** Would cut a landed attempt to about 2.5 minutes, and it is what Chromium CQ and Google effectively do at scale. It directly breaks the stated outcome that main never receives a commit that failed the configured checks: 37% of red merge verify runs fail in the core stage, including leaf-caused semantic breaks (a leaf switching an audit to real HTTP probing broke 24 renderer integration cases). Rejected under the operator's precision condition, stated plainly as the one option that is much faster only by being less precise.

**Flaky-test quarantine as the design.** Real but small. Named flake or unattributed cases in the solo-red sample are a handful of 64 (a 5-second wrangler bundle timeout, a timing-threshold median, an unattributed browser-count, a recurring remote-image network assertion riding along on unrelated leaves). Akrogon already has the inconsistent-rerun rule, known-red receipts, `src/flaky.ts` flip reporting and framework red-records. Expected gain under half a minute per landed leaf. Hygiene, not the answer.

**External CI runners / more hardware.** The host is a 32-thread Ryzen 9 9950X3D with 123 GB RAM, `bun install` setup measures 0.04 minutes, and the verify wall is set by sequential chains, not raw CPU saturation. Moving verify off-host adds checkout and setup costs to fix a parallelism-shape problem that P1b fixes locally.

**Status quo (stacking as-is, or solo with no turn changes).** Stacking was settled in the previous fork. Plain solo with no changes leaves the two measured wastes in place: merge as first full-suite exposure, and a 666-second sequential chain setting every green verify's wall.

## 3. Evidence

Tier key per questions.md: measured/inspected code is better-than-training; named external operators are practitioner; vendor docs are better-than-training. All sources read 2026-10-19.

### Where a solo turn's minutes go (framework repo, measured)

Config (`akrogon config` in the framework repo, read today): `checks` is one command, `cheap` (`bun install`, own-modules guard, `framework:verify:cheap`); `merge_checks` is one command, `verify` (`framework:verify`); `merge_covers` is `[cheap]`. So leaf-scope verify is cheap only, and merge-scope verify is the full suite only. `framework:verify` runs two stages in sequence: fast (`framework:verify:cheap` then `hooks:selftest`), and on fast failure core does not run; then core (10 groups in parallel, `--no-exit-on-error`, so a red core still runs to completion).

From `issues/verify-runs.jsonl` (680 runs, 2026-10-14 onward) and `issues/timings.jsonl`:

- Leaf verify (cheap): 401 completed runs, median 0.49 minutes, 96% green. Setup (`bun install --frozen-lockfile`): median 0.04 minutes in timings. Neither matters.
- Merge verify: 271 completed runs, green median 12.05 minutes, red median 1.42. Red runs are bimodal: 76 of 134 finish within 2 minutes (fast-stage failures, core never runs), 50 take 8 minutes or more (core failures), 8 between.
- Green merge verify anatomy, consistent across 4 sampled green logs (stage markers in the retained `check-verify` logs): fast 72-80 seconds (cheap about 26, hooks:selftest 46-55), core 655-668 seconds, of which `framework:verify:rest-b` is 655-667 (it is the wall), rest-a 185-191, longest parallel single suite 105. Inside rest-b: `test:meta-content-coverage` 420-426 seconds, next `test:e2e:emdash-kit` about 60, `test:variant-parity` about 49, `test:offer-tracking` about 37.
- Solo attempt split, pairing 175 solo attempts with the merge verify runs inside their window: merged attempts median 13.0 minutes total, of which verify is 12.1 and everything else (buildStack, seat startup and reading, review-B.md, briefs, phase calls, push) is median 0.9, mean 1.2. Red solo attempts median 7.3 total, verify 5.3, rest 1.5. Verify runs per attempt: 1.10 merged, 1.08 red, so reruns and restack reruns are not a major cost. Push cost is inside the 0.9 and not separately visible; nothing suggests it is large.
- All-in cost today: solo attempt minutes per solo-landed leaf including failed attempts is 18.59 over the full 333-attempt file (slot B's M10 in stack-fate-B.md; consistent with my recounts). Solo green rate among merged-or-red solo attempts: 173 of 237, about 73% (76% in the earlier 267 snapshot).

### Where the 24% red rate comes from

Keyword scan of the attempt-matched `review-B.md` merge sections for all 64 solo red attempts, cross-read in full for the ambiguous ones. This is a classification of B's recorded judgments, not a re-run:

- About 39-41 of 64: B records a direct cause in the leaf's own diff. Two subkinds dominate. First, global-inventory staleness exposed by `hooks:selftest`, which never runs at check: fixed expected command lists (`verify-aliases`), undeclared runner input reads (`input-manifest-vocabulary`, `validate-handoff-schema`), runner-coverage and census counts, seeded file sha and recording mismatch. Leaves: promotion-script, disavow-evidence-scope, prior-pack-diff, cadence-inputs, d1-location, url-serving, purchase-facts, backup-real-layouts. Second, real semantic interactions exposed by core suites: dilutor-liveness (audit now probes real URLs, 24 renderer cases fail), frozen-assignment (init now requires a hosting pool), scratch-lifetime (preload breaks a child entry point), upload-form-declaration (widened Playwright discovery), hub-child-links and cadence-ideation (new verification reaches unadapted fixtures).
- A small cluster on 2026-10-13/14 never reached a verify verdict at all: GitHub auth diagnosed per attempt (favicon-render three times, pass-two-review-notes, technical-pack-selection, flaky-test-fixes), host load stalling verify (load average 393 recorded), and memory-admission waits (favicon-render twice). The auth cause was later corrected by the operator to a session D-Bus configuration. These are agent-session and host-policy failures recorded as red attempts, not code reds.
- A small flake/unattributed residue: fail-fast (wrangler bundle test timed out at 5000 ms, passed on base, B records no plausible cause in the diff), spec-path-open-categories (a `SCALE_50_SITE` timing-threshold median, then timeouts on retry), slow-lane-reads (unattributed after full comparison), and `test:remote-image`'s "no network attempts during build" assertion appearing as an extra unattributed failure inside at least three unrelated leaves' red runs (d1-location, satellite-no-inert-form, replay-cases).
- Genuine new-main interactions (leaf green against its old base, red only against newer main) exist but are the minority of the sample: media-range (main's new build-output guard refuses the leaf's bring-up fixture), neutral-identities (main's new `cf_hosting_pool` changes a hashed fixture config), flaky-test-fixes' resumed attempt (leaf's new inventory misclassifies main's new test file, and its file trips main's scanner). Rebase conflicts themselves are not the red cause in the sample; where they occur they are resolved before verify and the red is semantic.
- No solo red in the sample is a trailer refusal; trailer gaps are handled at `merged --check` after green verify and do not produce red attempts. Mechanical generator-type reds at merge are rare in the sample (recording refresh in prior-disavow-lookup is the closest).

Conclusion the design rests on: the red rate is mostly not "leaves keep breaking against new main". It is "merge is the first run of selftest plus core, so first-exposure failures surface at the most expensive, most serialized point in the system". What a leaf proved at check (cheap, 30 seconds, plus its plan's targeted criterion commands, which timings show can be large: `test_changed` runs at implement/check.fix have median 15.5-17.3 minutes over 95 runs) does not include the two suites that produce nearly all merge reds. Merge then re-proves cheap on the rebased tree (necessary, 26 seconds) and proves selftest and core for the first time.

### Model used for the option estimates

Inputs: green verify 12.1 median (fast 1.3, core 11.1), red verify median 5.3 paired, attempt overhead about 1.0, per-leaf green probability p about 0.75. Solo expected verify minutes per landed leaf on a simple geometric model: (0.75×12.1 + 0.25×5.3) / 0.75 ≈ 13.9, in line with the empirical 18.6 once ejected, held and long-tail attempts are included. Pair batch with split-on-red: expected verify minutes per 2-leaf cycle = 12.1 × (1 + (1−p²) + (1−p²)p); at p=0.75 that is 21.4 minutes for at most 1.5 expected landed leaves, at least 14.3 per leaf, worse than solo before counting interaction failures between the paired leaves. At p=0.9 it is 16.5 for 1.8, about 9.2 per leaf against solo about 12.7. Breakeven near p≈0.83. P1b estimate assumes core wall becomes max(420-426 meta-content, balanced remainder about 310-330, singles 105) plus contention, hence 440-480. P1a estimate assumes most fast-stage leaf-caused reds (fast failures are 57% of red verify runs; the sample's fast reds are overwhelmingly leaf-caused) are caught at check instead, leaving core reds and true interactions: merge red rate from about 25% to an estimated 13-17%. These are estimates with stated inputs, not measurements; P2's gates exist precisely to re-measure before building.

### Inspected code (akrogon, read in full today where new)

- `src/verify.ts`: receipts are keyed by tree plus scope plus exact command list (`greenRun`), and `verify` reuses a green receipt for an identical tree. That is exactly the hook a speculative prefix needs: a green run on the predicted tree is a valid receipt when that tree becomes the push candidate. Known-red acceptance is also mechanical (base run covers head's failing test names). Each run builds a fresh sparse worktree, runs setup, then the scope's commands in sequence.
- `src/verify.ts` scope rule: leaf scope runs all `checks`; merge scope runs `checks` minus `merge_covers` plus `merge_checks`. P1a is therefore a framework config edit (add a `selftest` check, add it to `merge_covers`), zero akrogon code.
- `src/next.ts` merge turn and `src/phase.ts` merge paths (read in the prior fork, unchanged since): the command already builds the top, owns the push, restack and recovery. The B seat's irreducible inputs on the applied-top path are running `akrogon verify`, judging red cause, and gathering completion briefs for the broadcast. `verifyCaller` requires a leaf holding a batch attempt in merge phase, and `mergeQueue` (`src/turn.ts`) sorts any leaf holding a batch record first, so a speculative run cannot simply reuse `state.batch` on the second leaf without breaking the holder rule; P2 needs a separate speculative record or a holder-rule change. Named here so the leaf that builds P2 does not discover it late.
- `src/flaky.ts`: flip detection over verify runs already exists (`akrogon flaky`), supporting the "quarantine is hygiene" judgment.

### Outside research (practitioner first, read 2026-10-19)

- Practitioner: Juloori et al., Uber, "CI at Scale: Lean, Green, and Fast" (arXiv:2501.03440v2, 2025-05-19), https://arxiv.org/abs/2501.03440. SubmitQueue speculatively builds a tree of pending-change combinations, prunes it with conflict analysis so independent changes build concurrently, prioritizes by predicted success and build time, and lands only green outcomes. Their caution is the cost side: 40-65% of speculative builds were being aborted, and adding a speculation threshold (only build the most probable combinations) plus prioritization cut CI resource use 53% and p95 wait 37%. Supports P2's shape (prefix speculation, depth limited, gated) and warns against unbounded speculation on one host.
- Practitioner: Memon et al. (Google), "Taming Google-Scale Continuous Testing" (ICSE 2017, TAP), https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/45861.pdf. Affected-test selection at Google is computed from reverse dependencies over declared build targets, and postsubmit still tests bundled milestones because per-change full testing is unaffordable. Supports rejecting affected-only selection here: its soundness comes from the declared dependency graph this repo lacks.
- Practitioner: Chromium CQ documentation (Chromium infra team), https://chromium.googlesource.com/chromium/src/+/HEAD/docs/infra/cq.md. The normal CQ runs a curated subset optimized for turnaround, reuses passing builds across trivial rebases within a commit-distance or 24-hour window, and reserves near-full coverage for the opt-in Mega CQ. This is the fast-gate-plus-reuse design operating at scale, and it explicitly trades precision for speed, which is why it is evidence for the rejected fast-only gate rather than for the pick.
- Practitioner: Rust Forge, Rollup Procedure (Rust release/integration team), https://forge.rust-lang.org/release/rollups.html. With a roughly 3.5-hour CI, operators hand-pick low-risk PRs into rollups; on failure they bisect via log analysis, unapprove the culprit, and recreate the rollup without it. Batching pays there because one verify is 17x longer than here and members are pre-screened for risk by humans. Neither condition holds here.
- Practitioner/vendor: Mergify, "How to cut CI costs with batching and bisection", https://mergify.com/guides/cut-ci-costs-batching-bisection. Sizes batches from queue failure rate: under 2% failures, batches of 5-10; 2-5%, batches of 3-5; over 5%, batches of 2-3 and treat the failure rate as the real problem, since bisection runs cancel the saving. This repo's roughly 25% per-leaf red rate is off their chart, in the direction of P1a.
- Carried from the previous fork, read 2026-10-19 in that exchange: Zuul gating (speculative prefixes, window halving on failure toward serial at high failure rates), GitHub merge queue docs (cumulative groups, failing PR removed and later groups rebuilt), GitHub's own merge-queue operating account and Mergify batch docs via slot B's notes (stack-fate-B.md F5). They agree with the sources above: batching and speculation pay when failure is rare or CI is parallel and deep; everyone pairs them with culprit removal or per-prefix receipts.

## 4. Pitfalls and what removes each

- P1b regrouping may break a hidden serialization reason: rest-b's sequential list may serialize browser or port-using suites against each other, not just accumulate them. Removed by a framework-side probe before the regrouping is kept: run the split composition once on a known-green tree and compare per-suite results and wall against the current composition; a suite that fails only when parallel stays serialized against its conflict partner. Owner: the framework change itself, as a done-criterion.
- P1a makes every leaf verify about 50-80 seconds slower and runs selftest far more often across 24 active leaves, adding host load. Removed by measurement, not hope: leaf verify runs are already recorded in verify-runs.jsonl, so the check-loop cost delta and the merge fast-red delta are both measurable within days; if merge fast reds do not fall, the config edit is one line to revert. Note selftest also runs inside merge's fast stage regardless, so total system selftest runs rise; the trade is deliberate (cheap parallel time at check against serialized time at merge).
- P1c removes B's red-cause judgment, the memberless mechanical repair that occasionally lands a leaf in the same turn, and the seat that sends completion broadcasts. Removed by keeping all three as explicit paths, not habits: red policy is recorded (green receipt or mechanical known-red lands; anything else goes to check.fix with the retained log, which is already what a second red does today); mechanical-repair-at-merge is dropped knowingly, its cases take one check.fix round instead; the broadcast gets a named new owner in the leaf contract (the command cannot send it, since broadcast-issue is seat-run by rule; the completion line must be handed to a named seat or the rule changed by the operator). The solo conflict form keeps its seat unchanged.
- P2 speculation can starve the host or collide on ports: two full verifies run the same browser suites, and this host has recorded load averages in the hundreds during the October 14 episode, plus a memory admission gate that already queues verifies. Removed by the pre-build probe in P2's gate: two concurrent `framework:verify` runs in separate sparse worktrees on green trees, measuring wall against solo, failure names against solo runs, and admission behavior. If combined wall approaches 2x solo or timing-sensitive suites flip, P2 is not built. The speculative record must also not reuse `state.batch` (holder-rule hazard named in Evidence); the leaf that builds P2 carries a criterion that exactly one leaf can pass `phaseCommand`'s holder check at any time.
- Every phase-2 number here is model output, and the model's p is the thing phase 1 changes. Removed by gating P2 and any batching revisit on the measured post-P1a green rate in merge-attempts over a stated window (suggested: at least 50 solo attempts), not on this note's estimate. If the rate does not move, phase 2 does not happen and nothing was built for it.
- Faster verify invites more parallelism elsewhere until timing-sensitive tests (the recorded `SCALE_50_SITE` median threshold, browser timeouts) start flipping under load, raising the red rate the design just lowered. Removed by treating the flip rate as a monitored output: `akrogon flaky` over verify runs before and after P1b, with the regrouping reverted or re-serialized for any suite whose flips appear with the change.

## 5. Questions the fork does not ask

- Q1: Who owns P1a and P1b? Both are framework-repo changes (akrogon config for that repo, and its `package.json` verify composition), while this chart lives in akrogon. The fastest precise design is mostly not akrogon code. Does the operator want this chart to hand off framework leaves, seed framework issues, or only decide the akrogon side (P1c, P2) and record the framework recommendations?
- Q2: Should merge-attempts record the failing stage and command (fast/core, suite name) at record time? This whole analysis required archaeology across verify-runs, timings and review-B prose. One field on the attempt record (and the same on the verify run's red exit) would make the red rate by stage, and therefore every future queue decision including P2's gate, a one-line query. Not a culprit command; just recording what already printed.
- Q3: Is full-suite-on-every-leaf itself the precision bar the operator wants kept, or is the bar "no red lands" with the suite composition open? The brief locks the outcome as every landed leaf checked against its landing base with the configured checks, and I have treated the configured suite as fixed. But nothing in the fork asks whether, say, a docs-only leaf should pay the same 12 minutes. A risk-tiered suite is a precision decision only the operator can make; Chromium's answer (curated presubmit subset) is the scaled precedent if he ever wants it asked.
- Q4: What is the host budget for merge work against the 24 active leaf seats? Every parallel design (P1b's wider core, P2's second verify) spends the same host the leaf seats are using, and the October 14 load and admission episodes show the ceiling is real. The fork asks for the fastest precise merge; it does not ask how much of the host merge may claim, which bounds P2 more than any code does.

Most important: land solo, and spend the effort on the turn itself. Move selftest into check, take `test:meta-content-coverage` and half of rest-b out of the sequential chain that sets every green verify's wall, and take the seat out of the green path. That is an estimated 13.0 to about 9-9.5 minutes per landed attempt at identical precision, with speculative prefixes as the one faster design worth building after the green rate proves it can pay for speculation.
