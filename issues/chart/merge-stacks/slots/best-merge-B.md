## 1. Pick, reason and cost

**D1. Build a command-driven queue that verifies predicted prefixes concurrently and publishes them in order. First shorten the full verification pipeline. Start with two independent verification slots, then size the window from measured capacity and wasted work. Keep a separate green receipt for every leaf boundary.**

One-at-a-time verification is not the only precise option. For leaves A and B, construct immutable candidates `T1 = main + A` and `T2 = T1 + B`. Verify both concurrently. Publish T1 only after its checks pass. Publish T2 only after T1 lands unchanged and T2's own checks pass. If A fails, T2 is invalid evidence for B landing without A and must be rebuilt. This preserves the per-leaf integration guarantee without requiring a trustworthy dependency graph or a machine-learning model.

I would build the following in this order:

- **A1. Shorten the suite without dropping assertions.** The measured critical path repeats the same real-browser capture eight times and places a seven-minute test command late inside a serial lane. Reuse immutable capture outputs within that test file and schedule that command as its own bounded lane. Static critical-path arithmetic suggests a full run around 5.4 minutes instead of 12.4. This needs a real benchmark before being promised.
- **A2. Automate green turns.** The command builds the candidate, runs deterministic preflight gates, verifies, checks the receipt and publishes. An agent handles conflicts, red causes and repairs. Do not require an agent to reread every log and assemble a report before a mechanical green push. Preserve owner completion and notification delivery explicitly.
- **A3. Add bounded prefix speculation.** Two workers verify the holder and the next eligible leaf on its predicted successor. They need real independent capacity or demonstrated spare capacity, not merely two more processes on this host. Keep the publisher serialized. A larger window is available when measurements justify it.
- **A4. Catch integration mistakes earlier.** Add the roughly 50-second hooks selftest increment to the cheap check before merge admission. It will catch some current queue rejects earlier. Continue checking the final integration state because new main can invalidate earlier proof.

**Estimated 11-leaf verification service:** today's solo-only path is about **143–152 minutes for eleven healthy leaves**, or **190–225 minutes per eleven landed-leaf equivalents** when historical failed-attempt work is charged. D1 targets **35–45 minutes healthy**, or **50–65 minutes per eleven landed-leaf equivalents**, with two isolated workers and the suite improvement established. Before optimizing the suite, two workers alone model at roughly **110–145 minutes per eleven landed-leaf equivalents**, not eleven leaves in one 13-minute run.

These are conditional estimates, not measured new-system performance. A leaf requiring a repair is not made landable by a queue algorithm. The estimates exclude time in `check.fix` and re-review. They cannot promise when all eleven initially queued leaves will actually land. If no second execution slot is available, A1 and A2 still target roughly **60–70 minutes healthy**, with failed-attempt service plausibly **90–120 minutes**. Partial optimization that only shares captures, without safely splitting the lane, has a weaker target near eight minutes per full run.

**Cost:** a second worker, explicit candidate/job state, cancellation and recovery, stronger receipt identity, and a machine-owned green path. This is more implementation work than deleting members. It buys speed with additional computation while retaining every required integration proof. It is the design I would defend for this repository. Eleven workers could verify eleven healthy prefixes in roughly one suite interval, but this host's overload history makes unrestricted local concurrency a poor default.

There is no mathematical requirement for parallel CI to make batching cheaper under a weaker batch-top guarantee. There is also no requirement to accept that weaker guarantee to get parallel speed. O4 verifies all prefixes, so it addresses the actual question directly.

### Model and drain-time limits

For two equal-duration prefix jobs per wave, A passes with probability q. If it passes, B's prefix can also be decided. If A fails, B's speculative proof is discarded. Expected landed good leaves per wave are `q + q²`, giving O4's formula. This assumes independent outcomes, unchanged run time with two workers, immediate scheduling and no repair delay. At observed p values 0.24–0.31, the model gives 9.35–10.72 minutes per landed leaf at V=12.5, or 4.04–4.63 at V=5.4. It is not a replay of the real queue.

The improvement over one worker disappears if two-worker run time grows by roughly `1+q`, about 1.7 times. The first capacity experiment therefore measures both suite duration and useful landed receipts, not just the number of simultaneous jobs. On this host, deploy one optimized runner first unless two-suite overlap has demonstrated capacity. A second isolated machine avoids many local interference problems.

Adaptive batch size must use meaningful causal integration failures, not the raw 24%/27% mixture of contract failures, timeouts, retries and repeat attempts. Under an independence approximation, `q^k` is 0.533, 0.389, 0.284 and 0.031 for k=2,3,4,11 at p=0.27. These are illustrations, not bounds. Correlated load failures violate the assumption. A large prediction window can still be useful with enough workers because prefixes retain separate receipts. A large one-check batch changes the proof.

### F6. Code constraints that matter to the new design

Better-than-training tier, repository code read 2026-10-19:

- **C1. Receipt identity is currently too coarse for general input caching.** `src/verify.ts:97` matches tree, successful setup and command list. `checkedRun` supplies `AKROGON_BASE`, but the receipt does not record it. Equal trees do not guarantee equal Git-aware checks, toolchain or environment. Extend proof identity before using future-base or per-command reuse. `scope` is stored, but `greenRun` eligibility is driven by the expected command list rather than an explicit scope comparison.
- **C2. Known-red acceptance is a separate policy.** `src/verify.ts:257` accepts a matching green receipt **or** `knownRedReceipt`. That is weaker than a literal requirement that every configured check pass. No sampled landing was shown to rely solely on red merge receipts, but the code permits that route. D1's strict publication gate must require green evidence. A pre-existing failed required check needs repair or an explicit policy change, not a hidden exception.
- **C3. Future-base verification needs an explicit base.** Today `verify` derives the base against the tracking branch. For T2 checked before T1 lands, the correct future predecessor is T1, not today's main. Record and pass that predecessor to Git-aware checks. Configuration changes in T1 must also affect T2's expected check set as they would after publication.
- **C4. Existing run execution can be reused, scheduling cannot.** `runOnce` already creates isolated worktrees and uses logged checks and systemd run scopes. `verifyCaller` currently requires a live merge holder attempt. A speculative candidate needs its own authorized job target rather than impersonating the current holder. `src/admission.ts:142` starts registered runs immediately. It does not supply a global capacity limit for the proposed window.
- **C5. Publication recovery already exists.** Reuse `batchPush`, `finishPush` and `reconcileBatch` concepts for compare-and-publish, lost-reply ancestry checks and exactly-once phase transitions. Replace multi-leaf member state and one-push-many-completions with per-leaf candidate/predecessor/receipt state. Retain clean holder integration, retirement, citations, review authorization and owner completion.
- **C6. Green automation needs explicit workflow changes.** The merge skill currently assigns log judgment, completion-owner reads, reports and broadcasts to B. Move deterministic green work into the command and preserve necessary delivery, rather than claiming removing B is just suppressing a prompt. Red repair remains an agent task.

## 4. Pitfalls and what removes each

- **R1. A later leaf hides an earlier failing leaf.** Require one green integration receipt per leaf boundary. Never promote AB's success into A's missing or failed proof. This rules out optimistic-prefix acceptance and ordinary one-check batching under the requested contract.
- **R2. A successor was tested against a different predecessor.** Persist the candidate's explicit predecessor SHA and check base, immutable reviewed head, tree, configuration/command digest and execution-input identity. Publish only if the expected predecessor actually landed. Rebuild affected descendants after predecessor failure, mutation, stop, reorder or unexpected main movement.
- **R3. The cache ignores inputs outside the source diff.** Cache only proven action inputs. Include setup/tool versions, environment identity without exposing values, lockfiles, fixtures, manifest inventories and Git-sensitive base context. Non-hermetic network/live checks remain noncacheable without versioned external inputs. Do not infer independence from directories.
- **R4. More jobs recreate the recorded host overload.** Separate workers or measure stable overlap before increasing the window. Compare elapsed drain, per-job inflation, memory/pressure, cancellations and useful green receipts. Preserve foreground holder priority. Declining speculation under demonstrated resource contention is scheduling, not weakening proof.
- **R5. Shared test setup weakens or contaminates proof.** Share only immutable identical-input capture results. Keep the no-card run separate, preserve every route/width and assertion, and leave mutated-input repair tests isolated. Verify the shared setup against the existing assertions before crediting its projected savings.
- **R6. A machine publishes work an agent has not approved.** Bind merge admission to a reviewed immutable head. Run citation, scope, retirement, current configuration and receipt checks before publication. Mechanical conflicts and judgment-bearing repairs go back to an agent and require new proof. Green automation is not permission for automated test-expectation changes.
- **R7. Retry/quarantine silently changes the policy.** Keep all currently required checks gating. A known-red baseline or later green combined tree is not enough for strict publication. Fix harness causes and obtain green evidence. A deliberate quarantine or postsubmit-only test is an explicit coverage change, with its speed estimate excluded from D1.
- **R8. Crash recovery moves several leaves on one ambiguous result.** Maintain per-leaf publication candidates and exactly-once completion records. On a lost push reply, inspect remote ancestry before retrying or changing phase. Reuse existing recovery behavior for each candidate. Finish/reconcile old applied member stacks before replacing their live state representation.
- **R9. Claimed drain improvement excludes repairs or double-counts savings.** Track service time, queue wait, repair/review delay and compute consumption separately. Do not add modeled agent, caching, flake and suite gains as though independent. The 50–65-minute target assumes the measured suite bottleneck is actually removed and worker runtimes stay stable.
- **R10. Tests validate the scheduler's words instead of its guarantee.** Use the existing bun:test/Git fixtures to demonstrate A-green/B-green publication, A-red descendant invalidation, B-red after A lands, B fixing A while A remains red, external-main races, stopped/edited leaves, future-base configuration changes, different `AKROGON_BASE` on equal trees, dirty worktrees, lost push replies and restart recovery. No new test framework is needed.

## 5. Questions this fork still needs to make concrete

- **Q1. What execution capacity will the implementation actually have?** The architecture scales beyond two prefixes, but the honest initial window depends on whether the operator wants another isolated runner or wants to stay on this host. No current evidence proves that concurrent full suites here retain their solo duration. This changes cost and the forecast, not the safety algorithm.
- **Q3. Is the target queue service or time until every originally queued leaf lands after repairs?** The measured red sample contains real defects and stale proof. Predicting the latter requires repair/re-review durations and the actual eleven leaves. The data supports a materially faster verification service, not a guarantee that defective work lands on a fixed deadline.
