Akrogon · operator guide

Two agents build it. You decide what.

Akrogon runs software work through two AI agents from different vendors. They plan, build, review, and merge on their own. You write down what you want, answer questions, and read the result. This guide explains every moving part from first principles, then walks through a normal working day.

01 · The idea

One file says where the work is. Everything else follows from that.

You write a short description of one piece of work into a folder. Akrogon opens a terminal tab with two agents in it. Agent B (Codex) plans and builds. Agent A (Claude) reviews and merges. They hand the work back and forth through a fixed list of phases until it lands on main.

There is no server and no database. The phase of every piece of work is one line in a file called state.yaml. When an agent finishes, it changes that line with one command. A hook notices, reads the file, and prompts whoever is next.

You are the operator. You decide what gets built, answer questions during planning, and read reviews when something fails. You do not watch the agents work.

file → hook → next → prompt · the whole loop

Why two vendors

One model reviewing its own work misses the same things twice. In the first real run, A found only style nits by reading the code. B found four real bugs by running it. Two different minds catch more.

Why a file and not a program

A running program can be in a wrong state. A file cannot. If akrogon crashes, nothing is lost. If you want to change what happens next, you edit one line. Both agents, git, and you can all read the same file with nothing running.

02 · Every moving part

The words, one at a time

Twelve words cover the whole system. Read them once and the rest of this guide reads easily.

03 · The state file

state.yaml, line by line

You write the first seven lines when you create a leaf. Akrogon writes the rest. You may edit any of it by hand when nothing is running.

slug: query-api            # name, also the branch name
phase: plan.synthesis      # where it is right now
created: 2026-09-11
priority: "n"
repo: my-app               # which registered repo
debate: "no"               # yes = both plan, then argue
blocked-by:                # must be merged first
  - build-index
hand_built: false          # true = next skips it

# written by akrogon from here down
attempts: { A: 0, B: 1 }
done: []
fix_rounds: 0
verdict: {}
tab: w8:tE
worktree: /home/me/app/issues/worktrees/query-api
pane: { A: w8:pN, B: w8:pP }
slot: B
prompted: { B: session-id }
  • slugUnique across the repo. Lowercase and dashes. Becomes the git branch and the tab label.
  • phaseThe only signal. One of the nine phases in section 08.
  • debateWith yes, both agents write a plan alone, reply once, then B writes the final plan. With no, B just plans. Start phase is plan.positions for yes, plan.synthesis for no.
  • blocked-byLeaf slugs. The leaf cannot start until every one of them is merged. This is the only ordering rule.
  • hand_builtSet true to drive a leaf yourself. next ignores it completely.
  • attemptsHow many times each slot was prompted in this phase. Resets on every phase change. At 3, the leaf fails.
  • doneSlots that reported this phase. When every required slot is in it, the phase moves.
  • fix_roundsHow many review→fix loops so far. Capped by repo config.
  • verdictWhat each reviewer said: ready, nits, or fix.
  • tab · paneWhich herdr tab and panes belong to this leaf.
  • worktreeWhere the branch is checked out.
04 · Install once

One command per machine

Needs bun, git, flock, herdr, the agent CLIs, and an authenticated gh if you use GitHub issues.

cd ~/Work/infra/akrogon
bun install
bun src/akrogon.ts install
01

Links the command

~/.local/bin/akrogon points at the source. Edit src/ and the change is live. Make sure ~/.local/bin is on your PATH.

02

Links the skills

Every folder in skills/ is linked into each agent's skill folder. Both agents read the same skill text. When a skill changes on main, every agent sees it on its next prompt.

03

Links the plugin

The herdr plugin runs akrogon pull --all and akrogon next --all at herdr start, and akrogon next whenever an agent changes status or a pane exits.

If a destination already exists and is not the right link, install prints the rm commands and stops. Run them and install again. Update the tool with git pull in the akrogon checkout. Nothing needs reinstalling.

Global config

Lives at the akrogon repo root, config.yaml. It says which agents run, how to launch them, and which repos exist.

max_active: 3                 # at most 3 leaves running at once, machine-wide
slots:
  a: { harness: claude, model: claude-fable-5-1, effort: medium }
  b: { harness: codex,  model: gpt-6-astra,      effort: medium }
harnesses:                    # how to launch each agent, {model} and {effort} filled in
  claude: claude --model {model} --effort {effort} --dangerously-skip-permissions
  codex: codex -m {model} -c model_reasoning_effort={effort} -a never -s danger-full-access
toolkits:
  typescript: bun:test
repos:
  akrogon: /home/me/Work/infra/akrogon
  my-app: /home/me/Work/my-app
Why max_active

Each active leaf is two agents spending tokens plus a worktree on disk. Three is a lot. The limit counts across every registered repo, not per repo. Raise it when you have the budget.

05 · Set up a repo

Once per repo you want agents in

The easy way: open your own agent session in the repo and run the init-issues skill. It inspects the repo, proposes the settings below, and calls the command for you. The direct way, when the repo has no tests yet:

cd ~/Work/my-app
akrogon init --toolkit typescript="bun test"
akrogon config                 # prints what an agent will see

Init writes issues/config.yaml, creates issues/open/ and learnings/LESSONS.md, adds ignore lines for worktrees, seeds, and lock files, and registers the repo in the global config under its folder name. Running it again keeps existing choices.

Repo config

remote: origin
default_branch: main
worktree_root: issues/worktrees
rebuttal: true          # in debate mode, do A and B get one reply each
fix_rounds: 3           # review→fix loops before the leaf is marked failed
implement: subagents    # B may delegate to workers, or "inline" to do it alone
checks:                 # every one must pass before review and before merge
  format: bun run format
  test: bun test
  typecheck: bun run typecheck
  test_changed: ': "${AKROGON_BASE:?AKROGON_BASE is required}" && bun test --changed="$AKROGON_BASE"'
advisory: []            # commands whose failure is reported but does not block
grounding:
  index: REFERENCE.md   # a short map of the repo that planners read first
broadcast:              # optional: post a summary when an issue completes
  discord:
    webhook_env: [DISCORD_WEBHOOK_URL, DISCORD_WEBHOOK_URL_2]

Secrets like webhook URLs go in ~/.config/akrogon/env, one NAME=value per line, never in the repo. AKROGON_BASE is the commit the leaf branched from. Akrogon sets it in every pane so a changed-tests command can compare against it.

06 · Create work

Four doors in, from most to least planning

All four are things you do in your own agent session, with you present. The loop never decides what to build.

You haveUseYou get
A goal, but the route is unclear and will take many sessions/chart-issuesA chart of decisions you settle one by one. It ends by writing a set of leaves with blocked-by wired between them.
One clear thing to build/create-issueA short interview, then one leaf: brief.md, design.md, state.yaml.
One observation: "X happened, Y should have"/seed-issueA GitHub issue in the right repo. No planning yet.
Open GitHub issuesakrogon pullOne file per issue in issues/seeds/. Runs at every herdr start. Import a seed through /create-issue. When the leaf merges, the GitHub issue is closed with the commit.
Why decide before agents start

A decision made during planning gets re-argued in every later phase. A decision written in the brief is settled. Agents build faster when there is nothing left to argue about.

Or just write the files

The minimum is a brief.md saying what and why, and a state.yaml. Commit them in the registered checkout and push.

mkdir -p issues/open/rename-flag
cat > issues/open/rename-flag/brief.md <<'EOF'
# Rename --verbose to --debug

The flag does debug logging, not verbose output. Rename it, keep --verbose as an alias for one release.

Done when: `mytool --debug` works, `mytool --verbose` prints a deprecation line, tests cover both.
EOF
cat > issues/open/rename-flag/state.yaml <<'EOF'
slug: rename-flag
phase: plan.synthesis
created: 2026-09-11
priority: "n"
repo: my-app
debate: "no"
blocked-by: []
EOF
akrogon sync

Ordering with blocked-by

If leaf api must land before leaf ui, put blocked-by: [api] in the ui state. That is the whole ordering system. Leaves with no blockers start whenever there is capacity, in parallel. When a leaf merges, the leaves that named it become free on the next next. The list itself is never edited by the tool.

The chart handoff writes these lists for you. When you write leaves by hand, you write them.

07 · How next picks work

The start button, and what it actually does

akrogon next --all

That is the whole start button. In order:

  1. For every registered repo, find every leaf at merged. Close its tab if still open, remove its worktree and branch.
  2. For every registered repo, walk issues/open/ in folder order and look at every leaf.
  3. Skip a leaf if it is merged, failed, or hand_built. Skip it if any slug in blocked-by is not merged.
  4. If the leaf already has a tab, prompt whoever its phase needs, if they are idle.
  5. If it has no tab and fewer than max_active leaves are running anywhere, create the worktree and branch, open a tab with two panes, start the agent, and send one prompt.
  6. Exit.

The prompt is always four words: skill, slug, slot, phase. For example plan-issue rename-flag slot=B phase=plan.synthesis. The agent reads the skill file and does the rest.

Nothing keeps running afterwards. The herdr hook calls akrogon next again every time an agent goes idle. That call finds the leaf that owns the pane, reads its new phase, and prompts whoever is next. When a leaf reaches merged, that same call sweeps every repo once, so leaves waiting on it start right away.

The four forms

CommandLooks atUse it when
akrogon next --allCleans up every merged leaf, then every leaf in every registered repo.Starting the day by hand. Herdr runs this itself at startup.
akrogon nextEvery leaf in the repo you are standing in.A quick nudge from inside a repo.
akrogon next <folder>Only leaves under that folder. The folder can be an epic, an issue, or one leaf.You want only this epic to take the free seats right now.
akrogon next <slug>Exactly this leaf. Prints the reason if it cannot start: blocked, hand-built, no seat.One leaf is stuck and you want to know why.

How order is decided

There is no priority field the tool reads. The priority line in state.yaml is for you. Order comes from two things only:

  • blocked-by. A leaf waits until every named leaf is merged. This is the strong ordering.
  • Folder scan. Among leaves that are ready, the tool starts them in folder order until the seats are full. Rename folders if you care which ready leaf gets the last seat.

An epic is not a queue. If five leaves in an epic have no blockers, they all count as ready and race for seats along with every other ready leaf in every repo. If you want an epic to run in a fixed order, chain the leaves with blocked-by.

The prose in EPIC.md, ISSUE.md, or brief.md is for humans and planners. The tool never reads it for ordering.

08 · The phases

Nine phases, in the order they happen

Every phase names who works, what skill they follow, and what moves it forward. A leaf with debate: "no" skips the first two.

  1. plan.positionsA + B

    plan-issue. Each writes a plan alone, not reading the other's. Then → plan.rebuttal, or straight to synthesis if rebuttal: false.

  2. plan.rebuttalA + B

    plan-issue. Each reads the other's plan and replies once. Then → plan.synthesis.

  3. plan.synthesisB

    plan-issue. Writes the final plan.md, or the only plan when debate is off. Then → implement.

  4. implementB

    implement-issue. Builds it in the worktree, runs every check, writes implementation/brief.md, commits the code on the branch. Then → check.review. The move is refused if the worktree is dirty or if any file under issues/ is on the branch.

  5. check.reviewA + B

    check-issue. Each reviews the diff and writes review-A.md or review-B.md with a verdict: ready, nits, or fix. If nobody said fix → merge. Otherwise → check.fix.

  6. check.fixB

    implement-issue. Repairs the listed defects. Then → check.review, but only A reviews this time. Each loop adds one to fix_rounds. Past the cap → failed.

  7. mergeA

    merge-issue. Rebases the branch on origin/main, runs every check, pushes the branch as the new main, records lessons. Then → merged. A conflict or red check → check.fix instead.

  8. mergednobody

    Terminal. When every leaf in the issue is merged, the issue folder moves to issues/closed/, linked GitHub issues are closed, and the broadcast goes out. The tab closes itself. The worktree and branch are removed at the next startup sweep.

  9. failedyou

    Waits. Read the reviews and the diagnosis paragraph A appended to plan.md, then send it back with akrogon phase <slug> implement.

How a phase moves

An agent ends its phase by running one command. This is the only way a phase changes.

akrogon phase rename-flag check.review --slot B
akrogon phase rename-flag merge --slot A --verdict nits

The command refuses illegal moves, refuses a slot that already reported, and moves the phase only when every required slot has reported. Until then it prints recorded and waits for the other slot. That is why you sometimes see "transition refused" in a pane: the agent tried twice, the second was rejected, and that is correct.

Why re-review after a fix uses only A

B just wrote the fix. B reviewing its own fix costs tokens and adds little. A checks the repair diff only. If A says fix again, B goes another round, up to fix_rounds.

Why a stuck agent's work goes to the other pane

If a slot is prompted twice and does not start, the third try goes to the other agent's pane as a stand-in. A stuck agent is usually a stuck process, not a stuck task. The other pane is a fresh process with the same skill files. After three tries the leaf fails.

09 · Where files live

The leaf branch carries code. The checkout carries issues.

Two places write to the repo at the same time. Agents build on the leaf branch inside the worktree. Akrogon and the skills write plans, reviews, state, and the log inside your registered checkout, on main.

The rule that keeps them from colliding: nothing under issues/ is ever committed on a leaf branch. The phase command checks this at handoff and refuses if it finds one.

So after a merge, main on the remote has the new code, and your checkout has new issue files that are not pushed yet. One command reconciles the two.

akrogon sync

It stages everything in the checkout, commits it as sync issues if anything is staged, pulls with rebase, and pushes. Agent work is never overwritten. Your issue files ride on top of it.

two writers, two folders, one remote · the branch never touches issues/

Why this rule exists

Before it, plans and reviews were committed on the leaf branch and also in the checkout. Every merge produced rebase conflicts on the same review file. Now each folder has exactly one writer, and conflicts in issues/ cannot happen.

What each artifact is

10 · Merge and broadcast

How work lands, and how the team hears about it

Amerges and broadcasts
1message per issue, not per leaf
3sections: before, now, next
2000chars per discord message

A does not merge into your checkout. It fetches, rebases the leaf branch on origin/main, runs every check, and pushes the branch as the new main. If two leaves finish at once, git rejects the second push, A rebases again and retries. If the rebase conflicts, the leaf goes to check.fix, B resolves it, A re-checks.

After the push, A runs akrogon phase <slug> merged. If that was the last leaf of the issue, the command prints issue complete, moves the folder to issues/closed/, and closes any linked GitHub issue. A then sends the broadcast itself, in the same session, and closes its own tab as its very last act.

The broadcast is written for every team member, not just developers. It always has the same shape:

## 🧪 my-app: Search results load in under a second (09/11/26)

**Before**
- Searching a large project took several seconds and sometimes timed out.

**Now**
- Results come back in under a second because the index is built once and reused.

**Next**
- Nothing to do. The change is live after the next deploy.

Detail scales with size. A small issue gets one or two bullets per section. An epic gets more, and the sender splits long messages at section boundaries. The repo name always comes first in the title. Targets are the names listed under broadcast.discord.webhook_env, and the values live only in ~/.config/akrogon/env.

A failed broadcast is visible in the pane but does not reopen the issue. The merge is already done.

11 · A working day

What you actually do, hour by hour

Morning

start

Open herdr. The plugin runs akrogon pull --all and akrogon next --all. Merged leaves from yesterday are cleaned up, new GitHub issues land in issues/seeds/, and every ready leaf starts up to the seat limit. If you would rather choose what starts, set max_active: 0 before opening herdr, then raise it and run akrogon next <folder> yourself.

Bring your checkout up to date with the code that merged overnight:

akrogon sync

Adding work

any time

In your own agent session, run /create-issue for one clear thing, or /chart-issues for a route you cannot see yet. Or write the two files by hand. Then akrogon sync. The next hook call, or akrogon next, picks it up.

Watching

glance, do not stare
akrogon status                 # every repo, every open leaf, phase, age, blockers
akrogon status rename-flag     # one leaf's state and last ten log lines
herdr plugin log list --plugin akrogon   # why the hook did or did not act

Or read the tab. A on the left, B on the right. Or read the leaf folder: plan.md, review-A.md, review-B.md.

Answering

when asked

An agent showing a startup dialog or a permission prompt is blocked on a human. Answer it in the pane. The hook sees the status change and continues. No attempt is counted against the leaf.

A failed leaf shows a herdr notification. Read review-A.md and the last paragraph of plan.md, fix the brief if the brief was the problem, then:

akrogon phase rename-flag implement

Evening

stop

Close herdr, or just leave it. Every leaf's phase is in its file. Nothing is lost. Tomorrow's startup sweep resumes from the files. The last tab that merged closes itself. If one is still open, the startup sweep closes it.

Run akrogon sync once more so the day's issue files are on the remote.

12 · Use cases

The questions that come up, answered

I have one epic and one normal issue. Can they run in parallel?

Yes, by default. Every ready leaf in every repo competes for the same seats. If the epic has three unblocked leaves and max_active is 3, the epic can take all three and the issue waits for the first merge. The tool does not balance between folders.

I only want this epic to use the free seats

akrogon next issues/open/search

Only leaves under that folder are considered. The folder can be an epic, an issue, or a single leaf. Two catches: the hook still sweeps everything when a leaf merges, and the startup next --all starts every ready leaf. To keep a leaf from starting at all, give it a blocker or set hand_built: true.

I want to stop today and do it in a different order tomorrow

Nothing is remembered between runs except state.yaml. Edit the blocked-by lists of the leaves that have not started. Add a slug to make one wait, remove a slug to free one. Then run next. Two limits: a leaf that already has a tab keeps running whatever you edit, and you can only name leaves, so to make issue 2 wait for a whole epic, name the epic's last leaf.

I want to run one leaf by hand

Set hand_built: true. next skips it. Do the work yourself in a branch, and move its phase with the same akrogon phase commands the agents use. Useful for the first leaf of a new repo, before you trust the loop there.

I want to send a leaf back

Edit phase in state.yaml to implement, then akrogon next <slug>. The state file is the only truth. If the leaf is failed, use akrogon phase <slug> implement instead, which also resets the fix counter.

I want to stop one running leaf

Close its tab. Nothing restarts it until the next next, and that will reopen a tab and re-prompt the current phase. If you want it to stay stopped, add a blocker or set hand_built: true first.

I want to pause everything

Set max_active: 0 in the global config. Running leaves finish their current phase and then nothing new is prompted for leaves without a tab. Leaves that already have tabs keep going.

Two leaves touched the same lines

Nothing to do. The merge rebase conflicts, the leaf goes to check.fix, B resolves it in the same worktree, A re-checks the repair, then merges.

A skill needs changing

Skills only change through akrogon leaves in the akrogon repo. File a seed there. Once merged, every agent on the machine sees the new text at its next prompt, because the skill folders are symlinks.

13 · Limits you must know

Things that will surprise you if you do not know them

ordering

A running leaf ignores blocked-by edits

The list is read once, when next decides whether to start the leaf. After that the tab exists and the list is never read again. Change order before running next, not after.

ordering

blocked-by only names leaves

Not epics, not issues. To wait for a whole epic, name its last leaf. One line in one file.

capacity

max_active is machine-wide, first come first served

Counted across every registered repo. Ready leaves start in folder order. One epic can take every seat. Priority in state.yaml is not read.

capacity

Folder targeting does not reserve seats

next <folder> starts only that folder's leaves now, but the next hook call sweeps everything, and startup runs --all.

cleanup

Cleanup happens only at startup or with --all

Herdr's idle signal flickers between tool calls, so nothing destructive is tied to it. A merge closes its own tab. Worktrees and branches wait for next --all or the next herdr start.

cleanup

The last tab may stay open

If a merge session dies before its final close, the tab lingers until the next startup sweep. It is harmless. Close it by hand or run akrogon next --all.

files

Issue files never go on a leaf branch

The handoff to review refuses any file under issues/ on the branch, and refuses a dirty worktree. Agents write issue files only in the registered checkout.

files

sync commits everything in the checkout

akrogon sync stages all changes and commits them as sync issues. Do not leave unrelated half-done code in the registered checkout.

agents

Blocked is not counted, stuck is

A permission dialog waits for you forever with no penalty. A prompt that does not take counts one attempt. Three attempts and the leaf fails.

agents

Blind positions cannot ask the peer

In plan.positions the two plans must be independent. Peer questions are allowed in every other phase, one per need, through a file under questions/.

broadcast

Only the merge slot broadcasts

Never a subagent, never a cheaper model, because the tab closes as soon as the pane goes idle. A failed broadcast does not reopen the issue.

tests

bun test in the akrogon root also scans worktrees

Test counts change while leaves are live. Run bun test tests for the root suite only.

15 · Nits, lessons, seeds

Where leftovers go

Reviews produce three kinds of leftovers. Each has exactly one exit, so nothing piles up.

nit

A finding that is not a defect

Stays in the review file. At merge, A decides: a reusable rule becomes a lesson, real work becomes a seed.

lesson

One line plus a history file

One line in learnings/LESSONS.md naming mechanism, date, and history path, plus a dated file under learnings/history/. Every plan reads the lines. A lesson is deleted when a leaf applies it, or at the next chart when it has stopped being useful.

seed

A GitHub issue

Filed with seed-issue. If it is about a skill, it goes to the akrogon repo, because skills only change through akrogon leaves. Otherwise it goes to the repo the work is in.

Why agents do not fix nits as they see them

Then every review becomes a small implementation with no plan and no second reviewer. Nits become seeds, seeds become leaves, leaves get the full loop.

16 · Cheat sheet

Everything on one screen

# once per machine
bun install && bun src/akrogon.ts install

# once per repo
akrogon init --toolkit typescript="bun test"     # or the init-issues skill
akrogon config                                    # what agents will see

# create work, in your own agent session
/chart-issues     /create-issue     /seed-issue
akrogon pull                                      # GitHub issues → issues/seeds/
akrogon sync                                      # commit + rebase + push the checkout

# run
akrogon next --all                                # cleanup, then start everything ready
akrogon next <folder>                             # only this epic, issue, or leaf
akrogon next <slug>                               # one leaf, with the reason if it cannot
akrogon phase <slug> <phase> --slot A|B [--verdict ready|nits|fix]

# look
akrogon status [<slug>]
tail issues/log.jsonl
herdr plugin log list --plugin akrogon

# order
blocked-by: [other-leaf]      # in state.yaml, before the leaf starts
hand_built: true              # next skips it
max_active: 0                 # in config.yaml, pause new starts

# files
~/Work/infra/akrogon/config.yaml      # slots, harnesses, repos, max_active
<repo>/issues/config.yaml             # checks, fix_rounds, broadcast
~/.config/akrogon/env                 # secrets, one NAME=value per line
akrogon · guide · state.yaml is the only truth
