Akrogon Guide

How to run software work through two AI agents that plan, build, review, and merge on their own, while you make the decisions.

1. The idea in one minute

You write down a piece of work. Akrogon gives it to two agents from different vendors, one called A (Claude) and one called B (Codex). B does most of the building. A reviews and merges. They pass the work back and forth through a small set of phases until it lands on main.

You are the operator. You decide what gets built and answer questions during planning. You do not babysit the agents. When they are done, the branch is on main and the terminal tab is gone.

Why two vendors? One model reviewing its own work misses the same things twice. In the first real run, A found only style nits by reading the code while B found four real bugs by running it. Two different minds catch more.

2. The pieces

WordWhat it is
RepoA git checkout you registered with akrogon. It has an issues/ folder.
IssueA folder under issues/open/. One unit of intent, like "add a status command".
LeafAny folder that has a state.yaml. This is the thing agents actually work on. An issue is usually one leaf. A big issue can be a folder of several leaves.
PhaseOne word in state.yaml that says where the leaf is: planning, implementing, reviewing, merging. This is the only signal. There is no database.
SlotA or B. Which agent a phase needs.
TabA terminal tab in herdr, one per active leaf, with two panes: A on the left, B on the right.
WorktreeA separate checkout of the repo on a branch named after the leaf, under issues/worktrees/<slug>. Agents work there so they never touch your main checkout.
SkillThe instructions an agent follows in a phase, like plan-issue or check-issue. Installed into each agent's skill folder.
Why is the phase in a file? Because a file can be read by you, by git, and by both agents with no server running. If akrogon crashes, nothing is lost. If you want to change what happens next, you edit one line.

A leaf's state.yaml, explained

slug: status              # the leaf's name, also its branch name
phase: plan.synthesis     # where it is right now
created: 2026-09-09
priority: "n"
repo: akrogon             # which registered repo it belongs to
debate: "no"              # yes = A and B both plan first, then argue
blocked-by:               # leaves that must be merged before this starts
  - command
  - core-skills
attempts: { A: 0, B: 1 }  # how many times each slot was prompted this phase
done: []                  # slots that finished this phase
fix_rounds: 0             # how many review/fix loops so far
verdict: {}               # review results, filled by check.review
tab: w8:tE                # filled in by akrogon when it starts the leaf
worktree: /home/ivan/Work/infra/akrogon/issues/worktrees/status
pane: { A: w8:pN, B: w8:pP }
slot: B                   # who was prompted last

You write the first six fields when you create the leaf. Akrogon manages the rest.

3. Install

Once per machine. Needs bun, git, and herdr.

cd ~/Work/infra/akrogon
bun install
bun run src/akrogon.ts install

This creates:

  • ~/.local/bin/akrogon, a link to the source. Edits to src/ are live immediately.
  • Links from every folder in skills/ into ~/.claude/skills and ~/.agents/skills, so both agents read the same skill text.
  • The herdr plugin, which calls akrogon next whenever an agent goes idle or a pane exits.

If a destination already exists and is not the right link, install prints rm commands and stops. Run them and install again.

Why symlinks? One copy of the truth. When a leaf merges a skill change, every agent on the machine sees it on its next prompt with no reinstall.

Global config

Lives at the akrogon repo root, config.yaml. It says which agents run and which repos exist.

max_active: 3                 # at most 3 leaves running at once
slots:
  a: { harness: claude, model: claude-fable-5-1, effort: medium }
  b: { harness: codex,  model: gpt-6-astra,      effort: medium }
harnesses:                    # how to launch each agent; {model} and {effort} are filled in
  claude: claude --model {model} --effort {effort} --dangerously-skip-permissions
  codex: codex -m {model} -c model_reasoning_effort={effort} -a never -s danger-full-access
repos:
  akrogon: /home/ivan/Work/infra/akrogon
Why max_active? Each active leaf is two agents burning tokens and a git worktree on disk. Three at once is a lot. Raise it when you have the budget.

4. Set up a repo

Once per repo you want agents to work in.

cd ~/Work/my-app
akrogon init --toolkit typescript="bun test"

This writes issues/config.yaml, creates issues/open/ and learnings/LESSONS.md, adds the ignore lines for worktrees and lock files, and registers the repo in the global config under its folder name.

Repo config

remote: origin
default_branch: main
worktree_root: issues/worktrees
rebuttal: true          # in debate mode, do A and B get one reply to each other's plan
fix_rounds: 3           # how many review/fix loops before the leaf is marked failed
implement: subagents    # B may delegate to workers, or "inline" to do it alone
checks:                 # every one of these must pass before review and before merge
  format: bun run format
  test: bun test
  typecheck: bun run typecheck
advisory: []            # commands whose failure is reported but does not block
grounding: none         # or { index: docs/INDEX.md }, a two-level map of the repo that planners read first
broadcast:              # optional: post a summary on merge
  discord:
    webhook_env: [DISCORD_WEBHOOK_URL]

Secrets like the webhook URL go in ~/.config/akrogon/env, one NAME=value per line, never in the repo.

Check what an agent will see with:

akrogon config

5. Create work

Three ways in, from most to least planning.

You haveUseWhat you get
A goal, but the route is unclear and spans many sessions/chart-issuesA chart of decisions you settle one by one with an agent, ending in a set of leaves with blocked-by wiring
One clear thing to build/create-issueA short interview, then one leaf: brief.md, design.md, state.yaml
One observation, "X happened, Y should have"/seed-issueA seed report to import later through create-issue, or a GitHub issue

All three are things you run in your own agent session, by hand, with you present. The loop never plans intent for you.

Why decide before agents start? A decision made during planning gets re-argued in every later phase. A decision written in the brief is settled. Agents build faster when there is nothing to argue about.

Example: a small leaf by hand

You can also just write the files. The minimum is brief.md saying what and why, and a state.yaml:

mkdir -p issues/open/rename-flag
cat > issues/open/rename-flag/brief.md <<'EOF'
# Rename --verbose to --debug

The flag does debug logging, not verbose output. Rename it, keep --verbose as an alias for one release.

Done when: `mytool --debug` works, `mytool --verbose` prints a deprecation line, tests cover both.
EOF
cat > issues/open/rename-flag/state.yaml <<'EOF'
slug: rename-flag
phase: plan.synthesis
created: 2026-09-11
priority: "n"
repo: my-app
debate: "no"
blocked-by: []
EOF
git add issues && git commit -m "issue: rename-flag"

Start phase is plan.synthesis when debate: "no", and plan.positions when debate: "yes".

Ordering with blocked-by

If leaf api must land before leaf ui, put blocked-by: [api] in the ui state. That is the only ordering mechanism. Leaves with no blockers start whenever there is capacity, in parallel.

6. Run the loop

akrogon next --all

That is the whole start button. What it does, in order:

  1. Reads every leaf in every registered repo.
  2. For each leaf that is not merged, not failed, not hand-built, and whose blockers are all merged: if fewer than max_active leaves are running, create the worktree and branch, open a tab with two panes, and start the agent the current phase needs.
  3. Sends one prompt: the skill name, the slug, the slot, the phase. For example plan-issue status slot=B phase=plan.synthesis.
  4. Exits.

Nothing keeps running. The herdr plugin calls akrogon next again every time an agent goes idle. That call sees the new phase in state.yaml and prompts whoever is next. That is the entire loop: file says phase, hook fires, next reads file, next prompts.

Why no daemon? A daemon can be in a wrong state. A file plus a hook cannot. If you close herdr and open it again, the plugin's startup hook runs next --all and everything resumes from the files.

Other forms

akrogon next              # leaves under the current folder
akrogon next status       # exactly this leaf; errors if it cannot start
akrogon next issues/open/akrogon-loop   # every leaf under a folder

7. What happens in each phase

PhaseWhoSkillWhat they doThen
plan.positionsA and Bplan-issueEach writes a plan alone, not reading the other'splan.rebuttal
plan.rebuttalA and Bplan-issueEach reads the other's plan and replies onceplan.synthesis
plan.synthesisBplan-issueWrites the final plan.md, or the only plan if debate is offimplement
implementBimplement-issueBuilds it on the leaf branch, runs checks, writes implementation/brief.mdcheck.review
check.reviewA and Bcheck-issueEach reviews the diff and writes review-A.md or review-B.md with a verdict: ready, nits, or fixmerge if nobody said fix, else check.fix
check.fixBimplement-issueFixes the listed defectscheck.review, A only this time
mergeAmerge-issueRebases the branch on origin/main, runs checks, pushes, records lessonsmerged
mergednobodyTab closed, worktree and branch removed, issue folder moved to issues/closed when all its leaves are merged
failednobodyWaits for youimplement, when you say so

An agent ends its phase by running one command, which is the only way the phase changes:

akrogon phase status implement --slot B
akrogon phase status check.review --slot A --verdict nits

The command refuses illegal moves, refuses a slot that already reported, and moves the phase only when every required slot has reported. That is why you sometimes see "transition refused" in a pane: the agent tried twice, the second was rejected, and that is correct.

Why does check.review after a fix use only A? B just wrote the fix. Having B review its own fix adds cost and little signal. A re-checks, and if A says fix again, B goes another round, up to fix_rounds.

Merging without a local main

A does not merge into your checkout. It rebases the leaf branch on origin/main, runs the checks, and pushes the branch as the new main. If two leaves finish at once, the second push is rejected by git, A rebases again and retries. If the rebase has a conflict, the leaf goes to check.fix and B resolves it, then A re-checks.

Your local main is therefore behind after every merge. Pull when you want it:

git pull --rebase

A full example, start to finish

  1. You commit the rename-flag leaf and push.
  2. akrogon next --all. A tab named rename-flag appears. Codex starts in the right pane and gets plan-issue rename-flag slot=B phase=plan.synthesis.
  3. Codex writes plan.md and runs akrogon phase rename-flag implement --slot B. It goes idle. The hook fires.
  4. next reads phase implement, prompts Codex again with implement-issue. Codex builds, runs the three checks, commits on the branch, moves the phase to check.review.
  5. next prompts both panes with check-issue. Claude starts in the left pane. Each reviews and reports a verdict. Say Claude says nits and Codex says fix.
  6. Phase goes to check.fix. Codex fixes, moves to check.review. Only Claude is prompted this time and says ready.
  7. Phase goes to merge. Claude rebases, runs checks, pushes main, moves to merged.
  8. next sees merged: closes the tab, removes the worktree and branch, moves the issue folder to issues/closed.
  9. You git pull --rebase.

8. Watching and intervening

Everything is visible in three places:

  • The tab. Left pane A, right pane B. Read it like any terminal.
  • The leaf folder. state.yaml for where it is, plan.md, implementation/brief.md, review-A.md, review-B.md for what was done.
  • issues/log.jsonl. One line per phase change with time, slot, commit, and diff size.

To see why the hook did or did not act:

herdr plugin log list --plugin akrogon

Changing course

Edit state.yaml. It is the only truth. To send a leaf back to implementation, set phase: implement and run akrogon next <slug>. To stop a leaf, close its tab; nothing will restart it until the next next. To pause everything, set max_active: 0.

Hand-built leaves

Set hand_built: true in a leaf you are driving yourself. next skips it entirely. You move its phase with akrogon phase the same way agents do. Useful for the first leaves of a new repo, before you trust the loop.

9. When things go wrong

You seeWhat it meansDo
An agent showing a startup dialogThe agent is blocked on a prompt only a human can answerAnswer it. The hook sees the status change and continues. No attempt is counted.
attempts climbing to 2The prompt did not take, twiceLook at the pane. The third try goes to the other agent's pane as a stand-in. After that the leaf is failed.
phase: failedThree fix rounds or three prompt failuresRead the reviews, decide, then akrogon phase <slug> implement to send it back.
Leaf never startsA blocker is not merged, or max_active is reachedakrogon next <slug> prints the reason.

Merge conflictTwo leaves touched the same linesNothing. It goes to check.fix, B resolves, A re-checks.
"Transition refused"The agent called phase twiceNothing. The first call worked.
Tests count changes between runsbun test in the akrogon root also scans live worktreesCosmetic. Scope the test runner if it bothers you.
Why does the loop hand a slot to the other agent's pane? A stuck agent is usually a stuck harness, not a stuck task. The other pane is a fresh process with the same skill files. It is cheaper than failing the leaf.

10. Nits, lessons, seeds

Reviews produce three kinds of leftovers, and each has one exit so nothing piles up.

  • Nit. A reviewer finding that is not a defect. Stays in the review file. At merge, A decides: if it is a reusable rule, it becomes a lesson; if it is real work, it becomes a seed.
  • Lesson. One line in learnings/LESSONS.md plus a dated file under learnings/history/. Every plan-issue run reads the lines. A lesson is deleted when a leaf applies it, or at the next chart when it has stopped being useful.
  • Seed. A GitHub issue filed with seed-issue. If a lesson is about a skill, the seed goes to the akrogon repo, because skills only change through akrogon leaves. Otherwise it goes to the repo the work is in.
Why not just let agents fix nits as they see them? Then every review becomes a small implementation with no plan and no second reviewer. Nits become seeds, seeds become leaves, leaves get the full loop.

11. Cheat sheet

# one time
bun install && bun run src/akrogon.ts install

# per repo
akrogon init --toolkit typescript="bun test"
akrogon config                      # what agents will see

# work
/create-issue   /chart-issues   /seed-issue    # in your own agent session
akrogon next --all                  # start everything that can start
akrogon next <slug>                 # start or nudge one leaf, with reasons
akrogon phase <slug> <phase> --slot A|B [--verdict ready|nits|fix]

# look
cat issues/open/**/state.yaml
tail issues/log.jsonl
herdr plugin log list --plugin akrogon

# after merges
git pull --rebase
