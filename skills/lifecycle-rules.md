# Lifecycle rules

The four rules below are held once for the plan-issue, implement-issue, check-issue and merge-issue seats. Each skill reaches this file through a `lifecycle-rules.md` link inside its own folder and states beside that link what is its own: its seat's record file, its red-check command form and any seat-only clauses. "The seat's record file" and "the seat's operator-blocker stop" below mean the file and the stop its own skill names. This file holds no relative links: a file or section it names, such as seed-issue's `## Lifecycle filing` section, is found through the skill that holds it.

## Grant reuse and count lines

A seat reuses `grants[]` for the operations they cover, within their bounds; before each covered operation, paid model launches included, it compares operation, target, identity and bounds with the grant, records the grant reference, results and created IDs in its pass artifact, never widens it, and treats anything outside it as an operator blocker under the seat's operator-blocker stop. Every covered launch runs through `akrogon run-check` and one that reaches its paid or live stage counts against its bound's unit, whatever its outcome and whatever the bound's wording; "known-good" never narrows a bound. A seat writes one count line per launch in its record file before the launch — the grant entry it draws on, the bound, the count so far and the unit — and completes it after the launch with the outcome, IDs, sessions and cost when known; before its first launch it reads the count lines in the leaf's earlier artifacts, and prior use that cannot be established is written as unknown, never as a number. Before a launch past a repeat-count bound of a paid operation a seat writes a warning in its record file and its visible reply and continues; live-change repeat bounds, spend caps, operation, target, identity, effects, expiry and `stop_line` clauses keep their operator-blocker stop, and the stop wins when both apply; unknown prior use warns for a repeat count, and when it prevents establishing compliance with a stop-type bound the seat takes the operator-blocker stop.

## Environment files and producer keys

A seat never opens, prints, appends to, or writes `.env` or `.env.*` with any tool: declared checks and live operations consume values only inside a run process such as `bun --env-file=<file> <script>` printing only results, never values, and presence is checked with the `Missing:` lines of `akrogon status <slug>`, where absent or empty counts as missing, ending the pass with the seat's operator-blocker stop when a required value is absent. A seat's own exception is named beside its skill's link to this file.

For the plan-issue and implement-issue seats only, a producer's key is saved only through the operation recorded in `produces[].save` (entry point, inspected revision, non-secret `args`, key `name`, the `holder` repo's real file and the private `value_source`): the value passes privately to it, writes the holder repo's real `.env` file and never the worktree `.env`, never returns through seat arguments, output or artifacts, and the new key is revoked when saving fails.

## Kept command output

A seat keeps command output only through `akrogon run-check --name <label> -- <cmd>` and cites the `check <label>: <exit> <path>` line it prints to stderr; a cited log is read back with `akrogon log <path>`. Exempt: the printed `checks` commands and `akrogon verify`, which already keep logs; `akrogon phase ... merged`, which moves its own owner; and coordination commands (fetch, push), whose errors are quoted in the report as text.

## Red check with no cause in the leaf's diff

Wherever a lifecycle seat meets a red test or check with no cause in the leaf's diff — a failing planned check for plan-issue, implement end and check.fix for implement-issue, check.review for check-issue, the merge turn for merge-issue — the same judgment applies, run through the seat's own command form and recorded in its record file.

A red with no cause in the leaf's diff (failing output plus `git diff "$AKROGON_BASE"...HEAD` shows no touched file or plausible cause; a judgment gate, never automatic) gets one retry of that same command, args and scope in the corresponding working directory — through `akrogon run-check` for the plan, implement and check seats, keeping each run's own exit status before any reporting pipeline such as `echo`, `grep` or `head`, and as one rerun of `akrogon verify --attempt <id>` on the unchanged head for the merge seat. A green retry marks the check `inconsistent` in the record file with both logs (at merge it goes on to `merged --check`); a red retry keeps the seat's repair path — blocks like any red check at check.review — until the known-red step clears it. A red that stays red runs the seat's known-red command on that head — `akrogon verify --known-red` for the plan, implement and check seats, `akrogon verify --attempt <id> --known-red` for the merge seat — which reruns the head when no completed red head run exists and then runs the base at the head's merge-base with the tracked default branch, skipping that base pass when the merge-base tree already holds a whole-green row — a green base never covers a red head, so it judges `fail` —, and the seat reads the head and base logs of each red command for runner completeness and causal fit, meaning one of: the red command logged a real test name and that name also fails on the base; or the red command's log names no test on the head and on the base, and the seat, having read both logs whole, finds that the head shows no failure the base lacks (judged in substance, never as exact text), that the command ended by its own verdict and was not killed, timed out or crashed, and that the leaf's diff holds no plausible cause. A command that ended by its own verdict with an ordinary error, a missing input or a load diagnostic is not excluded for naming no tests. When both logs exist but show too little to establish a cause, the seat withholds agreement and its blocking path applies. In both cases the leaf's own done-criteria proofs must pass on their own; a cover never stands in for them. A check recorded `blocked` in a verify receipt did not run, so the check named as its blocker is fixed first, except when the blocker is a known-red the judgment agrees with (named or nameless): the blocked check stays recorded as not run, is named as not run in the record file and never reported as passing, and does not by itself stop the leaf. A done-criterion whose proof is a blocked check cannot be shown, so that leaf stops under its existing rule. No blocked command is run by the seat or by `--known-red`. A known-red exit 0 counts as passing only when that judgment agrees, recorded in the record file beside the kept logs (a pass the merge seat agrees with goes on to `merged --check`); a failing exit or a disagreeing judgment keeps the repair path (takes the ending the merge skill names). When the known-red judgment agrees for a configured command, or when, for a command outside `checks` (a done-criterion proof or ad-hoc suite), the seat's own completed base run of the same command fails the same tests and the pass holds that evidence, the seat files that red through seed-issue's `## Lifecycle filing` section inside this pass and records the created or found URL, or the failing command and its error, in its record file; a green retry (`inconsistent`), a disagreeing judgment, or a killed or incomplete base run is not filed as a base red; filing changes no verification status and adds no proof run, so a red done-criterion stays blocking.
