# Implement issue

Leaf prompts are `implement-issue <slug> slot=A phase=implement leaf=<folder>` or `phase=check.fix` with the same `leaf=`; a prompt without a leaf is a standalone task in the current checkout with this session as A, or the direct form `implement-issue direct chart=<chart-folder> worktree=<path>` run by the chart door.

## Shared context

Read [ponytail.md](ponytail.md) before editing, [brief-template.md](brief-template.md) when writing a brief, and [worker-protocol.md](worker-protocol.md) when delegating or validating a worker return.

Ground in docs first.
Challenge fuzzy terms.
Verify with a concrete scenario.
Check the live surface.

For leaf work, read `akrogon config` once, locate the unique slug in the registered repo's authoritative `issues/open/`, and use its `plan.md`, `design.md` and current review findings while editing only the leaf worktree and its worker worktrees.

Pass artifacts are written under the `leaf=` folder while code is read and edited only in the leaf worktree and its worker worktrees, and a manual prompt naming a slug without `leaf=` falls back to locating the slug under the registered repo's `issues/open/`. Standalone keeps its no-config, local-artifact behavior except in the direct form below.

Temp files and logs go under `$TMPDIR`, never a fixed `/tmp/<name>`; a base copy is made only through `akrogon base-run`; anything needed later goes in the leaf folder.

Effective settings supply `implement`, `checks`, optional `advisory` and `setup`, `AKROGON_BASE`; when `akrogon config` prints `setup`, a dependency-using proof outside the printed commands runs `flock "$(git rev-parse --git-path akrogon-install.lock)" sh -c <quoted setup>` first; the command owns state/counters and dispatch, while a repeated pass finishes remaining work from the diff and artifacts, rerunning checks for changed code, missing evidence or a specific concern.

The plan's read-first list supplies worker context and the index is opened only on a gap. Implement updates every doc the plan names plus any doc the diff makes stale before review, keeping affected `AREA.md` files at most 40 lines with exactly Commands, Key files, Non-obvious patterns and See also as second-level sections.

A reusable lesson found during leaf work gets an active line naming mechanism/date/history path and a history file with case, evidence and learning ([lesson rule](../lesson-rule.md)); `learnings/LESSONS.md` is not pass input, and applying a lesson lands the running mechanical guard covering its mechanism on every reachable path, removes its active line and appends `Applied <YYYY-MM-DD> by <guard file:line>: <what it enforces>` to its history file without rewriting the historical case; guard, line removal and Applied append land in the leaf's own diff.

The A seat proceeds without posing questions or holding the pass open, deciding from the plan, the design, and the worktree alone. When a step physically requires the operator (a permission A cannot grant, an env value A cannot obtain), A writes the blocker into its current pass artifact with the input's name or ID, the attempted operation, the identity reference, the error, the owner and the next action, never a value, plus the exact operator action, runs `akrogon phase <slug> failed --reason "<blocker plus artifact>" --slot A`, and ends the pass. A review finding whose fix needs operator access follows the operator-only rule in check-issue Shared context.
A fix that needs a locked decision changed ends the pass the same way, with `akrogon phase <slug> failed --reason` naming that decision and the same blocker fields in the artifact.

A done-criterion still failing during implement or check.fix after the repairs the protocol permits (a red criterion-proof or checks sub-brief, a slow-run leaf's in-branch fix) and unable to pass within the leaf's owned surfaces ends the pass the same way, with `akrogon phase <slug> failed --reason "<criterion> red: <cause>" --slot A` and the same blocker fields in the artifact; it is never handed off as pre-existing, base red or modulo anything. A proof that cannot run because its machinery or environment is unsuitable ends the pass the same way, required not optional, and the seat never writes or extends proof machinery to reach evidence.

During implement end and check.fix, a red test or check with no cause in the leaf's diff (failing output plus `git diff "$AKROGON_BASE"...HEAD` shows no touched file or plausible cause; a judgment gate, never automatic) gets one retry of that same command, args and whole-folder or single-file scope in the corresponding working directory; before retrying, the seat writes one comparison record file per red check under the `leaf=` folder holding the first run, so a replaced session that finds it retries no further, and each record holds at most one retry. The first-run and retry logs go under `<leaf>/implementation/` beside the `base-<id>.log` `base-run` writes. A green retry marks the check `inconsistent` and no base run happens. A red retry runs the command once without the change as `akrogon base-run --base "$AKROGON_BASE" -- <command>` from the matching directory of the leaf worktree (the verb runs a printed `setup` under `git rev-parse --git-path akrogon-install.lock` inside the checkout, writes child output to the `log:` path it prints, and removes the checkout) under the same material conditions as the leaf run, keeping each run's own exit status and terminal result before any reporting pipeline such as `echo`, `grep` or `head`. The record lists command, args, cwd, scope, material conditions, leaf and counterpart revisions, completeness per run, both log paths, and per failing unit its runner or stage, file or suite, full name and outcome on each run with a log reference: `known-red` fails in both with-change runs and without the change with no cause in the diff, `new` passes without the change and `unverified` is missing, crashed, timed out, skipped or unreadable on either side or blocked by a failed setup or build stage. Only `known-red` units let the leaf continue; `new` and `unverified` units keep the existing repair or incomplete-verification path, and a unit of the leaf's own done-criteria is never `known-red` — a wrong expectation there is A's correction under `test-proof-rules`. The seat passes each record on its phase move with repeatable `--compare <file>`; the command validates each record, opens or joins one repo red entry per `known-red` unit, resolves entries whose unit passes on the base run's revision or a descendant, and sends the operator one notice per new entry, with `akrogon status` listing active entries. The base run uses the active harness's longest run mode, and a base run still killed, interrupted or crashed before its terminal result is incomplete: the seat keeps its logs and termination cause and ends with `akrogon phase <slug> failed --reason "<command> incomplete base run <sha>: <cause>" --slot A` with no automatic rerun and no base-defect claim.

A refreshes the leaf branch onto current main: it fetches the configured remote, rebases the leaf branch onto the current `<remote>/<default_branch>` and refreshes `AKROGON_BASE` from `akrogon config`. Before every refresh A commits outstanding scoped work, never stashing or discarding it. Conflicts resolve inside the rebase keeping both true sides under the merge-issue solo rule; when resolution needs a plan correction A makes it under the `check.fix` plan-correction rule and resolves by it, `plan.md` lives in the registered checkout so the rebase stays in progress meanwhile, and such a conflict never ends the pass `failed`. A fetch failure or another refresh error with no conflict to resolve is recorded with its original error in `implementation/report.md`; A aborts a rebase only if one is in progress and the pass ends with no phase move; the re-prompted pass resumes at the refresh instead of redoing committed work and compares any red check again; A never proceeds on an old tip. A comparison record holds only for the head and pass it was written in; after a refresh or a later commit a red check is rerun and compared on the new head, never carried over. `implementation/report.md` records each refresh that moves the branch with prior and new base and prior and new head; a report handed off from `check.fix` also records the prior reviewed base and head and the handed-off base and head.

Proof order applies at implement end and after every check.fix repair. A slow run is any live run, or a proof whose plan.md size is hours or unknown.
1. Cheap proof first: before the first slow run, A runs every `checks` command and every done-criterion proof whose prerequisites are valid and which needs no slow or live result, whatever its own size. Checks and proofs that need a slow run's output run after it, and the blocked-check and final-proof rules stay.
2. Overlap, delegated mode only: while a slow run is in flight, A may start a unit or repair in a worker worktree when it does not consume the run's result, edits nothing the run reads and shares none of its test resources. An overlap wave starts from the lane's committed HEAD, and pending lane commits, cherry-picks and any landing wait until the slow run returns. A then reruns the changed stages and their consumers under the slow-run rerun rule. Inline mode waits for the run.
3. Wait on exit: A waits on a slow command's exit and status, waits again when a wait returns before the command has exited, never sleeps a fixed interval and then reads the log, and treats the exit status as the result, never a quiet log.

A never opens, prints, appends to, or writes `.env` or `.env.*` with any tool; declared checks and live operations consume values only inside a run process such as `bun --env-file=<holder file> <script>` printing results, never values, and presence is checked with the `Missing:` lines of `akrogon status <slug>`, where absent or empty counts as missing, ending the pass with the stop above when a required value is absent.

A producer's key is saved only through the operation recorded in `produces[].save` (entry point, inspected revision, non-secret `args`, key `name`, `holder` repo's real file, private `value_source`): the value passes privately, writes the `holder` repo's real `.env` file and never the worktree `.env`, never returns through seat arguments, output or artifacts, and the new key is revoked when saving fails.

A reuses `grants[]` for probes, implementation, repairs, reruns, merge checks and cleanup without asking again; before mutating it compares operation, target and identity with the grant, records the grant reference, results and created IDs in its pass artifact, never widens it, and treats anything outside it as an operator blocker under the stop rule.

## implement

Run the Shared context refresh before the first unit. Before coding, when an implementation-only constraint is missing from `plan.md` under the `leaf=` folder, append one dated `## Implementation notes` section naming each constraint and the decision it refines; a locked decision is never changed there, and a conflict with one is a mismatch recorded for review. Then implement the plan yourself in wave order, then listed order inside a wave, when config says `inline`, otherwise write one sub-brief per unit from the template, one unit included, and delegate them to subagents with A running each plan wave whole, up to 3 workers at once, and waiting on all together, each in its own worktree, using the worker protocol.

Inline has no worker, sub-briefs or mismatch returns and follows the same rules with A as the only seat; both modes run the resolved changed-tests command as work lands with `AKROGON_BASE` from config, and workers receive only that command, not A's criterion proof and every `checks` command run.

A test exists only as the proof of a done-criterion or as the red-first reproduction of a proven bug; a consequential edge or negative case is a done-criterion written at charting, and after planning no seat adds a case on a named consequence alone. Implementation runs the planned tests rather than writing them: workers, implement A and check.fix A write and edit no test. The two exceptions are A's correction of one wrong expectation in a planned test, in its own commit with a `Test-Change:` trailer citing the brief line or real output, and A's one reproduction test for a proven product bug during implement or check.fix, shown red on the head before the fix and committed first with a `Test-Change:` trailer citing the bug's realistic source. A writes and commits the reproduction before delegating the fix, never a worker; a worker who finds a planned test red or wrong returns a mismatch, and a wrong criterion ends the pass under the locked-decision stop above. The report links each done-criterion and each real bug fix to its test or evidence. The test-writing rules bind the planner and the bug-reproduction exception, never the worker: one test may prove several criteria; an existing assertion, fixture or recorded output changes or is deleted only with a cited brief outcome or real source (a real build, user action or content, integration or attacker-reachable input) that the old expectation contradicts; default to the smallest test at the real boundary (CLI, HTTP, browser, DB), with unit or property tests only for logic that matters where they catch bugs more cheaply and E2E only where smaller tests miss browser, runtime or wiring bugs; extend existing tests before adding files; delete a false or outdated expectation with its reason, a duplicate only after naming the test that still catches the same bug, batches judged as batches, keeping tests guarding real past regressions; a bug fix shows fail-before/pass-after and new behavior shows one deliberate break turning its test red, with no mutation score.

A credential absent on `akrogon status <slug>`'s `Missing:` lines at implement is never requested as a pasted value: A records the missing variable in `<leaf>/implementation/report.md` as a human-only blocker with the `add <VAR> to .env` action, what the value is, and where the operator obtains it, then runs `akrogon phase <slug> failed --reason "<missing <VAR> blocks <criterion>; see implementation/report.md>" --slot A` and ends the pass.

A red test or check with no cause in the leaf's diff takes the Shared context comparison rule before any repair.

After the last implementation unit, with every worker worktree removed, commit any remaining edits on top of the wave commits on the leaf branch, making no empty commit, and run the Shared context refresh, then supply passing proof for every done-criterion in the Shared context proof order, run changed tests including affected consumers and every `checks` command, reuse earlier evidence for a test only when it ran after the latest change to that test and to every helper or fixture it uses, run `merge_checks` only at merge unless a done-criterion needs a whole run, with one other case: a `check.fix` pass after a red merge ending replays the exact rejected command recorded in `review-B.md`; repair any failure by the protocol (yourself in inline mode), and write `<leaf>/implementation/report.md` with changed files and reasons, commands run with pasted results and artifact paths, each proof result recording the command, the commit it ran on and the result, the base and committed head, known limitations and unverified criteria, folding worker returns into it, before handoff; `akrogon phase` refuses a dirty worktree and refuses any file under `issues/` on the branch, because every issue artifact is written only in the registered checkout.
Tests are locked after planning: any commit that changes an existing file matched by the path rule in `src/test-files.ts` ends its message with a `Test-Change: <exact path> <source and reason>` trailer in the final trailer block, one per changed old test file, a later trailer-only empty commit is the allowed exception to the no-empty-commit rule, and the phase move is refused without it. A commit adding a case to an existing test file carries the same trailer, naming what was added and that no existing expectation changed, citing no source. The `plan.synthesis` to `implement` move records in state every path the branch changed against the target, its content id or absent for deletions; a later move refuses a recorded path changed or gone, or an added `src/test-files.ts`-matched path outside the record, until a `Test-Change:` trailer names it in the last commit touching it or a later commit; when no branch commit touches the path, a later trailer-only commit must carry it on a commit new since the record, a replayed planning-era trailer does not count.
The report records wall time for every command sized minutes, hours or unknown.
For a slow run it also records the in-branch fixes made, the reused stages with their source commit, what changed and which stages it feeds, and the blocked checks.

Every command under `checks` blocks; `advisory` failures are reported as Nits.

Finish with `akrogon phase <slug> check.review --slot A`, then print the footer and stop.

## check.fix

Run the Shared context refresh before reading the findings. A red test or check with no cause in the leaf's diff takes the Shared context comparison rule before any repair.

Read the recorded findings and reviewed commit in the existing review files, revise the plan notes and affected sub-briefs around those defects without weakening criteria or failing tests, and use worker waves in delegated mode, grouping repair sub-briefs by the same rule so findings with disjoint paths and no shared resource repair in one wave, and repair yourself in inline mode. The only test check.fix adds is the reproduction: for a proven bug, the fixing seat commits one reproduction test shown red on the head before the fix, with a `Test-Change:` trailer citing the review finding's realistic source; A writes and commits it, never a worker, so a delegated repair starts after that commit. A criterion still red after those repair rounds takes the failed exit under Shared context.

A repair requested from merge starts at the rebased head recorded in `review-B.md` and treats the failing output as the finding. Before judging the failure, the pass replays the recorded commands after its opening Shared context refresh; a green replay needs no repair and goes on to the record below, and only a red replay takes the base-run rule, against the refreshed base. After the repair commits, the pass runs the Shared context refresh again, then their normal proof (done-criteria proof, changed tests, `checks`) and replays every exact command the red ending recorded verbatim, same command, arguments and scope, in the leaf worktree. `implementation/report.md` records each replayed command and its arguments, the rejected run's base and head, and the rerun's base and head (the resolved rebased head after any conflict) with the result. A red rerun takes the same repair path again inside this pass and the replay repeats; a red rerun is never handed to `check.review`, which only a green replay reaches.

The newest entry in `review-B.md` decides A's input. A `Handed to A` list from B's check.repair means A repairs only those items. For each named plan correction A first corrects `plan.md` before changing code, resolving a repeated problem as a corrected rule or added step, a contradicted plan decision as a corrected decision within the plan's own scope (the brief and the locked design are never weakened), a missing step as that step, and adds an executable check A runs for the corrected rule. Red merge checks mean the failing output and the recorded command are the finding and the replay's target. Otherwise A repairs every recorded Fix, which covers a leaf already in check.fix before check.repair existed.

When the review files list open items under `Operator actions`, check.fix repairs the doable Fixes and supplies their proof as below, then ends with the one `failed` stop of the operator-only rule in check-issue Shared context instead of `check.review`.

Do required work for Fixes only; Nits get no separate work or test and may only disappear incidentally through Fix repair. A repair commit that changes an existing file matched by the path rule in `src/test-files.ts` carries the `Test-Change:` trailer. After every repair, commit any remaining edits and run the Shared context refresh, then supply passing proof for every done-criterion in the Shared context proof order, run changed tests including affected consumers and every `checks` command, reuse earlier evidence for a test only when it ran after the latest change to that test and to every helper or fixture it uses, run `merge_checks` only at merge unless a done-criterion needs a whole run, with one other case: a `check.fix` pass after a red merge ending replays the exact rejected command recorded in `review-B.md`; update affected docs/index lines and append the repair's before and after commits to `report.md` under the `leaf=` folder, then finish with `akrogon phase <slug> check.review --slot A`, print the footer and stop.

## Standalone

Use the prompt as the task, plan briefly in `implementation/brief.md`, derive changed-test commands from the checkout, delegate through the same template/protocol, check the report and changed-test evidence, and repair yourself before returning. Standalone has no leaf state or phase guard, so its only test rule is order: tests from the brief first, committed, then code.

Except for the direct form, standalone has no config or leaf reads, lifecycle state/log writes, phase call or checker; its template and protocol are entirely skill-local, and its footer reports completion or the concrete unresolved task limitation. Standalone takes the prompt and the checkout as its full input and sends no questions back.

### Direct form

The prompt `implement-issue direct chart=<chart-folder> worktree=<path>` is the chart-issues direct route's implementation step, run by the chart door as A. The task is the chart's draft brief and design, read in place and not rewritten as a new brief. The checkout is `worktree=<path>`, where all code is read and edited. Run `akrogon config` there once for `checks` and the base. The plan goes in `<chart-folder>/direct/plan.md` and the report in `<chart-folder>/direct/report.md`, not in `implementation/`.

Delegation, checking and self-repair work as in Standalone, with A owning the result. A makes no phase call and does not finish: it returns to the door, which sends the result to B for review and back to A for repair rounds under the chart-issues direct route. Direct follows the same order rule: tests from the chart's draft brief first, committed, then code.

## Printed footer

```text
Last operation: <changes, verification and observed phase result>
Next: <skill> <slug> slot=<A|B> phase=<phase> leaf=<folder>
```

After leaf implementation the next pass is check-issue in A and B at `check.review` (one prompt per slot); after repair it is B only, while `Next: none <reason>` covers standalone, waiting or terminal outcomes.

The lines are printed only, with actual command results rather than assumed progress.
