# Chart issues

Dependency: the installed `akrogon` command. This is an attended door by default, not a lifecycle phase; only the operator's words can switch it to autopilot for a session (`## Autopilot`).

## Shared context

Ground in docs first.
Challenge fuzzy terms.
Verify with a concrete scenario.
Check the live surface.

Read [questions](assets/questions.md) before an operator round, [shapes](assets/shapes.md) before creating a chart or handing off, and [standing design](assets/standing-design.md) when preparing leaf designs.

Ask operator questions in printed chat text, never through a question tool. Decision rounds, including prerequisite and handoff choices, follow [questions](assets/questions.md) and include a reply key.

## Open

In the first reply, name each operator-supplied peer pane in naming order — the first named peer is B, then C, D and so on — or say single slot when none is named; under autopilot the first reply instead follows `## Autopilot`; read `akrogon config` and use its registered repo root for chart and handoff writes, resolving worktrees through their shared Git common directory rather than their inert issues copy. An unregistered repo can be charted locally, but handoff requires a registered destination; registration and initialization are outside this door.

When the operator asks for peers without naming panes and the door's own environment has `HERDR_ENV=1`, the door creates the peer panes at open, asking once for the harness kind and arguments of each created peer except C. C defaults to `pi` with empty argv (`{"seat":"C","kind":"pi","argv":[]}` in the seats list), and an operator-named kind or arguments win. The door then runs `bun <skill-folder>/scripts/peer-create.ts <root> <A pane> '<seats>'` with `<seats>` a JSON list in naming order of `{"seat":"B","kind":"<kind>","argv":["<arg>",...]}`, which splits B right of A, stacks each later peer below it at equal heights, starts each peer and prints one line per seat with the pane that addresses it; a failed create ends the turn with the printed states reported. Supplied panes are used as given and never moved or resized, the door moves no pane it did not create, and the requested sizes (A 65% wide, all created peers sharing the right 35% at equal heights) hold only when A's pane fills its tab; otherwise only A's area is split. Outside herdr the door says so and continues single slot or with supplied panes.

Consultants restart with an empty context when the door enters a chart, before that chart's first consultant exchange, and again when it re-enters a chart after the consultants worked on another chart; one run before a shared opening map covers the map, A's own work or compaction alone never triggers it, it runs only after every prompted exchange is collected (the caller ensures this and an idle pane does not prove it), and a dropped consultant is never restarted. The door runs `bun <skill-folder>/scripts/peer-restart.ts <A pane> <seat> <pane> [<seat> <pane>...]` over every named consultant still active; it stops each consultant's agent and starts the same kind and arguments again in the same pane, so pane ids and the layout never change, and it never touches A or unrelated panes. A restarted seat's new seats.yaml entry keeps its letter and is appended from the `restarted` line's `session` when it is not `none` (pi shows its session at start; codex shows `none` until its first exchange), never with a null session. A failed restart ends the turn with the printed states reported; under autopilot every seat not `restarted` is dropped like a herdr prompt refusal with its printed state recorded under `consultant:`.

Run `akrogon pull` at open: report an unregistered or non-GitHub repo and continue charting, while any other failed refresh blocks a drain relying on that refresh rather than permitting stale mirrored intake; independent operator notes can continue.

Read the configured `grounding.index` top file, relevant linked areas and `learnings/LESSONS.md` as resources and report absent resources as gaps. Reusable findings get one mechanism/date/history-path line in LESSONS.md and a case/evidence/learning file at `learnings/history/<date>-<slug>.md` ([lesson rule](../lesson-rule.md)), with historical lessons treated as observations rather than rules. Run `akrogon flaky` and `akrogon status` beside them and show each listed test, and each leaf stopped in `failed` with its reason, as an intake candidate the operator can confirm.

Import operator notes, and mirrored `issues/seeds/*.md` and legacy `issues/open/<slug>.md` only when the door opens without an operator note or the note asks for them, using the provenance in shapes: skip exact GitHub identities already in open/closed leaf `sources` or any chart intake, and legacy source paths already imported, preserving original reports and copying imported text verbatim separately from agent findings and scope.

At open, name each skipped GitHub identity that is still open on GitHub and offer `akrogon close <owner/repo#n> --by <text>` for it. During the pass, run that command for any identity the chart records as delivered or duplicate, passing what delivered it: the delivering leaf slug and commit, or the other identity. A confirmed full match with no other owner whose work is undelivered is exempt and stays open as `sources` until its completion owner delivers. One further exception: a report whose close depends on a step on main that can only follow a leaf's merge is withheld from closing `sources`, and the door closes it after making and verifying the edit, not at leaf completion.

The seat record holds the open time, the time the door began its first pass on this chart, before the opening map, and one entry per seat holding pane, harness kind and session id as `herdr agent list` prints them (`pane_id`, `agent`, `agent_session.value`), kept with the door's temporary files while no chart folder exists and written to `<chart>/seats.yaml` when the chart folder is created, covering A and each named peer; neither folder creation nor a replacement session resets the open time. The door appends a seat entry with the same seat letter from the `session` field of each exchange step's outcome lines and of each `restarted` restart line whenever that field shows a session it has not recorded for that seat, and reads no separate `herdr agent list` for seat records. The same record keeps `spans`, one span opened when the door begins work on a chart and closed on handoff, close or hold, when the chart waits on an approval, need or prerequisite, or before switching to another chart, once every outstanding consultant turn is collected, held open while the door waits on this chart's consultants and reopened as a new span on re-entry, so only the last span may be open, the first chart's first span covers the shared opening map so the map counts once, and a record without `spans` reads as a legacy window. On a handover continuation fresh A appends its A seat entry with its live `agent_session.value` and opens its first span before chart work; the exchange-appended rule covers its later sessions. Outside herdr the record holds the open time and no session, and the usage table says `usage unmeasured`. The door asks the operator nothing new for this record.

## Drain

Show a proportional territory map before grilling, including material forks, practitioner questions and pitfalls over the work's lifetime, what each option could break or invite later and not only now, grounded in inspected surfaces; when peers are named, A and each named peer map independently before A merges with attribution, using the blind file exchange in questions; waits on a peer follow the peer-wait script rule in questions.

A round takes one fork, the next answerable fork first, preferring the one whose answer reshapes the most remaining forks; a destination with one fork costs one round.

Propose the split by destination and speed of resolution before writing: independently checkable outcomes sharing a destination can be parallel leaves of one issue, independent issues run side by side, and only an actual dependency orders work, never file overlap or presentation preference.

Write one chart folder per destination. Rounds work one chart at a time and never mix charts: when the current chart hands off, closes, is held or waits on an asynchronous approval, need or human-only prerequisite (a presented round or handoff review is not such a wait), the door moves on without asking for a selection to the chart the operator names, else a chart whose wait has cleared, else the open chart not waiting whose CHART.md was first committed earliest, else the next seed when the door imports seeds, else the pass ends; a chart whose forks are all taken is handed off without waiting for charts that still hold one. A move-on to a named next chart is a handover: the door appends the handover entry and resets the pane per `## Handover`. A direct single item whose map finds no open fork and no fog writes the same chart structure and proceeds to the handoff review immediately, where the route is chosen. Under autopilot the drain takes only the handed list per `## Autopilot`, with no oldest-chart or seed steps and nothing new imported.

## Take

Research precedes every question and is redone when an answer reshapes one. Before a round, gather for each question the strongest source available in the tier order in questions: operator-placed material, a named practitioner, primary documentation or code, and the model's own knowledge only together with the searches that found nothing stronger. A question about this repository's own mechanism cites the inspected file and line and the documentation of the tool it calls; a question about anything outside it names an outside source or the recorded failure to find one. Research decides which questions are asked, which pitfalls the options are built to avoid and which option is recommended, never the answer, and a recommendation that contradicts a practitioner source shows the contradiction in the question.

With named peers, A owns interviewing and recording, sends only intake, current Question and carries, related fork paths, locks and verbatim operator corrections while developing its own view, then merges the completed independent notes with agreeing-slot tags such as `(A)`, `(B,C)`, `(A,B,C)`, `(A,B,C,D)`, a merge tag citing only a line the peer wrote, and obtains one disagreement-only rebuttal from each peer; A alone then writes the formatted operator round and presents it with the rebuttals under the challenge check; each peer answers direct operator requests in its own pane and runs one focused check before A records later corrections: all mechanism or contract corrections from one operator reply (under autopilot, one pick) for one fork go into one proposed final shape with the corrections marked and are sent to every named peer, per the final-shape rule in questions; waits on a peer follow the peer-wait script rule in questions.

Record operator answers and their reasons in fork files. After each answer, re-read Fog and move newly sharp material questions into their own fork files, removing only that material from Fog. Reshape the remaining forks and update CHART.md's ordered Open forks list before selecting and researching the next fork; handoff becomes ready only when no material question or fog requires the implementer to guess, with small optional prototypes explicitly chosen as measurements whose scratch code is discarded.

Every external operation a brief names, whether API method and path, CLI command or launch flag, gets one real call run with the identity the leaf will use before handoff, recorded in the fork with the command, inputs, identity reference without secret values, version, date, observed result, cleanup result and limits stating what the call does not prove, linked from the leaf's `proofs` records in `readiness.yaml`. Writes use the smallest reversible call on a throwaway target with checked cleanup. A provider dry-run or validate call counts only for the property the provider documents it proves, run with the real identity and target. When a decision locks a setting of an outside tool (a config key, file setting, flag or environment variable), its proof uses that same key, location and value and observes the property the decision relies on, and a proof of a different form, such as the CLI flag for a locked config key, does not count for it. Declining a required probe holds the handoff; when no safe sufficient probe exists the handoff is held and scope is not narrowed. There is no waiver.

As soon as a genuinely human-only prerequisite appears, show it under Pitfalls avoided as the step that removes its trap, with its owner, exact action and pending status until done, and record completion before opening a leaf or starting a direct attempt. Needs are not such a prerequisite but are anticipated, never discovered by a blocked seat: after the forks settle and before the door's proof calls, the door shows one sheet listing every need across the proposed leaves, each with purpose, consuming leaves, exact permissions and resources, official source and date checked, destination (keys and values to the declared holder's env, files to their paths, approvals to authorization records) and what done looks like; the operator completes the sheet at their own pace, with asynchronous approvals waited for before the affected proofs; the door checks presence on each draft `readiness.yaml` and runs the proofs, and a failed proof yields a specific repair step; handoff stores the steps in `inputs[].steps`, so `akrogon status` prints a still-missing need and `akrogon next` refuses dispatch. The operator creates every missing outside-account key in one batch before handoff, from the door's list; a leaf that creates something with its own key stores that key itself, declared up front in `produces`, and dependents wait on it through `blocked-by`.

Each leaf's `grants` records one scoped grant during charting, covering live changes and paid model launches (read-only and nested ones included), before the first covered proof and confirmed at handoff review: approval provenance; the verified principal and account with credential name and holding repo, never the value; targets by name or ID; leaf-created fixtures by account, purpose, ownership marker, naming rule and count, with created IDs linked to the leaf before change or deletion; operations including transitive helpers, checks and cleanup; explicit destructive, public, billing, DNS and retention effects; repeat and recovery bounds; the stop line for what stays human; and lifetime. A different identity or account, a target outside the set, a new or different covered operation, larger effects or expiry needs new approval.

Proof fixtures are disposable by default. Before creation the contract names the cleanup sequence covering transitive resources, contents and config, the identity for each step (the creating identity by default, another only when declared and proven before handoff) and the authenticated absence read-back with visibility shown first; the door proves a small create/use/delete cycle with the declared identities at charting. Each pass records created IDs under the grant and runs cleanup on success and failure; a leftover disposable resource is a blocker recorded with IDs, error, owner and next step. A fixture stays after its proof only by agreement before creation, naming purpose, resources, an accepting owner, removal date, cost and exposure, cleanup identity and route, and why the proof needs it alive; a cleanup failure never becomes retention afterward, and retention never satisfies a deletion criterion.

A producer's contract names its save operation: entry point, inspected revision, non-secret arguments, key name, the holding repo's real file and the private value source. Saving happens inside the producer process or in a narrow save subprocess receiving the value privately, never returned to the agent to build a command. At charting the door proves on disposable data that only the named entry changes, other entries are preserved and nothing prints, inspects the real target's effective harness controls and records why the result transfers, and proves real revocation on a disposable provider-issued key; the operator's approval of that recorded, proven operation is the explicit permission. A control that denies the operation is reconciled at its source and re-proved; tool edits, shell redirects and dumping stay refused.

## Handoff

Prepare the complete contracts using shapes and standing design, and present one attended handoff review (under autopilot, written in A's pane and answered by A itself per `## Autopilot`) with tree, scope, registered repo, relevant operator choices, each leaf's recorded grant, paid model launches included, confirmed, and each leaf's effective seats; the review also shows the route question or the one-line refusal from `## Direct route`; the seat question is asked at this review only when the intake, map or a leaf design names model-sensitive work, defaults to writing no block, and an answer goes into a `slots:` front matter block (shape in shapes.md) in the operator's chosen owner index (`ISSUE.md` or `EPIC.md`) before any leaf `state.yaml`; recognize concrete handoff authorization already supplied in the session instead of asking again. Right before the handoff review the door runs `bun <skill-folder>/scripts/chart-usage.ts <chart-folder> [<until>]` with `<skill-folder>` resolved to the loaded chart-issues skill directory, shows the printed lines in the review, reports the outcome word and continues on `outcome partial`, a failed measurement never holding a handoff. The door also writes its own review line for each leaf whose done-criteria need a live run, as door prose outside that script output: the session count, how many run at once with rounds counted, an estimated elapsed time and the worst case if every session hits its timeout, labelled an estimate, the existing machinery each live criterion uses, the timeout basis named as the destination's session timeout by file and value, a recorded measured case replacing that basis, or `unknown` with its reason when no basis exists; the line is information only, it never times out a leaf and never waives a criterion, and the operator approves the contract or narrows scope. A done-criterion needing machinery absent on the destination's default branch is proposed as a prerequisite leaf that delivers it, proven by one known-good case passing and one deliberate break failing and listed in the product leaf's `blocked-by`, or the criterion is narrowed with the operator at this review.

When peers are named, leaf writing is a mandatory exchange after approval and before any handoff write: A drafts every brief and design to the scratchpad, each named peer reviews each draft as an implementer and returns disagreements with evidence, A corrects the scratchpad draft files, keeping one final scratchpad version per leaf, marking changed lines with agreeing-slot tags such as `(A)`, `(B,C)`, `(A,B,C)`, `(A,B,C,D)` and carrying any held disagreement into the leaf design, and the corrected files are transferred by name into `issues/open/`, state last and prerequisites before dependents, after the existing collision and preflight checks; no contract is written a second time.

Check destinations at destination selection and again right before the handoff review, one check when both coincide and the opening pull counting only when it coincides with a checkpoint: checked repos are the source repo plus each selected registered destination, deduplicated within a checkpoint, and the source is never exempt, including when it is also the only destination. At each checkpoint run plain `akrogon pull` with cwd at each checked repo's registered root from `akrogon config` `repos`; report an unregistered or non-GitHub destination and hold the handoff to that destination only, while any other failed refresh likewise holds only that destination and other destinations continue. Then compare each checked destination's `issues/seeds/*.md` against the chart's scoped work, show candidate matches to the operator, and act only on operator confirmation; checking never imports a destination's unrelated seeds.

Audit the proposed contracts as an implementer and the Take operation-proof rule, and run the preflight in shapes before writing, refusing collisions by naming the conflicting destination and missing dependencies before any handoff write; the shapes audit also refuses a leaf owning a lesson-traced complete stop without a retirement criterion naming that history path.

Before any handoff write, run this presence check verbatim per draft leaf folder from the akrogon root resolved by `readlink -f $(command -v akrogon)`, printing names only, never values:

```bash
bun -e "import {readGlobal} from './src/config.ts'; import {readReadiness, gaps} from './src/readiness.ts'; console.log(JSON.stringify(gaps(readGlobal(), readReadiness('<draft folder>')!)))"
```

`akrogon status` cannot see drafts without `state.yaml`, so this is the pre-handoff presence check; after valid writes `akrogon status` validates the emitted files.

## Direct route

The direct route is a second ending for the handoff: the door implements one small settled chart itself in a worktree, B — the first named peer — reviews, and the door lands it on the default branch without leaf files. It needs no repo setting: the door offers it at its own discretion whenever the chart is eligible, and the operator can always decline.

Direct is not offered, and the review names the refusal in one line and the handoff goes to the lifecycle, when any of these holds:

- the draft needs `inputs`, `grants`, `produces` or `retained`;
- a done-criterion needs a live run or outside call during implementation (charting proofs do not count);
- more than one outcome or an unfinished dependency exists (door judgment);
- a human prerequisite is pending;
- B is not named;
- the door is running under autopilot (`## Autopilot`).

When eligible, the review asks one route question with the door's recommendation and a reply key: lifecycle or direct. The door may recommend lifecycle for a risky small job. Explicit direct authorization already given in the session is the answer. The chosen route is recorded in CHART.md as the `Route:` line. Selecting direct includes the door's push authority; push, source close and broadcast are coordination, not live calls under eligibility.

Protocol, using the shapes in shapes.md:

1. Attempt start: choose a slug, create the worktree with `git worktree add --lock --reason "<chart-folder> direct" <worktree_store>/<slug>` on branch `<slug>` from the destination's default branch, and write the `Direct attempt` section with the slug recorded.
2. Implement: the door itself runs `implement-issue direct chart=<chart-folder> worktree=<path>`, which writes `<chart>/direct/plan.md` and `<chart>/direct/report.md`.
3. B review: send the chart's B pane `check-issue direct slot=B chart=<chart-folder> worktree=<path> base=<sha> head=<sha> out=<chart>/slots/review-B-<n>.md`, with `n` = 1 for the initial review and the exact path named. The Fix/Nit bar and verdict rules are check-issue's.
4. Repair rounds per the bound below.
5. Landing, after B returns ready or nits on a committed head:
   1. fetch, rebase onto `<remote>/<default_branch>`, refresh `AKROGON_BASE` from `akrogon config` in the worktree;
   2. conflict resolution sends B a focused re-check of the resolved range with the range-diff recorded, a clean rebase reruns checks only;
   3. `akrogon verify --holder <chart>/direct` in the worktree, which runs `checks` then `merge_checks` on a fresh checkout of the rebased head and writes the receipt direct-guards requires; on a red run the door retries that command once on the same head, judges the diff for a cause, and on a no-cause red runs `akrogon verify --holder <chart>/direct --known-red`, which reruns the head when no completed red head run exists and runs the base at the head's merge-base with the tracked default branch, reusing each command already green on the base tree under the same name and command text and running only what lacks one, and the door reads the head and base logs of each red command for runner completeness and causal fit and records that judgment in `<chart>/direct/report.md` beside the kept logs; only a failing known-red result or a disagreeing judgment is a blocking landing-check failure;
   4. `bun <skill-folder>/scripts/direct-guards.ts <worktree> <repo-key> <chart-folder>` must exit 0, with `<skill-folder>` resolved as for chart-usage.ts, run only after the fetch and rebase above;
   5. `git push <remote> <sha>:refs/heads/<default_branch>` of the exact tested SHA, never force; a rejected push keeps the branch, and at most 2 push attempts are made, each with a fresh rebase, checks and B conflict re-check, then stop with the branch kept;
   6. per delivered source, after checking other owners' outstanding work, `akrogon close <id> --by "<chart> direct <sha>"`;
   7. broadcast-issue as sender when the repo configures broadcast, with the chart brief, pushed SHA and closed sources as context, and a failure does not reopen;
   8. `git worktree unlock <path>` then `git worktree remove <path>` verified by `git worktree list`, then `git branch -D <slug>` verified by empty `git branch --list <slug>`;
   9. `akrogon pack <chart>` when `<chart>/direct` holds a log, then the landed SHA into the `Direct attempt` section, then `Closed <date>`.
      The root checkout is never reset, and a failed local update is reported.

Repair bound: one round is B `fix` (or a blocking landing-check failure, which is only a failing known-red result or a judgment that disagrees with a pass, never a red with no cause in the diff), one door repair pass over all Fixes, and B's re-check of the repair diff. The bound is the repo's `fix_rounds` from `akrogon config`, with the count kept in `Direct attempt` so it survives session replacement. A passing last round lands. Exhaustion stops with the open Fixes listed, and the operator chooses one more round, lifecycle handoff, or abandon. Push attempts are not rounds.

Growth stop: stop coding and landing when a locked decision must change, a need eligibility excludes appears, a criterion cannot pass in scope after permitted repairs, or a second outcome appears. The door commits existing work as one partial-labelled commit so the tree is clean, keeps the worktree, updates `Direct attempt` (trigger, done, not done) and opens the trigger as a new fork. Continuations:

- lifecycle handoff: `git worktree unlock <path>` before the handoff because the command's `ensureWorktree` adopts the worktree as-is and leaf rules must be able to remove it later; the leaf slug equals the branch so the command's worktree setup adopts it, the leaf starts at its normal planning phase, the planner decides what to keep, and lifecycle review covers the whole diff;
- abandon: `git worktree unlock`, then branch and worktree removed, `akrogon pack <chart>` when `<chart>/direct` holds a log, then `Held <date>`.

No new direct attempt starts while a chart names a live direct branch.

## Autopilot

Autopilot is a non-default mode the operator switches on in words for one door session. While it is on, the door runs every step it runs today, and at each point where the operator would answer — fork rounds, the split proposal, the handoff review including seats — A writes the full round in its pane, then answers it itself by the evidence and the operator's values: simplicity, function over form, removing over adding, systems thinking, speed and price. Each pick is recorded in the fork's Taken as A's, with its reason, the rejected options and any standing consultant dissent, never as operator words; this is the one exception to "Recommendations and silence cannot supply an operator answer" in questions.md, while approvals stay operator-only.

Autopilot starts only from the operator's words in the door's own pane, at door start or later naming a chart; the words carry the mode, the handed work and the consultants or none. Outside herdr the door says autopilot cannot start. The first reply echoes the mode, the handed work and the consultants, and says that handed-off work waits for the operator's watcher, which the door cannot check. After the door reads the handed work, the first reply shows a best-guess list of things to supply (logins, API keys, files), each with purpose and destination and no approvals on the list. The operator's words go verbatim into each handed chart's INTAKE.md, and a mode line goes into its CHART.md with the time, the door pane and A's session id; answers the operator gave before a mid-chart switch-on stay the operator's.

These make that chart wait while the door moves on within its handed list: grant approval, fixture retention and secret-save approval; a mutating or paid proof call, which waits for the operator's grant approval while other read-only proofs proceed; a missing need; and a human-only prerequisite. Existing checks still stop a handoff, and A repairs what they refuse. A step on main or a lesson write that would change autopilot's own switch or limits also waits for the operator. The door never turns autopilot on, extends the handed list, changes the consultants or raises an existing bound in the skill.

Under autopilot every handed chart takes the lifecycle route; the direct route is not offered. Drain takes only the handed list, with no oldest-chart or seed steps, and imports nothing new. A full match between a destination seed and handed work is A's to confirm; other seed matches, open-time close offers for skipped identities, and flaky tests or failed leaves outside the handed list are recorded only. Handed work is held when another door's open chart — a chart under the registered root's `issues/chart/` whose last marker is not `Handed off`, `Closed` or `Held` and whose latest A seat in `seats.yaml` is on a different pane — shares its chart folder, GitHub identity or legacy path, or shows the same outcome in its Destination. Two doors started on the same work at the same moment is a stated limit. A failed leaf the operator hands to the door is charted like other handed work.

A consultant is dropped for the rest of the session, never re-prompted, with its completed returns kept, when its exchange ends `failure` or `blocked`, when herdr refuses its prompt, when a restart leaves it not `restarted` (a failed restart drops every such seat with its printed state recorded under `consultant:`), or when `budget` with status idle or done and `signal: unproven` repeats after one more full wait. A return file that arrives after the drop is ignored and recorded as ignored; working-status budgets still rerun at once, and a mistake in A's own call is repaired without dropping anyone. A consultant whose pane is a peer seat in another door's open chart is skipped the same way; the door's own charts never cause a skip.

The mode ends when every handed chart's last marker is `Handed off` or `Closed`. A chart waiting on a need, approval or prerequisite keeps the mode on, also across the end of a pass, and the operator's next message in that door — such as a supplied key — resumes it. Only the operator's words in the door pane turn it off early; supplying a key or changing the handed list keeps it on. Every mode change (on, off, changed list, "continue autopilot") is appended to the mode record with its time, and the door reads the latest entry before continuing: the same session id continues after compaction, while a different session id starts attended until the operator says "continue autopilot", which resumes the same handed list with lost consultants still lost. Once off, an open peer turn is collected first and the next question goes to the operator.

CHART.md records the mode record and the `## Autopilot` section per shapes.md, written as the pass goes. The pass ends with one line per chart in the door pane. The handoff footer says "handed off", not "started", and names a pause when `akrogon status` shows one. Nothing computes a score.

Under autopilot the handover fires only when switching to the next runnable handed chart, per `## Handover`: old A appends `handover <time> <log>: handed <remaining list>; consultants <surviving>; instructions <verbatim with provenance and scope, or none>` to the mode record of every handed chart still open, and a folder it creates for the next chart carries INTAKE.md plus CHART.md with its mode record where an attended switch creates only the CHART.md with a pending Destination. The resume entry is `continue autopilot (handover <time>)`, after which fresh A continues the same handed list.

For a next chart whose folder old A creates for this handover, defer `seats.yaml` creation to fresh A, overriding Open's folder-creation rule. Fresh A creates that record on entry with `opened` and its first span's `from` set to its entry time, and its first A seat uses its live `agent_session.value`. Existing charts keep their original `opened` time and append the new session as usual.

## Handover

A handover resets the A pane into a fresh session for the next chart. It triggers when Drain moves on to a named next chart — the current chart handed off, closed, held, or waiting on an approval, need or prerequisite — after the outgoing chart's records are written, every consultant turn is collected and its span is closed; never at first entry, inside a chart, at a presented round or handoff review, after compaction, or at pass end.

Old A appends the handover entry `handover <time> <log>: attended next <chart>; consultants <surviving>; instructions <verbatim with provenance and scope, or none>` to the next chart's Mode record — the reset log path, the next chart, the surviving consultants and every conversation-only operator instruction still in force verbatim with its provenance and scope, or `none`. When the next chart has no folder, old A creates only its CHART.md, holding `pending map by fresh A (<seed path, legacy path or operator note reference>)` under Destination plus the Mode record and no INTAKE.md, until fresh A writes the Destination after its map. Old A then runs `bun <skill-folder>/scripts/door-reset.ts <A pane> <A session> <log> <start prompt>` and ends its turn. The start prompt names A's pane, the handover time, the next chart, its absolute chart folder and the absolute path to this skill.

A fresh session continues the handover only when its start prompt names its pane and next chart and matches the latest Mode entry, which must be an unconsumed handover; it appends `continue attended (handover <time>)`, records its A seat with its live `agent_session.value` — a folder created for the handover holds no seats.yaml until fresh A writes it on entry — and opens its first span before chart work. Without that start prompt or when it does not match, a new session starts attended in no chart.

Operator input recorded in A's session after the queue point cancels the reset: `superseded` is logged and nothing more is sent. The check runs while the turn end is waited on and again at the last check before the send. The input record per kind: a claude `user` entry or `queued_command` attachment with `origin.kind` `human`, a codex `task_started` or role-`user` `response_item` message, a pi role-`user` `message`.

Handover is supported for claude (`/clear`), codex and pi (`/new`); every other kind and runs outside herdr keep same-session behavior. The modes differ only in the trigger and next-chart selection, the created folder's contents and the resume entry's name.

## Printed footer

End each door pass with the actual result and reason no automatic pass follows, printed rather than saved:

```text
Last operation: <what this pass wrote or observed>
Next: none <awaiting operator answer, dispatch, or named blocker>
```

The pass that queued a handover prints `Next: none handover queued to a fresh A in <pane>`.

The footer is printed only when the turn ends, and never while a prompted peer's turn is open.
