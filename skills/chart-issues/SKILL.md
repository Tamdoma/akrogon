# Chart issues

Dependency: the installed `akrogon` command. This is an attended door by default, not a lifecycle phase; only the operator's words can switch it to autopilot for a session (`## Autopilot`).

## Shared context

Ground in docs first.
Challenge fuzzy terms.
Verify with a concrete scenario.
Check the live surface.

Read [questions](assets/questions.md) before an operator round, [shapes](assets/shapes.md) before creating a chart or handing off, and [standing design](assets/standing-design.md) when preparing leaf designs.

Ask operator questions in printed chat text, never through a question tool. Decision rounds, including prerequisite and handoff choices, follow [questions](assets/questions.md) and include a reply key.

## Open

In the first reply, name each operator-supplied consultant terminal by its hc address in naming order — the first named consultant is B, then C, D and so on — and say that supplied consultants are used as given, never moved, killed or restarted, or say single slot when none is named, and name the mode and who answers the signposts; under autopilot the first reply follows `## Autopilot` for its other contents; read `akrogon config` and use its registered repo root for chart and handoff writes, resolving worktrees through their shared Git common directory rather than their inert issues copy. An unregistered repo can be charted locally, but handoff requires a registered destination; registration and initialization are outside this door.

The door is inside hc when `HC_TERMINAL_ID` is set and `hc get $HC_TERMINAL_ID` answers; outside hc the door says it is outside hc and continues single slot or with supplied consultants. When the operator asks for consultants without naming terminals and the door is inside hc, the door creates them, asking once for the model and effort of every created consultant and for its harness except C, whose harness defaults to `pi`; an operator-named harness, model or effort wins. Each created consultant starts at its first exchange with `akrogon seat --slot <x> --harness <harness> --model <model> --effort <effort> --task "You are slot <X>. Read and follow <brief path>"`, run from the door's terminal: it starts as a child of the door named `<prefix>-slot-<x>`, in the door's tab and folder and unboxed, prints its address, and its 60 s start proof is the first ask's delivery proof; a failed start ends the turn with the printed result reported. After a consultant is added or removed the door runs `herdr-consultant-column <door address> <consultant address>...` over the door-created consultants in seat-letter order, which lays the door out on the left and one column of consultants on the right at equal heights. Supplied consultants are never passed to the column helper, never moved, killed or restarted, and keep their context. A column helper exit saying the door is not in a tab is recorded once in the round's log and the round continues; any other non-zero exit is a check-in for A, never a stop.

Door-created consultants restart with an empty context when the door enters a chart, before that chart's first consultant exchange, and again when it re-enters a chart after the consultants worked on another chart; one run before a shared opening map covers the map, A's own work or compaction alone never triggers it, it runs only after every prompted exchange is collected (the caller ensures this and an idle consultant does not prove it), and a dropped consultant is never restarted. For each door-created consultant still active the door runs `herdr-consultant-column --save <door address> <consultant address>...`, `hc kill <address>`, `hc rm <address>`, the same `akrogon seat --slot` with the seat's recorded recipe and the next exchange's task, then `herdr-consultant-column --restart <door address> <consultant address>...` with the new address in the old one's place, so the operator's dragged sizes stay; it never touches A, supplied consultants or other terminals. A restarted seat's new seats.yaml entry keeps its letter, with its new address and its transcript path once known, never with an unknown path. A failed restart ends the turn with the printed result reported; under autopilot each seat whose restart failed is dropped with that result recorded under `consultant:`.

Run `akrogon pull` at open: report an unregistered or non-GitHub repo and continue charting, while any other failed refresh blocks a drain relying on that refresh rather than permitting stale mirrored intake; independent operator notes can continue.

Read the configured `grounding.index` top file, relevant linked areas and `learnings/LESSONS.md` as resources and report absent resources as gaps. Reusable findings get one mechanism/date/history-path line in LESSONS.md and a case/evidence/learning file at `learnings/history/<date>-<slug>.md` ([lesson rule](../lesson-rule.md)), with historical lessons treated as observations rather than rules. Run `akrogon flaky` and `akrogon status` beside them and show each listed test, and each leaf stopped in `failed` with its reason, as an intake candidate the operator can confirm.

Import operator notes, and mirrored `issues/seeds/*.md` and legacy `issues/open/<slug>.md` only when the door opens without an operator note or the note asks for them, using the provenance in shapes: skip exact GitHub identities already in open/closed leaf `sources` or any chart intake, and legacy source paths already imported, preserving original reports and copying imported text verbatim separately from agent findings and scope.

At open, name each skipped GitHub identity that is still open on GitHub and offer `akrogon close <owner/repo#n> --by <text>` for it. During the pass, run that command for any identity the chart records as delivered or duplicate, passing what delivered it: the delivering leaf slug and commit, or the other identity. A confirmed full match with no other owner whose work is undelivered is exempt and stays open as `sources` until its completion owner delivers. One further exception: a report whose close depends on a step on main that can only follow a leaf's merge is withheld from closing `sources`, and the door closes it after making and verifying the edit, not at leaf completion.

The seat record holds the open time, the time the door began its first pass on this chart, before the opening map, and one entry per seat holding the hc address, the hc name (null for A and supplied consultants), the launch recipe (`harness`, plus `model` and `effort` for door-created consultants) and `session`, the transcript path `bun <skill-folder>/scripts/transcript.ts <address>` prints, covering A and each named consultant. The chart folder and `<chart>/seats.yaml` are written at Open; neither a later chart folder nor a replacement session resets the open time. After every prompted consultant in an exchange is collected or dropped, including the first exchange after a start or restart, the door reads `transcript.ts` for itself and each consultant and appends an entry with the same seat letter whenever that seat's address or transcript path changes. These lookups wait until collection finishes because the resolver's `hc get` consumes child news. An unknown path (`-`) is never recorded and never counts as the same conversation; older recorded paths stay usable for usage only. The same record keeps `spans`, one span opened when the door begins work on a chart and closed on handoff, close or hold, when the chart waits on an approval, need or prerequisite, or before switching to another chart, once every outstanding consultant turn is collected, held open while the door waits on this chart's consultants and reopened as a new span on re-entry, so only the last span may be open, the first chart's first span covers the shared opening map so the map counts once, and a record without `spans` reads as a legacy window. On a handover continuation fresh A appends its A seat entry with its transcript path and opens its first span before chart work. Outside hc the record holds the open time and no seat, and the usage table says `usage unmeasured`. The door asks the operator nothing new for this record.

The signposts round sets the session's direction: the ranked priorities, the hard limits and the order or drop of the session's charts that steer every map and every later pick. It runs once per door session, after intake import and the consultant restart and before any map, and map briefs carry its answers. One consultant exchange adds missed angles first. The latest earlier signposts record on the same repo is offered as proposed answers, which the operator answers "same" or changes. The round's light shape and its unanswered, correction and conflict rules live in questions.md, the record and copy rules in shapes.md, and who answers it in `## Autopilot`. The signposts rule applies to door sessions opened after it lands.

One needs sheet travels with the signposts round, asked once per door session covering every handed chart and completed before the first map: its rows are every foreseeable operator-only need and authorization the session's charting will require — keys, logins, files, accounts, resources and permissions, human-only actions, grants for live changes and paid or nested launches, paid budget, fixture retention, secret-save and closes that need an operator decision (delivered-identity closes the door runs under Open are not rows) — answered only by the operator and never A's pick under autopilot, or "none" when empty. Rows stay pending without blocking charting: only the affected proofs and the handoff wait on them, and a pending row is never re-asked as a question. A route whose authority cannot be named by then is unavailable under the sheet. A chart added to the session after the signposts round by a changed-list yes gets its rows asked with that proposal, before its charting.

## Drain

Show a proportional territory map before grilling, including material forks, practitioner questions and pitfalls over the work's lifetime, what each option could break or invite later and not only now, grounded in inspected surfaces; when peers are named, A and each named peer map independently before A merges with attribution, using the blind file exchange in questions; waits on consultants follow the exchange wait in questions.

A round takes one fork, the next answerable fork first, preferring the one whose answer reshapes the most remaining forks; a destination with one fork costs one round.

Propose the split by destination and speed of resolution before writing: independently checkable outcomes sharing a destination can be parallel leaves of one issue, independent issues run side by side, and only an actual dependency orders work, never file overlap or presentation preference.

Write one chart folder per destination. Rounds work one chart at a time and never mix charts: when the current chart hands off, closes, is held or waits on an asynchronous approval, need (a pending needs-sheet row included) or human-only prerequisite (a presented round or handoff review is not such a wait), the door moves on without asking for a selection to the chart the operator names, else to the first chart not waiting in the session's signposts order, else a chart whose wait has cleared, else the open chart not waiting whose CHART.md was first committed earliest, else the next seed when the door imports seeds, else the pass ends, and a dropped chart or seed named in the session's signposts is not charted this session; a chart whose forks are all taken is handed off without waiting for charts that still hold one. A move-on to a named next chart is a handover: the door appends the handover entry and resets A per `## Handover`. A direct single item whose map finds no open fork and no fog writes the same chart structure and proceeds to the handoff review immediately, where the route is chosen. Under autopilot the drain takes only the handed list per `## Autopilot`, with no oldest-chart or seed steps and nothing new imported.

## Take

Research precedes every question except the signposts round, which has no research line, and is redone when an answer reshapes one. Before a round, gather for each question the strongest source available in the tier order in questions: operator-placed material, a named practitioner, primary documentation or code, and the model's own knowledge only together with the searches that found nothing stronger. A question about this repository's own mechanism cites the inspected file and line and the documentation of the tool it calls; a question about anything outside it names an outside source or the recorded failure to find one. Research decides which questions are asked, which pitfalls the options are built to avoid and which option is recommended, never the answer, and a recommendation that contradicts a practitioner source shows the contradiction in the question.

With named peers, A owns interviewing and recording, sends only intake, current Question and carries, related fork paths, locks and verbatim operator corrections while developing its own view, then merges the completed independent notes with agreeing-slot tags such as `(A)`, `(B,C)`, `(A,B,C)`, `(A,B,C,D)`, a merge tag citing only a line the peer wrote, and obtains one disagreement-only rebuttal from each peer; A alone then writes the formatted operator round and presents it with the rebuttals under the challenge check; each peer answers direct operator requests in its own terminal and runs one focused check before A records later corrections: all mechanism or contract corrections from one operator reply (under autopilot, one pick) for one fork go into one proposed final shape with the corrections marked and are sent to every named peer, per the final-shape rule in questions; waits on consultants follow the exchange wait in questions.

Record operator answers and their reasons in fork files. After each answer, re-read Fog and move newly sharp material questions into their own fork files, removing only that material from Fog. Reshape the remaining forks and update CHART.md's ordered Open forks list before selecting and researching the next fork; handoff becomes ready only when no material question or fog requires the implementer to guess, with small optional prototypes explicitly chosen as measurements whose scratch code is discarded.

Every external operation a brief names, whether API method and path, CLI command or launch flag, and every key part of a kept done-criterion — a clause whose pass rests on something existing before the leaf builds, an outside system's acceptance, an existing checker's verdict, existing data or recordings — gets one real observation run with the identity the leaf will use before handoff, by the smallest call that reaches it, free before paid, within the one operator-approved paid test budget. A proof counts only for the property it observed, which its `limits` records: a provider dry-run or validate call counts only for the property the provider documents it proves, run with the real identity and target, and when a decision locks a setting of an outside tool (a config key, file setting, flag or environment variable) its proof uses that same key, location and value and observes the property the decision relies on, a proof of a different form such as the CLI flag for a locked config key not counting for it. A clause needing an existing checker to accept output the leaf builds is split: its existing input or contract assumption is observed at charting, while acceptance of the new output stays the leaf's own done-criterion proof. Every observation, free ones included, is recorded in the fork with the command, inputs, identity reference without secret values, version, date, observed result, cleanup result and limits stating what the call does not prove, linked from the leaf's `proofs` records in `readiness.yaml`; writes use the smallest reversible call on a throwaway target with checked cleanup, and standing-design's cheapest-sufficient-test rule picks the call. Every operation and every key part kept in the contract needs its proof before handoff: a declined probe, or no safe sufficient one, cuts the contract to what is proven at the handoff review, naming what was cut and where it lands — a prerequisite leaf under the missing-machinery rule, an exclusion in each dependent's design, or an Off route entry — and the cut removes that proof obligation, a cut operation dropping out of the brief's What. A cut that removes the chart's useful outcome is a scope question that parks the chart for the operator under the existing approval-that-is-not-a-grant wait, never answered by A. There is no waiver: nothing unproven is handed off as promised.

As soon as a genuinely human-only prerequisite appears, show it under Pitfalls avoided as the step that removes its trap, with its owner, exact action and pending status until done, and record completion before opening a leaf or starting a direct attempt. Needs are not such a prerequisite but are anticipated, never discovered by a blocked seat: the door asks one needs sheet per door session with the signposts round before the first map (rules in `## Open`), listing every need across the session's handed charts, each with purpose, consuming leaves, exact permissions and resources, official source and date checked, destination (keys and values to the declared holder's env, files to their paths, approvals to authorization records) and what done looks like; the canonical record is `## Needs` in the session's forks/signposts.md original, one line per row with status (pending, supplied, late), re-copied verbatim to the session's charts like any correction. The operator completes rows at their own pace; charting proceeds while rows are pending and only the affected proofs and the handoff wait. A need or wider authority found after the signposts round is a late find: the door continues a useful outcome inside recorded authority under the cut rule above; otherwise the chart parks, drain moves on, and at that moment the door writes one terminal statement and runs one `akrogon notice --attention` naming the chart, what blocks it and the record path (never a secret value), records the notice path or its failed result on the row and adds the row as `late` — once per park, never per pass or on resume, and outside hc or in an unregistered repo the terminal statement and record only. The door checks presence on each draft `readiness.yaml` and runs the proofs, and a failed proof yields a specific repair step; handoff stores the steps in `inputs[].steps`, so `akrogon status` prints a still-missing need and `akrogon next` refuses dispatch. The operator creates every missing outside-account key in one batch before handoff, from the door's list; a leaf that creates something with its own key stores that key itself, declared up front in `produces`, and dependents wait on it through `blocked-by`.

Each leaf's `grants` records one scoped grant during charting, covering live changes and paid model launches (read-only and nested ones included), inside the bounds the sheet's rows recorded — a field the operator was not asked to approve is not approved, and the record binds only inside what was approved — before the first covered proof and confirmed at handoff review: approval provenance; the verified principal and account with credential name and holding repo, never the value; targets by name or ID; leaf-created fixtures by account, purpose, ownership marker, naming rule and count, with created IDs linked to the leaf before change or deletion; operations including transitive helpers, checks and cleanup; explicit destructive, public, billing, DNS and retention effects; repeat and recovery bounds; the stop line for what stays human; and lifetime. A different identity or account, a target outside the set, a new or different covered operation, larger effects or expiry needs new approval. Each repeat bound names its unit and what consumes one in plain words (for example, "at most 2 recorder invocations, counting every invocation that reaches a paid session, whatever its outcome"), and a nested unit, such as sessions per invocation, is its own bound; `stop_line` never restates a repeat count. A renewal entry states its new total or "N more after <date or commit>", and the next count line names the entry it draws on. The door's charting probe counts against the leaf grant it runs under, and the door itself never warns and runs: every paid proof call still waits for operator approval.

Proof fixtures are disposable by default. Before creation the contract names the cleanup sequence covering transitive resources, contents and config, the identity for each step (the creating identity by default, another only when declared and proven before handoff) and the authenticated absence read-back with visibility shown first; the door proves a small create/use/delete cycle with the declared identities at charting. Each pass records created IDs under the grant and runs cleanup on success and failure; a leftover disposable resource is a blocker recorded with IDs, error, owner and next step. A fixture stays after its proof only by agreement before creation, naming purpose, resources, an accepting owner, removal date, cost and exposure, cleanup identity and route, and why the proof needs it alive; a cleanup failure never becomes retention afterward, and retention never satisfies a deletion criterion.

A producer's contract names its save operation: entry point, inspected revision, non-secret arguments, key name, the holding repo's real file and the private value source. Saving happens inside the producer process or in a narrow save subprocess receiving the value privately, never returned to the agent to build a command. At charting the door proves on disposable data that only the named entry changes, other entries are preserved and nothing prints, inspects the real target's effective harness controls and records why the result transfers, and proves real revocation on a disposable provider-issued key; the operator's approval of that recorded, proven operation is the explicit permission. A control that denies the operation is reconciled at its source and re-proved; tool edits, shell redirects and dumping stay refused.

## Handoff

Prepare the complete contracts using shapes and standing design, and present one attended handoff review (under autopilot, written in A's terminal and answered by A itself per `## Autopilot`) with tree, scope, registered repo, relevant operator choices, each leaf's recorded grant, paid model launches included, confirmed, and each leaf's effective seats; the review also shows the route question or the one-line refusal from `## Direct route`; the seat question is asked at this review only when the intake, map or a leaf design names model-sensitive work, defaults to writing no block, and an answer goes into a `slots:` front matter block (shape in shapes.md) in the operator's chosen owner index (`ISSUE.md` or `EPIC.md`) before any leaf `state.yaml`; recognize concrete handoff authorization already supplied in the session instead of asking again. Right before the handoff review the door runs `bun <skill-folder>/scripts/chart-usage.ts <chart-folder> [<until>]` with `<skill-folder>` resolved to the loaded chart-issues skill directory, shows the printed lines in the review, reports the outcome word and continues on `outcome partial`, a failed measurement never holding a handoff. The door also writes its own review line for each leaf whose done-criteria need a live run, as door prose outside that script output: the session count, how many run at once with rounds counted, an estimated elapsed time and the worst case if every session hits its timeout, labelled an estimate, the existing machinery each live criterion uses, the timeout basis named as the destination's session timeout by file and value, a recorded measured case replacing that basis, or `unknown` with its reason when no basis exists; the line is information only, it never times out a leaf and never waives a criterion, and the operator approves the contract or narrows scope. One further line per leaf lists each pre-existing key part — a clause whose pass rests on something existing before the leaf builds — with the `proofs` entry that reached it and anything cut with its landing; like the live-run line it is information only, not a gate. When the chart changes the door's own skill, the review states the change reaches doors only at the next release link. A done-criterion needing machinery absent on the destination's default branch is proposed as a prerequisite leaf that delivers it, proven by one known-good case passing and one deliberate break failing and listed in the product leaf's `blocked-by`, or the criterion is narrowed with the operator at this review.

When peers are named, leaf writing is a mandatory exchange after approval and before any handoff write: A drafts every brief and design to the scratchpad, each named peer reviews each draft as an implementer and returns disagreements with evidence, A corrects the scratchpad draft files, keeping one final scratchpad version per leaf, marking changed lines with agreeing-slot tags such as `(A)`, `(B,C)`, `(A,B,C)`, `(A,B,C,D)` and carrying any held disagreement into the leaf design, and the corrected files are transferred by name into `issues/open/`, state last and prerequisites before dependents, after the existing collision and preflight checks; no contract is written a second time.

Check destinations at destination selection and again right before the handoff review, one check when both coincide and the opening pull counting only when it coincides with a checkpoint: checked repos are the source repo plus each selected registered destination, deduplicated within a checkpoint, and the source is never exempt, including when it is also the only destination. At each checkpoint run plain `akrogon pull` with cwd at each checked repo's registered root from `akrogon config` `repos`; report an unregistered or non-GitHub destination and hold the handoff to that destination only, while any other failed refresh likewise holds only that destination and other destinations continue. Then compare each checked destination's `issues/seeds/*.md` against the chart's scoped work, show candidate matches to the operator, and act only on operator confirmation; checking never imports a destination's unrelated seeds.

Audit the proposed contracts as an implementer and the Take operation-proof rule, and run the preflight in shapes before writing, refusing collisions by naming the conflicting destination and missing dependencies before any handoff write; the shapes audit also refuses a leaf owning a lesson-traced complete stop without a retirement criterion naming that history path.

Before any handoff write, run this presence check verbatim per draft leaf folder from the akrogon root resolved by `readlink -f $(command -v akrogon)`, printing names only, never values:

```bash
bun -e "import {readGlobal} from './src/config.ts'; import {readReadiness, gaps} from './src/readiness.ts'; console.log(JSON.stringify(gaps(readGlobal(), readReadiness('<draft folder>')!)))"
```

`akrogon status` cannot see drafts without `state.yaml`, so this is the pre-handoff presence check; after valid writes `akrogon status` validates the emitted files.

## Direct route

The direct route is a second ending for the handoff: the door implements one small settled chart itself in a worktree, B — the first named peer — reviews, and the door lands it on the default branch without leaf files. It needs no repo setting: the door offers it at its own discretion whenever the chart is eligible, and the operator can always decline.

Direct is not offered, and the review names the refusal in one line and the handoff goes to the lifecycle, when any of these holds:

- the draft needs `inputs`, `grants`, `produces` or `retained`;
- a done-criterion needs a live run or outside call during implementation (charting proofs do not count);
- more than one outcome or an unfinished dependency exists (door judgment);
- a human prerequisite is pending;
- B is not named;
- the door is running under autopilot (`## Autopilot`).

When eligible, the review asks one route question with the door's recommendation and a reply key: lifecycle or direct. The door may recommend lifecycle for a risky small job. Explicit direct authorization already given in the session is the answer. The chosen route is recorded in CHART.md as the `Route:` line. Selecting direct includes the door's push authority; push, source close and broadcast are coordination, not live calls under eligibility.

Protocol, using the shapes in shapes.md:

1. Attempt start: choose a slug, create the worktree with `git worktree add --lock --reason "<chart-folder> direct" <worktree_store>/<slug>` on branch `<slug>` from the destination's default branch, and write the `Direct attempt` section with the slug recorded.
2. Implement: the door itself runs `implement-issue direct chart=<chart-folder> worktree=<path>`, which writes `<chart>/direct/plan.md` and `<chart>/direct/report.md`.
3. B review: `hc send --json <B address> "check-issue direct slot=B chart=<chart-folder> worktree=<path> base=<sha> head=<sha> out=<chart>/slots/review-B-<n>.md. When the review file is written, run: hc send <door address> 'done B: <out path>'"`, with `n` = 1 for the initial review and the exact path named, sent only while B's last status under the asking rule in questions is `idle` or `done`, and the door collects the review by that report and the out file under the exchange rules in questions. The Fix/Nit bar and verdict rules are check-issue's.
4. Repair rounds per the bound below.
5. Landing, after B returns ready or nits on a committed head:
   1. fetch, rebase onto `<remote>/<default_branch>`, refresh `AKROGON_BASE` from `akrogon config` in the worktree;
   2. conflict resolution sends B a focused re-check of the resolved range with the range-diff recorded, a clean rebase reruns checks only;
   3. `akrogon verify --holder <chart>/direct` in the worktree, which runs `checks` then `merge_checks` on a fresh checkout of the rebased head and writes the receipt direct-guards requires; on a red run the door retries that command once on the same head, judges the diff for a cause, and on a no-cause red runs `akrogon verify --holder <chart>/direct --known-red`, which reruns the head when no completed red head run exists and runs the base at the head's merge-base with the tracked default branch, skipping that base pass when the merge-base tree already holds a whole-green row — a green base never covers a red head, so it judges `fail` —, and the door reads the head and base logs of each red command for runner completeness and causal fit, meaning one of: the red command logged a real test name and that name also fails on the base; or the red command's log names no test on the head and on the base, and the door, having read both logs whole, finds that the head shows no failure the base lacks (judged in substance, never as exact text), that the command ended by its own verdict and was not killed, timed out or crashed, and that the diff holds no plausible cause; a command that ended by its own verdict with an ordinary error, a missing input or a load diagnostic is not excluded for naming no tests; when both logs exist but show too little to establish a cause, the door withholds agreement and the existing blocking path applies; in both cases the attempt's own done-criteria proofs must pass on their own, a cover never standing in for them; and the door records that judgment in `<chart>/direct/report.md` beside the kept logs; a check recorded `blocked` behind an agreed known-red is named as not run in `<chart>/direct/report.md` and never reported as passing; when the known-red judgment agrees for a configured command, or when, for a command outside `checks`, the attempt's own completed base run of the same command fails the same tests and the attempt holds that evidence, the door files that red through seed-issue's `## Lifecycle filing` section and records the created or found URL, or the failing command and its error, in `<chart>/direct/report.md`; a green retry (`inconsistent`), a disagreeing judgment, or a killed or incomplete base run is not filed as a base red; filing changes no verification status and adds no proof run; only a failing known-red result or a disagreeing judgment is a blocking landing-check failure;
   4. `bun <skill-folder>/scripts/direct-guards.ts <worktree> <repo-key> <chart-folder>` must exit 0, with `<skill-folder>` resolved as for chart-usage.ts, run only after the fetch and rebase above;
   5. `git push <remote> <sha>:refs/heads/<default_branch>` of the exact tested SHA, never force; a rejected push keeps the branch, and at most 2 push attempts are made, each with a fresh rebase, checks and B conflict re-check, then stop with the branch kept;
   6. per delivered source, after checking other owners' outstanding work, `akrogon close <id> --by "<chart> direct <sha>"`;
   7. broadcast-issue as sender when the repo configures broadcast, with the chart brief, pushed SHA and closed sources as context, and a failure does not reopen;
   8. `git worktree unlock <path>` then `git worktree remove <path>` verified by `git worktree list`, then `git branch -D <slug>` verified by empty `git branch --list <slug>`;
   9. `akrogon pack <chart>` when `<chart>/direct` holds a log, then the landed SHA into the `Direct attempt` section, then `Closed <date>`.
      The root checkout is never reset, and a failed local update is reported.

Repair bound: one round is B `fix` (or a blocking landing-check failure, which is only a failing known-red result or a judgment that disagrees with a pass, never a red with no cause in the diff), one door repair pass over all Fixes, and B's re-check of the repair diff. The bound is the repo's `fix_rounds` from `akrogon config`, with the count kept in `Direct attempt` so it survives session replacement. A passing last round lands. Exhaustion stops with the open Fixes listed, and the operator chooses one more round, lifecycle handoff, or abandon. Push attempts are not rounds.

Growth stop: stop coding and landing when a locked decision must change, a need eligibility excludes appears, a criterion cannot pass in scope after permitted repairs, or a second outcome appears. The door commits existing work as one partial-labelled commit so the tree is clean, keeps the worktree, updates `Direct attempt` (trigger, done, not done) and opens the trigger as a new fork. Continuations:

- lifecycle handoff: `git worktree unlock <path>` before the handoff because the command's `ensureWorktree` adopts the worktree as-is and leaf rules must be able to remove it later; the leaf slug equals the branch so the command's worktree setup adopts it, the leaf starts at its normal planning phase, the planner decides what to keep, and lifecycle review covers the whole diff;
- abandon: `git worktree unlock`, then branch and worktree removed, `akrogon pack <chart>` when `<chart>/direct` holds a log, then `Held <date>`.

No new direct attempt starts while a chart names a live direct branch.

## Autopilot

Autopilot is a non-default mode the operator switches on in words for one door session. The door session is the logical session, from the operator's first message in the door until the operator starts a new door run; it survives pass end while autopilot waits, replies, compaction and handovers to a same-session or fresh A, none of which asks the signposts again, and a chart resumed in a later door run takes that run's signposts, never a chart folder's earlier ones. Three modes, read from the operator's words with their scope rather than a fixed phrase: manual, the default, where the operator answers the signposts and every fork; autopilot, where the operator answers the signposts once and A answers every fork after; and full autopilot, "autopilot signposts", where A answers both. Words that delegate only the signposts while the operator keeps the forks match none of the three modes, so the door asks which mode is meant. While it is on, the door runs every step it runs today, and at each point where the operator would answer — fork rounds, the split proposal, the handoff review including seats — A writes the full round in its terminal, then answers it itself by the evidence, the session's signposts, and where they are silent the operator's values: simplicity, function over form, removing over adding, systems thinking, speed and price. A recommendation names the signpost that decided it. Each pick is recorded in the fork's Taken as A's, with its reason, the rejected options and any standing consultant dissent, never as operator words; this is the one exception to "Recommendations and silence cannot supply an operator answer" in questions.md, while approvals stay operator-only.

Autopilot starts only from the operator's words in the door's own terminal, at door start or later naming a chart; the words carry the mode, the handed work and the consultants or none. Outside hc the door says autopilot cannot start. The first reply echoes the mode, the handed work and the consultants, and says that handed-off work waits for the operator's watcher, which the door cannot check. After the door reads the handed work, the first reply previews the session's needs sheet: every foreseen supply and approval the charting will require, each with purpose and destination. The operator's words go verbatim into each handed chart's INTAKE.md, and a mode line goes into its CHART.md with the time, the door's hc address and A's transcript path; answers the operator gave before a mid-chart switch-on stay the operator's, and a session switched on mid-chart with no signposts yet asks the signposts round before A answers anything. Under autopilot the signposts round is a presented round, not a wait: no chart parks on it and no chart work starts before it is answered. Under full autopilot A answers the signposts too; its picks are echoed in the first reply, recorded as A's in `## Autopilot` (`signposts: A`), never as operator words, and may order the handed charts but never drop one — a drop A would make is recorded only, for the operator.

These make that chart wait while the door moves on within its handed list: a pending needs-sheet row — grant approval, fixture retention and secret-save approval, a missing need — asked only with the signposts round or a changed-list proposal, never mid-chart; a new-chart proposal, an operator approval that is not a grant; a mutating or paid proof call, which waits for the operator's grant approval while other read-only proofs proceed; and a human-only prerequisite. A late find that cannot continue inside recorded authority parks the chart with one terminal statement and one `akrogon notice --attention` per park (Take), a new-chart proposal's park sends the same one notice, and each `wait:` line names the row and its status. Existing checks still stop a handoff, and A repairs what they refuse. A step on main or a lesson write that would change autopilot's own switch or limits also waits for the operator. The door never turns autopilot on, extends the handed list, drops a handed chart, changes the consultants or raises an existing bound in the skill.

A handed chart parks for a new-chart proposal only when work found while charting it is its own destination with its own observable outcome, the handed chart cannot hand off without it, and no existing open leaf or chart already covers it, judged with the research the chart already did. Work the handed chart does not need stays recorded only, a dependency serving the same outcome stays a prerequisite leaf, and splitting expressly handed intake at the map stays A's. When an existing open chart already covers the found work, A writes no proposal: the waiting chart's `wait:` line names that chart, the chart resumes once that chart's leaves are written with the same ordering as after a yes, and A takes that chart next when it is on the handed list and runnable, otherwise moving to another runnable handed chart. A parks as soon as the proposal can be stated, with its findings recorded, and takes no further fork in that chart; nothing is created for the proposed chart — no folder, seed or file — before the operator's yes, the waiting chart's Destination does not change while it waits, and consultant agreement never answers the proposal. The proposal asks, fixed in form: "chart <X> on its own (yes) or bring it into <waiting chart> (no)?" A yes is the operator's words adding <X> to the handed list, recorded as a `changed list` mode entry: A charts <X> in the same autopilot run with the usual handover, and the waiting chart resumes after <X>'s leaves are written, handing off with `blocked-by` on them when the dependent leaf shares their destination repo. A no makes A resume the waiting chart with the found work in scope as forks or prerequisite leaves, rewriting the Destination under that answer and recording the operator's no verbatim; any other operator words stay a valid answer. When the waiting chart's dependent leaf has a different destination repo than <X>'s leaves, the waiting chart stays unhanded after <X> is handed off, with one `wait:` line naming every needed <repo>/<leaf> of <X> and its landed check — each named leaf folder under that repo's `issues/closed/` — and the operator's next message in the same door resumes it; there is no cross-repo `blocked-by` and no timer. Under autopilot the handed list wins over writing one chart folder per destination.

Under autopilot every handed chart takes the lifecycle route; the direct route is not offered. Drain takes only the handed list, with no oldest-chart or seed steps, and imports nothing new. A full match between a destination seed and handed work is A's to confirm; other seed matches, open-time close offers for skipped identities, and flaky tests or failed leaves outside the handed list are recorded only. Handed work is held when another door's open chart — a chart under the registered root's `issues/chart/` whose last marker is not `Handed off`, `Closed` or `Held` and whose latest A seat in `seats.yaml` has a different hc address — shares its chart folder, GitHub identity or legacy path, or shows the same outcome in its Destination. Two doors started on the same work at the same moment is a stated limit. A failed leaf the operator hands to the door is charted like other handed work.

A consultant is dropped for the rest of the session, never re-prompted, with its completed returns kept, when it stops a second time without its return file and report (questions `## Blind peer exchange`), when it blocks, errors or exits during an exchange, when its start fails or a send to it answers `started: false`, or when its restart fails (each seat whose restart failed is dropped with its printed result recorded under `consultant:`). A return file that arrives after the drop is ignored and recorded as ignored; a mistake in A's own call is repaired without dropping anyone. A consultant whose terminal is a consultant seat in another door's open chart is skipped the same way; the door's own charts never cause a skip.

The mode ends when every handed chart's last marker is `Handed off` or `Closed`. A chart waiting on a need, approval or prerequisite keeps the mode on, also across the end of a pass, and the operator's next message in that door — such as a supplied key — resumes it. Only the operator's words in the door's terminal turn it off early; supplying a key or changing the handed list keeps it on. Every mode change (on, off, changed list, "continue autopilot") is appended to the mode record with its time, and the door reads the latest entry before continuing: the same A transcript path continues after compaction, while a different or unknown path starts attended until the operator says "continue autopilot", which resumes the same handed list with lost consultants still lost. Once off, an open peer turn is collected first and the next question goes to the operator.

CHART.md records the mode record and the `## Autopilot` section per shapes.md, written as the pass goes. The pass ends with one line per chart in the door's terminal. The handoff footer says "handed off", not "started", and names a pause when `akrogon status` shows one. Nothing computes a score.

Under autopilot the handover fires only when switching to the next runnable handed chart, per `## Handover`: old A appends `handover <time> <log>: handed <remaining list>; consultants <surviving>; signposts <path>; instructions <verbatim with provenance and scope, or none>` to the mode record of every handed chart still open, and a folder it creates for the next chart carries INTAKE.md plus CHART.md with its mode record, where an attended switch creates the CHART.md with a pending Destination; both also carry the verbatim signposts copy per `## Handover`. The resume entry is `continue autopilot (handover <time>)`, after which fresh A continues the same handed list.

For a next chart whose folder old A creates for this handover, defer `seats.yaml` creation to fresh A, overriding Open's folder-creation rule. Fresh A creates that record on entry with `opened` and its first span's `from` set to its entry time, and its first A seat uses its transcript path. Existing charts keep their original `opened` time and append the new session as usual.

## Handover

A handover resets A's terminal into a fresh session for the next chart. It triggers when Drain moves on to a named next chart — the current chart handed off, closed, held, or waiting on an approval, need or prerequisite — after the outgoing chart's records are written, every consultant turn is collected and its span is closed; never at first entry, inside a chart, at a presented round or handoff review, after compaction, or at pass end.

Old A appends the handover entry `handover <time> <log>: attended next <chart>; consultants <surviving>; signposts <path>; instructions <verbatim with provenance and scope, or none>` to the next chart's Mode record, the mode line carrying A's hc address and transcript path — the reset log path, the next chart, the surviving consultants, the path of the session's signposts record so fresh A continues with it, and every conversation-only operator instruction still in force verbatim with its provenance and scope, or `none`. When the next chart has no folder, old A creates its CHART.md, holding `pending map by fresh A (<seed path, legacy path or operator note reference>)` under Destination plus the Mode record and no INTAKE.md, plus a verbatim copy of the session's `forks/signposts.md` naming the chart that holds the original — the one added file, an exception to "creates only its CHART.md" and to the autopilot folder contents — until fresh A writes the Destination after its map. As its last action old A runs `hc run --bg --no-notify --rm --no-parent -- sh -c 'log=$1; shift; exec bun "$@" >>"$log" 2>&1' sh <log> <skill-folder>/scripts/door-reset.ts <A address> <log> "<start prompt>"` from the registered repo root and ends its turn, `<log>` being `door-reset.log` in the next chart's folder, which exists by then; the shell sends everything the helper prints, its errors included, to `<log>`, so a helper that fails before or between its stages still leaves why there. The start prompt is plain text, never a slash command (codex rejects an unknown `/` command): `Run the chart-issues skill (<absolute skill folder>/SKILL.md): continue handover <time> door <A address> next <absolute chart folder>`.

The helper waits on hc events for A's turn to end, types the reset as keys into A's terminal (`/clear` for claude and agy, `/new` for codex and pi), then sends the start prompt, pressing enter once if it sits unsubmitted; each stage logs one line to `<log>`, and a stage that fails logs its result and stops. The helper confirms nothing after the reset: its `start-prompt` line means the prompt was sent, not that the reset worked. The session that receives the start prompt is the check.

Any session that receives a start prompt, before any other chart work, continues the handover only when the prompt names its address and next chart and matches the latest Mode entry, which must be an unconsumed handover, and its own transcript path from `bun <skill-folder>/scripts/transcript.ts <A address>` differs from the path on that entry; when the path is unknown (`-`) or equal to the entry's, it runs the script once more, and if that answer is the same it says `handover not continued: <unknown or same> transcript` and stops, leaving the entry unconsumed (a reset that did not happen lands the start prompt in the old conversation, which stops here). It appends `continue attended (handover <time>)`, records its A seat with its transcript path — a folder created for the handover holds no seats.yaml until fresh A writes it on entry — and opens its first span before chart work. Without that start prompt or when it does not match, a new session starts attended in no chart.

Operator input recorded in A's transcript after the helper started cancels the reset: `superseded` is logged and nothing more is sent. The helper reads the transcript once, after A's turn ended, since a submitted input is a record that stays. The input record per kind: a claude `user` entry or `queued_command` attachment with `origin.kind` `human`, a codex `task_started` or role-`user` `response_item` message, a pi role-`user` `message`, an agy user-input step (type 14) in its conversation database. Stated limit: text typed into A but not submitted is not seen.

Handover is supported for claude and agy (`/clear`), codex and pi (`/new`); every other kind and runs outside hc keep same-session behavior. Stated limit: a `/clear` or `/new` the operator types into a door or supplied consultant is not detected, so that seat's usage may count its old transcript until akrogon's next reset or restart. The modes differ only in the trigger and next-chart selection, the created folder's contents and the resume entry's name.

## Printed footer

End each door pass with the actual result and reason no automatic pass follows, printed rather than saved:

```text
Last operation: <what this pass wrote or observed>
Next: none <awaiting operator answer, dispatch, or named blocker>
```

The pass that queued a handover prints `Next: none handover queued to a fresh A in <A address>`.

The footer is printed only when the turn ends, and never while a prompted peer's turn is open.
