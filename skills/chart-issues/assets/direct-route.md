# Direct route

Read when the direct route is chosen.

Protocol, using the shapes in [shapes.md](shapes.md):

1. Attempt start: choose a slug, create the worktree with `git worktree add --lock --reason "<chart-folder> direct" <worktree_store>/<slug>` on branch `<slug>` from the destination's default branch, and write the `Direct attempt` section with the slug recorded.
2. Implement: the door itself runs `implement-issue direct chart=<chart-folder> worktree=<path>`, which writes `<chart>/direct/plan.md` and `<chart>/direct/report.md`.
3. B review: `hc send --json <B address> "check-issue direct slot=B chart=<chart-folder> worktree=<path> base=<sha> head=<sha> out=<chart>/slots/review-B-<n>.md. When the review file is written, run: hc send <door address> 'done B: <out path>'"`, with `n` = 1 for the initial review and the exact path named, sent only while B's last status under the asking rule in [questions.md](questions.md) is `idle` or `done`, and the door collects the review by that report and the out file under the exchange rules in [questions.md](questions.md). The Fix/Nit bar and verdict rules are check-issue's.
4. Repair rounds per the bound below.
5. Landing, after B returns ready or nits on a committed head:
   1. fetch, rebase onto `<remote>/<default_branch>`, refresh `AKROGON_BASE` from `akrogon config` in the worktree;
   2. conflict resolution sends B a focused re-check of the resolved range with the range-diff recorded, a clean rebase reruns checks only;
   3. `akrogon verify --holder <chart>/direct` in the worktree, which runs `checks` then `merge_checks` on a fresh checkout of the rebased head and writes the receipt direct-guards requires; on a red run the door retries that command once on the same head, judges the diff for a cause, and on a no-cause red runs `akrogon verify --holder <chart>/direct --known-red`, which reruns the head when no completed red head run exists and runs the base at the head's merge-base with the tracked default branch, skipping that base pass when the merge-base tree already holds a whole-green row — a green base never covers a red head, so it judges `fail` —, and the door reads the head and base logs of each red command for runner completeness and causal fit, meaning one of: the red command logged a real test name and that name also fails on the base; or the red command's log names no test on the head and on the base, and the door, having read both logs whole, finds that the head shows no failure the base lacks (judged in substance, never as exact text), that the command ended by its own verdict and was not killed, timed out or crashed, and that the diff holds no plausible cause; a command that ended by its own verdict with an ordinary error, a missing input or a load diagnostic is not excluded for naming no tests; when both logs exist but show too little to establish a cause, the door withholds agreement and the existing blocking path applies; in both cases the attempt's own done-criteria proofs must pass on their own, a cover never standing in for them; and the door records that judgment in `<chart>/direct/report.md` beside the kept logs; a check recorded `blocked` behind an agreed known-red is named as not run in `<chart>/direct/report.md` and never reported as passing; when the known-red judgment agrees for a configured command, or when, for a command outside `checks`, the attempt's own completed base run of the same command fails the same tests and the attempt holds that evidence, the door files that red through seed-issue's `## Lifecycle filing` section and records the created or found URL, or the failing command and its error, in `<chart>/direct/report.md`; a green retry (`inconsistent`), a disagreeing judgment, or a killed or incomplete base run is not filed as a base red; filing changes no verification status and adds no proof run; only a failing known-red result or a disagreeing judgment is a blocking landing-check failure;
   4. `bun <skill-folder>/scripts/direct-guards.ts <worktree> <repo-key> <chart-folder>` must exit 0, with `<skill-folder>` resolved as for chart-usage.ts, run only after the fetch and rebase above;
   5. `git push <remote> <sha>:refs/heads/<default_branch>` of the exact tested SHA, never force; a rejected push keeps the branch, and at most 2 push attempts are made, each with a fresh rebase, checks and B conflict re-check, then stop with the branch kept;
   6. per delivered source, after checking other owners' outstanding work, `akrogon close <id> --by "<chart> direct <sha>"`;
   7. broadcast-issue as sender when the repo configures broadcast, with the chart brief, pushed SHA and closed sources as context, and a failure does not reopen;
   8. `git worktree unlock <path>` then `git worktree remove <path>` verified by `git worktree list`, then `git branch -D <slug>` verified by empty `git branch --list <slug>`;
   9. `akrogon pack <chart>` when `<chart>/direct` holds a log, then the landed SHA into the `Direct attempt` section, then `Closed <date>`.
      The root checkout is never reset, and a failed local update is reported.

Repair bound: one round is B `fix` (or a blocking landing-check failure, which is only a failing known-red result or a judgment that disagrees with a pass, never a red with no cause in the diff), one door repair pass over all Fixes, and B's re-check of the repair diff. The bound is the repo's `fix_rounds` from `akrogon config`, with the count kept in `Direct attempt` so it survives session replacement. A passing last round lands. Exhaustion stops with the open Fixes listed, and the operator chooses one more round, lifecycle handoff, or abandon. Push attempts are not rounds.

Growth stop: stop coding and landing when a locked decision must change, a need eligibility excludes appears, a criterion cannot pass in scope after permitted repairs, or a second outcome appears. The door commits existing work as one partial-labelled commit so the tree is clean, keeps the worktree, updates `Direct attempt` (trigger, done, not done) and opens the trigger as a new fork. Continuations:

- lifecycle handoff: `git worktree unlock <path>` before the handoff because the command's `ensureWorktree` adopts the worktree as-is and leaf rules must be able to remove it later; the leaf slug equals the branch so the command's worktree setup adopts it, the leaf starts at its normal planning phase, the planner decides what to keep, and lifecycle review covers the whole diff;
- abandon: `git worktree unlock`, then branch and worktree removed, `akrogon pack <chart>` when `<chart>/direct` holds a log, then `Held <date>`.

No new direct attempt starts while a chart names a live direct branch.
